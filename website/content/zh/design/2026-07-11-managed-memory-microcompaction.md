# 托管内存的 Microcompaction 保留

## 问题

托管内存的 topic 文件通过 `read_file` 惰性加载。Microcompaction 目前将这些结果当作普通工具输出处理，并用 `[Old tool result content cleared]` 替换较早的内容。内存索引仍然可用，近期的修复也让之后的 `read_file` 能再次返回真实字节，但无法保证活跃模型会注意到它必须重新加载内存。

Issue #6487 还报告了 `/remember` 之后索引过期的问题；PR #6497 已经负责处理那部分。本设计只解决被 microcompaction 移除的托管内存内容。

## 选定的设计

添加一个窄口径的 `MicrocompactOptions` 回调，用于识别那些成功结果必须被保留的 `read_file` 路径。在构建空闲、强制或基于大小的清理计划之前，microcompaction 会将每个响应与其请求侧的 `file_path` 关联，并将受保护的结果从可压缩集合中移除。其他工具、普通文件读取、错误，以及无法解析路径的响应，保持当前行为。

所有生产 microcompaction 入口都提供同一个谓词：

- 发送前的空闲和基于大小的压缩
- `/compress-fast`
- 内存压力下的历史压缩

该谓词使用感知 realpath 的包含关系来识别项目、用户和团队的托管内存根目录。逃逸出托管根目录的符号链接不受保护。

## 为什么选择这一层级

把每个已加载的内存正文注入系统指令会使内存永久占用上下文，并会取代现有的索引加惰性读取设计。在完整压缩后重新附加每个内存文件需要单独的 token 预算和恢复策略。只保留托管内存读取不被 microcompaction 清除，能够以有界的改动直接修复复现出的清除行为，并把完整压缩保留为现有的硬性上下文削减边界。

因此完整压缩有意不保留字节。它的摘要能看到压缩前的内存内容，`MEMORY.md` 索引保留在系统指令中，文件读取缓存会被清空，使模型可以重新加载精确字节。此变更只保证在 microcompaction 过程中的保留。

## 风险与测试

对托管内存文件的重复读取可能会保留多份副本，直到完整压缩为止。这是有意的取舍：持久的指引比回收那些工具结果 token 更重要，而完整压缩仍然作为硬性上限可用。

测试覆盖项目、用户和团队根目录；普通读取；符号链接逃逸；空闲、强制和基于大小的路径；受保护与可压缩结果混合；歧义或缺失的响应 ID；以及逐出元数据。
