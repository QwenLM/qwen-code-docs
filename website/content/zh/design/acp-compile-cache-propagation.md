# ACP 编译缓存传播

## 背景

生产环境的 `cli-entry.js` 包装器已经为进程内的 `serve` 快路径启用了 Node 的模块编译缓存。守护进程随后通过 `createSpawnChannelFactory()` 派生 ACP 子进程，但 `module.enableCompileCache()` 只影响当前进程，并不会填充 `NODE_COMPILE_CACHE`。因此，除非运维人员在启动 Qwen Code 之前设置了该环境变量，否则 ACP 子进程启动时没有缓存可用。

这就是 #7264 上记录的 orthogonal compile-cache 候选项。它不会缩小急切加载的模块图，而是在惰性加载工作完成后，对剩余的模块图复用 V8 代码缓存。

## 目标

- 让生产环境的 ACP 后代进程复用守护进程入口包装器已启用的编译缓存目录。
- 保留运维人员提供的 `NODE_COMPILE_CACHE`。
- 保留 `NODE_DISABLE_COMPILE_CACHE=1`。
- 让缓存失败保持为静默的优化失败，而不是应用故障。
- 避免改动 ACP 桥接、配置或会话生命周期。

## 非目标

- 不引入 Qwen 特有的缓存位置、淘汰策略或清理命令。
- 不在 JavaScript API 不可用的 Node 版本上强行支持编译缓存。
- 不从守护进程或 ACP 生命周期中冲刷缓存。
- 不全局改变测试或覆盖率环境。

## 启动拓扑

生产环境的守护进程路径是：

1. `cli-entry.js serve`
2. 守护进程中调用 `module.enableCompileCache()`
3. 进程内导入打包后的 CLI
4. `createSpawnChannelFactory()` 复制 `process.env`
5. 新的 Node 进程在启动期间读取 `NODE_COMPILE_CACHE`
6. 子进程以 `--acp` 运行所选的 CLI 入口（默认为 `cli.js`，或在显式配置时使用 `QWEN_CLI_ENTRY`）

如今步骤 2 只让守护进程受益。步骤 4 复制的环境里没有编译缓存目录，所以步骤 5 和 6 中的子进程不会启用缓存。

## 提议的改动

捕获现有 `module.enableCompileCache()` 调用的结果。当它报告新启用了缓存、暴露了一个目录、且运维人员没有提供 `NODE_COMPILE_CACHE` 时，把该目录发布到 `process.env` 中。现有的子进程构建逻辑已经会复制环境，因此不需要改动 ACP 层。

不要覆盖已有的环境变量值。当 Node 是从已有的环境变量启用缓存时，它会报告已启用状态，原始的基目录必须保持原样。用 `getCompileCacheDir()` 或已启用结果替换它，可能会在后代进程中产生嵌套的版本目录。

启用失败、被禁用或 API 不可用时，不要合成目录。这些情况保持当前行为。

## 考虑过的替代方案

### 在 `spawnChannel` 中设置环境变量

否决。编译缓存的归属是进程级的全局入口行为，而 `spawnChannel` 是被嵌入式宿主使用的共享 ACP 基础设施。把策略放到那里会扩大架构面，并重复 Node 引导行为。

### 在 `QWEN_HOME` 下设置带 Qwen 版本号的缓存

否决。Node 已经会隔离不兼容的 Node 版本，并按模块内容为条目建立索引。Node 推荐使用其临时目录默认值，以避免陈旧缓存堆积。一个持久化的 Qwen 专用缓存需要新的清理、权限和生命周期策略，却没有证据表明它能改善被测路径。

### 无条件导出 `getCompileCacheDir()`

否决。当缓存是从已有环境变量启用时，报告的目录已经是特定 Node 版本的。把它作为下一个进程的基目录会再造一个嵌套版本目录，妨碍预期的共享。

## 失败与兼容性行为

- Node 没有 `enableCompileCache()`：不改动环境，无行为变化。
- `NODE_DISABLE_COMPILE_CACHE=1`：Node 报告已禁用；不传播任何目录。
- 运维人员提供的 `NODE_COMPILE_CACHE`：原样保留并正常继承。
- 不可写或其他无效的缓存目录：Node 报告失败但不抛异常；Qwen Code 继续运行但不使用缓存。
- Node 或 Qwen 升级：Node 会隔离不兼容的运行时版本，源码内容变化会产生不同的缓存条目。
- 覆盖率：生产快路径是唯一的改动点。单元测试运行器不会全局启用编译缓存。
- 关闭：Node 在正常进程退出时写入累积的代码缓存。强制终止可能丢失新生成的条目，但不影响正确性。

## 验证

可行性在实现之前就用同一个发布包对两个变体进行了门禁验证。两个守护进程变体接收同样的热父进程缓存。对照组在导入包之前移除缓存环境变量，因此 ACP 后代进程保持无缓存；候选组在导入之前发布相同的基目录，因此 ACP 后代进程继承它。

2-vCPU 参考主机上的门禁覆盖：

- 30 次交替成对的冷守护进程启动
- 30 次交替成对的预热启动
- `channel.initialize`、进程到首个会话、监听器就绪、峰值 RSS
- 一个热的第二个会话
- 并发的首个会话
- 遥测启用与禁用
- 旧版单会话行为
- 空缓存首次使用、热缓存复用、缓存占用、残留进程

只有当子进程专属的热缓存对比显示出可重复的初始化或进程到会话收益、且没有功能回归时，才继续实现。

## 验证结果

门禁在 2-vCPU、4-GB 的 Linux x64 主机上用 Node.js 22.23.1 运行。对照组和候选组使用 `77af061e` 的同一个包，唯一差别是 ACP 子进程是否继承父进程的编译缓存目录。

在 30 次热缓存成对运行中，候选组赢得了每一次 `channel.initialize` 对比。其成对中位数改进为 176.6 ms，bootstrap 95% 置信区间为 167.7–186.2 ms。成对的进程到首个会话中位数改进为 199.0 ms，95% 置信区间为 177.6–226.5 ms。候选组的进程树峰值 RSS 中位数高出 8.6 MB。

额外的一次 10 对确认使用 `origin/main` 上未修改的生产入口作为对照组，打补丁后的生产入口作为候选组。它复现了 181.6 ms 的 `channel.initialize` 中位数改进和 189.4 ms 的进程到首个会话中位数改进。

在 20 对独立的空缓存运行中，首次进程到会话运行的中位数慢了 117.2 ms，95% 置信区间为 69.3–130.9 ms。因此第二次 ACP 启动在被测负载下收回了一次性的生成成本。稳定后的缓存包含 362 个文件，占用 9.4 MB。

所有被测运行都成功完成且无残留进程。候选组还通过了并发首会话创建、禁用遥测的启动和旧版单会话行为。
