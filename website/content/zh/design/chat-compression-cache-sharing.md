# 聊天压缩缓存共享

## 背景

聊天压缩目前会发送一个冷的侧查询：使用专门的系统指令、不带主会话的工具声明、并使用对话的去媒体精简副本。对于 prompt 缓存键以工具和系统指令开头的提供方，无法复用主会话已缓存的前缀。

## 设计

当以下所有条件都为真时，压缩首先尝试一次专门的单轮请求：

- 压缩模型就是当前的主模型；
- 活动提供方是 Anthropic 或 DashScope 且启用了缓存控制；
- 聊天有提供方报告的 prompt 令牌数可用于锚定估算；
- 有效 prompt 令牌数加上有界的压缩输出预留能够装入模型的上下文窗口。

该请求使用当前轮次的有效 generation 配置（包括子代理使用的按请求工具覆盖），以及完整的整理后历史（包括媒体）。发送请求时应用常规的模型模态过滤，因此受支持的媒体保持不变，不受支持的媒体使用与其他模型请求相同的占位符。现有的压缩指令作为最后一条用户消息追加。
没有任何东西会消费或执行该请求中的函数调用。包含函数调用的响应、空响应、畸形的状态快照或请求错误都会被丢弃，并通过现有的冷侧查询重试一次。其去媒体精简输入只在该回退被需要时才惰性构建。取消不会触发回退。

使用当前的 `GeminiChat` 让请求保持在实时会话范围内。有意不使用进程级全局 fork 缓存，因为它只保留较短的历史尾部，且可能属于另一个并发会话。

使用独立压缩模型的会话保持走现有路径，因为它们的缓存标识与主会话不同。带媒体的历史优先使用共享路径，这样未变的面向提供方的前缀可以复用主会话的缓存。

## 验证

单元测试断言精确的系统、工具、完整历史和尾部指令的构建；提供方/模型门控；共享路径上的媒体保留；窗口预检；回退后的媒体精简；工具调用和畸形响应的回退；以及取消行为。提供方测试应对比主轮次与压缩请求的序列化请求前缀和缓存令牌用量。
