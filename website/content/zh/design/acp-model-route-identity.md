# ACP 模型路由标识

## 问题

Qwen Code 目前把 ACP 模型 ID 暴露为 `modelId(authType)`。因此，两个配置了相同模型 ID 和认证类型、但 `baseUrl` 不同的模型会坍缩成同一个 ACP 选择器。客户端无法识别活动行，也无法把一次选择往返送达预期的端点。

Core 已经把 `(authType, modelId, configured baseUrl)` 当作注册表标识。标识丢失只发生在它跨越 ACP 边界时。配置值必须与解析后的端点保持分离，因为提供方默认值可能在注册之后才填充 `baseUrl`。

## 设计

从现有的已配置模型列表构建 ACP 模型选项：

- 当 `modelId(authType)` 唯一时保留它。这让常规情况下保留现有 ID。
- 当多个选项会共享该 ID 时，把每个都替换为确定性的 `qwen-route:v1:<digest>` 选择器，摘要由非机密的模型元数据和公开的端点标识（去除凭据、query 和 fragment）派生。
- 拒绝清洗后仍无法区分的路由，而不是使用数组顺序——配置重排序后数组顺序可能让旧选择器重新映射到别处。
- 继续用 `ModelInfo.name` 和提供方元数据做展示。路由 ID 是一个不透明的机器选择器。

Core 把原始的可选注册表 `baseUrl` 与解析后的展示端点一并暴露。同一个选项构建器为 ACP 会话模型、配置选项、实时提供方状态和守护进程工作区提供方状态供货，让每个客户端看到相同的 ID，而服务端保留精确的注册表判别符。

在 `session/set_model` 时，Qwen Code 在切换前先用当前已配置模型列表解析选择器。它把解析出的 `baseUrl` 传给 Core，然后只持久化规范的设置值：

- `model.name`：实际模型 ID
- `model.baseUrl`：配置的注册表端点，或表示隐式默认值的空墓碑
- `security.auth.selectedType`：实际认证类型

不透明选择器永远不会写入 `settings.json`。

## 兼容性

- ACP schema 不变；`modelId` 仍是字符串。
- 唯一的现有模型 ID 保留当前的传输表示。
- 旧式 `modelId(authType)` 请求仍被接受。如果此类 ID 有歧义，为兼容性保留现有的首次匹配行为；新广播的选择器是精确的。
- 未知或过期的不透明选择器会被拒绝，而不是被当作字面模型 ID。
- 通用 ACP 客户端（包括 Zed）只需回显不透明选择器。
- CLI TUI 的设置和选择行为不变。

## 验证

- 重复路由获得各不相同、稳定的选择器，且不泄漏其 URL。
- 会话模型状态和配置选项发布相同的选择器以及精确的当前路由。
- 选择第二条路由会带着其 `baseUrl` 切换、持久化规范设置，并以其不透明选择器通知客户端。
- 守护进程提供方状态为 Web Shell 识别出精确的当前路由。
- 唯一模型和旧式模型的选择继续可用。
