# Goal loop 输入控制

## 问题

一个激活的 `/goal` 被实现为一个阻塞的 Stop hook。当模型正在运行时，交互
队列通常会将斜杠命令推迟到流变为空闲时才处理。goal 循环可能永远到不了
那个空闲边界，因此 `/goal clear` 和替换用的 `/goal` 命令无法生效。

Stop 响应还可能将 goal hook 与不相关的已配置 hook 聚合在一起。清除 goal
不得丢弃由其他 hook 拥有的阻塞决策。

## 设计

在激活的轮次期间，消息队列会将 `/goal` 命令与纯文本 steering 消息一起
排空（drain）。其他斜杠命令保持排队，等待正常的空闲处理。

CLI 通过现有的斜杠命令处理器执行被排空的 goal 命令：

- Clear 命令应用其副作用，但不产生模型输入。
- 替换命令替换挂起的 goal 指令。
- 当多个 goal 命令被一起排空时，只发送最终激活 goal 的指令。
- 幸存的指令保持其相对于纯文本 steering 消息的位置。
- 如果后续的 steering 准备被取消，已执行的 goal 命令不会被恢复；未执行
  的纯文本消息会被恢复。

Core 在 Stop hook 之前对队列采样一次，并在阻塞的 Stop hook 返回后再次
采样。阻塞的 goal 输出携带其 goal hook ID，并使其续接原因与普通 hook
原因保持分离。hook 桥还报告是否有其他 Stop 输出正在阻塞。如果 goal 在
第二个边界发生变化，core 只移除旧 goal 的续接；它仍会遵循独立的阻塞
原因。非阻塞的 hook 输出不会强制产生额外的 goal 迭代。

## 验证

- 队列测试覆盖激活轮次的 goal 排空和空闲边界推迟。
- CLI 流测试覆盖 clear、替换、批量命令、顺序和恢复行为。
- Core 测试覆盖 Stop hook 求值期间的 clear 和替换，包括聚合的独立阻塞者。
- 本地 tmux 会话针对构建出的交互式 CLI 演练 clear 和替换。
