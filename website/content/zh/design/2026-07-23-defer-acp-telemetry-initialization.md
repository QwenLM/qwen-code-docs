# 把 ACP 遥测初始化推迟到协议初始化之后

- **Issue**: #7264 候选 2
- **Scope**: 遥测启用的 ACP 子进程启动
- **Status**: 已实现并验证

## 问题

ACP 子进程目前从 `Config` 构造函数启动遥测。该调用是 fire-and-forget 的，但加载和求值遥测实现及配置的 exporter 链仍然会与 CLI 引导、ACP 模块加载、引导配置初始化和协议 `initialize` 处理器竞争同一个事件循环和 CPU。在受限主机上，候选 1 的测量显示这种竞争把工作加回到了用户可见的初始化窗口中。

遥测事件已经使用初始化门控：在 SDK 完成启动之前发出的事件会被丢弃。因此推迟启动是延长一个既有的丢失窗口，而不是引入新的缓冲或排序模型。

## 设计

ACP 配置设置现有的 `deferTelemetryInitialization` 选项。这会抑制构造函数的 fire-and-forget 启动，而不改变默认、无头模式、stream-JSON、交互式 TUI 或 daemon 运行时路径。

`runAcpAgent` 使用其 NDJSON transport 上现有的消息观察 hook，记住传入 `initialize` 请求的 JSON-RPC ID。该 hook 在解析后的请求入队之后、但其挂起的读取延续能够处理它之前运行。对于传出消息，同一 hook 只在编码后的响应成功写入底层 stdout 流之后运行。当观察到一个携带被记住 ID 的成功响应时，子进程通过现有的单飞门面启动遥测，只在该初始化落定之后注册其事件循环 gauge，并清除被记住的 ID。这个顺序是必需的，因为如果在 SDK 安装全局 meter provider 之前注册 gauge，metrics API 会缓存一个 no-op meter。

这创建了一个由 transport 定义的边界：遥测加载不可能在初始化响应写入解析完成之前开始。它不依赖事件循环调度假设。

## 所有权与下游消费方

ACP 子进程拥有一个进程全局的遥测 SDK 和一个引导 `Config`。延迟选项是配置作用域的，而最终的初始化器是进程全局且单飞的。每会话的配置继续共享该进程全局 SDK，不拥有独立的遥测运行时。

受影响的消费方是：

- **ACP 引导子进程**：从构造函数启动遥测改为响应写入启动遥测。其事件循环 gauge 注册移到 SDK 初始化之后，因此早期注册不会永久禁用所有指标。
- **ACP 会话创建和提示**：保留现有的初始化门控；在 SDK 加载完成之前，非常早的事件现在可能被丢弃得更久。
- **普通交互式 TUI**：保留通过 `startPostRenderPrefetches` 的首次渲染后启动。
- **无头模式和 stream-JSON CLI**：保留构造函数启动。
- **`qwen serve` 父级/daemon 运行时**：保留其显式延迟的核心运行时初始化和关闭。
- **进程退出清理**：保留 `Config.shutdown()`。在成功的协议初始化之前断开的子进程从不启动遥测。如果断开与刚启动的导入竞争，初始化器内部的 catch 会防止未处理的 rejection，ACP 外层路径仍然退出进程。虽然 `shutdownTelemetry()` 可以 await 一个进行中的初始化器，但 `Config.shutdown()` 只在 SDK 报告已初始化之后才调用它，因此当前的配置清理可以跳过仍在进行中的初始化。

## 失败与兼容行为

- 遥测禁用在响应之后仍然是门面空操作，不加载任何重型遥测模块。
- 在响应之前发出的一次性引导事件，包括初始的 `qwen-code.auth` 事件和一个早期的 `qwen-code.config` 事件，将从 ACP 遥测中永久缺席，而不仅仅是延迟。这是把 SDK 初始化移到响应之后所接受的成本；本变更不合成或缓冲替代事件。
- 格式错误或被拒绝的 `initialize` 请求不启动遥测。之后一个有效的 initialize 请求仍然可以启动它。
- stdout 写入失败不会运行已发送消息 hook，因此不会为客户端未收到的响应启动遥测。
- 重复或无关的 JSON-RPC 响应无法启动遥测，因为请求 ID 和成功响应形态必须都匹配；被记住的 ID 只被消费一次。
- SDK 加载保持 fire-and-forget 和尽力而为。其现有实现会捕获导入、组装和启动失败。
- 不改变协议形态、能力、认证时序、provider 选择、MCP 行为或遥测配置面。

## 已拒绝的备选方案

- **在 `QwenAgent.initialize()` 内部启动**：这在处理器返回之前，因此在 SDK 能够序列化或写入响应之前。
- **在处理器返回后使用 `queueMicrotask`、`setImmediate` 或定时器**：都无法证明 SDK 私有的写入队列已完成，而且定时器会引入任意的延迟策略。
- **包装或 fork `AgentSideConnection`**：没有必要，因为包本地的 NDJSON 流已经暴露写入后的消息观察。
- **等到第一个会话响应**：可能移除更多竞争，但会把丢弃事件的窗口扩大到超出候选 2 的范围，并且永远不会为一个空闲的已初始化 channel 初始化遥测。
- **缓冲早期遥测**：实质性地改变遥测语义和内存所有权；候选 2 明确接受丢弃早期事件。

## 验证

单元测试覆盖 ACP 配置延迟和确切的 transport 顺序：接收时不启动、无关响应、错误响应或写入失败时不启动；在匹配的成功响应写入后启动一次。现有的 transport 测试证明已发送 hook 在底层写入之后运行，并在写入被拒绝时被跳过。

发布 bundle 通过真实的 ACP 父/子路径在遥测启用和禁用下演练。兼容性检查覆盖冷通道和预热通道、并发首 session、旧版单会话模式、早期断开、清理和 outfile 记录产出。

该变更只有通过 #7264 的 2C4G 门禁才会落地：30 次交替配对串行冷启动，报告 `channel.initialize`、子进程到 initialize 响应、冷会话请求、process 到首个 session、峰值 RSS、预热行为和遥测开/关兼容性。由于工作是移后而不是消失，门禁必须同时报告初始化和首 session 的时序；一个仅在首个 session 之前被偿还的收益不视为成功的优化。

## 结果

对照组是 `origin/main`（`14f1f2bb365280a6e1d4a45b452f7992f1928187`）；候选组是同一 commit 加上这个确切的工作树变更。两个发布 bundle 都从同一个 lockfile 构建，并在提供的 2 vCPU、约 3.5 GiB RAM、无 swap、捆绑 Node.js 22.23.1 的 Linux 主机上测试。

在 outfile 遥测启用的情况下，30 次交替配对冷启动产生了：

| 指标                                 | 对照组 P50 / P95     | 候选组 P50 / P95      | P50 差值     |
| ------------------------------------ | -------------------- | --------------------- | ------------ |
| `channel.initialize`                 | 942.1 / 1245.0 ms    | 898.3 / 1002.4 ms     | **-43.8 ms** |
| 子进程到 initialize 响应             | 947.0 / 1249.8 ms    | 903.0 / 998.4 ms      | **-43.9 ms** |
| 冷 `POST /session`                   | 1235.5 / 1591.7 ms   | 1245.1 / 1462.0 ms    | +9.6 ms      |
| Process 到首个 session               | 1833.1 / 2190.6 ms   | 1845.5 / 2417.0 ms    | +12.4 ms     |
| 峰值 RSS                             | 418.7 / 443.6 MiB    | 406.7 / 438.4 MiB     | -11.9 MiB    |

配对分布显示 `channel.initialize` 在 30 对中有 26 对更快，配对中位数差值为 -44.2 ms。冷会话请求和 process→首个 session 的配对中位数差值分别为 +15.0 ms 和 +13.8 ms，候选组分别在 13/30 和 11/30 对中获胜。Process→首个 session 的配对中位数 bootstrap 95% 区间为 -2.8 到 +27.5 ms，因此本次运行既未确立端到端回归，也未确立改善。因此本变更只声称直接的 ACP 初始化边界收益。

在同一次运行的 30 对预热阶段，`channel.initialize` 从 950.5 / 1323.7 ms 改善到 908.4 / 964.4 ms P50/P95。已预热的会话请求从 82.1 / 94.8 ms 变为 83.7 / 131.6 ms，而 process→session 从 3683.5 / 4105.0 ms 变为 3686.1 / 3749.2 ms。配对的 session 和 process→session 中位数分别为 +1.4 ms 和 +1.0 ms。两个孤立的候选组 session 离群值和若干对照组初始化离群值放大了非配对的 P95 值；配对中位数保持中性。不声称预热内存有任何变化。

候选组功能运行通过了并发首 session、遥测禁用零记录和旧版单会话模式。全部 120 次遥测启用的基准运行都报告了有效的启动 profile 和非空的 outfile，每次运行都退出且无残留进程。一次通过官方 ACP 客户端的发布 bundle 冒烟测试还额外等待超过指标导出间隔，并确认了 `qwen-code.session.count` 和 `qwen-code.acp.event_loop.lag` 两者，防止注册到缓存的 no-op meter。两次针对可用 OpenAI 兼容端点的遥测启用实时提示冒烟都完成并产出了非空的遥测 outfile。直接的捆绑 ACP 冒烟测试还通过了两个早期断开边界：initialize 之前的 EOF 干净退出且未启动遥测，而成功 initialize 响应之后的 EOF 在创建 outfile 之后干净退出，两种情况下都没有 stderr 输出。
