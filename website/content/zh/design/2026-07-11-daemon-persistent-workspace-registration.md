# 持久化的 daemon 工作空间注册

## 目标

当 daemon 以相同的主工作空间和 `QWEN_HOME` 重新启动时，从 Web Shell 添加的工作空间能够在 `qwen serve` 进程重启后继续保留。

## 状态归属

动态工作空间注册属于用户私有的 daemon 配置，不是项目配置，也不是一次性的运行时输出。注册信息存储在：

```text
${QWEN_HOME:-~/.qwen}/daemon/workspaces/<primary-scope-sha256>.json
```

scope 哈希是规范化主工作空间路径的完整 SHA-256（在 Windows 上转为小写）。文件中会重复写入主路径，这样不匹配或损坏的 scope 会被拒绝，而不是被静默应用。

```json
{
  "schemaVersion": 1,
  "primaryWorkspace": "/repo/main",
  "workspaces": ["/repo/service-a"]
}
```

只存储规范化的次级路径。信任、环境、工作空间 id、会话和运行时错误都在每次 daemon 启动时重新推导。

## 生命周期

生产 daemon 在解析并规范化主工作空间之后读取这个小型注册文件。有效的存储路径会在显式 `--workspace` 输入之后合并。显式输入具有权威性：格式错误或不可用的显式路径仍然是启动错误，而不可用的存储路径会被跳过并附带警告，同时保留在磁盘上供之后的重启使用。

恢复的路径会在 `WorkspaceRegistry` 和 Express/ACP 表面组装之前进入常规的次级运行时构建循环。这使得能力、工作空间限定的 ACP 挂载、状态聚合以及默认的总会话数上限与恢复后的运行时集合保持一致。

对于应用组装之后的进程内新增，只要注册表存在，工作空间限定的 ACP 路由就保持挂载状态，并在首次使用时惰性创建受信任的次级挂载。这避免了启动时的单工作空间快照导致之后的 Web Shell 注册在重启之前不可用。

`POST /workspaces` 接受 `persist: true`。在注册文件更新成功完成之前，不会确认成功的持久化请求。对已经活跃的工作空间重复发起持久化请求会提升或确认其存储的注册，并以幂等方式成功。省略 `persist` 的现有调用方保持当前的进程内行为。

`GET /workspace-registrations` 暴露期望的存储集合以供管理。`DELETE /workspace-registrations/:id` 会遗忘一个存储的注册；活跃的运行时在重启之前保持存活。主工作空间永远无法通过该表面被存储或遗忘。

## 安全与失败行为

- 存储有上限：最多 24 个次级路径，每个不超过 daemon 的工作空间路径长度限制。
- 读取时拒绝符号链接、非常规文件、超大文件、格式错误的 JSON、未知的 schema 版本以及主 scope 不匹配。
- 写入使用进程内互斥锁、跨进程锁以及共享的原子文件写入 helper，权限模式为 `0600` 且不跟随符号链接。
- 变更路径绝不把损坏的存储当作空存储处理，防止之后的添加覆盖可恢复的数据。
- 有意不持久化信任；恢复的工作空间会经过当前的受信任文件夹计算。
- 缺失、不可访问、嵌套或超出活跃上限的存储条目会被跳过，而不会删除期望的条目。重复条目会使存储无效，且绝不会被隐式重写。

## 兼容性

增量的 `persistent_workspace_registration` 能力宣告了新契约。SDK 请求选项和 `persisted` 响应字段都是增量的。`runQwenServe` 拥有自动启动恢复。直接的 `createServeApp` 嵌入只有在显式提供注册存储时才会获得持久化管理路由，并且仍然负责在应用创建之前恢复其注入的工作空间注册表。

## 后续边界

热移除仍然是独立的部分：遗忘注册只影响下一次重启，不会终止会话或销毁活跃的工作空间 bridge。
