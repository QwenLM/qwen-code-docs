# Shell 超时错误语义

## 问题

前台 Shell 命令目前以文本描述超时，但返回成功的 `ToolResult`。因此下游代码将该调用记录为成功，发送带 `output` 字段的 function response，并且即使命令没有完成也可能渲染成功指示器。在超时之后到达的取消还可能覆盖原始原因。在 PTY 发现期间，已中止的调用仍可能启动进程，因为执行服务要到启动之后才观察该信号。

## 结果契约

Shell 自身的前台超时返回 `ToolErrorType.EXECUTION_TIMEOUT`。结果使用三个有意分离的通道：

| 通道            | 受众                                    | 超时内容                                                                                       |
| --------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `error.message` | hook、遥测、span、日志、告警            | 仅简短的超时摘要                                                                               |
| `llmContent`    | 模型 function response                  | 超时摘要、部分输出或显式的无输出说明，以及任何截断指针                                         |
| `returnDisplay` | 交互式历史和 ACP 客户端                 | 超时摘要、部分输出或无输出说明，以及任何截断指针                                               |

调度器将超时的 `llmContent` 转换为一个 function response，其 `response` 带有 `error` 字段而没有 `output` 字段。失败 hook 的附加上下文会一次性追加到该面向模型的错误中。顶层的 `ToolCallResponseInfo.error` 保持简短的运维摘要，使命令输出不会被复制到遥测或 hook 错误参数中。

其他软工具错误保留其现有的 Core 调度器行为。ACP 和 speculation 执行一致地使用错误信封编码所有软错误，因为这些路径直接调用工具，否则没有调度器的分类步骤。

## 第一原因规则

`AbortSignal.any()` 保留第一个中止的信号的原因。Shell 分类只在执行之后读取合并信号的原因：

- `TimeoutError` 加上已中止的执行是超时。
- 后台提升（background-promote）原因加上已中止且未提升的执行，是现有的 promote-refused 竞争。
- 其他任何已中止的执行是取消。
- 首先发生的超时不会被之后的用户取消或提升请求改变。
- 首先发生的取消或提升请求不会被之后的超时改变。

Core 调度器有第二个可选的全局执行计时器。工具返回的结构化超时即使父信号在调度器消费结果之前已中止，也仍然是超时。当调度器自己的计时器提供超时结果时，只有在计时器触发时父信号尚未中止，它才获胜。父取消之后计时器对不合作的工具触发，仍然保持已取消。

ACP 对结构化工具超时应用相同的规则：即使其父信号之后被观察到已中止，超时也是错误而不是中断。抛出的异常继续使用实时中止状态。

## 启动行为

`ShellExecutionService.execute()` 在其信号已中止时立即返回一个已中止、无进程的句柄。PTY 发现用 `getPty()` 与信号竞争，并在竞争之后移除其临时监听器。如果中止获胜，之后的 PTY 解析或拒绝会被消费掉，而不会启动 PTY，也不会回退到 `child_process`。返回的结果使用 `executionMethod: 'none'` 且没有 pid。

该行为影响仓库内该服务的所有消费者：前台和后台 Shell 管道、用户 `!` Shell、prompt 命令注入、ACP 桥接 shell 处理，以及 git 归因探测。唯一的行为变化是已中止的请求不再启动进程。

## 消费者行为

| 消费者                              | 超时行为                                                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Core 调度器                         | `status: error`，简短的顶层错误，详细的 `response.error`，超时失败类型                                             |
| ACP 会话                            | 失败的工具更新，模型历史和记录中的详细错误信封，简短的运维元数据                                                   |
| speculation 执行                    | 详细错误信封；被接受的 speculation 历史渲染 Error                                                                  |
| Anthropic 适配器                    | `tool_result.is_error: true`                                                                                       |
| OpenAI 兼容适配器                   | 显式的详细错误文本；协议层不存在错误位                                                                             |
| JSON 和 stream-json                 | `is_error: true`，优先使用详细的嵌套错误内容而非简短摘要                                                           |
| 上下文估算和批次预算                | `response.output` 和 `response.error` 文本都会计数；超大错误在卸载时保留 error 键                                  |

microcompaction 继续不触碰失败的工具结果。完整的聊天压缩现在能看到详细的错误大小，并能在正确的预算下触发。

## Claude Code 对比

Claude Code 将命令超时视为失败的工具结果，为模型和用户保留终止前产生的输出，并在 Anthropic 协议中将工具结果标记为错误。本设计采纳这些可观察的属性，同时保持 qwen-code 现有的 `ToolResult` 形状和遥测约定。它不会将命令输出复制到简短的运维错误通道中。

## 兼容性与可观测性

这是一次有意的线级（wire-level）修正。ACP 和 speculation 软失败从 `{ output }` 变为 `{ error }`；Core 仅对 `EXECUTION_TIMEOUT` 改变该形状。超时计数从成功指标转移到错误/超时指标，失败 hook 取代成功 hook。没有 schema、错误枚举、超时默认值、迁移或推广标志的变化。

部分命令输出可能包含敏感数据。它仍然可被模型、交互式结果、聊天记录和显式 JSON 输出获取，与分类修正之前一致。它不会被添加到 hook 错误参数、顶层错误、span 结果属性或运维日志摘要中。现有的截断和溢出到磁盘的限制适用于详细的模型通道。

## 不在范围内

- 心跳或周期性进度报告
- Todo 停止守卫或提示词变更
- 非零退出码语义
- 外部信号终止语义
- 后台 Shell 超时
- 全局调度器计时器获胜后等待部分输出
- 新的超时设置或协议字段
