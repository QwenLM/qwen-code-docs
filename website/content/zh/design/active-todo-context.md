# 活动 Todo 上下文

## 问题

`todo_write` 只在它自己的工具结果里把当前列表作为提醒呈现。经过更多工具调用后，该提醒失去显著性，模型可能在还有未完成项的情况下结束轮次。持久化的 todo 文件不适合作为实时控制状态，因为它可能比创建它的 work chain 存活得更久。

## 设计

一次成功的 `todo_write` 之后，把只包含未完成项的提醒挂在一个稳定的 work chain owner 之下。重试和相关自动轮次使用的 prompt ID 解析到该 owner，因此并发的通知分支不会移动或覆盖前台提醒。后台任务和循环唤醒在创建时捕获 owner，并在其自动轮次中带回；无关的 cron 和通知轮次使用一个隔离的 owner，在轮次结束时移除。在重试或相关自动轮次的首个请求上、以及后续工具轮次的函数响应之后注入提醒。在所有 todo 完成、新的普通 work chain 开始或会话变更时清除它。

每一份注入的副本都会永久记录在聊天历史中，因此逐轮注入会让实时上下文随工具轮次线性增长。所以工具轮次注入只在上次呈现该状态（`todo_write` 结果本身计入）之后每隔第三个工具轮次重新发出提醒；轮次起始注入总是触发并重置该节奏。载荷是一个紧凑的 `- [status] content` 行列表，上限 800 字符。历史保持只追加，因此提供方前缀缓存不受影响。

这不改变停止语义，也不启用 `todoStopGuard`。该守卫仍是模型已尝试停止之后的可选有界恢复；本改动在那次决定之前保住任务上下文。

## 验证

- 一次带未完成项的成功写入会更新会话提醒。
- 一个已完成的列表会清除它。
- Core 和 ACP 的工具结果消息在函数结果之后追加提醒。
- ACP 轮中用户输入保持位于最后，因此保持优先。
- 一条新的普通 prompt 清除陈旧状态，而重试/继续保留它。
- 独立的自动轮次被隔离；相关的自动轮次继承。
- 终止性的自动轮次释放其临时归属状态。
