# Plan 模式轮中指引与进入边界

## 问题

`enter_plan_mode` 会在模型轮次仍在处理期间更改审批模式。在本变更之前，一次成功的调用只返回一句简短的话，因此模型要到之后的轮次才会收到完整的 Plan 模式约束。同一模型响应中的兄弟工具调用也可能在模式转换的两侧执行：进入之前的调用在先前模式下运行，而之后的调用在 Plan 模式生效后运行，却没有针对新边界被重新调度。

## 契约

一次成功的或已经激活的 `enter_plan_mode` 调用返回与 `getPlanModeSystemReminder()` 产出的相同的完整提醒。SDK 会话接收 SDK 专属的变体。未经请求的 YOLO 进入、转换失败以及 subagent 或 teammate 的拒绝保留其现有结果，因为没有发生 Plan 模式转换。

当去重后的可执行批次包含多个调用且其中一个是 `enter_plan_mode` 时，第一个进入调用是一个执行边界。只有该调用有资格执行。所有其他可执行的兄弟调用，无论出现在进入之前还是之后，都会收到一个终态的 `EXECUTION_DENIED` 响应，指示模型在观察到新审批模式后于下一轮次重试。进入失败或幂等成功不会放行这些兄弟调用。

现有的终态决定保持优先。循环检测仍然首先拒绝整个批次。重复的 provider 响应在其原始位置发出，但不是可执行的兄弟调用。在结构化输出模式下，现有的结构化输出预扫描保持终态，并把 `enter_plan_mode` 与其他非结构化调用一起抑制。

`exit_plan_mode` 在本变更中不是执行边界。其显式的用户审批和过期上下文保护是独立的。

## 集成

核心调度器在调用 ID 去重和规范名称解析之后、权限检查、注册表查找、hook 或调用构造之前应用该边界。因此被跳过的调用不会请求权限，也不会运行每工具的 hook。它们仍然是终态的批次结果，因此现有的完成回调、记录、遥测和 `PostToolBatch` 审计路径为每个被接受的调用 ID 观察到完整的响应。运行时专属的内容生成器视图与其他终态结果一起被清理。

ACP 在循环和重复 provider 处理之后、执行其顺序批次或 Agent 批次之前应用相同的策略。重复响应保持有序。ACP 不引入 `PostToolBatch` hook，因为该路径有意不支持它。

无头模式在重复和结构化输出过滤之后应用该策略。被跳过的调用按原始顺序发出并作为被拒绝的工具结果返回，但不消耗 `--max-tool-calls` 预算。进入本身遵循正常的预算和中止行为。

## 输出保留

该提醒是生命周期策略，而不是普通的工具载荷。`enter_plan_mode` 声明无限的每工具输出上限，豁免调度器的持久化溢出门，也不是聚合批次卸载的候选。这三项保护防止该策略在下一个模型轮次之前被截断、替换为文件指针或缩减为预览。

## 验证

单元测试覆盖验证确切的 DEFAULT 和 SDK 提醒、成功与幂等进入、首个进入的选择、两侧的兄弟拒绝、重复 provider 的排序、无头模式预算核算、在刻意极小的输出阈值下完整提醒的保留、`PostToolBatch` 可见性以及运行时视图清理。现有的调度器、ACP 和无头模式测试套件覆盖外围的权限、循环、重复、结构化输出和中止行为。

托管宿主的验证应确认 ACP 客户端为每个工具调用收到一个结果，并且下一个模型请求包含完整的提醒加上兄弟拒绝响应。该验证需要一个已部署的构建和一个宿主会话 ID；本 PR 不会通过更改生产路由来模拟它。
