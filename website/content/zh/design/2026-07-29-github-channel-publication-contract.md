# GitHub Channel 发布契约

## 目标

让 GitHub channel 的回复可以安全地自动发布，并且事后可追溯。该 channel 只通过适配器发布代理的最终响应；中间推理、工具输出和流式 chunk 绝不会成为 GitHub 评论。

## 契约

- GitHub 适配器禁用块流式，因此每个被接受的入站事件至多产生一次最终响应投递尝试。
- 最终投递使用活跃 prompt 的 issue/PR 线程，而不是可能过期的共享会话 target。
- Channel 指令告知代理不要使用 `gh` 或 GitHub API 创建评论或评审。适配器拥有公开发布。
- 修剪后内容只有 `<no-reply/>` 哨兵的最终响应被有意抑制。空白、大小写、`/>` 前的空格和单个包裹代码围栏会被归一化；其他任何内容原样发布。
- 抑制和发布记录在本地只追加的 JSONL 审计文件中，位于 `~/.qwen/channels/<workspace-scope>/<channel>-<name-hash>-github-audit.jsonl`。记录包含时间、channel、会话、源消息、线程、结果、存在时的 GitHub 评论标识/URL，以及回复的 SHA-256 和字符数。它们绝不包含回复文本、凭据或 GitHub token。
- 审计写入是尽力而为。审计失败只记录日志，不改变发布结果。模糊的 GitHub API 失败仍是投递失败且不重试；明确的未写入响应会写入私有待投递文件，并在下次 channel 启动时重试。

## 流程

1. GitHub 适配器把被接受的事件分发给 `ChannelBase`。
2. 活跃 prompt 保持入站消息和 issue/PR 线程可用，直到最终投递完成。
3. 代理返回一个最终响应。
4. 适配器要么抑制精确的哨兵，要么创建一条 issue 评论。
5. 适配器追加一条发布审计记录。终态任务生命周期仍由 `ChannelBase` 拥有。
6. 如果最终投递以明确的未写入响应失败，适配器把最终文本以私有文件权限存储在 `~/.qwen/channels/<workspace-scope>/<channel>-<name-hash>-github-pending-deliveries.json`，并在重启后重试而不重新运行代理。

## 非目标

- 这不重试模糊的发布失败，不创建状态评论，也不启用响应流式。那些是 issue #8012 的单独部分。
- 反对直接 `gh`/API 发布的指令是代理的运维边界，不是沙箱强制。工具级 GitHub 写入限制的执行属于运行时权限模型。
- 待投递保留策略，包括最大尝试次数、最大时限、大小上限、过期回复处理和孤儿临时文件清理，在 #8142 中单独跟踪。

## 验证

聚焦的 GitHub 适配器测试覆盖哨兵抑制、正常最终评论投递、不含回复文本的审计字段，以及非阻塞的审计写入失败。现有的路由和投递测试保持不变。
