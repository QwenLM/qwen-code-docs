# GitHub 通知 reason 分发

## 目标

使用 `notification.reason` 来选择 GitHub channel 发送的 prompt，而不改变其
轮询、游标推进、重试或错误报告行为。

| Reason              | 行为                                                            |
| ------------------- | --------------------------------------------------------------- |
| `mention`           | 只发送实际 mention 了 bot 的内容。                              |
| `review_requested`  | 对 pull request，发送携带 pull request 数据的评审 prompt。      |
| `assign`            | 发送携带 issue 数据的分诊 prompt。                              |
| `author`, `comment` | 把窗口内的新评论聚合成一个跟进 prompt。                         |
| 其他                | 保持逐评论处理，并识别通知 reason。                             |

评审和指派事件使用 GitHub 事件的行为人（actor）作为信封发送者，使现有的发送
者策略检查的是发起操作的人，而不是 issue 或 pull request 的作者。聚合只包含
被允许的发送者，并限制为最新 20 条评论、每条评论 400 字符。配对策略保持逐
评论分发，使每个发送者被独立授权。

游标记住最多 500 个已分发评论和直接事件的节点 ID。一个固定的安装时间下限让
延迟到达的评审和指派通知无需重放安装前的历史就能找到其事件。通知 ID 不被
持久化，因为 GitHub 会为同一线程上的后续活动复用它。

## 验证

聚焦的适配器测试覆盖每条路由、直接触发的元数据、mention 剥离、聚合授权，
以及评论和直接事件的去重。
