# Fork 恢复实时能力

## 问题

旧版 fork 后台 transcript 持久化了父级渲染的系统指令和内联工具声明。在
执行使用当前 `ToolRegistry` 的同时重放那些启动时声明，可能让一个已移除
或已变更的工具保持模型可见，尽管它无法被执行。

## 设计

保留 fork 的引导和运行时消息作为其持久身份。恢复时，从当前父会话重建
其可执行表面：

- 使用当前父级渲染的系统指令；
- 取得当前父级通告的工具名称，并通过被恢复 agent 的当前注册表解析它们
  的 schema；
- 在续接轮次中包含当前的 MCP、deferred-tool 和 Skill 提醒，同时声明更
  早的能力清单作废；
- 当无法重建当前父级的 prompt 或工具表面时，让任务保持暂停。

启动时的系统指令和工具声明在旧 transcript 中保持可读以便兼容，但恢复不
再把它们当作可执行的权威。新 transcript 持久化继承的历史和任务 prompt，
而不是能力快照；当前运行时状态是权威的。

启动时的执行限制不同于能力快照。当 fork 使用 `fork_tools` 时，其
`executionAllowedTools` 策略存储在 `AgentMeta` sidecar 中，并在活跃工
具表面重建后重新应用。持久化的空列表仍是拒绝一切；缺失的字段仍是无限
制。

## 后果

已移除的工具在恢复后不再被通告，已变更的工具使用其当前 schema。一个被
恢复的 fork 只有在其持久化的执行策略也允许某工具时，才能获得对其父级新
近可用的工具。这优先保证实时一致性而非逐字节相同的重放，同时不削弱显式
的启动限制。重新绑定也可能使旧的 prompt-cache 前缀失效，这优于发送过期
的能力。
