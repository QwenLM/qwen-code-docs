# PDF vision bridge 回退

## 背景

当主模型缺乏原生 PDF 支持时，`read_file` 对 PDF 以文本优先。对于扫描文档，文本提取仍可能失败，而单个密集页面可能超出安全的 12K token 工具结果预算。直接向纯文本 provider 返回渲染的页面并不安全，而把每个大型文本结果都当作图像处理，会使普通的多页读取更慢且更不精确。

## 设计

文件处理层可以准备一个内部的、仅针对 PDF 的 vision bridge 候选。该选项与交互式 `@` 附件所用的现有 unsupported-image 保留机制分离，因此普通图像读取不会改变。候选包含渲染的图像部分、触发原因、实际渲染的页面范围、结构化的续读元数据，以及当转录无法完成时要恢复的原始文本提取错误。续读元数据在无法统计页数时区分已知存在的页面与可能存在的页面。

候选只在 PDF 文本提取失败，或显式或实际的单页读取仍超出 12K 估算 token 时创建。多页文本溢出、大文档的页范围门控和文件大小门控保留其现有指引。渲染从请求的起始页开始，每次 `read_file` 调用最多处理四页。当已知时，请求的范围会被裁剪到 PDF 的实际页数：对一个六页文档请求 `pages: "4-8"` 会渲染第 4-6 页，而不会虚构第 7-8 页。当无法统计页数时，一个简短且未按字节截断的渲染被视为文件结束；完整的四页渲染或字节截断只报告可能还存在额外请求的页面。

`ReadFileTool` 只在主模型为纯文本且已配置或可用 vision bridge 模型时才启用准备。它在构建最终工具响应之前调用 bridge，只传递渲染的图像页面以及结构化的 PDF 页面上下文。bridge 被指示在转录章节上标注原始 PDF 页码。续读指引在转录之后追加，并且只指向原始 PDF，绝不指向临时渲染的图像。

成功时，`read_file` 返回不可信的、有损的机器转录，且不包含图像数据。一条结构化显示通知会披露所选的 vision 模型、已知时的端点、已转录的页面范围，以及已知或可能的续读位置。即使成功的读取输出被折叠、以及 transcript 详情被展开时，TUI 也会渲染该通知；ACP、非交互式结构化输出和会话导出在工具调用内容中包含相同的文本，而不是依赖不透明的原始输出。在 bridge 失败、空输出、超时或模型选择变更时，图像数据被丢弃，精确的原始 PDF 错误被恢复给模型，而 bridge 尝试仅在用户显示中可见。用户取消会传播。因此，候选图像不可能通过工具结果到达纯文本主 provider。

显式配置的 `visionModel` 被视为使用该模型的授权，即使它托管在另一个 provider 上。现有的 bridge 通知会报告实际端点，使数据边界保持可见。

## 兼容性

公共的 `read_file` schema 不变。原生 PDF 模型、具备视觉能力的主模型、未配置 bridge 模型的场景、普通的 PNG/JPEG 读取，以及现有的交互式图像行为都保留其当前路径。交互式 `@` PDF 解析还额外受益于单页溢出回退。

## 验证

单元测试覆盖不以第 1 页开始的请求范围、超出实际文档末尾的请求、未知页数、字节截断、空渲染、单页与多页溢出、bridge 成功与失败、取消、配置变更、跨 TUI/ACP/导出表面的端点披露、页码提示，以及纯文本结果不包含 `inlineData` 的不变量。E2E 验证使用一个六页扫描 PDF、一个密集单页 PDF 和一个多页文字密集 PDF，将全局基线与本地构建进行比较。
