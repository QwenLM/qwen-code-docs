# Переменные CI и релиза

Несколько параметров конвейеров CI и релиза доступны как переменные репозитория GitHub Actions (контекст `vars.*`), чтобы операторы могли настраивать их без создания pull request. На этой странице перечислены переменные, влияющие на выполнение тестов в `.github/workflows/ci.yml` и `.github/workflows/release.yml`, а также их значения по умолчанию и области применения.

## Настройка переменной

Сопровождающие репозитория настраивают их в разделе **Settings → Secrets and variables → Actions → Variables**. Для неустановленной (или пустой) переменной используется фолбэк в выражении workflow. Лимит воркеров применяется только на зарезервированных runner'ах, даже если соответствующая переменная установлена.

Файлы workflow являются источником истины для этих параметров, а тестовые наборы фиксируют выражения workflow побайтно: `scripts/tests/package-scripts.test.js` фиксирует общее выражение лимита воркеров в `release.yml` (`QWEN_CI_VITEST_MAX_WORKERS` с защитой `ecs-qwen-`), `scripts/tests/no-ak-integration-ci.test.js` фиксирует выражение лимита воркеров в `ci.yml`, а `scripts/tests/release-workflow.test.js` фиксирует выражения таймаутов повторов и тестов workspace в `release.yml`. `scripts/tests/package-scripts.test.js` также проверяет задокументированные значения по умолчанию и расположение параметров в обоих workflow. Поскольку эта проверка выполняется в полной CI-ветке (`test:scripts`), а не только в проверках документации, проверяйте изменения, касающиеся этой страницы, локально перед созданием pull request с помощью `npm run test:scripts` (или `npx vitest run --config ./scripts/tests/vitest.config.ts scripts/tests/package-scripts.test.js`). Если документация и workflow когда-либо расходятся, руководствуйтесь workflow и обновите эту страницу в том же изменении.

## Переменные

| Переменная                               | По умолчанию | Используется в          | Управление                                                                            |
| ---------------------------------------- | ------------ | ----------------------- | ------------------------------------------------------------------------------------- |
| `QWEN_CI_VITEST_RETRY`                   | `2`          | `ci.yml`                | Количество повторов для основного шага тестирования workspace и скриптов в CI         |
| `QWEN_CI_HOST_LOAD_MAX_RATIO`            | `2.0`        | `ci.yml`                | Потолок нагрузки на CPU, при котором или выше self-hosted Linux-хост отклоняется до начала unit-наборов тестов |
| `QWEN_CI_RPC_RETRY`                      | `1`          | `ci.yml`                | Повторные запуски набора тестов workspace, который завершился без упавших тестов, кроме таймаута RPC воркера Vitest |
| `QWEN_RELEASE_VITEST_RETRY`              | `2`          | `release.yml`           | Количество повторов для шардов тестов workspace при релизе                            |
| `QWEN_RELEASE_WORKSPACE_TIMEOUT_MINUTES` | `45`         | `release.yml`           | Таймаут задания для каждого шарда тестов workspace при релизе                         |
| `QWEN_CI_VITEST_MAX_WORKERS`             | `4`          | `ci.yml`, `release.yml` | Лимит воркеров для основных unit-тестов CI и тестов workspace/quality на зарезервированных runner'ах |

### Счетчики повторов

`QWEN_CI_VITEST_RETRY` и `QWEN_RELEASE_VITEST_RETRY` передаются в Vitest как `--retry=<n>` в основном шаге тестирования CI (`test:ci` каждого workspace, который этот шаг запускает в двух параллельных ветках, и `npm run test:scripts:unit`) и в релизной ветке (`npm run test:release:workspaces`) соответственно. У двух веток разные переменные, чтобы их можно было настраивать независимо.

Vitest перезапускает упавшие тесты в рамках одного запуска. Это может помочь при периодической конкуренции за ресурсы, но если сбой устраняется в рамках бюджета повторов, проверка становится зелёной и не фиксируется трекером нестабильных перезапусков как сбой. Устанавливайте скромный бюджет, а не используйте повторы для маскировки нестабильного набора тестов. Обе переменные также принимают буквальное значение `off`, которое полностью опускает флаг `--retry` вместо передачи `--retry=0` (командный флаг `--retry=0` переопределяет собственную конфигурацию Vitest workspace и отключил бы преднамеренную политику повторов).

### Таймауты RPC воркеров на загруженном хосте

`QWEN_CI_RPC_RETRY` — это другой рычаг, отличный от `--retry`: он повторно запускает весь набор тестов workspace, и только если отчёт самого набора не показывает упавших тестов, а единственным необработанным ошибкой был лимит RPC от воркера к главному процессу Vitest (`Timeout calling "onTaskUpdate"`). В этом пуле такая картина означает загрузку хоста, а не регрессию — запуски main 43018456551 и 43016357976 оба стали красными при 902 из 902 пройденных тестах в `packages/channels/github`. Первая попытка сохраняет собственный пакетный вызов npm; повторно запускаются только те workspace, которые npm называет упавшими, каждый по отдельности.

Релизная ветка уже предоставляет этот же повторный прогон для собственных шардов (`.github/scripts/run-release-workspace-tests.sh`), и правила проверки — те, которые фиксирует `scripts/tests/release-workflow.test.js`: запуск должен достичь проходящего количества, не должен быть убит сигналом, а собственное количество необработанных ошибок Vitest должно равняться количеству таймаутов транспорта в отчёте. Количество, а не заголовок сбоя — заголовок выбирается продюсером, поэтому любой паттерн по заголовкам неполон. Цифра `Errors` — это сумма по всему отчёту, тогда как цифра транспорта считает только внутри секций `Unhandled Errors` Vitest — вывод консоли теста также отображается в колонке 0, поэтому печатная копия не должна сдвигать её — и внутри этих секций она совпадает с собственной строкой заголовка ошибки ( `Error: [vitest-worker]: Timeout calling` в колонке 0), никогда не с сообщением, стеком или фреймом кода, которые просто цитируют префикс. Проходящее количество одной попытки не может покрыть сбой более поздней попытки.

Linux-ветки намеренно делают необработанные ошибки фатальными (`scripts/tests/unit-vitest-configs.test.ts`, #10438), поэтому это не игнорирует их: любой упавший тест, любая вторая необработанная ошибка или процесс, умерший до отчётности, отклоняют повтор. Зависание, пережившее обе попытки, всё равно завершается сбоем. Установите `0`, чтобы первый сбой оставался.

**Количество — единственная граница.** Повторный запуск не имеет временного условия: более ранняя версия этой ветки пропускала повторный запуск, когда оставалось менее половины бюджета шага тестирования, и эта защита была удалена, а не исправлена. Она отклоняла повторный запуск при 74% бюджета, потому что добавляла прошедшее время пакета дважды, и корректная версия недоступна изнутри скрипта ветки — шаг начинается до скрипта (`chown -R`, `mktemp`, дисковый сэмплер), поэтому собственный `SECONDS` скрипта — не часы шага, а передача начала шага из workflow была бы большей новой поверхностью, чем одно усечение, которое она бы избежала. Принятая стоимость: повторный запуск, выполненный достаточно поздно, может быть убит `timeout-minutes: 45` шага. Когда это происходит, задание завершается сбоем, и лог первой попытки всё ещё на месте, потому что первая попытка записывается в файл — усечение, которое сохраняет доказательства, а не отклонение, которое выбрасывает повтор, пока четверть бюджета не использована.

### Допуск загрузки хоста

`QWEN_CI_HOST_LOAD_MAX_RATIO` — это потолок нагрузки на CPU шага `Host load gate (self-hosted)` в шардах unit-тестов. Гейт выбирает пятиминутную среднюю загрузку из `/proc/loadavg` относительно `nproc`, ожидает до шести выборок с интервалом в десять секунд и допускает задание, как только одна выборка очищает потолок. Хост, всё ещё находящийся на уровне или выше потолка, проваливает шаг до начала наборов тестов.

Гейт не может переместить задание: GitHub уже разместил его, и только повторный запуск переносит его на другой хост. Что меняется — так это когда задание завершается сбоем. Рядом с ним находится гейт дискового пола, который допускает по свободным байтам и инодам, что ничего не говорит о конкуренции за CPU; 2026-11-11 пул hk1 запускал 64-CPU хосты при загрузке 53-98 с 28-140 одновременными процессами Vitest, и именно эта загрузка истекает 60-секундные бюджеты тестов, бюджет RPC воркера Vitest и весь 45-минутный бюджет шага тестирования. Отклонение стоит уже потраченной установки и возвращает этот бюджет, с сообщением, которое говорит повторить, а не сбой теста, который не создавала ни одна ветка.

**Гейт — это страховочный предел, а не предсказатель.** По умолчанию `2.0` калибруется по пятиминутной нагрузке на CPU шардов, которые упали 2026-11-11, и четырёх шардов, которые прошли на том же пуле в тот же час:

| Шард | Хост   | При входе | Медиана | Пик  | Результат              |
| ---- | ------ | --------- | ------- | ---- | ---------------------- |
| 2/2  | hk1-4  | 1.34      | 1.43    | 1.54 | таймаут RPC воркера    |
| 2/2  | hk1-30 | 1.45      | 1.42    | 1.54 | таймаут RPC воркера    |
| 2/2  | hk1-29 | 0.85      | 1.42    | 1.54 | 45-минутный таймаут шага |
| 1/2  | hk1-7  | 0.94      | 1.40    | 1.49 | пройден                |
| 2/2  | hk5-27 | 1.03      | 1.03    | 1.19 | пройден                |
| 1/2  | hk2-32 | 0.75      | 0.97    | 1.18 | пройден                |
| 1/2  | hk3-28 | 0.48      | 0.67    | 0.87 | пройден                |

Диапазоны пересекаются. Хост, который прошёл, достиг 1.49, тогда как хост, который упал, начал с 0.85 — загрузка росла во время прогона, и только два из трёх упавших хостов уже были загружены, когда их наборы тестов начались. Никакой порог времени входа не разделяет их, поэтому потолок, достаточно жёсткий, чтобы поймать два загруженных, также отклонит хосты, которые явно проходят. `2.0` находится выше каждого показания, измеренного на хосте, который завершил свои наборы тестов: он отклоняет хост, который не пережила ни одна из этих выборок, и не сработал бы ни на одном инциденте в таблице. Ужесточение, как ожидается, даст ложные отклонения; повышение его намного дальше делает гейт неактивным.

RPC-флейк в этой таблице — это другая проблема, и этот гейт не её исправление: решение требует собственного отчёта набора, которого не существует до запуска наборов. #16945 добавляет повторный запуск на уровне ветки именно для такой формы — полностью зелёный отчёт, единственной необработанной ошибкой которого был таймаут RPC воркера. Они независимы и могут настраиваться или отключаться отдельно.

Потолок — это соотношение, а не абсолютная загрузка, потому что пул смешивает размеры хостов. Установите `off`, чтобы допускать каждый хост, пока флот изменяется в размере. Гейт запускается только на self-hosted Linux; ветки GitHub-hosted и macOS не затрагиваются, а нечитаемое количество CPU или средняя загрузка, или отсутствующий `awk`, допускает задание с предупреждением, а не блокирует ветку. Неверный порог завершается сбоем как ошибка конфигурации, которой он является, вместо тихого отключения гейта.

### Таймаут тестов workspace

`QWEN_RELEASE_WORKSPACE_TIMEOUT_MINUTES` задаёт `timeout-minutes` на уровне задания для каждого из трёх шардов `workspace_tests` в конвейере релиза. Таймаут определяется загрузкой зарезервированного хоста, а не самого набора тестов, поэтому увеличивайте его при высокой загрузке хоста, а не предполагайте регрессию тестов.

### Лимит воркеров Vitest на self-hosted runner'ах

`QWEN_CI_VITEST_MAX_WORKERS` ограничивает количество процессов Vitest в перечисленных ниже шагах (`VITEST_MAX_THREADS` / `VITEST_MAX_FORKS`, с минимальным значением, принудительно установленным в `1`) на зарезервированных self-hosted runner'ах, чьи имена начинаются с `ecs-qwen-`. Переменная экспортируется только основным шагом тестирования workspace в CI и шагами `workspace_tests` и `quality_scripts` в релизе; другие интеграционные тесты, использующие Vitest и попадающие на тот же зарезервированный пул в workflow CI и релиза, не потребляют её — они используют собственные ограничения Vitest. Web-shell E2E smoke запускается в пуле ARM64 с собственными двумя воркерами Playwright, поэтому лимит на него не распространяется. На runner'ах GitHub переменная игнорируется, и Vitest использует собственные значения по умолчанию.

Каждый запуск Vitest применяет лимит самостоятельно. Основной шаг тестирования workspace в CI запускает две ветки одновременно (`.github/scripts/ci/run-unit-test-lanes.sh`): основная ветка запускает наборы тестов CLI и core с лимитом, а побочная ветка запускает наборы тестов остальных workspace и `npm run test:scripts:unit` с половиной лимита, но не менее 1, поэтому в пике шаг выполняет лимит плюс эту половину. На runner'ах GitHub побочной ветки Vitest использует 2 воркера.

Шаг выполняется в двух шардах (`Linux unit tests (shard N/2)`), каждый из которых передаёт `--shard=N/2` в каждый запуск Vitest. Шарды также применяют лимит самостоятельно, поэтому пул видит до двух таких шагов одновременно. Они устанавливаются без сборки `prepare` и распаковывают дерево, собранное один раз заданием `test_build`. `Test (ubuntu-latest, Node 22.x)` проходит только когда сборка и каждый шард проходят успешно.

`test_build` — единственное задание, которое выполняет сборку. Оно работает через `scripts/ci-build-cache.mjs`: pull request восстанавливает сборку, сохранённую push'ем в `main` базового коммита (`key --at <base>`), с фолбэком на самую новую кэшированную сборку, и пересобирает только те workspace, чьи входные данные изменились: отслеживаемые файлы workspace кроме тестов, корневые файлы, `patches/` и `scripts/` вне `scripts/tests/`, а также workspace'ы, от которых он зависит. Push в `main` всегда выполняет сборку с нуля и сохраняет её. Ключ кэша не несёт архитектуру CPU: пул с меткой x64 включает хосты ARM64, и единственные архитектурно-зависимые выходные данные — нативная библиотека opentui бандла — пересобираются для хоста после каждого восстановления и распаковки (`ci-build-cache.mjs host-assets`).

Шарды unit-тестов, два шарда `Integration Tests (no-AK, shard N/2)` и два шарда web-shell smoke распаковывают это единственное дерево. `test_build` также запускает проверки, которые его читают: serve fast-path bundle closure, экспорты core subpath и проверку свежести settings-schema, для которой `Lint & Static` раньше выполнял сборку. `Integration Tests (no-AK, No Sandbox)` проходит только когда сборка и каждый интеграционный шард проходят успешно. Draft pull request пропускает интеграционные шарды и browser smoke; отметка его готовым к ревью запускает прогон, который их включает. Изменение, ограниченное `packages/managed-agent-server/` или `packages/sdk-java/` (кроме файлов, которые читают наборы тестов TypeScript), классифицируется как `java_only`: `Lint & Static` запускает свою нагрузку плюс наборы `scripts/tests`, которые именуют эти деревья, а сборка и тестирование TypeScript пропускаются.

### Связанные переменные вне выполнения тестов

`release.yml` также предоставляет `QWEN_RELEASE_STATIC_TIMEOUT_MINUTES` (по умолчанию `60`, управляет веткой статического линтинга `quality_static`) и `QWEN_RELEASE_BUILD_TIMEOUT_MINUTES` (по умолчанию `45`, управляет веткой сборки артефактов `quality_build`). Поскольку они регулируют статический линтинг и сборку артефактов, а не выполнение тестов, они выходят за рамки выполнения тестов, описанных на этой странице.
