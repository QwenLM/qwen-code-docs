# Отправка через WeCom Webhook

Используйте webhook Message Push внутренней группы WeCom (ранее называвшийся групповым
роботом) для отправки уведомлений и результатов задач. Для этого нужен только URL webhook
группы, без Bot ID/Secret, учётных данных приложения, долгого соединения
или публичного входящего сервера. Для общения с агентом используйте
[интеллектуального робота WeCom](./wecom); для самостоятельно собранного приложения см.
[WeCom Callback](./wecom-callback).

## Создание группового назначения

1. Откройте настройки внутренней группы WeCom и найдите Message Push.
2. Создайте собственный Message Push и скопируйте его URL webhook, начинающийся с
   `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=`.
3. Если пункт недоступен, проверьте права на создание в вашей организации.
   Администраторы могут ограничивать, какие участники могут создавать Message Push, а
   в группах под управлением владельца этот пункт доступен только владельцу группы.

Внешние группы не поддерживаются в этой конфигурации. Официальные условия создания
описывают права для внутренних групп и администраторов; они не устанавливают
универсальное требование или исключение для сертификации предприятия.

URL содержит учётные данные для отправки. Храните его в конфигурации Channel или в
переменной окружения, но никогда в промпте задачи или назначении доставки. Используйте URL
в том виде, в котором он выдан WeCom. Локальная проверка допускает ровно один параметр `key`, содержащий
буквы, цифры, `-`, `.`, `_` или `~`; percent-кодирование, фрагменты и
дополнительные параметры не принимаются. Отдельного секрета подписи нет.

## Настройка Channel

Настройте эту интеграцию в [Web Shell](#use-web-shell) или `settings.json`, как
показано ниже.

Добавьте именованный экземпляр в настройки Channel рабочего пространства:

```json
{
  "channels": {
    "team-notices": {
      "type": "wecom-webhook",
      "webhookUrl": "$WECOM_WEBHOOK_URL"
    }
  }
}
```

Установите `WECOM_WEBHOOK_URL` в окружении, используемом для запуска Qwen Code, затем запустите
демон в этом рабочем пространстве:

```bash
qwen serve --channel team-notices
```

Один именованный экземпляр представляет одну группу. Создайте дополнительные экземпляры для других
групп. Изменение URL экземпляра меняет будущие доставки через него.

Запуск приводит Channel в локальную готовность к отправке. Он не отправляет тестовое
сообщение и не проверяет удалённые учётные данные. Остановка отменяет находящиеся в процессе отправки;
перезапуск или перезагрузка применяет сохранённые изменения конфигурации.

## Использование Web Shell

Если ваша сборка содержит поддержку на стороне бэкенда, но предшествует Web-интеграции,
Channels не перечисляет этот метод или существующие экземпляры `wecom-webhook`. Используйте
шаги с `settings.json` и `qwen serve --channel`, описанные выше, пока не обновитесь до
сборки, содержащей Web-интеграцию.

В Channels выберите WeCom, затем Webhook (только отправка). Выберите рабочее пространство,
сохраните URL webhook и запустите Channel. Секрет подписи не требуется.
Настройки получения, сопряжения и сессий агента не применяются к этому методу.
Метод интеллектуального бота остаётся в WeCom; WeCom Callback сохраняет свой
отдельный пункт.

В Scheduled Tasks выберите постоянную сессию задач и выберите этот Channel
как назначение доставки. Web Shell автоматически заполняет настроенную группу;
наблюдаемые контакты или введённый вручную ID чата не нужны. Существующие ограничения доставки
для каждого запуска и ручного триггера остаются в силе.

Те же элементы управления доступны через `WebShellWithProviders`, когда хост
включает Channels и Scheduled Tasks и предоставляет рабочее пространство демона.

## Явная доставка через API

Notify и явная доставка промпта/scheduled используют существующий target Channel.
Этот адаптер владеет одним логическим назначением, `chat/default`:

```json
{
  "text": "# Daily report\n\nThe checks passed.",
  "delivery": {
    "kind": "channel",
    "target": {
      "channelName": "team-notices",
      "type": "chat",
      "id": "default"
    }
  }
}
```

Это тело запроса Notify рабочего пространства. `default` именует настроенную группу;
это не chat ID WeCom. Другие ID, целевые объекты пользователей и треды отклоняются.
Задачи хранят логическое назначение; учётные данные остаются в настройках Channel.

Постоянные scheduled задачи используют то же назначение. Доставка сохраняет
существующее поведение best-effort для успешного конечного результата, включая текущие
ограничения для каждого запуска и ручного триггера.

## Форматирование сообщений и ограничения

- Отправляет `markdown_v2` с исходным текстом. Поддерживаемое подмножество включает
  заголовки, списки, ссылки, код в ограждениях и таблицы; обычный текст, китайские символы и
  эмодзи являются допустимым вводом. Полная совместимость с GitHub-flavored Markdown не
  гарантируется.
- Этот формат не поддерживает упоминания или разметку цвета шрифта. Адаптер
  не отправляет массивы упоминаний и не превращает текст задачи в упоминания.
  Строки, похожие на упоминания, такие как `< @all>`, остаются в теле.
- Клиенты до 4.1.36 (Android до 4.1.38) отображают сообщение как обычный текст.
  Используйте актуальный клиент для рендеринга Markdown.
- Окончательный **content** ограничен **4096 байтами UTF-8**, до JSON-экранирования.
  Китайские символы и эмодзи занимают больше байт, чем ASCII. Это не ограничение в 4096 символов
  и не ограничение на полный JSON-запрос.
- Превышающий размер контент явно отклоняется перед отправкой. Тихого обрезания
  адаптером, автоматического разбиения или повтора нет. Общая граница доставки всё ещё
  применяется до платформо-специфичной проверки.
- WeCom разрешает **20 сообщений в минуту на webhook**. Делайте scheduled отчёты
  лаконичными и избегайте всплесков; deliveries с троттлингом сообщают о сбое без постановки в очередь.

## Сбои и транспорт

Проверяются как HTTP-статус, так и числовой WeCom `errcode`. Недействительные или
отключённые учётные данные, отклонённые групповые назначения и ограничения скорости приводят к
наблюдаемым сбоям. Диагностика опускает URL, ключ, содержимое сообщения и текст сырой
ошибки провайдера.

Каждая попытка выполняет не более одного запроса с таймаутом 15 секунд. Принятие API
не является подтверждением прочтения; таймаут или отмена могут оставить удалённое принятие
неизвестным. Транспорт учитывает разрешённый прокси рабочего пространства и существующее
поведение `NO_PROXY`.

Этот режим не получает сообщения, не запускает входящие задачи webhook и не стартует циклы
Channel. Он не добавляет вложения, интерактивные карточки, автоматические уведомления о сбоях/отменах,
долговечные повторы или универсальный протокол webhook.

См. официальный [протокол Message Push](https://developer.work.weixin.qq.com/document/path/91770)
и [руководство по настройке](https://open.work.weixin.qq.com/help2/pc/14931) для актуальных
требований платформы.
