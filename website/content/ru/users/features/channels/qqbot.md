# QQ Bot (QQ-бот)

В этом руководстве описывается настройка канала Qwen Code в QQ через официальный API QQ Bot Open Platform.

## Предварительные требования

- Учётная запись QQ (мобильное приложение для сканирования QR-кода)

## Настройка

### Вход по QR-коду

Запустите канал — при первом запуске появится QR-код. Отсканируйте его с помощью приложения QQ для активации. Ни регистрация разработчика, ни ручная настройка не требуются. Учётные данные сохраняются и используются повторно автоматически.

```json
{
  "channels": {
    "my-qq": {
      "type": "qq"
    }
  }
}
```

```bash
qwen channel start my-qq
# Отсканируйте QR-код в терминале с помощью приложения QQ
```

### Ручная настройка (портал разработчика)

Вы также можете использовать учётные данные с портала разработчика [QQ Bot Open Platform](https://q.qq.com/), если у вас уже зарегистрировано приложение:

```json
{
  "channels": {
    "my-qq": {
      "type": "qq",
      "appID": "YOUR_APP_ID",
      "appSecret": "$QQ_APP_SECRET"
    }
  }
}
```

Установите секрет через переменную окружения:

```bash
export QQ_APP_SECRET=<your-app-secret>
```

## Конфигурация

```json
{
  "channels": {
    "my-qq": {
      "type": "qq",
      "appID": "YOUR_APP_ID",
      "appSecret": "$QQ_APP_SECRET",
      "sandbox": false,
      "privatePolicy": "open",
      "sessionScope": "user",
      "cwd": "/path/to/your/project",
      "instructions": "你是一个通过 QQ Bot 对话的 AI 助手。回复控制在 2000 字符以内。",
      "groupPolicy": "disabled",
      "groups": {
        "*": { "requireMention": true }
      }
    }
  }
}
```

> `sessionScope` по умолчанию равен `"thread"`. При `groupPolicy: "disabled"` это режим только для личных сообщений, где и `"thread"`, и `"user"` дают каждому личному сообщению свой контекст. `"thread"` показан здесь для согласованности с разделом [Session Isolation](#session-isolation) ниже — прочитайте примечание об обновлении в этом разделе перед изменением области действия существующего канала.

`privatePolicy`, `allowedUsers`, `sessionScope`, `cwd`, `instructions`, `groupPolicy`, `groups`, `dispatchMode`.

## Запуск

```bash
# Запустить только канал QQ
qwen channel start my-qq

# Или запустить все настроенные каналы вместе
qwen channel start
```

Откройте QQ и отправьте сообщение вашему боту. Вы должны увидеть ответ в чате.

## Групповые чаты

Чтобы использовать бота в группах QQ:

1. Установите `groupPolicy` в `"allowlist"`, `"pairing"` или `"open"` в конфигурации канала.
2. Добавьте бота в группу QQ через панель управления QQ Bot Open Platform или попросите администратора группы пригласить его.
3. Участники группы должны **@упомянуть** бота, чтобы вызвать ответ.
4. Если используется `groupPolicy: "pairing"`, одобрите запрос на спаривание группы один раз перед началом ответов. Обратите внимание, что после одобрения группы **любой участник этой группы** может использовать бота по умолчанию (ограничьте с помощью `senders: "allowlist"` и `allowedUsers` группы); `privatePolicy` и `allowedUsers` корневого уровня не регулируют доступ участников одобренной группы.

API QQ Bot V2 доставляет только групповые сообщения, в которых упоминается бот — бот не видит все сообщения группы. По умолчанию `requireMention` равно `true`, и для QQ это значение следует оставить.

Сообщения от другого бота по умолчанию отбрасываются. Установите `forwardBotMessages: true` для их доставки: такое сообщение достигает модели с префиксом `[bot]` в строке отправителя, и модель решает, имеет ли смысл отвечать. Разговор между ботами — это возможность, а не дефект, и переключатель — это вся его граница — QQ доставляет события сообщений только для пользовательских сообщений (отправки самого бота возвращаются в ответе API отправки, а не как события), поэтому включенный путь может нести только сообщение другого бота; намеренно нет автоматического ограничения скорости на включенном пути; человеческие участники группы и собственные правила молчания модели (`<noreply>`) являются защитой, поэтому включение — это явный компромисс оператора.

### Запланированные циклы и проактивная доставка

Результаты loop, webhook-task, фоновых задач или задач с именем доставляются обратно в чат, который их создал, как **активные сообщения** — QQ публикует их без якоря ответа, поэтому они не зависят от недавнего входящего сообщения. В группе каждая такая доставка расходует квоту активных сообщений группы на платформе.

Если администратор группы отключил активные сообщения, эти доставки завершаются ошибкой вместо тихого фолбэка на заякоренный пассивный ответ: проверки цели loop и webhook отклоняют запуск до хода агента, результаты фоновых задач и задач с именем отклоняются при доставке с `ACTIVE_MSG_DISABLED`, и планировщик циклов считает последовательные сбои и автоматически отключает цикл после 5. Проактивная доставка также требует, чтобы тип чата уже был изучен: цель loop или webhook в группе, от которой бот никогда не получал сообщений, отклоняется вместо отправки.

### Изоляция сессий

Канал QQ по умолчанию использует `sessionScope: "thread"`: участники одной группы делят единый контекст разговора с ключом `<channel>:<group_openid>`, в то время как разные группы изолированы друг от друга. Каждое личное сообщение получает свой контекст с ключом `<channel>:<user_openid>`.

Сессия потока группы — это **общая сессия**: каждый участник группы читает и продолжает одну и ту же историю разговора. Команды, работающие с этой сессией (`/clear`, `/cancel`, `/who`, `/status`, `/loop`, `/btw`), ответы на разрешения (`/approve`, `/approve-always`, `/deny`) и управление текущим ходом (обычное сообщение участника встает в очередь вместо управления текущим ходом) ограничены участниками, перечисленными в `operators` канала; `allowedUsers` и `senderPolicy` **не** предоставляют их. `operators` по умолчанию не установлен, поэтому из коробки общая групповая сессия **не имеет** участников, авторизованных для выполнения этих команд — и запрос разрешения, поднятый в группе, не имеет никого, кто мог бы на него ответить. Установите `operators` в QQ id участников, которые должны иметь возможность управлять сессией группы. Для группового сообщения гейт сравнивает с `member_openid` этого участника — тем же пространством id, что и `allowedUsers` уровня группы выше — а не `user_openid` личных сообщений; список, заполненный `user_openid`, не соответствует никому, и поскольку список не пуст, предупреждение при запуске остается тихим, поэтому каждая команда выше просто отклоняется. Канал с областью `single` или `chat_thread` затрагивается тем же способом, потому что эти области также делят сессии личных сообщений. Префикс хост-оболочки `!` отключен в каждом групповом чате QQ, независимо от области; в личном сообщении то же правило области определяет это — `!` работает только там, где область сохраняет сессию приватной для одного отправителя (`"thread"` или `"user"`), и отклоняется для личных сообщений также при `"single"` или `"chat_thread"` и для каждого группового сообщения. Если участники группы не должны делить историю или управлять ходами друг друга, установите `sessionScope: "user"` (каждый участник получает приватную сессию — см. примечание об обновлении ниже перед переключением существующего канала) или ограничьте тех, кто может говорить с ботом, с помощью управления `senders` / `allowedUsers` уровня группы — например `groups: {"*": {"senders": "allowlist", "allowedUsers": ["<member_openid>"]}}`. `senderPolicy`, `allowedUsers` и `privatePolicy` верхнего уровня управляют только личными сообщениями; они не регулируют доступ участников одобренной группы.

Для режима полных сообщений это значение по умолчанию уже является тем, что вам нужно — с `groupAllPolicy: "all"`, сохранение `"thread"` дает вам общий контекст внутри группы и изоляцию между группами. Если вместо этого вы установите `sessionScope: "user"`, трафик полных сообщений фрагментируется по отправителю (отдельная сессия для каждого участника), что не подходит для групповых сценариев полных сообщений.

Другие общие области не являются эквивалентами. `sessionScope: "chat_thread"` маршрутизирует групповые сообщения точно как `"thread"` (QQ не предоставляет id потока, поэтому оба используют ключ `<channel>:<chatId>`), но он рассматривается как общий для **каждого** чата: каждое личное сообщение становится общей сессией, подчиняющейся гейту `operators`, поэтому `/clear` в личных сообщениях отклоняется, и вызов инструмента в личных сообщениях не имеет никого, кто мог бы на него ответить. `sessionScope: "single"` также делят личные сообщения и дополнительно используют ключ **каждой** группы и каждого личного сообщения для единого контекста `<channel>:__single__`, поэтому история группы A отвечает с историей группы B и с историей личных сообщений — это перекрестное утечка, о которой идет речь в этом разделе. Канал предупреждает при запуске, когда `groupAllPolicy` равен `"keyword"` или `"all"` и область не `"thread"`. С включенным `multiSession` область фиксируется на `"user"`, поэтому это предупреждение называет эти две настройки как взаимоисключающие и говорит оператору изменить `groupAllPolicy` или выключить `multiSession`, вместо совета использовать `"thread"`.

**Обновление со старого канала QQ.** Область по умолчанию изменилась с `"user"` на `"thread"`. (Канал с `groupAllPolicy: "keyword"` или `"all"` ранее был принудительно установлен на `"single"` — одна глобальная сессия. Канал, который не фиксировал `sessionScope`, теперь разрешается в `"thread"`, если `multiSession` не включен, что разрешается в `"user"` — сессии по отправителю являются единственной формой, которую поддерживает `multiSession`, поэтому он побеждает над плагином по умолчанию; для канала без `multiSession` эффективное изменение от этой глобальной сессии к сессии на группу. Канал, который явно фиксировал `sessionScope`, больше не переопределяется, поэтому явный `"user"` теперь вступает в силу и фрагментирует групповой трафик полных сообщений по отправителю — измените его на `"thread"` вручную.) Устаревшие маршруты сессий не удаляются автоматически: пока `purgeLegacySessions` выключен, каждый запуск считает маршруты, которые охватывает очистка — ключ эпохи одной области `<channel>:__single__` и ключи устаревшей пользовательской области этого канала `<channel>:<senderId>:<chatId>` — и оставляет их и их сессии на стороне демона нетронутыми. Маршрут эпохи `chat_thread` `<channel>:<chatId>:<threadId>` не охватывается: он не считается и не очищается. Чтобы удалить охваченные маршруты, установите `purgeLegacySessions` в `true` на канале. С включенной опцией каждый такой маршрут освобождается, и его сессия на стороне демона отбрасывается, поэтому старые сопоставления разговоров перестают существовать; очистка запускается при каждом запуске, пока опция включена. Ничто не удаляется, если резервная копия не достигает диска: непосредственно перед первым удалением канал добавляет обреченные маршруты в `<channel>-sessions-purged.json` в каталоге состояния канала (например, `~/.qwen/channels/my-qq-sessions-purged.json`; символы вне `A-Za-z0-9_-` в имени канала становятся `_`), и если эта запись не удается, он ничего не удаляет и оставляет маршруты на месте. Файл записывается только тогда, когда удаление действительно происходит — никогда при запуске, который оставляет все в покое. Это JSON-список записей очистки, каждая с `purgedAt` временной меткой, `sessionScope` и `routes`; каждый маршрут несет свой `kind`, `key`, `sessionId`, `target` и — когда сохраненное состояние сессии маршрутизатора все еще записывает их — `cwd`, `turns`, `startedAt`, `isolation` и `workspaceCwd`. Записи добавляются, а не перезаписываются, поэтому запись более ранней очистки выживает после более поздней (самые старые записи отбрасываются, когда список превышает 20); файл, который не может быть прочитан или не содержит список записей очистки, сообщается в логе и переименовывается в соседний файл `<path>.corrupt-<timestamp>`, поэтому поврежденная копия сохраняется для ручного восстановления, и новая запись никогда не теряется. Это только метаданные маршрутизации — без содержимого разговора — поэтому они показывают вам, что было отброшено, и позволяют вам воссоздать сопоставление вручную: маршрут, запись которого включает `cwd` и не имеет `isolation`, разрешается в то же рабочее пространство при восстановлении; когда запись также несет `isolation: "worktree"`, `cwd` — это (обычно уже удаленный) worktree на сессию, поэтому восстановите против `workspaceCwd` записи и сохраните `isolation`, чтобы маршрутизатор переподключил его через управляемый путь загрузки. Когда сохраненное состояние маршрута не имеет `cwd` (запись отсутствует или предшествует полю), запись просто опускает `cwd`, а не угадывает, поэтому восстановление такого маршрута вручную также требует путь рабочего пространства канала. Установка `sessionScope: "user"` после очистки **не** возвращает старые разговоры сама по себе — эти маршруты уже ушли и не восстанавливаются автоматически.

Подробнее о групповых политиках и условиях упоминания см. в разделе [Group Chats](./overview#group-chats).

## Инструменты управления группами

С `moderationTools: true` канал предоставляет API управления группами QQ агенту как **клиентские MCP-инструменты в сессиях этого канала**. Инструменты **выключены по умолчанию**: они разрушительны и работают с собственным токеном бота, поэтому существующее развертывание держит их выключенными, пока оператор не включит их для каждого канала. После включения агент вызывает их сам при ответе — нет слеш-команды для ввода и нет шага подтверждения оператора. Собственные правила платформы являются единственным ограничением, плюс правило отзыва по участнику ниже: отзыв `member_openid` разрешен только когда собственный отправитель хода является этим участником, или когда ход не имеет отправителя-участника (например, ход, инициированный оператором).

| Инструмент                                                  | Эндпоинт QQ                                            | Требование                                                                                                                                                                                       |
| --------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `qq_recall_message`                                       | `DELETE /v2/groups/{id}/messages/{msg_id}`             | Только групповые чаты, и каждый вызов должен указывать цель (`member_openid` или `message_id`). Бот должен быть администратором группы для отзыва сообщения другого участника. Собственные сообщения бота не могут быть отозваны |
| `qq_get_group_info`                                       | `GET /v2/groups/{id}/info`                             | Зарезервировано — только по приглашению для приложения бота (`11253` в противном случае)                                                                                                          |
| `qq_get_bot_state`                                        | `GET /v2/groups/{id}/bot_state`                        | Зарезервировано — только по приглашению для приложения бота                                                                                                                                       |
| `qq_list_join_requests`                                   | `GET /v2/groups/{id}/join_request_list`                | Бот является администратором группы                                                                                                                                                               |

| `qq_list_join_approval_strategies`                        | `GET /v2/groups/join_approval_strategy`                | Уровень бота, не на группу                                                                                                                                                                        |
| `qq_create_join_approval_strategy`                        | `POST /v2/groups/join_approval_strategy`               | Один из `group_openids` / `group_ids`; не более 20 стратегий на бота                                                                                                                              |
| `qq_update_join_approval_strategy`                        | `PATCH .../join_approval_strategy/{id}`                | Id группы должны использовать форму, с которой стратегия была создана                                                                                                                             |
| `qq_delete_join_approval_strategy`                        | `DELETE .../join_approval_strategy/{id}`               | —                                                                                                                                                                                                |
| `qq_execute_join_approval_strategy`                       | `POST .../join_approval_strategy/{id}/execute`         | Запускает полное сканирование; асинхронно, около 10 минут                                                                                                                                         |
| `qq_set_join_approval_whitelist`                          | `POST .../join_approval_strategy/{id}/whitelist_users` | До 10 000 номеров за вызов, 100 000 на стратегию                                                                                                                                                  |
| `qq_list_group_members`                                   | `GET /v2/groups/{id}/members`                          | Зарезервировано — только по приглашению на платформе, до 30 участников на страницу                                                                                                                |
| `qq_get_group_member`                                     | `GET /v2/groups/{id}/members/{member_openid}`          | Зарезервировано — только по приглашению                                                                                                                                                           |
| `qq_kick_member`                                          | `POST /v2/groups/{id}/batch_remove_members`            | Зарезервировано — только по приглашению, до 20 участников, опциональный черный список                                                                                                             |
| `qq_list_member_blacklist` / `qq_update_member_blacklist` | `GET`/`POST /v2/groups/{id}/member_blacklist`          | Зарезервировано — только по приглашению; участник, все еще находящийся в группе, не может быть добавлен в черный список                                                                           |

"Зарезервированные" инструменты подключены и вызываемы, но открытая платформа QQ в настоящее время отвечает `11253`, если приложение бота не было добавлено в белый список, поэтому агент сообщает об отказе платформы вместо предположения об успехе. Каждый инструмент сообщает код ошибки платформы и то, что он означает, поэтому агент может отличить "бот не является администратором группы" от "сообщение больше не может быть отозвано" от "этому приложению не разрешено вызывать этот эндпоинт".

Чтобы групповое действие достигло сообщения участника по имени, канал запоминает последние входящие сообщения на чат. `moderationRecallWindowMs` ограничивает, как долго запись хранится, и по умолчанию равен `-1` (без ограничения по времени), поэтому запись остается разрешимой, пока ограничение на чат или очистка 256 чатов не вытеснит ее; перезапуск полностью сбрасывает память, и нет ничего для отзыва по участнику до прибытия новых сообщений. Он также хранит только сообщения, которые шлюз действительно доставил: с незаданным `groupAllPolicy` бот получает только @-упоминания (и личные сообщения), поэтому отзыв по участнику может достичь **не @** сообщения обычного участника только когда `groupAllPolicy` равен `"keyword"`, `"all"` или `"log"`; @-упоминания, которые доставляет шлюз, отслеживаются в любом случае. Модель может назвать участника только по полному `member_openid`, когда `allowMention` включен (по умолчанию): с `allowMention: false` транскрипт несет усеченное имя отправителя вместо этого, поэтому работает только явный `message_id`. Отзыв `member_openid` разрешен только для собственного отправителя хода или на ходе без отправителя-участника (например, ход, инициированный оператором), поэтому один участник не может цензурировать сообщение другого через токен администратора бота. Каждый вызов должен указывать цель: `member_openid` отзывает последнее отслеженное сообщение этого участника, `message_id` отзывает явный id. Нет неявной цели, и инструмент никогда не отзывает собственные сообщения бота — поэтому прямой чат, где платформа отзывает только их, не поддерживается. Успешный отзыв сообщает id сообщения, которое он уничтожил, и удаляет этот id из кольца на чат, поэтому второй отзыв по участнику достигает предыдущего сообщения вместо повторной попытки уничтоженного; неудачный отзыв сохраняет запись, поэтому та же цель может быть повторена.

Каждый экземпляр канала владеет своими инструментами: один бридж может обслуживать несколько каналов, и инструмент предлагается только сессиям канала, который его зарегистрировал, поэтому два канала QQ в одном процессе никогда не действуют на чаты или учетные данные друг друга.

## Поддержка Markdown

Канал QQ Bot поддерживает форматирование Markdown (`msg_type=2`). Ответы агента в Markdown отправляются как есть, а QQ отображает их с богатым форматированием (жирный шрифт, курсив, блоки кода, ссылки, списки).

Если сервер QQ отклоняет сообщение в Markdown по какой-либо причине, канал автоматически повторяет отправку как обычный текст — так ваши сообщения всегда доходят, даже если возможность использования Markdown ограничена на стороне сервера.

Это противоположно каналу WeChat, который удаляет весь Markdown. Вы можете позволить агенту использовать полный Markdown в канале QQ.

## Изображения, видео и файлы

Пользователи могут отправлять боту изображения, видео, файлы и голосовые сообщения. Изображение передаётся агенту как визуальный вход, так что агент видит саму картинку — скриншоты, сообщения об ошибках и диаграммы работают — и тот же файл также сохраняется во временный локальный путь на случай, если модель не поддерживает изображения. Видео, файл или голосовое сообщение сохраняется во временный локальный путь, и агенту сообщается этот путь.

Медиа-сообщение не требует текста — сообщение только с изображением, только с видео, только с файлом или только с голосом начинает ход, и канал использует `(image)`, `(video)`, `(file)` или `(voice)` в качестве заполнителя. Если сообщение содержит текст, этот текст сохраняется как подпись.

Файл — это всё, что платформа доставляет как `content_type: file` — документы Word, PDF, таблицы, архивы, исходные файлы. QQ не сообщает MIME-тип для файла, поэтому канал сохраняет собственное расширение отправителя (ограниченное буквами и цифрами, с фолбэком на `.bin`, если расширение отсутствует) и сохраняет байты в `channel-files/<uuid>/` во временном каталоге системы; инструмент чтения агента использует это расширение, чтобы определить, как открыть документ.

Голосовое сообщение приходит как `content_type: voice`. Помимо оригинального SILK URL, QQ предоставляет `voice_wav_url` — тот же аудио, уже конвертированный в WAV — и канал предпочитает его; когда платформа не отправляет его, канал использует фолбэк на оригинальный URL. Байты сохраняются в `channel-files/<uuid>/` как `qq_voice.wav` или `qq_voice.silk`, когда использовался оригинальный SILK URL, и агенту сообщается этот путь. ASR-текст платформы не используется; агент работает из сохранённого аудиофайла.

- Изображения ограничены 8 МБ, видео, файлы и голосовые сообщения — 20 МБ, и обрабатывается не более пяти вложений на сообщение. Всё, что больше, пропускается и логируется в stderr канала.
- Скачанные файлы не удаляются. Они остаются во временном каталоге системы, который очищается по собственному расписанию системы.

Ввод изображений требует модели, принимающей изображения. Объявите возможность, если модель мультимодальна, но не распознана по имени. Это поле должно находиться в записи провайдера, обслуживающего модель, поскольку значение `model.generationConfig` верхнего уровня игнорируется для моделей провайдера:

```json
{
  "modelProviders": {
    "openai": [
      {
        "id": "your-model-id",
        "baseUrl": "https://example.invalid/v1",
        "generationConfig": {
          "modalities": { "image": true }
        }
      }
    ]
  }
}
```

При использовании текстовой модели агент получает уведомление «unsupported image» плюс сохранённый путь вместо изображения.

Отправка изображений, видео, файлов или голосовых сообщений обратно в QQ не поддерживается.

## Управление токенами

Токены доступа истекают примерно через 2 часа. Канал автоматически обновляет их при достижении 80% времени жизни (TTL) (обычно ~1,6 часа). Если обновление не удалось, оно повторяется через 60 секунд.

Обновление токенов продолжается после переподключения WebSocket — канал никогда не отключается из-за истекшего токена, пока AppID и AppSecret остаются действительными.

## Устойчивость соединения

- **Автопереподключение:** При разрыве WebSocket канал повторяет попытку с экспоненциальной задержкой (до 20 попыток, максимум 30 секунд между повторениями).
- **Восстановление сессии:** Если WebSocket ненадолго отключается, канал использует код операции `RESUME` QQ для восстановления сессии без потери сообщений, находящихся в процессе передачи.
- **Продолжение контекста между серверами:** Состояние чатов и маршрутизация сохраняются на диск. Если демон перезапускается, разговоры продолжаются с того же места.
- **Мониторинг heartbeat:** Тайм-ауты HEARTBEAT_ACK обнаруживаются и вызывают принудительное переподключение, чтобы избежать «зомби»-соединений.
- **Дедупликация сообщений:** Повторно отправленные сообщения после переподключения обнаруживаются и пропускаются.

## Советы

- **Свободно используйте Markdown** — В отличие от WeChat, QQ отображает Markdown нативно. Жирный шрифт, блоки кода, списки и ссылки — всё работает.
- **Держите ответы в пределах 2000 символов** — Более длинные ответы автоматически разбиваются на части. Добавление подсказки о длине в инструкции помогает агенту быть лаконичным.
- **Sandbox для тестирования** — Установите `"sandbox": true`, чтобы использовать sandbox API во время разработки. На рабочие сообщения это не повлияет.
- **Ограничьте доступ** — Используйте `privatePolicy: "allowlist"` для фиксированного набора пользователей QQ или `"pairing"` для подтверждения новых пользователей из CLI. Подробнее см. в [DM Pairing](./overview#dm-pairing).

## Устранение неполадок

### Бот не отвечает

- Проверьте вывод в терминале на наличие ошибок.
- Убедитесь, что канал запущен (`qwen channel status`).
- Если используется `privatePolicy: "allowlist"`, проверьте, что ваш QQ ID находится в `allowedUsers`.
- При первом запуске в терминале появится QR-код — отсканируйте его с помощью приложения QQ.

### Бот не отвечает в группах

- Проверьте, что `groupPolicy` установлено в `"allowlist"`, `"pairing"` или `"open"` (по умолчанию `"disabled"`).
- Если используется `"pairing"`, убедитесь, что запрос на спаривание группы был одобрен.
- **Вы должны @упомянуть бота** — QQ доставляет только сообщения с тегом бота.
- Убедитесь, что бот добавлен в группу.

### Вход по QR-коду завис

- QR-код отображается в терминале. Отсканируйте его с помощью мобильного приложения QQ (Я → Сканировать).
- Если QR-код истёк (обычно через несколько минут), перезапустите канал, чтобы получить новый.

### Сообщения в Markdown отображаются как обычный текст

- Возможно, сервер QQ отклонил сообщение в Markdown, и канал незаметно переключился на обычный текст. Проверьте терминал на наличие логов `"Markdown rejected"`.
- На платформе QQ Bot Open Platform это редкость, но может произойти, если возможность использования Markdown ограничена на стороне сервера.

### Срок действия токена истёк после долгого простоя

- Если канал был отключён более 2 часов, токен доступа истечёт. При переподключении канал получает новый токен — никаких действий не требуется.
- Если сам AppSecret стал недействительным (например, был изменён на портале разработчика), обновите поле `appSecret` или удалите файл `~/.qwen/channels/<name>-credentials.json`, чтобы повторно запустить вход по QR-коду.
