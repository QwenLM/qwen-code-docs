# Конфигурация Qwen Code

> [!tip]
>
> **Аутентификация / API-ключи:** Аутентификация (API-ключ, Alibaba Cloud Coding Plan) и переменные окружения, связанные с авторизацией (например, `OPENAI_API_KEY`), описаны в разделе **[Аутентификация](../configuration/auth)**.

> [!note]
>
> **Примечание о новом формате конфигурации**: Формат файла `settings.json` обновлен до новой, более структурированной версии. Старый формат будет автоматически мигрирован.
> Qwen Code предлагает несколько способов настройки своего поведения, включая переменные окружения, аргументы командной строки и файлы настроек. В этом документе описаны различные методы конфигурации и доступные параметры.

## Уровни конфигурации

Конфигурация применяется в следующем порядке приоритета (меньшие номера переопределяются старшими):

| Уровень | Источник конфигурации | Описание |
| ----- | ---------------------- | ------------------------------------------------------------------------------- |
| 1 | Значения по умолчанию | Жестко заданные значения по умолчанию в приложении |
| 2 | Системный файл настроек по умолчанию | Общесистемные настройки по умолчанию, которые могут быть переопределены другими файлами настроек |
| 3 | Файл пользовательских настроек | Глобальные настройки для текущего пользователя |
| 4 | Файл настроек проекта | Настройки, специфичные для проекта |
| 5 | Системный файл настроек | Общесистемные настройки, переопределяющие все остальные файлы настроек |
| 6 | Переменные окружения | Общесистемные или специфичные для сессии переменные, которые могут загружаться из файлов `.env` |
| 7 | Аргументы командной строки | Значения, передаваемые при запуске CLI |

## Файлы настроек

Qwen Code использует JSON-файлы настроек для персистентной конфигурации. Предусмотрено четыре расположения для этих файлов:

| Тип файла | Расположение | Область действия |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Системный файл настроек по умолчанию | Linux: `/etc/qwen-code/system-defaults.json`<br>Windows: `C:\ProgramData\qwen-code\system-defaults.json`<br>macOS: `/Library/Application Support/QwenCode/system-defaults.json` <br>Путь можно переопределить с помощью переменной окружения `QWEN_CODE_SYSTEM_DEFAULTS_PATH`. | Обеспечивает базовый уровень общесистемных настроек по умолчанию. Эти настройки имеют наименьший приоритет и предназначены для переопределения пользовательскими, проектными или системными настройками. |
| Файл пользовательских настроек | `~/.qwen/settings.json` (где `~` — это ваша домашняя директория). | Применяется ко всем сессиям Qwen Code для текущего пользователя. |
| Файл настроек проекта | `.qwen/settings.json` в корневой директории вашего проекта. | Применяется только при запуске Qwen Code из этого конкретного проекта. Настройки проекта переопределяют пользовательские настройки. |
| Системный файл настроек | Linux: `/etc/qwen-code/settings.json` <br>Windows: `C:\ProgramData\qwen-code\settings.json` <br>macOS: `/Library/Application Support/QwenCode/settings.json`<br>Путь можно переопределить с помощью переменной окружения `QWEN_CODE_SYSTEM_SETTINGS_PATH`. | Применяется ко всем сессиям Qwen Code в системе для всех пользователей. Системные настройки переопределяют пользовательские и проектные настройки. Может быть полезно для системных администраторов на предприятиях, чтобы контролировать настройки Qwen Code у пользователей. |

> [!note]
>
> **Примечание о переменных окружения в настройках:** Строковые значения в ваших файлах `settings.json` могут ссылаться на переменные окружения, используя синтаксис `$VAR_NAME` или `${VAR_NAME}`. Эти переменные будут автоматически разрешены при загрузке настроек. Например, если у вас есть переменная окружения `MY_API_TOKEN`, вы можете использовать её в `settings.json` так: `"apiKey": "$MY_API_TOKEN"`.

### Директория `.qwen` в вашем проекте

Помимо файла настроек проекта, директория `.qwen` проекта может содержать другие специфичные для проекта файлы, связанные с работой Qwen Code, такие как:

- [Пользовательские профили песочницы](../features/sandbox) (например, `.qwen/sandbox-macos-custom.sb`, `.qwen/sandbox.Dockerfile`).
- [Навыки агента (Agent Skills)](../features/skills) в директории `.qwen/skills/` (каждый навык — это директория, содержащая файл `SKILL.md`).

### Миграция конфигурации

Qwen Code автоматически мигрирует устаревшие параметры конфигурации в новый формат. Перед миграцией старые файлы настроек резервируются. Следующие параметры были переименованы из негативных (`disable*`) в позитивные (`enable*`):

| Старый параметр | Новый параметр | Примечания |
| ---------------------------------------- | ------------------------------------------- | ---------------------------------- |
| `disableAutoUpdate` + `disableUpdateNag` | `general.enableAutoUpdate` | Объединены в один параметр |
| `disableLoadingPhrases` | `ui.accessibility.enableLoadingPhrases` | |
| `disableFuzzySearch` | `context.fileFiltering.enableFuzzySearch` | |
| `disableCacheControl` | `model.generationConfig.enableCacheControl` | |

> [!note]
>
> **Инверсия булевых значений:** При миграции булевы значения инвертируются (например, `disableAutoUpdate: true` становится `enableAutoUpdate: false`).

#### Политика объединения для `disableAutoUpdate` и `disableUpdateNag`

Если оба устаревших параметра присутствуют с разными значениями, миграция выполняется по следующему правилу: если **либо** `disableAutoUpdate`, **либо** `disableUpdateNag` равен `true`, то `enableAutoUpdate` становится `false`:

| `disableAutoUpdate` | `disableUpdateNag` | Мигрированный `enableAutoUpdate` |
| ------------------- | ------------------ | --------------------------- |
| `false` | `false` | `true` |
| `false` | `true` | `false` |
| `true` | `false` | `false` |
| `true` | `true` | `false` |

### Доступные параметры в `settings.json`

Параметры организованы по категориям. Большинство параметров должно находиться внутри соответствующего объекта категории верхнего уровня в вашем файле `settings.json`. Некоторые параметры верхнего уровня, такие как `proxy` и `plansDirectory`, остаются прямыми корневыми ключами для обеспечения совместимости.

**timeout (таймаут запроса):**

`timeout` — это таймаут каждого запроса в миллисекундах (по умолчанию `120000`). Установите значение `0`, чтобы отключить таймаут запроса (согласно соглашению `QWEN_STREAM_IDLE_TIMEOUT_MS=0`) и избежать прерывания запроса. Также может быть задан через переменную окружения `QWEN_CODE_API_TIMEOUT_MS`. Это отличается от `QWEN_STREAM_IDLE_TIMEOUT_MS`, который ограничивает время бездействия _между_ передаваемыми чанками.

**max_tokens (лимит токенов на вывод):**

Если не заданы ни `samplingParams.max_tokens`, ни `QWEN_CODE_MAX_OUTPUT_TOKENS`, Qwen Code обычно использует заявленный лимит вывода выбранной модели в качестве лимита вывода по умолчанию для запроса. Если ответ всё равно достигает этого лимита, Qwen Code может повторить попытку с повышенным лимитом (с нижним порогом 64K), а затем продолжить работу в следующих итерациях.

Для OpenAI-совместимых провайдеров `samplingParams` также служит обходным механизмом передачи параметров: если он задан, его ключи передаются без изменений, и Qwen Code не генерирует значение `max_tokens` по умолчанию. Используйте это для специфичных для провайдера параметров, таких как `max_completion_tokens`.

Чтобы принудительно установить фиксированный лимит вывода, задайте `samplingParams.max_tokens` в настройках или используйте переменную окружения `QWEN_CODE_MAX_OUTPUT_TOKENS`. Явные лимиты отключают автоматическое увеличение лимита токенов вывода.

**toolResultContentFormat:**

Управляет сериализацией результатов инструментов, содержащих только текст, в OpenAI-совместимых запросах. Значение по умолчанию `"parts"` сохраняет стандартную структуру массива частей контента. Установите `"string"` только для устаревших OpenAI-совместимых сред выполнения, шаблоны инструментов которых игнорируют текстовые части контента, например, старые шаблоны GLM-5.1 vLLM/SGLang. Медиафайлы, возвращаемые инструментами, по-прежнему управляются параметром `splitToolMedia`.

**contextWindowSize:**

Переопределяет размер контекстного окна по умолчанию для выбранной модели. Qwen Code определяет контекстное окно, используя встроенные значения по умолчанию на основе сопоставления имени модели, с постоянным резервным значением. Используйте эту настройку, когда фактический лимит контекста провайдера отличается от значения по умолчанию в Qwen Code. Это значение определяет предполагаемую максимальную ёмкость контекста модели, а не лимит токенов для каждого запроса.

Если выбранная модель определена в `modelProviders`, задайте `contextWindowSize` в `generationConfig` этой записи провайдера, а не в `model.generationConfig` верхнего уровня. Записи моделей провайдеров изолированы, поэтому настройки генерации верхнего уровня не заполняют отсутствующие поля провайдера.

**modalities:**

Переопределяет автоматически обнаруженные входные модальности для выбранной модели. Qwen Code автоматически определяет поддерживаемые модальности (изображения, PDF, аудио, видео) на основе сопоставления шаблонов имён моделей. Используйте эту настройку, если автоопределение работает некорректно — например, чтобы включить `pdf` для модели, которая его поддерживает, но не распознаётся. Формат: `{ "image": true, "pdf": true, "audio": true, "video": true }`. Пропустите ключ или установите для него значение `false` для неподдерживаемых типов.

**customHeaders:**

Позволяет добавлять пользовательские HTTP-заголовки ко всем API-запросам. Это полезно для трассировки запросов, мониторинга, маршрутизации API-шлюзов или когда разным моделям требуются разные заголовки. Для моделей провайдеров определите `customHeaders` в `modelProviders[].generationConfig.customHeaders`. Для моделей среды выполнения без соответствующей записи провайдера определите их в `model.generationConfig.customHeaders`. Слияние между этими двумя уровнями не происходит.

Поле `extra_body` позволяет добавлять пользовательские параметры в тело запроса, отправляемого в API. Это полезно для специфичных для провайдера опций, которые не покрываются стандартными полями конфигурации. **Примечание: Это поле поддерживается только для OpenAI-совместимых провайдеров (`openai`, `qwen-oauth`). Оно игнорируется для провайдеров Anthropic и Gemini.** Для моделей провайдеров определите `extra_body` в `modelProviders[].generationConfig.extra_body`. Для моделей среды выполнения без соответствующей записи провайдера определите его в `model.generationConfig.extra_body`.

#### Устранение проблем с производительностью поиска файлов

Если вы столкнулись с проблемами производительности при поиске файлов (например, при использовании автодополнения с `@`), особенно в проектах с очень большим количеством файлов, вот несколько действий, которые можно предпринять в порядке рекомендуемого приоритета:

1. **Используйте файл игнорирования:** Создайте файл `.qwenignore` или настроенный пользовательский файл игнорирования в корне проекта, чтобы исключить директории с большим количеством файлов, на которые вам не нужно ссылаться (например, артефакты сборки, логи, `node_modules`). Сокращение общего количества индексируемых файлов — самый эффективный способ повысить производительность.
2. **Отключите нечеткий поиск:** Если игнорирования файлов недостаточно, вы можете отключить нечеткий поиск, установив для `enableFuzzySearch` значение `false` в файле `settings.json`. При этом будет использоваться более простой алгоритм сопоставления без нечеткого поиска, что может работать быстрее.
3. **Отключите рекурсивный поиск файлов:** В крайнем случае вы можете полностью отключить рекурсивный поиск файлов, установив для `enableRecursiveFileSearch` значение `false`. Это самый быстрый вариант, так как он исключает рекурсивный обход проекта. Однако это означает, что при использовании автодополнения с `@` вам придется вводить полный путь к файлам.

#### permissions

Система разрешений (permissions) предоставляет детальный контроль над тем, какие инструменты могут запускаться, какие требуют подтверждения, а какие заблокированы.

**Приоритет принятия решений (от высшего к низшему): `deny` > `ask` > `allow` > _(по умолчанию/интерактивный режим)_**

Срабатывает первое совпавшее правило. Правила имеют формат `"ToolName"` или `"ToolName(specifier)"`.

| Настройка             | Тип             | Описание                                                                                                      | По умолчанию     |
| ------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------- | ----------- |
| `permissions.allow` | array of strings | Правила для автоматически одобренных вызовов инструментов (подтверждение не требуется). Объединяются из всех областей видимости (user + project + system). | `undefined` |
| `permissions.ask`   | array of strings | Правила для вызовов инструментов, которые всегда требуют подтверждения пользователя. Имеют приоритет над `allow`.                         | `undefined` |
| `permissions.deny`  | array of strings | Правила для заблокированных вызовов инструментов. Наивысший приоритет — переопределяют как `allow`, так и `ask`.                               | `undefined` |

**Псевдонимы инструментов (в правилах работает любой из них):**

| Псевдоним                 | Канонический инструмент      | Примечания                     |
| --------------------- | ------------------- | ------------------------- |
| `Bash`, `Shell`       | `run_shell_command` |                           |
| `Read`, `ReadFile`    | `read_file`         | Мета-категория — см. ниже |
| `Edit`, `EditFile`    | `edit`              | Мета-категория — см. ниже |
| `Write`, `WriteFile`  | `write_file`        |                           |
| `NotebookEdit`        | `notebook_edit`     |                           |
| `NotebookEditTool`    | `notebook_edit`     |                           |
| `Grep`, `SearchFiles` | `grep_search`       |                           |
| `Glob`, `FindFiles`   | `glob`              |                           |
| `ListFiles`           | `list_directory`    |                           |
| `WebFetch`            | `web_fetch`         |                           |
| `Agent`               | `task`              |                           |
| `Skill`               | `skill`             |                           |

**Мета-категории:**

Некоторые имена правил автоматически охватывают несколько инструментов:

| Имя правила | Охватываемые инструменты                                        |
| --------- | ---------------------------------------------------- |
| `Read`    | `read_file`, `grep_search`, `glob`, `list_directory` |
| `Edit`    | `edit`, `write_file`, `notebook_edit`                |

> [!important]
> `Read(/path/**)` соответствует **всем четырем** инструментам чтения (чтение файла, grep, glob и список директорий).
> Чтобы ограничить только чтение файлов, используйте `ReadFile(/path/**)` или `read_file(/path/**)`.

**Примеры синтаксиса правил:**

| Правило                          | Значение                                                        |
| ----------------------------- | -------------------------------------------------------------- |
| `"Bash"`                      | Все shell-команды                                             |
| `"Bash(git *)"`               | Shell-команды, начинающиеся с `git` (граница слова: НЕ `gitk`) |
| `"Bash(git push *)"`          | Shell-команды вроде `git push origin main`                     |
| `"Bash(npm run *)"`           | Любой скрипт `npm run`                                           |
| `"Read"`                      | Все операции чтения файлов (read, grep, glob, list)              |
| `"Read(./secrets/**)"`        | Читать любой файл внутри `./secrets/` рекурсивно                   |
| `"Edit(/src/**/*.ts)"`        | Редактировать TypeScript файлы в корне проекта `/src/`               |
| `"WebFetch(api.example.com)"` | Загружать данные с `api.example.com` и всех его поддоменов            |
| `"mcp__puppeteer"`            | Все инструменты с MCP-сервера puppeteer                        |

**Префиксы паттернов путей:**

| Префикс | Значение                               | Пример             |
| ------ | ------------------------------------- | ------------------- |
| `//`   | Абсолютный путь от корня файловой системы    | `//etc/passwd`      |
| `~/`   | Относительно домашней директории            | `~/Documents/*.pdf` |
| `/`    | Относительно корня проекта              | `/src/**/*.ts`      |
| `./`   | Относительно текущей рабочей директории | `./secrets/**`      |
| (нет) | То же, что и `./`                          | `secrets/**`        |

**Предотвращение обхода shell-командами:**

Правила разрешений для `Read`, `Edit` и `WebFetch` также применяются, когда агент запускает эквивалентные shell-команды. Например, если `Read(./.env)` находится в `deny`, агент не сможет обойти это с помощью `cat .env` в shell-команде. Поддерживаемые shell-команды включают `cat`, `grep`, `curl`, `wget`, `cp`, `mv`, `rm`, `chmod` и многие другие. Неизвестные/безопасные команды (например, `git`) не подпадают под действие правил для файлов/сети.

**Миграция с устаревших настроек:**

| Устаревшая настройка  | Эквивалентное правило `permissions`   | Примечания                                                        |
| --------------- | ------------------------------- | ------------------------------------------------------------ |
| `tools.allowed` | `permissions.allow`             | Автоматически мигрирует при первой загрузке                                  |
| `tools.exclude` | `permissions.deny`              | Автоматически мигрирует при первой загрузке                                  |
| `tools.core`    | `permissions.allow` (allowlist) | Автоматически мигрирует; не указанные в списке инструменты отключаются на уровне реестра |

**Пример конфигурации:**

```json
{
  "permissions": {
    "allow": ["Bash(git *)", "Bash(npm run *)", "Read(//Users/alice/code/**)"],
    "ask": ["Bash(git push *)", "Edit"],
    "deny": ["Bash(rm -rf *)", "Read(.env)", "WebFetch(malicious.com)"]
  }
}
```

> [!tip]
> Используйте `/permissions` в интерактивном CLI для просмотра, добавления и удаления правил без прямого редактирования `settings.json`.

| ------------------------ | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| `slashCommands.disabled` | array of strings | Имена slash-команд, которые нужно скрыть и отказаться их выполнять. Сопоставляются без учета регистра с итоговым именем команды (для команд расширений это уточненная форма, например, `myext.deploy`). **Объединяются как объединение (union) across scopes**, поэтому настройки рабочего пространства могут добавлять, но не удалять записи, определенные в настройках пользователя или системы. | `undefined` |

Тот же самый список блокировок (denylist) также может быть задан через флаг CLI
`--disabled-slash-commands` (через запятую или повторением) и переменную окружения
`QWEN_DISABLED_SLASH_COMMANDS`; значения из всех трех источников объединяются.

**Пример — блокировка встроенных команд для изолированного развертывания:**

```json
{
  "slashCommands": {
    "disabled": ["auth", "mcp", "extensions", "ide", "quit"]
  }
}
```

При использовании этих значений в системном `settings.json` (`/etc/qwen-code/settings.json`
или `QWEN_CODE_SYSTEM_SETTINGS_PATH`), пользователи не смогут уменьшить список блокировок
из своей области видимости, а отключенные команды не будут отображаться в автодополнении или
выполняться при вводе.

> [!note]
> Эта настройка управляет только slash-командами (например, `/auth`, `/mcp`). Она не
> влияет на разрешения инструментов — для этого см. `permissions.deny`. Она также не
> перехватывает сочетания клавиш, такие как `Ctrl+C` или `Esc`.

#### mcpServers

Настраивает подключения к одному или нескольким серверам Model-Context Protocol (MCP) для обнаружения и использования пользовательских инструментов. Qwen Code пытается подключиться к каждому настроенному MCP-серверу для обнаружения доступных инструментов. Если несколько MCP-серверов предоставляют инструмент с одинаковым именем, к именам инструментов будет добавлен префикс в виде псевдонима сервера, определенного вами в конфигурации (например, `serverAlias__actualToolName`), чтобы избежать конфликтов. Обратите внимание, что система может удалять некоторые свойства схемы из определений инструментов MCP для обеспечения совместимости. Должен быть указан хотя бы один из параметров: `command`, `url` или `httpUrl`. Если указано несколько, порядок приоритета следующий: `httpUrl`, затем `url`, затем `command`.

| `mcpServers.<SERVER_NAME>.url`          | string           | URL MCP-сервера, использующего Server-Sent Events (SSE) для связи.                                                                                                                                                                                                   | Да            |
| `mcpServers.<SERVER_NAME>.httpUrl`      | string           | URL MCP-сервера, использующего потоковый HTTP (streamable HTTP) для связи.                                                                                                                                                                                           | Да            |
| `mcpServers.<SERVER_NAME>.headers`      | object           | Карта HTTP-заголовков, отправляемых с запросами к `url` или `httpUrl`.                                                                                                                                                                                               | Да            |

Инструменты, указанные здесь, не будут доступны модели, даже если они предоставляются сервером. **Примечание:** `excludeTools` имеет приоритет над `includeTools` — если инструмент есть в обоих списках, он будет исключен. | Да            |

## История оболочки

CLI хранит историю запускаемых вами команд оболочки. Чтобы избежать конфликтов между различными проектами, эта история сохраняется в каталоге, специфичном для проекта, внутри вашей домашней папки пользователя.

- **Расположение:** `~/.qwen/tmp/<project_hash>/shell_history`
  - `<project_hash>` — это уникальный идентификатор, сгенерированный на основе корневого пути вашего проекта.
  - История хранится в файле с именем `shell_history`.

## Переменные окружения и файлы `.env`

Переменные окружения — это распространенный способ настройки приложений, особенно для конфиденциальной информации (например, токенов) или параметров, которые могут меняться в зависимости от окружения.

Qwen Code может автоматически загружать переменные окружения из файлов `.env`.
Информацию о переменных, связанных с аутентификацией (например, `OPENAI_*`), и рекомендуемом подходе с использованием `.qwen/.env` см. в разделе **[Аутентификация](../configuration/auth)**.

> [!tip]
>
> **Исключение переменных окружения:** Некоторые переменные окружения (например, `DEBUG` и `DEBUG_MODE`) по умолчанию автоматически исключаются из файлов `.env` проекта, чтобы предотвратить вмешательство в поведение CLI. Переменные из файлов `.qwen/.env` никогда не исключаются. Вы можете настроить это поведение с помощью параметра `advanced.excludedEnvVars` в вашем файле `settings.json`.

## Аргументы командной строки

Аргументы, переданные непосредственно при запуске CLI, могут переопределять другие конфигурации для данного сеанса.

При выборе образа песочницы приоритет следующий: `--sandbox-image` > `QWEN_SANDBOX_IMAGE` > `tools.sandboxImage` > встроенный образ по умолчанию.

Поддерживаются абсолютные пути, относительные пути и раскрытие `~`. Пример: `qwen --openai-logging-dir "~/qwen-logs" --openai-logging` |
## Контекстные файлы (Иерархический контекст инструкций)

Хотя контекстные файлы (по умолчанию `QWEN.md`, но настраиваемые через параметр `context.fileName`) не являются строгой конфигурацией _поведения_ CLI, они критически важны для настройки _контекста инструкций_ (также называемого "памятью"). Эта мощная функция позволяет передавать ИИ специфичные для проекта инструкции, руководства по стилю кода или любую другую важную справочную информацию, делая его ответы более точными и адаптированными под ваши задачи. CLI включает элементы интерфейса, например, индикатор в футере, показывающий количество загруженных контекстных файлов, чтобы вы всегда были в курсе активного контекста.

- **Назначение:** Эти Markdown-файлы содержат инструкции, рекомендации или контекст, о которых модель Qwen должна знать во время взаимодействия. Система разработана для иерархического управления этим контекстом инструкций.

### Пример содержимого контекстного файла (например, `QWEN.md`)

Вот концептуальный пример того, что может содержать контекстный файл в корне TypeScript-проекта:

```markdown
# Проект: Моя крутая TypeScript-библиотека

## Общие инструкции:
- При генерации нового TypeScript-кода, пожалуйста, соблюдайте существующий стиль кодирования.
- Убедитесь, что все новые функции и классы имеют JSDoc-комментарии.
- По возможности используйте парадигмы функционального программирования.
- Весь код должен быть совместим с TypeScript 5.0 и Node.js 22+.

## Стиль кода:
- Используйте 2 пробела для отступов.
- Имена интерфейсов должны иметь префикс `I` (например, `IUserService`).
- Приватные члены классов должны иметь префикс в виде подчеркивания (`_`).
- Всегда используйте строгое равенство (`===` и `!==`).

## Специфичный компонент: `src/api/client.ts`
- Этот файл обрабатывает все исходящие API-запросы.
- При добавлении новых функций для вызова API убедитесь, что они включают надежную обработку ошибок и логирование.
- Используйте существующую утилиту `fetchWithRetry` для всех GET-запросов.

## Касательно зависимостей:
- Избегайте добавления новых внешних зависимостей, если это не абсолютно необходимо.
- Если новая зависимость требуется, пожалуйста, укажите причину.
```

Этот пример демонстрирует, как можно предоставить общий контекст проекта, специфичные соглашения по написанию кода и даже заметки о конкретных файлах или компонентах. Чем более релевантными и точными будут ваши контекстные файлы, тем лучше ИИ сможет вам помочь. Настоятельно рекомендуется использовать специфичные для проекта контекстные файлы для установления соглашений и контекста.

- **Иерархическая загрузка и приоритеты:** CLI реализует иерархическую систему памяти, загружая контекстные файлы (например, `QWEN.md`) из нескольких мест. Содержимое файлов, находящихся ниже в этом списке (более специфичных), обычно переопределяет или дополняет содержимое файлов, находящихся выше (более общих). Точный порядок конкатенации и итоговый контекст можно проверить в диалоговом окне `/memory`. Типичный порядок загрузки:
  1. **Глобальный контекстный файл:**
     - Расположение: `~/.qwen/<configured-context-filename>` (например, `~/.qwen/QWEN.md` в домашней директории пользователя).
     - Область действия: Предоставляет инструкции по умолчанию для всех ваших проектов.
  2. **Контекстные файлы в корне проекта и родительских директориях:**
     - Расположение: CLI ищет настроенный контекстный файл в текущей рабочей директории, а затем в каждой родительской директории вплоть до корня проекта (определяется по наличию папки `.git`) или вашей домашней директории.
     - Область действия: Предоставляет контекст, относящийся ко всему проекту или его значительной части.
- **Конкатенация и индикация в UI:** Содержимое всех найденных контекстных файлов объединяется (с разделителями, указывающими на их происхождение и путь) и передается как часть системного промпта. В футере CLI отображается количество загруженных контекстных файлов, что дает быстрое визуальное представление об активном контексте инструкций.
- **Импорт содержимого:** Вы можете модуляризовать свои контекстные файлы, импортируя другие Markdown-файлы с помощью синтаксиса `@path/to/file.md`. Подробнее см. в [документации по памяти](../features/memory.md).
- **Команды для управления памятью:**
  - Используйте `/memory` для открытия диалогового окна управления памятью.
  - Обновите память из диалогового окна, чтобы повторно сканировать и перезагрузить контекстные файлы из всех настроенных мест.
  - См. [документацию по командам](../features/commands.md) для получения полной информации о команде `/memory`.

Понимая и используя эти уровни конфигурации и иерархическую природу контекстных файлов, вы можете эффективно управлять памятью ИИ и адаптировать ответы Qwen Code под свои конкретные задачи и проекты.

## Песочница

Qwen Code может выполнять потенциально небезопасные операции (например, команды оболочки и изменение файлов) в изолированной среде (песочнице) для защиты вашей системы.

[Песочница](../features/sandbox) отключена по умолчанию, но вы можете включить её несколькими способами:

- С помощью флага `--sandbox` или `-s`.
- Установив переменную окружения `QWEN_SANDBOX`.
- Настроив `tools.sandbox` в настройках.

> ⚠️ **`--yolo` _не_ включает песочницу автоматически.** Режим YOLO только автоматически одобряет вызовы инструментов; песочницу всё равно нужно явно включить через `--sandbox`, `QWEN_SANDBOX` или `tools.sandbox`. При запуске в headless / неинтерактивном режиме с `--yolo` (или `--approval-mode=yolo`) и без песочницы модель может выполнять инструменты shell, write и edit с уровнем привилегий текущего процесса — в этом случае Qwen Code выводит предупреждение в stderr. После оценки рисков вы можете подавить его с помощью `QWEN_CODE_SUPPRESS_YOLO_WARNING=1`.

По умолчанию используется предварительно собранный Docker-образ `qwen-code-sandbox`.

Для специфичных для проекта требований к песочнице вы можете создать собственный Dockerfile по пути `.qwen/sandbox.Dockerfile` в корневой директории вашего проекта. Этот Dockerfile может быть основан на базовом образе песочницы:

```dockerfile
FROM qwen-code-sandbox
# Добавьте сюда свои пользовательские зависимости или конфигурации
# Например:
# RUN apt-get update && apt-get install -y some-package
# COPY ./my-config /app/my-config
```

Если файл `.qwen/sandbox.Dockerfile` существует, вы можете использовать переменную окружения `BUILD_SANDBOX` при запуске Qwen Code для автоматической сборки пользовательского образа песочницы:

```bash
BUILD_SANDBOX=1 qwen -s
```

## Статистика использования

Чтобы помочь нам улучшить Qwen Code, мы собираем анонимную статистику использования. Эти данные помогают нам понять, как используется CLI, выявить типичные проблемы и определить приоритеты для новых функций.

**Что мы собираем:**

- **Вызовы инструментов:** Мы логируем названия вызываемых инструментов, успешность их выполнения и время выполнения. Мы не собираем аргументы, передаваемые инструментам, или любые данные, возвращаемые ими.
- **API-запросы:** Мы логируем модель, использованную для каждого запроса, длительность запроса и его успешность. Мы не собираем содержимое промптов или ответов.
- **Информация о сессии:** Мы собираем информацию о конфигурации CLI, такую как включенные инструменты и режим одобрения.

**Что мы НЕ собираем:**

- **Личная информация (PII):** Мы не собираем никакую личную информацию, такую как ваше имя, адрес электронной почты или API-ключи.
- **Содержимое промптов и ответов:** Мы не логируем содержимое ваших промптов или ответы модели.
- **Содержимое файлов:** Мы не логируем содержимое никаких файлов, которые читаются или записываются CLI.

**Как отказаться:**

Вы можете отказаться от сбора статистики использования в любое время, установив для свойства `usageStatisticsEnabled` значение `false` в категории `privacy` в вашем файле `settings.json`:

```json
{
  "privacy": {
    "usageStatisticsEnabled": false
  }
}
```

> [!note]
>
> Когда статистика использования включена, события отправляются на endpoint сбора RUM Alibaba Cloud.
