## 1. Фон и проблема

В qwen-code сейчас **Ctrl+O привязан к `TOGGLE_COMPACT_MODE`**: **глобальный двухпозиционный переключатель** (`compactMode`, персистится в `settings.ui.compactMode`). Когда включен:

- скрывает вывод результатов завершенных (Success) инструментов;
- сворачивает блоки размышлений в одну строку `Thought for …`;
- одно нажатие клавиши **ретроспективно перерисовывает всю историю** (`refreshStatic()` перевешивает `<Static>`).

Это создает глобальный разрыв «**компактный режим vs подробный режим**»: одна и та же история из-за одного глобального переключателя целиком скачет между двумя совершенно разными формами, высока когнитивная нагрузка, заметна визуальная тряска, и это расходится с философией дизайна как upstream gemini-cli, так и Claude Code.

> **Этот план наслаивается на базу partition из [#5661](https://github.com/QwenLM/qwen-code/pull/5661) (уже слит в main).** #5661 отрефакторил рендеринг групп инструментов по умолчанию: расширил `CompactToolGroupDisplay` до **суммарного рендерера с разбивкой по категориям** (`ToolCategory` / `TOOL_NAME_TO_CATEGORY` / `CATEGORY_ORDER` / `getToolCategory` / `buildToolSummary`) и изменил решение о сворачивании `ToolGroupMessage` на **type-based partition**: с инверсным гейтингом `forceExpandAll` инструменты **по типу** делятся на `collapsibleTools` (read/search/list, через `isCollapsibleTool(name)`) → сворачиваются в сводку партиции `CompactToolGroupDisplay`, и `nonCollapsibleTools` (edit/write/command/agent и Canceled) → **всегда по одному** `ToolMessage`. **Замечание: #5661 не связан с `compactMode`** — `compactMode` больше не влияет на рендеринг инструментов, сворачивание по партициям чисто определяется типом инструмента + `forceExpandAll`. Этот PR **не перестраивает базу рендеринга инструментов** — он поверх partition-базы #5661 + мышиной инфраструктуры #5751 добавляет (1) удаление остаточного глобального `compactMode`, (2) полнодетальный transcript-экран Ctrl+O, (3) раскрытие блока инструмента кликом мыши на месте. Подробнее §3.1 (partition-база), §4.1 / §5 (список удаления), §9 (стековое разбиение коммитов).
>
> **Примечание к ревизии (rebase на слитое состояние #5661)**: ранняя версия этого документа писалась по раннему state-based снимку #5661 (`showCompact = (compactMode || allComplete)`, сворачивание всей группы при завершении всей группы). #5661 в процессе ревью эволюционировал в вышеописанный **type-based partition** и уже слит в main. §3.1 / §4.1 / §4.5 / приложение переписаны по фактической слитой реализации: ключевые символы — `isCollapsibleTool` / `forceExpandAll` (**они действительно существуют**), `fullDetail` в transcript напрямую ставит `forceExpandAll=true` (а не меняет уже несуществующий `showCompact`).

### Цели

**Полностью отменить различие глобальных режимов «компактный/подробный»**, выровняться по Claude Code:

1. Главный вид разговора имеет **только один стабильный, склонный к компактности рендеринг по умолчанию** и больше не деформируется целиком глобальным переключателем.
2. **Ctrl+O отвечает только за «посмотреть полные детали некоторых блоков»** — открывает **отдельный полнодетальный прокручиваемый Transcript-экран**; главный вид всегда остается чистым.
3. Инлайн-подсказка `(ctrl+o to expand)` служит указанием «здесь есть больше содержимого, нажмите Ctrl+O, чтобы увидеть полную картину в transcript».
4. **(follow-up, не в этом PR) раскрытие деталей блока кликом мыши на месте**: как VP-only MVP последующего PR — клик по свернутой строке сводки партиции раскрывает детали всей группы на месте. **Этот PR не поставляет** (причины в §4.8: при type-based partition свернутые инструменты уже агрегированы в одну строку, нет per-tool цели клика, нужно переопределить гранулярность клика; плюс риск SGR-мыши/нативного выделения; объем ~250–400 строк). Клик по свернутому блоку размышлений, открывающий ThinkingViewer, уже предоставлен main/#5751, этот PR его не трогает.

> Явное указание пользователя: **просто выровняться по Claude Code**. Этот план берет за ориентир «точное воспроизведение модели ctrl+o = toggleTranscript из Claude Code». Раскрытие кликом мыши — наслаиваемый поверх второй канал взаимодействия (клавиатура + мышь).

## 2. Сравнение поведения трех продуктов (выводы исследования)

| Измерение              | qwen-code (текущее / база #5661)                                          | Claude Code (фактический)                        | gemini-cli (upstream)                     |
| ---------------------- | ------------------------------------------------------------------------- | ------------------------------------------------ | ----------------------------------------- |
| Привязка Ctrl+O        | `TOGGLE_COMPACT_MODE`                                                     | `app:toggleTranscript`                           | `SHOW_MORE_LINES` + `EXPAND_PASTE`        |
| Базовая модель         | **глобальное двухпозиционное компактный/подробный** (персистится) + автосворачивание partition #5661 | **глобальный transcript-экран** + по-блочное раскрытие | глобальный `constrainHeight` + per-tool раскрытие |
| Влияние на главный вид | одно нажатие ретроспективно перерисовывает всю историю                    | главный вид постоянен; transcript — отдельный экран | переключение ограничения высоты, раскрытие «последнего хода» |
| Состояние блоков       | ❌ нет                                                                     | ✅ `expandedKeys` (по tool_use_id/uuid)          | ✅ `ToolActionsContext.toggleExpansion`    |
| Выход                  | повторный Ctrl+O переключает обратно                                      | повторный Ctrl+O / Esc к промпту                 | повторный Ctrl+O сворачивает              |

**«Новая текущая база» qwen = модель type-based partition из #5661 (стартовая точка этого плана, а не старая база, которую нужно ломать):** #5661 перевел рендеринг групп инструментов по умолчанию с «полное отображение/полное скрытие через `compactMode`» на **сворачивание по партициям на основе типа инструмента** — когда `forceExpandAll` ложен, `collapsibleTools` (read/search/list, через `isCollapsibleTool(name)`, не Canceled) сворачиваются в строку сводки партиции `CompactToolGroupDisplay` (агрегация по `CATEGORY_ORDER`: search/read/list/command/edit/write/agent/other, например `Read 3 files, edited 2 files`), `nonCollapsibleTools` (edit/write/command/agent + Canceled) **всегда по одному** `ToolMessage`; force-условия (подтверждение/ошибка/фокус shell/инициировано пользователем/терминальный субагент) дают `forceExpandAll=true` → все раскрываются по одному. **Эта модель не связана с `compactMode`** — `compactMode` в #5661 уже не влияет на рендеринг инструментов (остаточно влияет только на блоки размышлений). Этот план на этой базе **сохраняет весь механизм type-based partition без изменений**, только удаляет остаточный глобальный переключатель `compactMode` и добавляет `fullDetail` в transcript (ставит `forceExpandAll=true`).

**Фактический механизм Claude Code (форензика упакованных исходников `claude-code`):**

- `defaultBindings.ts`: `'ctrl+o': 'app:toggleTranscript'`.
- `useGlobalKeybindings.tsx`: `setScreen(s => (s === 'transcript' ? 'prompt' : 'transcript'))`, плюс телеметрия `tengu_toggle_transcript`.
- `REPL.tsx`: при `screen === 'transcript'` рендерит **всю** историю с **виртуальной прокруткой**, причем `verbose={true}` (принудительное полное раскрытие); в режиме `prompt` есть лимит отображаемых строк.
- `CtrlOToExpand.tsx`: в конце усеченного блока рендерится `(ctrl+o to expand)`, клик/нажатие входит в transcript для полной картины.
- Есть также отдельный `expandedKeys` (per-message), но **главный канал взаимодействия — именно transcript-экран**.

**Per-block модель gemini-cli (дополнение форензики)**: gemini-cli идет по пути per-tool раскрытия — `expandedTools` / `toggleExpansion` в `ToolActionsContext` ведут состояние раскрытия по отдельному инструменту. Это **та же идея, что уже существующее в main qwen по-блочное раскрытие размышлений через Alt+T (`ThoughtExpandedContext`)**: оба решают «раскрыть один блок на месте». А transcript из этого плана решает **другое измерение** — «полный обзор всей сессии» (freeze-снимок в alt-screen, все блоки в fullDetail, прокрутка), они ортогональны и дополняют друг друга (подробнее §4.7).

**Ключевое преимущество**: в qwen-code уже есть вся база, нужная для transcript-экрана (`ScrollableList`/`VirtualizedList` + уже приземленный `AlternateScreen.tsx`), см. §4.4.

## 3. Определение целевого поведения

### 3.1 Базовая линия по умолчанию (главный вид) = модель partition из #5661

Главный вид применяет ко **всем элементам истории** единое стабильное правило рендеринга, **никакой глобальный переключатель его не переключает**. Эта базовая линия **не построена этим планом с нуля**, а является **моделью type-based partition (сворачивание по партициям на основе типа инструмента)**, уже приземленной в [#5661](https://github.com/QwenLM/qwen-code/pull/5661) — этот план сохраняет ее без изменений, лишь удаляя несвязанный с ней глобальный переключатель `compactMode`:

| Тип блока                                                            | Рендеринг базовой линии по умолчанию (модель type-based partition #5661)                                                                                                                                      | Полностью видно только в transcript           |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| Размышление (gemini_thought / \_content)                             | однострочная сводка `✻ Thought for 3s (ctrl+o to expand)`; при стриминге отображается вживую, после фиксации сводится в сводку                                                                                  | да                                            |
| **collapsible инструменты** (read/search/list, не force)             | через `isCollapsibleTool(name)` попадают в `collapsibleTools`, **сворачиваются** в **строку сводки партиции** `CompactToolGroupDisplay` (агрегация по `CATEGORY_ORDER`, например `Read 3 files, edited 2 files, ran 1 command`) | детали по каждому инструменту видны в transcript |
| **non-collapsible инструменты** (edit/write/command/agent / Canceled) | попадают в `nonCollapsibleTools`, **всегда по одному** `ToolMessage` с полным рендерингом (их вывод сам по себе является ответом) — даже если вся группа завершена, не сворачиваются в сводку                     | ——                                            |
| Смешанная группа (collapsible + non-collapsible вместе)              | **строка сводки + по одному сосуществуют**: collapsible часть → одна строка сводки `CompactToolGroupDisplay`; non-collapsible часть → по одному `ToolMessage`. **Не сворачивание всей группы**                  | частично                                      |
| string/ansi результаты завершенных collapsible инструментов          | по умолчанию свернуты (`shouldCollapseResult = !forceShowResult && Success && isCollapsibleTool(name) && (string\|ansi)` → область результата не рендерится); **результаты non-collapsible типа Shell/Edit всегда видны**; у diff/plan/todo/task свои рендереры | полностью видны в transcript                  |
| Ошибка / ожидает подтверждения / инициировано пользователем / фокус shell / терминальный субагент | дают `forceExpandAll=true` → вся группа по одному `ToolMessage`; инструмент-триггер получает `forceShowResult=true`, снимающее сворачивание результата                                                    | ——                                            |
| Обычные текстовые сообщения                                          | отображаются полностью                                                                                                                                                                                          | ——                                            |

Ключевые пункты:

- **Сворачивание по партициям управляется `forceExpandAll` + `isCollapsibleTool` из #5661** — в `ToolGroupMessage` `forceExpandAll = hasConfirmingTool || hasSubagentPendingConfirmation || hasErrorTool || isEmbeddedShellFocused || isUserInitiated || hasTerminalSubagent` (**не включает `compactMode`/`allComplete`**). Когда `forceExpandAll` ложен, по `isCollapsibleTool(name)` (read/search/list, не Canceled) выделяются `collapsibleTools` → сводка `CompactToolGroupDisplay`, остальные уходят в `nonCollapsibleTools` → по одному `ToolMessage`; когда истинен, все инструменты уходят в `nonCollapsibleTools`.
- **Сворачивание завершенных результатов управляется гейтом `shouldCollapseResult` из #5661** — в `ToolMessage` `shouldCollapseResult = !forceShowResult && status === Success && isCollapsibleTool(name) && (renderer.type === 'string' || 'ansi')`. **Обратите внимание на дополнительный гвард `isCollapsibleTool(name)`**: сворачиваются только string/ansi результаты read/search/list, результаты non-collapsible инструментов типа Shell/Edit/Agent **всегда видны**. `ToolGroupMessage` в force-сценариях **по одному** передает инструменту-триггеру `forceShowResult=true` (`isUserInitiated || Confirming || Error || pending-agent || терминальный субагент`).
- **Force-условия — это семантика безопасности «должно быть видимо»** — стеки ошибок, запросы подтверждения, фокус shell, инициированные пользователем инструменты все через `forceExpandAll` не сворачиваются партицией, а результаты non-collapsible инструментов не сворачиваются по природе (плюс `forceShowResult` инструмента-триггера). **Ключевые символы `forceExpandAll` / `isCollapsibleTool` действительно существуют** (слитая реализация #5661); **не нужны** отдельные `shouldForceFullDetail.ts` / `COLLAPSIBLE_CATEGORIES` — force-семантика инлайн в `forceExpandAll`, гейт сворачивания результатов инлайн в `shouldCollapseResult` (см. §4.5).
- **`fullDetail` должен вступать в силу до двух early return в `ToolGroupMessage` (важный пункт реализации, не допускать регрессии)** — в `ToolGroupMessage` **до** вычисления `forceExpandAll` есть два раннего возврата, обходящих логику партиций: (1) **чисто параллельная группа агентов** → плотная панель `InlineParallelAgentsDisplay`; (2) **завершенная memory-only группа** → бейдж `Recalled/Wrote N memories`. Оба приводят к тому, что в fullDetail transcript **все равно не полное отображение**. Поэтому оба early return охраняются **`!fullDetail`**: когда fullDetail истинен, они пропускаются, и каждый инструмент/агент уходит в по-одному `ToolMessage` (`forceExpandAll=true` + `forceShowResult=true` + без усечения). Уже покрыто регрессионным тестом (memory-only группа в fullDetail рендерится по одному, а не бейджем).

### 3.2 Ctrl+O = открыть/закрыть полнодетальный Transcript-экран (отдельный freeze-экран снимка)

Точное воспроизведение transcript из Claude Code (подтверждено форензикой исходников claude-code):

- В любой момент нажмите **Ctrl+O**: переключение на transcript, занимающий весь экран, рендерится **freeze-снимок**: фиксирует историю на момент входа, **снимает усечение высоты/строк на уровне UI** (полный текст размышлений, выводы инструментов максимально полно), поддерживает прокрутку вверх/вниз/постранично/Home/End. Путь VP по умолчанию переиспользует alternate screen, уже занятый ink root; только легаси-путь `<Static>` через компонент `AlternateScreen` пишет DEC `1049` (`\x1b[?1049h`) для временного входа. ⚠️ «Полный» относится только к уровню UI — **содержимое, уже удаленное бюджетом ответа модели или сжатием display истории, не может быть восстановлено из UI history** (см. §4.4), это не буквально «полный текст».
- **Семантика freeze-снимка (включая pending; хранится длина, а не клон истории)**: история qwen-code — **двухфазная** — зафиксированная `history: HistoryItem[]` (`UIStateContext.tsx:45`) и стримящаяся `pendingHistoryItems` (`:123`, при рендеринге конкатенируются с отрицательными id, `MainContent.tsx:456-461`). Freeze в Claude Code фактически хранит только два числа `{ messagesLength, streamingToolUsesLength }` и делает slice при рендеринге, а не клон на момент входа. **qwen-code по этому образцу замораживает обе фазы, но в самой экономной форме**: для зафиксированной history **хранится только длина** `historyLength` (при рендеринге `history.slice(0, historyLength)`, без клонирования всей истории), для стримящейся `pendingItems: [...pendingHistoryItems]` **хранится поверхностная копия** (pending — временная область, будет перезаписана или очищена позже, нужна копия, чтобы зафиксировать форму того момента). Рендеринг transcript конкатенирует `history.slice(0, historyLength)` с **зафиксированным на момент входа** снимком pending. Новые history / pending, добавленные фоном позже, **не входят** в transcript, гарантируя, что фиксация не дрожит.
- **Не влияет на данные главного экрана**: фоновый разговор/стриминг продолжают работать (только не рендерятся поле ввода/спиннер). При выходе путь VP по умолчанию восстанавливает главное дерево в том же root alt-screen; легаси-путь после выхода из временного alt-screen через `refreshStatic()` перевешивает текущую history, гарантируя отсутствие дублей, отсутствие пропусков и отсутствие загрязнения scrollback.
- **Клавиши выхода**: закрытие `Esc` / `q` (стиль less) / `Ctrl+C`; повторный **Ctrl+O** также закрывает по toggle. После выхода возврат на главный экран, видно новое стримящееся содержимое, добавленное фоном, пока transcript был открыт.
- Семантика инлайн-подсказки `(ctrl+o to expand)` **унифицирована в «нажмите Ctrl+O, чтобы войти в transcript и увидеть полный контекст», а не «здесь усечено»**. Заметьте, сводка блока размышлений всегда несет эту подсказку (независимо от длины исходного текста), а вывод инструментов несет `+N lines` только при усечении ограничением высоты — у этих двух подсказок разные условия срабатывания, это ожидаемо (см. §7 #7).

> Форензика: `ink/components/AlternateScreen.tsx`, `termio/dec.ts:16` (`ALT_SCREEN_CLEAR: 1049`), `screens/REPL.tsx:1325/4184/4381` (frozenTranscriptState + slice), `keybindings/defaultBindings.ts:160-169` (`escape/q/ctrl+c → transcript:exit`) из claude-code.

### 3.3 Отношение к Ctrl+S (`SHOW_MORE_LINES` / `constrainHeight`)

- `SHOW_MORE_LINES` (текущий Ctrl+S) остается без изменений: он снимает ограничение высоты **текущей pending-области**, относится к «временно увидеть больше строк во время стриминга», и это ортогональная transcript вещь.

### 4.2 Добавление машины состояний Transcript-экрана + возможности alt-screen

**Для возможности alt-screen есть готовый компонент для переиспользования**: qwen-code использует официальный upstream **`ink ^7.0.3`** (замечание: это **другой пакет и другая мажорная версия**, чем у gemini-cli — gemini-cli использует форк `npm:@jrichman/ink@6.6.9`(v6); **не** рассматривайте их больше как одну версию). Что еще важнее, **в main уже приземлен готовый к переиспользованию `packages/cli/src/ui/components/AlternateScreen.tsx` (PR #5627)**, не нужно создавать новый, переносить хук или вносить форк ink:

- **Переиспользование готового компонента**: `AlternateScreen.tsx` в `useEffect` пишет `writeRaw(ENTER_ALT_SCREEN + CLEAR + HIDE_CURSOR)`, при размонтировании/`process.on('exit')` пишет `writeRaw(SHOW_CURSOR + EXIT_ALT_SCREEN)`; внутри использует `useTerminalOutput()`/`useTerminalSize()`. Transcript'у достаточно обернуть `TranscriptView` в `<AlternateScreen>`, чтобы получить полный жизненный цикл «вход в alt-screen при входе, возврат в normal buffer при размонтировании».
- **Путь взаимодействия по умолчанию уже использует `alternateScreen: true` ink root**: при старте `startInteractiveUI.tsx` один раз вычисляет финальное решение VP через `shouldUseVirtualViewport(setting, screenReader, isInteractiveTerminal())` и использует его одновременно для `alternateScreen` ink и как замороженное начальное значение, передаваемое в `AppContainer`. Обычный интерактивный терминал, когда настройка не указана, по умолчанию входит в VP/alt-screen; явный `ui.useTerminalBuffer: false`, screen-reader, CI, не TTY или `TERM=dumb` идут по легаси-пути `<Static>` + нативный scrollback.
- ⚠️ **В режиме VP ink root уже постоянно в alt-screen, нужно использовать проп `disabled`, чтобы избежать double-enter**: когда замороженное при старте решение VP истинно, если transcript напишет `?1049h` еще раз, это сломает состояние буфера. `AlternateScreen.tsx` поэтому предоставляет проп `disabled?: boolean` (его комментарий: «Skip escape writes when the root Ink renderer already owns the alt screen (VP mode)»). Transcript всегда оборачивается в **`<AlternateScreen disabled={useVP}>`**:
  - режим не-VP (`useVP=false`): компонент нормально пишет `ENTER_ALT_SCREEN`/`EXIT_ALT_SCREEN`, входит/выходит из alt-screen;
  - режим VP (`useVP=true`): передается `disabled`, пропускающий запись escape-последовательностей, поскольку ink root уже в alt-screen, а transcript рендерится прямо в этом буфере, заменяя главное дерево содержимого.
- **Сходимость деградации / определения доступности**: больше не нужен размытый эвристический `isAltScreenSupported()`. Определение сходится к двум явным основаниям — (1) **находимся ли уже в alt-screen определяется `useVP`** (определяет, передавать ли `disabled`); (2) **гвард не-TTY**. ⚠️ **Уточнение текущего состояния (форензика)**: в `AlternateScreen.tsx` сейчас **нет** гварда `process.stdout.isTTY` (в `useEffect` безусловный `writeRaw(ENTER_ALT_SCREEN…)`). Но сам TUI рендерится только когда `interactive` истинен, а без промпта `interactive = process.stdin.isTTY ?? false` (`config.ts:1532`) — **не-TTY по умолчанию вообще не входит в интерактивный рендеринг**, TranscriptView/AlternateScreen не монтируются; единственный угол — явный `-i` (принудительный interactive, при котором stdout может быть не TTY). **К реализации**: добавить в `AlternateScreen` гвард `process.stdout.isTTY` (проверка перед записью escape, не-TTY не занимает весь экран, деградирует в рендеринг внутри обычного буфера), в соответствии с существующими соглашениями репозитория (`startInteractiveUI.tsx:77/81`, `notificationService.ts:53` и др. все проверяют `isTTY` перед записью escape в терминал). Изменение минимально, относится к «страховке для соответствия соглашениям», плюс соответствующий юнит-тест.

Состояние (**единственный источник истины: `useState` в `AppContainer`, локальное хранение, потребление на верхнем уровне — не выносится в широкий `UIStateContext`**):

> **Компромисс дизайна (форензика: согласовано с ThinkingViewer + REPL-local из claude-code + прецедент gemini-cli)**: transcript — это единое UI-состояние, «открываемое глобальной клавишей Ctrl+O и потребляемое в layout верхнего уровня», **без глубинных потребителей**. Ближайший аналогичный overlay этого репозитория `ThinkingViewer` хранит каноническое состояние в локальном `useState` `AppContainer` (`thinkingViewerData`) и передает вниз только минимальное действие `open` через **выделенный** `ThinkingViewerContext`, **не** запихивая в широкий `UIStateContext`; состояние transcript-экрана в claude-code тоже остается локальным на верхнем уровне `REPL`. Поэтому transcript тоже **остается локальным в `AppContainer`** и в верхнеуровневом JSX `AppContainer` условно рендерится `<TranscriptView>` подобно `<ThinkingViewer>`, **без** проекции через `UIStateContext`/`UIActionsContext`. (Замечание: **код реализации уже таков** — `transcriptFreeze` это локальный useState в `AppContainer`, в `UIStateContext` нет полей transcript; в раннем документе было написано «вынести в UIStateContext» — здесь исправлено.)

- **каноническое (локальное)**: `AppContainer` через `useState` несет `transcriptFreeze: { historyLength: number; pendingItems: HistoryItemWithoutId[] } | null` (`HistoryItemWithoutId` — тип элементов `pendingHistoryItems`), `isTranscriptOpen = transcriptFreeze != null` выводится напрямую.
- **действие (локальные замыкания)**: `openTranscript()` (делает снимок двух фаз: `setTranscriptFreeze({ historyLength: history.length, pendingItems: [...pendingHistoryItems] })`) / `closeTranscript()` (ставит null) / `toggleTranscript()` — все локальные колбэки `AppContainer`, вызываются напрямую из обработки глобальных клавиш (§4.3), без прохождения через `UIActionsContext`.
- **момент и семантика снимка**: каждый `openTranscript()` **заново делает** текущий снимок; `closeTranscript()` очищает. То есть transcript фиксируется на «моменте этого открытия», после закрытия и повторного открытия обновится до последнего — это не вечная фиксация на первом открытии. Заметьте, снимок для **зафиксированной history хранит только длину** (`historyLength`, при рендеринге `history.slice(0, historyLength)`, согласовано с Claude Code, хранящим `messagesLength`, а не клон), для **стримящейся pending-области хранит поверхностную копию** (`[...pendingHistoryItems]`, поскольку pending — временная область, будет перезаписана/очищена позже, нужна копия, чтобы зафиксировать форму того момента). **Не клонирует всю history**.
- **`isTranscriptOpen` не сливается с агрегатом `dialogsVisible`** (см. анализ Esc/клавиш в §4.3 — слияние ошибочно заденет логику вроде «Esc может отменить запрос только при Responding и без dialog»); экранирование composer'а достигается естественно тем, что transcript через alt-screen занимает весь экран, без зависимости от `dialogsVisible`.

### 4.3 Переписывание обработки клавиши Ctrl+O

В `AppContainer.handleGlobalKeypress`:

```ts
// 删除：TOGGLE_COMPACT_MODE 分支
// 新增：
} else if (keyMatchers[Command.TOGGLE_TRANSCRIPT](./key)) {
  toggleTranscript();           // open <-> close
}
```

- Добавляется `Command.TOGGLE_TRANSCRIPT = 'toggleTranscript'`, привязка по умолчанию `[{ key: 'o', ctrl: true }]`.

**Принадлежность клавиш (избежание гонки двойной обработки)**: `KeypressContext` — это **широковещательный, без consumed flag** (`KeypressContext.tsx:655`, все подписчики `useKeypress` получают одну и ту же клавишу). Поэтому нужен **единый владелец**, правила:

- **Ctrl+O обрабатывается только глобальным `handleGlobalKeypress`** (семантика toggle работает и на открытие/закрытие). **Собственный `useKeypress` TranscriptView никогда не обрабатывает Ctrl+O**, иначе одно нажатие обрабатывается в двух местах → гонка закрыл-и-снова-открыл.
- **Esc / q / Ctrl+C закрывают transcript: обрабатывается глобальным `handleGlobalKeypress`, и это должен быть [самый первый, первый] ветка в `handleGlobalKeypress`** — ⚠️ заметьте, существующая первая ветвь это `Command.QUIT` (Ctrl+C, `AppContainer.tsx:3104`), вторая — `Command.EXIT` (Ctrl+D, `:3121`), только третья — `ESCAPE` (`:3132`), а в начале ветви `ESCAPE` еще есть vim-гвард `if (vimEnabled && vimMode==='INSERT') return;`. Поэтому ветвь закрытия transcript должна быть **раньше всех них** — раньше QUIT/Ctrl+C, раньше EXIT, раньше ветви ESCAPE и его vim-гварда INSERT — короткое замыкание:
  ```ts
  const handleGlobalKeypress = (key) => {
    // 必须是整个 handleGlobalKeypress 的第一个分支：
    // 早于 QUIT(Ctrl+C) / EXIT(Ctrl+D) / ESCAPE 分支（及其 vim INSERT 守卫）
    if (isTranscriptOpenRef.current &&
        (key.name === 'escape' || key.name === 'q' || (key.ctrl && key.name === 'c'))) {
      closeTranscript(); return;
    }
    if (keyMatchers[Command.QUIT](./key)) { ... }   // 现有 :3104
    ...
  ```
  Иначе: при открытом transcript нажатие Ctrl+C сначала запустит выход/`ctrlCPressedOnce`; нажатие Esc будет поглощено vim-гвардом INSERT и transcript не закроется. Поскольку эта ветка охраняется `isTranscriptOpenRef` и действует только при открытом transcript, на нормальное редактирование vim влияния нет. **Тесты**: `Ctrl+C closes transcript and does NOT set quit/ctrlCPressedOnce`; `Esc closes transcript even when vim INSERT mode is active`.
  - **Почему `q` (обычная буква) безопасна**: эта ветка охраняется `isTranscriptOpenRef` и срабатывает только при открытом transcript (когда composer захвачен alt-screen и нет фокуса текстового ввода); когда transcript закрыт, `q` уходит прямо в нормальный поток ввода, без влияния. Новой привязки `Command` не нужно, достаточно inline-совпадения.
- Поскольку `isTranscriptOpen` **не сливается с `dialogsVisible`**, это **не проходит** через `useDialogClose`; Esc transcript обрабатывается независимо в вышеописанной глобальной пре-ветке (`useDialogClose` остается без изменений).
- Чтобы избежать устаревания замыкания, добавляется `isTranscriptOpenRef` (по образцу существующего паттерна `dialogsVisibleRef`, `AppContainer.tsx:2425`).

- **Контейнер рендеринга (обратите внимание на гейтинг)**: `ScrollableList`/`VirtualizedList` **уже существуют в main** (стандартные компоненты Ink 7, не форк Ink; `ScrollableList.tsx` имеет `scrollBy/scrollTo/scrollToEnd/scrollToIndex` и PageUp/Down/Home/End/колесо), используются `MainContent` в пути VP/virtual-viewport по умолчанию; только явный opt-out, screen-reader, CI, не-интерактивные или несовместимые терминалы фолбэкятся на `<Static>` + pending. Transcript **безусловно переиспользует** эти два компонента (отвязан от гейтинга главного экрана, сам управляет контейнером прокрутки). ⚠️ Эти компоненты относительно новые, производительность прокрутки на длинных сессиях, прокрутка клавиатурой, перестройка при resize должны войти в тесты (§8), нельзя предполагать «нулевую стоимость переиспользования».
- **`estimatedItemHeight` (оценка высоты виртуальной прокрутки, нужно увеличить/адаптировать)**: `MainContent` сейчас использует константу `estimatedItemHeight=3` для `VirtualizedList`. Transcript рендерит в `fullDetail` (полный текст размышлений, полный вывод инструментов), **каждый элемент намного выше 3 строк**, если сохранить 3, это исказит скроллбар/позиционирование и собьет шаг PageUp/Down. Transcript должен использовать **больший или адаптивный `estimatedItemHeight`** (оценка по типу содержимого, либо коррекция через механизм фактического измерения высоты `VirtualizedList`). Эта оценка входит в тесты (§8).
- **Полное раскрытие (проп `fullDetail`)**: в путь рендеринга вводится явный `fullDetail` вместо прежнего вывода через `!compactMode`. При `fullDetail=true`: блоки размышлений `expanded={true}`; вывод инструментов **одновременно** удовлетворяет двум пунктам, чтобы снять обрезку высоты UI — (a) `availableTerminalHeight={undefined}` (проверка, что `ToolGroupMessage.tsx:357-365` по этому делает `availableTerminalHeightPerToolMessage` undefined); (b) отключение ограничения высоты `MaxSizedBox`, `sliceTextForMaxHeight`, shell'евых `shellStringCapHeight/shellOutputMaxLines` (`ToolMessage.tsx:67-74,750-756`). ⚠️ **Сохраняются бюджет ответа модели и сжатие display интерактивной истории** — это границы тела запроса и хранилища сессии, не относящиеся к обязанности UI-раскрытия transcript, чтобы один сверхбольшой вывод не обрушил запрос, файл сессии или виртуальную прокрутку.
- **Трехслойные границы обрезки (важно, избегать избыточных обещаний)**: (1) **слой ответа модели**: бюджеты превью и финальной партии производителей Shell/MCP укорачивают `responseParts`, отправляемые модели, полный текст может храниться только во временном output artifact; rich `resultDisplay` независим от этого, MCP на производителе все еще может сохранять полный transformed display. (2) **слой интерактивной истории**: перед записью в UI историю/сессию `compactResultDisplayForInteractiveHistory` / сжатие записи дополнительно сжимают по символам слишком большие rich display. (3) **слой UI**: `MaxSizedBox`/`sliceTextForMaxHeight` и т.п. обрезают по высоте терминала. **Transcript может снять только третий слой**; он не может восстановить содержимое, уже удаленное из ответа модели или display истории. Правило: сохранять существующие маркеры усечения/сжатия; «прочитать персистентный output artifact и показать» числится **последующим опциональным усилением**, не в этой итерации. i18n/тексты не должны заявлять «посмотреть полный вывод инструмента», менять на «посмотреть полный контекст (без частей, усеченных границами ответа модели или хранилища сессии)».
- **Разделение клавиатуры**: собственный `useKeypress` TranscriptView (`isActive: isTranscriptOpen`) **обрабатывает только клавиши прокрутки** (вверх/вниз/постранично/Home/End). **Клавиши закрытия (Esc/q/Ctrl+C/Ctrl+O) всегда обрабатываются глобальным `handleGlobalKeypress`** (§4.3), TranscriptView их не трогает, искореняя двойную реакцию на широковещание.
- **Модель рендеринга (явная единая стратегия, устранение неоднозначности)**: одиночный ink root может линейно рендерить только одно дерево. Когда transcript открыт, layout верхнего уровня **заменяет главное дерево содержимого `TranscriptView`, обернутым в `<AlternateScreen disabled={useVP}>`** (`MainContent` размонтируется из рендеринга, **больше не рисуется**); фоновый разговор/стриминг только обновляют **слой данных** (`history`/`pendingHistoryItems` продолжают расти), но **не рисуются**. При выходе путь VP по умолчанию остается в уже занятом root alt-screen, и React восстанавливает главное дерево; легаси-путь `<Static>` через `AlternateScreen` выходит в normal buffer, затем через `refreshStatic()` перевешивает history, гарантируя, что на главном экране нет дублей, пропусков и смещений.
- **Подавление/гвард `refreshStatic` во время открытого transcript (избежание загрязнения scrollback главного экрана)**: внутренние пути вроде `useResizeSettleRepaint` (например, resize) могут запустить `refreshStatic` пока transcript открыт — если не контролировать, это запишет/перестроит главное содержимое в **scrollback normal-buffer**, пока экран занят alt-screen, приводя к смещению главного экрана после выхода или загрязнению scrollback. Правило: **охранять `refreshStatic` через `isTranscriptOpenRef`, всегда пропускать пока transcript открыт**; при выходе из transcript один раз сделать `refreshStatic()` для перерисовки главного экрана (то есть предыдущий пункт). Это проясняет «scrollback normal-buffer главного экрана не загрязняется записями во время alt-screen». **Тест**: пока transcript открыт, фоном завершается раунд вызовов инструментов / срабатывает resize, после выхода содержимое этого раунда появляется на главном экране ровно один раз, scrollback не разрушен.
- **Заголовок/подвал**: название (например, `Transcript — ↑↓ scroll · Ctrl+O/Esc/q to close`), начальный `initialScrollIndex` прокручен до низа (согласовано с Claude Code — открытие сразу на последнем).

### 4.5 Введение связки `fullDetail` поверх базы #5661 (путь transcript ставит `forceExpandAll=true`)

База type-based partition из #5661 уже сделала два слоя решений: «какие инструменты сворачиваются в сводку партиции» (партиция `forceExpandAll` + `isCollapsibleTool`) и «сворачивать ли завершенные результаты» (гейт `shouldCollapseResult`). Этот PR **не переписывает эти два слоя**, только добавляет один явный сигнал `fullDetail`, чтобы путь transcript мог **целиком снять** сворачивание партиции + сворачивание результата + ограничение высоты. **Ключевое преимущество**: при базе type-based transcript'у достаточно слить `fullDetail` в `forceExpandAll` (`forceExpandAll = fullDetail || hasConfirmingTool || ...`) — одно место одновременно отключает партицию (все инструменты уходят в `nonCollapsibleTools` и рендерятся по одному) и связывает по-инструментный `forceShowResult`, снимающий сворачивание результата, **не нужно менять уже несуществующий `showCompact`**.

- **Два слоя решений, уже на месте от #5661 (сохраняются)**:
  - Когда `forceExpandAll` в `ToolGroupMessage` (`fullDetail || hasConfirmingTool || hasSubagentPendingConfirmation || hasErrorTool || isEmbeddedShellFocused || isUserInitiated || hasTerminalSubagent`) истинен → пропускается type-based partition, все инструменты по одному `ToolMessage`; когда ложен → по `isCollapsibleTool` делится на collapsible (сводка) / non-collapsible (по одному).
  - Проп `forceShowResult` в `ToolMessage` через `shouldCollapseResult = !forceShowResult && status === Success && isCollapsibleTool(name) && (string|ansi)` решает, сворачиваются ли string/ansi результаты завершенных collapsible инструментов. `ToolGroupMessage` в force/fullDetail сценариях передает инструментам `forceShowResult={fullDetail || isUserInitiated || Confirming || Error || pending-agent || терминальный субагент}`.
  - **Вышеописанные force-условия и несут семантику безопасности «ошибка/ожидает подтверждения/инициировано пользователем/фокус shell/субагент должно быть полностью видимо»** — этот PR сохраняет их как есть, **не добавляет** `shouldForceFullDetail.ts`, **не мигрирует** никаких решений.
- **Блоки размышлений**: `HistoryItemDisplay` меняет `expanded` блока размышлений с зависимости от `compactMode` на `resolvedThoughtExpanded = fullDetail || (thoughtExpanded ?? contextThoughtExpanded)` (§4.7) — путь transcript fullDetail или по-блочный переключатель Alt+T в main, любое истинно → раскрытие; в нормальном состоянии главного вида `fullDetail=false`.

**Связка `fullDetail` (когда путь transcript = true, все вступает в силу одновременно)**:

При `fullDetail=true` (transcript) нужно одновременно выполнить следующие пункты, чтобы это было по-настоящему «по одному инструменту, полно и без усечения»:

1. **Поставить `forceExpandAll=true`** (слить `fullDetail` в `forceExpandAll`) — снимает type-based partition #5661, все инструменты уходят в `nonCollapsibleTools` и рендерятся по одному `ToolMessage` (вместо агрегации collapsible части в строку сводки партиции);
2. **По инструментам передавать `forceShowResult=true`** (слить `fullDetail` в `forceShowResult`) — `!forceShowResult` в `shouldCollapseResult` больше не срабатывает, string/ansi результаты завершенных collapsible инструментов тоже раскрываются (результаты non-collapsible и так отображаются);
3. **Снять ограничение высоты `MaxSizedBox`** — `ToolGroupMessage` в fullDetail передает каждому `ToolMessage` `availableTerminalHeight={undefined}`; внутри `ToolMessage` `availableHeight` становится undefined, `maxHeight` `MaxSizedBox` безграничен, shell'евый `isCappingShell` (включая `!forceShowResult`) снимается. ⚠️ **Сохраняются бюджет ответа модели и посимвольный лимит display истории** — различайте «обрезка высоты строки (для текущего UI, transcript снимает)» и «границы запроса/хранилища сессии (transcript не снимает)»;
4. **`expanded` блоков размышлений** — компонента `fullDetail` в `resolvedThoughtExpanded` пути transcript истинна (см. выше).

**Поток данных `fullDetail` (кто вычисляет, кто передает, значение по умолчанию)**:

- `fullDetail` — явный проп `HistoryItemDisplay` / `ToolGroupMessage`, **вычисляется и передается родителем по контексту рендеринга**, не читается из context (избегаем создания еще одного неявного глобального состояния).
- **Главный вид** (`MainContent`): не передает `fullDetail` (по умолчанию `false`). «Какие группы инструментов должны отображаться полностью» полностью определяется условиями `forceExpandAll`/`forceShowResult`, уже инлайн в `ToolGroupMessage` из #5661 (входы вроде `embeddedShellFocused`/`activeShellPtyId` `HistoryItemDisplay` и так держит и передает), **не нужно отдельно вычислять force-булевы в `MainContent`**.
- **Transcript** (`TranscriptView`): для всех элементов всегда передает `fullDetail={true}`, запуская вышеописанную связку.

> Так различие «главный вид vs transcript» сходится к одному чистому булеву `fullDetail`: главный вид использует type-based partition + force-семантику безопасности #5661, transcript через `fullDetail` (слитый в `forceExpandAll` + `forceShowResult`) снимает эти два слоя вместе с ограничением высоты. **Не вводится новых файлов, не мигрируют решения, не меняется логика партиций #5661**.

### 4.6 Фоновое взаимодействие во время открытого Transcript (диалоги подтверждения / resize)

Transcript через alt-screen занимает весь экран, но фоновый разговор продолжает работать — это порождает несколько правил взаимодействия, которые нужно явно определить:

1. **Блокирующие подтверждения/диалоги (предотвращение deadlock'а, обязательно обработать, покрыть все виды)**: блокирующие подтверждения — **не только `WaitingForConfirmation`** — `DialogManager.tsx` также рендерит `shellConfirmationRequest`(ShellConfirmationDialog), `loopDetectionConfirmationRequest`(LoopDetectionConfirmation), `confirmationRequest`(ConsentPrompt), `confirmUpdateExtensionRequests`(ConsentPrompt), `providerUpdateRequest`(ProviderUpdatePrompt) и т.д. Если любой из них закрыт alt-screen, пользователь его не видит и не может ответить → **deadlock**. Правило: **когда любое блокирующее подтверждение/диалог требует ввода пользователя, автоматически `closeTranscript()`** (добавить в `AppContainer` `useEffect`, слушающий состояние этих запросов + объединение с `streamingState===WaitingForConfirmation`, любое истинно → выход из alt-screen), позволяя пользователю увидеть и ответить. Это проще и однозначнее, чем «рендерить разные диалоги подтверждения внутри alt-screen». **Тесты должны по одному покрыть автоматическое закрытие каждым из вышеописанных блокирующих подтверждений** (§8).
2. **Resize окна**: когда transcript открыт и меняется размер терминала, `VirtualizedList` должен перестроиться по новой ширине и пересчитать высоты строк. Достаточно переиспользовать его существующую реакцию на resize; при выходе из transcript `refreshStatic()` из §4.4 тоже перестроит главный экран. Тест должен покрыть «позиция прокрутки не рушится после resize внутри transcript».
3. **Автоотправка очереди сообщений (гвард, избежание тихой отправки)**: логика опустошения (drain) очереди сообщений в `AppContainer.tsx` имеет гвард `if (dialogsVisible) return;`, избегающий тихой автоотправки поставленных в очередь сообщений, когда открыт dialog. Поскольку `isTranscriptOpen` **не сливается с `dialogsVisible`** (§4.2/§4.3), этот гвард не покрывает состояние открытого transcript. Правило: **в эту логику drain добавить `|| isTranscriptOpenRef.current` (или эквивалентное условие)**, гарантируя, что пока transcript открыт, сообщения очереди **не отправляются автоматически**, а нормально опустошаются после выхода из transcript. **Тест**: пока transcript открыт, поставленные в очередь сообщения не отправляются автоматически, после выхода drain возобновляется.

### 4.7 Отношение к существующему в main по-блочному механизму размышлений (дополняющее сосуществование, не конфликт)

После слияния upstream main в репозитории уже есть **по-блочный (per-block) механизм раскрытия размышлений**, который с transcript всей сессии из этого плана **дополняюще сосуществует**, решая разные потребности:

- **По-блочные возможности, уже предоставленные main**:
  - `ThoughtExpandedContext` — `Alt+T` (`Command.TOGGLE_THINKING_EXPANDED`) переключает на месте раскрытие/сворачивание **одного блока размышлений**;
  - `ThinkingViewer` / `ThinkingViewerContext` — просмотр **полного текста** одного блока размышлений;
  - связанный поток данных: пропы блоков размышлений `thoughtExpanded` / `thinkingFullText`, `buildThinkingFullTextMap`, `ClickableThinkMessage`.
- **Определение expanded блока размышлений после слияния**: блок размышлений при рендеринге `expanded = isPending || fullDetail || resolvedThoughtExpanded` — любой из трех источников истинен → раскрытие:
  - `isPending`: полный текст вживую при стриминге (§4.5);
  - `fullDetail`: путь transcript всегда true (§4.5);
  - `resolvedThoughtExpanded`: по-блочный переключатель Alt+T из main.
    Преобразование `fullDetail` из этого плана **берет на себя только первые два**, не трогая `resolvedThoughtExpanded` — по-блочный механизм сохраняется как есть.
- **Почему нет конфликта (прямой ответ на обеспокоенность ревьюера «исходная потребность пользователя — per-block»)**: потребность «раскрыть один блок размышлений на месте», о которой беспокоился ревьюер, **уже удовлетворена Alt+T / ThinkingViewer в main**; transcript этого плана решает **другое измерение** — «полный обзор всей сессии» (freeze-снимок в alt-screen, все блоки рендерятся в fullDetail, прокрутка). У них разные цели, разные входы (Alt+T vs Ctrl+O), разный охват (один блок vs вся сессия), **ортогональны и дополняют друг друга**, никакого выбора «или-или» нет.

**(Черновик дизайна follow-up) раскрытие/сворачивание деталей блока вызова инструмента кликом на месте**

Переиспользует зрелую парадигму, уже существующую в main (`ClickableThinkMessage` + `measureElementPosition` + `useMouseEvents`), обобщая ее с «блоков размышлений» на «блоки инструментов». **Точка выравнивания: раскрытие кликом per-tool = переключить на месте этот инструмент/группу в `forceExpandAll=true` (не сворачивается партицией) + `forceShowResult=true`** (используя per-id состояние раскрытия, по попаданию toggle), **переиспользуя существующие механизмы `forceExpandAll` / `forceShowResult` из #5661**, не создавая отдельной ветки рендеринга:

1. **Per-tool состояние раскрытия (новое)**: у блоков инструментов сейчас **нет** пользовательского переключаемого состояния раскрытия одного блока (партиция/сворачивание результата в #5661 вычисляется автоматически по force-правилам). Добавить легкийковесный context (по образцу форм `ToolActionsContext` из gemini-cli / `ThoughtExpandedContext` из main):
   - Состояние: `expandedToolGroupIds: ReadonlySet<string>` (по id tool_group или callId). Каноническое хранится в useState `AppContainer`.
   - **Передача вниз через выделенный малый context** (по образцу форм `ToolActionsContext` из gemini-cli / `ThinkingViewerContext`/`ThoughtExpandedContext` этого репозитория), выставляет `toggleToolExpanded(id)` / `isToolExpanded(id)` — **не** запихивать в широкий `UIStateContext`/`UIActionsContext`. В отличие от transcript (§4.2, чисто локальный, потребление на верхнем уровне, без глубинных потребителей): у per-tool раскрытия **есть** кросс-слойные производители (клик по глубинному блоку инструмента вызывает set) + потребители (`ToolGroupMessage` читает `isToolExpanded` и сливает в `forceExpandAll`), поэтому передача вниз оправдана, но использовать выделенный context, а не загрязнять глобальный агрегат UI-состояния.
2. **Подключение к двухслойному механизму #5661 (без третьего пути)**: инструмент/группа, раскрытая по клику, при рендеринге выглядит так —
   - `ToolGroupMessage`: сливает `isToolExpanded(id)` в компоненту «истинно» `forceExpandAll` (`forceExpandAll = fullDetail || isToolExpanded(id) || hasConfirmingTool || ...`) → снимает type-based partition, по одному `ToolMessage`;
   - `ToolMessage`: этому инструменту передается `forceShowResult=true` (`!forceShowResult` в `shouldCollapseResult` больше не срабатывает), плюс совместно снимается ограничение высоты.
   - То есть раскрытие кликом **переиспользует** ту же пару переключателей «`forceExpandAll=true` + `forceShowResult=true`» из связки transcript fullDetail (§4.5 #1/#2), только область действия — один кликнутый инструмент/группа, а не вся сессия. Симметрично многоисточниковому синтезу `expanded` блоков размышлений (§4.7).
3. **Попадание клика в ToolMessage / ToolGroupMessage**: на **строку заголовка** и **область вывода** инструмента навесить по кликабельному Box (`ref` + hit-тест `measureElementPosition`, копируя `left-press` + определение включения координат из `ClickableThinkMessage`). Попадание → `toggleToolExpanded(id)`.
   - Область попадания — это «строка заголовка» или «область вывода», клик по любой переключает детали этого инструмента.
   - Гвард `isActive`: навешивать слушатель клика только когда инструмент **завершен и его результат свернут `shouldCollapse` или вывод усечен по высоте** (то есть есть «что еще посмотреть»), избегая навешивания неэффективных слушателей на блоки без раскрываемого содержимого; внутри transcript не нужно (уже все раскрыто).
4. **Выравнивание VP/координат**: в режиме VP координаты yogaNode и есть координаты viewport, `measureElementPosition` применим напрямую (та же предпосылка, что у `ClickableThinkMessage`); режим Static из-за append-only не участвует в раскрытии кликом (раскрытие кликом в основном служит VP/видимой области, в Static по-прежнему доступен Ctrl+O в transcript).
5. **Не переделывать клик по блокам размышлений**: раскрытие кликом по свернутой строке размышлений уже предоставлено main'овым `ClickableThinkMessage` + #5751, этот PR не переделывает, только обеспечивает сосуществование с новой базой/transcript.
6. **Отношение к transcript**: клик по блоку инструмента — это «раскрыть детали одного инструмента на месте» (остается в главном виде, область — один инструмент/группа), Ctrl+O — это «обзор всей сессии» (все элементы в fullDetail) — подобно Alt+T vs Ctrl+O для блоков размышлений, ортогонально и дополняет.

> Примечание о зависимости: доступность этой функции предваряется = фиксом подсчета ссылок мыши из #5751 (иначе в VP мышь может быть ошибочно отключена размонтированием какого-нибудь свернутого блока). Дизайн и реализация предполагают «#5751 уже в main»; порядок коммитов см. §9.

### 4.9 Дополнение слоя данных полной детализации Transcript (устранение промежуточного состояния «второго слоя сворачивания»)

**Фон**: этот PR определяет Ctrl+O как «полнодетальный transcript-экран» (§3.2) — главный вид сохраняет компактную сводку партиций #5661, Ctrl+O в любой момент вызывает «полную запись», все элементы рендерятся в `fullDetail`. Дизайн **обещает**, что внутри transcript вывод инструментов **полностью раскрыт, не свернут, не усечен по высоте**; в реализации это достигается слиянием единого сигнала `fullDetail` в `forceExpandAll` + по-инструментный `forceShowResult` + `availableTerminalHeight=undefined` (§4.5).

**Проблема (проверено при приемке, §3.4)**: модель «трех слоев сворачивания» пользователя застревает на втором слое — первый слой (главный вид) `✔ read 1 file, listed 1 dir` сводка партиции должна сохраниться; второй слой (Ctrl+O сейчас) по одному инструменту в строке + **краткая сводка** (`列出文件 Listed 3 items` / `Grep Found 4 matches` / `读取文件 README.md`); а **самый детальный слой отсутствует** (фактические записи каталога, строки совпадений grep, полный текст файла). **Сворачиваемые read-only инструменты** типа `read_file` / `ls` / `grep` / `glob` в transcript доходят только до уровня сводки, нарушая семантику «полной детализации».

**Первопричина (слой данных, не переключатели сворачивания)**: по форензике, цепочка `fullDetail → forceExpandAll / forceShowResult / availableTerminalHeight=undefined` из §4.5 **вся корректно работает**; проблема в том, что фронтенд вообще не получает полные детали:

- У `ToolResult` две дорожки содержимого (`packages/core/src/tools/tools.ts:443+`): `llmContent` («фактический исход», полный) и `returnDisplay` (комментарий явно говорит «user-friendly **summary**»).
- `returnDisplay` у `ls` / `grep` / `ripGrep` / `read_file` несет только сводку (`Listed N` / `Found N` / `''`), полное содержание уходит только в `llmContent` (форензика: возвраты в `ls.ts` / `grep.ts` / `ripGrep.ts` / `read-file.ts`).
- Во фронтенд-структуре отображения инструментов `IndividualToolCallDisplay` (`packages/cli/src/ui/types.ts:65`) **есть только `resultDisplay`**, нет поля полного содержимого; точка преобразования `useReactToolScheduler.ts:330` берет только `response.resultDisplay` (сводку).
- Полное содержимое хотя и приходит на фронтенд как `ToolCallResponseInfo.responseParts` (`turn.ts:116`), но это обертка `functionResponse`, а `partToString` / `getResponseTextFromParts` берут только `part.text`, **не читают `functionResponse.response.output`** (`partUtils.ts:61-69`, `generateContentResponseUtilities.ts:14`) — в parts, полученных фронтендом, есть полное содержимое, но **нет готового helper'а, чтобы его достать**.

**Ключевое открытие: полные детали фактически уже персистированы естественно (определяет направление плана)**

- `convertToFunctionResponse(...)` (`coreToolScheduler.ts:679-714`) пишет **полный `llmContent`** в `functionResponse.response.output` (string кладется напрямую; из array извлекается **весь** `text` и конкатенируется, media уходит в `parts`) — то есть в parts результата инструмента **уже содержатся полные детали**.
- Персистированный `ChatRecord.message` хранит именно `response.responseParts` (форензика: вызовы `recordToolResult(...)` в `coreToolScheduler.ts:4009`, `Session.ts:3334/4404` и др. все передают `responseParts`), это **полный functionResponse**, не сводка.
- Поэтому полные детали уже на месте и из одного источника во всех трех путях: **live** (`trackedCall.response.responseParts`) / **resume** (`record.message.parts`, case tool_result в `resumeHistoryUtils`) / **ACP replay** (`HistoryReplayer.replayToolResult` уже передает `message: record.message.parts` в `emitResult`). «Персистирование» **естественно удовлетворено** на уровне данных, не нужно новых персистентных полей (эта предпосылка охраняется тестом «защита предпосылки плана Y» в §8 — утверждается, что полный `output` в `message.parts` не теряется и не уходит ошибочно в API `compressedHistory` через четыре этапа recording / loadSession / resume / replay; **при провале — откат к плану X**).

**План Y (единый полный источник данных + извлечение на слое отображения, согласовано с claude code)**

Механизм claude code — «**слой хранения сохраняет полное, слой отображения усекает по `verbose`**», не разбивая на `llmContent`/`returnDisplay`, после resume transcript все так же полнодетален (форензика: `claude-code/src/screens/REPL.tsx:4185-4194,4381-4382,4402` frozen transcript = снимок messages в памяти + `verbose=true`; `src/utils/toolResultStorage.ts`, `sessionStorage.ts` персистят полное содержимое/ссылки на файлы). Полное содержимое в qwen уже персистировано в parts, поэтому применяем ту же идею — **не добавлять персистентных полей, а централизованно извлекать полный текст для отображения из уже существующего functionResponse**.

- **Не выбран X (новое поле `contentForDisplay` сквозь core→сериализацию→replay→фронтенд, 8 мест)**: **избыточность содержимого** с уже персистированным `responseParts` (одно и то же полное содержимое хранится дважды), расширяет схему персистирования и поверхность миграции.
- **Не выбран B (по-инструментно изменить `returnDisplay`, чтобы нес полное)**: нарушает семантику `returnDisplay` = «сводка», меняет много инструментов.
- **Не выбрано «разрозненное раздирание протокола на фронтенде»**: хрупкость по первопричине — но план Y использует **один централизованный core helper** для извлечения, не раздирает во многих местах.

**Точки изменения (план Y)**:

1. **Новый core helper извлечения** `getToolResponseDisplayText(parts: Part[]): string | undefined` (рядом с `getResponseTextFromParts`). **Реализуемые правила приоритета** — media висит на **вложенных `functionResponse.parts`** (не верхнеуровневых, форензика: `coreToolScheduler.ts:661-744`, `postCompactAttachments.ts:149-161`, `compactionInputSlimming.ts:205-213`): обход верхнеуровневых parts → для каждого `functionResponse` читать непустой текст `response.output` и конкатенировать; затем обход его **вложенных `functionResponse.parts`**, для `inlineData`/`fileData` выводить плейсхолдер (например, `<image: mimeType>`), плейсхолдер для вложенных `{text}` тоже сохранять (compaction slimmer порождает эту форму); **если нет output, но есть вложенные media → вернуть плейсхолдер**; **нет ни output, ни media → вернуть `undefined`, чтобы UI деградировал до сводки** (избегая пустого отображения или ошибочного «Tool execution succeeded» для media-only `read_file`). **Единая точка извлечения, общая для live/resume/replay**.
2. **В cli `IndividualToolCallDisplay` (`types.ts:65`) добавляется** `detailedDisplay?: string` — **производное значение, не персистится** (каждый раз извлекается из уже персистированных parts).
3. **Извлечение live**: ветка success в `useReactToolScheduler`: `detailedDisplay = getToolResponseDisplayText(trackedCall.response.responseParts)` (**без вторичного усечения**, см. ниже «Память и лимиты»).
4. **Извлечение resume**: case `tool_result` в `resumeHistoryUtils` (:411-431, уже держит `record.message.parts`) извлекает тем же helper'ом.
5. **Извлечение ACP replay**: `HistoryReplayer.replayToolResult` (:259) уже передает `message: record.message.parts` в `emitResult`; в точке маппинга ACP→display (`resumeHistoryUtils` / `ToolCallEmitter`) выводится тем же helper'ом. **Не нужны новые поля протокола ACP**.
6. **Разделение рендеринга (фикс утечки `forceShowResult`)**: в `ToolMessage` **явно передавать `fullDetail`** (передается вниз из `ToolGroupMessage`). Только когда **`fullDetail && isCollapsibleTool(name) && detailedDisplay`**, `detailedDisplay` замещает сводку `resultDisplay`.
   - **Ключевое**: разделить «снятие сворачивания/высоты» (`forceShowResult`/`forceExpandAll`, может запускаться `isUserInitiated` / `Confirming` / `Error` / pending-agent / terminal-subagent, см. `ToolGroupMessage.tsx:469-475`) и «переключение на полный источник данных» (**только** `fullDetail`). Иначе в главном виде force-сценарии user-initiated/error и т.п. ошибочно покажут полные детали, нарушая «главный вид неизменен».

**Память и лимиты (без вторичного усечения, соответствует семантике «полной детализации»)**: `detailedDisplay` **не** проходит через 32k усечение `compactStringForHistory` — это превратило бы Ctrl+O в «32k bounded preview», а не «полную детализацию», конфликтуя с обещаниями §3.2/§3.4 (особенно `read_file`: `maxOutputChars=Infinity`, сам управляет пагинацией, изъят из посимвольного усечения планировщика, см. `read-file.ts:385-390`, законные большие чтения превысят 32k; при этом в `functionResponse.response.output` все равно >32k полного содержимого, UI не должен резать снова). `detailedDisplay` прямо = полный текст `getToolResponseDisplayText(parts)`, его границы — это **уже примененные core** `truncateToolOutput`/собственная пагинация инструментов (UI не может вернуть содержимое, уже отброшенное core, §4.5) — **слой UI больше не добавляет посимвольных лимитов**. `detailedDisplay` — производное значение, не в базу; содержимое уже существует в `responseParts`, лишь одна дополнительная строковая ссылка. Сверхбольшие выводы рендерятся виртуальной прокруткой `ScrollableList` transcript по viewport (ограниченно), ту же идею, что claude code «хранение хранит полное, слой отображения решает `verbose`».

**Область (определяется по категории, без жестко зашитого списка)**:

- По **`isCollapsibleTool(name)`** — категорийный уровень `read/search/list`, **включая `glob`/`FindFiles`** (`getToolCategory` относит GLOB к search, см. `CompactToolGroupDisplay.tsx:74-95`; `returnDisplay` в `glob.ts:267-280` так же только `Found N matching file(s)`). **Не** зашивать `read_file/ls/grep`.
- Главный вид (не `fullDetail`), `run_shell_command` (`returnDisplay = result.output`, полный) / `edit` / `write` (полный diff) **не меняются**.

**Точки тестирования (входят в §8)**:

- core helper: извлечение `functionResponse.response.output`, плейсхолдеры media, деградация при пустом/отсутствующем;
- **оба пути live + resume выдают `detailedDisplay`**, особенно **transcript после resume/воспроизведения все еще полнодетален**; путь ACP через `transformPartsToToolCallContent` уже несет полный текст (не TUI transcript, не нужен `detailedDisplay`);
- `ToolMessage`: `fullDetail && collapsible && detailedDisplay` использует полное; **`forceShowResult`, но не fullDetail (user-initiated/error в главном виде) все еще использует сводку** (регрессия: главный вид неизменен);
- покрыть `glob` (или legacy search displayName), не только read/grep/list;
- старая сохраненная история: `detailedDisplay` извлекается из parts, parts старых записей так же на месте → естественно полнодетальны; сверхстарые записи без parts деградируют до сводки.

## 6. Миграция и совместимость

- **settings.ui.compactMode / compactInline**: могут уже существовать в пользовательской конфигурации. Стратегия: **убрать из схемы** CLI (`settingsSchema.ts`), но **сохранить `ui.compactMode` в `WEB_SHELL_SETTINGS` (`workspace-settings.ts:36`)** — у web-shell есть собственный `CompactModeContext` (`packages/web-shell/client/App.tsx` читает `'ui.compactMode'`), слой serve должен продолжать пробрасывать, иначе сломается web-shell (см. #12 / §7 #5). Проверено, что система настроек **толерантна** к неизвестным ключам — `getSettingsFileKeyWarnings` (`settings.ts:250-309`, обработка неизвестных ключей в `:290-306`, `debugLogger.warn` в `:303-305`) только пишет в `debug`, не выдает ошибку и не блокирует. Поэтому старая конфигурация CLI пользователя может безопасно читаться (игнорируется CLI), новый CLI настройки UI/API больше не перечисляет этот пункт. **На стороне CLI обратная семантика не сохраняется** — концепция режима удалена целиком, сохранять негде, чтобы оно работало; оставить или убрать compact на стороне web-shell — **оценивается отдельным делом**.
- **Кастомизация горячих клавиш (подсказка миграции)**: в текущей кодовой базе **нет** механизма пользовательски настраиваемых переопределений keybinding — `keyMatchers` (`keyMatchers.ts`) всегда строится из жестко зашитых `defaultKeyBindings`, в `settingsSchema` тоже нет пункта keybinding (только `vimMode`). Поэтому **не существует** пользовательски персистированных привязок `toggleCompactMode`, которые были бы тихо потеряны, обнаружение миграции при старте **не имеет объекта сканирования, сейчас неприменимо**. Когда в будущем будут введены пользовательски настраиваемые keybinding, добавить «обнаружение остаточных привязок `toggleCompactMode` и одноразовую подсказку перепривязать на `toggleTranscript`». **Текущему PR достаточно** заметки в release note о том, что семантика Ctrl+O изменилась на transcript (`docs/users/reference/keyboard-shortcuts.md` уже обновлен).
- **Телеметрия**: можно выровняться по Claude Code, добавив событие `toggle_transcript` (опционально).

## 7. Границы, риски и открытые пункты

1. **Производительность на большой истории**: transcript рендерит всю историю. Виртуальная прокрутка (`VirtualizedList`) ограничена viewport'ом; различать два вида лимитов — **снимать только усечение «высоты строк»** (для отображения, transcript снимает), но **сохранять лимит «числа символов»** (для производительности, всегда сохраняется). Заметьте, в qwen-code **не существует** `SlicingMaxSizedBox` (это из gemini-cli); посимвольная защита на стороне qwen — порог усечения вывода инструментов `DEFAULT_TRUNCATE_TOOL_OUTPUT_THRESHOLD` (~25000). При реализации проверить плавность прокрутки истории на десятки тысяч строк.
2. **Координация alt-screen (переиспользование существующего компонента уже сильно снизило риск)**: этот план **переиспользует уже приземленный в main `AlternateScreen.tsx` (PR #5627)** для входа/выхода в alt-screen, вместо собственноручного тайминга `?1049h/l`, риск заметно ниже, чем в дизайне первой версии. Два оставшихся пункта: (a) **double-enter в режиме VP** — когда `useTerminalBuffer` включен, ink root уже занимает alt-screen, нужно передавать `disabled={useVP}`, пропускающий escape (§4.2); (b) **завершающая перерисовка при выходе** — при выходе главный экран через `refreshStatic()` один раз очищается и перерисовывается (§4.4), причем во время transcript `refreshStatic` охраняется `isTranscriptOpenRef` и пропускается, избегая загрязнения scrollback normal-buffer. Заметьте, старый compact делал refreshStatic **при каждом toggle**, этот план только **один раз при закрытии** transcript, частота намного ниже. Все еще нужно проверить в tmux / iTerm2 / VSCode / Apple Terminal.
3. **Force-семантика безопасности (сохранить инлайн-условия #5661, не удалить ошибочно)**: когда этот PR добавляет в префикс `forceExpandAll` `fullDetail || isToolExpanded(id) ||`, обязательно **сохранить** остальные `hasConfirmingTool || hasSubagentPendingConfirmation || hasErrorTool || isEmbeddedShellFocused || isUserInitiated || hasTerminalSubagent`, а также гейт `shouldCollapseResult` (включая гвард `isCollapsibleTool`) в `ToolMessage` — это уже на месте от #5661 семантика безопасности «ошибка/ожидает подтверждения/инициировано пользователем/фокус shell/субагент должно быть полностью показано» (§4.5), ошибочное удаление приведет к регрессии «ошибочный инструмент свернут и виден не полностью». **Не нужна** миграция в какие-либо новые файлы.
4. **Координация мыши / SGR**: обратить внимание на потенциальное наложение с проблемой «SGR mouse tracking ломает нативное выделение текста», записанной в [[project_vp_text_selection]] — нужно взвесить, включать ли колесо мыши внутри transcript (включить колесо vs сохранить нативное выделение терминала). Обработка входа/выхода мыши следует существующим механизмам `AlternateScreen` и VP root, не нужно дополнительного собственноручного кода.
5. **web-shell (отдельная поверхность, не в области удаления этого PR)**: у web-shell есть **собственный** `CompactModeContext` (`packages/web-shell/client/App.tsx` читает `'ui.compactMode'`), это две отдельные реализации с compact CLI. Чтобы не сломать его, этот PR **сохраняет `ui.compactMode` в `WEB_SHELL_SETTINGS`** (даже если схема CLI больше не определяет этот ключ, слой serve продолжает пробрасывать, см. #12 / §6). В этой итерации CLI только очищает собственные тексты и пункты настроек; **оставить или убрать собственный compact web-shell оценивается отдельным делом**, не в области реализации этого дизайна.
6. **Сливать ли Ctrl+S/`SHOW_MORE_LINES`**: в этой итерации сохранить отдельно, избегая неконтролируемого объема изменений; зачислено в последующие опциональные оптимизации.
7. **Семантика подсказки `(ctrl+o to expand)` (определена)**: сводка блоков размышлений **всегда** несет эту подсказку (указание «войти в transcript и увидеть полный контекст», не «здесь усечено»); вывод инструментов несет `+N lines` только при усечении ограничением высоты. Разные условия срабатывания у этих двух — **ожидаемое поведение**, тексты i18n должны отражать «посмотреть полный контекст», а не «раскрыть усеченное содержимое», избегая введения в заблуждение.

## 8. План тестирования

- **Юнит-тесты**:
  - `AlternateScreen` (переиспользование существующего компонента + **интеграционные тесты после добавления гварда isTTY**): режим не-VP при входе/выходе пишет `ENTER_ALT_SCREEN`/`EXIT_ALT_SCREEN`; **путь режима VP (`disabled=true`) пропускает запись escape, не double-enter**; **не-TTY (`process.stdout.isTTY` ложен) пропускает запись escape** (гвард готов к добавлению, §4.2).
  - `TranscriptView`: открытие рендерит всю историю + **снимок pending на момент входа**, размышления/инструменты полностью раскрыты без усечения, API прокрутки, двухфазная заморозка (новые history/pending, добавленные фоном, не входят в вид), **позиционирование прокрутки не искажается после увеличения/адаптации `estimatedItemHeight`** (§4.4).
  - `ToolGroupMessage`/`ToolMessage` (база type-based partition + связка fullDetail): без force collapsible (read/search/list) сворачиваются в сводку `CompactToolGroupDisplay`, non-collapsible (edit/write/command/agent) по одному `ToolMessage`, смешанная группа — строка сводки + по одному сосуществуют; force-группа (ошибка/подтверждение/фокус shell/инициировано пользователем/терминальный субагент) `forceExpandAll=true` → все по одному, инструмент-триггер `forceShowResult=true`; при `fullDetail=true` (transcript/раскрытие кликом) `forceExpandAll=true` + `forceShowResult=true` + `availableTerminalHeight=undefined` снимают ограничение высоты; результаты non-collapsible инструментов видны и без force всегда (гвард `isCollapsibleTool` в `shouldCollapseResult`); сводка размышлений содержит `(ctrl+o to expand)`; блоки размышлений `resolvedThoughtExpanded = fullDetail || (thoughtExpanded ?? contextThoughtExpanded)` (сосуществует с по-блочным переключателем Alt+T из main, §4.7).
  - Клавиши: Ctrl+O переключает transcript (одна реакция на открытие/закрытие, без двойной обработки); при открытом transcript **Ctrl+C закрывает transcript и не запускает quit/`ctrlCPressedOnce`** (проверить, что короткое замыкание раньше ветки QUIT, §4.3); **Esc закрывает transcript даже в режиме vim INSERT** (проверить, что раньше vim-гварда ветки ESCAPE, §4.3); Esc/q закрывают transcript и **не отменяют фоновый запрос**; Ctrl+S по-прежнему переключает constrainHeight, не мешая друг другу.
  - Взаимодействие (предотвращение deadlock'а, по одному покрыть все блокирующие подтверждения): пока transcript открыт, фон запускает **любое** из `WaitingForConfirmation`, `shellConfirmationRequest`, `loopDetectionConfirmationRequest`, `confirmationRequest`, `confirmUpdateExtensionRequests`, `providerUpdateRequest` → автоматический `closeTranscript()` (§4.6 #1).
  - Очередь сообщений: пока transcript открыт, сообщения в очереди **не отправляются автоматически**, после выхода drain возобновляется (§4.6 #3).
  - Модель рендеринга + гвард `refreshStatic`: пока transcript открыт, фоном завершается раунд вызовов инструментов / срабатывает resize, **во время transcript `refreshStatic` охраняется `isTranscriptOpenRef` и пропускается**, при выходе один раз перерисовывается — содержимое этого раунда **появляется ровно один раз** (без повторного воспроизведения/без пропусков/scrollback не разрушен, §4.4).
  - Трехслойные границы обрезки: вывод инструментов, уже усеченный на слое ответа модели или слое display истории, в transcript все равно показывает соответствующий маркер, не выдумывает «полный текст» (§4.4).
  - **Сквозная передача полных деталей §4.9 (реализовано + тесты)**: извлечение core helper'ом из `functionResponse.response.output` + плейсхолдеры media + деградация при пустом/отсутствующем; `detailedDisplay` (специфично для TUI, производное поле `IndividualToolCallDisplay`) выдается на **обоих путях live (`useReactToolScheduler`) + resume (`resumeHistoryUtils`)**, особенно **Ctrl+O transcript после resume / воспроизведения все еще показывает полные finalized detail момента записи** (не откатывается до сводки); **путь ACP не нуждается в `detailedDisplay`** — `ToolCallEmitter.transformPartsToToolCallContent` пишет тот же finalized `functionResponse.response.output` в ACP `content[]` (его SSE-клиенты сами рендерят, не TUI transcript), поэтому переиспользование `message: record.message.parts` без новых полей протокола удовлетворяет §4.9; `ToolMessage` использует полные детали только при `fullDetail && isCollapsibleTool && detailedDisplay`, а **`forceShowResult`, но не fullDetail (user-initiated/error и т.п. в главном виде) все еще использует сводку `resultDisplay`** (регрессия «главный вид неизменен»); покрыть `glob` (или legacy search displayName), не только read/grep/list; **не делать дополнительного усечения UI** (`output` `read_file` > 32K, но все еще в пределах бюджета финальной партии, в Ctrl+O остается полным; содержимое за пределами бюджета ответа модели все равно может быть восстановлено только через персистентный artifact); сверхстарые записи без `parts` деградируют до сводки.
  - **Защита предпосылки плана Y (персистирование/воспроизведение не теряют finalized detail)**: сконструировать `functionResponse.response.output` длиной > `MAX_RETAINED_TOOL_RESULT_DISPLAY_CHARS`, но ниже `toolOutputBatchBudget`, рядом положить сводку `toolCallResult.resultDisplay` и добавить запись `chat_compression`; утверждать, что `record.message.parts[0].functionResponse.response.output` на **четырех этапах recording / loadSession / `resumeHistoryUtils` / `HistoryReplayer` сохраняет finalized string**, и что `detailedDisplay` выводится из `message.parts` (**не** из `resultDisplay`, **не** из API `compressedHistory`). **Провал этого кейса запускает откат к плану X** (новое персистентное поле display). По исходникам предпосылка выполняется: финальный ответ инструмента сначала завершает сходимость бюджета на границе агрегации рантайма, затем `ChatRecordingService.recordToolResult` через `createUserContent(message)` как есть пишет `record.message`, только санитизируя `resultDisplay`; TUI resume / ACP replay идут через `conversation.messages`, не через API `compressedHistory`. Эта предпосылка гарантирует «записанные finalized detail больше не теряются», не «обход бюджета ответа модели для сохранения исходника производителя».

## 10. Взаимное обучение с существующим дизайн-документом #3100

Предшествующая работа [PR #3100](https://github.com/QwenLM/qwen-code/pull/3100) уже дала `docs/design/compact-mode/compact-mode-design.md` (284 строки анализа конкурентов). Отношение этого плана к ней:

1. **Мы приняли путь, который она анализировала, но тогда не пошла**. #3100 §4.4 уже сравнил «screen-level transcript (Claude Code)» vs «component-level toggle (выбор qwen тогда)» и указал, что первый «проще, согласованность гарантирована». Этот план именно переходит на screen-level transcript.
2. **Исправление одной фактической ошибки**: таблица #3100 утверждала, что у Claude Code «Frozen snapshot: None (no concept)». По форензике последних исходников claude-code, **freeze-снимок есть** (`frozenTranscriptState` + `messages.slice(0, len)`). Этот план по фактической реализации использует freeze-снимок и в §3.2 указывает источник.
3. **Прямое переиспользование ее выводов**: #3100 §4.3/§5.4 отстаивали «диалоги подтверждения используют отдельный слой overlay, структурная гарантия, что они никогда не будут скрыты». Когда transcript — отдельный экран, подтверждения/ошибки главного экрана и так не подвержены его влиянию, естественно удовлетворяя этому требованию. А «ошибка/ожидает подтверждения/фокус shell должно быть видимо» на стороне главного вида обеспечивается условиями `forceExpandAll` из #5661 + `forceShowResult` (этот PR сохраняет без изменений, §4.5), отдельный механизм не нужен.
4. **Разрешение спора о персистировании**: #3100 §4.2/§5.3 многократно взвешивали, нужно ли персистировать compact (settings vs session-scoped). Этот план **удаляет сам режим**, больше нет состояния для персистирования, этот спор автоматически исчезает; не нужна и сложность «session override» из §5.3.
5. **Обращение с документом**: в PR реализации пометить `docs/design/compact-mode/` как «superseded by ctrl-o-detail-expand» (сохранить историю, добавить одну строку указания), избегая сосуществования двух взаимно противоречивых дизайнов.

> Одной фразой: #3100 — это дизайн «как хорошо сделать режим compact»; этот план — дизайн «почему не нужен режим compact, а нужен transcript», это итеративные решения одной и той же проблемы.
