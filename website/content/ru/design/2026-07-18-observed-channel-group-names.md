# Имена наблюдаемых групп каналов

## Проблема

Граф наблюдаемых контактов с областью действия рабочего пространства, представленный в #7109, сохраняет полные ID групп платформы, но каждая `groups[].label` в настоящее время откатывается к этому ID. Некоторые callback'и входящих каналов уже несут человекочитаемое имя группы, а адаптеры отбрасывают его до общей границы наблюдения.

Пользователям, выбирающим цель проактивной доставки, нужно читаемое имя рядом с полным стабильным ID платформы. Имя — это наблюдательное метаданное, а не ключ маршрутизации.

## Область применения

Добавить опциональное имя группы в общий входящий конверт (envelope) и заполнять его только из метаданных, уже присутствующих в принятом входящем сообщении.

- DingTalk отображает `conversationTitle` callback'а Stream.
- Telegram отображает `title` входящего чата для групп и супергрупп.
- Feishu сохраняет фолбэк на полный `chat_id`, поскольку `im.message.receive_v1` не включает отображаемое имя чата.
- Остальные адаптеры сохраняют фолбэк на ID, если их существующая полезная нагрузка входящего сообщения не содержит задокументированное поле имени группы.

Это изменение не вызывает API каталога платформы, деталей группы или информации о чате; не добавляет разрешений; не меняет маршрутизацию или идентичность сессии; не обнаруживает авторитетный состав; не наблюдает вывод бота; не добавляет имена топиков.

## Контракт

`Envelope` получает одно опциональное поле:

```ts
chatName?: string;
```

Поле описывает отображаемое имя `chatId`, наблюдаемое в этом сообщении. Для прямых сообщений оно игнорируется. `chatId` остается полным ключом доставки платформы и продолжает определять сессии, дедупликацию и идентичность графа.

Общий путь наблюдения использует санированный непустой `chatName` в качестве метки группы. Отсутствующие или непригодные значения откатываются к полному `chatId`. Существующее хранилище реестра ограничивает сохраняемые метки 256 кодовыми единицами UTF-16 без разбиения суррогатных пар.

## Семантика обновления

Принятое более позднее сообщение для того же канала, пользователя и группы обновляет наблюдение. Если оно несет другой пригодный `chatName`, существующая семантика замены хранилища обновляет производную метку группы без создания другого узла группы. Свежесть остается `lastObservedAt`; имена не рассматриваются как постоянные или авторитетные.

Платформа, опускающая имя группы в более позднем сообщении, вносит фолбэк на ID для этого наблюдения. Производка графа уже выбирает самое свежее наблюдение, поэтому возвращаемая метка представляет новейшее принятое свидетельство, а не скрытый долгоживущий кеш имен.

## Платформенные свидетельства

- Пример DingTalk Stream для robot-message включает `conversationTitle` во входящем callback'е: [DingTalk Stream protocol](https://opensource.dingtalk.com/developerpedia/docs/learn/stream/protocol/#%E5%9B%9E%E8%B0%83%E6%8E%A8%E9%80%81).
- Telegram определяет `Message.chat` как `Chat`, чей `title` доступен для групповых чатов и супергрупп: [Telegram Bot API — Chat](https://core.telegram.org/bots/api/#chat).
- Событие получения сообщения Feishu перечисляет `chat_id`, `chat_type` и `thread_id`, но не отображаемое имя чата: [Feishu Open Platform — Receive message](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/events/receive).

## Стратегия тестирования

- Тесты базового канала доказывают, что пригодные имена групп распространяются, непригодные имена откатываются к полным ID, прямые сообщения игнорируют `chatName`, а более поздние наблюдения могут обновлять метки.
- Тесты адаптера DingTalk доказывают, что `conversationTitle` попадает в конверт без изменения обработки callback'ов.
- Тесты адаптера Telegram доказывают, что заголовки групп и супергрупп попадают в конверт, а приватные чаты остаются неизменными.
- Существующие тесты Feishu продолжают доказывать путь фолбэка на ID без трафика API.
- Целевые тесты хранилища покрывают замену более новыми метками; миграция схемы не требуется, поскольку сохраняемые наблюдения уже содержат `group.label`.
