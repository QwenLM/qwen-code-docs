# Гейт триажа по паттернам ревертов

Дата: 2026-07-27
Статус: предложено
Область: CI-триаж — `.github/workflows/qwen-triage.yml`, `.qwen/skills/triage/`

## Проблема

Небольшие нейтральные к поведению maintenance-PR сейчас потребляют ту же
многостадийную емкость триажа и ревью модели, что и изменения поведения.
Первоначальное предложение (PR #7414) пыталось отфильтровать их, но измерение
мейнтейнера на живом бэклоге показало лишь ~2% попаданий — функция целилась в
почти несуществующую проблему.

Тем временем в истории репозитория **111 revert-коммитов** (только в июле
2026 — 19), и **61,5% ревертов происходят в течение 24 часов после мержа** —
то есть проблема обнаруживается быстро, но уже после попадания в `main`.
Реальная стоимость — не ревью безвредных PR, а мерж PR, которые приходится
откатывать.

Этот дизайн предлагает основанный на данных гейт триажа, нацеленный на PR,
которые действительно вызывают реверты, а не на те, что уже безвредны.

## Данные

### Методология

Трехфазный анализ полной истории ревертов репозитория:

1. **Сбор**: `git log --all --grep="^Revert "` нашел 111 revert-коммитов.
   Тело каждого реверта парсилось на `This reverts commit <hash>`, затем
   исходный коммит отслеживался до его PR через `gh api`. Результат: 46
   уникальных ревертнутых PR (59 ревертов отслеживаются до номера PR; 52
   реверта имели только заголовок исходного коммита без ссылки на PR).

2. **Обогащение**: Для каждого ревертнутого PR извлекались наблюдаемые на
   момент триажа сигналы: область касания (core/auth/providers/tools/services),
   размер diff, число раундов ревью, Critical-находки бота, циклы
   CHANGES_REQUESTED, временной зазор мерж→реверт, самореверт, наличие
   E2E-верификации. 31 из 46 PR успешно обогащены; 15 удалены и недоступны
   (HTTP 404).

3. **Сравнение с контрольной группой**: Взяты 60 недавно смерженных, но не
   ревертнутых PR, извлечены те же сигналы. Вычислены precision
   (TP / (TP + FP)) и recall для каждого сигнала.

Скрипты и сырые данные (локальные артефакты анализа, не закоммичены):
`.qwen/scripts/revert-analysis-*.mjs`, `.qwen/scripts/revert-data-*.json`,
`.qwen/scripts/revert-analysis-report-v2.json`.

### Precision и recall сигналов

| Сигнал                       | Precision | Recall | Ревертнутые (n=31) | Контроль (n=60) |
| ---------------------------- | --------- | ------ | ------------------ | --------------- |
| `touches_high_risk`          | **66,7%** | 32,3%  | 10                 | 5               |
| `non_maintainer + high_risk` | **58,3%** | 22,6%  | 7                  | 5               |
| `core + contested`           | **50,0%** | 19,4%  | 6                  | 6               |
| `non_maintainer + core`      | 46,2%     | 38,7%  | 12                 | 14              |
| `touches_core`               | 44,7%     | 54,8%  | 17                 | 21              |
| `has_contested_pattern`      | 40,9%     | 29,0%  | 9                  | 13              |
| `had_changes_requested`      | 40,7%     | 35,5%  | 11                 | 16              |
| `non_maintainer`             | 39,6%     | 67,7%  | 21                 | 32              |
| `large_diff_gt_200`          | 37,0%     | 54,8%  | 17                 | 29              |
| `critical_count > 0`         | 28,6%     | 12,9%  | 4                  | 10              |
| `fast_revert_24h`            | 100,0%    | 25,8%  | 8                  | 0               |
| `self_reverted`              | 100,0%    | 9,7%   | 3                  | 0               |

**Оговорка о выборке:** precision вычислен на соотношении case-control 1:1,9
(31 ревертнутый против 60 контрольных), тогда как реальная базовая доля
репозитория ~1,37% (46/3358). Precision (PPV) — метрика, наиболее чувствительная
к такому обогащению — истинная положительная предиктивная ценность при базовой
доле репозитория намного ниже (например ~5% для `touches_high_risk`).
Sensitivity (recall) и специфичность инвариантны к соотношению выборки и
являются подходящими метриками для сравнения сигналов. _Ранжирование_ сигналов
по precision все еще валидно (оно монотонно по отношению правдоподобия при
фиксированном n), но абсолютные значения не следует цитировать контрибьюторам
как апостериорные вероятности.

`fast_revert_24h` и `self_reverted` имеют precision 100%, но это
**сигналы после мержа** — их нельзя использовать как гейты триажа, потому что
они наблюдаемы только после того, как PR уже смержен и ревертнут. Они
подтверждают существование проблемы, но не помогают ее предотвратить.

`critical_count > 0` изначально считался сильным сигналом (бот указывал на
точную корневую причину в кейсах вроде PR #6866), но после исправления regex
так, чтобы матчить только теги `**[Critical]**` (а не голое слово «critical»
в тексте вроде «no critical blockers»), precision упал до 28,6%. Бот слишком
разбрасывается Critical-находками — 16,7% PR контрольной группы тоже имеют
теги Critical.

### Определение высокорисковых путей

Сигнал `touches_high_risk` проверяет, соответствует ли любой измененный файл
этим паттернам подсистем:

- `openaiContentGenerator` — парсинг потоковых ответов
- `streamingToolCallParser` — парсинг потока вызовов инструментов
- `geminiChat` — пайплайн чата Gemini
- `acpConnection` — спавн процессов ACP
- `shell.ts` / `shellExecutionService` — выполнение shell-инструмента
- `mcp-client` / `mcp-pool` — управление MCP-серверами
- `LspServer` — управление LSP-серверами
- `acp-integration` — интеграция сессий ACP
- `relaunch.ts` — жизненный цикл перезапуска desktop-приложения
- `sandbox.ts` — управление процессами песочницы
- `electron-run-as-node` — точка входа Electron node-mode (совпадение пути)

Это пути, где неверные изменения с наибольшей вероятностью вызывают
наблюдаемые регрессии, требующие реверта.

### Временной зазор мерж→реверт

Из 13 PR с валидными (неотрицательными, после мержа) данными о зазоре:

- Медиана: 4 часа
- В пределах 24ч: 61,5%
- В пределах 72ч: 84,6%
- Максимум: 97 часов

Это подтверждает, что дефекты, вызывающие реверты, всплывают быстро после
мержа, но ущерб уже в `main`.

### Flip-flop PR

8 PR ревертились многократно (циклы revert → re-revert), что указывает на
неразрешенное противостояние:

- PR #6754 (3 реверта), PR #6751 (3 реверта), PR #3433 (3 реверта)
- PR #6869 (2 реверта), PR #5668 (2 реверта), PR #3567 (2 реверта),
  PR #3478 (2 реверта), PR #5060 (2 реверта)

Эти flip-flop PR — исходы с наибольшей стоимостью: они потребляют несколько
раундов ревью, несколько циклов мерж/реверт и часто требуют патч-релизов.

## Дизайн

### Эскалация высокорисковых путей

Когда PR не от мейнтейнера касается любого высокорискового пути (см.
определение выше), триаж Stage 1 эскалирует PR на самый глубокий уровень ревью
вместо обычного пути. Это **не** блокирует и не закрывает PR — это
гарантирует, что полный пайплайн `/review` выполняется с максимальным
покрытием агентами.

Это самый сильный сигнал на момент триажа: 10 из 31 ревертнутого PR (32,3%
sensitivity) касались этих путей, против 5 из 60 контрольных PR (91,7%
специфичности; Fisher p = 0,006).

Реализация: текст навыка Stage 1e инструктирует модель триажа выполнить
`gh pr view --json files | grep -E '...'` против паттернов высокорисковых
путей. Изменение YAML workflow не требуется — детекция выполняется внутри
навыка, а не отдельным шагом workflow.

### Чего этот дизайн НЕ делает

- **Не закрывает и не отклоняет PR автоматически.** Гейт эскалирует глубину
  ревью и рекомендует внимание мейнтейнера; он никогда не блокирует мерж и не
  закрывает PR.
- **Не использует Critical-находки бота как сигнал.** Данные показывают 28,6%
  precision — бот ставит Critical и на 16,7% безопасных PR. Critical слишком
  шумны для гейтинга.
- **Не фильтрует только по размеру PR.** `large_diff_gt_200` имеет precision
  37,0% — размер без контекста не предсказателен.
- **Не требует E2E-верификацию для всех PR.** `no_e2e` не дискриминативен —
  100% контрольной группы тоже не имеют E2E-комментариев, поэтому сигнал не
  может отличить склонные к реверту PR от безопасных.

## Не цели / follow-up

- **Уточнение Critical бота.** Текущая детекция Critical ботом слишком шумная
  (precision 28,6%). Если бы бот мог отличать «неразрешенный Critical» от
  «разрешенного Critical» (проверяя, помечен ли тред находки как resolved),
  сигнал мог бы стать полезным. Это отдельное улучшение бота, а не изменение
  гейта триажа.
- **Временно выровненная контрольная группа.** Текущая контрольная группа
  взята из 200 самых недавних смерженных PR, но ревертнутые PR охватывают
  2025–2026. Временно выровненная контрольная группа дала бы более точные
  доли false positive. API `gh pr list` не поддерживает глубокую пагинацию,
  поэтому требуется выборка на основе GraphQL-курсора.
- **Восстановление 15 удаленных PR.** 15 из 46 ревертнутых PR удалены и
  недоступны через GitHub API. Их паттерны могут отличаться от 31, которые
  удалось обогатить. Пути восстановления нет — GitHub навсегда удаляет
  закрытые PR в определенных состояниях.
- **Детекция flip-flop как realtime-гейт.** Текущий анализ обнаруживает
  flip-flop ретроспективно (после нескольких ревертов). Realtime-версия
  отслеживала бы паттерны revert→re-revert на `main` и предупреждала бы
  мейнтейнеров. Это требует отдельного workflow мониторинга, а не гейта триажа.
- **Расширение списка высокорисковых путей.** Текущий список вручную отобран
  из путей файлов ревертнутых PR. По мере эволюции кодовой базы могут
  появиться новые высокорисковые пути. Периодический повторный запуск скриптов
  анализа поддерживал бы актуальность списка.
