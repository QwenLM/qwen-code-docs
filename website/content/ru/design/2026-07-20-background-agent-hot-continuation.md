# Горячее продолжение фоновых агентов

## Контекст

Завершенный фоновый субагент в настоящее время теряет свой внутрипроцессный
рантайм. Более поздний `send_message` реконструирует новый `AgentHeadless` из
транскрипта JSONL. Это сохраняет большую часть видимой истории разговора, но
воссоздает чат, поверхность инструментов, реестры каждого агента и состояние
кеша на стороне провайдера.

Путь запуска также конструирует обычных фоновых агентов дважды: один раз с
родительским эмиттером и еще раз с выделенным фоновым эмиттером. Первый
экземпляр никогда не выполняется и не освобождается.

Этот дизайн касается жизненного цикла внутри сессии. Логическое обнаружение и
продолжение после восстановления родительской сессии обрабатываются отдельно в
дизайне восстановления ростера фоновых агентов.

Это различие поведенческое, а не просто деталь реализации. В пределах одной
сессии оживление транскрипта уже сохраняет видимый модели разговор, поэтому
горячее продолжение в первую очередь избегает реконструкции рантайма и
сохраняет состояние провайдера/инструментов. За пределами восстановления
родительской сессии исходный внутрипроцессный рантайм не может пережить
завершение процесса. Поэтому логическая непрерывность обеспечивается
восстановлением идентичности задачи и транскрипта в новой сессии с последующей
одной холодной реконструкцией.

## Цели

- Создавать один рантайм для нового обычного фонового агента.
- Сохранять этот рантайм резидентным после успешного хода.
- Продолжать завершенную задачу на том же чате и подготовленной поверхности
  инструментов.
- Сохранять текущую строку задачи, ID задачи, события начала/завершения каждого
  хода и финальные уведомления.
- Оставить оживление транскрипта фолбэком, когда совместимого резидентного
  рантайма не существует.
- Освобождать резидентные ресурсы при сбое, отмене, завершении/сбросе сессии,
  вытеснении терминальных записей, смене рабочего каталога, переключении ветки
  и закрытии/освобождении ACP-сессии.
- Атомарно захватывать ввод, поставленный в очередь в окне завершения, до
  публикации успешного завершения.

## Не цели

- Персистентность живого рантайма между процессами или восстановлением
  родительской сессии.
- Добавление значения `idle` в общий union статусов задач.
- Изменение способа внедрения сообщений, отправляемых активно работающему
  агенту, между раундами инструментов.
- Сделать форк-агентов постоянными.
- Продление времени жизни временных worktree за пределами завершенных ходов.
- Сделать глобально зарегистрированные frontmatter-хуки безопасными для
  оставления установленными, пока агент простаивает.

## Дизайн

### Переиспользуемый headless-рантайм

`AgentHeadless` сохраняет свой `GeminiChat` и подготовленные объявления
инструментов как состояние экземпляра. Его публичный `execute()` остается
операцией каждого хода:

- одновременно может выполняться только один вызов;
- финальный текст и режим завершения сбрасываются в начале; статистика
  сбрасывается для новой родительской инструкции, но остается накопительной
  между внутренними повторами stop-hook'а этой инструкции;
- первый вызов создает чат и подготавливает инструменты;
- последующие вызовы добавляют новый ход пользователя в тот же чат и эмитят
  событие внешнего сообщения, чтобы транскрипт JSONL оставался полным.

Это сохраняет существующие хуки `AgentHeadless`, телеметрию, дренирование
внешних сообщений и контракт терминального результата. `AgentInteractive` не
используется, поскольку его API очередей не обеспечивает семантику результата
завершения каждого хода и уведомлений, требуемую фоновыми задачами.

### Резидентный контроллер

`BackgroundTaskRegistry` владеет внутрипроцессной таблицей контроллеров с
ключами по ID задачи. Контроллер намеренно отделен от `AgentTask`, который
остается сериализуемой записью UI/статуса.

Контроллер умеет:

- начинать продолжение с завершенной строки;
- прерывать и освобождать свой рантайм.

При `send_message` на завершенную задачу инструмент сначала спрашивает реестр о
резидентном продолжении. Попадание синхронно переводит существующую строку
обратно в `running`, захватывает обычный слот фонового выполнения и
планирует новый ход после полного устаканивания предыдущего хода. Промах
использует существующий сервис оживления транскрипта.

`completed` по-прежнему означает «последний ход завершен». Резидентность
рантайма — внутренний факт реализации, поэтому общий статус задач и UI не
получают нового состояния idle.

### Ресурсы хода и резидентные ресурсы

Каждое продолжение получает новый AbortController, пару хуков SubagentStart/Stop,
спан трассировки, событие начала задачи, уведомление о завершении и переход
статуса sidecar. Рантайм, которому требовалась бы аренда разрешений AUTO
только для дочерних, не удерживается, поскольку эти аренды не подсчитываются по
ссылкам между конкурентными субагентами.

Чат, подготовленные инструменты, писатель JSONL, слушатели событий, реестр
инструментов с областью действия агента и ресурсы MCP каждого агента остаются
живыми, пока контроллер резидентен. Освобождение идемпотентно.

Существующий лимит удержания терминальных записей также ограничивает резидентные
контроллеры. Очистка строки освобождает ее контроллер. Сброс и завершение работы
реестра освобождают все контроллеры, включая уже завершенные.

### Исключения совместимости

Первая версия удерживает только обычных именованных фоновых агентов, которые:

- завершились нормально;
- не используют `isolation: "worktree"`;
- не объявляют frontmatter-хуки;
- не требуют аренды разрешений AUTO только для дочерних.

Временные worktree в настоящее время финализируются после каждого хода, поэтому
удержание рантайма оставило бы его Config указывающим на удаленный каталог.
Frontmatter-хуки в настоящее время регистрируются глобально на время своей
жизни, поэтому их удержание в простое могло бы повлиять на несвязанную работу.
Аренды AUTO только для дочерних мутируют родительский менеджер разрешений и не
подсчитываются по ссылкам между конкурентными субагентами, поэтому повторный
захват на каждом горячем ходу был бы небезопасным. Агенты с хуками, изоляцией
worktree и AUTO только для дочерних продолжают идти через существующий поток
оживления JSONL. Реконструированный агент worktree выполняется из текущего
родительского рабочего каталога, поскольку его временный worktree запуска уже
финализирован.

## Гонки и обработка сбоев

- Непосредственно перед публикацией успешного завершения совместимым рантаймом
  активный ход дренирует очередь реестра без уступки (yield). Если он
  захватывает ввод, тот же headless-рантайм выполняет этот ввод, и задача
  остается running. Если очередь пуста, сохранение транскрипта и переход
  running→completed происходят синхронно, поэтому более поздний `send_message`
  наблюдает завершенную строку и использует путь резидентного продолжения
  вместо получения вводящего в заблуждение подтверждения о постановке в очередь.
  Ходы с изоляцией worktree выполняют свое финальное дренирование перед
  разбором, поскольку их рантайм намеренно не может быть продолжен после.
- Реестр выполняет переход completed→running синхронно до планирования промиса
  продолжения. Второй конкурентный `send_message` поэтому наблюдает `running` и
  использует существующую очередь сообщений внутри раунда.
- Следующий ход прицепляется после промиса предыдущего хода, покрывая окно, в
  котором уведомление о завершении эмитится до завершения предыдущего блока
  `finally`.
- Сбойные и отмененные ходы удаляют и освобождают резидентный контроллер.
- Если захват фонового слота не удается, строка остается completed, и вызывающий
  может использовать существующий путь ошибки холодного оживления.
- Освобождение во время активного хода прерывает его контроллер и откладывает
  разрушающую очистку ресурсов до финализатора хода.

## Валидация

Юнит-тесты должны доказать:

- новый фоновый запуск создает ровно один `AgentHeadless`;
- два последовательных хода используют один `GeminiChat` и один подготовленный
  список инструментов;
- завершенный `send_message` предпочитает резидентный контроллер;
- отсутствие резидентного контроллера по-прежнему вызывает оживление транскрипта;
- вторая инструкция пользователя присутствует в JSONL;
- сброс, завершение работы/отмена и очистка терминальных записей освобождают
  ровно один раз.
- `/branch` отказывает работающей фоновой работе и освобождает резидентных
  терминальных агентов только после успешной инициализации ветки;
- смены рабочего каталога и освобождение ACP-сессии высвобождают резидентные
  рантаймы.

Сценарий E2E использует один ID задачи для двух завершенных фаз и проверяет, что
вторая фаза помнит nonce из первой. Физическая идентичность рантайма проверяется
юнит-тестами, поскольку stream JSON не раскрывает количество конструкторов.
