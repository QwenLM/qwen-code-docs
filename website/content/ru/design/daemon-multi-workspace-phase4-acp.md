# Фаза 4 мульти-воркспейсного демона: ACP с квалификацией по рабочему пространству

## Резюме

Этот документ проектирует Фазу 4 задачи #6378: ACP с квалификацией по
рабочему пространству для `qwen serve`. Он строится непосредственно на ветке
Фазы 3 с REST, квалифицированным по рабочему пространству
(`codex/phase3-workspace-qualified-rest`, PR #6567), которая **еще не слита**
(состояние `CHANGES_REQUESTED`). Фаза 4 монтирует эндпоинт ACP на каждое
рабочее пространство по адресу `/workspaces/:workspace/acp`, дает каждому
рантайму рабочего пространства свой диспетчер ACP и состояние соединений, и
позволяет Web Shell выбирать рабочее пространство из `/capabilities`. Legacy
`/acp` остается привязанным к primary-рантайму, поэтому существующие Web Shell
и ACP-клиенты не затрагиваются.

Фаза 4 ограничена транспортом ACP (Streamable HTTP + reverse-WebSocket
`/acp`, его зеркалированные методы рабочего пространства и reverse MCP/CDP).
Voice (`/workspaces/:workspace/voice/stream`) и управляемые демоном воркеры
каналов — это **Фаза 4b**; динамическое добавление/удаление рабочих
пространств — это **Фаза 5**. Ни то, ни другое сюда не входит.

Ключевой вывод из исследования стыков: Фаза 4 — в основном изменение
_обвязки и маршрутизации_, а не переписывание. `AcpDispatcher` уже привязан к
рабочему пространству по конструкции, его проверка согласованности
`workspaceCwd` уже существует, Фаза 3 уже сделала зеркалированную
REST-поверхность per-runtime, а `clientMcpSenderRegistry` уже является полем
per-runtime. Реальная работа состоит в том, чтобы (1) превратить единственное
монтирование ACP в один диспетчер на рантайм (каждый со своей remember-полосой;
по-прежнему один вызов `mountAcpHttp` и один слушатель upgrade;
`AcpHttpHandle`, владеющий реестрами всех рантаймов), (2) расширить этот
слушатель upgrade WebSocket для диспетчеризации по пути URL, (3) сохранить
реестр device-flow общедемоновым и разделяемым между всеми монтированиями (с
fan-out событий по мере возможности в бридж каждого доверенного рантайма), и
(4) синхронизировать новый тег возможности (capability)
`workspace_qualified_acp` в типах возможностей SDK/CLI и тестах.

## Систематическая переработка (ужесточение, PR #6621)

Ревью выявило Critical: более ранняя итерация сделала реестр device-flow
per-runtime, что оставило вторичные монтирования неаутентифицированными
(`device_flow "not configured"`). Монтирование ACP было переработано по восьми
осям; итоговая архитектура такова:

1. **Фабрика монтирований ACP рантайма.** Один вызов `mountAcpHttp` владеет
   `primaryMount` плюс картой `secondaryMounts` (по одному `RuntimeAcpMount`
   на не-primary рантайм), каждый с флагом `primary`. HTTP и WS оба разрешают
   монтирование по селектору и делегируют общим обработчикам.
2. **Маршрутизация + изоляция соединений.** Множественный селектор алиасит
   primary-рабочее пространство на `primaryMount` и в остальных случаях
   разрешает монтирование per-runtime. Недоверенные не-primary рабочие
   пространства отклоняются (403) и на HTTP-, и на WS-пути до запуска любого
   потомка.
3. **Разбор сырого request-target WS.** Слушатель upgrade разбирает сырой
   request-target (а не `new URL().pathname`, который нормализует `%2e%2e`),
   так что ненормализованный селектор с точечными сегментами/обратными
   слэшами уничтожается до маршрутизации.
4. **Общедемоновый device-flow + fan-out.** Реестр device-flow остается единым
   инстансом демона (учетные данные OAuth процесс-глобальны). Вторичные
   монтирования разделяют его через `opts.deviceFlowRegistry`; события потока
   аутентификации рассылаются по мере возможности в бридж каждого доверенного
   рантайма (`resolveEventBridges`).
5. **Только primary для CDP + client-MCP.** Захваты CDP-туннеля гейтятся по
   `activeMount.primary`; множественный POST возвращает промис диспетчеризации.
6. **Гейт жизненного цикла после dispose.** После `dispose()` общие
   HTTP-обработчики возвращают `503 server_disposed` вместо гонки с
   разобранными реестрами во время дренирования при завершении. `dispose()`
   идемпотентен.
7. **Агрегированная наблюдаемость.** `AcpHttpHandle.getSnapshot()` суммирует
   счетчики соединений и WS-потоков по primary и всем вторичным
   монтированиям, так что метрики демона сообщают ACP-соединения всех рабочих
   пространств, а не только primary.
8. **Объявление возможностей.** `resolveAcpHttpEnabled()` — единственная
   интерпретация `QWEN_SERVE_ACP_HTTP`; `workspace_qualified_acp` объявляется
   только когда поверхность ACP HTTP включена **и** мульти-воркспейсные
   сессии активны.

## Ужесточение стыков после ревью

Архитектура монтирований выше остается без изменений. Финальный проход
исправления закрывает шесть пробелов границ, не заменяя `AcpHttpHandle` и не
вводя новый модуль политики маршрутов.

1. **Одно решение о готовности квалифицированного маршрута.** ACP с
   квалификацией по рабочему пространству готов только когда ACP HTTP включен
   и реестр рабочих пространств содержит более одного рантайма. Регистрация
   HTTP-маршрутов, распознавание пути WebSocket, объявление возможностей и
   освобождение от внешнего rate-limiter должны согласовываться с этим
   решением. Демоны с одним рабочим пространством продолжают предоставлять
   только legacy `/acp`.
2. **Одно списание rate-limit.** Внешний лимитер Express точно освобождает
   включенный транспортный путь `/workspaces/<single-selector>/acp`, включая
   существующее поведение маршрута по регистру и завершающему слэшу. Близкие
   пути остаются лимитированными. Транспорт ACP остается ответственным за
   применение уровней методов JSON-RPC, так что квалифицированный промпт
   потребляет только бакет промптов, а не оба бакета мутаций и промптов.
3. **Структурированная ошибка неправильного пути.** Ошибки декодирования
   параметров маршрута Express, которые одновременно являются экземплярами
   `URIError` и помечены HTTP-статусом 400, возвращают структурированный
   `400 invalid_request`. Другие брошенные значения `URIError` и несвязанные
   ошибки сохраняют общую обработку 500. Путь WebSocket сохраняет свой
   существующий явный ответ 400.
4. **Лог-безопасные селекторы.** Декодированный селектор, используемый в
   ориентированном на оператора логе отказа WebSocket, проходит через
   существующий санитизатор `logSafe`, так что кодированные управляющие
   символы терминала не могут подделать или разбить строки stderr.
5. **Терминальный dispose.** `dispose()` — необратимый переход жизненного
   цикла. После его выполнения `attachServer()` не может воссоздать сервер
   WebSocket или слушатель upgrade. Повторные вызовы `dispose()` и
   `attachServer()` остаются безвредными.
6. **Полная диагностика с атрибуцией по рабочему пространству.** Агрегированный
   снимок ACP получает аддитивную диагностику соединений, декорированную
   `workspaceId`, `workspaceCwd` и `primary`. Счетчики сводки остаются без
   изменений, публичный primary-`registry` остается доступным для
   совместимости, и демон с `detail=full` читает агрегированный список
   соединений. Существующий лимит соединений остается ограничением per-mount,
   поскольку каждое монтирование конструируется с одним и тем же настроенным
   лимитом.

Каждый контракт закреплен регрессионным тестом, написанным до его
продакшен-изменения. Верификация включает фокусированные наборы ACP,
rate-limit, daemon-status и serve-server, плюс сборку, typecheck, lint и
проверку замыкания бандла быстрого пути serve.

## Зависимости от Фазы 3 (не слита)

Фаза 4 потребляет эти стыки Фазы 3. Поскольку PR #6567 находится в состоянии
`CHANGES_REQUESTED`, относитесь к ним как к _подлежащим стабилизации_;
реализация Фазы 4 должна перебазироваться на слитую Фазу 3.

- `packages/cli/src/serve/workspace-route-runtime.ts`:
  - `resolveRegisteredWorkspaceRuntimeByPathSelector(registry, selector)` —
    чистая функция, возвращает `WorkspaceRuntime | undefined`. **Переиспользуема
    слушателем upgrade WS** (см. Открытые вопросы).
  - `resolveWorkspaceRuntimeFromParam(registry, req, res, param)` — привязана к
    Express (пишет `res.status().json()`). **Пригодна для HTTP-маршрутов ACP,
    но не для пути upgrade WS** (у слушателя upgrade есть только сырые
    `IncomingMessage` + `socket`, без Express `res`).
  - `requireTrustedWorkspaceRuntime(runtime, res)` — гейт доверия, привязанный
    к Express, переиспользуется HTTP-маршрутами ACP.
  - `isPortableAbsolutePath` / `sendWorkspaceMismatch` — переиспользуются для
    разбора селектора и формы ошибки.
- Обработчики REST per-runtime, зарегистрированные в `server.ts`
  (`registerWorkspaceQualified{FileRead,FileWrite,Trust,Status,Permissions,Settings,Lifecycle,McpControl,Tools}Routes`).
  Диспетчер ACP зеркалирует эти поверхности; Фаза 4 полагается на то, что их
  поведение per-runtime существует.
- `workspaces[]` в `/capabilities` (Фаза 2a), построенный в
  `packages/cli/src/serve/routes/capabilities.ts` (L79-84) и зеркалированный в
  `packages/cli/src/serve/daemon-status.ts` (L432-437) с `id` / `cwd` /
  `primary` / `trusted` на рантайм. Объявления feature-флагов и их предикаты
  объявления/переключения находятся в
  `packages/cli/src/serve/capabilities.ts`.

## Базовая линия: текущий стык ACP (дерево Фазы 3)

- `mountAcpHttp(app, primaryBridge, opts)` в
  `packages/cli/src/serve/acp-http/index.ts` вызывается один раз из
  `server.ts` (L1226-1275) со **всецело primary** входами: `primaryBridge`,
  `primaryBoundWorkspace`, `primaryWorkspace`,
  `primaryRouteFileSystemFactory`, глобальным для приложения
  `deviceFlowRegistry`, `primaryRuntime.clientMcpSenderRegistry` и
  `primaryRuntime.env` (для voice `extraWsRoute`).
- Один диспетчер на монтирование: `mountAcpHttp` строит один `AcpDispatcher` и
  один `ConnectionRegistry` и возвращает `AcpHttpHandle`, чей `registry` — это
  тот единственный реестр, а `attachServer` устанавливает ровно один слушатель
  `httpServer.on('upgrade', ...)` (index.ts L1536, L1555). `dispose` удаляет
  этот один слушатель и закрывает этот один реестр (index.ts L1543-1553).
- **Единственный слушатель upgrade WebSocket** (index.ts `setupWebSocket`,
  обработчик upgrade на L903-1045). Он устанавливается один раз через
  `AcpHttpHandle.attachServer(server)` после `listen()`. Он:
  - разбирает URL upgrade,
  - отклоняет любой путь, не являющийся `opts.path` (`/acp`), `/cdp` или
    записью `extraWsRoutes` — `socket.destroy()` на неизвестном пути
    (index.ts L935-939),
  - выполняет общие проверки безопасности (loopback, allowlist хостов,
    CSRF/origin, bearer-токен) для **всех** путей,
  - затем ветвится: `/cdp` -> `attachCdpClient`; `extraRoute` ->
    `onConnection`; иначе handshake инициализации ACP.
  - Комментарий в документации на L328-337 явен: второй слушатель `'upgrade'`
    не может сосуществовать, поскольку этот уничтожает неизвестные пути. Фаза 4
    должна расширить этот один слушатель, а не добавлять другой.
- `AcpDispatcher` (dispatch.ts L644-656) уже привязан к рабочему пространству
  конструктором: `bridge`, `boundWorkspace`, `workspace`,
  `workspaceRememberLane`, `fsFactory?`, `deviceFlowRegistry?`,
  `sessionShellCommandEnabled`, `registry?`, `archiveCoordinator`. Все
  зеркалированные методы рабочего пространства, которые он обслуживает, читают
  эти поля, поэтому привязка диспетчера к рантайму автоматически ограничивает
  file / permissions / settings / trust / tools / mcp / memory / agents / auth
  этим рантаймом.
- Две из этих зависимостей диспетчера сегодня привязаны к primary в
  единственном экземпляре:
  `workspaceRememberLane = new WorkspaceRememberTaskLane(primaryBridge)`
  (server.ts L816) и `archiveCoordinator = new SessionArchiveCoordinator()`
  (server.ts L596). `sessionShellCommandEnabled` — глобальная политика, ее
  безопасно разделять.
- Проверка согласованности уже существует: `parseRequestedWorkspace`
  (dispatch.ts L694-697) бросает `WorkspaceMismatchError`, когда `workspaceCwd`
  запроса не равен `this.boundWorkspace`; ошибка отображается в
  `INVALID_PARAMS` (L577).
- `WorkspaceRuntime` (workspace-registry.ts L28-38) несет
  `clientMcpSenderRegistry` per-runtime, но **не имеет поля
  `deviceFlowRegistry`** — device-flow все еще глобален для приложения
  (`setupDeviceFlowRegistry({ app, bridge })` на server.ts L609, привязан к
  primary-бриджу).

## Архитектура: монтирование ACP per-runtime

Сохраняем Вариант B: один демон, N независимых рантаймов рабочих пространств.
Для ACP:

- Каждый зарегистрированный рантайм получает свой `AcpDispatcher` +
  `ConnectionRegistry` + фабрику провайдеров reverse-MCP, все привязанные к
  `bridge` / `workspace` / `routeFileSystemFactory` /
  `clientMcpSenderRegistry` / `env` этого рантайма. Каждый диспетчер получает
  один и тот же общедемоновый реестр device-flow.
- Legacy `/acp` остается привязанным к диспетчеру primary-рантайма
  (поведение протокола без изменений).
- Новый `/workspaces/:workspace/acp` привязывается к диспетчеру разрешенного
  рантайма.
- **Инвариант: `mountAcpHttp` по-прежнему вызывается ровно один раз** и
  устанавливает ровно один слушатель `httpServer.on('upgrade', ...)`. Он
  меняется с «единственный бридж + opts» на прием `WorkspaceRegistry` (плюс
  общие, не связанные с рабочими пространствами вопросы: токен,
  allowedOrigins, имя хоста, `checkRate`, `sessionShellCommandEnabled`,
  `cdpTunnelRegistry`). Внутри он строит
  `Map<workspaceId, RuntimeAcpMount>`; primary-запись остается адресуемой по
  legacy-пути `/acp`.
- Каждый `RuntimeAcpMount` конструируется с собственными `bridge`,
  `workspace`, `routeFileSystemFactory`, `clientMcpSenderRegistry`, `env`
  рантайма, новым per-runtime `WorkspaceRememberTaskLane(runtime.bridge)`, его
  `AcpDispatcher` и его `ConnectionRegistry`. Общедемоновый реестр
  device-flow, `archiveCoordinator` и `sessionShellCommandEnabled`
  разделяются.
- Все четыре точки входа диспетчеризации должны выбирать монтирование
  разрешенного рантайма, а не primary: `POST`, `GET` (SSE) и `DELETE` на
  множественном пути (Express, через `resolveWorkspaceRuntimeFromParam`;
  сегодня каждый замыкает единственный диспетчер на index.ts
  L533/L675/L849), плюс ветка upgrade WS (ниже). Legacy `/acp`
  POST/GET/DELETE/upgrade продолжают диспетчеризацию в primary.
- `AcpHttpHandle` должен вырасти из единственного `registry` во владение
  диспетчером + `ConnectionRegistry` каждого рантайма; `dispose` закрывает их
  все и удаляет единственный слушатель upgrade.
- Жизненный цикл сессий: ACP `session/new` / `load` / `resume` на множественном
  монтировании должны вызывать те же колбэки `register` / `remove` жизненного
  цикла бриджа, которые питают `WorkspaceSessionOwnerIndex` Фазы 2b
  (workspace-registry.ts L48-119). Сессия, созданная через
  `/workspaces/B/acp`, должна затем быть обнаруживаемой чтениями REST с
  диспетчеризацией по владельцу (context, stats и т.д.), и наоборот. Фаза 2b
  уже огранила этот индекс покрытием «REST и поздний диспетчер ACP»; Фаза 4 —
  это место, где сторона ACP действительно подключается.

## Диспетчеризация upgrade WebSocket (ключевой дизайн)

Слушатель upgrade — единственное место, где маршрутизация ACP не управляется
Express, поэтому ей нужна явная обработка пути.

- Сохранить общие проверки безопасности (loopback / allowlist хостов / CSRF /
  bearer) ровно как есть, применяемыми единообразно до любого разрешения
  рабочего пространства.
- Расширить классификацию пути. Сегодня:
  `pathname === '/acp' | '/cdp' | extraRoute`. Фаза 4 добавляет ветку для
  `/workspaces/:workspace/acp`:
  1. Сопоставить префикс и извлечь сырой сегмент селектора `:workspace`.
  2. Разрешить чистой функцией
     `resolveRegisteredWorkspaceRuntimeByPathSelector(registry, decodeURIComponent(selector))`
     (сначала id, затем кодированный канонический cwd, соответствуя
     резолверу REST).
  3. При отсутствии совпадения: отклонить upgrade закрытием класса 400
     (`socket.write('HTTP/1.1 400 ...')` + `destroy()`), зеркаля REST
     `workspace_mismatch`. Без фолбэка на primary.
  4. При совпадении: выполнить handshake инициализации ACP против диспетчера +
     `ConnectionRegistry` разрешенного рантайма (а не primary).
- Reverse `/cdp` и voice `extraWsRoutes` остаются привязанными к primary в
  Фазе 4 (voice — это 4b). Ветка `/cdp` без изменений.
- Legacy `/acp` upgrade продолжает привязываться к primary-диспетчеру.
- `%2F` в кодированном cwd-селекторе: демон сам разбирает сырой URL upgrade
  (`new URL(req.url, ...)`), поэтому он не подвержен декодированию путей
  Express, но reverse-прокси все равно могут нормализовать `%2F`.
  Рекомендуйте селектор на основе `id` для WS в деплойментах с прокси (та же
  рекомендация, что и для REST Фаз 2b/3). HTTP-множественные маршруты вместо
  этого переиспользуют `resolveWorkspaceRuntimeFromParam`, который читает
  `req.params` (Express декодирует один раз), поэтому они бесплатно наследуют
  обработку кодированного селектора из Фазы 3.
- Наблюдаемость: путь upgrade WS и его диспетчеризация ACP обходят middleware
  Express, поэтому телеметрия/логирование демона должны явно штамповать
  разрешенное рабочее пространство здесь (та же причина, по которой
  `checkRate` пробрасывается через `opts`); хэширование рабочего пространства
  во время запроса Фазы 1 покрывает только маршруты Express.

## Реестр device-flow per-runtime (заменено — см. ось 4 «Систематической переработки»)

> **Заменено.** Этот раздел — дизайн до переработки (реестр device-flow
> per-runtime). Ревью обнаружило, что он оставлял вторичные монтирования
> неаутентифицированными, поэтому поставленная реализация вместо этого
> сохраняет единый общедемоновый реестр, разделяемый всеми монтированиями, с
> fan-out событий по мере возможности — см. ось 4 «Систематической
> переработки» выше. Подразделы ниже сохранены только как контекст истории
> дизайна и не описывают поставленное поведение.

Device-flow — единственная зеркалированная поверхность, которая все еще
глобальна для приложения и должна измениться.

- Добавить `deviceFlowRegistry` в `WorkspaceRuntime` (или строить по одному на
  рантайм внутри `mountAcpHttp`). Диспетчер каждого рантайма получает свой
  реестр.
- `setupDeviceFlowRegistry` должен вызываться per-runtime (привязанным к
  бриджу/окружению этого рантайма), а не один раз против primary-бриджа.
- Маршруты/методы аутентификации с квалификацией по рабочему пространству
  (`GET/DELETE /workspaces/:workspace/auth/device-flow/:id` и методы ACP
  `_qwen/workspace/auth/device_flow/*`) должны разрешать реестр целевого
  рантайма и отклонять/скрывать потоки, принадлежащие другому рабочему
  пространству.
- Завершение должно освобождать реестр каждого рантайма, а не только
  `app.locals.deviceFlowRegistry`.
- Колбэки установки провайдеров аутентификации уже ограничены
  `boundWorkspace` внутри диспетчера; диспетчеры per-runtime делают это
  корректным автоматически. Legacy primary-маршруты аутентификации продолжают
  писать в primary.

## Зеркалируемая поверхность диспетчера (привязка рантайма)

Reverse `/acp` WS зеркалирует большую поверхность REST (index.ts
`WS_READ_METHODS` L186-219 и вендорные методы dispatch.ts): чтение/листинг/
glob/stat файлов, mcp / skills / providers / env / preflight / trust /
permissions / voice / tools / agents / memory / auth рабочего пространства,
группы сессий, setup-github. Поскольку все они читают поля конструктора
диспетчера, привязка диспетчера к рантайму ограничивает их бесплатно. Фаза 4
**не** реализует их заново; она только гарантирует, что диспетчер каждого
рантайма конструируется с зависимостями этого рантайма. Этот набор явно
включает per-runtime `deviceFlowRegistry` и `WorkspaceRememberTaskLane`: если
любой из них оставить синглтоном primary, не-primary вызовы
`_qwen/workspace/memory/remember` и `auth/device_flow` молча выполнялись бы
против primary-бриджа.

Гарантия согласованности: поскольку каждый смонтированный диспетчер привязан
к рантайму, а `parseRequestedWorkspace` уже бросает `WorkspaceMismatchError`,
когда `workspaceCwd` запроса отличается от `boundWorkspace`, клиент,
подключившийся к `/workspaces/A/acp`, но отправляющий `workspaceCwd: B` в
параметрах, отклоняется. Фазе 4 следует добавить тест, утверждающий это, и
подтвердить, что тот же охранник покрывает `session/new`
(`parseOptionalWorkspaceCwd`, dispatch.ts L1059).

## Изоляция reverse MCP / CDP

- Reverse-канал инструментов: `clientMcpProviderFactory` сейчас замыкает
  `primaryRuntime.clientMcpSenderRegistry` + `primaryBridge` (server.ts
  L1252-1257). Монтирования per-runtime строят фабрику из
  `clientMcpSenderRegistry` + `bridge` _разрешенного рантайма_, так что
  WS-соединение на `/workspaces/B/acp` регистрирует размещенные у клиента
  MCP-серверы только в рантайме B.
- Per-connection `ClientMcpWsConnection` и `cdpEndpoint` остаются
  per-connection; они просто присоединяются к диспетчеру владеющего рантайма.
- CDP-туннель: `cdpTunnelRegistry` ограничен процессом, а CDP-бридж захватывается
  соединением `/acp` расширения, у которого
  `clientInfo.name === 'qwen-cdp-bridge'`. Фаза 4 сохраняет захват CDP на
  legacy `/acp` (primary) как прагматичный дефолт; CDP с областью по рабочему
  пространству вынесен в Открытые вопросы, а не решен здесь, поскольку один
  loopback-клиент puppeteer + один эндпоинт `/cdp` не отображаются чисто на N
  рантаймов. Конкретно, не-primary `RuntimeAcpMount` должны оставлять ветку
  `cdpTunnelOverWs` / `/cdp` и регистрацию runtime-MCP `chrome-devtools`
  выключенными; их подключает только primary-монтирование.

## Гейт доверия

- Недоверенные зарегистрированные рабочие пространства остаются
  видимыми/read-only, но не должны запускать потомка. На
  `/workspaces/:workspace/acp` операции, предоставляющие владение
  (`session/new`, `session/load`, `session/resume`; dispatch.ts
  `CONN_ROUTED_METHODS` L239-243), должны отклоняться с ошибкой
  `untrusted_workspace` и не запускать потомка, соответствуя семантике REST 403
  `untrusted_workspace`, уже реализованной в `routes/session-runtime.ts`
  (L39-53) и `routes/session.ts` (гейты доверия создания/загрузки/возобновления
  сессии плюс `session_workspace_conflict`).
- Переиспользовать решение о доверии, которое Фаза 3 предоставляет через
  `requireTrustedWorkspaceRuntime`, для HTTP-маршрутов ACP; для пути WS
  эквивалентная проверка выполняется по флагу `trusted` разрешенного рантайма
  до того, как handshake предоставит сессию.
- Доверие, замороженное при загрузке, — базовая линия Фазы 2a; флипы доверия в
  рантайме (дренирование/остановка ACP-потомка рабочего пространства +
  очистка его индекса сессий при отзыве) остаются согласованными с тем, какая
  фаза мутаций доверия будет поставлена, и здесь не реализуются заново.

## Возможности и пикер Web Shell

- Добавить feature-флаг ACP (например, `workspace_qualified_acp`) в
  `packages/cli/src/serve/capabilities.ts` (объявление флага + предикат
  объявления/переключения), объявляемый только когда зарегистрировано более
  одного рантайма и ACP включен (зеркаля гейтинг `multi_workspace_sessions` на
  capabilities.ts L408-409). Если Фаза 4 поставляется через несколько PR, не
  объявляйте тег, пока полный множественный цикл ACP (HTTP + WS + device-flow
  + подключение индекса владельца) не завершен, чтобы клиенты никогда не
  строили URL `/workspaces/:id/acp` против наполовину подключенной поверхности
  (та же философия охранника половинчатого включения, как у feature-гейта Фазы
  2a). Обновите примечание к `workspace_qualified_rest_core` (L264-271),
  которое сейчас гласит: «ACP/WebSocket, auth, voice и расширения остаются на
  своих существующих маршрутах primary-рабочего пространства в этой фазе».
- Добавление тега не локально для `capabilities.ts`. Он должен быть
  синхронизирован с: построителем ответа `/capabilities` в
  `routes/capabilities.ts`, типами возможностей SDK
  (`packages/sdk-typescript/src/daemon/types.ts`), типами serve CLI
  (`packages/cli/src/serve/types.ts`) и ассерцией feature-set в
  `server.test.ts` (L376-381). Это обязательная работа Фазы 4, а не
  опциональная.
- `workspaces[]` уже существует (Фаза 2a), построен в `routes/capabilities.ts`
  (L79-84) и `daemon-status.ts` (L432-437) с `id` / `cwd` / `primary` /
  `trusted` на рантайм. Web Shell читает его и строит URL соединений
  `/workspaces/:id/acp`; пикер отключает (или помечает read-only) недоверенные

- `DaemonClient` в SDK (добавлен в Фазе 3) уже читает `caps.workspaces[].cwd`

  рабочему пространству — естественное расширение. Синхронизация типов
  возможностей выше обязательна; сам помощник подключения может последовать.

## Пути ошибок

- `workspace_mismatch`: неизвестный селектор WS/HTTP -> отклонение класса 400;
  никогда не откатываться на primary.
- `untrusted_workspace`: операция ACP, предоставляющая владение, на недоверенном
  рантайме -> отклонение, без запуска.
- Несовпадение параметра `workspaceCwd`: `WorkspaceMismatchError` ->
  `INVALID_PARAMS` (уже подключено).
- Крах потомка: изолирован во владеющем рантайме; диспетчеры и соединения
  других рантаймов не затрагиваются (больший радиус отказа единого демона —
  документированное известное ограничение).
- Отзыв доверия: когда будет поставлена фаза мутаций доверия, отзыв рантайма
  должен дренировать/останавливать его ACP-потомка и очищать его индекс
  сессий; Фаза 4 только гарантирует, что монтирование ACP per-runtime
  дренируемо, она не добавляет саму мутацию доверия.
- Глобальное завершение: освободить `ConnectionRegistry` каждого рантайма,
  затем один раз освободить единственный общедемоновый реестр device-flow.
- Rate limiting: допуск ACP HTTP/WS использует `checkRate` с ключами по
  соединению/сессии (index.ts L627-641, L1175-1178). Множественные
  монтирования разделяют один лимитер; ключи должны оставаться однозначными
  между рантаймами, чтобы одно рабочее пространство не могло исчерпать или
  обойти бюджет другого.
- Емкость: `maxConnections` обеспечивается `ConnectionRegistry` per-runtime,
  так что общее число ACP-соединений масштабируется до N x `maxConnections`
  (бюджет на рабочее пространство, соответствуя модели `maxSessions` на
  рабочее пространство). Общее число новых сессий остается ограниченным
  допуском `maxTotalSessions` Фазы 2a на стыке бриджа, через который уже
  проходит создание сессий ACP.

## Стратегия тестирования

- Диспетчеризация upgrade WS: юнит-тестировать классификацию пути — `/acp`
  (primary), `/workspaces/:id/acp` (разрешено), неизвестный селектор
  (отклонение), кодированный `%2F` cwd-селектор, и что общие проверки
  безопасности по-прежнему выполняются для множественного пути.
- Кросс-воркспейсная изоляция: соединение на `/workspaces/A/acp` не может
  видеть или управлять сессией, принадлежащей B; `session/list` и
  зеркалированные чтения возвращают только представление A.
- Владение через транспорты: сессия, созданная через `/workspaces/B/acp`,
  разрешается чтениями REST с диспетчеризацией по владельцу (например,
  `GET /session/:id/stats`) и через `resolveLiveSessionOwner`, подтверждая,
  что создание ACP питает индекс владельца.
- Согласованность: подключиться к A, отправить `workspaceCwd: B` ->
  `WorkspaceMismatchError`.
- Гейт доверия: `session/new|load|resume` на недоверенном рантайме ->
  отклонение, без запуска потомка.
- Device-flow: каждое монтирование достигает общедемонового реестра;
  публикация событий рассылаются в primary и доверенные вторичные бриджи, один
  сбойный бридж не блокирует другие, и завершение освобождает реестр один раз.
- Reverse MCP: `mcp_register` на `/workspaces/B/acp` попадает только в
  `clientMcpSenderRegistry` B и бридж B.
- Rate limiting: промпты/мутации на `/workspaces/A/acp` и `/workspaces/B/acp`
  измеряются независимо, и ни один не может обойти общий лимитер.
- Возможности: `workspace_qualified_acp` объявляется только при более чем 1
  рантайме; форма `workspaces[]` без изменений.

## Открытые вопросы / обратная связь для Фазы 3

1. **Сохранить `resolveRegisteredWorkspaceRuntimeByPathSelector` чистой
   функцией.** Слушатель upgrade WS не может использовать привязанную к
   Express `resolveWorkspaceRuntimeFromParam`. Фаза 4 зависит от того, что
   чистый резолвер остается свободным от связки с `req`/`res`. Если ревью
   Фазы 3 меняет этот стык, сохраните чистую точку входа
   `(registry, selector) => runtime | undefined`.
2. **Владение device-flow (решено).** Сохранить реестр общедемоновым,
   поскольку учетные данные OAuth процесс-глобальны. Фаза 4 разделяет этот
   реестр с каждым диспетчером и рассылает санитизированные события в бриджи
   доверенных рантаймов.
3. **Модель CDP-туннеля per-workspace.** Один loopback-клиент puppeteer + один
   эндпоинт `/cdp` не отображаются чисто на N рантаймов. Фаза 4 сохраняет CDP
   на primary; подтвердите, что это приемлемо, или ограничьте follow-up для
   CDP с квалификацией по рабочему пространству.
4. **Откладывание voice.** Подтвердите, что voice остается только на primary
   до Фазы 4b, даже несмотря на то, что диспетчер ACP уже предоставляет чтения
   `_qwen/workspace/voice`.
5. **Область `archiveCoordinator`.** Сегодня это один
   `SessionArchiveCoordinator` (server.ts L596). Подтвердите, что его
   разделение между рантаймами безопасно с учетом квалифицированного по
   рабочему пространству архива/организации Фазы 3, или сделайте его
   per-runtime.
6. **Измерение ключей rate-limit.** Решите, нужны ли ключам допуска
   множественного ACP явное измерение по рабочему пространству, или ключи по
   соединению/сессии уже однозначны между монтированиями.
