# Диспетчеризация по причине уведомлений GitHub

## Цель

Использовать `notification.reason` для выбора промпта, отправляемого каналом
GitHub, не меняя его polling, продвижение курсора, повторы или поведение
сообщения об ошибках.

| Причина             | Поведение                                                                   |
| ------------------- | --------------------------------------------------------------------------- |
| `mention`           | Отправлять только контент, который действительно упоминает бота.             |
| `review_requested`  | Для pull request отправлять промпт ревью с данными pull request.             |
| `assign`            | Отправлять промпт триажа с данными issue.                                    |
| `author`, `comment` | Агрегировать новые комментарии окна в один follow-up промпт.                 |
| Другая              | Сохранять по-комментарную обработку и идентифицировать причину уведомления.  |

События ревью и назначения используют актора события GitHub как отправителя
Envelope, чтобы существующая политика отправителей проверяла человека,
инициировавшего действие, а не автора issue или pull request. Агрегация
включает только разрешенных отправителей и ограничена последними 20
комментариями и 400 символами на комментарий. Политика спаривания сохраняет
по-комментарную диспетчеризацию, поэтому каждый отправитель авторизуется
независимо.

Курсор запоминает до 500 ID диспетчеризованных узлов комментариев и прямых
событий. Фиксированный нижний порог времени установки позволяет запоздалым
уведомлениям о ревью и назначении находить свое событие без воспроизведения
предустановочной истории. ID уведомлений не сохраняются, потому что GitHub
переиспользует их для более поздней активности в том же треде.

## Верификация

Сфокусированный тест адаптера покрывает каждый маршрут, метаданные прямого
триггера, вырезание упоминаний, авторизацию агрегации и дедупликацию
комментариев и прямых событий.
