# Адаптивный лимит вызовов инструментов на ход

Дата: 2026-07-17
Статус: Реализовано
Область: `packages/core` обнаружение циклов

## Проблема

Всегда включенный лимит вызовов инструментов на ход (`model.maxToolCallsPerTurn`, по умолчанию 100) — это грубый прерыватель: он останавливает ход на 101-м вызове инструмента независимо от того, действительно ли модель застряла или выполняет продуктивную работу. Большие ходы реализации в нескольких пакетах легитимно превышают 100 вызовов инструментов, поэтому лимит убивает продуктивную работу — ложное срабатывание.

Конкретный случай: сессия `80db472f-…` (qwen-code-x1, «Web Shell git status/diff chip»). Ход `继续Phase 2` сделал ровно 100 вызовов инструментов и был жестко остановлен посреди `npm run build` без сводки завершения. Анализ этого хода и соседних:

| ход | вызовов инструментов | различных ключей (инструмент, аргументы) | макс. повторов одного ключа | макс. серия одинаковых имен |
| --- | -------------------- | ---------------------------------------- | -------------------------- | -------------------------- |
| 7   | 96                   | 96                                       | 1                          | 7                          |
| 8   | 100                  | 99                                       | 2                          | 3                          |
| 9   | 95                   | 95                                       | 1                          | 7                          |

Продуктивные ходы очень разнообразны: ни один вызов `(инструмент, аргументы)` не повторяется более двух раз. Действительно застрявший ход повторяет один и тот же вызов много раз.

## Дизайн

Поведение зависит от того, был ли `maxToolCallsPerTurn` **явно настроен** (отслеживается `Config.isMaxToolCallsPerTurnExplicit()`):

- **Явное значение `N`** → **жесткий лимит** (выпущенный контракт): ход останавливается на вызове, превышающем `N`, без адаптивного продления. Это сохраняет обратную совместимость — пользователь, установивший значение для ограничения стоимости без присмотра, по-прежнему получает ровно эту границу. (v0.19.10 выпустил лимит как жесткий; более ранняя итерация этого PR умножала явные значения на 3, что было ломающим изменением — отменено.)
- **По умолчанию (не установлено, `S = 100`)** → **адаптивный**: отличать продуктивный длинный ход от застрявшего, используя сигнал повторений, и жестко останавливать только последний (плюс абсолютный страховочный предел). Современные модели легитимно делают сотни вызовов на задачу, поэтому значение по умолчанию не должно жестко останавливать продуктивные длинные ходы.

Два порога для адаптивного (по умолчанию) лимита:

- **Мягкий лимит `S`** (100): когда ход превышает `S` вызовов инструментов, останавливать только при наличии сигнала застревания с повторами; иначе считать ход продуктивным и позволить ему продолжаться.
- **Жесткий лимит `S * ADAPTIVE_CAP_HARD_MULTIPLIER`** (множитель 10 → 1000): абсолютный страховочный предел. Останавливать независимо от повторений при превышении, чтобы убегающий процесс, меняющий аргументы при каждом вызове (который не ловит ни один сигнал повторений), все равно был ограничен. Множитель достаточно высок, чтобы продуктивные ходы с сотнями вызовов не давали ложных срабатываний.

Сигнал застревания с повторами: максимальное число появлений любого одиночного ключа `(инструмент, аргументы)` в ходе достигает `GLOBAL_DUPLICATE_THRESHOLD` (6). Это переиспользует существующую семантику глобальных дубликатов и имеет широкий запас безопасности (наблюдаемые продуктивные ходы ≤ 2).

Серия одинаковых имен намеренно НЕ используется как сигнал гейта: параллельные пакеты инструментов (например, несколько `read_file` разных файлов в одном сообщении ассистента) легитимно создают серии одинаковых имен из 6–7, слишком близко к порогу стагнации действий 8.

### Всегда включенное отслеживание

Лимит всегда включен (не гейтится `skipLoopDetection`), но существующая карта `globalToolCallCounts` поддерживается только внутри гейтированного эвристического пути. Чтобы всегда включенный лимит был независим от гейтированного пути, лимит поддерживает свой небольшой всегда включенный трекер:

- `capKeyCounts: Map<string, number>` — счетчики по `(инструмент, аргументы)` для этого хода.
- `capMaxKeyRepeat: number` — текущий максимум счетчика любого одиночного ключа.

Поддерживается в `checkAlwaysOnSafeties` для каждого `ToolCallRequest`, очищается в `reset()` и при `Retry` (согласованно с тем, как эвристический путь очищает `globalToolCallCounts` при повторе).

## Матрица поведения

Явное значение `N` (жесткий лимит):

| всего вызовов | результат        |
| ------------- | ---------------- |
| `≤ N`         | разрешить        |
| `> N`         | остановка (жесткая) |

По умолчанию (не установлено), мягкий лимит `S = 100`, жесткий лимит `H = 1000`:

| всего вызовов   | сигнал повторений        | результат             |
| --------------- | ------------------------ | --------------------- |
| `≤ S`           | любой                    | разрешить             |
| `S < всего ≤ H` | макс. повторов ключа `< 6` | разрешить (продуктивный) |
| `S < всего ≤ H` | макс. повторов ключа `≥ 6` | остановка (застрял) |
| `> H`           | любой                    | остановка (страховочный предел) |

Когда `S ≤ 0`, лимит отключен (`getMaxToolCallsPerTurn()` возвращает `Infinity`); поведение не меняется (никогда не срабатывает).

## Не цели / последующие работы

- Возобновление остановленного хода на месте (архитектурно неосуществимо: ход уже возвращен, когда появляется диалог).
- Изменение UI диалога обнаружения цикла (отдельное улучшение).
- Отдельная настройка для жесткого лимита (выводится из мягкого лимита; поднятие `maxToolCallsPerTurn` масштабирует оба).
- Сигнал застревания с окном недавности или учетом результатов. Текущий сигнал — это монотонный максимум на ход: один и тот же `(инструмент, аргументы)`, повторенный 6 раз в любом месте хода, помечает его застрявшим, даже если эти повторы легитимны (например, перезапуск той же сборки/теста после последовательных фиксов). Это никогда не регрессия — сигнал действует только за мягким лимитом, где старый лимит всегда останавливал, — но этот продуктивный класс не выигрывает. Свидетельство «продуктивные ходы повторяют ≤ 2» исходит из трех ходов одной сессии; пересмотреть с оконным сигналом, если телеметрия покажет этот паттерн ложного застревания.
- Различение двух причин остановки в телеметрии. Застревание на мягком лимите и жесткий страховочный предел оба выпускают `TURN_TOOL_CALL_CAP`; булево/атрибут на `LoopDetectedEvent` показал бы, какой сработал в реальных условиях (полезно для валидации множителя 10×). Headless-сообщение уже подстраховывается, покрывая оба.
- Путь ACP/демона (`recordDaemonToolCalls` в `packages/cli/src/acp-integration/session/Session.ts`) имеет свой грубый лимит на ход, не использующий `LoopDetectionService`. Он всегда трактует значение как жесткий лимит независимо от повторений. Согласование его с адаптивным значением по умолчанию — отдельная последующая работа (он отслеживает вызовы инструментов пакетами и потребовал бы собственного отслеживания повторов по `(инструмент, аргументы)`). Интерактивный путь TUI, создавший описанное ложное срабатывание, исправлен здесь.
