# Дизайн восстановления после краха сессии и унифицированного сервиса восстановления

## 1. Цели дизайна

Recovery Service — унифицированный слой принятия решений для восстановления
сессии. Он читает восстановленную историю сессии, классифицирует текущее
состояние восстановления, строит протокольные исправления и payload
продолжения, необходимые для продвижения, и выставляет один и тот же
результат для TUI, демона, SDK и headless-входов.

Существующие возможности включают:

- Append-only JSONL-хранилище сессий.
- Загрузку сессии и реконструкцию истории API.
- Исправление осиротевших `tool_use` / `tool_result`.
- Обнаружение прерывания с тремя состояниями.
- Entrypoint продолжения для headless, управления nonInteractive и ACP.

Главная проблема сегодня не в том, что возможность восстановления полностью
отсутствует. Проблема в том, что:

- Решения о восстановлении разбросаны по нескольким entrypoint.
- TUI / демон / SDK не видят одно и то же состояние восстановления.
- Исправление происходит неявно на низком уровне и не видно пользователям или
  клиентам.
- Любое будущее состояние восстановления нужно было бы повторно прошивать в
  несколько entrypoint.

Цели унифицированного Recovery Service:

- Унифицированная классификация: каждый entrypoint использует один и тот же
  план восстановления.
- Унифицированное исправление: каждый entrypoint переиспользует одно и то же
  исправление пар инструментов и классификацию прерывания.
- Унифицированная видимость: TUI / демон / SDK могут все определить, чистое
  ли возобновление, прерванное или деградированное.
- Унифицированные данные отладки: исправления, синтезированные результаты и
  отбрасывания выставляются как структурированный вывод для отображения и
  логов.
- Унифицированное тестирование: одни и те же фикстуры краха могут покрывать
  основной план и каждый адаптер entrypoint.

## 2. Основной дизайн: Recovery Service

Добавить сервис в core:

```text
packages/core/src/core/session-recovery.ts
```

Он не рендерит UI и не исполняет инструменты. Его единственная
ответственность — создавать детерминированный `SessionRecoveryPlan` из
транскрипта сессии и текущей истории чата.

Предлагаемые типы:

```ts
export type SessionRecoveryKind =
  | 'clean'
  | 'interrupted_prompt'
  | 'interrupted_turn'
  | 'degraded_history';

export type RecoveryRepair =
  | { type: 'synthesized_tool_result'; callId: string; name: string }
  | { type: 'dropped_duplicate_tool_result'; callId: string; name: string }
  | { type: 'history_gap'; childUuid: string; missingParentUuid: string };

export interface SessionRecoveryPlan {
  planId: string;
  sessionId: string;
  kind: SessionRecoveryKind;
  originalApiHistory: Content[];
  apiHistory: Content[];
  repairs: RecoveryRepair[];
  canContinue: boolean;
  canAutoContinue: boolean;
  requiresUserConfirmation: boolean;
  visibleNotice?: string;
  continuation?: {
    mode: 'retry_user_parts' | 'tool_result_parts';
    parts: Part[];
    displayText: string;
  };
}
```

Предлагаемый entrypoint:

```ts
export function buildSessionRecoveryPlan(input: {
  sessionId: string;
  conversation: ConversationRecord;
  historyGaps?: HistoryGap[];
  options?: {
    allowAutoContinue?: boolean;
  };
}): SessionRecoveryPlan;
```

Основной поток:

1. Построить `originalApiHistory` из `ConversationRecord`.
2. Если существуют неигнорируемые `historyGaps`, классифицировать сессию как
   `degraded_history`.
3. Запустить `detectTurnInterruption` на `originalApiHistory`. Это должно
   произойти до исправления. Иначе висящий `model[functionCall]` был бы
   сначала закрыт синтетическим `functionResponse`, делая невозможной
   классификацию состояния как `interrupted_turn`.
4. Клонировать `originalApiHistory` в безопасную для провайдера историю,
   запустить существующий `repairOrphanedToolUseTurns` на клоне и сохранить
   результат в `plan.apiHistory`.
5. Построить payload продолжения из классификации:
   - `interrupted_prompt`: воспроизвести хвостовые пользовательские части с
     семантикой Retry.
   - `interrupted_turn`: закрыть висящие вызовы инструментов синтетическими
     частями `functionResponse` с ошибкой.
6. Создать `visibleNotice` и `repairs` для отображения и отладки UI / демона /
   SDK.

Совместимость именования:

- Продолжать использовать существующую публичную строку протокола
  `interrupted_turn`; не добавлять `interrupted_tool_turn`. Управление
  nonInteractive, ACP и существующие тесты уже зависят от
  `interrupted_turn`, и Recovery Service не должен добавлять стоимость
  миграции.

## 3. Роль и ценность Recovery Service

### 3.1 Надежность

Унифицированный сервис превращает текущее неявное и разбросанное поведение
восстановления в явную машину состояний.

Текущее состояние:

- Инициализация возобновления исправляет осиротевшие записи `tool_use`, но
  entrypoint не всегда знают, что исправление произошло.
- Headless / ACP могут продолжать, но TUI не знает, что сказать пользователю.
- Пробелы родительской цепочки уже имеют частичную видимую обработку:
  `SessionService.loadSession` возвращает `historyGaps`, и TUI / ACP могут
  отображать уведомления о пробелах. Однако по-прежнему нет унифицированных
  метаданных восстановления или консистентной политики safe mode.

После внедрения Recovery Service:

- Каждое возобновление сначала выдает явное состояние: `clean`,
  `interrupted_prompt`, `interrupted_turn` или `degraded_history`.
- Любой entrypoint может решить, продолжать ли, уведомлять или деградировать,
  основываясь на одном и том же плане.
- Пробелы истории не трактуются молча как чистая история.
- Если позже добавляются новые состояния восстановления, нужно расширить
  только построение плана; каждому entrypoint не нужно переимплементировать
  логику.

Выигрыш в надежности состоит в том, что восстановление переходит от «каждое
место исправляет понемногу по необходимости» к «каждое восстановление имеет
один унифицированный результат классификации».

### 3.2 Безопасность

Самый большой риск безопасности при восстановлении — автоматическое повторение
действий с побочными эффектами, таких как shell-команды, записи файлов или
вызовы внешних API.

Принципы безопасности Recovery Service:

- По умолчанию не воспроизводить автоматически неизвестные инструменты.
- По умолчанию преобразовывать висящие вызовы инструментов в неудачные части
  `functionResponse` и позволять модели решать, повторять ли.
- `interrupted_turn` по умолчанию имеет `requiresUserConfirmation = true`,
  если вызывающий явно не включил иное.
- `degraded_history` никогда не продолжается автоматически.
- Все синтетические исправления включаются в `repairs` для логов и отладки.

Это обеспечивает приоритет:

- Провайдеры не получают невалидную историю.
- Пользователи не повторяют опасные действия из-за логики восстановления.
- TUI / SDK могут ясно показать, какие результаты инструментов были
  синтезированы как сбои восстановления.

Ценность безопасности в том, что восстановление не возобновляет исполнение
вслепую. Оно сначала исправляет форму протокола, затем продолжает с
консервативной политикой.

### 3.3 Полнота

Этот дизайн не решает немедленно каждый сценарий краха. Он фокусируется на
состояниях, которые текущие возможности могут классифицировать надежно.

Покрывается немедленно:

- Чистое возобновление.
- Хвостовой пользовательский промпт: `interrupted_prompt`.
- Хвостовая отправка результата инструмента: также классифицируется как
  `interrupted_prompt` и воспроизводится с Retry.
- Висящий вызов инструмента: `interrupted_turn`, с синтезированными
  результатами инструмента с ошибкой.
- Несмежный результат инструмента: существующее исправление поднимает его в
  легальную позицию. Первая версия этого плана не записывает детали
  подъема отдельно, если API исправления позже не будет расширен возвращать
  их.
- Дублирующийся результат инструмента: отбросить дубликат.
- Пробел родительской цепочки: `degraded_history`.

Еще не покрывается:

- Стрим текста модели, который отключается на середине, но оставляет хвост,
  выглядящий как обычный текст модели.
- Тонкое различие между graceful-прерыванием и неизвестным крахом.

Полнота здесь достигается не добавлением большого количества кода за один раз.
Она достигается консолидацией текущих возможностей в унифицированный план,
чтобы состояния, которые можно классифицировать сегодня, обрабатывались
консистентно.

### 3.4 Инженерная архитектура

Recovery Service должен находиться в core, а не в CLI, TUI, демоне или любом
отдельном entrypoint.

Причины:

- `SessionService`, `buildApiHistoryFromConversation`, исправление
  `GeminiChat` и `detectTurnInterruption` — все находятся в core или
  прилегающих к core слоях.
- TUI / headless / ACP / демон / SDK — адаптеры.
- Классификация восстановления — доменная логика, а не логика рендеринга UI.

Предлагаемое расслоение:

```text
SessionService
  Read JSONL, rebuild ConversationRecord, return historyGaps

SessionRecoveryService
  Build RecoveryPlan from ConversationRecord + historyGaps

GeminiClient / GeminiChat
  Consume plan.apiHistory to initialize chat
  Execute plan.continuation when needed

TUI / headless / ACP / daemon / SDK
  Display plan.visibleNotice
  Trigger continuation from user or API requests
```

Преимущества этого расслоения:

- Core владеет фактами и решениями.
- UI владеет отображением.
- Демон / SDK владеют протокольным выводом.
- Тесты могут проходить основной план напрямую без загрузки полного TUI.

### 3.5 Видимость и отлаживаемость

План, создаваемый Recovery Service, должен быть преобразуем в два вида
вывода:

1. Видимое пользователю уведомление:

```text
The previous session stopped after tool execution. Marked 2 unfinished tool
calls as failed so the history can be sent safely. You can continue the task;
the model will decide whether to retry based on the failure results.
```

2. Лог отладки или опциональная системная запись:

```ts
type RecoveryDebugPayload = {
  planId: string;
  kind: SessionRecoveryKind;
  repairs: RecoveryRepair[];
  timestamp: string;
};
```

Эта информация не попадает в историю API. Она только для диагностики,
экспорта и отладки. Персистентность как системной записи может быть отложена
и не является жестким требованием этого дизайна.

Ценность:

- Пользователи знают, что произошло во время восстановления.
- Клиенты SDK могут показывать точное состояние.
- Отчеты о багах могут включать `planId` и `repairs`.
- Один и тот же прерванный хвост с меньшей вероятностью будет продолжен
  автоматически несколько раз.

## 4. Интеграция entrypoint

### 4.1 TUI

После `/resume` или запуска с `--resume`:

1. `SessionService.loadSession(sessionId)`.
2. `buildSessionRecoveryPlan(...)`.
3. `config.startNewSession(sessionId, sessionData, recoveryPlan)` или
   эквивалентный механизм для удержания плана.
4. Загрузить историю UI.
5. Если `plan.kind !== 'clean'`, вставить элемент INFO.
6. Предоставить `/continue` или действие "Continue interrupted turn".

TUI не продолжает автоматически `interrupted_turn` / `degraded_history` по
умолчанию.

### 4.2 Headless / управление nonInteractive

`continueInterrupted` или `continue_last_turn` больше не вызывает разбросанные
детекторы напрямую. Вместо этого:

1. Построить план из текущей истории чата или возобновленного разговора.
2. Если `plan.canContinue = false`, вернуть no-op.
3. Если продолжение разрешено, исполнить `plan.continuation`.

### 4.3 ACP / демон

Добавить метаданные восстановления в ответ `loadSession` / `resumeSession`:

```ts
{
  recovered: boolean;
  recoveryKind: SessionRecoveryKind;
  canContinue: boolean;
  requiresUserConfirmation: boolean;
  repairs: {
    type: string;
    count: number;
  }
  [];
}
```

`continueLastTurn` также должен принимать / отклонять на основе плана, затем
ревалидировать непосредственно перед исполнением.

### 4.4 SDK

Интеграции SDK нужно различать две категории:

- SDK на базе демона: потребляет метаданные восстановления из ответов демона
  `loadSession` / `resumeSession`, показывает баннер восстановления и
  позволяет пользователю или хост-приложению запускать продолжение.
- SDK на базе процесса: запускает CLI через `ProcessTransport` и использует
  флаги `--resume` / `--continue`. Ему нужны эквивалентные метаданные
  восстановления, выставляемые через системное сообщение stream-json или поле
  протокола SDK.

Ни одна категория SDK не должна напрямую понимать низкоуровневый JSONL или
исправление пар инструментов. Они должны только потреблять структурированный
результат восстановления, выставляемый слоем entrypoint, и они должны
блокировать автопродолжение в деградированных состояниях.

## 5. Дизайн unit-тестов

Recovery Service должен иметь независимые unit-тесты, не зависящие от TUI или
реального провайдера.

Основные фикстуры:

1. Чистая история:
   - Хвост текста модели.
   - Полный вызов инструмента + результат инструмента + финальная модель.

2. `interrupted_prompt`:
   - Последняя запись — текст пользователя.
   - Последняя запись — группа пользовательских частей functionResponse.
   - Несколько хвостовых записей пользователя.

3. `interrupted_turn`:
   - functionCall модели без functionResponse.
   - Несколько functionCall, из которых завершены только некоторые.
   - FunctionCall без id пропускается.

4. Исправление:
   - Несмежный functionResponse поднимается, и безопасная для провайдера
     история легальна.
   - Дублирующийся functionResponse отбрасывается.
   - Форма синтетического результата инструмента остается консистентной с
     существующим исправлением.

5. `degraded_history`:
   - `historyGaps` непусты.
   - Подтвердить `canAutoContinue = false`.
   - Подтвердить, что `visibleNotice` включает информацию о пробелах.

6. Контрольная точка сжатия:
   - Хвост после последнего сжатия обнаруживается корректно.
   - Системные записи не попадают в историю API.

Тесты адаптеров entrypoint:

- TUI `/resume` вставляет элемент INFO после получения нечистого плана.
- Headless `continueInterrupted` использует продолжение плана и не
  дублирует сообщение пользователя.
- ACP `continueLastTurn` возвращает тот же вид восстановления для той же
  фикстуры.
- Ответ демона `loadSession` включает метаданные восстановления.

Ключевая цель тестов: одна и та же фикстура истории должна давать один и тот
же вид восстановления в core / TUI / ACP / демоне.

## 6. Заключение

Унифицированный Recovery Service — изменение с наибольшей ценностью на этом
этапе, потому что он в основном консолидирует существующие возможности вместо
немедленного введения множества новых механизмов.

Его прямая ценность:

- Делает состояние восстановления консистентным между TUI / демоном / SDK /
  headless.
- Превращает существующее исправление осиротевших `tool_use` из неявного шага
  предотвращения 400 в явный план восстановления.
- Превращает продолжение прерванного хода из локальной возможности headless /
  ACP в переиспользуемую возможность core.
- Предоставляет стабильную точку расширения для будущих состояний
  восстановления.

Он не решает каждую проблему краха сам по себе, особенно крахи в середине
стрима текста. Этот документ намеренно держит эти расширения вне области для
этого раунда, чтобы избежать чрезмерного дизайна. Текущая цель —
унифицировать возможности восстановления, которые уже существуют и могут быть
классифицированы надежно.
