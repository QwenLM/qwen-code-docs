# Фолбэк vision-бриджа для PDF

## Контекст

`read_file` для PDF работает с приоритетом текста, когда первичная модель не имеет нативной поддержки PDF. Извлечение текста все равно может не работать для сканированных документов, а одна плотная страница может превысить безопасный бюджет результата инструмента в 12K токенов. Возвращать отрендеренные страницы напрямую небезопасно для текстового провайдера, тогда как обработка каждого большого текстового результата как изображения сделала бы обычные многостраничные чтения медленнее и менее точными.

## Дизайн

Слой обработки файлов может подготовить внутреннего кандидата vision-бриджа только для PDF. Эта опция отделена от существующего сохранения неподдерживаемых изображений, используемого для интерактивных `@`-вложений, поэтому обычные чтения изображений не меняются. Кандидат содержит отрендеренные части изображений, причину срабатывания, фактический диапазон отрендеренных страниц, структурированные метаданные продолжения и исходную ошибку извлечения текста для восстановления, если транскрипцию не удается завершить. Метаданные продолжения различают страницы, которые точно существуют, и страницы, которые могут существовать, когда подсчет страниц недоступен.

Кандидаты создаются только когда извлечение текста PDF не удается или когда явное или фактическое одностраничное чтение все равно превышает оценку в 12K токенов. Переполнение текста на нескольких страницах, гейты диапазона страниц больших документов и гейты размера файла сохраняют свои существующие рекомендации. Рендеринг начинается с запрошенной первой страницы и обрабатывает не более четырех страниц за один вызов `read_file`. Запрошенный диапазон обрезается до фактического числа страниц PDF, когда оно известно: шестистраничный документ, запрошенный как `pages: "4-8"`, рендерит страницы 4-6 и не выдумывает страницы 7-8. Когда подсчет страниц недоступен, короткий рендер без усечения по байтам трактуется как конец файла; полный рендер из четырех страниц или усечение по байтам сообщает только о том, что могут существовать дополнительные запрошенные страницы.

`ReadFileTool` включает подготовку, только когда первичная модель текстовая и настроена или доступна модель vision-бриджа. Он вызывает бридж перед построением финального ответа инструмента, передавая только отрендеренные страницы изображений плюс структурированный контекст страниц PDF. Бриджу дается инструкция помечать секции транскрипции оригинальными номерами страниц PDF. Рекомендации по продолжению добавляются после транскрипции и указывают только на оригинальный PDF, никогда на временные отрендеренные изображения.

При успехе `read_file` возвращает недоверенную, приблизительную машинную транскрипцию и никаких данных изображений. Структурированное отображаемое уведомление раскрывает выбранную vision-модель, эндпоинт, когда он известен, диапазон транскрибированных страниц и известное или возможное продолжение. TUI рендерит это уведомление даже при свернутом выводе успешного чтения и при развернутых деталях транскрипта; ACP, неинтерактивный структурированный вывод и экспорты сессий включают тот же текст в содержимое вызова инструмента вместо опоры на непрозрачный сырой вывод. При сбое бриджа, пустом выводе, таймауте или изменении выбора модели данные изображений отбрасываются, а модели восстанавливается точная исходная ошибка PDF, при этом попытка бриджа остается видимой только в отображении пользователю. Отмена пользователем распространяется. Следовательно, никакое изображение кандидата не может достичь текстового первичного провайдера через результат инструмента.

Явно настроенная `visionModel` трактуется как разрешение использовать эту модель, даже если она размещена у другого провайдера. Существующее уведомление бриджа сообщает фактический эндпоинт, чтобы граница данных оставалась видимой.

## Совместимость

Публичная схема `read_file` не меняется. Нативные PDF-модели, первичные модели с поддержкой vision, конфигурации без модели бриджа, обычные чтения PNG/JPEG и существующее поведение интерактивных изображений сохраняют свои текущие пути. Интерактивное разрешение `@` PDF дополнительно выигрывает от фолбэка переполнения одной страницы.

## Верификация

Юнит-покрытие проверяет запрошенные диапазоны, начинающиеся не со страницы 1, запросы за пределами фактического конца документа, неизвестное число страниц, усечение по байтам, пустые рендеры, переполнение одной и нескольких страниц, успех и сбои бриджа, отмену, изменения конфигурации, раскрытие эндпоинта на поверхностях TUI/ACP/экспорта, подсказки с номерами страниц и инвариант, что текстовые результаты не содержат `inlineData`. E2E-верификация сравнивает глобальный базовый уровень с локальной сборкой, используя шестистраничный сканированный PDF, плотный одностраничный PDF и многостраничный PDF с большим объемом текста.
