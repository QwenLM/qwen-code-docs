# Фоновые обновления npm

## Проблема

Опубликованный CLI разбит по коду на JavaScript-чанки с content-hash. Запуск
`npm install -g` из активной сессии заменяет эти чанки на месте, поэтому
более поздний динамический импорт в старом процессе может упасть с
`ERR_MODULE_NOT_FOUND`. Откладывание установки до выхода из сессии избегает
повреждения, но превращает фоновое обновление в задержку при выходе и не дает
пользователям пользы до тех пор, пока они не покинут сессию.

## Дизайн

Для перезаписываемых глобальных установок npm проверка обновления после
рендера устанавливает точную разрешенную версию в каталог, выведенный из
глобального лаунчера:

```text
~/.qwen/updates/npm/<launcher-id>/versions/<version>/
```

Проверка версии запускает npm в его глобальном контексте, а подготовленная
установка использует изолированный prefix. Подготовленная команда явно
сохраняет исходную глобальную конфигурацию npm, поэтому смена prefix не
переключает настройки реестра или аутентификации между обнаружением и
установкой.

Лаунчер разрешает `QWEN_HOME` из тех же `.env`-файлов скоупа home перед
выбором версии. Это держит путь бутстрэпа согласованным с хранилищем CLI,
хотя полный загрузчик окружения выполняется позже.

Установка и активация выполняются в отвязанном воркере, поэтому выход из TUI
не прерывает уже идущее обновление. После успешного выхода npm воркер
проверяет имя пакета, версию, бандл и лаунчер, затем атомарно записывает
указатель `active.json` рядом с версиями этого лаунчера. Глобальный npm-пакет
не модифицируется. Уже запущенный процесс и любые дочерние команды, которые
он запускает, остаются привязанными к своей исходной сборке. При следующем
вызове стабильный лаунчер читает указатель и запускает проверенный каталог
версии.

Каждый глобальный npm-лаунчер имеет свой указатель и payload версий, поэтому
установки под разными prefix npm или nvm могут разделять `~/.qwen` без
переопределения друг друга или разделения зависимостей. Более медленное
конкурентное обновление не может заменить более новую активную версию.

Неполная установка никогда не меняет активный указатель. Перед активацией
воркер валидирует установленный манифест и запускает smoke-тест лаунчера.
Отсутствующий, некорректный или не совпадающий с лаунчером указатель
игнорируется, и исходный npm-пакет остается фолбэком. Указатель также
записывает базовый пакет и идентичность лаунчера, поэтому более поздняя явная
глобальная установка npm замещает управляемую версию. Поскольку лаунчер не
заменяется управляемыми обновлениями, существующие поля `active.json` —
контракт совместимости: будущие изменения могут добавлять поля, но не должны
удалять или переинтерпретировать их.

Каталоги версий сохраняются, потому что старая живая сессия все еще может
загружаться из них. Очистка намеренно отложена до тех пор, пока использование
диска не покажет, что нужен сборщик на основе аренды.

## Область

Это меняет автоматические обновления только для установок npm. Другие
менеджеры пакетов и автономные архивы сохраняют существующее безопасное к
выходу поведение, пока у них не появится эквивалентной раскладки установки с
иммутабельными версиями.
