# Ленивая загрузка undici (ленивый запуск, фаза 3)

- Статус: реализовано
- Issue: QwenLM/qwen-code#7264 (кандидат 4), продолжение #4748
- Предшественники: `2026-07-19-lazy-telemetry-sdk-loading.md`,
  `2026-07-19-telemetry-protocol-split.md`

## Проблема

После фаз телеметрии undici — единственный крупнейший оставшийся сторонний
участник жадного замыкания запуска ACP: 2057 КиБ в двух скопированных копиях в
бандле (cli резолвит свою `undici`, core резолвит другую). Каждый статический
`import { … } from 'undici'` где-либо в замыкании тянет полную копию в
parse/compile холодного старта, хотя undici нужен только когда запрос
действительно отправляется — прокси-диспетчеры, предподключение, опции fetch
IDE-клиента, настройка GitHub, самообновление.

Metafile показал восемь точек импорта значений (импорты только типов бесплатны):

| Пакет | Точка                          | Использует                                 |
| ----- | ------------------------------ | ------------------------------------------ |
| core  | `utils/runtimeFetchOptions.ts` | `Agent`, `ProxyAgent`, `EnvHttpProxyAgent` |
| core  | `config/config.ts`             | `EnvHttpProxyAgent`, `setGlobalDispatcher` |
| core  | `ide/ide-client.ts`            | `Agent` (HTTP keep-alive IDE)              |
| cli   | `utils/apiPreconnect.ts`       | `fetch`                                    |
| cli   | `commands/channel/proxy.ts`    | `EnvHttpProxyAgent`, `setGlobalDispatcher` |
| cli   | `utils/gitUtils.ts`            | `ProxyAgent`                               |
| cli   | `services/setup-github.ts`     | `ProxyAgent`                               |
| cli   | `utils/standalone-update.ts`   | `fetch`                                    |

## Дизайн

Все восемь точек переходят на динамический `import('undici')`, сведенный в две
локальных для пакета single-flight помощницы:

- `packages/core/src/utils/runtimeFetchOptions.ts` — `loadUndici()`, плюс
  существующая `preloadRuntimeFetchModule()` теперь делегирует ей. Синхронные
  потребители (`getOrCreateSharedDispatcher`, `buildFetchOptionsWithDispatcher`)
  сохраняют свою громко падающую `requireUndici()`; асинхронные точки входа,
  которые могут ждать (`createContentGenerator`, `Config.initialize`,
  подключение IDE-клиента), предзагружают до выполнения любого синхронного
  построения.
- `packages/cli/src/utils/load-undici.ts` — тот же хелпер, намеренно
  продублированный (см. «Почему два хелпера»).

Заметки по точкам вызова:

- `Config`: глобальный прокси-диспетчер устанавливается асинхронно; промис
  сохраняется и ожидается в начале `initialize()`, поэтому диспетчер на месте
  до любой сетевой активности, соответствуя прежней синхронной гарантии порядка.
- `createContentGenerator` делает `await preloadRuntimeFetchModule()` до того,
  как конструкторы провайдеров синхронно построят опции fetch на основе undici.

## CJS-интероп esbuild (сложная часть)

esbuild компилирует CJS-пакет undici в динамический чанк **только с default**:
`export default require_undici()`, без именованных экспортов. Поэтому
`const { Agent } = await import('undici')` работает в Node и vitest (которые
синтезируют именованные экспорты для CJS), но деструктурирует `undefined` в
бандле. Локальные запуски тестов не могут это поймать — только собранный в
бандл smoke-запуск.

`loadUndici()` поэтому нормализует: если `Object.keys(mod)` в точности
`['default']`, распаковать `mod.default`; иначе вернуть пространство имен как
есть. Проверка единственного ключа (а не `mod.default ?? mod` или
`'default' in mod`) намеренна:

- мок-прокси vitest **бросают исключение** при доступе к несуществующему
  экспорту `default`, поэтому зондирование `mod.default` ломает каждый тест с
  `vi.mock('undici')`;
- моки, построенные как `{ ...actual }`, могут нести ключ `default` рядом с
  именованными экспортами и не должны распаковываться.

## Почему два хелпера (а не один, экспортированный из core)

cli и core резолвят **разные** копии undici. Если бы код cli вызывал
размещенную в core `loadUndici()`, `import('undici')` резолвился бы внутри
области видимости пакета core, ускользая от `vi.mock('undici')` в тестах cli —
моки молча перестают перехватывать (наблюдалось: мок `ProxyAgent` никогда не
вызывался в `setup-github.test.ts`). Один хелпер на пакет сохраняет способность
тестов каждого пакета мокать свою собственную undici.

## Защита

`scripts/check-serve-fast-path-bundle.js` добавляет undici в
`FORBIDDEN_ACP_PACKAGES`: статический повторный импорт где-либо в жадном
замыкании ACP роняет CI. После изменения жадное замыкание уменьшается с
15,42 МиБ / 132 чанка до 13,39 МиБ / 130 чанков, байты undici 2057 КиБ → 0;
бандль сохраняет ровно два динамических entry-чанка undici (по одному на копию
пакета), оба за нормализующими хелперами.

## Принятие (2C4G, дисциплина #4748)

30 парных последовательных холодных стартов, контроль = сборка фазы 2,
кандидат = это изменение: парный P50 процесс→первая сессия −89,5 мс
(1336,8 → 1255,2), кандидат быстрее в 30/30 пар; прогретый путь не изменился
(P50 80,7 → 78,0); RSS после первой сессии −8,1 МБ. Функциональные гейты
(конкурентность, отключенная телеметрия, legacy одиночная сессия) все пройдены.
Полные числа в `.qwen/e2e-tests/phase3-lazy-undici-bench-results.md`.

## Отклоненные альтернативы

- **Единый общий хелпер, экспортированный из core**: ломает моки тестов cli и
  связывает копию undici в cli с копией core (две копии уже на разных версиях
  в HEAD: 7.27.2 против 7.28.0).
- **Жадная предзагрузка верхнего уровня, запускаемая при старте**: держит
  стоимость parse вне критического пути, только если ничто не ждет ее, но весь
  смысл в том, что большинству холодных стартов undici не нужна до первой
  сессии; предзагрузка вернула бы конкуренцию за CPU на 2 ядрах, которую
  измерила фаза 2.
- **Замена использования undici на глобальный `fetch`**: глобальный fetch в
  Node — это undici, но коду нужны опции диспетчеров
  `Agent`/`ProxyAgent`/`EnvHttpProxyAgent`, которые глобальная поверхность не
  предоставляет.
