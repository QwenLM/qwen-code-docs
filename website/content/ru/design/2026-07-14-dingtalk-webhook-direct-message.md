# Дизайн доставки в личные чаты DingTalk через Webhook

## Статус

Реализовано и проверено на реальной цепочке личного чата. Соответствующий Issue:
[QwenLM/qwen-code#6883](https://github.com/QwenLM/qwen-code/issues/6883).

## Предпосылки

Каналы, размещенные в демоне, могут принимать прошедшие аутентификацию внешние события Webhook, запускать агента в виде задачи без присмотра и проактивно доставлять итоговый результат в заранее настроенные цели чата. В настоящее время DingTalk поддерживает доставку только в групповые чаты: цель должна иметь `isGroup: true`, и адаптер отправляет Markdown через API групповых сообщений.

Из-за этого источники Webhook, такие как CI-системы и мониторинговые алерты, не могут напрямую уведомить конкретного ответственного пользователя DingTalk и могут доставлять только в групповой чат.

## Цели

- Доставлять результаты задач Webhook демона в личные чаты DingTalk.
- Сохранить неизменным существующее поведение доставки Webhook в групповые чаты DingTalk.
- Сохранить прием только групповых целей DingTalk для обычной проактивной доставки и channel loop, не принимая идентификатор беседы входящего личного чата за идентификатор пользователя.
- Переиспользовать существующие структуру конфигурации целей, кеш токенов, форматирование Markdown, фрагментацию сообщений, повторы и обработку ошибок доставки.
- Использовать существующий канал DingTalk, не добавляя новых каналов или полей конфигурации.

## Не цели

- Нативные карточки DingTalk или колбэки карточек.
- Потоковые обновления карточек, кнопки, обратная связь или отмена задач из DingTalk.
- Несколько получателей в одной цели.
- Доставка в темы DingTalk.
- Новые типы каналов или изменения протокола Webhook демона.

## Конфигурация целей

Новые поля конфигурации не требуются. Существующие поля целей Webhook имеют следующие значения в канале DingTalk:

| `isGroup` | Значение `chatId`                 | API доставки                    |
| --------- | --------------------------------- | ------------------------------- |
| `true`    | `openConversationId` группы DingTalk | `robot/groupMessages/send`   |
| `false`   | Идентификатор пользователя DingTalk  | `robot/oToMessages/batchSend` |

`senderId` по-прежнему является виртуальной идентификацией, используемой для маршрутизации задач Webhook в сессии агента, а не идентификатором получателя DingTalk.

Пример конфигурации:

```json
{
  "webhooks": {
    "sources": {
      "github-ci": {
        "secretEnv": "QWEN_CHANNEL_GITHUB_CI_SECRET",
        "targets": {
          "operator": {
            "chatId": "DINGTALK_USER_ID",
            "senderId": "webhook:github-ci",
            "isGroup": false
          },
          "team": {
            "chatId": "OPEN_CONVERSATION_ID",
            "senderId": "webhook:github-ci",
            "isGroup": true
          }
        }
      }
    }
  }
}
```

Цель должна явно задавать `isGroup`. Адаптер по-прежнему отклоняет следующие цели: с пустым `chatId`, с заданным `threadId`, без `isGroup` или использующие URL вебхука вместо стабильного идентификатора цели.

## Цепочка доставки

Маршруты демона и IPC воркеров не меняются; общая среда выполнения каналов добавляет только проверку целей, специфичную для Webhook:

```text
POST /channels/:channelName/webhooks/:source
  -> демон аутентифицирует и валидирует событие
  -> воркер канала запускает задачу агента без присмотра
  -> ChannelBase вызывает DingtalkChannel.pushProactive()
  -> адаптер выбирает API DingTalk по target.isGroup
  -> DingTalk получает Markdown
```

Общая среда выполнения каналов использует отдельную проверку возможностей целей Webhook. Реализация по умолчанию по-прежнему использует правила целей обычной проактивной доставки; DingTalk лишь дополнительно принимает `isGroup: false` при разрешении задач Webhook. Поэтому обычный channel loop продолжает отклонять цели личных чатов, не принимая `conversationId` входящего личного чата за идентификатор пользователя, требуемый API сообщений один-на-один.

Цели групповых чатов продолжают использовать существующее тело запроса:

```json
{
  "robotCode": "CLIENT_ID",
  "openConversationId": "OPEN_CONVERSATION_ID",
  "msgKey": "sampleMarkdown",
  "msgParam": "{...}"
}
```

Цели личных чатов отправляют тот же шаблон Markdown через API сообщений один-на-один:

```json
{
  "robotCode": "CLIENT_ID",
  "userIds": ["DINGTALK_USER_ID"],
  "msgKey": "sampleMarkdown",
  "msgParam": "{...}"
}
```

Оба пути совместно используют существующий кеш access-токенов с обновлением за минуту до истечения токена; при HTTP 401 выполняется одна повторная попытка; при этом используются одни и те же нормализация Markdown и лимиты фрагментации. Доставка из нескольких фрагментов останавливается после сбоя первого фрагмента.

## Обработка ошибок

- Невалидные цели не проходят валидацию задачи Webhook до запуска агента.
- Сбой получения токена по-прежнему трактуется как сбой доставки и логируется без раскрытия учетных данных.
- HTTP 401 очирует кешированный токен и выполняет одну повторную попытку для текущего фрагмента.
- Другие неуспешные HTTP-ответы прерывают доставку и выводят маскированные детали ошибки API в лог воркера канала.
- Ответ демона `202 {"accepted": true}` по-прежнему означает лишь то, что воркер принял задачу, а не успешность доставки в DingTalk.

В скоупе этого релиза поддерживается только Markdown, поэтому стратегия деградации Markdown не требуется.

## Тесты

### Юнит-тесты

- Webhook принимает явно настроенные цели групповых и личных чатов; обычная проактивная доставка по-прежнему принимает только цели групповых чатов.
- Отклоняются цели без `isGroup`, с пустым идентификатором, использующие URL вебхука и с заданным `threadId`.
- Существующий эндпоинт группового чата и тело запроса с `openConversationId` сохраняются неизменными.
- Личный чат использует эндпоинт сообщений один-на-один и тело запроса с `userIds`.
- Отправка в групповой и личный чаты совместно использует кешированный токен.
- После HTTP 401 токен обновляется, и выполняется только одна повторная попытка.
- Доставка в личный чат также следует правилам фрагментации сообщений и прерывания после первого сбоя.

### Локальная сквозная верификация

Составить план тестирования в `.qwen/e2e-tests/`, сначала используя глобально установленный `qwen` CLI, и задокументировать базовое поведение, при котором цели Webhook личных чатов сейчас отклоняются. После завершения реализации:

1. Настроить по одной цели личного чата и группового чата.
2. Включить канал DingTalk и запустить `qwen serve`.
3. Отправить `curl` по одному событию на каждый из двух `targetRef`.
4. Подтвердить, что оба запроса возвращают `202`.
5. Подтвердить, что воркер канала завершил обе задачи.
6. Подтвердить, что целевой пользователь DingTalk и групповой чат получили ожидаемые сообщения Markdown.

Если локально нет доступных учетных данных DingTalk или целей-получателей, использовать юнит-тесты как автоматизированную верификацию доставки и явно указать недостающие шаги онлайн-верификации.

## Документация

Обновить документацию по Webhook каналов, показав оба варианта конфигурации целей DingTalk — личный чат и групповой чат, — и указать, что в `chatId` цели личного чата указывается идентификатор пользователя DingTalk.

## Совместимость

Это инкрементальное изменение. Конфигурация, валидация, эндпоинты, тела запросов, форматирование и поведение повторов для существующих целей групповых чатов не меняются, миграция конфигурации не требуется. Добавленная в общую среду выполнения проверка целей Webhook по умолчанию делегирует исходной проверке целей проактивной доставки, поэтому поведение других каналов не меняется.
