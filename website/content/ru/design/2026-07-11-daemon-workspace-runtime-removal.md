# Удаление среды выполнения рабочего пространства демона

## Контекст

Регистрация рабочих пространств в среде выполнения и персистентная регистрация уже доступны, но забывание персистентной регистрации не выгружает живой бридж, ACP-монтирование, состояние допуска сессий или дорожку памяти. Этот дизайн добавляет синхронное горячее удаление для вторичных сред выполнения, сохраняя существующий API забывания регистраций.

## Скоуп и инварианты

- Удаляемыми являются только динамически зарегистрированные и восстановленные из персистентности вторичные среды выполнения. Первичная среда выполнения и все среды выполнения `--workspace` статичны.
- `DELETE /workspaces/:workspace` удаляет среду выполнения и все известные персистентные алиасы. Оно никогда не удаляет файлы рабочего пространства, настройки, транскрипты, архивы или другие данные проекта.
- Удаление без принуждения носит наблюдательный характер: если замороженная среда выполнения имеет активность, все гейты откатываются, и запрос возвращает `409 workspace_busy`. Удаление с принуждением завершает эту активность.
- Персистентность фиксируется до деструктивной очистки. Сбой хранилища восстанавливает активную среду выполнения. Сбои очистки после фиксации хранилища не могут откатить операцию и используют синхронное принудительное завершение бриджа как фолбэк.
- Удаленный cwd остается зарезервированным до завершения очистки, после чего может быть зарегистрирован снова со свежими бриджем, ACP-диспетчером, реестром соединений и дорожкой памяти.

## Протокол

Продакшен-демоны анонсируют `workspace_runtime_removal`, когда установлен контроллер удаления. Строки рабочих пространств в возможностях (capabilities) получают опциональное поле `removable`; старые клиенты и демоны остаются совместимыми.

`DELETE /workspaces/:workspace` использует существующий селектор по идентификатору рабочего пространства или каноническому cwd и принимает опциональное JSON-тело с булевым `force`. При успехе возвращаются удаленная идентификация, был ли запрошен режим принуждения, был ли удален какой-либо персистентный алиас, и финальный снимок активности после дренирования. Запрос без принуждения, который уже наблюдаемо занят, может вернуть более ранний снимок до дренирования без кратковременного гейтования среды выполнения. Существующий `DELETE /workspace-registrations/:id` остается только забыванием.

## Жизненный цикл

Реестр отслеживает активные, дренируемые и удаленные среды выполнения. Публичное разрешение видит только активные среды выполнения; управленческое разрешение сохраняет дренируемые среды выполнения для отчетности о конфликтах и резервирования cwd.

Удаление сначала делает быстрый снимок активности. Затем синхронно помечает реестр как дренируемый, закрывает допуск сессий для данного рабочего пространства и дренирует ACP-монтирование и дорожку памяти. Финальный снимок читает ожидающие резервирования сессий до подсчета живых бриджей, чтобы переход резервирования в сессию не мог выглядеть как отсутствие активности. Занятый запрос без принуждения откатывает гейты. В противном случае все известные идентификаторы регистраций удаляются атомарно, поставленная в очередь работа с памятью завершается ошибкой, средство запуска суб-сессий и бридж останавливаются, ACP-монтирование освобождается, индексы владения очищаются, и запись реестра завершается.

Очистка среды выполнения мемоизируется по идентификации среды выполнения, а не по cwd, чтобы более поздняя среда выполнения, зарегистрированная по тому же пути, не могла переиспользовать старое обещание очистки. Завершение работы демона запечатывает управленческие операции, ждет их сходимости, останавливает средства запуска и затем использует тот же путь завершения бриджа для оставшихся управляемых сред выполнения.

## Идентификация персистентности

Восстановление записывает идентификатор каждого исходного сохраненного пути до канонизации. Несколько исходных алиасов, разрешающихся в одну среду выполнения, сохраняются как один набор идентификаторов, включая алиасы, затененные явно заданным рабочим пространством запуска. Удаление удаляет этот набор вместе с каноническим идентификатором регистрации под одной блокировкой хранилища без изменения схемы.

## UI

Web Shell предоставляет удаление только при наличии как тега возможности, так и `removable: true`. Действие остается доступным для недоверенных рабочих пространств. Первое подтверждение выполняет запрос без принуждения; `workspace_busy` отображает счетчики активности и предлагает удаление с принуждением. Принуждение отключено, когда текущая сессия принадлежит целевому рабочему пространству. При успехе согласуются возможности и списки сессий, при необходимости выполняется откат к первичному рабочему пространству.

## Анализ сбоев и совместимости

Отключения клиентов и таймауты SDK не отменяют очистку на стороне сервера. Параллельные операции добавления, повышения персистентности и удаления сериализуются по каноническому cwd. Завершение работы отклоняет новые управленческие операции с `daemon_shutting_down` и ждет уже начатую работу. Старые клиенты игнорируют опциональные поля возможностей и саму возможность; старые демоны продолжают генерировать обычный `DaemonHttpError` для отсутствующего маршрута.

Группа воркеров каналов с областью действия рабочего пространства предоставляет активность и завершение через тонкий адаптер. Дренирование блокирует перезагрузку и маршрутизацию вебхуков для целевого рабочего пространства; зафиксированное удаление останавливает и дерегистрирует только этот воркер, чтобы статус демона и метаданные pidfile сошлись без влияния на другие рабочие пространства.

## Верификация

Юнит-покрытие нацелено на переходы состояний реестра и очистку владельца, откат дренирования допуска, пакетное удаление алиасов, поведение маршрутов при занятости/принуждении/сбое хранилища, идемпотентность причины завершения бриджа, отмену дорожки памяти, кодирование запросов SDK, а также гейты возможности и принуждения в Web Shell. План E2E находится в `.qwen/e2e-tests/workspace-runtime-removal.md`.
