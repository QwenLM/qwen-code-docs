# Адаптеры каналов код-хостинга — дизайн

## Обзор

Адаптер опроса GitHub позволяет AI-агентам мониторить GitHub на предмет задач, опрашивая notifications API и публикуя ответы агента как комментарии к issue/PR. В отличие от IM-адаптеров (webhook'и/long-poll в реальном времени), этот адаптер опрашивает по интервалу.

## Архитектура: уведомление как сигнал пробуждения

Ключевая идея: уведомления платформы имеют **уровень треда** и **мутируемы** — любая активность (комментарий, пуш, смена лейбла) поднимает `updated_at`. Уведомления нельзя использовать как надежный поток событий по каждому комментарию.

Вместо этого уведомления служат только **сигналом пробуждения** («что-то произошло в этом треде»). Адаптер затем перечисляет фактические комментарии через comments API платформы, используя watermark для каждого треда, чтобы определить, какие комментарии новые.

## GitHub: окно комментариев на основе курсора

### Рассогласование таймстампов уведомления/комментария

Критичная проблема тайминга: **`updated_at` уведомления и `updated_at` комментария рассогласованы**.

- `notification.updated_at` поднимается _любой_ активностью треда (комментарий, пуш, смена лейбла) и подвержен задержкам доставки
- `comment.updated_at` отражает, когда комментарий был фактически создан/отредактирован

Между этими таймстампами нет причинно-следственной связи. Уведомление может прибыть через 16 секунд после комментария, который его вызвал, и может быть снова поднято несвязанной активностью. Использование таймстампов уведомления для гейтинга перечисления комментариев поэтому дает два режима сбоев:

1. **Дублирующие ответы** — `PUT /notifications` асинхронен (202 Accepted) с отсечкой `last_read_at`. Ответ бота поднимает `updated_at` выше отсечки до того, как сервер обработает пометку, поэтому уведомление никогда не помечается прочитанным. Следующий опрос выкачивает его заново и повторно обрабатывает те же комментарии.
2. **Пропущенные ответы** — курсор продвигается до `max(notification.updated_at)`, что может перескочить комментарии на поздно прибывающих уведомлениях. Когда эти уведомления наконец прибывают, их комментарии оказываются ниже окна курсора и молча исключаются.

### Дизайн

Корректность достигается **окном комментариев на основе курсора**, а не статусом прочтения уведомления:

Цикл опроса:

1. `GET /notifications?since={cursor-1s}` — обнаружить непрочитанные треды
2. Сохранить `windowSince = cursor.lastProcessedAt` (курсор **до** того, как этот опрос его продвинет)
3. `markNotificationsAsRead(maxUpdatedAt)` — глобальная пометка по мере возможности (best-effort) (очищает уведомления, не относящиеся к issue)
4. Продвинуть глобальный курсор до `max(notification.updated_at)`
5. По каждому треду: `listComments(since=windowSince)` — перечислить комментарии
6. Исключить: собственные комментарии бота; комментарии с `created_at > maxUpdatedAt` (выше окна); комментарии с `created_at <= windowSince` (ниже окна)
7. Обработать: детекция упоминания → Envelope → `handleInbound`

Эффективное окно комментариев — `(windowSince, maxUpdatedAt]`. Комментарии, обработанные в предыдущем опросе, имеют `created_at <= windowSince` (`maxUpdatedAt` предыдущего опроса) и исключаются. Это предотвращает дубли независимо от того, succeeded ли `PUT /notifications`. Редактирования комментариев не запускают повторную обработку — только `created_at` используется для членства в окне.

Глобальная пометка все равно вызывается (шаг 3), чтобы очистить уведомления не об issue/PR и уменьшить список непрочитанных, но она не является несущей для дедупликации.

### Известное ограничение: поздняя доставка уведомлений

Поскольку курсор глобальный (а не по треду), уведомление, прибывающее в более позднем опросе, чем `created_at` его комментариев, может получить эти комментарии исключенными окном курсора. Это требует, чтобы доставка уведомления задержалась через границу опроса И чтобы комментарии другого треда тем временем продвинули курсор мимо них. На практике это окно узкое (доставка уведомлений обычно завершается в пределах одного интервала опроса); пользователь может упомянуть повторно, чтобы повторить.

### Известное ограничение: комментарии ревью PR

`issues.listComments` возвращает только комментарии общего обсуждения, а не комментарии ревью PR (покомментарные комментарии к diff). @-упоминание в комментарии ревью PR молча отбрасывается. Вместо этого используйте комментарий общего обсуждения на PR.

### Поведение по сценариям

| Сценарий                          | Поведение                                                                                                                     |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Новый тред (@bot в комментарии)   | Появляется (непрочитанный) → перечисление с курсора → обработка                                                               |
| Существующий тред, новый комментарий | Появляется снова (непрочитанный) → перечисление с курсора → старые комментарии исключены `<= windowSince` → только новые  |
| Активность без комментариев (push/label) | Появляется → ноль новых комментариев в окне → пропуск                                                               |
| Пользователь помечает прочитанным на github.com | Исчезает из API → не обрабатывается                                                                              |
| Сбой markNotificationsAsRead      | Окно курсора все равно предотвращает дубли → без влияния на корректность                                                      |
| Краш после markRead, до завершения | Курсор не сохранен → следующий старт выкачивает те же уведомления → сбойный батч обрабатывается повторно, не теряется        |
| Бот отвечает в тред               | `updated_at` поднят → уведомление может остаться непрочитанным → следующий опрос выкачивает его → комментарии исключены окном курсора → нет дубля |
| Новый issue с @bot в теле         | Нет комментариев → тело содержит упоминание → подать тело как триггер (дедупликация через `dispatchedBodies`)                |

## PollingChannelBase

`PollingChannelBase<Cursor>` (в `packages/channels/base/`) расширяет `ChannelBase` и предоставляет инфраструктуру цикла опроса:

- **Цикл опроса**: старт/стоп через `startPollLoop()`/`stopPollLoop()`, вызываемые из `connect()`/`disconnect()`
- **Интервал опроса**: читается из конфигурации канала `pollInterval` (мс), валидируется как положительное конечное число, по умолчанию 60000
- **Персистентность курсора**: JSON-курсор сохраняется атомарно после каждого успешного `pollOnce()`; загружается при конструировании (поврежденная или неразбираемая дата → фолбэк на `createInitialCursor()`)
- **Валидация курсора**: виртуальный хук `validateCursor()` — база отклоняет не-объекты и массивы; подклассы добавляют проверки формы (например, GitHub отклоняет отсутствующую/невалидную дату `lastProcessedAt`)
- **Backoff**: экспоненциальный 2с → 30с при ошибках опроса, сброс при успехе
- **Прерываемый sleep**: `abortableSleep(ms)` выставляется как protected-метод — интервал опроса и backoff ошибок прерываемы через `disconnect()`

Подклассы реализуют только:

- `pollOnce()` — выполнить работу, мутировать `this.cursor`
- `createInitialCursor()` — дефолтное значение первого запуска

Дженерик `Cursor` — любой JSON-сериализуемый объект. GitHub использует `{ lastProcessedAt: string; dispatchedBodies?: string[] }` (последнее ограничивает дедупликацию тел первых контактов последними 500 записями).

## Детекция упоминаний

Основанная на теле, нечувствительная к регистру регулярка. Отдельные функции для детекции (`testBotMention`) и вырезания (`stripBotMention`):

- Детекция: явное совпадение регулярки, возвращающее boolean — никогда не выводится из сравнения до/после вырезания (различия в пробелах вызывают ложные срабатывания)
- Вырезание: удаляет только `@bot`, сохраняя все остальное форматирование (без схлопывания пробелов)

## Область сессии

Адаптеры опроса используют scope `chat_thread`: ключ маршрутизации = `channel:chatId:threadId`. Это предотвращает коллизии сессий между репозиториями (`repo-a/issue:42` против `repo-b/issue:42`).

## Обработка ошибок

Доставка — **по мере возможности (best-effort)**. При сбое `handleInbound` публикуется один комментарий об ошибке на тред за цикл опроса (затем `break` выходит из цикла комментариев — предотвращает N одинаковых комментариев об ошибке); пользователь упоминает повторно, чтобы повторить. Ошибки API по каждому уведомлению используют `continue` — одно сбойное уведомление не блокирует остальной батч. Уведомления без `subject.url` (типы Discussion, SecurityAlert) пропускаются молча.

Если процесс падает посреди обработки, курсор не сохраняется (он персистится только после завершения `pollOnce()`), поэтому следующий старт выкачивает те же уведомления — но окно комментариев на основе курсора исключает уже обработанные комментарии, предотвращая дубли.

Предотвращение дублей **не** зависит от успеха `PUT /notifications`. Глобальная пометка — это best-effort очистка; окно курсора — несущий механизм дедупликации.
