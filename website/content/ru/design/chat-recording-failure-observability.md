# Наблюдаемость сбоев записи чата

## Контекст

`ChatRecordingService` навсегда перестает принимать записи после первого асинхронного сбоя записи JSONL. Транскрипт остается валидным префиксом, но без отдельного сигнала пользователи и удаленные клиенты могут ошибочно полагать, что более поздние сообщения все еще записываются.

## Основной жизненный цикл

`Config.onChatRecordingFailure()` — это локальная для процесса граница подписки. Каждый записыватель, созданный `Config`, перенаправляет свой первый асинхронный сбой записи снимку зарегистрированных слушателей. Событие несет ID сессии сбойной записи и нормализованную `Error`; сбои слушателей изолированы от промиса писателя. Подписки переживают замену записывателя и удаляются независимо своими диспозерами. `Config.shutdown()` сохраняет слушателей живыми через финализацию и flush записывателя, затем очищает их.

Синхронные сбои создания файла разговора не выпускают событие, потому что записыватель не вошел в свое постоянное сбойное состояние и более поздний вызов может повторить. Сбойный записыватель выпускает событие один раз; пропущенные потомки, более поздние дописки и повторные flush'и не выпускают его снова.

## Поверхности локального CLI

TUI и текстовый вывод рендерят общее предупреждение, по которому можно действовать, без путей файловой системы, значений errno или нижележащей ошибки. JSON, stream-json и двойной вывод выпускают сообщение `system/session_recording_degraded`, чьи верхнеуровневый и payload ID сессии оба берутся из события сбоя, а не из текущей сессии `Config`.

Одноразовый структурированный вывод финализирует записыватель и ждет до двух секунд его flush перед выпуском терминального результата. Долгоживущие сессии stream-json подписываются один раз, делают flush между ходами без финализации и финализируются только при завершении сессии. Таймаут сохраняет отзывчивость и не отменяет нижележащую запись.

## Протокол демона и долговечное живое состояние

Дочерний процесс ACP отправляет `qwen/notify/session/recording-degraded` с версией протокола 1, ID затронутой сессии и `reason: "write_failed"`. Бридж валидирует полезную нагрузку, публикует `session_recording_degraded` и помечает живую запись сессии как degraded. Уведомления, прибывающие до регистрации записи, используют существующий ограниченный буфер ранних событий; дренирование буфера обновляет и кольцо воспроизведения, и состояние записи.

`session_snapshot.recordingDegraded` сохраняет состояние после того, как живое событие покидает кольцо воспроизведения. Это состояние только в памяти демона: перезапуск демона создает новый записыватель и начинает в здоровом состоянии. Событие аддитивно при `EVENT_SCHEMA_VERSION = 1`; изменения capability не требуется.

## SDK и WebUI

SDK валидирует живое событие и опциональное поле снимка. Редьюсер сессий трактует живое событие как безопасное для ресинка прилипающее обновление. Присутствующее поле снимка авторитетно, тогда как отсутствующее поле сохраняет состояние для совместимости со старыми демонами.

Нормализатор UI мапит любое представление degraded в одну и ту же восстановимую ошибку записи. WebUI использует явный ID уведомления `daemon.session_recording_degraded:<sessionId>`, чтобы воспроизведенное событие, за которым следует снимок, было идемпотентным. Закрытие уведомления удаляет текущий экземпляр; более поздний снимок может снова показать все еще активный риск.

## Граница закрытия

Строгие пути закрытия, требующие успешного flush, сохраняют запись демона живой, когда flush не удается, так что событие остается доставляемым. Существующий порядок закрытия по мере возможности (best-effort) не меняется: если его EventBus уже закрыт, когда обнаружен поздний сбой, только debug-лог сохраняет этот сбой.

## Не-цели

Этот дизайн не повторяет записи, не восстанавливает degraded-записыватель, не меняет содержимое JSONL или родительские ссылки, не добавляет fsync, не выставляет сырые ошибки файловой системы и не координирует конкурирующих писателей между процессами.
