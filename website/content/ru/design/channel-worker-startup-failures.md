# Отчет о сбоях запуска воркера каналов

## Контекст

[Issue #6909](https://github.com/QwenLM/qwen-code/issues/6909) выявляет диагностический пробел в каналах, управляемых демоном. Отклонение `connect()` адаптера логируется воркером, но затем воркер сообщает только ready или завершается с `No channels connected.` Супервизор, API динамического управления, SDK и CLI поэтому теряют ошибку провайдера, по которой можно действовать.

Это изменение проносит ограниченные, санитизированные сбои `connect()` через границу запуска воркера. Оно не меняет разбор конфигурации, загрузку расширений, конструирование адаптеров, поведение fail-fast при загрузке демона или историю сбоев после старта.

## Поведение

- Если хотя бы один выбранный адаптер подключается, воркер становится ready. Его текущий снимок содержит имена и причины сбойных каналов, и динамическое включение все равно возвращает успех с `partial: true`.
- Если каждый адаптер падает во время динамического включения, замены или перезагрузки, запрос возвращает `502 channel_worker_start_failed` с попытками сбоев. `state` описывает текущее состояние после отката; попытки сбоев не персистятся в это состояние.
- Если каждый адаптер падает при загрузке демона, запуск остается fail-fast. Поскольку слушатель демона не остается доступным, более поздний GET не обещается.
- Новое поколение воркера очищает сбои запуска предшествующего поколения.

Только отклонения `connect()` создают эти записи. `phase` сейчас — `connect`; SDK намеренно расширяет его до `string`, чтобы будущая добавочная фаза не потребовала ломающего изменения типа. Значения `code` адаптера диагностические и не являются стабильной кросс-адаптерной таксономией.

## Контракт

Текущий снимок воркера может содержать:

```ts
interface ChannelStartupFailure {
  channel: string;
  phase: 'connect';
  code?: string;
  message: string;
}

interface ChannelWorkerSnapshot {
  startupFailures?: ChannelStartupFailure[];
  startupFailuresTruncated?: boolean;
}
```

Сбой динамического старта может дополнительно содержать сбои, аннотированные доверенным рабочим пространством супервизора:

```ts
interface ChannelStartupAttemptFailure extends ChannelStartupFailure {
  workspaceCwd: string;
}
```

Существующие верхнеуровневая строка ошибки, поля отката и state остаются совместимыми. Все новые поля опциональны.

## IPC и жизненный цикл

Дочерний процесс отправляет по одному сообщению `channel_startup_failure` из каждого catch `connect()` и ждет `channel_startup_report_ack` перед попыткой следующего адаптера. Родитель валидирует, санитизирует, сохраняет и только затем подтверждает элемент. Колбэк отправки — не граница долговечности: он доказывает только, что Node принял сообщение, тогда как ACK доказывает, что супервизор обработал его до того, как воркер сможет синхронно завершиться.

Передается максимум 64 сбоя. Сбой 65 создает один маркер `channel_startup_failures_truncated`, который также подтверждается; более поздние сбои остаются только в stderr. Одновременно незавершенным может быть только один отчет, поэтому ACK не нужен идентификатор запроса.

Некорректные, слишком длинные, внеочередные или не подлежащие подтверждению сообщения протокола запуска валят ограниченный запуск и завершают дочерний процесс. Несвязанные неизвестные IPC-сообщения сохраняют свое существующее поведение. Существующие схема ready и валидация намеренно не меняются.

Каждый терминальный путь до ready оборачивает уже принятые сбои в `ChannelWorkerStartupError`. Ошибки reconcile и менеджера клонируют эти детали, сохраняя проблемы очистки или восстановления отдельно как `rollbackError`. Рабочее пространство добавляется из конфигурации супервизора, никогда из IPC дочернего процесса.

## Безопасность и лимиты

Воркер и супервизор оба нормализуют управляющие и невидимые символы, точно редактируют (redact) токен демона и чувствительные значения окружения, применяют общие правила для учетных данных и обрезают по Unicode code points. HTTP-ответ динамического сбоя и границы отображения CLI валидируют снова, применяют общее редактирование, ограничивают вывод и игнорируют некорректные записи.

Лимиты: 64 сбоя, 128 code points для channel, 64 для code и 512 для message. Объекты сбоев и снимки клонируются на границах владения, чтобы вызывающие не могли мутировать состояние супервизора.

## Отклоненные альтернативы

- Чтение stderr в супервизоре неоднозначно, связывает поведение с текстом логов и не может обеспечить надежную атрибуцию каналов.
- Ожидание только колбэка `process.send()` все равно гоняется с синхронным завершением воркера.
- Персистирование последней неудачной попытки изменило бы семантику жизненного цикла и пересекается с отдельной работой по последней ошибке/истории; динамические сбои вместо этого живут только в сбойном ответе.
- Изобретение категорий auth/network/config создало бы нестабильную таксономию между адаптерами. Реализация сохраняет только предоставленную адаптером строку или конечный числовой код.

## Верификация

Юнит-покрытие прогоняет порядок ACK, полный/частичный сбой, пути прерывания и таймаута, некорректный ввод протокола, сбой ACK, безопасный доступ к исключениям, точное и общее редактирование, глубокие копии, сброс поколений, усечение 64/65, распространение отката, HTTP-валидацию, экспорты SDK и форматирование CLI. Реальный интеграционный тест plugin-example использует локально выделенный, а затем закрытый порт, чтобы получить детерминированный `ECONNREFUSED` без внешних учетных данных или сетевых зависимостей.
