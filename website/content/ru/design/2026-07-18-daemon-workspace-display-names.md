# Отображаемые имена рабочих пространств демона

## Цель

Позволить клиентам демона и TypeScript SDK прикреплять опциональное
человекочитаемое отображаемое имя к зарегистрированному рабочему пространству,
не меняя идентичность или маршрутизацию рабочего пространства. Позволить
пользователям Web Shell задавать это имя при добавлении рабочего пространства
и видеть его в списке рабочих пространств. Позволить клиентам API обновлять или
очищать презентационные метаданные активного рабочего пространства.

## Контракт

- Записи `workspaces[]` получают опциональные метаданные `displayName`.
- `POST /workspaces` принимает опциональный `displayName` при регистрации или
  постоянном повышении вторичного рабочего пространства.
- `PATCH /workspaces/:workspace` — endpoint обновления рабочего пространства.
  Текущая форма запроса — `{ displayName: string | null }`; `null` очищает имя.
- `POST /workspaces`, `PATCH /workspaces/:workspace` и списки постоянной
  регистрации возвращают эффективное отображаемое имя, если оно существует.
- `workspace_display_name` анонсирует контракт. TypeScript SDK предоставляет
  опцию регистрации и `updateWorkspace()`.
- Когда возможность анонсирована, диалог добавления рабочего пространства Web
  Shell принимает опциональное отображаемое имя и использует его для меток
  рабочего пространства.

`id` и `cwd` остаются единственными селекторами рабочего пространства.
Отображаемое имя никогда не используется для поиска и не обязано быть
уникальным.

## Рантайм и персистентность

Рантайм владеет эффективным отображаемым именем. Обновление любого активного
рабочего пространства изменяет метаданные этого рантайма. Когда у рантайма есть
совпадающие идентификаторы постоянной регистрации, то же обновление атомарно
записывается во все из них; в противном случае обновление остается локальным для
процесса. Локальные для процесса рабочие пространства теряют и рантайм, и его
имя при остановке демона и никогда не зависят от хранилища регистраций при
обновлении отображаемого имени.

Существующий файл регистрации schema-v1 сохраняет форму `workspaces: string[]`
и добавляет опциональный объект `displayNames` с ключами по существующему
стабильному id регистрации. Обновления переиспользуют существующую блокировку
хранилища, перечитывание под блокировкой и атомарную запись. Старые демоны
игнорируют аддитивное поле, а новые демоны продолжают читать файлы, которые его
не содержат. Удаление регистрации также удаляет запись ее отображаемого имени.

## Валидация и сбои

Отображаемые имена рабочих пространств ограничены 256 символами после обрезки
окружающих пробельных символов. Внутренние управляющие символы C0 и DEL
отклоняются; пустой результат рассматривается как отсутствие имени. Некорректный
ввод возвращает `400 invalid_display_name` до начала работы с файловой системой
или рантаймом. Дублирующиеся отображаемые имена разрешены.

Когда локальное для процесса рабочее пространство впервые сохраняется, запись в
хранилище регистраций завершается до того, как сохраненное отображаемое имя
будет раскрыто в рантайме. Аналогично, PATCH обновляет совпадающие постоянные
записи до раскрытия нового значения в рантайме, поэтому обычный сбой хранилища
оставляет рантайм неизменным.

## Совместимость

Все проводные (wire) изменения аддитивны для протокола v1. Старые SDK игнорируют
`displayName`; новые SDK типизируют его как опциональный и продолжают работать со
старыми демонами, которые опускают и поле, и тег возможности. Web Shell скрывает
элементы управления отображаемым именем, когда тег возможности отсутствует.

## Верификация

- Тесты хранилища регистраций покрывают legacy-файлы, начальные имена,
  валидацию, атомарные обновления алиасов, восстановление после перезапуска и
  очистку при удалении.
- Тесты управления рабочими пространствами покрывают создание локальных для
  процесса и постоянных, обновление/очистку, ошибки персистентности и
  идемпотентное повышение.
- Тесты возможностей/статуса и SDK покрывают аддитивное поле, формы запросов,
  `updateWorkspace()` и анонсирование `workspace_display_name`.
- Тесты Web Shell покрывают опциональный ввод, проброс опции SDK и фолбэк
  метки. Скриншоты браузера проверяют реальную форму добавления рабочего
  пространства и итоговую метку в сайдбаре.
- Ручная end-to-end проверка покрывает регистрацию локальных для процесса
  рабочих пространств и восстановление постоянных после перезапуска.
