# Чтение текстовых диапазонов, привязанных к дескриптору

## Контекст

PR #7947 позволил файловой системе рабочего пространства Serve возвращать
ограниченные окна строк из текстовых файлов больше `MAX_READ_BYTES` (256 КиБ).
Чтобы эти чтения оставались привязанными к одной inode на протяжении валидации,
бинарного пробинга и стриминга, он пронес принадлежащий вызывающей стороне
`FileHandle` вниз в `readTextRange` как опциональное поле и добавил второе
опциональное поле `forceStreaming` для подавления быстрого пути с
буферизацией, который иначе сводил бы на нет ограничение памяти.

Два опциональных поля на одной точке входа давали четыре комбинации, из
которых одна осмысленна, одна недостижима и одна небезопасна:

| `fileHandle` | `forceStreaming` | Результат                                                               |
| ------------ | ---------------- | ----------------------------------------------------------------------- |
| не задано    | не задано        | обычное чтение по пути                                                   |
| не задано    | задано           | стримит маленький файл — используется одним тестом                       |
| задано       | задано           | чтение границы Serve                                                     |
| задано       | не задано        | буферизует весь файл через дескриптор — **ни один вызывающий не достигает** |

Недостижимая комбинация имела отдельный хелпер `readFileHandleBuffer` без
покрытия тестами. Отдельно `readFileWithLineAndLimit` принимал тот же
`fileHandle`, но мог уважить его только в своей ветке диапазона: неограниченное
чтение проваливалось в `readFileWithEncodingInfo` по пути, молча возвращая
байты из того, во что путь разрешался в этот момент, а не из привязанной
inode. Follow-up коммит PR #7947 защитил это рантайм-`RangeError`, который
задокументировал ловушку, не убирая ее.

Детекция кодировки раздвоилась по той же причине. `detectFileEncoding`
принимает путь и открывает собственный дескриптор, поэтому путь дескриптора не
мог его использовать; рядом был добавлен приватный `detectFileHandleEncoding`,
выводящий имя кодировки из `decodeBufferWithEncodingInfoAsync(...).encoding`
вместо chardet напрямую. Оба расходятся, когда chardet называет кодировку,
которую `iconv-lite` не может загрузить: вариант по пути возвращает это имя,
вариант по дескриптору возвращает `'utf-8'` и полагается на сбой стримингового
декодера с `fatal: true`. Оба отказывают файлу, с разными сообщениями.

## Цели

- Один детектор кодировки, пригодный и для пути, и для заимствованного
  дескриптора.
- Без флагов режима на читателе диапазона; сделать недостижимую комбинацию
  непредставимой, а не просто неиспользуемой.
- Сделать проваливание по пути структурно невозможным вместо охраняемого.
- Никаких наблюдаемых изменений на границе Serve или в инструменте `read_file`.

## Не цели

- Слияние `decodeBufferWithEncodingInfo` (синхронной) с ее асинхронным
  близнецом. Синхронный вариант — намеренный шим совместимости публичного API
  ([`lazy-first-use-dependencies.md`](./lazy-first-use-dependencies.md)),
  зафиксированный parity-тестом.
- Любые изменения того, что возвращает граница Serve. Это подготовка к
  пагинации по байтовому курсору, а не сама функция.

## Дизайн

### Один детектор

`detectFileEncoding(source: string | FileHandle)`. Предоставленный дескриптор
_заимствуется_: чтения используют явные позиции, поэтому позиция файла
вызывающей стороны не трогается, а блок `finally` закрывает только дескриптор,
открытый самой этой функцией. `detectFileHandleEncoding` удаляется, а
закодированный вручную switch BOM-в-имя заменяется существующим
`bomEncodingToName`.

Это делает путь дескриптора чуть строже, что и есть намеченное направление:
кодировка, которую `iconv-lite` не может загрузить, теперь поднимает
`LargeNonUtf8TextError(detected)` с именем этой кодировки вместо достижения
декодера и поднятия общего варианта `'invalid-utf8'`. Отказ не меняется;
сообщение улучшается. Граница Serve отображает оба в `binary_file`, поэтому
нижнее по течению ничего не сдвигается.

Вторая, меньшая дельта приходит со слиянием: `detectFileEncoding` ловит все
ошибки и откатывается на `'utf-8'`, тогда как у `detectFileHandleEncoding` не
было обработчика, и сбой I/O распространялся. Сбой не теряется — дескриптор,
достаточно плохой, чтобы не пройти пробинг 8 КиБ, не пройдет и стриминговое
чтение сразу после, а файл, который на самом деле не UTF-8, по-прежнему
отклоняется декодером с `fatal: true` — поэтому ошибка всплывает из другого
вызова, а не исчезает. Принято ради единой политики фолбэка; отмечено,
поскольку это реальное изменение того, какой вызов сообщает о проблеме.

### Две точки входа

```ts
readTextRange(request: ReadTextRangeRequest)                    // path
readTextRangeFromHandle(fh, request: ReadTextRangeFromHandleRequest)
```

Вариант по дескриптору всегда стримит — флага нет, потому что вызывающий
тянется к дескриптору именно тогда, когда чтение должно быть ограниченным, а
быстрый путь с буферизацией прочитал бы весь файл. Его тип запроса не имеет
`path` (нечего дизамбигуировать), сохраняет числовой `fileSize`, захваченный
из открывающего `fstat`, и делает обе байтовые границы обязательными вместо
опциональных. `maxOutputBytes` ограничивает то, что чтение возвращает,
`maxScanBytes` ограничивает его стоимость, а `fileSize` предотвращает
расширение снимка дескриптора добавлением в конец, пока чтение in flight.
Привязанное к дескриптору чтение существует потому, что границе безопасности
нужны все три ограничения.

`maxScanBytes` остается опциональным в варианте по пути, где по умолчанию
равен `Infinity`, поэтому инструмент `read_file` не меняется.

Оба делегируют в одну и ту же стриминговую реализацию, которая теперь
принимает `source: string | FileHandle` и выбирает `createReadStream` или
`chunksFromHandle` соответственно. `readFileHandleBuffer` и ветка, которая
его вызывала, удаляются.

### Проваливание исчезает

`readFileWithLineAndLimit` теряет `fileHandle`, `forceStreaming` и
`maxScanBytes` — его единственный продакшен-вызывающий не передает ни одного
из них. `StandardFileSystemService.readTextFileFromHandle` теперь вызывает
`readTextRangeFromHandle` напрямую, и оба пути чтения разделяют хелпер
`toReadTextFileResponse`, чтобы их формирование метаданных не дрейфовало. Без
оставшегося параметра `fileHandle`, который можно игнорировать, гейт
`RangeError` удален: ловушка, которую он описывал, больше не может быть
выражена.

`readTextFileFromHandle` остается вне интерфейса `FileSystemService`, поэтому
`AcpFileSystemService` и типизированный фолбэк-mock в `filesystem.test.ts` не
тронуты.

## Радиус поражения

- `readTextRange` не экспортируется из `packages/core/src/index.ts`; три
  класса ошибок, обращенных к границе, экспортируются. Переформатированная
  поверхность читателя внутренняя для core.
- `readTextRange` и `readFileWithLineAndLimit` имеют ровно по одному
  продакшен-вызывающему каждый (`fileUtils.ts`, `fileSystemService.ts`).
- `detectFileEncoding` публична через `export * from './utils/fileUtils.js'`.
  Расширение параметра совместимо по исходникам.
- Единственный кросс-пакетный импортер затронутых модулей —
  `packages/cli/src/serve/fs/workspace-file-system.ts`. Его единственное
  изменение — выброс двух аргументов, которые путь дескриптора больше не
  принимает — см. ниже; импорт `decodeBufferWithEncodingInfoAsync`, который он
  также несет, не тронут.

### `CoreReadTextFileHandleRequest` становится самостоятельным

Он был `Omit<CoreReadTextFileRequest, 'limit' | 'stats' | 'maxOutputBytes'> &
{...}`, что оставляло два поля, которые путь дескриптора никогда не читает:

- **`stats`** был задокументирован как обязательный — «должен передавать
  Stats, захваченные из этого дескриптора», — и ничто ниже по течению не
  читало объект. Финальный API сохраняет только его числовой `fileSize`: пути
  дескриптора не нужны метаданные для выбора стратегии, но нужен открывающий
  размер, чтобы чтения оставались ограниченными, когда файл одновременно
  дополняется.
- **`path`** стал мертвым, когда `readTextRangeFromHandle` заменил вызов
  путь-плюс-дескриптор: чтение привязано к дескриптору, а ошибки помечаются
  путем границей Serve, которая им владеет.

Ни одно не было поймано компилятором. ACP `ReadTextFileRequest`, из которого
был выведен этот тип, допускает лишние свойства, поэтому передача поля,
удаленного из типа, ничего не поднимала. Это и есть аргумент за объявление
типа самостоятельным вместо вывода: цепочка `Omit` вырезала четыре из шести
унаследованных полей и молча допускала остальные обратно.

На коммите рефакторинга в `packages/core` изменено 282 строки продакшен-логики;
более поздний follow-up с курсором добавляет поведение и тесты поверх этой
базовой линии.

## Тестирование

На коммите рефакторинга существующие наборы тестов были спецификацией: весь
смысл был в том, что граница Serve не должна замечать разницы. Более поздний
follow-up с курсором добавляет поведение границы и собственные тесты.

Три теста из `read-text-range.test.ts` переехали на `readTextRangeFromHandle`.
Два использовали `fileHandle` напрямую. Третий использовал _путь_ с
`forceStreaming: true`, чтобы форсировать стриминг на файле слишком маленьком,
чтобы покинуть быстрый путь, и проверить границу бюджета на EOF; с исчезновением
флага вариант по дескриптору — единственное, что всегда стримит.

Один из переехавших тестов поменял смысл. Раньше он передавал дескриптор для
одного файла и путь, называющий другой файл, утверждая, что дескриптор
побеждает — тест на путаницу, которую допускала старая сигнатура. У варианта
по дескриптору нет `path`, поэтому та путаница теперь непредставима, и тест
ничего бы не утверждал. Он переписан на свойство, которое действительно
мотивировало API: открыть дескриптор, переименовать другой файл поверх пути и
подтвердить, что чтение по-прежнему следует за inode.

Два теста в `fileSystemService.test.ts` удалены вместо починки. Они мокали
`readFileWithLineAndLimit` и утверждали объект аргументов, который тот
получал; поскольку `readTextFileFromHandle` больше его не вызывает, их можно
было сохранить только переведя на новый mock, что снова утверждало бы лишь,
что одна функция передает аргументы другой. Поведение, которое они номинально
покрывали, протестировано на реальных файлах в `read-text-range.test.ts` и на
реальной границе в `workspace-file-system.test.ts`. Тесты валидации аргументов
рядом с ними сохранены — им не нужен mock.

## Follow-up

`chunksFromHandle` получил параметр `from` как единственный стык, который
нужен пагинации текста по байтовому курсору. Follow-up теперь использует его
для возобновления с ненулевого байтового смещения.
