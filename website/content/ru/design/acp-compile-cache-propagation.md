# Распространение compile-кэша ACP

## Контекст

Продакшен-обертка `cli-entry.js` уже включает compile-кэш модулей Node для быстрого пути `serve` внутри процесса. Позже демон порождает дочерний процесс ACP через `createSpawnChannelFactory()`, но `module.enableCompileCache()` влияет только на текущий процесс и не заполняет `NODE_COMPILE_CACHE`. Поэтому дочерний процесс ACP запускается без кэша, если только оператор не задал эту переменную окружения до запуска Qwen Code.

Это ортогональный кандидат по compile-кэшу, записанный в #7264. Он не сокращает eager-граф модулей; он повторно использует кэш кода V8 для графа, который остается после работы по ленивой загрузке.

## Цели

- Позволить продакшен-потомкам ACP повторно использовать каталог compile-кэша, уже включенный оберткой входа демона.
- Сохранять предоставленный оператором `NODE_COMPILE_CACHE`.
- Сохранять `NODE_DISABLE_COMPILE_CACHE=1`.
- Оставить сбои кэша тихой оптимизационной неудачей, а не сбоем приложения.
- Избежать изменений ACP-бриджа, конфигурации или жизненного цикла сессии.

## Не-цели

- Не вводить Qwen-специфичное расположение кэша, политику вытеснения или команду очистки.
- Не навязывать поддержку compile-кэша на версиях Node, где JavaScript API недоступен.
- Не сбрасывать кэш из демона или жизненного цикла ACP.
- Не менять окружения тестов или покрытия глобально.

## Топология запуска

Продакшен-путь демона:

1. `cli-entry.js serve`
2. `module.enableCompileCache()` в процессе демона
3. внутрипроцессный импорт собранного CLI
4. `createSpawnChannelFactory()` копирует `process.env`
5. новый процесс Node читает `NODE_COMPILE_CACHE` при старте
6. дочерний процесс выполняет выбранный вход CLI с `--acp` (по умолчанию `cli.js`, либо `QWEN_CLI_ENTRY`, если явно настроен)

Сегодня шаг 2 приносит пользу только демону. В окружении, скопированном на шаге 4, нет каталога compile-кэша, поэтому дочерний процесс на шагах 5 и 6 не подключается к кэшу.

## Предлагаемое изменение

Зафиксировать результат существующего вызова `module.enableCompileCache()`. Когда он сообщает о впервые включенном кэше, предоставляет каталог, и оператор не предоставил `NODE_COMPILE_CACHE`, опубликовать этот каталог в `process.env`. Существующее построение дочерних процессов уже копирует окружение, поэтому изменений на уровне ACP не требуется.

Не перезаписывать существующее значение окружения. Когда Node включил кэш из уже существовавшей переменной окружения, он сообщает о состоянии already-enabled, и исходный базовый каталог должен остаться нетронутым. Замена его на `getCompileCacheDir()` или результат already-enabled может создать вложенный каталог версий у потомков.

Не синтезировать каталог, когда включение не удалось, отключено или API недоступен. Эти случаи сохраняют текущее поведение.

## Рассмотренные альтернативы

### Установить переменную окружения в `spawnChannel`

Отклонено. Владение compile-кэшем — это глобальное для процесса поведение входа, тогда как `spawnChannel` — общая инфраструктура ACP, используемая встраиваемыми хостами. Перенос политики туда расширяет архитектурную поверхность и дублирует поведение bootstrap Node.

### Установить Qwen-версионируемый кэш в `QWEN_HOME`

Отклонено. Node уже разделяет несовместимые версии Node и ключирует записи содержимым модулей. Node рекомендует свой вариант с временным каталогом по умолчанию, чтобы избежать накопления устаревшего кэша. Постоянный Qwen-специфичный кэш потребовал бы новой политики очистки, прав и жизненного цикла без доказательств, что он улучшает измеряемый путь.

### Безусловно экспортировать `getCompileCacheDir()`

Отклонено. Когда кэш был включен из существующей переменной окружения, сообщаемый каталог уже специфичен для версии Node. Повторное его использование как базы следующего процесса создает еще один вложенный каталог версий и мешает предполагаемому совместному использованию.

## Поведение при сбоях и совместимость

- Node без `enableCompileCache()`: никаких изменений окружения и никаких изменений поведения.
- `NODE_DISABLE_COMPILE_CACHE=1`: Node сообщает disabled; каталог не распространяется.
- Предоставленный оператором `NODE_COMPILE_CACHE`: сохраняется дословно и наследуется обычным образом.
- Неподдающийся записи или иной невалидный каталог кэша: Node сообщает о неудаче без выброса исключения; Qwen Code продолжает работу без кэша.
- Обновление Node или Qwen: Node изолирует несовместимые версии рантайма, а изменения содержимого исходников создают разные записи кэша.
- Покрытие: продакшен-быстрый путь — единственная точка изменения. Раннеры юнит-тестов глобально не подключаются к compile-кэшированию.
- Завершение: Node пишет накопленный кэш кода при нормальном выходе процесса. Принудительное завершение может потерять свежегенерированные записи, но не может повлиять на корректность.

## Верификация

Осуществимость проверяется гейтом до реализации с использованием одного и того же релизного бандла для обоих вариантов. Оба варианта демона получают одинаковый кэш прогретого родительского процесса. Контроль убирает окружение кэша перед импортом бандла, так что потомки ACP остаются без кэша; кандидат публикует тот же базовый каталог перед импортом, так что потомки ACP наследуют его.

Гейт на референс-хосте с 2 vCPU покрывает:

- 30 чередующихся парных холодных запусков демона
- 30 чередующихся парных прогретых запусков
- `channel.initialize`, время от процесса до первой сессии, готовность слушателя и пиковый RSS
- прогретую вторую сессию
- одновременные первые сессии
- включенную и отключенную телеметрию
- легаси-поведение одиночной сессии
- первое использование с пустым кэшем, повторное использование прогретого кэша, занимаемый кэшем объем и остаточные процессы

Реализация продолжается, только если сравнение прогретого кэша для дочернего процесса показывает воспроизводимую выгоду в инициализации или времени от процесса до сессии без функциональной регрессии.

## Результаты валидации

Гейт выполнялся на хосте Linux x64 с 2 vCPU и 4 ГБ с Node.js 22.23.1. Контроль и кандидат использовали один и тот же бандл из `77af061e` и различались только тем, наследует ли дочерний процесс ACP каталог compile-кэша родителя.

За 30 парных прогонов с прогретым кэшем кандидат выиграл каждое сравнение `channel.initialize`. Его парное медианное улучшение составило 176,6 мс при 95% доверительном интервале bootstrap 167,7–186,2 мс. Парное медианное улучшение времени от процесса до первой сессии составило 199,0 мс при 95% доверительном интервале 177,6–226,5 мс. Медианный пиковый RSS дерева процессов кандидата был выше на 8,6 МБ.

Дополнительное подтверждение на 10 парах использовало неизмененный продакшен-вход из `origin/main` как контроль и пропатченный продакшен-вход как кандидат. Оно воспроизвело медианное улучшение `channel.initialize` в 181,6 мс и медианное улучшение времени от процесса до первой сессии в 189,4 мс.

За 20 независимых пар с пустым кэшем первый прогон от процесса до сессии был на медиане медленнее на 117,2 мс при 95% доверительном интервале 69,3–130,9 мс. Второй запуск ACP, следовательно, отбивает единовременную стоимость генерации под измеряемой нагрузкой. Стабильный кэш содержал 362 файла и занимал 9,4 МБ.

Все измеряемые прогоны завершились успешно без остаточных процессов. Кандидат также прошел одновременное создание первых сессий, запуск с отключенной телеметрией и легаси-поведение одиночной сессии.
