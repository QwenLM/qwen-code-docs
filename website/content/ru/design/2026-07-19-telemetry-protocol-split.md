# Разделение протоколов экспортеров телеметрии (ленивый SDK, фаза 2)

- Статус: реализовано
- Issue: QwenLM/qwen-code#7264 (кандидат 1), продолжение #4748
- Предшественник: `2026-07-19-lazy-telemetry-sdk-loading.md` (разделение фасад / реализация)

## Проблема

Фаза 1 переместила весь SDK телеметрии за динамический `import()`, поэтому
процессы с отключенной телеметрией не загружают ничего. Но процессы с
**включенной** телеметрией по-прежнему загружают полное статическое замыкание
`sdk-impl.ts`, которое включает обе цепочки протокола OTLP независимо от того,
какую из них выбирает конфигурация:

| Кластер                                                                                                              | Размер (metafile, de962a5ecf + фаза 1) | Нужен                                  |
| -------------------------------------------------------------------------------------------------------------------- | -------------------------------------- | -------------------------------------- |
| Цепочка gRPC (`@grpc/grpc-js`, `protobufjs`, `@grpc/proto-loader`, `exporter-*-otlp-grpc`, `long`, `lodash.camelcase`) | 1121 КиБ / 125 модулей              | только `otlpProtocol: 'grpc'`          |
| Цепочка HTTP (`exporter-*-otlp-http`)                                                                                | 23 КиБ / 17 модулей                    | только `otlpProtocol: 'http'`          |
| Общий слой OTLP (`otlp-transformer`, `otlp-exporter-base`)                                                           | 915 КиБ / 41 модуль                    | обоим протоколам OTLP, **не** outfile  |

Metafile показывает два статических импортера поверхности OTLP вне самих пакетов
экспортеров:

1. `sdk-impl.ts` (его импорт `CompressionAlgorithm`) — устраняется переносом
   построения экспортеров в модули протоколов.
2. Сам `@opentelemetry/sdk-node` — его `utils.js`/`sdk.js` жадно вызывают
   `require()` для каждого пакета экспортеров (otlp proto/http/grpc × 3 сигнала,
   zipkin, prometheus), чтобы поддержать автоконфигурацию на основе окружения
   `OTEL_*_EXPORTER`. qwen-code никогда не достигает этих путей кода: он всегда
   передает явные `spanProcessors` / `logRecordProcessors` (пустой массив все
   равно закорачивает фолбэк на окружение). Обрабатывается заглушкой на этапе
   сборки бандла, см. ниже.

Когда оба устранены, разделение убирает всю поверхность OTLP с пути outfile,
цепочку gRPC — с пути HTTP, а цепочку HTTP — с пути gRPC.

Бенчмарк фазы 1 на 2C4G показал, почему это важно: при включенной телеметрии
(outfile) динамическая загрузка sdk-impl конкурирует за CPU с подготовкой сессии
на 2 ядрах (`config_construction`/`bootstrap` +50 мс), съедая большую часть
выигрыша −50 мс от цепочки импортов. Уменьшение того, что действительно
загружается, уменьшает эту конкуренцию.

## Дизайн

Два новых модуля владеют построением экспортеров и загружаются через динамический
`import()` из `startTelemetrySdk` только в соответствующей ветке конфигурации:

- `packages/core/src/telemetry/sdk-exporters-grpc.ts`
  - Импортирует три gRPC-экспортера + `CompressionAlgorithm` +
    `PeriodicExportingMetricReader`.
  - `createGrpcExporters(endpoint)` → `{ spanExporter, logExporter, metricReader }`,
    все со сжатием gzip, точно соответствуя текущему построению.
- `packages/core/src/telemetry/sdk-exporters-http.ts`
  - Импортирует три HTTP-экспортера + `PeriodicExportingMetricReader` +
    `LogToSpanProcessor`.
  - `createHttpExporters({ tracesUrl, logsUrl, metricsUrl, logToSpan })` →
    `{ spanExporter?, logExporter?, metricReader?, logToSpanProcessor? }`.
    Решение о бридже logs→spans (endpoint логов отсутствует, traces присутствует)
    перемещается сюда вместе с ним, поскольку бридж строит HTTP trace-экспортер.

Изменения `sdk-impl.ts`:

- Отбрасывает все шесть импортов экспортеров и `CompressionAlgorithm`;
  переменные экспортеров типизируются по интерфейсам SDK (`SpanExporter`,
  `LogRecordExporter`), от которых он уже зависит.
- `startTelemetrySdk` становится `async`. Порядок веток сохранен:
  - gRPC без базового endpoint'а по-прежнему возвращает `undefined` **до**
    загрузки любого модуля протокола.
  - Валидация URL HTTP (`validateUrl`) остается в `sdk-impl.ts`; модуль HTTP
    импортируется только когда хотя бы один URL сигнала проходит валидацию.
  - Ветка outfile не трогает ни один модуль протокола.
- Фасад делает `await startTelemetrySdk` (он уже выполняется внутри
  single-flight асинхронного замыкания, поэтому видимых вызывающим изменений нет).

`esbuild.config.js` получает `sdkNodeExporterStubPlugin`: когда — и только когда —
импортером является `@opentelemetry/sdk-node`, пакеты экспортеров резолвятся в
заглушку, чьи конструкторы бросают исключение. Наши модули протоколов продолжают
резолвить реальные пакеты. sdk-node трогает эти привязки только внутри своих
функций конфигурации на основе окружения, которые явные аргументы процессоров
qwen-code делают недостижимыми для traces и logs; единственный достижимый путь
(`OTEL_METRICS_EXPORTER=otlp` и т.п.) теперь бросает исключение внутри
`NodeSDK.start()` — пойманное существующим try/catch фасада, — вместо молчаливого
экспорта на endpoint localhost по умолчанию. Выбор экспортера на основе
переменных окружения никогда не был поддерживаемой поверхностью конфигурации
qwen-code.

Что загружает каждая конфигурация после разделения (измеренное статическое
замыкание каждого собранного entry-чанка):

| Конфигурация | Загружает                                         | Пропускает           |
| ------------ | ------------------------------------------------- | -------------------- |
| outfile      | только замыкание sdk-impl (975 КиБ)               | обе цепочки протоколов |
| OTLP http    | + замыкание цепочки HTTP (1,2 МиБ вкл. общий слой) | кластер gRPC         |
| OTLP grpc    | + замыкание цепочки gRPC (1,9 МиБ вкл. общий слой) | HTTP-экспортеры      |

## Защита

`scripts/check-serve-fast-path-bundle.js` получает проверку с корнем в чанке
`sdk-impl`: его замыкание статических импортов не должно достигать ни одного
члена `FORBIDDEN_OTLP_PROTOCOL_PACKAGES` — кластера gRPC (`@grpc/grpc-js`,
`@grpc/proto-loader`, `protobufjs`, `exporter-*-otlp-grpc`) плюс
`@opentelemetry/otlp-transformer`, который находится в общем слое сериализации,
подтягиваемом обеими цепочками протокола, и поэтому также ловит статический
повторный импорт модуля HTTP. Это фиксирует разделение протоколов тем же
способом, которым черный список фазы 1 фиксирует разделение фасада.

## Тестирование

- `sdk.test.ts` сохраняет свою настройку `vi.mock` без изменений: перехват
  vitest применяется к импортам тех же пакетов экспортеров модулями протоколов,
  поэтому существующие проверки аргументов конструкторов переносятся.
- Принятие следует дисциплине #4748: 30 парных последовательных холодных
  стартов на хосте 2C4G, телеметрия включена (outfile), контроль = сборка фазы
  1, кандидат = это изменение, с отчетом по channel.initialize и P50/P95
  процесс→первая сессия.

## Отклоненные альтернативы

- **Модули на каждый экспортер (на каждый сигнал)**: три дополнительных модуля
  без измеримого выигрыша — три сигнала одного протокола всегда конфигурируются
  вместе.
- **Перенос валидации URL в модуль HTTP**: отложил бы предупреждения `diag` о
  некорректных URL за загрузку модуля и изменил бы путь без корректных URL с
  «никакого импорта» на «импорт, затем ничего не делать».
