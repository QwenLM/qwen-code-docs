# Классификация безопасности shell

## Контекст и область действия

Issue [#6949](https://github.com/QwenLM/qwen-code/issues/6949) требует, чтобы режим Plan отличал команды с доказанной read-only семантикой от команд, поведение которых нельзя установить статически. Булево значение не может сохранить это различие, поэтому данное изменение вводит трёхсостояный слой фактов в `shellAstParser.ts`, не меняя маршрутизацию разрешений.

Это изменение не модифицирует маршрутизацию или логику точек вызова в Shell, Monitor, PermissionManager, спекуляции, агентах с областью памяти, ACP, промптах режима Plan или поведении выхода из Plan. Существующие булевы потребители могут стать более консервативными там, где классификатор усилен. Последующее изменение может маршрутизировать `unknown`-команды в одноразовое одобрение, используя новый факт без изменения этого классификатора.

## Контракт

`classifyShellCommandSafety(command)` — внутренний API модуля с такими результатами:

| Результат   | Значение                                                                                                                         |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `read-only` | Каждый исполняемый путь по текущим правилам доказанно не изменяет персистентное или внешнее состояние.                            |
| `write`     | Синтаксис содержит положительное свидетельство мутации файла, Git, процесса или другого состояния. Команде не обязательно в итоге выполниться успешно. |
| `unknown`   | Команда не может быть доказана как безопасная или мутирующая поддерживаемыми статическими правилами.                              |

Для валидного AST результаты комбинируются в порядке `write > unknown > read-only`. Дерево, содержащее `ERROR`, классифицируется как `unknown` до оценки частичного синтаксиса. Подстановки команд и процессов задают «пол» `unknown`, пока сканируется их исполняемое содержимое, поэтому вложенный известный писатель поднимает результат до `write`. Анализ перенаправлений владеет подстановками внутри узлов перенаправления, а оценщики команд и операторов исключают эти узлы из своих сканирований подстановок, предотвращая повторный обход вложенных подстановок. Управляющие конструкции используют тот же пол `unknown` и сканируют возможные ветки. Определение функции не является выполнением и поэтому остаётся `unknown`, не классифицируя её тело как выполненную запись.

Отдельное чистое присваивание и `cd` сохраняют существующее поведение совместимости. Присваивание, предшествующее команде или разделяющее составную последовательность с другим оператором, задаёт пол `unknown`, поскольку переменные вроде `LD_PRELOAD`, `PATH`, `PAGER` или специфичная для инструмента конфигурация могут изменить поведение; явные свидетельства записи всё равно побеждают. Под-шеллы и группы команд агрегируют своё выполняемое содержимое. API анализирует только предоставленную строку исходника; он не разворачивает `sudo` или интерпретаторы, не резолвит PATH или алиасы и не загружает конфигурацию shell.

## Сбой парсера и API совместимости

Приватный классификатор может бросать исключение при загрузке или выполнении tree-sitter. Публичный трёхсостояный API отображает эти сбои в `unknown` и никогда не подменяет их уверенностью regex. Парсер, бросающий исключение при разборе, отбрасывается и пересоздаётся из уже загруженного языка Bash, поскольку неудачный экземпляр может остаться «отравленным»; это не перезагружает рантайм или язык. Существующий API совместимости `isShellCommandReadOnlyAST()` возвращает `true` только для `read-only`, но сохраняет существующий regex-фолбэк, когда tree-sitter не может загрузиться или бросает исключение во время выполнения. Синтаксически невалидное дерево — это нормальный результат `unknown`, а не сбой парсера, поэтому оно никогда не попадает в этот фолбэк. Каждое успешно возвращённое дерево освобождается один раз в блоке `finally`.

Эта асимметрия намеренная: новым потребителям нужен честный факт неопределённости, а существующие булевы потребители сохраняют поведение доступности парсера, пока явно не мигрируют.

## Поддерживаемые свидетельства

Классификатор распознаёт ограниченный, чувствительный к регистру набор прямых писателей файловой системы, команд сигнализации процессов, перенаправления вывода, семейства мутаций Git и явные режимы записи в `find`, `sed`, `awk`, `sort`, `tree`, `uniq`, `tee` и `dd`. Sed и AWK используют общие линейные сканеры, которые отличают инлайн-программы от значений опций и файловых аргументов, поэтому экранированный, некорректный или сильно повторяющийся ввод не может вызвать regex-бэктрекинг или сфабриковать свидетельство записи из имени файла. Выходные файлы Git для `diff`, `log` и `show` являются записями. Формы `printf -v` с состоянием — unknown. Явные Git-хелперы и проверка подписи, включая опции окружения pager/config, хелперы diff/text-conversion, внешний pager grep и заполнители подписи, — unknown; неподдерживаемые глобальные опции Git и пути справки подкоманд также завершаются fail closed, поскольку справка может запустить внешний просмотрщик. Динамическое выполнение, внешние скрипты, неоднозначные цели вывода, интерпретаторы и обёртки, `sort --compress-program`, препроцессоры ripgrep, хелперы hostname и поиск в архивах (`--pre`, `--hostname-bin`, `--search-zip` и `-z`), а также обычные команды pager остаются `unknown`. Терминаторы опций и арность значений поддерживаемых опций интерпретируются, чтобы файл или сообщение с буквальным именем `--help` не были приняты за вызов справки. Имена команд в другом регистре, неперечисленные пакетные менеджеры, сервисы и пользовательские исполняемые файлы также остаются `unknown`; классификатор — не песочница.

Устаревший синхронный чекер отражает каждый вновь отклоняемый паттерн, необходимый синхронному планировщику. Он сохраняет развёртки параметров с sentinel'ами вместо того, чтобы позволять `shell-quote` стирать их, отклоняет некорректные завершающие пайплайны и составные конструкции с присваиваниями и оценивает обёртки из исходной команды. Он намеренно остаётся булевым и более консервативен, чем AST-классификатор: `printf`, `sort` с множеством опций, команды `tree`, `uniq`, `rg` и `ripgrep`, а также формы веток Git за пределами простейших режимов листинга выполняются последовательно.

## Потребители и граница миграции

Текущие булевы потребители — Shell, Monitor, PermissionManager, гейт спекуляции и конфигурация агентов с областью памяти; их точки вызова не меняются в этом рефакторинге. Синхронный чекер также используется основным планировщиком инструментов и легаси-утилитой разрешений shell. Планировщик теперь передаёт чекеру исходную команду, чтобы обёртки оставались unknown вместо разворачивания в якобы read-only команду. `extractCommandRules()` остаётся независимой от классификации безопасности.

Последующее изменение `fix(core): Route unknown Plan shell commands to one-off approval` должно потреблять `classifyShellCommandSafety()` только на границе разрешений Plan. Оно должно отдельно определить происхождение одобрения, время жизни, поведение ACP и взаимодействие с выходом из Plan; эти политики не принадлежат слою фактов.

## Референс Claude Code

Bash-анализ Claude Code полезен как свидетельство для двух принципов дизайна: неопределённость разбора должна быть представлена явно, а решения о разрешениях должны завершаться fail closed, когда разбор недоступен или слишком сложен. Его более крупный парсер Bash и движок политик не копируются, поскольку Qwen Code нужен лишь небольшой классификатор на текущей границе.

## Проверка

Покрытие модульными тестами использует таблично-управляемые матрицы для всех трёх состояний, приоритета составных конструкций, подстановок, синтаксических ошибок, инициализации парсера и сбоев во время выполнения, ограниченного поведения на враждебном вложенном и экранированном вводе и монотонности совместимости. Тесты синхронного чекера и планировщика предотвращают попадание вновь известных небезопасных команд в параллельные пакеты Shell.
