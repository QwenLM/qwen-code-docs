# Фаза 4b мульти-воркспейсного демона: воркеры каналов по рабочим пространствам

## Резюме

Этот документ проектирует срез воркеров каналов Фазы 4b задачи #6378:
группировку управляемых демоном воркеров каналов по рабочим пространствам.
Voice (`/workspaces/:workspace/voice/stream`) — отдельный срез Фазы 4b и сюда
не входит.

Сегодня `qwen serve --channel <name>` запускает один воркер каналов,
привязанный к primary-рабочему пространству. В мульти-воркспейсном режиме
воркеры должны группироваться по рабочему пространству, владеющему каждым
каналом: каждое зарегистрированное доверенное рабочее пространство получает
свой процесс воркера, привязанный к cwd этого рабочего пространства,
`QWEN_DAEMON_WORKSPACE` и эффективному оверлею окружения. Pidfile и статус
демона получают аддитивный список воркеров, сохраняя существующие поля
одного воркера. `--channel all` остается только для primary в v1. Поведение с
одним рабочим пространством не меняется.

Модель отображения: каналы группируются **неявно по их разрешенному cwd** —
канал принадлежит тому зарегистрированному рабочему пространству, в которое
разрешается его настроенный cwd. Новый синтаксис CLI не добавляется.

## Базовая линия: текущий стык воркера каналов

- `run-qwen-serve.ts` создает один `ChannelWorkerSupervisor` в колбэке
  listen (привязанный к `boundWorkspace`, то есть primary) и запускает его в
  `completeRuntimeStartup`. `completeRuntimeStartup` — единственная точка
  схождения всех путей старта рантайма (eager-путь `deps.bridge` и путь
  `startRuntime` -> `buildRuntime`). `deps.bridge` ограничен одним рабочим
  пространством, поэтому мульти-воркспейсный режим всегда проходит через
  `startRuntime`.
- `commands/channel/daemon-worker.ts` валидирует свое рабочее пространство
  против `capabilities.workspaceCwd` (primary), поэтому не-primary воркер
  бросает исключение. `validateChannelWorkspaces` дополнительно требует,
  чтобы разрешенный cwd каждого канала был равен рабочему пространству
  демона.
- `config-utils.ts` разрешает cwd канала как
  `resolvePath(rawConfig.cwd || defaultCwd)`; `loadChannelsConfig(W)`
  возвращает `loadSettings(W).merged.channels`, который сливает области
  system/user/workspace.
- `channel-worker-supervisor.ts` строит окружение воркера из
  `{...process.env}`. В мульти-воркспейсном режиме родительское окружение —
  это базовое окружение демона (изоляция окружения Фазы 2a), поэтому в нем
  будет недоставать собственного `.env` рабочего пространства.
- Pidfile `ServiceInfo` — на один воркер (`channels[] / servePid? /
  workerPid?`); статус демона `runtime.channelWorker` — один снимок.
- Реестр рабочих пространств (собираемый внутри `buildRuntime`)
  предоставляет `env.effectiveEnv`, `trusted` и канонический `workspaceCwd`
  каждого рантайма. Маршрутизация сессий Фаз 2a/3 уже нацеливается на
  рантайм по `workspaceCwd`.

## Алгоритм группировки

Чистая функция `resolveChannelWorkspaceGroups` зеркалирует
`validateChannelWorkspaces` на стороне воркера и разрешение cwd в
`config-utils` — иначе группировка на слое serve и собственная валидация
воркера могли бы разойтись. Поскольку `loadChannelsConfig(W)` слит между
областями, владение нельзя решить по тому, «слитая конфигурация какого
рабочего пространства содержит имя».

Для каждого выбранного канала `name` переберите зарегистрированные рабочие
пространства `W`. Если `name` присутствует в `loadChannelsConfig(W)`,
вычислите `resolvedCwd = canonicalizeWorkspace(resolvePath(cfg[name].cwd ?? W))`.
`W` является кандидатом во владельцы **тогда и только тогда, когда
`resolvedCwd === W`** (то есть канал прошел бы `validateChannelWorkspaces`
при `W`):

- явный `cwd` = зарегистрированный путь X: удовлетворяет только `W === X` ->
  владелец = X (однозначно).
- без `cwd`, определен только в области собственного рабочего пространства
  (`/B/.qwen/settings.json`): появляется только в слитой конфигурации B и
  разрешается в B -> владелец = B (однозначно).
- без `cwd`, определен в области user/system: удовлетворяет при каждом W ->
  несколько владельцев -> действительно неоднозначно.
- явный `cwd` = незарегистрированный путь: не удовлетворяет ни одному W ->
  ноль владельцев.

Ошибки и агрегация:

- ноль владельцев -> `channel_workspace_mismatch` (не настроен, либо cwd
  указывает на незарегистрированное рабочее пространство).
- более одного владельца -> `ambiguous_channel_workspace` (канал области
  user/system без `cwd`; оператор должен привязать его к рабочему
  пространству или добавить явный `cwd`).
- владелец недоверенный -> `untrusted_workspace` (каналу нужно создавать
  сессии).
- уникальный доверенный владелец -> группировка имен по владельцу -> каждая
  группа получает `{mode:'names', names}`.
- `mode:'all'` -> только primary: `[{ workspaceCwd: primary, selection:
  {mode:'all'} }]`. Primary-воркер загружает слитые каналы primary; записи,
  чей cwd не является primary, сохраняют существующее поведение ошибки
  `validateChannelWorkspaces`.
- одно рабочее пространство (только primary): `resolvedCwd` может быть только
  primary, порождая ровно ту же единственную группу, что и сегодня.

Общий помощник cwd используется разбором конфигурации и группировкой
владения. Явные абсолютные пути и `~/...` сохраняют свое существующее
значение; обычные относительные пути разрешаются относительно рабочего
пространства, чьи настройки загружаются. Путь владельца затем канонизируется,
так что слой serve и воркер не могут разойтись во владении.

## Идентичность и окружение воркера

`CreateChannelWorkerSupervisorOptions` получает опциональный `workerBaseEnv`
(по умолчанию `process.env`). `createWorkerEnv` использует
`workerBaseEnv ?? process.env` как базу; все остальное без изменений
(`QWEN_DAEMON_WORKSPACE`, очистка окружения от токена, инъекция токена
демона). Менеджер групп передает `runtime.env.effectiveEnv ?? process.env` —
прямое чтение поля избегает импорта приватного помощника из `server.ts`, а у
рантайма в режиме родительского процесса (одно рабочее пространство)
`effectiveEnv` не определен и происходит откат на `process.env` ровно как
сегодня.

## Исправление валидации daemon-worker

`DaemonCapabilitiesLike` получает опциональный
`workspaces?: Array<{ cwd; id; primary; trusted }>` (уже публикуется
`/capabilities` начиная с Фазы 2a). Валидация разрешает
`daemonWorkspace = canonicalizeWorkspace(opts.workspace)`; когда
`capabilities.workspaces` присутствует, он должен совпадать с одним из них и
быть доверенным, иначе происходит откат на legacy-проверку
`== capabilities.workspaceCwd` для старых одно-воркспейсных демонов. Обе
стороны каноничны (супервизор передает `runtime.workspaceCwd`), поэтому
сравнение стабильно. Остальная часть воркера (загрузка конфигурации каналов,
`validateChannelWorkspaces`, `createOrAttach({workspaceCwd})`) уже работает с
мульти-воркспейсной маршрутизацией.

## Менеджер групп супервизора

Тонкий `ChannelWorkerGroup` владеет
`Map<workspaceId, ChannelWorkerSupervisor>`:

- строится из разрешенных групп и реестра; каждый супервизор привязан к
  `workspaceCwd`, выбору и `env.effectiveEnv` своего рантайма и создается
  через ту же внедряемую фабрику, что и единственный воркер.
- `start()` запускает супервизоры последовательно и откатывает уже запущенные,
  если более поздний запуск не удался. `stop()` ждет любого выполняющегося
  перезапуска и останавливает все супервизоры. `killAllSync()` остается
  фолбэком обработчика сигналов.
- `restart()` — транзакция перезагрузки всего демона. Конкурентные запросы
  коалесцируются; супервизоры перезапускаются последовательно, и любой сбой
  останавливает всю группу, чтобы избежать частично перезагруженного парка.
- `snapshots()` возвращает снимки по рабочим пространствам
  (`ChannelWorkerSnapshot & { workspaceId; workspaceCwd; primary }`);
  `primarySnapshot()` поддерживает legacy-поля одного воркера.
- `onReady` / `onExit` любого супервизора запускает полную перезапись pidfile
  из `snapshots()` (никогда инкрементное обновление одной записи — см. ниже).

## Схема pidfile и конкурентность

`ServiceInfo` получает опциональный
`workers?: Array<{ workspaceId?; workspaceCwd?; channels: string[]; workerPid? }>`.
Верхнеуровневый `channels` становится объединением каналов всех воркеров, а
верхнеуровневый `workerPid` остается pid первичного воркера, поэтому старые
читатели (`qwen channel status`, который читает только `workerPid` и
`channels`) не затрагиваются.

Конкурентность: при N воркерах колбэки `onReady`/`onExit` срабатывают
одновременно. Чтение-изменение-запись одной записи теряло бы обновления.
Вместо этого писатель берет полный набор снимков из группы и выполняет одну
синхронную полную перезапись. `writeServeServiceInfo` использует синхронные
`openSync`/`writeSync` без `await`, поэтому запись полного снимка достаточно
атомарна — последняя запись всегда содержит полную картину.
`writeServeServiceInfo` получает опциональный параметр `workers`, записываемый
как есть под существующим охранником `O_RDWR + O_NOFOLLOW` + владения serve;
`parseServiceInfo` опционально валидирует `workers?` и пропускает его дальше.

## Схема статуса демона

`DaemonStatusRuntime` получает опциональный
`channelWorkers?: Array< ChannelWorkerSnapshot & { workspaceId; workspaceCwd; primary }>`;
обязательный `channelWorker` остается снимком primary-группы для старых
клиентов. Геттер (`getChannelWorkerSnapshots`) пробрасывается из
`run-qwen-serve` через `ServeAppDeps` и `BuildDaemonStatusOptions`, зеркаля
существующий путь `getChannelWorkerSnapshot`, и также предоставляется в
bootstrap-статусе. До создания группы (до старта) он сообщает снимок
отключенного состояния.

## Оркестрация и тайминг

- Единственная переменная `channelWorker` становится ссылкой на менеджер групп
  во внешней области видимости, чтобы писатель pidfile и пути завершения
  по-прежнему видели ее.
- Ранний fail-fast: в момент listen (до `buildRuntime`) чистая функция
  группировки выполняется один раз против `workspaceInputs` + `loadSettings`
  + замороженного при загрузке доверия (`getWorkspaceTrustStatus`).
  Неизвестное, неоднозначное, недоверенное и невалидное владение cwd
  отклоняет старт до того, как будет предоставлен пригодный handle.
  Разрешенный план групп замораживается на остаток старта; настройки не
  перегруппировываются позже под другим снимком файловой системы.
- Фактическое создание/запуск перемещается в `completeRuntimeStartup`: он
  читает реестр из `runtimeApp.locals.workspaceRegistry` (гарантированно
  присутствует для мульти-воркспейсного режима, который всегда проходит через
  `startRuntime` -> `buildRuntime`), строит супервизор на каждую замороженную
  группу и запускает их — заменяя единственный `channelWorker.start()`.
- Вновь построенное приложение рантайма публикуется и присоединяется к
  транспортам ACP до старта супервизоров каналов. Воркерам во время bootstrap
  нужен маршрут `/capabilities` рантайма, и они могут получать трафик каналов
  сразу после подключения, поэтому их маршруты сессий демона уже должны быть
  доступны. Это соответствует существующему порядку с одним рабочим
  пространством на `main`; `runtimeReady` по-прежнему устаканивается только
  после того, как каждый запрошенный супервизор достигнет ready.
- Сбой запуска воркера каналов остается фатальным. Публикация рантайма
  отзывается до того, как группа, pidfile, бриджи и слушатель будут разобраны;
  таймаут старта рантайма во время фазы воркеров следует тем же путем вместо
  того, чтобы оставить слушающий демон. Отмена группы также предотвращает
  запуск более позднего супервизора рабочего пространства после начала этого
  teardown.
- Резервирование pidfile сохраняет агрегированные имена каналов; пути
  завершения (`stopChannelWorkerAfterFailedStartup`, `killAllSync`, обычное
  завершение) рассылаются в группу.

Риск регрессии: для одного рабочего пространства тайминг создания
перемещается из колбэка listen в `completeRuntimeStartup`. Существующие
канальные тесты `run-qwen-serve.test.ts` (внедренная фабрика,
pidfile-по-ready, форсированный kill по второму сигналу) должны оставаться
зелеными. Покрытие мульти-воркспейсной оркестрации также зондирует живой
маршрут `/capabilities` демона из старта супервизора, чтобы порядок
рантайм/воркер не мог регрессировать за внедренной фабрикой только-для-ready.

## Поведение при загрузке

- одно рабочее пространство: идентично сегодняшнему.
- мульти-воркспейсный режим + `--channel names`: группировка по владельцу,
  один воркер на доверенное рабочее пространство; ноль / несколько
  владельцев / недоверенное -> явная ошибка загрузки (без половинчатого
  включения).
- мульти-воркспейсный режим + `--channel all`: только primary-воркер, с
  примечанием в stderr о том, что не-primary каналы не размещаются.

## Совместимость и ограничения

- одно рабочее пространство без изменений; старые читатели pidfile/статуса
  сохраняют `channels`/`workerPid`/`channelWorker`.
- рекомендации оператору: чтобы разместить канал в не-primary рабочем
  пространстве, определите его в собственном `.qwen/settings.json` этого
  рабочего пространства (`cwd` не нужен) или определите его в любой области с
  явным `cwd`, равным пути рабочего пространства. Канал области user/system
  без `cwd` должен быть устранен от неоднозначности в мульти-воркспейсном
  режиме, иначе демон завершится ошибкой загрузки.
- ограничения v1: неоднозначные/одноименные каналы нуждаются в будущем явном
  синтаксисе; `--channel all` только для primary; радиус отказа единого
  демона покрывает воркеры всех рабочих пространств; один токен демона
  покрывает все рабочие пространства.

## Открытые вопросы

- Должны ли неоднозначные каналы разрешаться явным синтаксисом
  `--channel <workspace>:<name>` вместо ошибки загрузки?
- Должен ли `--channel all` в конечном итоге распределяться по всем рабочим
  пространствам?

## Вне области

- voice `/workspaces/:workspace/voice/stream` и voice per-workspace.
- динамическое добавление/удаление рабочих пространств (Фаза 5).
