# Heartbeat беззвучных команд

Дата: 2026-07-14
Статус: реализовано

## Проблема

Команда shell на переднем плане, не производящая вывода, не выпускает никаких событий между запуском и завершением. В интерактивном использовании TUI это не проблема — спиннер продолжает двигаться, — но для headless-потребителей (ACP-шлюзы, такие как DataAgent, конвейеры `--output-format stream-json`) сессия полностью замолкает на все время выполнения команды. Шлюз, наблюдающий за потоком событий, не может отличить «165-секундный SQL-зонд все еще выполняется» от «цепочка выполнения умерла», поэтому долго выполняющиеся беззвучные команды сообщаются пользователями как зависание агента.

Продакшен-диагностика такой сессии (сессия DataAgent `77255d98`, задача на 41 минуту, ~32 минуты в ожиданиях инструментов) определила отсутствующий сигнал живости как один из трех P0-фиксов надежности, наряду с семантикой таймаутов shell (PR 1, отдельное изменение) и stop-гейтом todo (PR 3).

Референс-реализация: Claude Code опрашивает файл вывода каждую секунду и вызывает свой колбэк прогресса, даже когда содержимое пустое, а затем выпускает троттлируемые события `tool_progress` с минимальной нагрузкой потребителям SDK. Прогресс никогда не попадает в контекст модели.

## Цели

- Пока команда shell на переднем плане беззвучна, периодически выпускать структурированный сигнал живости для потребителей, которым он нужен (ACP-клиенты, stream-json).
- Нести только статистику — прошедшее время, возраст вывода, количество строк/байтов, эффективный таймаут. Никогда не вывод команды.
- Никогда не попадать в контекст модели; никогда не нарушать отображение живого вывода интерактивных потребителей.

## Не цели

- Автоматический перевод в фон по таймауту (отслеживается отдельно как P1-элемент).
- Потоковая передача живого вывода команды ACP-клиентам (фреймы `content`).
- Проброс MCP `mcp_tool_progress` через ACP, распространение heartbeat'ов субагентов в `AgentResultDisplay` или улучшения отображения TUI — все это последующие работы.

## Дизайн

### Форма события

`ShellProgressData` присоединяется к объединению `ToolResultDisplay` в `packages/core/src/tools/tools.ts`, повторяя существующий прецедент `McpToolProgressData`, с общим экспортируемым гейтом `isShellProgressData`:

```ts
interface ShellProgressData {
  type: 'shell_progress';
  elapsedMs: number; // монотонное, с момента запуска после инициализации PTY
  lastOutputAgeMs?: number; // монотонный возраст последнего вывода; отсутствует = еще не было
  totalLines?: number; // только путь PTY/AnsiOutput
  totalBytes?: number; // только путь PTY/AnsiOutput
  timeoutMs?: number; // эффективный таймаут, включая значение по умолчанию 120с; отсутствует при отключении
}
```

Длительности монотонны (дельты `performance.now()`), поэтому коррекции NTP не могут их исказить; `lastOutputAgeMs` по той же причине является возрастом, а не меткой времени эпохи.

### Продюсер

`ShellToolInvocation.execute()` запускает `setInterval` после получения дескриптора выполнения (чтобы время динамического импорта PTY не могло создать heartbeat для процесса, который не существует) и только при наличии колбэка `updateOutput`. Каждый тик выпускает heartbeat тогда и только тогда, когда обновление отображения не срабатывало в течение полного интервала — проверка переиспользует существующее состояние троттлинга `lastUpdateTime`, поэтому команды с идущим выводом никогда не выпускают heartbeat. Таймер очищается в тех же трех местах, что и существующие таймеры завершающего сброса/предупреждения о таймауте: catch броска сервиса, `finally` результата и `onAbort` (после аборта сигнал «все еще выполняется» в окне между kill и завершением был бы ложью).

Интервал берется из `tools.shell.heartbeatIntervalMs` (настройки → конфигурация CLI → `ConfigParameters` ядра → `getShellHeartbeatIntervalMs()`, та же цепочка, что и для `defaultTimeoutMs`), по умолчанию 10 000 мс; `0` отключает.

### Потребители

| Потребитель                          | Поведение                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CoreToolScheduler` liveOutputCallback | Пробрасывает heartbeat'ы в `outputUpdateHandler`, но пропускает замену liveOutput и уведомление об обновлении — объект статистики не должен затирать накопленный живой вид.                                                                                                                                                                                                                                                                                                                                                               |
| `useReactToolScheduler` (TUI)        | Игнорирует heartbeat'ы; TUI уже показывает спиннер.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `agent-core` (среда выполнения субагентов) | Игнорирует heartbeat'ы; их трансляция перезаписала бы `liveOutputs` вида субагента.                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ACP `Session.runTool`                | Передает колбэк обновлений в `invocation.execute()`. Heartbeat'ы становятся fire-and-forget фреймами только с метой `tool_call_update { status: 'in_progress', _meta: { toolName, shellProgress } }`. Гейт `toolSettled`, устанавливаемый в момент возврата `execute()` (включая бросок), отбрасывает тик, гонящийся с путем завершения, поэтому клиент никогда не может наблюдать `in_progress` после `completed`. Количество heartbeat'ов и возраст последнего вывода записываются как атрибуты спана `shell.heartbeat_count` / `shell.last_output_age_ms` на существующем спане выполнения инструмента. |
| stream-json                          | `createToolProgressHandler` пробрасывает heartbeat'ы через существующий конвейер `emitToolProgress` (события потока `tool_progress`, гейтируемые `--include-partial-messages`). `ToolProgressStreamEvent.content` расширяется до `McpToolProgressData \| ShellProgressData`.                                                                                                                                                                                                                                                                       |
| desktop `QwenAgent`                  | Пропускает обновления `status: in_progress` в `handleToolCallUpdate` — ранее он преобразовывал каждый `tool_call_update` в терминальный `tool_result`, что преждевременно завершило бы команду с пустым результатом на первом heartbeat'е.                                                                                                                                                                                                                                                                                                |
| каналы `DaemonChannelBridge`         | Отбрасывает фреймы `in_progress` без kind вместо пометки их как некорректных (`tool_call_update` там требует `kind`, которого heartbeat'ы только с метой не несут).                                                                                                                                                                                                                                                                                                                                                                        |
| нормализатор daemon UI web-shell     | Отбрасывает фреймы heartbeat'ов — нормализация одного из них перезаписала бы человекочитаемый заголовок блока инструмента голым именем инструмента, выведенным из `_meta.toolName`.                                                                                                                                                                                                                                                                                                                                                          |

`ToolCallUpdate` ACP определяет каждое поле, кроме id, как опциональное, а `_meta` — как точку расширения, поэтому клиенты, соответствующие протоколу, игнорируют новые фреймы. Однако этот контракт не самоприменим: полный обход потребителей `tool_call_update` в репозитории нашел три, которые неправильно обрабатывали фреймы (desktop-агент, бридж каналов демона, нормализатор web-shell — исправлены выше, каждый с регрессионным тестом), тогда как остальные (VS Code companion, сжатие acp-bridge, экспорт сессий, адаптер daemon TUI) сливают условно и безопасны для heartbeat'ов как есть. На пути запроса разрешения (который сегодня не выпускает уведомление о старте) heartbeat может быть первым обновлением, которое клиент видит для вызова инструмента — тот же контракт упорядочивания, что и для существующих обновлений только о завершении.

### Почему не ShellExecutionService

Сервис дал бы чуть более точный `lastOutputAt`, но слой инструмента уже наблюдает каждое событие вывода, и размещение таймера там означало бы управление им через жизненные циклы PTY/child_process/promote, в то время как PR 1 параллельно перерабатывает семантику до аборта в том же файле. Пользовательский shell `!` не нуждается в heartbeat'ах, поэтому ничего не теряется.

## Верификация

- Юнит: периодичность/форма/очистка продюсера (фейковые таймеры, включая `performance`), проброс планировщиком без замены liveOutput, сохранение хука TUI, фреймы ACP только с метой + гейт поздних heartbeat'ов, форма событий stream-json и гейт partial-messages.
- E2E stream-json: `sleep 15` породил `tool_progress` с `{type:'shell_progress', elapsedMs:10001, timeoutMs:30000}` и без полей статистики вывода.
- E2E ACP (stdio JSON-RPC): `tool_call` → heartbeat `tool_call_update` (только мета, 10 с) → `completed`, без завершающего `in_progress`.
- TUI (tmux): беззвучная команда показывает обычный спиннер/строку прошедшего времени; никаких утечек JSON во время выполнения или в финальном транскрипте.
