# Персистентная регистрация рабочих пространств демона

## Цель

Рабочие пространства, добавленные из Web Shell, переживают перезапуск процесса `qwen serve`,
когда демон перезапускается с тем же первичным рабочим пространством и `QWEN_HOME`.

## Владение состоянием

Динамическая регистрация рабочих пространств — это приватная конфигурация демона пользователя,
а не конфигурация проекта и не одноразовые выходные данные среды выполнения. Регистрации
хранятся в:

```text
${QWEN_HOME:-~/.qwen}/daemon/workspaces/<primary-scope-sha256>.json
```

Хеш области — это полный SHA-256 канонического пути первичного рабочего пространства
(в нижнем регистре на Windows). Путь первичного рабочего пространства дублируется в файле,
чтобы несовпадающая или поврежденная область отклонялась, а не применялась молча.

```json
{
  "schemaVersion": 1,
  "primaryWorkspace": "/repo/main",
  "workspaces": ["/repo/service-a"]
}
```

Хранятся только канонические вторичные пути. Доверие, окружение, идентификаторы рабочих
пространств, сессии и ошибки среды выполнения выводятся заново при каждом запуске демона.

## Жизненный цикл

Продакшен-демон читает небольшой файл регистрации после разрешения и канонизации первичного
рабочего пространства. Валидные сохраненные пути объединяются после явных входных значений
`--workspace`. Явные входные значения авторитетны: некорректный или недоступный явный путь
остается ошибкой запуска, тогда как недоступный сохраненный путь пропускается с
предупреждением и сохраняется на диске для последующего перезапуска.

Восстановленные пути попадают в обычный цикл построения вторичных сред выполнения до сборки
`WorkspaceRegistry` и поверхностей Express/ACP. Это сохраняет согласованность возможностей,
ACP-монтирований с указанием рабочего пространства, агрегации статуса и лимита общего числа
сессий по умолчанию с восстановленным набором сред выполнения.

Для локальных для процесса добавлений после сборки приложения ACP-маршруты с указанием
рабочего пространства остаются смонтированными, пока существует реестр, и создают доверенное
вторичное монтирование лениво при первом использовании. Это не позволяет снимку запуска с
одним рабочим пространством сделать последующую регистрацию из Web Shell непригодной до
перезапуска.

`POST /workspaces` принимает `persist: true`. Успешный персистентный запрос не
подтверждается, пока успешно не завершится обновление файла регистрации. Повторный
персистентный запрос для уже активного рабочего пространства повышает или подтверждает его
сохраненную регистрацию и идемпотентно завершается успешно. Существующие вызывающие стороны,
не передающие `persist`, сохраняют текущее локальное для процесса поведение.

`GET /workspace-registrations` предоставляет целевой сохраненный набор для управления.
`DELETE /workspace-registrations/:id` забывает сохраненную регистрацию; активная среда
выполнения остается живой до перезапуска. Первичное рабочее пространство никогда не может
быть сохранено или забыто через эту поверхность.

## Безопасность и поведение при сбоях

- Хранилище ограничено 24 вторичными путями, каждый не длиннее лимита пути рабочего
  пространства демона.
- Чтение отклоняет символические ссылки, нерегулярные файлы, файлы слишком большого размера,
  некорректный JSON, неизвестные версии схемы и несовпадения первичной области.
- Запись использует внутрипроцессный мьютекс, межпроцессную блокировку и общий атомарный
  помощник записи файлов с режимом `0600` и без следования символическим ссылкам.
- Пути мутаций никогда не рассматривают поврежденное хранилище как пустое, что предотвращает
  перезапись восстанавливаемых данных при последующем добавлении.
- Персистентное доверие намеренно отсутствует; восстановленные рабочие пространства проходят
  через текущее вычисление доверенных папок.
- Сохраненные записи, которые отсутствуют, недоступны, вложены или превышают активный лимит,
  пропускаются без удаления целевой записи. Дублирующиеся записи делают хранилище
  невалидным и никогда не переписываются неявно.

## Совместимость

Аддитивная возможность `persistent_workspace_registration` анонсирует новый контракт. Опция
запроса SDK и поле ответа `persisted` аддитивны. `runQwenServe` владеет автоматическим
восстановлением при запуске. Прямые встраивания `createServeApp` получают маршруты
управления персистентностью только при явном предоставлении хранилища регистраций и остаются
ответственными за восстановление своего внедряемого реестра рабочих пространств до создания
приложения.

## Граница последующих работ

Горячее удаление остается отдельной задачей: забывание регистрации влияет на следующий
перезапуск, но не завершает сессии и не освобождает активный бридж рабочего пространства.
