# Исполнение плана обычной сессии

## Цель

Показывать Todo-план обычной сессии как граф зависимостей и связывать каждый
узел с выполнениями Agent, которые его реализуют. Переиспользовать
существующий стрим плана ACP, снимок задач сессии и сессию деталей субагента.

Эта функция наблюдательная. Она не планирует, не повторяет, не разблокирует и
не завершает работу.

## Контракт данных

`todo_write` принимает опциональные ID Todo `blockedBy`. Рантайм валидирует,
что ID уникальны, ссылки существуют, зависимости не дублируются и не ссылаются
на себя, и граф ацикличен.

Sidecar Todo хранит сгенерированный рантаймом `planId` вместе с текущим
снимком. ID остается стабильным, пока активный план пересматривается. Очистка
плана или начало непустой работы после завершения предыдущего плана начинает
новый план.

Отображения результата Todo несут `planId`, поэтому живая проекция ACP и путь
воспроизведения обычного транскрипта сохраняют одни и те же метаданные плана:

- обновление плана `_meta.qwenTodoPlan.id`: стабильная идентичность плана
- обновление плана `_meta.qwenTranscript.planToolCallId`: исходный вызов
  инструмента Todo
- запись плана `_meta.qwenTodo.id`: исходный ID Todo
- запись плана `_meta.qwenTodo.blockedBy`: ID зависимостей, когда присутствуют

Клиенты, игнорирующие `_meta`, продолжают получать стандартные записи плана
ACP.

Инструмент Agent принимает опциональный `todo_id`. Это руководство, а не гейт
рантайма: вызовы Agent верхнего уровня должны предоставлять его, когда
существует активный граф Todo. Существующий `AgentTask.toolUseId` связывает
вызов инструмента Agent с живым статусом задачи, поэтому API задач не
нуждается в дополнительном поле.

## Поток UI

Активный Todo-пилл продолжает рендерить существующий компактный список. Клик
по нему открывает существующий диалог Tasks. Когда присутствуют метаданные
плана, этот диалог добавляет нативную CSS-секцию исполнения плана над
существующим деревом задач:

1. Топологически расслоить узлы по `blockedBy`.
2. Сгруппировать вызовы инструмента Agent верхнего уровня по `args.todo_id`.
3. Соединить строки живых задач через `task.toolUseId === tool.callId`.
4. Держать вложенные строки Agent под корнем через `parentAgentId`.
5. Выбрать узел workflow, чтобы осмотреть его полное содержимое Todo, статус,
   зависимости и связанные выполнения Agent под графом.
6. Открыть существующую живую панель деталей субагента из связанного
   выполнения Agent; она остается источником для стримингового прогресса,
   вызовов инструментов и финального вывода.
7. Поместить отсутствующие или неизвестные привязки `todo_id` в группу
   Unassigned.

Библиотека графов не добавляется. Планы без метаданных зависимостей сохраняют
списковое представление.

## Одобрение в режиме планирования

Режим планирования — включаемый явно гейт исполнения для пользователей,
которые хотят просмотреть workflow до начала работы. Когда `exit_plan_mode`
запрашивает разрешение, Web Shell показывает авторитетное тело плана ACP, за
которым следует активный Todo-workflow, в существующей панели одобрения.
Представление Todo дополнительно, потому что его снимок может отличаться от
отправленного текста плана. Workflow с учетом зависимостей рендерится как тот
же DAG, который использует диалог Tasks; workflow без зависимостей сохраняет
списковое представление.

Существующий жизненный цикл разрешений остается авторитетным: одобрение
выходит из режима планирования и начинает исполнение, тогда как отклонение
оставляет сессию в режиме планирования. Если активного снимка Todo нет,
одобрение сохраняет свое существующее текстовое представление, используя тело
плана, переносимое ACP. Сессии, не входящие в режим планирования, не
изменяются.

## Композиция статуса

Статус Todo остается бизнес-источником истины. Состояние Agent — оверлей
исполнения:

1. Любое связанное выполнение выполняется: Running
2. Иначе, любое связанное выполнение на паузе: Paused
3. Todo завершен: Completed
4. Любой зависимый Todo не завершен: Blocked
5. Todo в процессе: In progress
6. Иначе: Ready

Сбойное или отмененное выполнение добавляет бейдж Needs attention без
изменения статуса Todo.

## Совместимость и границы

- Старые снимки Todo без ID или зависимостей остаются читаемыми.
- Вызовы Agent без `todo_id` остаются валидными.
- Пустые снимки Todo должны немедленно очищать активное состояние.
- Полные результаты субагентов остаются вне трехсекундного ответа опроса
  задач.
- Узлы Todo не выдумывают вывод шагов; детали исполнения берутся из связанных
  вызовов инструмента Agent и существующей сессии деталей субагента.
- Строгое принуждение «сначала план» для каждой сессии остается вне области,
  потому что проверка существования на уровне сессии могла бы принять
  устаревший план.
