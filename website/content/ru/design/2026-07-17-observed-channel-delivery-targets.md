# Наблюдаемые контакты каналов с областью действия рабочего пространства

## Проблема

Управляемые демоном обработчики каналов получают идентификаторы пользователей, групп и топиков платформы во входящих сообщениях, но эти идентификаторы эфемерны. Аутентифицированным клиентам рабочего пространства нужен read API, который перечисляет недавно наблюдаемые контакты IM, чтобы пользователь мог выбрать полную платформенную цель доставки, не находя и не вводя идентификаторы вручную.

## Область применения

Это изменение наблюдает принятые входящие сообщения, сохраняет ограниченный граф отношений для каждого рабочего пространства демона и возвращает полные идентификаторы платформы для каналов DingTalk, Feishu, Telegram и WeCom.

Оно не изменяет конфигурацию вебхуков или проактивную доставку, не запрашивает каталог платформы, не претендует на возврат полного состава группы, не наблюдает вывод бота и не восстанавливает исторический трафик. Автономный `qwen channel start` не меняется.

## Владение и персистентность

Рантайм рабочего пространства демона владеет реестром:

```text
$QWEN_HOME/channels/daemon/<workspaceHash>/observed-contacts.json
```

`QWEN_HOME` имеет уровень процесса, но `<workspaceHash>` разделяет данные по каноническому пути рабочего пространства. Реестр не хранится в чекауте рабочего пространства и не является единым общепроцессным графом. Его каталог использует режим `0700`, где это поддерживается; атомарный JSON-файл использует режим `0600`.

Реестр хранит не более 500 наблюдений отношений по всем каналам и беседам рабочего пространства. Каждое наблюдение содержит `channelName`, идентификатор пользователя, опциональный идентификатор группы, опциональный идентификатор топика и `lastObservedAt`. Ключ дедупликации — `[channelName, user.id, group?.id, topic?.id]`. Поэтому шумная беседа может вытеснить более старые наблюдения из другой беседы. Наблюдения старше максимального 365-дневного читаемого окна удаляются при следующей принятой записи.

## Граница наблюдения

Запись происходит после того, как общий inbound preflight принимает реальное IM-сообщение, и до начала обработки команды или агентом. Таким образом, политика прямых/групповых сообщений, упоминаний, списка разрешенных отправителей и отклонения по сопряжению (pairing) происходят до сохранения.

Один и тот же объект `Envelope` записывается не более одного раза. Более позднее сообщение обновляет отметку времени и метки соответствующего отношения. Сохранение выполняется по мере возможности (best-effort): в лог записывается санированная ошибка без идентификаторов, а обработка принятого сообщения продолжается.

Реестр никогда не хранит текст сообщений, ID сообщений, вложения, полезные нагрузки, учетные данные, запросы вебхуков, проактивные отправки или вывод бота.

## Модель отношений

```ts
interface ObservedChannelContactObservation {
  user: { id: string; label: string };
  group?: { id: string; label: string };
  topic?: { id: string; label: string };
}
```

- Прямое сообщение записывает пользователя верхнего уровня по полному платформенному `senderId`.
- Групповое сообщение записывает группу по полному платформенному `chatId` и наблюдаемого пользователя внутри этой группы.
- Тредовое групповое сообщение также записывает топик по `threadId` и наблюдаемого пользователя внутри этого топика.
- Пользователь, замеченный только в группах, не появляется в `users` верхнего уровня. Если тот же пользователь также отправит прямое сообщение, он появляется и на верхнем уровне, и под соответствующими группами.
- `groups[].users` и `groups[].topics[].users` означают пользователей, наблюдаемых в этих беседах. Это не авторитетные списки состава платформы.
- Метки отправителей используют санированное отображаемое имя входящего сообщения с фолбэком на полный ID пользователя. Метки групп используют санированное имя, если его предоставляет принятый входящий конверт; DingTalk отображает `conversationTitle`, а Telegram — `chat.title`. Метки групп Feishu и WeCom, а также все метки топиков откатываются к своим полным ID.

Feishu отображает `root_id` в `threadId`; Telegram отображает `message_thread_id` в `threadId`. Текущие конверты DingTalk и WeCom не предоставляют стабильный идентификатор топика, поэтому их наблюдения останавливаются на уровне группы.

## Свежесть

Люди, беседы и отношения меняются. Read API фильтрует наблюдения, а не представляет реестр как постоянную истину:

- свежесть по умолчанию: семь дней;
- переопределение вызывающим: `freshWithinSeconds`, от 1 секунды до 365 дней;
- отметки времени пользователя, пользователя группы, пользователя топика, группы и топика выводятся независимо из недавних наблюдений;
- пассивное наблюдение не может немедленно обнаружить выход, удаление или переименование, не порождающие новых сообщений, поэтому устаревшие отношения исчезают только когда превышают запрошенное окно.

## Read API

Первичное рабочее пространство:

```http
GET /workspace/channel/observed-contacts?freshWithinSeconds=604800
Authorization: Bearer <daemon token>
```

Выбранное зарегистрированное рабочее пространство:

```http
GET /workspaces/:workspace/channel/observed-contacts?freshWithinSeconds=604800
Authorization: Bearer <daemon token>
```

Пример:

```json
{
  "users": [
    {
      "channelName": "feishu-main",
      "label": "Example User",
      "id": "ou_complete_user_id",
      "lastObservedAt": "2026-07-17T08:00:00.000Z"
    }
  ],
  "groups": [
    {
      "channelName": "feishu-main",
      "label": "oc_complete_chat_id",
      "id": "oc_complete_chat_id",
      "lastObservedAt": "2026-07-17T08:05:00.000Z",
      "users": [
        {
          "label": "Example User",
          "id": "ou_complete_user_id",
          "lastObservedAt": "2026-07-17T08:05:00.000Z"
        }
      ],
      "topics": [
        {
          "label": "om_complete_root_id",
          "id": "om_complete_root_id",
          "lastObservedAt": "2026-07-17T08:05:00.000Z",
          "users": [
            {
              "label": "Example User",
              "id": "ou_complete_user_id",
              "lastObservedAt": "2026-07-17T08:05:00.000Z"
            }
          ]
        }
      ]
    }
  ]
}
```

Ответы используют `Cache-Control: no-store`. Первичный маршрут читает только раздел первичного рабочего пространства. Квалифицированный маршрут требует точный зарегистрированный доверенный рантайм и никогда не откатывается к первичному для неизвестных, недоверенных, загружающихся, дренируемых или удаленных рабочих пространств.

Отсутствующий реестр возвращает пустой граф. Некорректные данные возвращают санированный `500` с кодом `channel_observed_contacts_unavailable`. Удалите файл `observed-contacts.json` рабочего пространства, чтобы сбросить некорректный или неподдерживаемый реестр; принятый трафик создаст его заново. Некорректная свежесть возвращает `400 invalid_freshness`.

Клиенты обнаруживают маршрут через возможность (capability) `workspace_channel_observed_contacts`. Маршрут доступен только для чтения и регистрируется после bearer-аутентификации демона.

## Совместимость

Разбор вебхуков, запросы, разрешение целей и доставка идентичны `main`. Этот API лишь предоставляет наблюдаемые идентификаторы; вызывающие сами решают, как их использовать. Реестр начинается с версии схемы 1, поскольку более ранний прототип с непрозрачными ссылками так и не был выпущен.

## Стратегия тестирования

- Тесты базового канала покрывают границу preflight, нормализацию топиков, дедупликацию Envelope и неблокирующие сбои сохранения.
- Тесты хранилища покрывают семантику прямых сообщений против групповых, отношения групп/топиков, свежесть, обновления, лимиты, разрешения и некорректные данные.
- Тесты маршрутов покрывают полные идентификаторы, ответы no-store, валидацию свежести, точное владение рабочим пространством и санированные сбои.
- Тесты сервера покрывают bearer-аутентификацию и анонсирование возможностей.
- Регрессионные тесты вебхуков проверяют, что поведение не отличается от `main`.
