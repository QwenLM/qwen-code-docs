# Происхождение контекста хука UserPromptSubmit

Issue: https://github.com/QwenLM/qwen-code/issues/7940

## Проблема

Хуки `UserPromptSubmit` могут возвращать `additionalContext`, который клиент
добавляет к исходящему запросу как голую текстовую часть. Поскольку
`recordUserMessage` сохраняет дополненный запрос, инъектированный текст
попадает в `message.parts` записи пользователя и неотличим от текста,
написанного пользователем.

Последствия:

- **Возобновление**: проекция UI конкатенирует все текстовые части, поэтому
  возобновленные сессии отображают инъектированный хуком контекст так, как
  будто его ввел пользователь.
- **Офлайн-анализ / нижестоящие потребители**: JSONL-транскрипт не может
  отделить текст пользователя от инъекции; потребители прибегают к хрупким
  эвристикам вырезания маркеров.
- **Телеметрия и отзыв auto-memory**: оба потребляли
  `partToString(request)` после инъекции, загрязняя атрибут промпта и запрос
  отзыва.

Живой TUI не затронут (он строит свой элемент истории из входа до хука), что
и есть та самая асимметрия, из-за которой загрязненный транскрипт было легко
пропустить.

## Дизайн

Изоморфен двум существующим паттернам: контекст `SessionStart` инъектируется
как тегированный блок в системную инструкцию, а записи mid-turn/notification
разделяют привязанный к модели `message` от проекции
`systemPayload.displayText`.

### Путь записи

1. **Тегированная инъекция** (`client.ts`): санированный `additionalContext`
   добавляется собственной частью, обернутой в
   `<qwen:user-prompt-submit-context>...</qwen:user-prompt-submit-context>`.
   `getAdditionalContext()` экранирует `<`/`>` в выводе хука, поэтому обертка
   не может быть закрыта или подделана изнутри. Текст, написанный
   пользователем, никогда не переписывается и не экранируется. `promptText`
   должен быть объявлен до присваивания инъекции, которое захватывает его в
   `preInjectionPromptText` (избегает TDZ, если окружающий try/catch Goal
   позже перетасуют).
2. **Происхождение отображения** (`chatRecordingService.ts`):
   `recordUserMessage` принимает опциональный
   `UserPromptRecordPayload { displayText? }`, сохраняемый как
   `systemPayload`. `message` хранит точный привязанный к модели Content —
   возобновление должно воспроизводить то, что модель действительно видела, —
   тогда как `displayText` сохраняет проекцию пользователя до инъекции.
   Инъектированный хуком текст остается в тегированном элементе
   `message.parts` (машиночитаемый). Payload записывается только когда хук
   действительно инъектировал контекст.
3. **Телеметрия и отзыв** (`client.ts`): `addUserPromptAttributes` и
   `MemoryManager.recall` используют текст промпта до инъекции, когда
   инъекция произошла.

### Путь чтения (проекция возобновления)

`resumeHistoryUtils` проецирует обычные записи пользователя через фолбэк из
трех форм:

- (a) новые записи: предпочитать `systemPayload.displayText`;
- (b) записи только с тегом (без payload): отбрасывать хвостовую часть,
  которая целиком представляет собой тегированный блок — только строгое
  совпадение всей части, поэтому проза пользователя, которая лишь содержит
  тег, никогда не вырезается. Единственная часть, соответствующая форме тега,
  также сохраняется (инъекция всегда добавляется после собственных частей
  пользователя, поэтому запись из одной части может быть только авторства
  пользователя);
- (c) легаси-записи с голой инъекцией: неизменная конкатенация.

Ветка возобновления `@`-команд по-прежнему предпочитает
`AtCommandRecordPayload.userText`, когда он присутствует; только фолбэк при
отсутствующем `userText` проходит через `extractUserRecordDisplayText`,
поэтому хвостовая тегированная часть не переопределяет отображаемый текст
`@`-команды.

## Заметки по области

- Сфокусировано на интерактивном пути `UserPromptSubmit`. Путь сессии ACP уже
  записывает текст промпта до инъекции, поэтому ему требовалась только та же
  обертка тегом для его инъекции, привязанной к модели (включено здесь).
  Инъекция контекста субагента (`SubagentStart` через `contextState`) требует
  собственного исследования и является follow-up.
- Другие потребители транскрипта (desktop, web UI) могут принять `displayText`
  в follow-up; до этого они видят тегированную форму, которая по крайней мере
  механически идентифицируема.

Потребители ACP/экспорта/демона, проходящие через `projectUserRecord` из
`transcript-replay`, также предпочитают `displayText` и вырезают хвостовую
тегированную часть для записей пользователя без подтипа (тот же фолбэк из
трех форм, что и путь возобновления TUI).
