# Явное одобрение выхода из плана

## Проблема

`exit_plan_mode` ранее смешивал одобрение и исполнение. Его колбэк
подтверждения изменял `ApprovalMode` до завершения хуков и исполнения, а
сессии AUTO/YOLO могли обойти пользователя через LLM Plan Approval Gate.
Правила разрешения permission-менеджера, хуки разрешений и автоодобрение
соседей также могли удовлетворить решение `ask` без фактического ответа
хоста/пользователя. Это делало вызов инструмента, порожденный моделью,
способным попытаться покинуть Plan mode без решения пользователя и создавало
вводящие в заблуждение уведомления о режиме, когда последующее исполнение не
удавалось.

## Дизайн

Вызовы инструментов могут объявлять `requiresUserInteraction()`. Это
внутреннее требование взаимодействия, а не другой уровень разрешений:
отказы — внутренние или permission-менеджера — все равно выигрывают, тогда
как правила разрешения и автоматические режимы одобрения не могут его
удовлетворить. `exit_plan_mode` основной сессии объявляет это требование.
Тиммейты, для которых требуется план, сохраняют свой путь одобрения лидером,
а обычные субагенты сохраняют существующее отклонение инструментов
жизненного цикла.

Колбэк подтверждения плана записывает только одно из четырех решений:
восстановить режим до плана, переключиться на auto-edit, переключиться на
default или отменить. Он никогда не меняет режим. Создание подтверждения
замораживает текст плана, режим до плана и текущую ревизию режима одобрения.
`execute()` проверяет, что одобрение существует, сигнал активен, сессия все
еще в Plan mode и ревизия все еще совпадает, прежде чем синхронно применить
переход режима. Это заставляет устаревшие, повторные и одновременные выходы
завершаться fail closed. Персистенция плана выполняется по мере возможности
(best-effort) только после успешного перехода.

`Config` владеет монотонной ревизией режима одобрения, которая
инкрементируется, только когда режим фактически меняется. Переопределения
режима одобрения владеют независимыми ревизиями. Существующий опциональный
аргумент сеттера `enteredByModel` временно остается как игнорируемый
параметр совместимости; происхождение от модели не влияет на одобрение.

LLM Plan Approval Gate и его связка с метаданными AskUserQuestion удаляются.
`prePlanMode` остается, потому что это видимый пользователю выбор выхода.
`originalRequest` и `researchSummary` остаются для ревью лидером тиммейтов,
для которых требуется план. `resolutionSummary` остается только как
deprecated входное свойство TypeScript для совместимости исходников и больше
не принимается схемой рантайма.

## Поведение хоста

Подтверждения CLI и IDE, `requestPermission` ACP и ответы разрешения
`can_use_tool` stream-json считаются явным взаимодействием. Хуки разрешения
PermissionRequest, правила разрешения PM, YOLO/AUTO/AUTO_EDIT и автоодобрение
соседей — не считаются. Решения отказа хуков остаются авторитетными.
Неинтерактивные вызывающие без хоста, способного одобрять, завершаются
fail closed.

ACP не отправляет обновление режима, когда разрешение ожидает, или когда
подтверждение, хуки, исполнение или переход не удаются. После успешного
исполнения жизненного цикла плана и фактического изменения режима он
отправляет одно обновление, используя режим, прочитанный из `Config`. Отказ
legacy-уведомления является рекомендательным, и боковой канал расширения все
равно пробуется с точным значением `legacyFrameSent`.

## Поведение при отказах

- Вызовы вне Plan mode безопасно завершаются с применимым к действию
  руководством по состоянию на той границе, которая наблюдает изменение
  режима. `execute()` возвращает ошибку с руководством, когда сессия вне
  Plan mode и нет снимка одобрения. `getConfirmationDetails()` бросает то же
  руководство при вызове вне Plan mode (например, через правило `ask` PM или
  переключение Plan-в-не-Plan между вычислением разрешения и построением
  подтверждения). Разрешение по умолчанию — `allow`; это проблема состояния,
  а не безопасности.
- Невалидные исходы подтверждения, отмена, прерывания, устаревшие ревизии и
  отказы перехода оставляют Plan mode активным.
- Два выхода, одобренные против одной ревизии, не могут оба succeed.
- Если хост ACP не может представить `switch_mode`, Plan mode остается
  активным, а ошибка направляет пользователя к селектору режима хоста или
  `/plan exit`.
- Сохранение уже одобренного плана выполняется по мере возможности и не
  откатывает успешный переход режима.

## Совместимость и область

Это изменение намеренно не расширяет общее исполнение shell в Plan mode и не
добавляет специфичные для DataWorks инструменты чтения. Это отдельные
изменения разрешений/инструментария. Публичный метод вызова опционален со
значением по умолчанию `false`, поэтому существующие инструменты и внешние
реализации остаются совместимыми.
