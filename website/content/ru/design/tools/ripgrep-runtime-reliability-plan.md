# План реализации надёжности рантайма Ripgrep

## 1. Предпосылки и решения

Когда ripgrep отсутствует, Qwen Code уже предоставляет основную цепочку фолбэков:

```text
встроенный ripgrep -> системный ripgrep -> GrepTool
                                          -> git grep
                                          -> системный grep
                                          -> обход файлов на JavaScript
```

Оставшаяся работа с высоким ROI — обеспечить целостность результатов во время выполнения, а не вводить ещё одну бинарную зависимость или ещё один общий слой фолбэков. Этот план реализует четыре связанных улучшения как одно изменение с чёткими границами:

1. Когда подтверждено, что ripgrep получил ошибку `EAGAIN` при создании потоков, повторить один раз в однопоточном режиме.
2. Интерпретировать код выхода 1 как «нет совпадений» только когда и stdout, и stderr пусты.
3. Различать неполное выполнение поиска и обычное усечение вывода; никогда не сообщать о неполностью выполненном поиске как о «совпадений не найдено».
4. Записывать не затрагивающую приватность телеметрию восстановления рантайма, чтобы измерить реальную пользу.

### Вне области действия

- Не вводить `@vscode/ripgrep`; Qwen Code уже поставляет бинарные файлы для разных платформ вместе с пакетом.
- Не менять текущий порядок выбора «сначала встроенная версия, затем системная версия».
- Не снижать навсегда число потоков ripgrep.
- Не переключаться автоматически на `GrepTool` после каждого сбоя рантайма. Ошибки разрешений, аргументов и файловой системы должны оставаться видимыми, а не прятаться за семантически отличающимся и более медленным поиском.
- Не повторять `EAGAIN` на фазе запуска дочернего процесса Node.js. Процесс, который ещё не успешно запустился, не может выиграть от аргумента ripgrep `--threads 1`; такие проблемы по-прежнему должны обрабатываться как явные сбои `spawn`.

## 2. Цель изменений и поведение до/после

Это изменение не для того, чтобы поиск «никогда не ломался», а чтобы Qwen Code мог точно различать три факта: совпадений действительно нет; поиск не удался и доступных результатов нет; поиск не удался, но дал частичные результаты. Только видя правильные факты, модель может решить, сузить ли поиск, использовать другой инструмент или продолжить с имеющимися частичными результатами.

### 2.1 Однопоточная повторная попытка при EAGAIN

**Цель изменения:** в ресурсно-ограниченных контейнерах или средах CI процесс ripgrep может успешно запуститься, но не суметь создать нужные рабочие потоки. В этом случае логика поиска и параметры сами по себе корректны, и после снижения параллелизма поиск обычно всё ещё может завершиться. Повторная попытка применяется только к подтверждённым сбоям создания потоков, чтобы ошибки параметров, ошибки разрешений или сбои запуска дочернего процесса ошибочно не считались восстанавливаемыми проблемами.

**До:** `RipGrepTool` фиксированно передаёт `--threads 4`. `runRipgrep()` не повторяет попытку при EAGAIN: если эта ошибка сначала не интерпретируется веткой кода выхода 1 как отсутствие совпадений и stdout отсутствует, инструмент возвращает модели явную ошибку grep; если stdout уже был получен, последующая логика может продолжить потреблять эти частичные результаты, но не сообщит, что этот поиск был досрочно прерван из-за EAGAIN.

```text
rg --threads 4
  -> сбой создания потоков
  -> без повторной попытки
  -> код выхода 1: трактуется как нет совпадений
  -> другая ошибка без stdout: возвращается ошибка
  -> есть stdout: может быть использован как полный результат
```

**После:** только когда по stderr подтверждено, что это EAGAIN создания потоков внутри ripgrep, и запрос ещё не отменён, `--threads 4` текущего вызова заменяется на `--threads 1` и выполняется одна повторная попытка. После успешной повторной попытки возвращается полный результат; если повторная попытка всё равно не удалась, возвращается ошибка или явно помеченный частичный результат. Последующие поиски по-прежнему используют 4 потока и не замедляются навсегда из-за одного временного сбоя.

```text
rg --threads 4
  -> подтверждён EAGAIN создания потоков
  -> rg --threads 1, повторить только один раз
     -> успех: возвращается полный результат
     -> сбой без stdout: возвращается явная ошибка
     -> сбой с stdout: возвращается явно помеченный частичный результат
```

### 2.2 Ужесточение определения «нет совпадений» по коду выхода 1

**Цель изменения:** не дать Qwen Code трактовать любой код выхода 1 с сообщениями об ошибках или аномальным выводом как «этого контента в репозитории нет». «Нет совпадений» — сильное заключение, влияющее на дальнейшие рассуждения модели, и его можно использовать только когда ripgrep действительно штатно сообщает об отсутствии совпадений.

**До:** `runRipgrep()` при виде `error.code === 1` сразу возвращает пустой stdout и отбрасывает stdout и stderr этого вызова. Даже если код выхода 1 сопровождается сообщением об ошибке, модель в итоге видит `No matches found`.

```text
код выхода 1 + пустой stdout + пустой stderr -> No matches found
код выхода 1 + непустой stderr                -> No matches found
код выхода 1 + непустой stdout                -> stdout отбрасывается, No matches found
```

**После:** штатный результат «нет совпадений» возвращается только когда код выхода равен 1 и stderr пуст. Код выхода 1 с непустым stderr обрабатывается как сбой выполнения. stdout не участвует в определении: код выхода 1 ripgrep не может нести результаты совпадений, а в режиме `--json` ripgrep даже при нуле совпадений выводит в конце stdout событие summary.

```text
код выхода 1 + пустой stderr   -> No matches found
код выхода 1 + непустой stderr -> явная ошибка выполнения
```

### 2.3 Различение усечённых результатов и неполного выполнения

**Цель изменения:** дать модели понять, что «для контроля длины вывода показана только часть» и «нижележащий поиск не завершился» — две совершенно разные вещи. Первое всё ещё доказывает, что эти совпадения существуют в полном поиске; второе нельзя использовать как доказательство отсутствия совпадений в других файлах.

**До:** `runRipgrep()` использует `truncated` одновременно для нижележащих завершений вроде тайм-аута и превышения максимального буфера, а `RipGrepTool` объединяет его с лимитами строк и символов при отображении. Когда произошла ошибка, но stdout уже получен, инструмент бросает ошибку только если stdout пуст; непустой stdout продолжает разбираться. Это может выглядеть как обычный результат, `(truncated)` или даже попасть в одну из двух веток `No matches found`, когда stdout пуст или не разобрано ни одного валидного совпадения. Модель не может надёжно определить, действительно ли поиск завершился.

**После:** обрезка на уровне отображения использует только `truncated`; досрочные завершения из-за тайм-аута, превышения максимального буфера или других ошибок выполнения используют `incomplete`. Порядок обработки сначала определяет полноту выполнения, затем наличие валидных совпадений:

| Результат выполнения после изменения        | Что видит модель                             | Какой вывод может сделать модель                             |
| ------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| Полное выполнение без совпадений            | `No matches found`                           | Можно считать, что в области этого поиска совпадений нет     |
| Полное выполнение, но показ превышает лимит | Результат с `(truncated)`                    | Поиск завершён, просто показаны не все строки совпадений     |
| Неполное выполнение без валидных совпадений | Явная ошибка незавершённого поиска           | Нельзя считать, что в репозитории нет совпадений; нужно скорректировать поиск или использовать другой метод |
| Неполное выполнение с валидными совпадениями | Частичный результат с `(incomplete)` и фиксированным предупреждением | Можно использовать возвращённые совпадения, но нельзя исключать другие места |
| Одновременно обрезка показа и неполное выполнение | Показываются и `(truncated)`, и `(incomplete)` | Не показаны все полученные результаты, и нижележащий поиск не завершён |

### 2.4 Телеметрия восстановления рантайма

**Цель изменения:** измерять частоту возникновения, успешность и типы сбоев повторных попыток при EAGAIN и защиты целостности результатов в реальных средах, чтобы на основе данных решать, стоит ли дальше вкладываться в более сложные возможности фолбэков рантайма, избегая при этом сбора пользовательских запросов и информации о репозитории.

**До:** существующее `RipgrepFallbackEvent` отправляется только при сбое стартового зонда, когда Qwen Code переключается с `RipGrepTool` на `GrepTool`. Для происходящих после запуска EAGAIN, тайм-аутов, превышений максимального буфера, аномальных завершений или сбоев spawn нет специальных структурированных метрик, поэтому невозможно ответить, «действительно ли восстановление рантайма полезно».

**После:** добавляется семантически независимое `RipgrepRuntimeRecoveryEvent`, отправляемое только при повторной попытке или финальном аномальном завершении. Событие записывает выбор встроенного/системного бинарного файла, была ли повторная попытка, увенчалась ли она успехом и фиксированную классификацию сбоя, но не записывает выражение поиска, пути, stdout, stderr, имена файлов или исходное сообщение об ошибке. Обычные успешные поиски событие не отправляют, чтобы не увеличивать объём логов без смысла.

### 2.5 Защита одиночного урегулирования

**Цель изменения:** гарантировать, что новая логика повторной попытки выполняется максимум один раз. Колбэк `execFile` и событие `error` дочернего процесса могут прибыть один за другим для одного и того же сбоя запуска; если оба канала независимо решат повторить, могут запуститься два однопоточных поиска.

**До:** оба канала могут попытаться урегулировать один и тот же Promise. Поскольку Promise принимает только первое урегулирование, а логики повтора пока нет, видимого пользователю дублирующегося выполнения обычно не возникает, но такая структура не подходит для прямого добавления ветки восстановления.

**После:** хелпер однократного выполнения использует общий settlement guard и производит один структурированный результат выполнения. Внешняя логика должна дождаться этого результата, прежде чем решать, повторять ли попытку, поэтому один поиск запускает максимум один вызов восстановления.

### 2.6 Общее изменение поведения

```text
До
выполнение rg
  -> код 0: обработать результат
  -> код 1: всегда трактуется как нет совпадений
  -> другая ошибка без stdout: возвращается ошибка
  -> другая ошибка с stdout: может обрабатываться дальше как полный или усечённый результат

После
выполнение rg
  -> код 0: обработать полный результат
  -> код 1 + stdout/stderr оба пусты: подтверждено отсутствие совпадений
  -> подтверждён EAGAIN потоков: одна повторная попытка в однопоточном режиме
  -> финальный сбой без stdout: возвращается явная ошибка
  -> финальный сбой с stdout: сохранить пригодные совпадения и пометить incomplete
  -> финальное исключение или восстановление (кроме отмены): отправить структурированную телеметрию без контента запроса
```

## 3. Обязательные семантики рантайма

### 3.1 Результат однократного выполнения

Отрефакторить `runRipgrep()` в `packages/core/src/utils/ripgrepUtils.ts`, выделив внутренний хелпер однократного выполнения. Этот хелпер должен сохранить существующие поведение: буфер 20 МБ, платформенно-зависимый тайм-аут, `AbortSignal`, частичный stdout и удаление потенциально неполной последней строки.

Хелпер должен гарантировать только одно урегулирование. `execFile` может сообщить о сбое запуска одновременно через колбэк и через событие `error` дочернего процесса, поэтому обработка колбэка и события должна использовать одну и ту же защиту урегулирования. Решение о повторной попытке может быть принято только после того, как первый вызов хелпера вернул результат; ни один из каналов завершения не должен напрямую запускать повтор.

Классифицировать сбои фиксированными значениями без чувствительной информации:

```typescript
type RipgrepFailureKind =
  | 'eagain'
  | 'timeout'
  | 'max_buffer'
  | 'exit'
  | 'spawn';
```

Отмена не относится к телеметрии сбоев рантайма и не должна запускать повторную попытку.

### 3.2 Определение отсутствия совпадений

Только когда одновременно выполнены оба следующих условия, вызов интерпретируется как успешно завершённый, но без совпадений:

```text
код выхода === 1
stderr.trim() === ''
```

Соглашение кодов выхода ripgrep: 0 = совпадения найдены, 1 = нет совпадений без ошибки, 2 = ошибка. Код выхода 1 не может нести результаты совпадений, поэтому проверять stdout не нужно. В режиме `--json` ripgrep даже при нуле совпадений выводит в конце stdout событие `summary`, поэтому пустота stdout не может быть критерием.

Код выхода 1 с непустым stderr относится к сбоям выполнения.

### 3.3 Восстановление при EAGAIN

Повторять попытку один раз, только когда одновременно выполнены все следующие условия:

- Сейчас первое выполнение, а не повтор.
- Запрос ещё не отменён.
- stderr подтверждает сбой создания потоков внутри ripgrep: совпадение с короткой меткой `os error 11`, либо требование, чтобы контекст создания потоков и полное сообщение об ошибке недоступности ресурсов присутствовали одновременно. Нельзя совпадать только с общим текстом недоступности ресурсов.
- Текущий список аргументов содержит текущую пару аргументов `--threads 4`.

При повторе значение числа потоков заменяется на `1`. Не добавлять задержку, не поддерживать другие варианты написания аргументов без реальной необходимости и не делать однопоточный режим постоянным для последующих поисков. После успешного повтора возвращается полный успешный результат без сохранения ошибки или неполного состояния первой попытки.

### 3.4 Полное выполнение, усечение и неполное выполнение

Явно различать три следующих состояния:

- **Полное (Complete):** ripgrep штатно завершил выполнение.
- **Усечение (Truncated):** Qwen Code ради отображения активно ограничил изначально полный вывод по числу строк или символов.
- **Неполное выполнение (Incomplete):** ripgrep после получения stdout завершился из-за ошибки выполнения, включая завершения по тайм-ауту и превышению максимального буфера; имеющиеся совпадения — лишь часть результатов поиска по репозиторию.

Расширить `RipgrepRunResult`, используя структурированные метаданные вместо сырого stderr или текста ошибки:

```typescript
interface RipgrepRecoveryMetadata {
  selectionMode: 'builtin' | 'system';
  retryTriggered: boolean;
  retrySucceeded?: boolean;
  failureKind?: RipgrepFailureKind;
}

interface RipgrepRunResult {
  stdout: string;
  incomplete: boolean;
  error?: Error;
  recovery: RipgrepRecoveryMetadata;
}
```

При реализации конкретную структуру можно упростить, но результат утилиты не должен продолжать использовать текущее поле `truncated` для сбоев тайм-аута или превышения максимального буфера. Усечение отображения вычисляется `RipGrepTool`; утилита отвечает за сообщение о неполном выполнении и результате повтора. Метаданные восстановления не должны содержать выражение поиска, пути поиска, stdout, stderr или исходное сообщение об ошибке.

В `packages/core/src/tools/ripGrep.ts` сначала необходимо определить, было ли выполнение полным, и только потом входить в существующие две ветки `No matches found`:

| Результат выполнения                                  | Поведение инструмента                                  |
| ----------------------------------------------------- | ------------------------------------------------------ |
| Ошибка и нет stdout                                    | Вернуть явную ошибку выполнения grep                   |
| Ошибка с stdout, но не разобрано ни одного валидного совпадения | Вернуть явную ошибку неполного выполнения поиска; никогда не возвращать отсутствие совпадений |
| Ошибка и разобрано хотя бы одно валидное совпадение    | Вернуть частичные совпадения с фиксированным пояснением о незавершённом поиске |
| Полное выполнение без валидных совпадений              | Вернуть существующий результат отсутствия совпадений   |

Частичный результат использует `(incomplete)` в `returnDisplay` и выводит LLM фиксированное пояснение, например: `Поиск выполнен не полностью: результаты выше могут содержать не все совпадения.` Обычные лимиты на количество результатов продолжают использовать `(truncated)`. Эти две метки могут присутствовать одновременно, но не могут заменять друг друга. При сбое выполнения не должно продолжать появляться текущее вводящее в заблуждение сообщение `[0 lines truncated]`.

## 4. Телеметрия рантайма

Добавить независимое `RipgrepRuntimeRecoveryEvent`; не переиспользовать `RipgrepFallbackEvent`, которое специально означает переключение зарегистрированного на этапе запуска инструмента с `RipGrepTool` на `GrepTool`.

Новое событие отправляется только при повторной попытке или финальном аномальном завершении. Обязательные поля:

```typescript
selection_mode: 'builtin' | 'system';
retry_triggered: boolean;
retry_succeeded?: boolean;
failure_kind: 'eagain' | 'timeout' | 'max_buffer' | 'exit' | 'spawn';
```

Нельзя записывать выражение поиска, пути, stdout, stderr, исходное сообщение об ошибке или имена файлов. Обычный успешный поиск без восстановления новое событие не отправляет.

`ripgrepUtils.ts` по-прежнему не зависит от `Config` и телеметрии. Она лишь возвращает метаданные восстановления; `RipGrepTool.performRipgrepSearch()`, владеющий `Config`, отправляет событие перед возвратом частичного результата или бросанием финальной ошибки.

Подключить это событие через существующий слой телеметрии:

- `packages/core/src/telemetry/types.ts`
- `packages/core/src/telemetry/constants.ts`
- `packages/core/src/telemetry/loggers.ts`
- `packages/core/src/telemetry/qwen-logger/qwen-logger.ts`
- публичные экспорты телеметрии в `packages/core/src/telemetry/index.ts`

Покрыть существующие пути Qwen logger и логов OpenTelemetry. Не нужно проектировать отдельную интеграцию Clearcut.

## 5. Порядок реализации

1. Добавить хелпер однократного выполнения и каркас сфокусированных модульных тестов с mock'ом `execFile`, включая `EventEmitter` дочернего процесса и поведение одиночного урегулирования.
2. Ужесточить определение кода выхода 1 и добавить классификацию сбоев, пока не меняя поведение повтора.
3. Добавить однократный повтор для подтверждённого EAGAIN потоков, заменяя `--threads 4` на `--threads 1`.
4. Пробросить структурированный `incomplete` и метаданные восстановления из `runRipgrep()` в `RipGrepTool`.
5. Обновить две точки определения отсутствия совпадений, чтобы отдельно рендерить сообщения о неполном выполнении и об усечении.
6. Добавить на уровне инструмента и подключить независимое событие телеметрии восстановления рантайма.
7. Запустить сфокусированную верификацию, затем выполнить требуемые репозиторием build, typecheck и процесс саморевью.

Сохранение этих шагов независимыми помогает быстро локализовать регрессии и не даёт телеметрической работе затенить основные изменения семантики результатов.

## 6. План тестирования

### `packages/core/src/utils/ripgrepUtils.test.ts`

Использовать Vitest hoisted mock для имитации `node:child_process` и покрыть:

- Код выхода 1 с пустыми stdout и stderr даёт полный результат отсутствия совпадений.
- Код выхода 1 с непустым stderr даёт сбой `exit`.
- Код выхода 1 с непустым stdout сохраняет stdout и помечается как неполное выполнение.
- После подтверждения EAGAIN потоков повторяется один раз и успешно завершается с `--threads 1`.
- После подтверждения EAGAIN потоков повторяется один раз, но повтор всё равно не удаётся.
- Повтор заменяет только текущее число потоков и не изменяет массив аргументов, переданный вызывающей стороной.
- `AbortError`/`ABORT_ERR` не запускает повтор.
- `EAGAIN` на фазе запуска дочернего процесса не запускает повтор и классифицируется как `spawn`.
- При тайм-ауте и превышении максимального буфера из частичного вывода удаляется потенциально неполная последняя строка.
- Колбэк и событие `error` дочернего процесса не могут вызвать повторное урегулирование или два повтора.

### `packages/core/src/tools/ripGrep.test.ts`

Покрыть семантику для вызывающих инструмент сторон:

- Полное выполнение с пустым выводом по-прежнему возвращает `No matches found`.
- Неполное выполнение с валидными совпадениями возвращает эти совпадения и явное сообщение о незавершённости.
- Неполное выполнение, чей stdout не дал ни одного валидного совпадения, возвращает ошибку неполного выполнения, а не `No matches found`.
- Ошибка без stdout по-прежнему возвращает явную ошибку выполнения grep.
- Метки усечения и неполного выполнения остаются независимыми и могут присутствовать одновременно.

### Тесты телеметрии

Расширить тесты logger и Qwen logger, проверив:

- Событие успешного повтора содержит режим выбора, статус срабатывания, статус успеха и классификацию EAGAIN.
- Финальный аномальный результат содержит фиксированную классификацию сбоя.
- Обычный успешный поиск не производит событие восстановления рантайма.
- Имя события OpenTelemetry, body и атрибуты Qwen logger корректны.
- В событии нет выражения поиска, путей, stdout, stderr или полей исходной ошибки.

## 7. Верификация и критерии приёмки

В соответствии с требованиями `AGENTS.md` запустить из соответствующего пакета или корня репозитория:

```bash
cd packages/core && npx vitest run src/utils/ripgrepUtils.test.ts
cd packages/core && npx vitest run src/tools/ripGrep.test.ts
cd packages/core && npx vitest run src/telemetry/loggers.test.ts
npm run typecheck
npm run build
```

Если реализация меняет выделенные тесты Qwen logger за пределами `loggers.test.ts`, необходимо также запустить соответствующие сфокусированные файлы тестов.

Изменение можно считать завершённым, только когда выполнены следующие условия:

- Один подтверждённый EAGAIN потоков ripgrep запускает максимум один однопоточный повтор.
- Отмена и сбой запуска дочернего процесса никогда не запускают этот повтор.
- Только код выхода 1 с пустым stderr означает отсутствие совпадений (stdout не проверяется).
- Ни один путь неполного выполнения не может попасть в две ветки возврата `No matches found`.
- Частичные совпадения по-прежнему полезны модели, но должны быть явно помечены как неполное выполнение.
- Телеметрия способна измерять восстановление, не собирая контент запросов или репозитория.
- Сфокусированные тесты, typecheck и build полностью проходят.
- Полный diff саморевьюирован в соответствии с требованиями репозитория, и после последней правки подряд выполнены две проверки без проблем.

## 8. Стоимость, польза и откат

Оценка стоимости реализации — примерно 1,5–3 рабочих дня инженера, включая тесты и подключение телеметрии. Область намеренно держится меньше, чем общий рефакторинг фолбэков рантайма.

Прямая польза включает:

- Когда ripgrep не может создать штатное число рабочих потоков, поиск может восстановиться в ресурсно-ограниченных средах CI или контейнерах.
- Устранение ложных отрицательных результатов, когда код выхода 1 сопровождается ошибкой.
- Устранение проблемы, когда частичные результаты поиска маскируются под полные доказательства по репозиторию.
- Получение продакшен-данных для решения, стоит ли дальше вкладываться в другие возможности восстановления.

Область отката локальна: можно удалить ветку повтора и событие рантайма без изменения выбора бинарного файла или существующей логики стартового фолбэка. Даже при откате самого повтора следует сохранить более строгое определение отсутствия совпадений и семантику неполного выполнения, поскольку их защита корректности не зависит от фактической частоты EAGAIN.

## 9. Учтённые замечания ревью

Один субагент уже отревьюировал этот план по текущему исходному коду репозитория. Его ревью внесло следующие существенные корректировки в первоначальный черновик:

- не переиспользовать телеметрию стартового фолбэка, вместо этого независимое событие рантайма;
- переместить точку отправки телеметрии из слоя утилиты в `RipGrepTool`;
- убрать спекулятивный повтор с задержкой для `EAGAIN` на фазе запуска дочернего процесса;
- сузить обнаружение EAGAIN до подтверждённых сбоев создания потоков;
- убрать поддержку отсутствующего аргумента потоков и других вариантов написания аргументов, которые сейчас невозможны;
- различать `incomplete` и `truncated`;
- требовать проверку полноты выполнения перед двумя ветками отсутствия совпадений;
- требовать, чтобы определение отсутствия совпадений по коду выхода 1 опиралось на пустоту stderr (без проверки stdout);
- добавить регрессионные тесты одиночного урегулирования и нуля валидных совпадений;
- вернуть шаги build репозитория, необходимые для будущей верификации реализации.
