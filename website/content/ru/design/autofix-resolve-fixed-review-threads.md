# Укрепление резолвинга review-тредов в Autofix

## Проблема

Qwen Autofix уже позволяет агенту обработки ревью идентифицировать inline-комментарии ревью, которые резолвятся в коде. Привилегированный хост-воркфлоу мапит эти ID REST-комментариев на review-треды GitHub и вызывает `resolveReviewThread` после пуша фикса.

Текущий порядок в целом безопасен, но он не доказывает, что живой head PR, который резолвится, — это в точности тот коммит, который покрыт детерминированной верификацией:

- Отклоненный пуш может быть спасен слиянием свежеподвинутого удаленного head. Слитый коммит пушится, даже если верификация предшествовала слиянию.
- Автор PR может запушить снова после пуша Autofix и до мутации резолвинга.
- Ремонт в том же запуске может унаследовать `resolved-comments.txt` или `comment-replies.json` от отклоненной первой попытки.

Эти пробелы могут пометить обсуждение resolved без доказательств, что текущий head PR все еще содержит верифицированный фикс.

## Текущее состояние

Ответственности уже разделены корректно:

- `.qwen/skills/autofix/SKILL.md` говорит агенту, как классифицировать находки и писать `resolved-comments.txt` или `comment-replies.json`.
- `.github/scripts/run-autofix-review-verification.sh` независимо запускает детерминированные build, typecheck, lint и тесты затронутых пакетов.
- `.github/workflows/qwen-autofix.yml` владеет GitHub PAT, пушит ветку, выкачивает review-треды и выполняет мутации.
- `scripts/tests/qwen-autofix-workflow.test.js` извлекает и выполняет shell-блоки воркфлоу с заглушенными ответами GitHub.

Мутация GitHub должна оставаться в доверенном воркфлоу. Агент не должен получать учетные данные GitHub.

## Предлагаемые изменения

### Гейт верификации

Требовать чистые отслеживаемые worktree и индекс перед детерминированными проверками, фиксировать SHA коммита и требовать, чтобы и SHA, и отслеживаемое состояние оставались неизменными после структурных проверок и снова после build, typecheck, lint и тестов. Затем записывать этот зафиксированный SHA как выход шага с именем `verified_head`. Не выпускать его для no-op или неудачных исходов. Это отклоняет устойчивые отслеживаемые изменения или коммиты, созданные контролируемыми веткой проверками; это не заявляет неизменную файловую систему и не детектирует скрипт, который временно меняет состояние и восстанавливает его в пределах одной команды, — это остается частью существующей модели доверия CI.

### Выбор финальной верификации

Пропускать выбранный SHA верификации через шаг финальной верификации:

- использовать первый SHA верификации, когда ремонт не выполнялся;
- использовать только SHA верификации ремонта, когда ремонт выполнялся;
- никогда не фолбэкаться на первый SHA для успешного отремонтированного исхода.

### Изоляция ремонта

Перед вызовом агента ремонта удалять `resolved-comments.txt` и `comment-replies.json` вместе с прочими артефактами предыдущих попыток. Попытка ремонта должна явно перегенерировать свои финальные disposition. Отсутствие файлов поэтому приводит к fail closed: ни один тред не резолвится и не получает ответа.

### Доказательство резолвинга после пуша

Перед резолвингом любого выбранного треда требовать все из следующего:

1. `verified_head` непуст.
2. Спасение от push-гонки не создало неверифицированный merge-коммит.
3. Локальный `HEAD` после успешного пуша равен `verified_head`.
4. Живой запрос `gh pr view` выполняется успешно.
5. Живой `headRefOid` PR равен `verified_head` перед каждой мутацией.
6. Живой `headRefOid` PR все еще равен `verified_head` сразу после каждой мутации.

Перед каждой мутацией единый GraphQL-гвард читает и живой `headRefOid`, и живое состояние `isResolved` целевого треда. Тред, уже резолвленный другим актором, пропускается. После мутации тот же гвард снова проверяет оба значения. Эта пост-проверка выполняется даже когда команда мутации возвращает ошибку, потому что потерянный ответ не доказывает, что GitHub не применил мутацию.

Если предусловие перед мутацией неизвестно или ложно, либо постмутационное условие неоднозначно — прекратить резолвить дополнительные обсуждения. Неудачную мутацию, чей пост-гвард доказывает, что верифицированный head не изменился и тред остается открытым, безопасно сопроводить предупреждением и продолжить. Воркфлоу не вызывает `unresolveReviewThread`: GitHub не выставляет предусловие compare-and-swap и атрибуцию мутаций, так что даже успешный ответ `resolveReviewThread` не может доказать, что другой актор не резолвил тред между пре-гвардом и мутацией. Автоматическое повторное открытие поэтому могло бы отменить действие другого ревьюера. Неуспешная команда мутации, за которой следует пост-гвард, подтверждающий верифицированный head и резолвленное состояние, считается наблюдением резолвленного состояния без атрибуции Autofix; любой неоднозначный результат останавливает оставшиеся мутации.

Пуш верифицированного кода и обычный отчет по раунду по-прежнему проходят успешно. Ответы для находок, намеренно оставленных открытыми, могут продолжаться после успешного пуша, потому что они не утверждают, что тред исправлен.

## Проектные решения

- **Fail closed для резолвинга:** нерезолвленный тред восстановим; некорректно резолвленный тред может скрыть реальный дефект.
- **Пропускать резолвинг после merge из-за гонки:** повторный прогон полного детерминированного гейта внутри publish-шага, несущего PAT, задублировал бы дорогую логику и выполнял бы контролируемые веткой скрипты с учетными данными в области видимости. Более поздний раунд ревью может безопасно резолвить тред.
- **Запрашивать живое состояние PR непосредственно перед мутацией:** конкурентность воркфлоу не может предотвратить прямые пуши контрибьюторов.
- **Сохранять существующий контракт disposition модели:** семантическое суждение остается за агентом, тогда как точная идентичность коммита обеспечивается детерминированно хостом.
- **Не добавлять общий код CLI/core:** это оркестрация воркфлоу Autofix, а не переиспользуемая рантайм-функция Qwen Code.

## Границы области действия

Включено:

- точное равенство верифицированного/живого head;
- поведение fail-closed при push-гонке;
- изоляция disposition попыток ремонта;
- сфокусированные контракт воркфлоу и поведенческие тесты.

Исключено:

- пагинация GraphQL за пределами существующих первых 100 тредов;
- резолвинг произвольных не-Autofix обсуждений PR;
- dismissal ревью `CHANGES_REQUESTED`;
- выдача модели прямых учетных данных GitHub;
- изменение общего поведения `/review` или CLI.

## Открытые вопросы

Нет. Консервативное поведение детерминировано до мутации: неопределенность предотвращает резолвинг дополнительных тредов. После мутации воркфлоу наблюдает и сообщает состояние, но никогда автоматически не аннулирует резолвинг без доказательств атомарного владения.
