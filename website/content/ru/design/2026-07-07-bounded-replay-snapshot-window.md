# Ограниченное окно снимков воспроизведения

## Проблема

Активные сессии демона в настоящее время хранят историю воспроизведения в памяти, чтобы `POST /session/:id/load` мог внедрить воспроизведение для клиентов, подключающихся после того, как сессия уже существует. Это хранение воспроизведения должно быть ограничено независимо от кольца SSE: восстановление в режиме ответа может массово загружать большие исторические обновления, а завершенные ходы в реальном времени могут накапливаться неограниченно в долгоживущих сессиях.

История сессий на диске остается авторитетным источником полного транскрипта. PR-1 ограничивает только окно воспроизведения демона в памяти в реальном времени; он не добавляет эндпоинт полного транскрипта.

## Цели

- Ограничить сохраняемые события воспроизведения по объему сериализованных байтов на каждую активную сессию, со значением по умолчанию 4 МиБ и отклонением недопустимой конфигурации при запуске.
- Применить лимит как к сегментам воспроизведения завершенных ходов в реальном времени, так и к восстановленному историческому воспроизведению в режиме ответа или потоковом режиме.
- Сохранить существующую форму снимка в протоколе: `compactedReplay`, `liveJournal` и `lastEventId`.
- Сохранять хотя бы одно реальное событие воспроизведения или один сегмент завершенного хода в реальном времени, даже если этот единственный элемент превышает лимит.
- Показывать усечение с помощью маркера `history_truncated` без идентификатора в начале `compactedReplay`.
- Рассматривать `history_truncated` только как статус. Он не должен вызывать `state_resync_required`, циклы перезагрузки или обратное сохранение в окно воспроизведения.

## Не цели

- ~~В PR-1 нет лимита на один выполняющийся ход в реальном времени; `liveJournal` продолжает удерживать активный ход до границы.~~ Добавлено в DAEMON-009 (PR #7622): `liveJournal` теперь ограничен `maxJournalEvents` (по умолчанию 10 000) и `maxJournalBytes` (по умолчанию 8 МиБ), настраивается через `--max-journal-events` / `--max-journal-bytes`.
- Нет лимита по количеству ходов. Количество ходов несет диагностическую ценность только тогда, когда движок может точно подсчитать отброшенные сегменты завершенных ходов.
- Нет тега возможности (capability) `/capabilities` для этого аддитивного события. Итоговый лимит отображается в статусе демона.
- Нет эндпоинта полного транскрипта. PR-2 должен спроектировать чтение транскрипта с пагинацией или потоковую передачу и не должен предоставлять одношаговый ответ с полным массивом.

## Дизайн

`TurnBoundaryCompactionEngine` хранит сохраняемое воспроизведение в виде упорядоченных сегментов вместо неограниченного плоского массива. Один завершенный ход в реальном времени — это один сегмент. Воспроизведение из восстановления/массовой загрузки хранится в виде сегментов уровня событий, чтобы при превышении лимита байтов самые старые события восстановления можно было отбрасывать независимо.

Определение размера переиспользует семантику безопасного определения размера JSON в EventBus. Ошибка определения размера записывается в диагностику, а такое событие считается имеющим нулевой размер в байтах, чтобы пути публикации и загрузки сохраняли контракт «никогда не бросать исключения».

Когда `replayBytes > maxReplayBytes`, движок отбрасывает самые старые сегменты, пока остается более одного сегмента. Он увеличивает `truncatedEvents`, а `truncatedTurns` увеличивает только для отброшенных сегментов ходов в реальном времени. `snapshot()` разворачивает сохраняемые сегменты и добавляет в начало:

```json
{
  "type": "history_truncated",
  "data": {
    "reason": "replay_window_exceeded",
    "truncatedEvents": 12,
    "retainedEvents": 8,
    "maxBytes": 4194304,
    "truncatedTurns": 3,
    "fullTranscriptAvailable": true
  }
}
```

Маркер является синтетическим и не имеет идентификатора. Он исключается из учета байтов и из временного хранения воспроизведения. `ingest()`, `seed(snapshot)` и `seedReplayEvents()` отфильтровывают его, так что загрузка ограниченного снимка не может привести к накоплению маркеров.

`EventBus.seedReplayEvents()` назначает идентификаторы и временные метки событиям воспроизведения из восстановления, вызывает специальный метод загрузки движка сжатия и, как и прежде, очищает кольцо SSE. Это предотвращает добавление массового воспроизведения из восстановления в `liveJournal`.

Обвязка CLI передает один итоговый лимит через yargs, парсер быстрого пути, `ServeOptions`, обвязку сервера, `BridgeOptions`, статус бриджа и отображение статуса демона. Недопустимые значения (`0`, отрицательные, нецелые, `NaN`, `Infinity` или значения свыше 256 МиБ) приводят к отказу по принципу fail closed.

SDK и WebUI знают о `history_truncated`, валидируют его содержимое, проецируют его в счетчики состояния представления и статус транскрипта и отображают терминальную статусную строку. Это событие не является неизвестным/отладочным событием и не участвует в гейтировании повторной синхронизации.

## Замечания по аудиту

Раунд 1: лимита только на завершенные ходы в реальном времени недостаточно, поскольку восстановление в режиме ответа может массово загружать большое историческое воспроизведение без границ в реальном времени. Поэтому в дизайн добавлены `seedReplayEvents()` и исторические сегменты уровня событий.

Раунд 2: переиспользование `state_resync_required` для усечения создало бы циклы перезагрузки, поскольку `/load` продолжал бы возвращать то же ограниченное окно. В дизайне используется отдельный статусный маркер, который никогда не устанавливает `awaitingResync`.

Раунд 3: лимит по количеству ходов не ограничивает память, если один ход содержит большой вывод инструмента. PR-1 использует только байтовое применение лимита и оставляет ограничение активного хода вне скоупа.

Раунд 4: возврат полного транскрипта в виде массива воссоздал бы ту же проблему пиковой памяти на момент запроса. PR-2 явно ограничен пагинацией или потоковой передачей.

Раунд 5: пустое воспроизведение после усечения привело бы к потере клиентами всего видимого состояния. Движок сохраняет самый новый сегмент, даже если он превышает размер.

## План верификации

- Юнит-тесты на обрезку ходов в реальном времени, обрезку загрузки из восстановления, размещение маркера, фильтрацию временных маркеров, сохранение превышающего лимит последнего элемента, безопасную обработку сбоев определения размера и поведение EventBus «никогда не бросать исключения».
- Юнит-тесты восстановления бриджа в режиме ответа и загрузки активной сессии с ограниченным окном.
- Юнит-тесты разбора CLI, разбора быстрого пути, валидации runQwenServe, обвязки серверного бриджа и лимитов статуса демона.
- Юнит-тесты валидации известных событий SDK, состояния редьюсера, нормализатора UI, статуса транскрипта, терминального рендеринга и внедрения воспроизведения в WebUI.
- Финальная верификация на `npm run build`, `npm run typecheck` и `npm run lint`.
