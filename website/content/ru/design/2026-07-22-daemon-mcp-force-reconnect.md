# Принудительное переподключение MCP демона

## Проблема

`POST /workspace/mcp/reload` перезагружает сохраненные настройки, но сверяет
MCP-подключения инкрементально. Сервер, чьи настройки не изменились, сохраняет
свой существующий транспорт. Поэтому OAuth-учетные данные, записанные другим
процессом Qwen Code, не считываются до тех пор, пока этот транспорт не
переподключится.

## Дизайн

Добавить опциональные поля `forceReconnectAll` и `forceReconnectWhich` к обоим
маршрутам перезагрузки MCP рабочего пространства и их методам бриджа SDK/ACP.
`forceReconnectAll` по умолчанию `false`; `forceReconnectWhich` выбирает
именованные серверы. Поля взаимно исключают друг друга.

Когда предоставлена любая из опций переподключения, демон сначала выполняет
обычное сверение настроек. Затем он переподключает каждый настроенный MCP-сервер
рабочего пространства или только имена, выбранные `forceReconnectWhich`:

- серверы из пула перезапускаются через пул транспортов рабочего пространства
  один раз на имя сервера, затем обновляют снимки инструментов модели для
  живых конфигураций;
- серверы без записи в пуле используют существующий путь обнаружения для каждой
  конфигурации, который отключается и переподключается перед повторным
  обнаружением.

Это намеренно не инициирует OAuth. Это лишь вызывает новое соединение, которое
считывает учетные данные, текуще сохраненные хранилищем токенов демона.

## API

`POST /workspace/mcp/reload` и
`POST /workspaces/:workspace/mcp/reload` принимают:

```json
{ "forceReconnectAll": true }
```

`forceReconnectWhich` принимает массив непустых имен серверов. Некорректные
значения возвращают 400.
Ответ остается `202 { "accepted": true }`, поскольку работа ставится в очередь.

## Верификация

- Тесты маршрутов покрывают проброс по умолчанию, проброс `true` и некорректный
  ввод.
- Тесты ACP покрывают распространение на каждую живую конфигурацию и поведение
  принудительного переподключения.
- План E2E документирует сценарий OAuth-токена, записанного извне.
