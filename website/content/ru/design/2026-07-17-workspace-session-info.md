# Агрегатный endpoint `session-info` рабочего пространства

## Проблема

`GET /workspace/:id/sessions` использует курсорную пагинацию и не возвращает общее
количество. `GET /daemon/status` предоставляет только живой `sessionCount` из памяти.
Рабочие пространства с большим числом сохраненных сессий (например, от задач по
расписанию) не могут узнать размер локального хранилища без перебора всех сессий.

## Предложение

Добавить:

```http
GET /workspace/:id/session-info
GET /workspaces/:workspace/session-info
```

Ответ (иллюстративный):

```json
{
  "active": 450,
  "archived": 30,
  "total": 480,
  "live": 2,
  "expensive": true,
  "cost": "disk_scan"
}
```

`live` опускается для недоверенного вторичного рабочего пространства, поскольку
эти чтения каталога не должны запрашивать живой бридж. Если сканирование достигает
своего лимита безопасности или не может классифицировать файл-кандидат JSONL,
ответ включает `"truncated": true`; сохраненные счетчики в этом случае являются
нижними границами.

## Модель стоимости

Сохраненные счетчики переиспользуют существующий паттерн полного сканирования
каталога, уже используемый поиском заголовков сессий
(`SessionService.findSessionsByTitle` / `findSessionTitlesByPrefix`):

1. `readdir` каталога чатов проекта (и его архивного близнеца)
2. фильтрация UUID `*.jsonl`
3. ограничение тем же лимитом безопасности обработки файлов
4. чтение только первой записи JSONL для проверки принадлежности к хешу проекта

Без гидратации заголовков/промптов. Это O(n) на диске, и его **нельзя опрашивать
поллингом**. Ответ всегда устанавливает `expensive: true` и `cost: "disk_scan"`,
чтобы клиенты могли применять fail closed на горячих путях. Документация явно это
оговаривает.

Пагинация списка по умолчанию остается неизменной и не вычисляет итоги. Не
переиспользуйте `listAllPersistedSummaries` организованных представлений для
счетчиков — этот путь гидратирует полные метаданные списка вплоть до 50 тыс. сессий.

## Возможность (capability)

Всегда включенная `session_info` в `/capabilities`, рядом с `session_list`.

## Не цели

- Кешируемые счетчики / учет через хуки мутаций (возможное продолжение, если
  точкам вызова понадобится более низкая задержка)
- Встраивание `total` в каждую страницу списка
- Итоги по организованным группам или с фильтрацией по родителю в v1
