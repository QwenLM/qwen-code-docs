# События подготовки вызовов инструментов

## Контекст

Qwen Code в настоящее время выпускает вызов инструмента только после того, как провайдер завершит потоковую передачу его аргументов. Для инструментов с большими или сложными входными данными генерация этих аргументов может занять гораздо больше времени, чем само выполнение инструмента. Поэтому ACP-клиенты не показывают никакой активности в течение дорогостоящей части, и пользователи могут принять ход за зависший запрос.

Потоки провайдеров уже предоставляют стабильную идентификацию инструмента до завершения аргументов:

- Anthropic отправляет `id` и `name` в `content_block_start` для блока `tool_use`, затем отправляет фрагменты аргументов как `input_json_delta`.
- OpenAI-совместимые провайдеры обычно отправляют `id` и `function.name` в первом элементе `choice.delta.tool_calls`, затем добавляют фрагменты аргументов.

Qwen Code намеренно ждет `content_block_stop` или `finish_reason` перед построением Gemini-совместимого `functionCall`. Это свойство безопасности выполнения должно остаться неизменным.

## Цель

Позволить ACP-клиентам рендерить карточку инструмента, пока модель еще готовит аргументы инструмента, со следующим жизненным циклом:

```text
preparing -> in_progress -> completed | failed
```

Раннее событие содержит только стабильный идентификатор вызова инструмента и имя инструмента. Оно никогда не содержит частичных аргументов и никогда не запускает выполнение инструмента.

## Скоуп

Это изменение поддерживает два пути провайдеров, используемые интегрирующимся клиентом:

- Потоковые ответы Anthropic и Anthropic-совместимых провайдеров.
- Потоковые ответы OpenAI и OpenAI-совместимых провайдеров.

Другие провайдеры сохраняют текущее поведение. Поскольку метаданные подготовки опциональны, они естественным образом деградируют до существующего жизненного цикла `in_progress -> completed | failed`.

Изменение не меняет:

- проверки разрешений инструментов;
- порядок хуков;
- планирование или выполнение инструментов;
- историю разговора модели;
- построение `functionCall` или `functionResponse`;
- выходные форматы, отличные от ACP.

## Дизайн

### 1. Внутренние метаданные ответа

Ассоциировать временные метаданные подготовки инструмента с каждым `GenerateContentResponse` через локальный для модуля `WeakMap`:

```ts
interface ToolCallPreparation {
  callId: string;
  toolName: string;
}
```

Адаптеры провайдеров сохраняют эти метаданные для чанка ответа верхнего уровня. Это ни перечисляемое свойство ответа, ни Gemini `Part`, поэтому они не сериализуются, и сборка истории Gemini продолжает видеть только части с текстом, размышлением и полным `functionCall`. Общие помощники предоставляют типизированные операции сохранения и чтения, избегая специфичных для провайдера приведений в ACP.

### 2. Продюсер Anthropic

В `AnthropicContentGenerator.processStream()`, когда `content_block_start(tool_use)` содержит непустые `id` и `name`, выпускать в остальном пустой чанк ответа Gemini, несущий одну запись подготовки.

Продолжать накапливать `input_json_delta` без изменений. На `content_block_stop` выпускать существующий полный `functionCall` с разобранными аргументами. Никакие данные аргументов не раскрываются до этого момента.

### 3. Продюсер OpenAI-совместимых провайдеров

В `convertOpenAIChunkToGemini()` наблюдать каждый элемент `choice.delta.tool_calls` после передачи его существующему локальному для потока парсеру вызовов инструментов. Когда стабильные непустые идентификатор и имя впервые становятся доступны, прикреплять одну запись подготовки к текущему чанку ответа.

Дедуплицировать по идентификатору вызова инструмента в пределах контекста запроса. Продолжать выпускать полный `functionCall` только при наличии `finish_reason`. Провайдеры, которые не раскрывают оба поля идентификации заранее, просто сохраняют существующее поведение.

### 4. Потребитель ACP и переходы состояний

ACP `Session` читает метаданные подготовки до сбора полных `functionCalls`. Для каждой новой подготовки выпускается стандартный фрейм ACP `tool_call` с:

```ts
{
  status: 'pending',
  rawInput: {},
  _meta: {
    phase: 'preparing',
    toolName,
    // существующие метаданные происхождения остаются присутствующими
  },
}
```

Существующий путь выполнения позже выпускает тот же `toolCallId` со `status: 'in_progress'` и полными аргументами. Существующий выпуск результатов затем завершает карточку как `completed` или `failed`.

`TodoWrite` сохраняет свою текущую специальную обработку и не выпускает карточку инструмента. Выпуск подготовки использует то же правило фильтрации, поэтому он не может создать карточку, которую путь выполнения намеренно подавляет.

### 5. Повтор, фолбэк, отмена и сбой потока

Каждый активный поток модели ACP отслеживает подготовки до завершения потока и передачи разобранных вызовов на выполнение инструментов. Когда попытка забрасывается из-за повтора, фолбэка модели, отмены пользователем или ошибки потока, ACP выпускает терминальный `tool_call_update` для каждой оставшейся записи:

```ts
{
  status: 'failed',
  content: [],
  _meta: {
    phase: 'preparing',
    preparationDiscarded: true,
    toolName,
  },
}
```

`preparationDiscarded` означает, что попытка модели была заброшена до того, как разобранный запрос инструмента достиг выполнения. Это не сбой выполнения инструмента. Интегрирующийся клиент должен удалить эту временную карточку, а не рендерить неудавшийся инструмент. Использование терминального статуса, валидного для протокола, гарантирует, что старые клиенты не сохранят бесконечно ожидающую карточку.

`RETRY` теперь очищает полные `functionCalls`, собранные из заброшенной попытки, соответствуя существующему поведению `MODEL_FALLBACK` во всех четырех путях потоков ACP. Это предотвращает выполнение разобранного вызова из неудавшейся попытки вместе с вызовами из замещающей попытки.

Когда прибывает полный `functionCall` с тем же идентификатором и поток завершается нормально, ACP передает его в существующий путь выполнения без обновления об отбрасывании. Если поток падает после разбора вызова, но до выполнения, подготовка все равно отбрасывается. Обычные ошибки инструмента поэтому продолжают идти через существующий путь результатов и никогда не помечаются как отброшенные.

## Влияние на нижестоящие компоненты

- `GeminiChat` и построители истории игнорируют опциональные метаданные верхнего уровня и продолжают сохранять только содержимое кандидатов.
- Ответ, содержащий только метаданные подготовки, не засчитывается как видимый пользователю вывод, поэтому повтор транспорта и фолбэк модели сохраняют свое существующее поведение до вывода.
- Идентификаторы подготовки используют ту же межходовую нормализацию, что и идентификаторы полных `functionCall`, сохраняя корреляцию обновлений ACP, когда провайдер переиспользует идентификатор из истории.
- Основной `Turn`, TUI и неинтерактивные потребители JSON сохраняют текущее поведение, поскольку не вводится ни новых Gemini `Part`, ни серверных событий.
- ACP — единственный потребитель, который включает эти метаданные и выпускает раннее состояние UI.
- Один и тот же контракт метаданных разделяется адаптерами Anthropic и OpenAI-совместимых провайдеров, поэтому в ACP нет ветвления по провайдерам.

## План тестирования

### Тесты основных провайдеров

- Anthropic: `content_block_start(tool_use)` выпускает метаданные подготовки до любого `input_json_delta` и до финального `functionCall`.
- Anthropic: отсутствие идентификатора или имени не выпускает метаданные подготовки.
- OpenAI-совместимые: первый delta со стабильными идентификатором и именем выпускает одну запись подготовки; последующие delta аргументов не дублируют ее.
- OpenAI-совместимые: полные вызовы по-прежнему появляются только на `finish_reason`, с неизменными разобранными аргументами.
- OpenAI-совместимые: отсутствие ранних полей идентификации приводит к откату на текущее поведение без невалидного события подготовки.
- GeminiChat: чанки только с подготовкой не подавляют повтор транспорта, фолбэк первичной модели или продолжение через цепочку фолбэка нескольких моделей.
- GeminiChat: дублирующиеся межходовые идентификаторы провайдера нормализуются согласованно в метаданных подготовки и полных вызовах.

### Тесты ACP

- Метаданные подготовки выпускают `pending` с `_meta.phase = 'preparing'` и без частичного ввода.
- Полный вызов переиспользует тот же идентификатор и переходит в `in_progress` с полными аргументами.
- Повтор, фолбэк, отмена и ошибка потока отбрасывают подготовки, не достигшие выполнения инструментов, с `_meta.preparationDiscarded = true`.
- Повтор и фолбэк модели очищают полные вызовы, собранные из заброшенной попытки, до принятия замещающих чанков.
- Подготовка, ставшая полным вызовом, не отбрасывается после нормально завершенного потока, но отбрасывается, если этот поток падает до выполнения.
- `TodoWrite` остается подавленным.

- Наборы тестов жизненного цикла ACP: 316 пройдено.

- Проверки Prettier и diff измененных файлов: пройдено.

## Критерии приемки

1. Ходы ACP Anthropic и OpenAI-совместимых провайдеров выпускают ожидающую карточку инструмента, как только становится доступна стабильная идентификация инструмента.
2. Никакой инструмент не запускается до полных аргументов и выполнения существующих путей разрешений и выполнения.
3. Полные вызовы и результаты сохраняют свои текущие идентификаторы, аргументы, порядок и представление в истории.
4. Заброшенные попытки не оставляют бесконечно ожидающих карточек подготовки.
5. Провайдеры без метаданных подготовки ведут себя в точности как раньше.
