# Контракт и совместимость прогрева ACP

## Контекст

Демон выставляет `POST /workspace/acp/preheat` и
`GET /workspace/acp/status`, но релизные клиенты не могут обнаружить эти маршруты
через `/capabilities`. TypeScript SDK также по умолчанию отправляет оба вызова через свой
активный ACP-транспорт, хотя это маршруты контрол-плейна REST демона. Наконец, HTTP-ожидатель, у которого истек таймаут, сейчас очищает общий промис
сервиса рабочего пространства, тогда как инициализация нижележащего канала
продолжается.

Это изменение делает существующие маршруты основного рабочего пространства обнаруживаемыми и
надежными. Оно не вводит устойчивое состояние готовности и не перемещает барьер первой
сессии. Сессия остается авторитетной операцией: прогрев и
создание сессии коалесцируют через инициализацию общего канала бриджа,
а создание сессии ревалидирует канал после любого статуса на момент времени или
ответа прогрева.

## Возможности (capabilities) и область применения

Демон объявляет два всегда включенных тега возможностей v1:

- `workspace_acp_preheat` для `POST /workspace/acp/preheat`
- `workspace_acp_status` для `GET /workspace/acp/status`

Каждый тег означает, что контракт именованного маршрута существует. Ни один из тегов не говорит о том, что
ACP-канал в данный момент живой. Маршруты остаются единичными и только для основного
рабочего пространства. Клиенты не должны использовать их для вторичного рабочего пространства или фолбэком
из вторичного рабочего пространства на основной рантайм.

Прогрев ACP с квалификацией по рабочему пространству требует отдельных семантик владения, доверия, дренирования
и лимитов ресурсов и выходит за рамки этого изменения.

## Семантика ответа

`GET /workspace/acp/status` возвращает снимок на момент времени:

```ts
{
  channelLive: boolean;
}
```

`POST /workspace/acp/preheat` сохраняет свою существующую форму ответа:

```ts
interface WorkspaceAcpPreheatResult {
  ready: boolean;
  channelLive: boolean;
  durationMs: number;
  reason?: 'timeout' | 'error';
  error?: string;
}
```

Применяются следующие инварианты:

- `ready` всегда равен `channelLive`.
- Живой снимок возвращает `ready: true` без `reason` или `error`.
- Таймаут ожидателя возвращает `reason: 'timeout'` только если канал все еще не
  живой на момент построения ответа.
- Неудачная инициализация, или резолвленный прогрев, который не привел к живому
  каналу, возвращает `reason: 'error'`.
- `durationMs` — конечное неотрицательное целое число, измеренное монотонными
  часами. Это прошедшее время текущего HTTP-вызова, а не время жизни
  общей инициализации, к которой, возможно, присоединился вызов.
- Видимый клиентом текст ошибок стабилен и санитизирован. Подробные ошибки дочернего процесса
  остаются в логах демона.

Операционный таймаут и неудача инициализации продолжают использовать HTTP 200, чтобы
существующие клиенты могли инспектировать результат. Невалидный ввод, авторизация, лимит частоты
и неудачи запуска отложенного рантайма сохраняют свои существующие контракты ошибок HTTP.

## Конкурентность и поведение при сбоях

Сервис рабочего пространства хранит один общий промис прогрева, пока этот промис
не урегулируется. Каждый запрос гоняет один и тот же промис против собственного таймаута. Таймаут
ожидателя завершает только этот запрос; он не отменяет операцию бриджа и не
очищает общий промис. Урегулирование очищает промис только когда его идентичность
все еще совпадает с текущей общей операцией, так что более старое завершение не может стереть
более новую попытку.

Когда общая операция урегулирована, более поздний запрос может повторить, если канал
не живой. Канал, который завершился после успешного ответа, не покрывается
арендой: статус сообщает новый снимок, и следующая сессия или прогрев начинает
новый канал.

## Совместимость клиентов

TypeScript SDK отправляет оба маршрута через свой путь REST fetch независимо от
настроенного ACP-транспорта. Он не выкачивает возможности автоматически;
вызывающие решают, когда делать префлайт.

Web UI использует маршруты только в своем отложенном, без-сессионном потоке начальной загрузки. Он
требует `workspace_acp_preheat`, гейтит опциональную оптимизацию статуса по
`workspace_acp_status` и требует, чтобы эффективное рабочее пространство точно совпадало с
`capabilities.workspaceCwd`. Точное сравнение может консервативно пропустить
прогрев для альтернативного написания основного пути, но оно не может прогреть
неправильный рантайм.

Если более старый демон опускает возможности, Web UI не делает запросов статуса ACP или
прогрева, и первая сессия следует существующему пути ленивой инициализации.
Неудача прогрева остается по мере возможности (best-effort) и не может привести к неудаче соединения или создания
сессии.

## Не-цели

- Ожидание прогрева перед первой сессией
- Перемещение прогрева раньше в старте демона или Web UI
- Аренда готовности, генерация, токен или повышение версии протокола
- Отмена инициализации общего канала, когда у HTTP-ожидателя истекает таймаут
- Маршруты прогрева или статуса ACP с квалификацией по рабочему пространству
- Заявление об улучшении латентности от этого изменения только контракта
