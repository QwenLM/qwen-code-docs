# Задержка первого вывода демона

- **Трекинг**: #7757
- **Follow-up по immediate-промпту**: #7982
- **Контекст**: #7264
- **Область**: задержка, наблюдаемая демоном/ACP-клиентом
- **Статус**: Измерение и атрибуция immediate-промпта

## Решение и область

Первый PR — только измерение: включаемый явно бенчмарк, чистые помощники классификации/статистики, тесты и версионируемые артефакты. Он не меняет продакшен-поведение запуска.

Отдельный прототип подготовки провайдера разрешен, только если однобандловый baseline проходит свой гейт. Публикация этого прототипа затем требует, чтобы отдельные контрольный и кандидатный бандлы прошли каждый гейт задержки, ресурсов, функциональности и очистки в этом документе. Валидный отрицательный результат завершает работу.

Бенчмарк измеряет путь от запуска процесса до первого вывода, произведенного моделью, разделяя при этом локальную подготовку, прибытие запроса к провайдеру, первый вывод, первый текст ответа и терминальное завершение. Существующий продакшен-показатель `ttft_ms` остается без изменений: он по-прежнему измеряет путь от отправки запроса провайдеру до первого видимого контента и не поглощает ленивую загрузку или локальную подготовку промпта.

Вне области: рендеринг TUI/Web Shell/редактора, кэширование промптов, сжатие, поведение thought/инструментов модели, предподключение сети, оптимизация задержки на реальной модели, изменения продакшен-телеметрии, публичные lifecycle API, поля протокола, конфигурация и feature-флаги.

Раннер отключен, если не задан `QWEN_FIRST_OUTPUT_BENCHMARK=1`. Его два режима входных данных взаимоисключающи:

- **Baseline**: `BENCHMARK_CLI_PATH`.
- **Сравнение**: оба `BENCHMARK_CONTROL_CLI_PATH` и `BENCHMARK_CANDIDATE_CLI_PATH`.

`BENCHMARK_POST_SESSION_DWELL_MS` — только для сравнения, принимает ровно `0`, `100` или `500`, по умолчанию `0`. `BENCHMARK_MEASURED_PAIRS` — тоже только для сравнения и принимает ровно `10` или `30`; по умолчанию `10` для 500 мс диагностики и `30` в остальных случаях. 500 мс прогон требует 10 пар, а 0/100 мс прогоны требуют 30, чтобы диагностику нельзя было ошибочно пометить как решающую. Формальные прогоны фазы 2 вызывают раннер отдельно для трех сценариев паузы (dwell); выборки из разных значений паузы никогда не объединяются. Отсутствие или смешение режимов, одинаковые бандлы сравнения, нечитаемые пути, неподдерживаемые значения паузы или числа пар и несогласованные планы паузы/выборок завершаются ошибкой `invalid_configuration` до начала выборки.

Пауза привязана к готовности SSE, а не к готовности сессии. SSE-подключение находится между ними, поэтому привязка к `sessionReady` позволила бы медленному подключению съесть всё окно и молча превратить 100 мс сценарий в прогон с immediate-промптом, который все равно сообщал бы свою настроенную паузу. `sseReadyToPromptMs` фиксирует окно простоя, которое каждый сэмпл получил фактически.

Показатели миллисекундного масштаба имеют смысл только тогда, когда ничто другое не конкурирует за хост, поэтому раннер исключен из общей конфигурации интеграционных тестов и имеет собственную serial-конфигурацию в `integration-tests/vitest.firstoutput.config.ts` (`fileParallelism: false`, последовательное выполнение, `retry: 0`). Тесты чистых помощников по-прежнему выполняются в общем наборе. Запуск бенчмарка:

```text
QWEN_FIRST_OUTPUT_BENCHMARK=1 QWEN_SANDBOX=false BENCHMARK_CLI_PATH=... \
  npx vitest run --config integration-tests/vitest.firstoutput.config.ts
```

Артефакты записываются ниже `.qwen/investigations/daemon-first-output-benchmark/`, вне одноразового каталога прогонов интеграционного харнесса. Это сохраняет успешные, неудачные и отрицательные прогоны после глобального teardown без необходимости `KEEP_OUTPUT`.

## Контракт измерений

### Одни часы

Все временные метки задержек используют `performance.now()` в родительском харнессе. Никакая длительность не комбинирует часы демона, ACP-потомка, провайдера или настенные часы. Значение времени ожидания в FIFO-очереди демона — это существующая отдельная длительность, считываемая после завершения изолированного промпта; она никогда не вычитается из родительской временной метки.

| Временная метка            | Наблюдаемое клиентом определение                                                   |
| -------------------------- | ---------------------------------------------------------------------------------- |
| `processSpawnAt`           | Непосредственно перед `spawn` демона                                                |
| `sessionReadyAt`           | Успешный ответ сессии полностью прочитан и провалидирован                           |
| `sseReadyAt`               | Наблюдён первый callback SSE-эпохи; точка привязки паузы                            |
| `promptStartedAt`          | Непосредственно перед запуском неблокирующего запроса промпта                       |
| `promptAcceptedAt`         | Тело HTTP `202` провалидировано, включая верхнеуровневый `promptId` и курсор воспроизведения |
| `userEchoAt`               | Соответствующий ретранслированный `user_message_chunk` разобран из SSE              |
| `providerRequestArrivalAt` | Фейковый провайдер принял измеряемый запрос, до своей фиксированной задержки        |
| `providerReadyAt`          | Фиксированная задержка 50 мс истекла, непосредственно перед доступностью потока ответа |
| `firstModelOutputAt`       | Разобрано первое подходящее SSE-событие для принятого верхнеуровневого `promptId`   |
| `firstAnswerTextAt`        | Разобрано первое подходящее событие текста ответа; может быть null                  |
| `terminalAt`               | Разобран соответствующий `turn_complete` или `turn_error`                           |

Сырые временные метки порождают ровно эти метрики:

| Метрика                                | Вычисление                                            |
| -------------------------------------- | ----------------------------------------------------- |
| `processToSessionReadyMs`              | `sessionReadyAt - processSpawnAt`                     |
| `sseReadyToPromptMs`                   | `promptStartedAt - sseReadyAt`, диагностика           |
| `promptToAcceptanceMs`                 | `promptAcceptedAt - promptStartedAt`                  |
| `acceptanceToProviderRequestArrivalMs` | `providerRequestArrivalAt - promptAcceptedAt`, со знаком |
| `promptToUserEchoMs`                   | `userEchoAt - promptStartedAt`                        |
| `userEchoToProviderRequestArrivalMs`   | `providerRequestArrivalAt - userEchoAt`, со знаком    |
| `daemonPromptQueueWaitMs`              | Существующая длительность ожидания в FIFO-очереди демона |
| `promptToProviderRequestArrivalMs`     | `providerRequestArrivalAt - promptStartedAt`          |
| `promptToFirstModelOutputMs`           | `firstModelOutputAt - promptStartedAt`                |
| `promptToFirstAnswerTextMs`            | `firstAnswerTextAt - promptStartedAt`, может быть null |
| `providerReadyToFirstModelOutputMs`    | `firstModelOutputAt - providerReadyAt`                |
| `promptToTerminalMs`                   | `terminalAt - promptStartedAt`                        |
| `processToFirstModelOutputMs`          | `firstModelOutputAt - processSpawnAt`                 |

`promptAcceptedAt` — диагностическая метка, а не начало отсчета задержки: запрос или событие провайдера может предшествовать получению HTTP `202`. Демон публикует соответствующее эхо пользователя до пересылки ACP-промпта, но доставка SSE все равно может проиграть гонку прибытию запроса к провайдеру. Поэтому и `acceptanceToProviderRequestArrivalMs`, и `userEchoToProviderRequestArrivalMs` — смещения со знаком, и отрицательные значения валидны. Все остальные длительности должны быть неотрицательными. Счетчик ожидания в очереди должен продвигаться ровно один раз на изолированный промпт и сохранять конечное неотрицательное значение `lastMs`; иначе сэмпл невалиден, поскольку значение нельзя безопасно скоррелировать. Отсутствие обязательных временных меток или неконечные значения делают сэмпл невалидным. Харнесс владеет 30-секундным дедлайном готовности SSE; таймаут подключения SDK записывается и устанавливается на пять секунд позже, чтобы порядок таймеров не мог превратить `sse_connect_timeout` в другой код ошибки.

Метрики атрибуции immediate-промпта намеренно останавливаются на существующих границах. Вместе они различают прием клиентом/маршрутом, ретранслированное эхо пользователя до пересылки, постановку в FIFO-очередь демона и оставшийся интервал ACP-потомка/локальной подготовки, не добавляя кросс-процессных временных меток, полей протокола или продакшен-телеметрии. Граница эха включает время ретрансляции SSE и является приблизительной, а не внутренней временной меткой демона. Эти метрики не делят оставшийся интервал между ACP-транспортом, подготовкой промпта, урегулированием загрузчика провайдера и конструированием запроса; более глубокая инструментация требует отдельных свидетельств и дизайна.

### Корреляция промптов и событий

Коллектор SSE активен до промпта или возобновляется с курсора, предшествующего ему, и буферизует фиксированное число событий, пока `202` не выдаст принятый верхнеуровневый `promptId`. Envelope принятия должен содержать непустой `promptId` и неотрицательный целый `lastEventId`; legacy-синхронный результат распознается только по своему `stopReason`, а любой другой неправильно сформированный ответ отклоняется. Таймаут принятия промпта прерывает нижележащий запрос до разборки сэмпла. Затем коллектор оценивает буферизованные и живые события в исходном порядке прибытия и принимает только точное совпадение верхнеуровневого ID. Более ранние события, события без ID и события посторонних промптов игнорируются; при переполнении буфера трекер защелкивает ошибку и прекращает буферизацию, так что сэмпл становится невалидным, а избыточные события отбрасываются.

Запросы к провайдеру не несут `promptId` демона. Поэтому каждый изолированный фейковый провайдер допускает только один ожидаемый измеряемый запрос за раз и сопоставляет свой уникальный sentinel фиксированной длины в промпте. Его временная метка может быть буферизована до `202`; лишний, отсутствующий, преждевременный или одновременный запрос делает сэмпл неудачным.

Первое подходящее событие определяет `firstOutputAt`:

| Событие                              | Вид                                      |
| ------------------------------------ | ---------------------------------------- |
| Непустой текст `agent_message_chunk` | `answer_text` и граница первого ответа   |
| Непустой текст `agent_thought_chunk` | `thought_text`                           |
| Правильно сформированный начальный `tool_call` | `tool_call`                    |

Непустой означает, что длина декодированного текста больше нуля; текст не обрезается и не переписывается. Кадры воспроизведения/статуса, локальные дискретные сообщения (включая вывод слеш-команд и фоновых уведомлений), эхо пользователя, чанки только с ролью или usage, диагностика сжатия, неправильно сформированные обновления и `tool_call_update` не засчитываются. `turn_error` всегда означает неудачу. `turn_complete` до подходящего вывода также означает неудачу. Чистый трекер допускает валидные ходы с первым выводом thought или tool и null-метрикой ответа, при этом живой фейковый провайдер должен выдать свой известный sentinel ответа.

## Фейковый провайдер и изоляция

Доступный только через loopback OpenAI-совместимый фейковый провайдер записывает прибытие запроса, валидирует запрос/модель, ждет настроенный таймер 50 мс, записывает фактическую истекшую задержку и `providerReadyAt`, испускает один стримящийся sentinel ответа и нормально завершается. Ответы бенчмарка явно используют `Connection: close`, чтобы warm-ход не мог выиграть от TCP-соединения, открытого cold-ходом; предподключение сети остается вне измеряемой оптимизации. Задержка отделяет локальную работу до запроса от распространения ответа/событий; она не моделирует реальное распределение задержек. Чистые тесты покрывают фикстуры с первым выводом thought и tool, не добавляя недетерминизма в живые прогоны.

Каждый baseline-процесс и каждый вариант сравнения получает свежее дерево процессов демона/ACP, рабочее пространство, home и `QWEN_HOME`, эфемерные порты демона/провайдера, коллектор событий и реестр запросов. Сэмплы выполняются последовательно.

Compile-кэши Node пусты на момент старта формального прогона, изолированы по бандлу и режиму, заполняются только исключенными warmup-прогонами и затем переиспользуются только тем же самым бандлом. Артефакт записывает каждый каталог кэша для прослеживаемости, но чистый прогон удаляет его при teardown, поэтому записанный путь не ожидается существующим после прогона. Контроль и кандидат никогда не делят их. Наблюдения warmup остаются в артефакте с `measured: false`.

Потомок стартует из минимального allowlist окружения. Он использует фиксированные locale/таймзону, изолированные доступные для записи пути, отключенную телеметрию/проверки обновлений, фиктивную конфигурацию провайдера и очищенные реальные учетные данные и переменные прокси. Артефакт записывает только намеренно предоставленные несекретные значения.

Формальные сравнения используют релизные бандлы, собранные из одного lockfile на одном idle 2-vCPU Linux-хосте. Артефакт записывает разрешенные пути, SHA-256 хэши, ревизии исходников при наличии, Node/OS/CPU/память и метаданные нагрузки. Кэш страниц файловой системы и шум планировщика нельзя надежно сбросить, поэтому AB/BA-упорядочение и гейт чувствительности к порядку обязательны.

## Фаза 1: однобандловый cold/warm baseline

Выполняются 2 исключенных warmup-процесса, затем 50 измеряемых процессов. Каждый измеряемый процесс:

1. создает новую сессию `sessionScope: thread` и отправляет один immediate-промпт фиксированной длины (`cold`);
2. ждет его провалидированного терминального события;
3. держит первую сессию открытой, создает отдельную сессию `sessionScope: thread` на том же ACP-потомке; и
4. отправляет один промпт той же длины с другим sentinel (`warm`).

Раннер записывает PID ACP-потомка после обоих ходов и делает сэмпл невалидным, если их обслуживал не ровно один неизмененный потомок. Только после второго хода он закрывает обе сессии. Вторая сессия таким образом имеет свежую ленивую обертку провайдера на сессию, но warm процесс-широкие кэши ESM/рантайма ACP. Пара ограничивает сверху одноразовую локальную стоимость первого прохода процесса через путь промпта, без примешивания истории разговора. Конструирование провайдера — одна из составляющих этой стоимости; первый промпт также платит за первое попадание в маршрут демона, первый ACP IPC round trip, прогрев JIT и любой несвязанный ленивый импорт. Дельта поэтому является верхней границей того, что может вернуть предзагрузка провайдера, а не оценкой загрузки провайдера, и прошедший гейт не устанавливает, что провайдер отвечает за какую-то конкретную долю. Атрибуция — это то, что проверяют парные сравнения фазы 2. Обе сессии по-прежнему конструируют своего провайдера при промпте, поэтому работа, которую прототип может перенести в паузу, не засчитывается; гейт консервативен. Метрики process-to второй сессии — диагностические.

Baseline ожидает ровно два запроса к провайдеру на процесс. Все 50 cold/warm пар должны быть валидны. Cold и warm делят процесс, поэтому их дельты — парные, а не независимые выборки, и гейт решается по парной медиане с её сидированным бутстрэп 95% интервалом:

```text
providerDelta[i] =
  cold promptToProviderRequestArrivalMs[i] -
  warm promptToProviderRequestArrivalMs[i]

providerDeltaCiLow = нижняя граница 95% CI медианы(providerDelta)
```

Фаза 1 проходит, когда либо:

```text
providerDeltaCiLow >= 25 ms
```

либо:

```text
providerDeltaCiLow >= 10% * P50(cold promptToFirstModelOutputMs)
```

Именно нижняя граница, а не точечная оценка, должна превысить порог, чтобы дельта, лишь едва превышающая его, не могла авторизовать прототип на силе шума. Разность двух P50 по-прежнему записывается для преемственности, но больше ничего не решает. Cold — всегда первая сессия, поэтому пара не может быть сбалансирована по порядку, как сравнение фазы 2; это известное ограничение конструкции, а не упущение.

Иначе артефакт сохраняется, и продакшен-работа останавливается.

## Сравнение и статистика

Каждая пауза сравнения использует 2 исключенные warmup-пары, за которыми следуют 30 измеряемых пар, кроме явно диагностического 500 мс сценария, который использует 10 и всегда сообщает неопределенный верхнеуровневый исход. Нечетные пары выполняют контроль, затем кандидат (AB); четные пары выполняют кандидат, затем контроль (BA). Каждый вариант имеет свежее состояние, и каждая записанная дельта — это `candidate - control`, так что отрицательная задержка означает быстрее.

Неудачные варианты остаются в сыром выводе и делают свои пары невалидными. Они не заменяются. Выборка останавливается после первого невалидного процесса или завершенной пары. Внешний дедлайн Vitest выводится консервативно из наибольшего легального плана выборки и каждого фиксированного таймаута жизненного цикла, с запасом на планировщик, чтобы даже легальные сэмплы около дедлайна не могли вытеснить запись артефакта. Аварийный teardown имеет свой собственный фиксированный дедлайн хука. Нет удаления выбросов, винсоризации, выбора подмножества или Vitest-retry. Любая невалидная первичная пара делает формальный прогон невалидным.

Для каждой метрики сообщаются P50/P90/P99 ближайшего ранга и среднее для каждого варианта, парная медианная дельта, победы/ничьи и медианы подгрупп AB/BA. P90/P99 описательны только при 30 парах; никакой вывод о P95 или хвостовой задержке не делается без как минимум 100 пар.

Два определения медианы сосуществуют намеренно, и читатель, сравнивающий столбцы, должен ожидать их расхождения на четном числе сэмплов. `p50` варианта — ближайшего ранга, поэтому это всегда наблюдаемое значение. Парная `median delta` и медианы, ресэмплируемые внутри бутстрэпа, усредняют два средних значения на четных количествах. Строка Markdown поэтому может показывать `p50` и `median delta`, которые не сходятся арифметически, при этом ни одно из них не является ошибочным.

95% доверительный интервал парной медианы использует 10 000 сидированных бутстрэп-ресэмплов с возвращением валидных парных дельт; seed и число итераций сохраняются. Его границы — перцентили ближайшего ранга 2,5 и 97,5. Seed каждой метрики смещен на её позицию в списке метрик, поэтому вставка или переупорядочение метрики сдвигает бутстрэп-границы всех последующих метрик и делает артефакты по обе стороны изменения несравнимыми даже при идентичных сырых выборках; сохраненный `seed` каждой метрики сохраняет это аудируемым. `orderSensitive` истинно, когда медианные дельты AB и BA имеют противоположные знаки и любая абсолютная медиана не меньше 10 мс. Чувствительность к порядку делает прогон неопределенным, а не усредняется.

Верхнеуровневый исход парного артефакта описывает только его первичную метрику в том одном сценарии. Он не оценивает кросс-сценарные, ресурсные, функциональные или публикационные гейты и сам по себе не может авторизовать pull request фазы 2.

## Ошибки, артефакты и очистка

Каждая классифицированная ошибка жизненного цикла или сэмпла сохраняется и имеет один первичный код:

| Код                               | Триггер                                                          |
| --------------------------------- | ---------------------------------------------------------------- |
| `invalid_configuration`           | Невалидный режим, путь, пауза, окружение или идентичность бандла |
| `daemon_boot_timeout`             | Нет слушающего эндпоинта до дедлайна                             |
| `daemon_exited_before_listen`     | Демон завершился до готовности                                   |
| `session_create_failed`           | Ошибка или неправильно сформированный ответ сессии               |
| `sse_connect_timeout`             | SSE не установлен до дедлайна                                    |
| `sse_stream_ended`                | SSE завершился до соответствующего терминального события         |
| `prompt_accept_timeout`           | Запрос промпта не завершился до дедлайна                         |
| `prompt_rejected`                 | Ошибка или неправильно сформированный ответ `202`                |
| `legacy_prompt_response`          | Эндпоинт завершился синхронно вместо возврата `promptId`         |
| `event_buffer_overflow`           | Превышен фиксированный буфер до принятия                         |
| `provider_request_count_mismatch` | Лишний, отсутствующий, преждевременный или одновременный фейковый запрос |
| `unexpected_output_kind`          | Живой бенчмарк с только ответом первым испустил другой вид вывода |
| `first_output_timeout`            | Нет подходящего вывода до дедлайна                               |
| `terminal_before_first_output`    | Чистое терминальное событие без подходящего вывода               |
| `turn_error`                      | Соответствующее ошибочное терминальное событие                   |
| `terminal_timeout`                | Нет терминального события после вывода до дедлайна               |
| `wrong_final_text`                | Ответ отличается от sentinel                                     |
| `cleanup_timeout`                 | Подконтрольные ресурсы не остановились к дедлайну                |
| `residual_process`                | Отслеживаемый потомок демона/ACP пережил очистку                 |
| `harness_error`                   | Неклассифицированный инвариант харнесса или ошибка I/O           |

Первая причинная ошибка жизненного цикла остается первичной; ошибки SSE/сессии и очистки процессов записываются отдельно и все равно делают пару невалидной. Неконечные длительности и невалидные отрицательные длительности, кроме двух смещений со знаком, сохраняются как ошибка харнесса, но нормализуются в `null` перед агрегацией, и неудачные прогоны никогда не вносят вклад в вычисления перцентилей или гейтов. Фиксированные таймауты, лимиты запросов и емкость буфера сериализованы. Диагностические сообщения и ограниченные хвосты stdout/stderr не влияют на решения.

Каждый вызов записывает JSON `daemon-first-output` версии схемы 2 плюс Markdown, выводимый только из этого JSON. Он содержит идентичность прогона/платформы/бандла, санитизированную конфигурацию, warmup-прогоны, каждую сырую относительную временную метку и метрику, защелкнутые типы событий первого вывода/ответа/терминального события и счетчики корреляции, счетчики запросов к провайдеру, невалидные сэмплы и пары, ошибки, результаты очистки, сводки статистики/бутстрэпа/порядка и входные данные гейтов с явными причинами решений. Ресурсные прогоны фазы 2 расширяют свои свидетельства валидации измерениями RSS. Классифицированные ошибки сэмплов остаются в своих фиксированных слотах сэмплов; невалидная конфигурация или неклассифицированная ошибка харнесса порождает фатальный артефакт. Артефакты исключают учетные данные, токены и содержимое промптов, кроме несекретного sentinel бенчмарка.

Очистка всегда прерывает и ожидает SSE, закрывает живые сессии, захватывает PID потомков ACP/MCP, отправляет `SIGTERM` подконтрольной группе процессов, пока её лидер еще известен как живой, и эскалирует на группу только если тот же лидер переживает фиксированный grace-период. Захваченные потомки и защелка полноты перечисления остаются прикрепленными к активному ресурсу до аварийной очистки. После выхода лидера очистка никогда больше не зондирует и не сигнализирует его числовой ID группы процессов, поскольку POSIX может переиспользовать его; она только верифицирует сохраненный набор потомков и безопасно завершается ошибкой, если потомок выжил или перечисление было неполным. Сокеты провайдера закрываются только после разборки процесса, и временное состояние удаляется только после верификации обоих. Очистка никогда не использует завершение по имени процесса по всей системе. Любой невалидный процесс или завершенная пара немедленно останавливает выборку, сохраняя ошибку. Если подконтрольный процесс или слушатель не может быть проверен как остановленный, раннер записывает корень временных файлов, отложенный до аварийной очистки, помечает при необходимости незапущенный аналог для сохранения невалидной пары и делает ошибку аварийного teardown видимой, а не молча бросает его отслеживаемый ресурс. Аварийный teardown повторяет попытки для отслеживаемых процессов и провайдеров перед удалением отложенных временных корней или compile-кэшей.

## Фаза 2: подготовка провайдера по мере возможности (best-effort)

### Поведение и граница

Текущий ленивый генератор мемоизирует один промис загрузчика между генерацией, стримингом, подсчетом токенов и эмбеддингами. Подготовка может запустить этот же промис рано; она не должна добавлять другой загрузчик/провайдер, выполнять какой-либо запрос model/token/embed, обновлять учетные данные или менять eager-валидацию и тайминг учетных данных Qwen OAuth. Immediate-промпт должен присоединиться к тому же промису.

Отклоненный промис подготовки остается мемоизированным, чтобы первый промпт наблюдал ту же ошибку. Отсоединенный вызывающий может прикрепить наблюдателя отклонения только для предотвращения unhandled rejection; он не должен очищать или заменять сохраненный промис. Возможность (capability) остается внутренней для Core и не расширяет публичный контракт `ContentGenerator`.

Самый ранний разрешенный триггер — успешная запись потомком ACP результата `session/new`:

1. наблюдать полученный ID запроса;
2. наблюдать отправленный ответ с тем же ID и...
3. полагаться на существующее наблюдение, происходящее только после разрешения `writer.write(frame)`; и
4. запланировать один `setImmediate` с unref, который запускает, но не ожидает, подготовку.

Неудачные ответы, аутентификация, `session/load`, `session/resume` и другие RPC не запускают её. Никакой sleep не используется для угадывания доставки ответа. Импорт ESM неотменяем, поэтому закрытая сессия может позволить уже начатому импорту завершиться; она по-прежнему не должна выполнять ни одного запроса, удерживать внешний ресурс и порождать unhandled rejection.

Эта граница — только по мере возможности (best-effort). Демон все равно выполняет работу по персистенции владения/конфигурации/источника сессии и сериализует внешний HTTP-ответ после записи потомка. Импорт провайдера может конкурировать на 2-vCPU хосте и ухудшить `processToSessionReadyMs`; `setImmediate` не создает кросс-процессного отношения happens-before. Не-ухудшение сессии поэтому блокирующее. Если оно не проходит, останавливайтесь, а не подкручивайте таймер. Точный сигнал завершения внешнего ответа пересек бы HTTP-транспорт, бридж демона и ACP-потомка и требует отдельного дизайна только если измеряемая ценность оправдывает эту сложность.

### Публикационные гейты

Используйте отдельные релизные бандлы на референсном хосте:

| Сценарий                      | Требуемый результат                                                                                                 |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Фейк, пауза 0 мс, 30 пар      | Верхняя граница 95% CI парной медианы для обоих `processToSessionReadyMs` и `promptToFirstModelOutputMs` — `<= +10 ms` |
| Фейк, пауза 100 мс, 30 пар    | Парная медиана `processToFirstModelOutputMs` — `<= -10 ms`, а её верхняя граница 95% CI — `< 0`                     |
| Фейк, пауза 500 мс, 10 пар    | Только диагностическая верхняя граница; не может компенсировать другой непройденный гейт или самостоятельно обосновать слияние |

По всем фейковым прогонам 0 и 100 мс все 60/60 пар должны быть валидны, с нулем запросов к провайдеру в окне предзагрузки, нулем остаточных процессов и отсутствием чувствительности к порядку.

Измеряйте RSS всего дерева процессов для 1, 4 и 16 idle-сессий после того, как подготовка провайдера устоялась, и до любого промпта. Оба гейта должны пройти:

- P50 RSS кандидат-минус-контроль для одной сессии `<= +10 MiB`;
- инкрементальный рост кандидат-минус-контроль от 1 до 16 живых сессий `<= +0.5 MiB` на дополнительную сессию:

```text
((candidateRss16 - candidateRss1) -
 (controlRss16 - controlRss1)) / 15
```

Каждый зонд idle-сессий создает сессии последовательно, ждет, пока подготовка устоится, и не отправляет промпт до измерения RSS; любой запрос к провайдеру делает его неудачным. Число пар и упорядочение фиксируются в артефакте валидации фазы 2 до формального измерения.

Только после прохождения всех фейк/ресурсных гейтов выполняется проверка внешней валидности с реальным провайдером на том же хосте: 30 пар AB/BA при 100 мс плюс 10-парный immediate smoke. Функциональные/аутентификационные/стриминговые ошибки и ошибки ответа блокируют. Сетевая неопределенность сообщается, но не может переопределить фейк-локальные выводы ни в одну из сторон.

## Валидация и решение

Чистые тесты фазы 1 покрывают классификацию answer/thought/tool; исключения local/replay/diagnostic; корреляцию точную и до `202`; переполнение буфера; терминальные/ошибочные пути; nullable-метрики ответа; перцентили ближайшего ранга; детерминированный бутстрэп; знак дельты; сохранение невалидных пар; чувствительность к порядку; репрезентативные фатальные артефакты; и рендеринг JSON-в-Markdown. Включаемый явно smoke релизного бандла валидирует обвязку провайдера, жизненный цикл, схему артефактов и очистку. Формальные бенчмарки не входят в CI по умолчанию.

Кандидат фазы 2 дополнительно тестирует тайминг триггера и фильтрацию RPC, single-flight с immediate-промптом, ноль запросов к провайдеру/обновлений учетных данных, мемоизированное отклонение, неблокирующую запись ответа и безопасное завершение. Он должен пройти сборку, typecheck, затронутые модульные/интеграционные тесты и полные гейты артефактов.

```text
50-процессный cold/warm baseline валиден и порог достигнут?
├─ нет → сохранить артефакт; остановиться
└─ да  → прототип отдельно
         └─ фейк 0 мс не хуже?
            ├─ нет → сохранить артефакт; остановиться
            └─ да
               └─ фейк 100 мс существенно быстрее с CI < 0?
                  ├─ нет → сохранить артефакт; остановиться
                  └─ да
                     └─ 60/60 валидны + гейты запросов/очистки/порядка/RSS пройдены?
                        ├─ нет → сохранить артефакт; остановиться
                        └─ да
                           └─ прогоны с реальным провайдером функционально проходят?
                              ├─ нет → сохранить артефакт; остановиться
                              └─ да  → PR оптимизации может быть опубликован
```
