# Rewind и shell сессий мульти-воркспейсного демона

## Статус

Финальный дизайн реализации. Этот документ заменяет утверждение Фазы 2a о
primary-only для снимков rewind живых сессий, rewind и shell.

## Проблема

Демон предоставляет API сессий в единственном числе, тогда как
мульти-воркспейсный демон владеет одним бриджем на рантайм рабочего
пространства. Большинство маршрутов живых сессий уже разрешают владельца
сессии, но снимки rewind, rewind и shell все еще были привязаны к
primary-бриджу или отклоняли вторичного владельца. Из-за этого валидная живая
вторичная сессия была неотличима для клиентов от неподдерживаемого маршрута.

## Решение

Сохранить REST API в единственном числе и разрешать владеющий живой рантайм
на каждом запросе:

- `GET /session/:id/rewind/snapshots` использует маршрутизацию чтения с
  учетом владельца.
- `POST /session/:id/rewind` и `POST /session/:id/shell` используют
  маршрутизацию мутаций с учетом владельца и общего координатора архива
  сессий.
- Вызовы rewind в SDK всегда выбирают прямой REST, даже когда клиент настроен
  на транспорт ACP. Это сохраняет строгий гейт REST-мутаций.
- Shell в SDK сохраняет настроенный транспорт. Дефолтный транспорт REST
  получает маршрутизацию по владельцу; клиент ACP с квалификацией по рабочему
  пространству сохраняет `_qwen/session/shell`.
- Не вводится ни REST API сессий с квалификацией по рабочему пространству, ни
  метод rewind ACP, ни изменения core, ни изменения ACP-потомка, ни миграции
  FileHistory.

## Владение и авторизация

Реестр рабочих пространств ищет id сессии во всех сводках живых бриджей.
Ровно один доверенный владелец диспетчеризует в этот рантайм. Отсутствие
владельца возвращает `404 session_not_found`; недоверенный владелец возвращает
`403 untrusted_workspace`; несколько владельцев возвращают
`500 ambiguous_session_owner`. Все три исхода происходят до выполнения
операции целевого бриджа. Персистентные сессии сначала должны быть загружены
или возобновлены в рантайм.

Rewind и shell сохраняют `mutate({ strict: true })`. Shell дополнительно
требует эффективного включения shell, валидного привязанного к сессии id
клиента и непустой команды. Rewind пробрасывает опциональный id клиента и
принимает `rewindFiles`, только когда тот опущен или является boolean.
Опущенный означает `true`; любой другой тип JSON возвращает
`400 invalid_rewind_files_flag`.

## Границы поведения

Shell стартует в cwd рабочего пространства владеющей сессии и не является
песочницей по пути файловой системы. Rewind восстанавливает только снимки,
записанные для `edit` и `write_file`. Он не отменяет изменения shell, Git,
скриптов или ручные изменения. Восстановление файлов — по мере возможности
(best-effort): разговор может уже быть перемотан, когда ответ сообщает
`rewound: false` с `filesFailed[]`. Активные промпты сохраняют
`409 session_busy` и `Retry-After: 5`; невалидные цели сохраняют
`400 invalid_rewind_target`. Web Shell продолжает запрашивать
`rewindFiles: false`.

Существующая схема `~/.qwen/file-history/<sessionId>` без изменений. Живая
коллизия UUID поэтому завершается fail closed через неоднозначность владельца,
а не выбором primary-рантайма.

## Возможности

`multi_workspace_session_rewind` объявляется только пока существует более
одного рантайма. `multi_workspace_session_shell` дополнительно требует
эффективного включения shell сессии, то есть и флага включения, и
настроенного токена.

Предполетная проверка клиента аддитивна:

- Rewind primary: `session_rewind`.
- Rewind secondary: `session_rewind` и
  `multi_workspace_session_rewind`.
- Shell primary: `session_shell_command`.
- Shell secondary: `session_shell_command` и
  `multi_workspace_session_shell`.

ACP-нативные клиенты используют initialize `_qwen.methods`; демон не объявляет
вендорный метод rewind ACP.

## Верификация

Покрытие юнит-тестами закрепляет диспетчеризацию по владельцу, ноль вызовов к
не владеющим бриджам, ошибки доверия и неоднозначности, порядок строгой
валидации, семантику `rewindFiles`, REST-фолбэк SDK, неизмененный транспорт
shell, условное объявление возможностей и отсутствие отображений rewind ACP.
ACP-тесты рабочих пространств сохраняют инвариант, что соединение A не может
оперировать сессией B, в то время как shell B с квалификацией по рабочему
пространству выполняется успешно.

Сценарий E2E создает сессию и отслеживаемые правки в рабочем пространстве B,
проверяет, что снимки и cwd shell имеют область B, проверяет оба файловых
режима rewind, доказывает, что файл, созданный shell, переживает rewind, и
записывает исходы busy, частичного восстановления и недоверенного secondary.
