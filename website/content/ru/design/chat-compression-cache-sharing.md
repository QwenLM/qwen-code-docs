# Совместное использование кэша при сжатии чата

## Контекст

Сжатие чата сейчас отправляет холодный side query с выделенной системной
инструкцией, без объявлений инструментов основной сессии и с облегченной по медиа
копией разговора. Провайдеры, у которых ключ prompt-кэша начинается с инструментов и
системной инструкции, не могут повторно использовать кэшированный префикс основной сессии.

## Дизайн

Сжатие сначала пытается выполнить специализированный однораундовый запрос, когда все из
следующего истинно:

- модель сжатия — текущая основная модель;
- активный провайдер — Anthropic или DashScope, и cache control включен;
- чат имеет сообщенное провайдером число токенов промпта, к которому привязывается оценка;
- эффективное число токенов промпта плюс ограниченный резерв вывода сжатия
  помещается в контекстное окно модели.

Запрос использует эффективную конфигурацию генерации текущего хода, включая
переопределения инструментов на запрос, используемые субагентами, и полную курированную
историю, включая медиа. Обычная фильтрация по модальностям модели применяется при
отправке запроса, поэтому поддерживаемые медиа остаются без изменений, а неподдерживаемые
медиа используют те же плейсхолдеры, что и другие запросы модели. Существующая
инструкция сжатия добавляется как финальное сообщение пользователя.
Ничто не потребляет и не выполняет вызовы функций из этого запроса. Ответ,
содержащий вызов функции, пустой ответ, некорректный снимок состояния или
ошибка запроса отбрасываются, и один раз повторяется попытка через существующий холодный side
query. Его облегченный по медиа вход строится лениво, только когда этот фолбэк
нужен. Отмена не запускает фолбэк.

Использование текущего `GeminiChat` держит запрос в рамках живой сессии.
Процесс-глобальный кэш форков намеренно не используется, потому что он хранит
только короткий хвост истории и может принадлежать другой параллельной сессии.

Сессии, использующие отдельную модель сжатия, остаются на существующем пути, потому что
их идентичность кэша отличается от основной сессии. Истории с медиа
сначала используют общий путь, чтобы неизменный обращенный к провайдеру префикс мог повторно
использовать кэш основной сессии.

## Верификация

Юнит-тесты проверяют точное построение system, tools, полной истории и завершающей
директивы; гейты провайдера/модели; сохранение медиа на общем пути;
префлайт окна; облегчение медиа после фолбэка; фолбэк при вызове инструмента и
некорректном ответе; и поведение отмены. Тестирование провайдера
должно сравнивать сериализованный префикс запроса и использование кэшированных токенов для
основного хода и запроса сжатия.
