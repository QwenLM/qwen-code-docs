# Общее ядро проекции из append-only ChatRecords в DaemonTranscriptBlocks

## Статус документа

- Статус: Реализовано
- Дата: 2026-07-14
- Дата реализации: 2026-07-15
- Скоуп: core, acp-bridge, cli, sdk-typescript, web-shell
- Вход: append-only неизвестные записи, уже разобранные вызывающей стороной из JSONL
- Выход: проекция `DaemonTranscriptBlock` с диагностикой и информацией о полноте

## Заключение

Результат реализации: подготовка записей, машина воспроизведения ACP, чистые построители live/replay, адаптер CLI, сжатие с учетом происхождения, нормализатор/редьюсер SDK и включаемый явно фасад SDK — все приземлено. Браузерный бандл демона по умолчанию остается в пределах бюджета 151 КиБ; минифицированный браузерный бандл транскрипта составляет 67 730 байт. Отдельные артефакты демона и демона/транскрипта суммарно составляют 222 335 байт, тогда как артефакт, импортирующий оба, занимает 222 722 байта. Дополнительные 387 байт — это накладные расходы обертки комбинированных модулей, поэтому вызывающим следует рассматривать подпуть транскрипта как явную стоимость opt-in. Базовые показатели синхронной производительности и рекомендации по Web Worker задокументированы в README SDK.

Web-вызывающие стороны используют отдельный включаемый явно подпуть SDK:

    import {
      projectChatRecordsToDaemonTranscript,
      type ChatRecordTranscriptProjection,
    } from "@qwen-code/sdk/daemon/transcript";

    const projection = projectChatRecordsToDaemonTranscript(records);
    const { blocks, diagnostics, complete, truncated } = projection;

Эта синхронная функция не запускает демон, Express или ACP-дочерний процесс; не обращается к файловой системе, сети, DOM или браузерному хранилищу; и не разбирает текст JSONL. Она принимает сырые append-only записи после `JSON.parse` и внутри выполняет:

    валидация в рантайме
      -> выбор активного листа
      -> реконструкция цепочки parentUuid
      -> агрегация фрагментов с одинаковым UUID
      -> воспроизведение персистентного транскрипта
      -> нормализация SessionUpdate
      -> проекция DaemonTranscriptBlock

Общая реализация разделена на три глубоких модуля с явным владением:

    packages/core/src/utils/transcript-records.ts
      -> экспорт пакета @qwen-code/qwen-code-core/transcriptRecords
      -> безопасная для браузера подготовка записей
      -> активная цепочка, агрегация, разрывы, диагностика

    packages/acp-bridge/src/transcript-replay.ts
      -> безопасная для браузера машина воспроизведения
      -> общие чистые построители SessionUpdate

    packages/sdk-typescript/src/daemon/ui/chat-record-transcript.ts
      -> адаптер SDK
      -> нормализатор/редьюсер/finalize
      -> публичный интерфейс проекции

`HistoryReplayer` CLI и живые `MessageEmitter`, `ToolCallEmitter` и `PlanEmitter` все переиспользуют чистые построители обновлений из acp-bridge. Это предотвращает дрейф, не сводящийся к простому перемещению из «CLI против Web» в «live против replay»: интерпретация записей и построение обновлений каждый имеют единственную реализацию.

Адаптер SDK оборачивает те же значения `SessionUpdate` как значения `DaemonEvent` без идентификатора, переиспользует существующие `normalizeDaemonEvent` и редьюсер транскрипта и в итоге возвращает `blocks`, `diagnostics`, `complete` и `truncated`.

## Предпосылки

Целевой сценарий — рендеринг только для чтения в WebShell персистентного JSONL, сгенерированного `qwen -p`, например:

    /root/.qwen/projects/-root--qwen-workspace/chats/<session-id>.jsonl

Браузер уже получил содержимое файла через хост, средство выбора файлов или другой доверенный путь чтения и отвечает за разбор текста JSONL в неизвестные записи. Полный путь после этого:

    разобранные append-only записи
      -> общая подготовка записей
      -> общее воспроизведение транскрипта
      -> проекция DaemonTranscriptBlock
      -> WebShellTranscript

Вызывающим не нужно понимать дерево `parentUuid`, активную ветку после перемотки, append-фрагменты с одинаковым UUID, записи артефактов сессии или разрывы истории. Оставить эти семантики персистентности вызывающим означало бы создать неглубокий модуль: интерфейс выглядел бы как одна функция, но корректное ее использование потребовало бы от вызывающих повторно реализовать знания `SessionService`.

Этот дизайн не использует `compactedReplay`. Это ограниченное окно восстановления в памяти, поддерживаемое демоном для живых сессий; эта утилита обрабатывает персистентные записи, явно предоставленные вызывающей стороной. Офлайн-проекция по умолчанию не имеет лимита по числу блоков, но сохраняет лимит безопасности для отдельного текстового блока и явно сообщает обо всей обработке с потерями через `diagnostics` и `truncated`.

## Существующая базовая линия: как `/load` демона воспроизводит JSONL

Текущий `/load` в режиме ответа не передает JSONL напрямую в SDK. Полный путь:

    SessionService.loadSession
      -> разбор JSONL
      -> последний не-артефактный лист
      -> buildOrderedUuidChain
      -> aggregateRecords для одинаковых UUID
      -> ResumedSessionData.conversation.messages

    QwenAgent.loadSession
      -> collectHistoryReplayUpdates
      -> HistoryReplayer
      -> MessageEmitter / ToolCallEmitter / PlanEmitter
      -> SessionUpdate[] в LOAD_REPLAY_META_KEY

    acp-bridge restoreSession
      -> extractLoadReplayResponse
      -> BridgeClient.seedSessionUpdates
      -> prepareSessionUpdateFrames
      -> EventBus.seedReplayEvents
      -> compactedReplay + liveJournal

    DaemonSessionClient.load
      -> replaySnapshot
      -> normalizeDaemonEvent
      -> reduceDaemonTranscriptEvents
      -> DaemonTranscriptState.blocks

Первая половина `/load` в потоковом режиме по-прежнему создается `HistoryReplayer`; обновления попадают в ожидающий восстановления `EventBus` как ACP-уведомления вместо включения в ответ загрузки. Оба режима в итоге проходят через одни и те же подготовку фреймов бриджа, нормализатор и редьюсер.

Текущая реализация имеет три ветки, которые должны сойтись:

- `SessionService` и `SessionTranscriptReader` имеют по собственной реализации `aggregateRecords`.
- `SessionService` выбирает в качестве листа последнюю не-артефактную запись, тогда как `SessionTranscriptReader` в настоящее время выбирает последнюю структурно валидную запись. Их семантики различаются, когда артефакт оказывается в конце файла.
- Воспроизведение JSONL зависит от классов эмиттеров CLI, поэтому браузер не может переиспользовать его без подтягивания `Config` и среды выполнения Node.

Этот дизайн не создает отдельного краткого пути из JSONL в блоки. Вместо этого он извлекает безопасную для браузера подготовку записей и построение `SessionUpdate` из пути выше, а затем продолжает использовать существующий хвост нормализации/редукции демона.

## Цели

- Предоставить синхронную, выполняемую в памяти, безопасную для браузера функцию, проецирующую сырые разобранные записи в транскрипт.
- Консолидировать выбор активной цепочки, агрегацию по одинаковым UUID и разрывы истории в одном модуле подготовки записей.
- Сделать так, чтобы воспроизведение CLI, загрузка демона и Web-офлайн-проекция совместно использовали правила интерпретации записей и построения `SessionUpdate`.
- Сделать так, чтобы живые эмиттеры и машина воспроизведения совместно использовали чистые построители обновлений для сохранения локальности live/replay.
- Сохранить временные метки, идентификацию исходных записей, порядок частей, корреляцию старта/результата инструментов, состояние пагинации и доводку висячих EOF.
- Выдавать детерминированную проекцию для одинакового ввода, используя детерминированные фолбэки для полей, не зависящих от текущего `Config`.
- Рассматривать персистентный JSON как недоверенный ввод и различать ошибки вызывающей стороны, восстановимую порчу и прямо совместимые неизвестные значения.
- Выпускать структурированную диагностику для каждого пропуска, неоднозначности и усечения; никогда не представлять частичную проекцию как полную.

## Не цели

- Чтение файлов или разбор текста JSONL.
- Симуляция `EventBus`, курсоров SSE, `Last-Event-ID` или `compactedReplay`.
- Вывод неперсистентных блоков только live — таких как permission, shell, user_shell или отмена — из записей.
- Подтягивание в браузерный бандл только-Node читателя ядра, типов провайдеров или полной среды выполнения.
- Гарантия однозначного восстановления параллельных вызовов инструментов с одинаковым именем при отсутствии персистентного идентификатора вызова.
- Возврат хранилища артефактов сессии; артефакты остаются отдельным побочным каналом.
- Перенос всей иерархии классов эмиттеров CLI в общий лист; совместно используются только чистые построители обновлений.

## Архитектура

### 1. Модуль подготовки записей

Подготовка записей принадлежит персистентной модели сессий ядра. Добавить безопасный для браузера лист:

    packages/core/src/utils/transcript-records.ts
      -> @qwen-code/qwen-code-core/transcriptRecords

Этот модуль:

- выполняет валидацию неизвестных записей в рантайме;
- выбирает явный `leafUuid` или по умолчанию последнюю валидную не-артефактную запись разговора;
- обходит от листа к корню через `parentUuid`;
- останавливается на отсутствующем родителе, не присоединяя более ранний остров, и создает `HistoryGap`;
- агрегирует фрагменты с одинаковым UUID в порядке активной цепочки;
- использует правила слияния полей, в настоящее время используемые `SessionService`;
- идентифицирует циклы, конфликтующие значения `parentUuid`, поврежденные записи и пропущенные записи артефактов; и
- возвращает новые массивы записей верхнего уровня и частей без изменения ввода. Валидированные вложенные нагрузки переиспользуются как readonly-значения вместо глубокого клонирования без пользы.

Полные массивы и потоковые индексы читаются по-разному, поэтому они совместно используют одни и те же семантические примитивы, а не заставляют `SessionTranscriptReader` загружать весь файл в память:

    validateTranscriptRecord
    isTranscriptConversationRecord
    selectTranscriptLeaf
    walkTranscriptUuidChain(lookup)
    aggregateTranscriptRecordFragments

`prepareTranscriptRecords` компонует эти примитивы для сырых массивов. `SessionService` использует скомпонованную функцию напрямую. `SessionTranscriptReader` сохраняет свои индекс по байтовым смещениям и пагинированные чтения, но использует те же классификатор, обход цепочки по lookup и агрегатор. Существующий `buildOrderedUuidChain` сворачивается в эту реализацию и не должен оставаться как второй обход.

Это одновременно убирает две реализации `aggregateRecords` и исправляет семантическое расхождение читателя, когда артефакт является последней записью, без жертвы его потоковым индексом или пагинированными чтениями.

Этот лист может импортировать только безопасные для браузера типы и чистые функции. Он не должен импортировать `fs`, `path`, `Buffer`, класс `ChatRecordingService` или код среды выполнения провайдеров.

Ядро в настоящее время не имеет карты exports. Реализация должна явно сохранить экспорты корня, `transcriptRecords`, `package.json` и существующие глубокие импорты `./dist/*`. Добавление браузерного листа не должно случайно закрыть пути `@qwen-code/qwen-code-core/dist/...`, записанные репозиторием как совместимые.

### 2. Модуль воспроизведения транскрипта

Семантики `SessionUpdate` принадлежат ACP, поэтому машина воспроизведения и чистые построители обновлений живут в:

    packages/acp-bridge/src/transcript-replay.ts
      -> @qwen-code/acp-bridge/transcriptReplay

Этот модуль скрывает:

- диспетчеризацию по типу/подтипу записей;
- порядок частей сообщения;
- преобразование текста, размышлений, изображений и вызовов функций;
- состояние старт/результат/висячий инструментов;
- Todo/план, diff/содержимое, использование и происхождение;
- результаты уведомлений, cron, сообщений внутри хода и слеш-команд;
- метаданные исходных записей; и
- состояние пагинированного воспроизведения.

Удаление этого модуля перераспределило бы сложность между воспроизведением CLI, живыми эмиттерами и проекцией SDK, поэтому он проходит тест удаления и имеет достаточную глубину.

### 3. Общие построители обновлений

Машина воспроизведения не дублирует существующие правила построения обновлений в `MessageEmitter`, `ToolCallEmitter` и `PlanEmitter`. Лист acp-bridge предоставляет чистые построители, используемые только адаптерами, такие как:

    createUserMessageUpdate
    createAgentMessageUpdate
    createAgentThoughtUpdate
    createUsageUpdate
    createToolCallStartUpdate
    createToolCallResultUpdate
    createPlanUpdate

Построители принимают только структурированные параметры и возвращают `SessionUpdate`. Они не обращаются к `Config`, реестрам, i18n или сети.

Живые эмиттеры CLI:

    вход среды выполнения
      -> адаптер метаданных CLI
      -> общий построитель
      -> sendUpdate

`HistoryReplayer`:

    подготовленный ChatRecord
      -> машина воспроизведения
      -> общий построитель
      -> sendUpdate

Офлайн-проекция SDK:

    подготовленный ChatRecord
      -> машина воспроизведения
      -> общий построитель
      -> DaemonEvent без идентификатора
      -> нормализатор/редьюсер

Превью diff, извлечение Todo, преобразование содержимого инструментов, порядок использование-к-плану и фолбэки происхождения должны жить в общих построителях или их приватных помощниках. Живые эмиттеры сохраняют только асинхронную отправку и обогащение в рантайме.

### 4. Адаптер проекции SDK

Фасад SDK живет в отдельном включаемом явно входе:

    packages/sdk-typescript/src/daemon/ui/chat-record-transcript.ts
    packages/sdk-typescript/src/daemon/transcript.ts
    @qwen-code/sdk/daemon/transcript

Он переиспользует нормализатор и редьюсер daemon UI, но не входит в браузерный бандл `@qwen-code/sdk/daemon` по умолчанию. Вызывающим нужно только установить SDK и не зависеть напрямую от подпутей core или acp-bridge.

## Стыки пакетов, безопасные для браузера

Добавить два внутренних листовых экспорта:

    @qwen-code/qwen-code-core/transcriptRecords
    @qwen-code/acp-bridge/transcriptReplay

Ограничения:

- Никаких импортов встроенных модулей Node в рантайме.
- Никакого доступа к `process`, `Buffer`, DOM или хранилищу.
- Предпочитать импорты только типов для пакетов провайдеров и ACP.
- Вход транскрипта SDK инлайнит реализацию в публикуемый бандл.
- Публикуемые `.d.ts` SDK должны инлайнить публичные типы входа/проекции и не должны ссылаться на подпуть acp-bridge, существующий только как dev-зависимость.
- Добавить гейты встроенных модулей Node для бандлов core, acp-bridge и транскрипта SDK.

### Политика валидации

Фатальные ошибки вызывающей стороны бросают `TranscriptProjectionInputError` напрямую и не возвращают частичного результата:

    export type TranscriptProjectionInputErrorCode =
      | "invalid_records"
      | "invalid_max_blocks"
      | "leaf_not_found"
      | "mixed_session_ids";

    export class TranscriptProjectionInputError extends TypeError {
      readonly code: TranscriptProjectionInputErrorCode;
    }

- `records` не является массивом.
- `options.maxBlocks` не является положительным безопасным целым.
- Явный `leafUuid` не существует.
- Две или более структурно валидных, различных значения `sessionId` смешаны в одной проекции.

Вход SDK экспортирует эту ошибку согласованно. Внутренняя ошибка валидации ядра маппится на границе фасада, чтобы внутренний класс пакета не просачивался в публичный `.d.ts`. За исключением этих случаев, отдельная некорректная запись не должна заставлять всю проекцию бросать исключение.

Когда отдельная запись или вложенная нагрузка некорректна, сохранять восстановимую историю там, где возможно, и выпускать диагностику:

- Пропускать не-объекты, записи без UUID, невалидные значения `parentUuid` и неизвестные типы записей.
- Сохранять записи с невалидными временными метками, но опускать `serverTimestamp` для таких записей.
- Для конфликтующих значений `parentUuid` среди фрагментов с дублирующимся UUID сохранять первый фрагмент и сообщать о конфликте.
- Останавливать цепочку и сообщать о разрыве, когда `parentUuid` отсутствует.
- Останавливать цепочку и сообщать о цикле, когда значения `parentUuid` образуют цикл.
- Пропускать некорректную часть распознанного вида и помечать проекцию неполной.
- Пропускать неизвестные прямо совместимые подтипы/части и выпускать предупреждение вместо бросания исключения.
- Пропускать распознанные системные подтипы, не создающие содержимое транскрипта, такие как `chat_compression`, `ui_telemetry`, `file_history_snapshot` и записи артефактов, согласно существующим семантикам, не влияя на `complete`.

Пустой вход возвращает пустые `blocks` с `complete`, установленным в `true`. Вход только из артефактов аналогично возвращает пустой транскрипт с информационной диагностикой.

Явный `leafUuid` должен указывать на запись разговора. Совпадение только с записью артефакта эквивалентно отсутствию листа. Записи артефактов не входят в цепочку UUID и не участвуют в обнаружении конфликтов дублирующихся родителей.

### Диагностика

    export interface TranscriptProjectionDiagnostic {
      readonly code: string;
      readonly severity: "info" | "warning" | "error";
      readonly message: string;
      readonly affectsCompleteness: boolean;
      readonly recordIndex?: number;
      readonly recordId?: string;
      readonly path?: string;
    }

Сообщения диагностики не должны содержать немаскированных аргументов, результатов, токенов или учетных данных. Вызывающим следует ветвиться по `code`; `message` предназначен только для логирования и отображения по умолчанию.

`projection.complete` означает:

- нет диагностики с `affectsCompleteness`, установленным в `true`;
- не произошло усечения блоков или текста;
- финализация воспроизведения завершилась; и
- не произошло неоднозначной корреляции инструментов.

Первая версия стабилизирует как минимум следующие коды диагностики. Коды — это контракт совместимости; сообщения — нет.

| код                             | affectsCompleteness | Значение                                              |
| ------------------------------- | ------------------- | ----------------------------------------------------- |
| invalid_record                  | true                | Целая запись была пропущена                           |
| invalid_timestamp               | false               | Содержимое сохранено без исторического времени        |
| conflicting_parent_uuid         | true                | Фрагменты с одинаковым UUID имеют конфликтующих родителей |
| history_gap                     | true                | В активной цепочке отсутствует родитель               |
| parent_cycle                    | true                | Активная цепочка содержит цикл                        |
| malformed_part                  | true                | Распознанная некорректная часть была пропущена        |
| unknown_record_or_part          | true                | Неизвестное расширение может содержать видимые данные |
| ambiguous_tool_call_correlation | true                | Результат инструмента не может быть скоррелирован однозначно |
| missing_tool_result             | true                | Вызов инструмента не имеет персистентного результата  |
| presentation_fallback           | false               | Адаптер отображения упал; использован фолбэк          |
| transcript_blocks_truncated     | true                | `maxBlocks` удалил старые блоки                       |
| transcript_text_truncated       | true                | Текстовый блок превысил лимит символов                |

Вход только из артефактов может использовать информационную диагностику без влияния на `complete`. Добавление кода позже не должно менять семантику `affectsCompleteness` существующего кода.

## Интерфейс выпуска воспроизведения

Общий слой выпускает полные значения `SessionUpdate` и сохраняет происхождение проекции:

    import type { SessionUpdate } from "@agentclientprotocol/sdk";

    export interface TranscriptReplayEmission {
      readonly sourceRecordId: string;
      readonly sourceTimestamp?: string;
      readonly emissionOrdinal: number;
      readonly update: SessionUpdate;
    }

Выпуск соответствует проекции одной записи, поэтому внешняя форма сохраняет единственное число `sourceRecordId`. При записи в `SessionUpdate` он становится одноэлементным массивом `sourceRecordIds` для безопасного слияния последующими операциями сжатия/upsert.

    export interface TranscriptReplayUsageState {
      readonly promptTokens: number;
      readonly cachedTokens: number;
      readonly candidateTokens: number;
      readonly apiTimeMs: number;
    }

    export interface PendingTranscriptToolCall {
      readonly callId: string;
      readonly toolName: string;
      readonly sourceRecordId: string;
      readonly sourceTimestamp?: string;
    }

    export interface TranscriptReplayStateV1 {
      readonly v: 1;
      readonly pendingToolCalls: readonly PendingTranscriptToolCall[];
      readonly cumulativeUsage: TranscriptReplayUsageState;
    }

    export interface TranscriptReplayMachineOptions {
      readonly initialState?: TranscriptReplayStateV1;
      readonly gaps?: readonly TranscriptReplayGapInput[];
      readonly presentation?: TranscriptReplayPresentationAdapter;
      readonly onDiagnostic?: (
        diagnostic: TranscriptProjectionDiagnostic,
      ) => void;
    }

Состояние воспроизведения должно быть версионировано, и `snapshot` возвращает отсоединенную копию. Некорректные ожидающие записи в `initialState` отфильтровываются с диагностикой; невалидное или неконечное использование сбрасывается в ноль с диагностикой. Неизвестная версия состояния отклоняется напрямую, чтобы избежать продолжения пагинации с некорректным состоянием.

Для совместимости с курсорами транскрипта, выпущенными до развертывания, устаревшее состояние без `v` повышается напрямую до v1, когда оно строго соответствует текущей форме `{ pendingToolCalls, cumulativeUsage }`. Явный неизвестный `v` по-прежнему отклоняется. Ветка устаревшего состояния разбирает только эту одну опубликованную форму и не эволюционирует во вторую схему состояния.

## Инкрементальная машина воспроизведения

    export interface TranscriptReplayMachine {
      project(
        record: TranscriptRecordInput,
      ): Iterable<TranscriptReplayEmission>;
      finalize(): Iterable<TranscriptReplayEmission>;
      snapshot(): TranscriptReplayStateV1;
    }

    export function createTranscriptReplayMachine(
      options?: TranscriptReplayMachineOptions,
    ): TranscriptReplayMachine;

`project` возвращает ленивый итератор. CLI немедленно ждет `sendUpdate` после получения каждого выпуска и запрашивает следующий выпуск только после успешной отправки. Изменения состояния после `yield` генератора поэтому фиксируются только после успешной предыдущей отправки.

Интерфейс должен явно документировать эти ограничения итерации:

- Адаптеры должны полностью итерировать каждое значение, возвращаемое `project`.
- После неудачной отправки обычного выпуска остановить текущую запись и все последующие записи.
- Сохранить текущий тайминг удаления ожидающего результата инструмента.
- Добавлять старт инструмента в ожидающие только после его успешной отправки.
- Фиксировать использование до того, как связанный построитель плана прочитает накопленные значения.
- `finalize` идемпотентен; его второй вызов возвращает пустой итератор.
- Адаптер CLI для `finalize` должен ловить ошибки отправки по отдельности, продолжать попытки оставшейся доводки висячих и сохранять первую ошибку доводки.
- Продолжать использовать `AggregateError`, когда существуют и ошибка воспроизведения, и ошибка доводки.

Адаптер SDK не имеет внешних сбоев асинхронной отправки и может потреблять каждый итератор полностью.

## Корреляция вызовов инструментов

Идентификаторы вызовов следуют этому приоритету:

1. Явно персистентный идентификатор в `functionCall.id`, `toolCallResult.callId` или `functionResponse.id`.
2. Если старт не имеет явного идентификатора, генерировать стабильный синтетический идентификатор с зарезервированным префиксом, включающим UUID исходной записи и индекс части.
3. Если результат не имеет явного идентификатора, коррелировать его только когда ровно один ожидающий вызов имеет то же имя.
4. Когда нет ожидающих вызовов или несколько ожидающих вызовов имеют это имя, не угадывать. Генерировать независимый синтетический идентификатор результата и выпускать диагностику `ambiguous_tool_call_correlation`.
5. Некоррелированные старты считать висячими инструментами во время `finalize`.

Синтетические идентификаторы используют префикс `qwen-replay-tool:`. Машина проверяет их на коллизии с явными идентификаторами и более ранними синтетическими идентификаторами, добавляя стабильный суффикс вхождения при коллизии.

Стабильный фолбэк гарантирует только детерминированную идентификацию; он не может гарантировать корректную корреляцию при отсутствии информации.

## Происхождение исходных записей

Идентификация записей должна проходить через CLI, демон и SDK, а не существовать только на внешнем выпуске. Текстовый блок обычно приходит из одной записи, тогда как блок инструмента поглощает и запись старта, и запись результата, поэтому события в протоколе и блоки используют упорядоченный, дедуплицированный массив. Построители воспроизведения добавляют это в `SessionUpdate._meta`:

    {
      qwenTranscript: {
        sourceRecordIds: ["..."]
      },
      timestamp: 1783958400000
    }

Ограничения:

- `sourceRecordIds` не являются идентификаторами `EventBus` и не должны записываться в `event.id` или участвовать в `Last-Event-ID`.
- Преобразовывать `sourceTimestamp` в конечное значение эпохи в миллисекундах на стыке адаптера и продолжать переиспользовать существующее поле `timestamp`.
- Выпуск разрыва истории использует `[gap.childUuid]` и временную метку дочерней записи.
- Живые эмиттеры без контекста персистентных записей не пишут `qwenTranscript`.
- Нормализатор повышает `sourceRecordIds` из `qwenTranscript`, затем удаляет внутренний транспортный объект из метаданных отображения.
- Добавить опциональные readonly `sourceRecordIds` в `DaemonUiEventBase` и `DaemonTranscriptBlockBase`.
- Редьюсер сливает текст/размышление/изображение только когда `sourceRecordIds` равны и все остальные условия слияния выполнены.
- Блоки инструментов продолжают upsert по `toolCallId` и объединяют `sourceRecordIds` в порядке событий. Блоки плана и других upsert используют то же правило стабильного объединения.
- Ключ текстового слота движка сжатия также включает `sourceRecordIds`, предотвращая слияния через границы записей.
- Когда движок сжатия сливает один и тот же `toolCallId`, он должен стабильно объединять `qwenTranscript.sourceRecordIds`; метаданные результата не должны перезаписывать происхождение старта.
- Сравнивать и индексировать `sourceRecordIds`, используя структурное равенство и `Map`, а не соединение с неэкранированным разделителем, позволяющее вредоносному UUID вызывать коллизии ключей.
- Живые события без `qwenTranscript` сохраняют текущее поведение сжатия.

Это сохраняет идентичную сегментацию записей для обоих режимов `/load` демона и офлайн-проекции, поэтому тестам соответствия не нужен тестовый-only контекст `activeRecordId`.

## Адаптер CLI

`HistoryReplayer` сохраняет свой существующий интерфейс вызова, но сокращается до асинхронного адаптера:

    подготовленные записи
      -> загрузка состояния воспроизведения
      -> machine.project(record)
      -> await sendUpdate(emission.update) по порядку
      -> machine.finalize() при запросе
      -> копия machine.snapshot()
      -> очистка активного контекста воспроизведения

Следующее поведение остается в CLI:

- обогащение `Config`/реестром инструментов;
- локализованный текст разрывов истории CLI;
- `messageRewriter.interceptUpdate`;
- обработка сбоев асинхронного `sendUpdate`;
- объединение ошибок воспроизведения и ошибок доводки висячих в `AggregateError`; и
- цели только live, stop-хуки и другие неперсистентные события.

Пути загрузки, пагинированного транскрипта и экспорта должны использовать одну и ту же подготовку записей и машину воспроизведения, чтобы один и тот же JSONL не создавал разные значения `SessionUpdate` через разные точки входа.

## Интерфейс транскрипта SDK

    export interface ChatRecordTranscriptOptions {
      readonly leafUuid?: string;
      readonly maxBlocks?: number;
    }

    export interface ChatRecordTranscriptProjection {
      readonly blocks: readonly DaemonTranscriptBlock[];
      readonly diagnostics: readonly TranscriptProjectionDiagnostic[];
      readonly complete: boolean;
      readonly truncated: boolean;
    }

    export function projectChatRecordsToDaemonTranscript(
      records: readonly unknown[],
      options?: ChatRecordTranscriptOptions,
    ): ChatRecordTranscriptProjection;

Когда `options.maxBlocks` опущен, офлайн-проекция не обрезает число блоков. Явное значение должно быть положительным безопасным целым. Когда происходит обрезка:

- `truncated` равен `true`;
- `complete` равен `false`;
- `diagnostics` включает `transcript_blocks_truncated`; и
- индексы инструментов, разрешений и родителей продолжают следовать правилам безопасной очистки редьюсера.

Офлайн-адаптер явно передает `Number.MAX_SAFE_INTEGER` как значение по умолчанию. Он не меняет `DEFAULT_MAX_BLOCKS` для онлайн `createDaemonTranscriptState` и не помещает `Infinity` в состояние редьюсера.

Путь событий адаптера SDK:

    TranscriptReplayEmission
      -> DaemonEvent без идентификатора (type = session_update)
      -> normalizeDaemonEvent
      -> reduceDaemonTranscriptEvents
      -> finalizeOfflineDaemonTranscriptState
      -> ChatRecordTranscriptProjection

События не имеют идентификатора, поскольку они не приходят из `EventBus`. `sourceTimestamp` становится `serverTimestamp`, а `sourceRecordIds` остаются отдельным происхождением проекции.

Офлайн-адаптер использует фиксированные часы редьюсера `0`, предотвращая попадание `Date.now` в наблюдаемые поля. Один и тот же ввод, опции и адаптер отображения должны производить глубоко равную проекцию; `serverTimestamp` представляет фактическое историческое время.

Новый приватный `finalizeOfflineDaemonTranscriptState` выполняет только очистку офлайн-проекции и не экспортируется из входа демона по умолчанию:

- устанавливает `streaming` активных блоков ассистента/размышления в `false`;
- очищает активные текстовые указатели;
- не фабрикует событие протокола или видимый блок; и
- не меняет финализированные статусы инструментов.

Отдельный текстовый блок продолжает использовать безопасный лимит символов SDK. Когда происходит усечение символов, хук диагностики редьюсера должен сообщать `transcript_text_truncated` и устанавливать `truncated=true` и `complete=false`; он не должен полагаться только на видимый суффикс `[truncated]`.

Чтобы сделать усечение блоков/текста наблюдаемым, добавить опциональный `onTruncation(detail)` в `DaemonTranscriptReducerOptions`. Деталь включает как минимум вид, идентификатор блока и `sourceRecordIds`, когда они есть. Обычные хранилища не передают этот колбэк; офлайн-адаптер собирает и дедуплицирует детали в диагностику проекции. Не выводить усечение сканированием `[truncated]`, поскольку пользовательский текст может содержать тот же суффикс.

## Безопасность недоверенных идентификаторов

UUID, идентификаторы вызовов и родительские идентификаторы в офлайн-вводе — недоверенные строки. Перед интеграцией изменить эти индексы редьюсера транскрипта на `Map` или объекты с нулевым прототипом:

- `blockIndexById`;
- `toolBlockByCallId`;
- `permissionBlockByRequestId`;
- `activeAssistantBlockByParent`;
- `activeThoughtBlockByParent`; и
- усеченные карты уведомлений.

Тесты должны покрывать `__proto__`, `constructor`, `prototype`, `toString` и сверхдлинные идентификаторы, чтобы гарантировать, что они не могут сломать lookup, отношения родитель-потомок или очистку усечения.

## Артефакты

Построитель результатов инструментов может продолжать помещать персистентные артефакты в метаданные `SessionUpdate` для использования побочным каналом артефактов бриджа демона. Однако `DaemonTranscriptBlock` не имеет поля артефактов, и офлайн-проекция SDK не возвращает хранилище артефактов.

Соответствие поэтому разделено на два слоя:

- Соответствие `SessionUpdate` включает артефакты.
- Соответствие `DaemonTranscriptBlock` явно игнорирует побочный канал артефактов.

Если `WebShellTranscript` в будущем понадобятся карточки артефактов, добавить отдельную проекцию артефактов вместо проноса артефактов в блоки транскрипта.

## Контракт согласованности

### Сильно согласованное поведение

Воспроизведение CLI и офлайн-проекция SDK совместно используют машину, поэтому следующее должно совпадать:

- активная цепочка и агрегация по одинаковым UUID;
- фильтрация записей/подтипов и порядок обновлений;
- поддерживаемые формы текста/размышления/изображения сообщений и порядок частей;
- идентификаторы вызовов инструментов и состояние старт/результат/висячий;
- Todo/план, diff/содержимое и сырые ввод/вывод;
- использование, использование выполнения задач и порядок статистики плана;
- позиции вставки уведомлений, cron, сообщений внутри хода, слеш-команд и разрывов; и
- временные метки, `sourceRecordIds` и диагностика воспроизведения.

Живые эмиттеры и машина воспроизведения совместно используют построители обновлений, поэтому поля `SessionUpdate`, сгенерированные для одного и того же семантического события, должны совпадать.

### Явно разрешенные различия адаптеров

- Заголовок инструмента, вид и местоположения, вычисленные из текущего `Config`/реестра инструментов CLI.
- Текст разрывов истории в текущей локали CLI.
- Производные сообщения, добавленные переписыванием сообщений CLI.
- Побочный канал артефактов.
- События разрешений, shell, отмены и сессии только live.

Если продукту потребуются идентичные поле-в-поле метаданные инструментов, метаданные воспроизведения должны быть персистентны в момент записи вызова инструмента и следовать правилу «персистентное значение прежде, детерминированный фолбэк». Историческая истина не должна пересчитываться из текущего реестра.

## Тесты соответствия

Тесты имеют шесть слоев:

1. Золотые тесты подготовки записей ядра: сырые append-only фикстуры к активной цепочке, агрегации, разрывам и диагностике.
2. Тесты построителей acp-bridge: входы live/replay проверяют полные значения `SessionUpdate`.
3. Тесты машины воспроизведения/сжатия: порядок, версионированное состояние, пагинация, синтетические идентификаторы, неоднозначная корреляция, финализация и сохранение `sourceRecordIds` во время сжатия текста/инструментов.
4. Регрессионные тесты адаптера CLI: асинхронная отправка, переписывание сообщений, частичный сбой, доводка висячих и `AggregateError`.
5. Тесты проекции SDK: события без идентификатора, `sourceRecordIds`, нормализация, сегментация записей, усечение, вредоносные идентификаторы и детерминированные блоки.
6. Межпакетное соответствие: одна и та же сырая фикстура проходит через реальное воспроизведение CLI и офлайн-проекцию SDK.

      -> SDK projectChatRecordsToDaemonTranscript
      -> sdkProjection

    сырые записи
      -> общая подготовка записей
      -> CLI HistoryReplayer
      -> захваченный SessionUpdate с метаданными qwenTranscript
      -> нормализатор/редьюсер/finalize SDK
      -> cliProjection

Выполнить глубокое равенство на канонической проекции. Каноникализатор может игнорировать только явно разрешенные различия адаптеров; он не должен удалять `sourceRecordIds`, временные метки, статус инструментов, диагностику или усечение.

Также добавить интеграционные фикстуры демона, проверяющие, что сохраненное воспроизведение `/load` в режиме ответа и потоковом режиме совпадает с офлайн-проекцией, когда не происходит усечения окна. Тесты должны пересекать границу последующего хода, чтобы покрыть сохранение бриджем/сжатием метаданных `qwenTranscript` и временных меток.

## Интеграция с WebShellTranscript

    import { useMemo } from "react";
    import {
      projectChatRecordsToDaemonTranscript,
    } from "@qwen-code/sdk/daemon/transcript";
    import { WebShellTranscript } from "@qwen-code/web-shell";

    function ReadonlyHistory({ records }: { records: readonly unknown[] }) {
      const projection = useMemo(
        () => projectChatRecordsToDaemonTranscript(records),
        [records],
      );

      return (
        <>
          {projection.complete ? null : (
            <TranscriptDiagnostics diagnostics={projection.diagnostics} />
          )}
          <WebShellTranscript blocks={projection.blocks} />
        </>
      );
    }

SDK владеет подготовкой данных и проекцией; WebShell владеет только рендерингом для чтения. `WebShellTranscript` не добавляет prop `records` и не запускает provider, сессию или сетевое соединение.

## Контракт синхронной производительности

Публичный фасад — это синхронная O(records + parts) проекция, сканирующая весь ввод, даже если явный `maxBlocks` в итоге сохраняет только хвостовые блоки. `maxBlocks` ограничивает память вывода, а не вычисления.

До реализации установить базовые показатели времени и пиковой памяти с использованием малых, средних и больших реальных фикстур и задокументировать рекомендуемый лимит главного потока в документации SDK. Хосты свыше этого лимита должны вызывать тот же безопасный для браузера интерфейс в Web Worker и передавать проекцию в главный поток.

Первая версия не добавляет отдельную обертку async/worker. Пересмотреть этот адаптер после появления второго реального вызывающего, избегая ложного стыка с единственным адаптером.

## Ограничения бандла и публикации

Конвертер не входит в бандл `@qwen-code/sdk/daemon` по умолчанию. Добавить этот экспорт пакета:

    "./daemon/transcript": {
      "types": "./dist/daemon/transcript.d.ts",
      "import": "./dist/daemon/transcript.js",
      "require": "./dist/daemon/transcript.cjs"
    }

Требования к сборке:

- Отдельные браузерные ESM и Node CJS бандлы.
- Отдельный гейт встроенных модулей Node.
- Отдельный бюджет размера с записанными коммитом базовой линии и командой измерения.
- Публичные `.d.ts` файлы не раскрывают dev-зависимости core/acp-bridge.
- Измерить дублирующийся код в образцовой сборке, импортирующей и `daemon`, и `daemon/transcript`.
- Не полагаться на импорт корня пакета или случайный tree shaking для безопасности браузера.

Бюджет демона по умолчанию 151 КиБ не увеличивается для этой функции.

## Порядок миграции

1. Добавить безопасный для браузера лист подготовки записей транскрипта в ядро и сделать так, чтобы `SessionService` и `SessionTranscriptReader` совместно использовали классификацию, выбор листа, обход цепочки и агрегацию.
2. Добавить чистые построители `SessionUpdate` в acp-bridge и постепенно мигрировать живые эмиттеры на них.
3. Добавить машину воспроизведения и золотые тесты.
4. Преобразовать `HistoryReplayer` в адаптер CLI, сохраняя его существующий интерфейс вызова и семантику ошибок.
5. Добавить метаданные `qwenTranscript` и расширить обработку `sourceRecordIds` в бридже, сжатии, нормализаторе и редьюсере.
6. Усилить индексы недоверенных идентификаторов редьюсера и диагностику усечения.
7. Добавить включаемый явно фасад `daemon/transcript` и отдельные публикуемые артефакты в SDK.
8. Добавить межпакетное соответствие и интеграционные фикстуры демона.
9. Подключить страницу WebShell только для чтения к `projection.blocks` и показывать диагностику.

На каждом шаге мигрировать существующих потребителей до удаления старой реализации, чтобы ни на одном этапе не было двух наборов правил активной цепочки, агрегации или построителей обновлений одновременно.

## Оценочный размер кода

- Подготовка записей ядра и миграция двух существующих потребителей: примерно 180–280 строк продакшен-кода.
- Построители acp-bridge и машина воспроизведения: примерно 400–550 строк.
- Адаптер `HistoryReplayer` CLI: примерно 60–100 строк.
- Фасад проекции SDK, идентификация и склейка диагностики: примерно 140–220 строк.
- Поддержка безопасности/усечения редьюсера: примерно 60–120 строк.
- Остальное — в основном фикстуры, регрессионные тесты и тесты соответствия.

Это межпакетное изменение ядра. Мейнтейнер должен подтвердить скоуп под гейтом триажа ядра репозитория до реализации. Дублирующуюся агрегацию или построители обновлений не следует сохранять только ради уменьшения числа строк.

## Скоуп с потерями

Проекция может восстановить только информацию, присутствующую в записях. Следующее явно невосстановимо или потенциально с потерями:

- блоки только live, такие как permission, shell, user_shell и prompt_cancelled;
- хранилище артефактов сессии;
- историческая истина для текущего `Config`/реестра/локали;
- неподдерживаемые бинарные/аудио/fileData;
- старое вложение суб-агентов боковой цепочки без `parentToolCallId`;
- точная корреляция при отсутствии явных идентификаторов вызовов и нескольких ожидающих инструментах с одинаковым именем;
- содержимое после безопасного лимита символов отдельного текстового блока;
- старые блоки, удаленные явно предоставленным вызывающей стороной `maxBlocks`; и
- содержимое, пропущенное из-за поврежденного ввода, неизвестных расширений или сломанной цепочки.

Каждый случай, влияющий на полноту, должен выпускать диагностику и устанавливать `complete=false`. Каждая фактическая обрезка также должна устанавливать `truncated=true`.
