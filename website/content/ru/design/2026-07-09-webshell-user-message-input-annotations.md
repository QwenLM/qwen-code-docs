# Аннотации пользовательского ввода сообщений в WebShell

## Предпосылки

Возможность `@` в WebShell уже поддерживает рендеринг выбранных файлов, расширений, ресурсов MCP и элементов кастомных provider'ов хоста в виде чипов в поле ввода. Чипы внутри поля ввода реализованы через inline-виджеты CodeMirror; виджет хранит полный объект `WebShellComposerTag`, поэтому стабильно доступны `id`, `kind`, `label`, `value`, `serialized`, `removable`, а также иконка, внедряемая хостом через `composerTagIcons`.

Первая версия реализации в текущем PR1 не меняла цепочку отправки: на этапе рендеринга сообщения пользователя ссылки `@...` заново парсились из текста `content`, и распознаваемые встроенные ссылки отображались как чипы. Это решало часть обратимых сценариев — например, `@.qwen/`, `@ext:name`, `@mcp:name`, — но полагалось на угадывание по тексту и не могло покрыть все реальные случаи ввода.

Фидбек из ревью выявил фундаментальную проблему этого подхода:

- `@Makefile`, `@LICENSE`, `@src/Makefile` — легитимные ссылки на файлы, но по одному только тексту их невозможно стабильно отличить от обычных упоминаний или токенов, похожих на пакеты.
- Для ссылок кастомных provider'ов вида `@dataset:users` после отправки остается только текст, и рендеринг по умолчанию не может получить исходные `kind`, `label`, `value` и иконку.
- Границы экранированных ресурсов MCP и следующей за ними пунктуации можно обрабатывать только эвристиками; дальнейшее добавление правил сделает парсер все более сложным и все равно не позволит доказать полную корректность.

Поэтому PR1 должен расширить скоуп: не меняя текст промпта, который получает модель, сохранять структурированные метаданные ввода, которыми уже располагает composer, вдоль цепочки отправки, транскрипта, локальных сообщений и воспроизведения. Рендеринг сообщения пользователя использует для отображения чипов только метаданные; старые сообщения или сообщения без метаданных по-прежнему отображаются как исходный текст, без попыток угадать ссылки из чистого текста.

Новое поле нельзя называть `composerTags`. `composerTag` — это деталь реализации текущего `@`-чипа, но во вводе пользователя WebShell есть и другие структурированные элементы ввода: слеш-команды `/`, команды навыков, кастомные команды, системные команды, локальные команды. Новые метаданные отправки должны выражать «структурированные аннотации пользовательского ввода»; в этом релизе записываются только аннотации ссылок `@`, а в будущем в том же поле можно будет добавлять аннотации команд `/`.

## Цели

- Чипы ссылок `@`, которые пользователь видит в поле ввода, после отправки сохраняют согласованный рендеринг чипов в пузыре сообщения пользователя.
- Поддержка встроенных файлов, расширений, тегов MCP, включая файлы без расширения и экранированные ресурсы MCP.
- Поддержка рендеринга чипов по умолчанию для кастомных provider'ов хоста, если provider предоставил `composerTag` в принятом элементе.
- Содержимое промпта на стороне модели не меняется; daemon/модель по-прежнему получают строку, сгенерированную текущей функцией `buildComposerPrompt(text, tags)`.
- Сохранить возможность переопределения `renderUserMessageContent`; если хост кастомизировал содержимое сообщения пользователя, он по-прежнему может полностью взять на себя рендеринг.
- Совместимость со старыми транскриптами, старыми демонами и сообщениями без метаданных: содержимое отображается как есть, просто без дополнительных чипов.
- Предусмотреть единую точку расширения для будущих структурированных элементов ввода: команд `/`, команд навыков, кастомных команд.

## Не цели

- Не менять протокол регистрации `@`-provider'ов.
- Не добавлять поддержку `@skill:` для навыков; WebShell сейчас ссылается на навыки через `/`.
- Не записывать URL иконок в персистентный транскрипт. Иконки, как и прежде, разрешаются по `kind` через `composerTagIcons` на этапе рендеринга.
- Не передавать метаданные модели и не менять семантику разбора промпта демона.
- Не пытаться на 100% восстановить из чистого текста все ссылки кастомных provider'ов или файлов без расширения.
- В этом релизе не менять рендеринг команд `/`; только спроектировать поле метаданных так, чтобы оно могло нести аннотации команд `/`.
- В этом релизе не восстанавливать аннотации при повторе Ctrl+Y; повтор переиспользует исходное сообщение пользователя, без нового дублирующего эха пользователя.
- В этом релизе не откатывать аннотации после сбоя `onSubmitBefore`; при сбое промпт не попадает в цепочку отправки, сохраняется текущее поведение отмены.

## Решения по скоупу

- В этом релизе допускается одновременное изменение `packages/web-shell`, `packages/webui`, `packages/sdk-typescript` и `packages/acp-bridge`. Первые три отвечают за отправку, локальное эхо, типы транскрипта/сообщений и рендеринг; `packages/acp-bridge` отвечает за запись эха пользователя демона в доступные для воспроизведения `user_message_chunk.update._meta`, иначе после обновления/повторного открытия сессии восстановить аннотации будет невозможно.
- И обычная отправка, и промпты в очереди должны поддерживать аннотации. Промпты в очереди также отображаются в области сообщения пользователя как текущий ввод; если они не будут нести метаданные, возникнет несогласованность с обычной отправкой.
- `renderUserMessageContent` должен получить расширенные параметры, чтобы кастомный рендерер хоста мог читать `inputAnnotations`. Рендерер по умолчанию использует метаданные для рендеринга чипов; рендерер хоста сохраняет за собой окончательное право переопределения.
- Удалить фолбэк, выводящий `@`-чипы из чистого текста, чтобы не продолжать поддержку эвристического парсера, который невозможно сделать полностью корректным.
- В этом релизе генерируются и рендерятся только аннотации ссылок `@`; для команд `/`, команд навыков и кастомных команд только зарезервировано место в структуре данных, без реализации рендеринга чипов после отправки.

## Обнаруженные возможности структурированного ввода

На стороне ввода WebShell сейчас есть как минимум следующие структурированные возможности:

- Ссылки `@`: предоставляются `useAtMentionMenu`, включают встроенные файлы, расширения, серверы/ресурсы MCP, а также кастомные provider'ы, внедряемые хостом через `atProviders`. После принятия создается `WebShellComposerTag`, а чип рендерится inline-виджетом CodeMirror.
- Слеш-команды `/`: автодополнение предоставляется `slashCompletion.ts`. Команды верхнего уровня приходят из `session.available_commands` демона, локальных команд WebShell, кастомных команд, команд навыков и системных команд.
- Субкоманды `/`: `slashCompletion.ts` поддерживает явные `subcommands`, встроенное дерево субкоманд и неявное дерево субкоманд. Например, `/mcp desc`, `/stats model`, `/memory show`, `/skills <skill-name>`.
- Категории команд: `commandDisplay.ts` делит команды на `custom`, `skill`, `system`. `App.tsx` помечает соответствующую команду категорией skill на основе `connection.skills`.
- Локальные слеш-команды: в `localCommands.ts` определены локальные команды `help`, `theme`, `language`, `model`, `mcp`, `skills`, `memory`, `context`, `agents`, `goal`, `tasks`, `extensions` и другие.
- Режим shell / `!`: composer может отправлять `!${prompt}` в режиме shell — это другая семантика пользовательского ввода, не входящая в скоуп рендеринга этого релиза.

Эти возможности показывают, что новое поле метаданных должно быть универсальным списком аннотаций, а не списком тегов, обслуживающим только `@`.

## Текущая цепочка

### Внутри поля ввода

`useComposerCore` поддерживает inline-теги в поле ввода. На момент отправки полный `WebShellComposerTag[]` уже доступен через `tagsOverride ?? composerTagsRef.current`. Эти теги используются в `buildComposerPrompt(text, tags)` и в итоге объединяются с текстом промпта, отправляемым демону.

### Отправка и локальное эхо

`sendPrompt` в `App.tsx` принимает только `text` и `images`; `sessionActions.sendPrompt(text, options)` также отправляет только текст промпта. Для оптимистичного отображения или эха локальных команд WebShell вызывает `store.appendLocalUserMessage(text, images)`.

`appendLocalUserMessage` сейчас записывает только `text/images` в `DaemonTextTranscriptBlock`, без структурированных метаданных ввода.

### Воспроизведение в компонент сообщения

`transcriptBlocksToDaemonMessages` преобразует блоки пользователя транскрипта в `DaemonUserMessage`, сохраняя сейчас только `content`, `images`, `timestamp` и `source`. `UserMessage` получает только `content/images`, поэтому первая версия реализации могла лишь заново угадывать теги через текстовый парсер.

## Обзор решения

Добавляется новая цепочка метаданных только для UI. Она делится на два смежных, но разных по ответственности пути: оптимистичное эхо на текущей странице и персистентное эхо в транскрипте демона.

```text
CodeMirror inline tags
  -> submitText / submitPromptFromEditor
  -> sendPrompt options
  -> sessionActions.sendPrompt / sessionActions.submitPrompt options
  -> A. store.appendLocalUserMessage(text, images, { inputAnnotations })
     -> немедленное отображение чипов сообщения пользователя в текущей вкладке
  -> B. PromptRequest._meta.inputAnnotations
     -> bridge echoPromptToSessionBus объединяет в user_message_chunk.update._meta
     -> replay/load получает тот же набор событий session_update
     -> normalizeDaemonEvent генерирует user.text.delta.meta.inputAnnotations
     -> reduceDaemonTranscriptEvents записывает в DaemonTextTranscriptBlock.meta.inputAnnotations
     -> transcriptBlocksToDaemonMessages
     -> DaemonUserMessage.inputAnnotations
     -> рендерер по умолчанию UserMessage
```

`content` по-прежнему является текстом промпта, который обрабатывают модель и демон. `inputAnnotations` описывают только структурированный ввод, необходимый для рендеринга UI, и не участвуют во вводе модели.

## Структуры данных

Добавляется универсальная структура аннотаций ввода; поле верхнего уровня называется `inputAnnotations`:

```ts
interface DaemonUserMessage {
  id: string;
  role: 'user';
  content: string;
  images?: Array<{ data: string; mimeType: string }>;
  source?: string;
  inputAnnotations?: DaemonInputAnnotation[];
}
```

`DaemonInputAnnotation` выражает «структурированную семантику, соответствующую определенному участку текста в content». Принцип дизайна: добавляется только внешняя обертка аннотации, а внутренняя нагрузка по возможности переиспользует существующие форматы объектов `@` и `/`, чтобы не создавать новый протокол, параллельный `WebShellComposerTag` и `CommandInfo`. В этом релизе реализуется только `type: 'reference'`; будущие команды `/` смогут расширяться в том же массиве:

```ts
interface DaemonInputReferenceAnnotation {
  type: 'reference';
  start: number;
  end: number;
  text: string;
  reference: DaemonInputReference;
}

interface DaemonInputReference {
  id: string;
  kind?: string;
  label?: string;
  value?: string;
  serialized?: string;
  removable?: boolean;
}

type DaemonInputAnnotation = DaemonInputReferenceAnnotation;
```

`start/end` — это смещения в UTF-16 относительно финального `content`, что согласуется с текущей обработкой строк в React/CodeMirror. Это избавляет будущий рендеринг от обратного поиска позиции в `content` по `serialized` и оставляет пространство для нескольких одинаковых ссылок, одинаковых команд и смешанного inline-текста.

В этом релизе нагрузка ссылок `@` напрямую переиспользует существующий `WebShellComposerTag`:

```ts
interface WebShellComposerTag {
  id: string;
  kind?: string;
  label?: string;
  value?: string;
  serialized?: string;
  removable?: boolean;
}
```

Будущая нагрузка команд `/` напрямую переиспользует существующий `CommandInfo`, добавляя на уровне аннотации только `subcommandPath`:

```ts
interface CommandInfo {
  name: string;
  description: string;
  argumentHint?: string;
  subcommands?: string[];
  source?: string;
  displayCategory?: 'custom' | 'skill' | 'system';
}
```

В `meta` блоков транскрипта SDK хранятся те же `inputAnnotations`:

```ts
interface DaemonTextDeltaMeta {
  inputAnnotations?: DaemonInputAnnotation[];
}
```

При реализации пакет SDK не должен импортировать типы клиента WebShell. В SDK определяется минимальная структура меты, совместимая по полям с `WebShellComposerTag` и `CommandInfo`, а адаптер WebShell затем преобразует эту структуру в типы, необходимые клиенту для рендеринга. Это позволяет избежать обратной зависимости SDK от WebShell и при этом сохранить форму полей, согласованную с существующими форматами `@` / `/`.

## Ключевые точки изменения

### 1. Цепочка отправки несет inputAnnotations

Скорректировать форму параметров отправки редактора, чтобы `sendPrompt` мог получать `DaemonInputAnnotation[]` на момент отправки.

Рекомендуется добавить легковесное поле options:

```ts
interface SendPromptInputMetadata {
  inputAnnotations?: DaemonInputAnnotation[];
}
```

`useComposerCore.submitText()` уже знает `tags` и финальный `prompt` при генерации текста промпта. Он должен преобразовать `@`-теги этого релиза в аннотации `reference` и затем вызвать вышестоящий `onSubmit`:

- `promptText`: текущий текст, отправляемый демону, без изменений.
- `images`: текущие изображения.
- `inputAnnotations`: снимок структурированных аннотаций ввода на момент отправки.

Если текущая сигнатура `onSubmit` не подходит для прямого расширения, можно добавить четвертый параметр метаданных, чтобы не ломать существующие вызовы:

```ts
onSubmit(promptText, images, commitAccepted, { inputAnnotations });
```

Правила генерации аннотаций в этом релизе:

- Для префиксов тегов, сгенерированных `buildComposerPrompt(text, tags)`, вычисляются `start/end`.
- Каждый тег соответствует одной аннотации `type: 'reference'`.
- `annotation.text` использует фактический сериализованный текст в финальном промпте.
- `annotation.reference` сохраняет минимально безопасные поля исходного `WebShellComposerTag`: `id/kind/label/value/serialized/removable`.
- URL иконок не сохраняются; иконки по-прежнему разрешаются на этапе рендеринга по `kind + composerTagIcons`.

Если в будущем командам `/` тоже понадобится структурированный рендеринг, можно генерировать аннотации `type: 'command'` при принятии автодополнения слеша, либо генерировать аннотации команд на этапе отправки на основе совпавшего `CommandInfo`. Нагрузка команд сохраняет существующие поля `CommandInfo` напрямую, а информация о субкомандах помещается в `subcommandPath` обертки аннотации.

### 2. Локальное эхо транскрипта сохраняет метаданные

Расширить хранилище транскрипта SDK:

```ts
appendLocalUserMessage(
  text: string,
  images?: Array<{ data: string; mimeType: string }>,
  meta?: { inputAnnotations?: DaemonInputAnnotation[] },
): void;
```

`appendLocalUserTranscriptMessage` синхронно принимает `meta`:

```ts
appendLocalUserTranscriptMessage(state, text, { images, meta });
```

Запись после создания текстового блока пользователя:

```ts
if (opts.meta) {
  block.meta = { ...block.meta, ...opts.meta };
}
```

Эта цепочка гарантирует лишь то, что оптимистичное сообщение пользователя в текущем фронтенд-хранилище немедленно получает чипы. Она сама по себе не гарантирует доступность метаданных после обновления или повторного открытия сессии, поскольку транскрипт после обновления приходит из воспроизведения демона, а не из локального добавления в памяти текущей вкладки.

Локальные слеш-команды без аннотаций ввода продолжают передавать пустые метаданные, без изменения существующего поведения.

### 3. Эхо промпта демона персистентно сохраняет метаданные

`PromptRequest` уже поддерживает `_meta?: Record<string, unknown> | null`. При отправке тот же `inputAnnotations` записывается в `PromptRequest._meta.inputAnnotations`:

```ts
const promptRequest = {
  prompt: toDaemonPromptContent(text, normalizedImages),
  _meta: inputAnnotations.length > 0 ? { inputAnnotations } : undefined,
};
```

Бридж внутри `sendPrompt` передает запрос промпту агента и одновременно публикует `user_message_chunk` через `echoPromptToSessionBus`. Здесь нужно объединить `_meta.inputAnnotations` запроса с `update._meta` эха:

```ts
_meta: {
  ...pickUserInputEchoMeta(req._meta),
  serverTimestamp,
  source: 'bridge-echo',
}
```

`pickUserInputEchoMeta` сохраняет только `inputAnnotations`, не записывая неизвестную мету запроса как есть в транскрипт сообщения пользователя. Это позволяет не раскрывать телеметрию, requestId, retry и прочие не-UI данные объекту `UserMessage`.

При воспроизведении `DaemonSessionProvider` заново нормализует `compactedReplay/liveJournal` в события UI; `normalizeDaemonEvent` уже помещает `user_message_chunk.update._meta` в `user.text.delta.meta`; редьюсер транскрипта уже записывает `meta` текстовых событий в `DaemonTextTranscriptBlock.meta`. Поэтому, как только событие эха демона будет нести `inputAnnotations`, после обновления и повторного открытия той же сессии рендеринг чипов можно будет восстановить.

### 4. Адаптер транскрипта пробрасывает метаданные

`transcriptBlocksToDaemonMessages` уже читает `meta.source` блоков пользователя. В том же месте читается `meta.inputAnnotations`, валидируется как массив и записывается в `DaemonUserMessage.inputAnnotations`.

Здесь нужна минимальная структурная валидация, чтобы неизвестная мета транскрипта не влияла на рендеринг:

- Должен быть массив.
- Каждая аннотация должна иметь непустые строковые `id/type/text`.
- `start` и `end` должны быть конечными числами и удовлетворять `0 <= start < end <= content.length`.
- В этом релизе генерируются и рендерятся только аннотации `type: 'reference'`; будущие аннотации команд могут расширяться в том же поле.
- Нагрузка reference минимально санируется по полям `WebShellComposerTag`: принимаются только строковые значения `id/kind/label/value/serialized` и булево значение `removable`.
- Нагрузка command минимально санируется по полям `CommandInfo`: принимаются только строковые значения `name/description/argumentHint/source/displayCategory` и строковый массив `subcommands`.
- Неизвестные поля не сохраняются.

### 5. UserMessage в первую очередь использует inputAnnotations

Props `UserMessage` дополняются:

```ts
inputAnnotations?: DaemonInputAnnotation[];
```

Параметры `renderUserMessageContent` синхронно дополняются одноименным полем:

```ts
renderUserMessageContent?.({ content, images, inputAnnotations });
```

Логика рендеринга по умолчанию меняется так:

1. Если в `inputAnnotations` есть валидные аннотации `type: 'reference'`, `content` разрезается по `start/end` и рендерятся чипы.
2. Если метаданные отсутствуют или валидных аннотаций нет, рендерится исходный текст.
3. Если хост предоставил `renderUserMessageContent`, по-прежнему в первую очередь используется рендерер хоста.

Рендеринг по метаданным больше не угадывает типы тегов из `content` и не ищет позиции по сериализованному тексту. При невалидных или перекрывающихся диапазонах соответствующая аннотация игнорируется, гарантируя, что никакое содержимое пользователя не будет скрыто.

### 6. Удаление фолбэка текстового парсера

`splitComposerTagContent` больше не сохраняется. Причина в том, что старый парсер мог угадывать типы ссылок только по форме строки:

- `@Makefile` и `@alice` оба могут быть легитимным текстом.
- `@dataset:users` требует метаданных provider'а, чтобы узнать label/value/иконку.
- Конечную пунктуацию экранированных ресурсов MCP трудно доказать корректной общими правилами.

Поэтому сообщение пользователя по умолчанию рендерит чипы только при наличии аннотаций; при отсутствии аннотаций показывается исходный текст. Таким образом, проблема `@Makefile` из ревью больше не зависит от эвристики, поскольку новые сообщения получают явный файловый тег из метаданных.

## Поведение кастомных provider'ов

Если provider предоставляет в принятом элементе:

```ts
composerTag: {
  id: 'dataset:users',
  kind: 'dataset',
  label: 'Dataset',
  value: 'users',
  serialized: '@dataset:users',
}
```

После отправки сообщение пользователя по умолчанию может отрендерить:

- label: `Dataset`
- value: `users`
- иконку: разрешается через `composerTagIcons.dataset`

Если provider не предоставил `composerTag`, после отправки остается только чистый текст; рендерер по умолчанию не обещает автоматически распознавать кастомных provider'ов. Хост по-прежнему может обработать это сам через `renderUserMessageContent`.

## Совместимость

- В старых транскриптах нет `meta.inputAnnotations`, они продолжают отображаться как исходный текст.
- Новый клиент, читающий события старого демона, не меняет поведения.
- Старый клиент, читающий транскрипт с `meta.inputAnnotations`, игнорирует неизвестную мету.
- `content` не меняется, поэтому разбор промпта демона, ввод модели, текст слеш-команд и содержимое исторических промптов не затрагиваются.
- Приоритет `renderUserMessageContent` не меняется; кастомный рендеринг хоста не переопределяется чипами по умолчанию.

## План тестирования

### Юнит-тесты

- `appendLocalUserTranscriptMessage` сохраняет `meta.inputAnnotations`.
- `createDaemonTranscriptStore().appendLocalUserMessage` принимает и сохраняет метаданные.
- `sessionActions.sendPrompt` и `sessionActions.submitPrompt` записывают `inputAnnotations` в `PromptRequest._meta`.
- `echoPromptToSessionBus` бриджа объединяет с `user_message_chunk.update._meta` только `inputAnnotations`, не записывая неизвестную мету запроса в эхо транскрипта.
- `user_message_chunk.update._meta.inputAnnotations` из воспроизведения проходят через `normalizeDaemonEvent` и редьюсер в `DaemonTextTranscriptBlock.meta.inputAnnotations`.
- `transcriptBlocksToDaemonMessages` преобразует `meta.inputAnnotations` блоков пользователя в `DaemonUserMessage.inputAnnotations`.
- `transcriptBlocksToDaemonMessages` отфильтровывает невалидную мету аннотаций.
- `UserMessage` рендерит `@Makefile`, `@LICENSE`, `@src/Makefile` с использованием аннотаций reference.
- `UserMessage` рендерит теги кастомных provider'ов с использованием аннотаций reference и разрешает `composerTagIcons`.
- `UserMessage` сохраняет отображение исходного текста при отсутствии метаданных.
- `UserMessage` игнорирует аннотации с невалидными или перекрывающимися диапазонами без потери исходного текста.
- Зарезервированный тип аннотаций command может сохраняться при проверке схемы, но в этом релизе рендеринг по умолчанию его игнорирует, не влияя на рендеринг reference.

### Интеграционная / браузерная верификация

- В локальном WebShell выбрать `.qwen/`, `Makefile` или `LICENSE`; после отправки сообщение пользователя по-прежнему показывает файловый чип.
- Выбрать ресурс MCP; после отправки сообщение пользователя показывает чип MCP, экранированные символы ресурса не обрезаются ошибочно.
- Внедрить кастомный provider, выбрать и отправить; сообщение пользователя показывает кастомные label/value/иконку.
- Обновить страницу или заново открыть ту же сессию; чипы сообщения пользователя сохраняются.

## Риски и меры контроля

- Риск: рост количества межпакетных типов увеличивает площадь PR. Мера контроля — определение минимального `DaemonInputAnnotation` в SDK, чтобы SDK не импортировал типы клиента WebShell.
- Риск: несоответствие метаданных и `content` приводит к смещению рендеринга. Мера контроля — UserMessage использует только валидные и неперекрывающиеся диапазоны; невалидные аннотации игнорируются, ничего из содержимого пользователя не скрывается.
- Риск: персистентная информация кастомных provider'ов может содержать кастомные поля хоста. Мера контроля — сохранение только `id/kind/label/value/serialized/removable`, без неизвестных полей и URL иконок.
- Риск: рост стоимости ревью после расширения скоупа PR1. Мера контроля — явная мотивация в описании коммита: это решение корневой причины, по которой текстовый парсер не может корректно восстановить идентичность файлов/кастомных/MCP ссылок, при сохранении промпта для модели без изменений.
- Риск: слишком узкое имя метаданных верхнего уровня ограничит будущие возможности `/`. Мера контроля — использование `inputAnnotations` как единой точки входа; в этом релизе записывается только `type: 'reference'`.

## Порядок реализации

1. Добавить минимальную структуру меты аннотаций ввода в типы транскрипта SDK.
2. Расширить `appendLocalUserTranscriptMessage` и `DaemonTranscriptStore.appendLocalUserMessage`.
3. Расширить options отправки WebShell, передавая `inputAnnotations` от `useComposerCore` через `App.sendPrompt` до отправки промптов из очереди.
4. При записи оптимистичного эха в `store.appendLocalUserMessage` передавать `inputAnnotations`.
5. Записывать `inputAnnotations` в `PromptRequest._meta` демона и позволить эху пользователя бриджа объединять их в `user_message_chunk.update._meta`.
6. В `transcriptBlocksToDaemonMessages` пробрасывать и санировать `meta.inputAnnotations`.
7. Расширить цепочку props от `DaemonUserMessage` и `MessageList` до `UserMessage`.
8. Расширить параметры `renderUserMessageContent`, открыв рендереру хоста доступ к `inputAnnotations`.
9. Рендеринг `UserMessage` по умолчанию использует только метаданные; при отсутствии метаданных текст показывается как есть.
10. Дополнить юнит-тесты и скриншоты браузерной приемки.

## Ключевые пункты описания PR

Описание PR должно объяснять:

- Это не изменение промпта модели, а сохранение метаданных аннотаций ввода UI, которыми WebShell уже располагает.
- Текстовый парсер не может надежно различать формы вроде `@Makefile`, `@alice`, `@dataset:users`, поэтому метаданные необходимы.
- Старые сообщения по-прежнему совместимо отображаются как исходный текст; кастомные provider'ы получают рендеринг чипов по умолчанию, только если предоставляют `composerTag`.
- Новое поле называется `inputAnnotations`; в этом релизе оно несет только ссылки `@`, в будущем сможет нести команды `/`, команды навыков, кастомные команды и другие структурированные элементы ввода.
- `renderUserMessageContent` остается окончательной точкой переопределения для хоста.
