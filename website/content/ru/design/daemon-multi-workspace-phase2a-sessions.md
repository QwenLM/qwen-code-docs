# Фундамент сессий Фазы 2a с несколькими workspace

> **Исторический статус:** этот документ фиксирует последовательность Фазы 2a /
> ранней Фазы 2b, а не текущую полную поверхность. Модель владения, семантика
> ошибок, границы ресурсов и оставшиеся primary-only маршруты теперь определены
> в
> [`daemon-multi-workspace-hardening.md`](./daemon-multi-workspace-hardening.md).
> Зафиксированные здесь снимки rewind живых сессий, rewind и ограничения shell
> заменены
> [`daemon-multi-workspace-session-file-ops.md`](./daemon-multi-workspace-session-file-ops.md).
> Поздняя primary-only классификация мутаций continue, language и артефактов
> живых сессий также заменена: эти REST-маршруты в единственном числе теперь
> диспетчеризуются во владеющий доверенный рантайм workspace. Другие утверждения
> в рамках фазы также могут быть заменены более поздними проектными записями и
> не должны рассматриваться как текущий инвентарь маршрутов.

## Резюме

Этот документ фиксирует контракт сессий с несколькими workspace для задачи
#6378 после PR `WorkspaceRegistry` Фазы 1, фундамента́льного PR Фазы 2a и
первого PR Фазы 2b по расширению маршрутов. Фаза 2a была разделена на два PR
реализации: PR 1 внедрил изоляцию окружения и защитные механизмы общего
допуска, пока работа с несколькими workspace оставалась под гейтом; PR 2
подключил диспетчеризацию не-primary живых сессий и опубликовал аддитивную
схему capabilities/статуса. PR 1 Фазы 2b добавляет индекс владельца сессий и
расширяет поверхность маршрутов только для сессий, не перенося файловую
систему, память, MCP, настройки, голос, channel workers, ACP или клиенты
workspace в SDK.

Работа с несколькими workspace остается только для сессий. Фаза 2a не
добавила множественные маршруты, `WorkspaceDaemonClient`, ACP/WebSocket с
квалификацией по workspace, перенос file, memory, MCP, settings, voice или
channel-worker. PR 1 Фазы 2b добавляет только множественный алиас списка
сессий, описанный ниже; он по-прежнему не добавляет API клиентов workspace и
не переносит поверхности, не связанные с сессиями. PR 1 не добавлял
capabilities `workspaces[]`, `multi_workspace_sessions`, диспетчеризацию
маршрутов или создание не-primary runtime.

## Фундаментальный контракт

- Флаг `--workspace` можно повторять на уровне парсера CLI, чтобы yargs
  сохранял массив входных данных, а не схлопывал его.
- Быстрый путь для `serve` откатывается к полному парсеру, если присутствуют
  повторяющиеся значения workspace.
- Массив workspace с одним элементом рассматривается как primary workspace и
  сохраняет существующее поведение для одного workspace.
- PR 1 оставлял несколько явных workspace под гейтом до загрузки runtime.
- PR 2 принимает различные невложенные явные workspace для режима с несколькими
  workspace только для сессий.
- Дублирующиеся канонические входные данные workspace по-прежнему явно
  вызывают ошибку.
- Вложенные входные данные workspace по-прежнему явно вызывают ошибку.
- Первый явный workspace является primary workspace и остается зеркалированным
  legacy-полями совместимости `workspaceCwd` / `app.locals.boundWorkspace`.

Внутренний контракт `WorkspaceRuntime` теперь содержит стабильные метаданные
для последующих работ Фазы 2a:

- `workspaceId`: стабильный хэш канонического cwd workspace.
- `workspaceCwd`: канонический cwd workspace.
- `primary`: true для primary runtime.
- `trusted`: метаданные доверия во время загрузки; прямой fallback
  `createServeApp` остается false, если в production не передано явное
  значение trusted.
- `env`: метаданные источника окружения, локального для runtime. В
  production с одним workspace primary runtime теперь получает вычисленный
  эффективный снимок окружения и изменяемый источник окружения, который может
  быть обновлен после перезагрузки окружения демона. Прямой fallback
  `createServeApp` остается метаданными родительского процесса.

Внутренний `WorkspaceRegistry` поддерживает точный поиск по cwd, точный поиск
по id, primary fallback `resolveWorkspaceCwd(undefined)` и разрешение
владельца активной сессии. Разрешение владельца активной сессии сканирует
только сводки runtime bridge; оно не сканирует постоянное хранилище, не
создает дочерние элементы и пока не маршрутизирует никакие запросы.
Дублирующиеся активные владельцы завершаются fail closed как неоднозначный
результат.

`createServeApp` может принимать внедренный реестр для тестов и будущей
сборки. Фундаментальный PR оставил модули маршрутов на входах primary
runtime; PR 2 расширяет только подключение маршрутов живой сессии, SSE и
разрешений сессий реестром, необходимым для диспетчеризации по владельцу.
Существующие legacy `app.locals.boundWorkspace` и `app.locals.fsFactory`
остаются локальными переменными совместимости только для primary.

## Классификация маршрутов Фазы 2a

Первый открытый этап Фазы 2a должен классифицировать все маршруты
`/session/:id/*` перед включением поддержки нескольких явных workspace.

Маршруты, диспетчеризируемые в Фазе 2a:

- `POST /session`
- `GET /session/:id/events`
- `POST /session/:id/prompt`
- `POST /session/:id/cancel`
- `POST /session/:id/permission/:requestId`
- `POST /session/:id/heartbeat`
- `POST /session/:id/detach`
- `GET /session/:id/pending-prompts`
- `DELETE /session/:id/pending-prompts/:promptId`
- `DELETE /session/:id`
- `GET /session/:id/status`

Дополнения, диспетчеризируемые в Фазе 2b:

- `POST /session/:id/load`
- `POST /session/:id/resume`
- `GET /session/:id/context`
- `GET /session/:id/context-usage`
- `GET /session/:id/stats`
- `GET /session/:id/supported-commands`
- `GET /session/:id/tasks`
- `GET /session/:id/lsp`
- `GET /session/:id/hooks`
- `GET /session/:id/artifacts`

Последующие маршруты или маршруты только для primary:

- `GET /session/:id/export`
- `POST /sessions/delete`
- `POST /sessions/archive`
- `POST /sessions/unarchive`
- `PATCH /session/:id/organization`
- мутации групп сессий
- мутации сессий: branch, fork, cd, rewind, shell, model и language
- не относящийся к сессиям `POST /permission/:requestId`
- `/acp`

## Меж-PR требования Фазы 2a

- Сохранять промахи при сканировании как `404 session_not_found`; никогда не
  откатываться к primary.
- Завершаться fail closed, если более одного runtime сообщает об одном и том
  же id активной сессии.
- Держать листинг не-primary постоянных сессий под гейтом, пока владение
  восстановлением, проверки доверия и обнаружение активных сессий не будут
  реализованы вместе.
- Переиспользовать локальные для runtime env-оверлеи PR 1 перед созданием
  не-primary дочерних процессов.
- Переиспользовать допуск `maxTotalSessions` из PR 1 на каждом будущем стыке
  нового создания, чтобы REST и primary `/acp` не могли его обойти, при этом
  attach по-прежнему обходит допуск (admission).
- PR 2 публикует `workspaces[]` и `multi_workspace_sessions` только после
  завершения цикла диспетчеризации живых сессий.
- PR 2 обновляет типы capabilities SDK для аддитивной схемы capabilities, но
  Фаза 2a по-прежнему не добавляет клиент workspace.

## Защитные механизмы PR 1

- Окружение runtime вычисляется из базового окружения демона плюс `.env`
  workspace, окружение настроек и дефолты Cloud Shell без мутации
  родительского `process.env` во время инициализации runtime.
- Помощник окружения намеренно не виртуализирует `QWEN_HOME`, Storage или
  маршрутизацию глобальной конфигурации. Это остается ответственностью
  загрузки демона/базового окружения.
- Запуск ACP-потомка принимает явный `sourceEnv`, а дешевые читатели
  статуса/конфигурации с областью workspace используют внедренное окружение
  вместо прямых чтений `process.env`.
- `maxTotalSessions` — опциональный общедемоновый лимит новых сессий. Он
  покрывает spawn, восстановление load/resume из постоянного хранилища и
  создание сессий branch/fork; attach обходит его. В режиме с несколькими
  workspace, когда оператор оставляет его неустановленным, а лимит
  `maxSessions` на workspace конечен, PR 2 выводит эффективный общий лимит как
  `maxSessionsPerWorkspace * workspaceCount`; режим с одним workspace
  сохраняет исторический неограниченный общий дефолт.
- Стык допуска бриджа — это синхронный хук резервирования. Неудачное новое
  создание освобождает резервирование, предотвращая конкурентную
  перепродажу между runtime, когда появятся не-primary бриджи.
- `/daemon/status.limits.maxTotalSessions` аддитивен. `/capabilities` и типы
  capabilities SDK остаются неизменными, пока PR 2 не снимет гейт с сессий с
  несколькими workspace.

## Замкнутый цикл сессий PR 2

PR 2 снимает явный гейт загрузки с несколькими workspace для режима демона
только для сессий. Несколько явных значений `--workspace` теперь создают один
runtime на канонический workspace, с первым workspace в качестве primary.
Дублирующиеся и вложенные входные данные workspace остаются ошибками
загрузки, поскольку они делают владение сессиями неоднозначным до того, как
какая-либо диспетчеризация на уровне маршрутов сможет безопасно разрешить
запрос.

Продакшен-сборка сохраняет существующие обязанности primary runtime:
идентичность демона, идентичность логов, id сервиса телеметрии, Web Shell,
`/acp`, file, memory, MCP, settings, voice, channel worker и legacy
REST-маршруты без workspace остаются только для primary. Не-primary runtime —
это runtime бриджа/сервисов workspace только для живых REST-сессий. Их
ACP-потомок по-прежнему ленивый: объект бриджа существует при загрузке, но ни
один не-primary потомок не запускается, пока доверенный запрос
`POST /session { cwd }` не потребует новую сессию.

Создание сессии разрешает `cwd` через точное сопоставление канонического cwd
в `WorkspaceRegistry`. Опущенный `cwd` разрешается в primary runtime.
Неизвестный `cwd` возвращает `400 workspace_mismatch`; недоверенный не-primary
`cwd` возвращает `403 untrusted_workspace`; доверенные зарегистрированные
runtime вызывают бридж этого runtime с его собственным каноническим cwd. Это
намеренно избегает сопоставления по префиксу, сопоставления ближайшего
родителя или поиска в постоянном хранилище в Фазе 2a.

Диспетчеризируемые маршруты живых сессий разрешают runtime владельца
сканированием сводок живых бриджей через
`WorkspaceRegistry.resolveLiveSessionOwner(sessionId)`. `not_found`
отображается в `404 session_not_found`, а `ambiguous` — в fail-closed ошибку
сервера. Сканирование синхронное и только по живым; оно никогда не запускает
потомка и никогда не рассматривает промах как fallback на primary.
Диспетчеризируемый набор маршрутов ровно:

- `GET /session/:id/events`
- `POST /session/:id/prompt`
- `POST /session/:id/cancel`
- `POST /session/:id/permission/:requestId`
- `POST /session/:id/heartbeat`
- `POST /session/:id/detach`
- `GET /session/:id/pending-prompts`
- `DELETE /session/:id/pending-prompts/:promptId`
- `DELETE /session/:id`
- `GET /session/:id/status`

`GET /workspace/:id/sessions` разрешает сначала точный id workspace, затем
точный канонический cwd. Primary сохраняет существующее слияние
постоянных/живых и поведение организованного представления. Не-primary
возвращает только живые сессии, отклоняет `archiveState=archived` и отклоняет
запросы organized/group, поскольку это поверхности на основе постоянного
хранилища/организации, зарезервированные для более поздних фаз.

`/capabilities` остается обратно совместимым: `workspaceCwd` по-прежнему
называет primary workspace. Когда зарегистрировано более одного runtime, он
дополнительно публикует `workspaces[]`, `multi_workspace_sessions` и
аддитивные лимиты сессий. `/daemon/status` добавляет те же метаданные
`workspaces[]` и агрегирует счетчики живых сессий между бриджами runtime,
оставляя полные секции workspace только для primary.

PR 2 Фазы 2a не добавляет множественные маршруты, ACP/WebSocket с
квалификацией по workspace, перенос file/memory/MCP/settings/voice/channel-worker,
динамическое добавление/удаление, не-primary постоянные
load/resume/export/archive/delete, branch/fork/cd/rewind, перенос
shell/model/language или API клиентов workspace в SDK.

## Индекс владельца и расширение восстановления PR 1 Фазы 2b

PR 1 Фазы 2b добавляет стык колбэков жизненного цикла бриджа и
`WorkspaceSessionOwnerIndex`, принадлежащий `WorkspaceRegistry`. События
жизненного цикла регистрации/удаления бриджа обновляют индекс при spawn,
load/resume, выходе канала, закрытии, kill и завершении демона. Разрешение
владельца сначала обращается к индексу, верифицирует индексированный runtime
через `getSessionSummary`, отбрасывает устаревшие записи индекса и
откатывается к существующему сканированию живых бриджей. Попадания при
откате кэшируются обратно в индекс. Индекс остается оптимизацией и стыком
согласованности, а не постоянной базой данных владения.

`POST /session/:id/load` и `POST /session/:id/resume` теперь принимают явный
`cwd` для любого доверенного зарегистрированного workspace. Опущенный `cwd`
по-прежнему разрешается в primary runtime. Неизвестный `cwd` возвращает
`400 workspace_mismatch`; недоверенный не-primary `cwd` возвращает
`403 untrusted_workspace`; если тот же id сессии уже жив или восстанавливается
в другом runtime, восстановление завершается fail closed с
`409 session_workspace_conflict`. Гонки восстановления в одном workspace
сохраняют существующий коалесцинг бриджа и поведение `restore_in_progress`.
Восстановление по-прежнему читает постоянное хранилище сессий из
существующего пути хранилища запрошенного workspace и не включает не-primary
export/archive/delete.

Маршруты только для чтения живых сессий, диспетчеризируемые по владельцу,
теперь используют бридж владеющего runtime: context, context-usage, stats,
supported-commands, tasks, lsp, hooks и artifacts. Эти маршруты не мутируют
постоянное хранилище и не требуют состояния, локального для соединения
ACP/WebSocket, поэтому они могут безопасно следовать за живым владельцем.
`GET /session/:id/rewind/snapshots` остается только для primary, поскольку
состояние rewind не входит в замкнутый цикл только для сессий.

`GET /workspaces/:workspace/sessions` — множественный алиас для
`GET /workspace/:id/sessions`. Оба разрешают сначала точный id workspace,
затем точный канонический cwd. Primary workspace сохраняют семантику слияния
постоянных/живых. PR 1 Фазы 2b оставил не-primary workspace только живыми и
отклоняющими представления списка archived или organized.

## Обнаружение постоянных сессий PR 2 Фазы 2b

Листинг сессий доверенных не-primary workspace теперь включает активные
постоянные сессии из хранилища сессий этого workspace и сливает
соответствующие живые сводки без дубликатов. Это завершает сторону
обнаружения потока восстановления Фазы 2b: клиенты могут получить список
доверенного вторичного workspace, найти активную постоянную сессию и затем
вызвать учитывающие workspace `POST /session/:id/load` или
`POST /session/:id/resume` из PR 1 Фазы 2b.

Если у доверенного не-primary workspace нет активных постоянных сессий,
листинг сохраняет прежнее поведение курсора только для живых. Представления
списка не-primary archived, organized и grouped остаются отклоненными,
поскольку поверхности archive/unarchive/delete и организации сессий — это
по-прежнему только primary/работа более поздних фаз.

Работа Фазы 2b на данный момент не добавляет новые теги capabilities, не
изменяет схему `/capabilities`, не меняет типы SDK и не маршрутизирует ACP,
voice, channel-worker, file, memory, MCP, settings, branch/fork/cd/rewind,
shell/model/language, export, archive, delete или поверхности организации в
не-primary runtime.

## Решения по аудиту

- Фундаментальный PR не должен создавать не-primary runtime или смягчать
  какие-либо REST-маршруты.
- Существующие `app.locals.boundWorkspace` и `app.locals.fsFactory` остаются
  локальными переменными совместимости только для primary.
- REST `routeFileSystemFactory` остается отдельным от файловых систем фабрик
  bridge; он не должен использоваться для представления границ не-primary
  bridge.
- Вторичные корни файловой системы IDE не должны повышаться до явных
  workspace runtime.
- Поведение родительского окружения для одного workspace остается совместимым
  до тех пор, пока не будет снят гейт с полноценного режима с несколькими
  workspace.
- Безопасная граница PR 2 — это замкнутый цикл живых сессий плюс аддитивные
  метаданные capabilities/статуса. Если маршруту нужно постоянное хранилище,
  состояние организации, настройки workspace или состояние, локальное для
  соединения ACP, он остается только для primary или на более позднюю фазу.
