## 1. Contexte et problème

qwen-code lie actuellement **Ctrl+O à `TOGGLE_COMPACT_MODE`** : un **interrupteur binaire global** (`compactMode`, persisté dans `settings.ui.compactMode`). Une fois activé :

- il masque la sortie des résultats des outils terminés (Success) ;
- il replie les blocs de réflexion en une seule ligne `Thought for …` ;
- une seule pression **redessine rétrospectivement tout l'historique** (`refreshStatic()` remonte `<Static>`).

Cela crée une fracture globale "**mode compact vs mode détaillé**" : le même historique bascule entièrement entre deux formes totalement différentes selon un interrupteur global, avec une charge mentale importante, des secousses visuelles notables, et en rupture avec la philosophie de conception de l'amont gemini-cli comme de Claude Code.

> **Ce schéma s'empile sur la baseline de partition de [#5661](https://github.com/QwenLM/qwen-code/pull/5661) (déjà fusionnée dans main).** #5661 a refactorisé le rendu par défaut des groupes d'outils : il a étendu `CompactToolGroupDisplay` en un **rendu de résumé partitionné par catégorie** (`ToolCategory` / `TOOL_NAME_TO_CATEGORY` / `CATEGORY_ORDER` / `getToolCategory` / `buildToolSummary`), et a changé la décision de repli de `ToolGroupMessage` en une **partition par type** : avec `forceExpandAll` comme porte inversée, les outils sont **répartis par type** en `collapsibleTools` (read/search/list, via `isCollapsibleTool(name)`) → repliés en résumé de partition `CompactToolGroupDisplay`, et `nonCollapsibleTools` (edit/write/command/agent et Canceled) → **toujours un par un** en `ToolMessage`. **À noter : #5661 est sans rapport avec `compactMode`** — `compactMode` n'affecte plus le rendu des outils, le repli de partition est purement déterminé par le type d'outil + `forceExpandAll`. Cette PR **ne reconstruit pas la baseline de rendu des outils** — elle s'empile sur la baseline de partition de #5661 + l'infrastructure souris de #5751, en ajoutant (1) la suppression du `compactMode` global résiduel, (2) l'écran transcript à détail complet par Ctrl+O, (3) l'expansion en place des blocs d'outils au clic de souris. Voir §3.1 (baseline de partition), §4.1 / §5 (liste de suppression), §9 (découpage en commits empilés).
>
> **Note de révision (rebase sur l'état fusionné de #5661)** : les premières versions de ce document étaient rédigées à partir d'un snapshot initial basé sur l'état de #5661 (`showCompact = (compactMode || allComplete)`, repli du groupe entier dès qu'il est terminé). #5661 a évolué pendant la review vers la **partition par type** ci-dessus et a été fusionné dans main. §3.1 / §4.1 / §4.5 / l'appendice ont été réécrits selon l'implémentation réellement fusionnée : les symboles centraux sont `isCollapsibleTool` / `forceExpandAll` (**ils existent bien**), le `fullDetail` du transcript pose directement `forceExpandAll=true` (au lieu de modifier un `showCompact` qui n'existe plus).

### Objectifs

**Supprimer complètement la distinction de mode global "compact/détaillé"**, s'aligner sur Claude Code :

1. La vue principale de conversation n'a **qu'un seul rendu par défaut stable, orienté concision**, qui ne se déforme plus globalement selon un interrupteur global.
2. **Ctrl+O ne sert qu'à "voir le détail complet de certains blocs"** — ouvrir un **écran de défilement Transcript à détail complet distinct** ; la vue principale reste toujours propre.
3. L'indication en ligne `(ctrl+o to expand)` sert de guide "il y a plus ici, pressez Ctrl+O pour voir l'ensemble dans le transcript".
4. **(follow-up, pas dans cette PR) Expansion en place du détail des blocs au clic de souris** : comme MVP VP-only d'une PR ultérieure — cliquer sur une ligne de résumé de partition repliée déploie en place le détail du groupe entier. **Cette PR ne le livre pas** (raisons au §4.8 : sous partition par type, les outils repliés sont déjà agrégés en une seule ligne, sans cible de clic par outil, il faut redéfinir la granularité du clic ; risque superposé de souris SGR/sélection native ; effort ~250–400 lignes). Le clic sur un bloc de réflexion replié pour ouvrir ThinkingViewer est déjà fourni par main/#5751, cette PR n'y touche pas.

> Instruction explicite de l'utilisateur : **alignons-nous simplement sur Claude Code**. Ce schéma prend pour référence "reproduire fidèlement le modèle ctrl+o = toggleTranscript de Claude Code". L'expansion au clic de souris est un second canal d'interaction superposé (double canal clavier + souris).

## 2. Comparaison du comportement des trois (conclusions d'étude)

| Dimension        | qwen-code (actuel / socle #5661)                                 | Claude Code (réel)                          | gemini-cli (amont)                      |
| ----------- | ------------------------------------------------------------ | -------------------------------------------- | --------------------------------------- |
| Liaison Ctrl+O | `TOGGLE_COMPACT_MODE`                                        | `app:toggleTranscript`                       | `SHOW_MORE_LINES` + `EXPAND_PASTE`      |
| Modèle central    | **binaire global compact/détaillé** (persisté) + repli automatique de partition de #5661 | **écran transcript global** + expansion bloc par bloc | `constrainHeight` global + expansion par outil  |
| Impact sur la vue principale  | un clic redessine rétrospectivement tout l'historique                                         | vue principale constante ; le transcript est un écran distinct              | bascule la contrainte de hauteur, déploie le "dernier tour"            |
| État par bloc    | ❌ aucun                                                        | ✅ `expandedKeys` (par tool_use_id/uuid)     | ✅ `ToolActionsContext.toggleExpansion` |
| Façon de sortir    | repressez Ctrl+O pour revenir                                             | repressez Ctrl+O / Esc revient au prompt                  | repressez Ctrl+O pour replier                        |

**Le "nouveau socle actuel" de qwen = le modèle de partition par type de #5661 (point de départ de ce schéma, pas une ancienne baseline à renverser) :** #5661 a fait évoluer le rendu par défaut des groupes d'outils de "tout afficher / tout masquer selon `compactMode`" vers un **repli partitionné par type d'outil** — quand `forceExpandAll` est faux, les `collapsibleTools` (read/search/list, via `isCollapsibleTool(name)`, hors Canceled) sont repliés en une ligne de résumé de partition `CompactToolGroupDisplay` (agrégée selon `CATEGORY_ORDER` : search/read/list/command/edit/write/agent/other, par ex. `Read 3 files, edited 2 files`), les `nonCollapsibleTools` (edit/write/command/agent + Canceled) **restent toujours un par un** en `ToolMessage` ; les conditions force (confirmation/erreur/shell focalisé/initié par l'utilisateur/sous-agent terminal) posent `forceExpandAll=true` → tout est déployé un par un. **Ce modèle est sans rapport avec `compactMode`** — dans #5661, `compactMode` n'affecte plus le rendu des outils (il ne reste qu'un effet résiduel sur les blocs de réflexion). Ce schéma **conserve intact tout le mécanisme de partition par type** sur ce socle, ne supprime que l'interrupteur `compactMode` global résiduel, et superpose le `fullDetail` du transcript (pose `forceExpandAll=true`).

**Le mécanisme réel de Claude Code (issu de l'analyse du source packagé de `claude-code`) :**

- `defaultBindings.ts` : `'ctrl+o': 'app:toggleTranscript'`.
- `useGlobalKeybindings.tsx` : `setScreen(s => (s === 'transcript' ? 'prompt' : 'transcript'))`, avec télémétrie `tengu_toggle_transcript`.
- `REPL.tsx` : quand `screen === 'transcript'`, rendu de **tout** l'historique par **défilement virtuel**, avec `verbose={true}` (expansion complète forcée) ; le mode `prompt` a une limite d'éléments affichés.
- `CtrlOToExpand.tsx` : rend `(ctrl+o to expand)` à la fin d'un bloc tronqué ; cliquer/presser entre dans le transcript pour voir l'ensemble.
- Il y a aussi `expandedKeys` indépendant (par message), mais **le principal canal d'interaction est l'écran transcript**.

**Le modèle par bloc de gemini-cli (complément d'analyse)** : gemini-cli procède par expansion par outil — `expandedTools` / `toggleExpansion` de `ToolActionsContext` maintiennent l'état d'expansion outil par outil. C'est **la même approche que l'expansion par bloc Alt+T déjà présente dans qwen main (`ThoughtExpandedContext`)** : toutes deux résolvent "déployer un seul bloc en place". Alors que le transcript de ce schéma résout une **dimension différente** — "une revue complète de toute la session" (snapshot gelé en alt-screen, tous les blocs en fullDetail, défilable), les deux sont orthogonales et complémentaires (voir §4.7).

**Avantage clé** : qwen-code possède déjà tout le socle nécessaire pour implémenter l'écran transcript (`ScrollableList`/`VirtualizedList` + `AlternateScreen.tsx` déjà en place), voir §4.4.

## 3. Définition du comportement cible

### 3.1 Baseline par défaut (vue principale) = modèle de partition de #5661

La vue principale applique une règle de rendu unique et stable à **tous les éléments d'historique**, **il n'existe aucun interrupteur global pour la basculer**. Cette baseline **n'est pas créée par ce schéma**, mais c'est le **modèle de partition par type (repli partitionné par type d'outil) déjà en place de [#5661](https://github.com/QwenLM/qwen-code/pull/5661)** — ce schéma le conserve intact, supprimant seulement l'interrupteur `compactMode` global sans rapport avec lui :

| Type de bloc                                                          | Rendu de baseline par défaut (modèle de partition par type de #5661)                                                                                                                                                                 | Visible en entier seulement dans le transcript         |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| Réflexion (gemini_thought / \_content)                              | Résumé sur une ligne `✻ Thought for 3s (ctrl+o to expand)` ; affiché en temps réel pendant le streaming, réduit en résumé une fois stabilisé                                                                                                                            | Oui                               |
| **Outils collapsible** (read/search/list, hors force)              | rangés via `isCollapsibleTool(name)` dans `collapsibleTools`, **repliés** en **ligne de résumé de partition** `CompactToolGroupDisplay` (agrégée selon `CATEGORY_ORDER`, par ex. `Read 3 files, edited 2 files, ran 1 command`)                         | Le détail outil par outil est visible en entier dans le transcript |
| **Outils non-collapsible** (edit/write/command/agent / Canceled) | rangés dans `nonCollapsibleTools`, **toujours un par un** en rendu complet `ToolMessage` (leur sortie est elle-même la réponse) — même terminé, le groupe entier n'est pas replié en résumé                                                                                             | ——                               |
| Groupe mixte (collapsible + non-collapsible coexistants)                    | **ligne de résumé + outils un par un coexistants** : partie collapsible → une ligne de résumé `CompactToolGroupDisplay` ; partie non-collapsible → `ToolMessage` un par un. **Pas de repli du groupe entier**                                                                  | Partiel                             |
| Résultats string/ansi d'outils collapsible terminés                      | repliés par défaut (`shouldCollapseResult = !forceShowResult && Success && isCollapsibleTool(name) && (string\|ansi)` → la zone de résultat n'est pas rendue) ; **les résultats non-collapsible comme Shell/Edit sont toujours affichés** ; diff/plan/todo/task ont chacun leur renderer | Visible en entier dans le transcript               |
| Erreur / en attente de confirmation / initié par l'utilisateur / shell focalisé / sous-agent terminal              | pose `forceExpandAll=true` → tout le groupe un par un en `ToolMessage` ; l'outil déclencheur correspondant reçoit `forceShowResult=true` pour lever le repli du résultat                                                                                                         | ——                               |
| Message texte ordinaire                                                    | Affiché en entier                                                                                                                                                                                                        | ——                               |

Points clés :

- **Le repli de partition est piloté par `forceExpandAll` + `isCollapsibleTool` de #5661** — dans `ToolGroupMessage`, `forceExpandAll = hasConfirmingTool || hasSubagentPendingConfirmation || hasErrorTool || isEmbeddedShellFocused || isUserInitiated || hasTerminalSubagent` (**sans `compactMode`/`allComplete`**). Quand `forceExpandAll` est faux, selon `isCollapsibleTool(name)` (read/search/list, hors Canceled), on extrait `collapsibleTools` → résumé `CompactToolGroupDisplay`, le reste va dans `nonCollapsibleTools` → `ToolMessage` un par un ; quand il est vrai, tous les outils vont dans `nonCollapsibleTools`.
- **Le repli des résultats terminés est piloté par la porte `shouldCollapseResult` de #5661** — dans `ToolMessage`, `shouldCollapseResult = !forceShowResult && status === Success && isCollapsibleTool(name) && (renderer.type === 'string' || 'ansi')`. **À noter la garde supplémentaire `isCollapsibleTool(name)`** : seuls les résultats string/ansi de read/search/list sont repliés, les résultats des outils non-collapsible comme Shell/Edit/Agent sont **toujours visibles**. Dans les scénarios force, `ToolGroupMessage` transmet **un par un** `forceShowResult=true` à l'outil déclencheur (`isUserInitiated || Confirming || Error || pending-agent || sous-agent terminal`).
- **Les conditions force sont la sémantique de sécurité "doit être vu"** — les piles d'erreur, les demandes de confirmation, le shell focalisé, les outils initiés par l'utilisateur ne sont pas repliés par partition grâce à `forceExpandAll`, et les résultats des outils non-collapsible ne sont naturellement pas repliés (plus le `forceShowResult` de l'outil déclencheur). **Les symboles centraux `forceExpandAll` / `isCollapsibleTool` existent bien** (implémentation fusionnée de #5661) ; **il n'est pas besoin** d'un `shouldForceFullDetail.ts` / `COLLAPSIBLE_CATEGORIES` indépendant — la sémantique force est en ligne dans `forceExpandAll`, la porte de repli des résultats est en ligne dans `shouldCollapseResult` (voir §4.5).
- **`fullDetail` doit prendre effet avant les deux early return de `ToolGroupMessage` (point d'implémentation, ne pas régresser)** — avant de calculer `forceExpandAll`, `ToolGroupMessage` a deux retours anticipés qui contournent la logique de partition : (1) **groupe pur-parallèle d'agents** → panneau dense `InlineParallelAgentsDisplay` ; (2) **groupe memory-only terminé** → badge `Recalled/Wrote N memories`. Ces deux-là feraient que sous fullDetail du transcript ce **n'est toujours pas un affichage complet**. Donc les deux early return sont gardés par **`!fullDetail`** : quand fullDetail est vrai, on les saute, laissant chaque outil/agent retomber en `ToolMessage` un par un (`forceExpandAll=true` + `forceShowResult=true` + pas de troncature). Déjà couvert par des tests de régression (un groupe memory-only sous fullDetail est rendu un par un plutôt qu'en badge).

### 3.2 Ctrl+O = ouvrir/fermer l'écran Transcript à détail complet (écran de snapshot gelé distinct)

Reproduire fidèlement le transcript de Claude Code (analysé depuis le source de claude-code) :

- Pressez **Ctrl+O** à tout moment : bascule vers le transcript qui prend en charge tout l'écran, rendant un **snapshot gelé** : fige l'historique au moment de l'entrée, **lève les tronçonnages de hauteur/nombre de lignes de la couche UI** (texte complet des réflexions, sortie des outils aussi complète que possible), prend en charge le défilement haut/bas/page précédente/page suivante/Home/End. Le chemin VP par défaut réutilise l'écran alternatif déjà occupé par la racine ink ; seul le chemin legacy `<Static>` fait écrire temporairement par le composant `AlternateScreen` le DEC `1049` (`\x1b[?1049h`) pour y entrer. ⚠️ « complet » ne désigne que la couche UI — **le contenu déjà retiré par le budget de réponse du modèle ou par la compaction du display de l'historique ne peut pas être restauré depuis l'historique UI** (voir §4.4), ce n'est pas littéralement le « texte complet ».
- **Sémantique du snapshot gelé (incluant pending ; stocke les longueurs plutôt que de cloner l'historique)** : l'historique de qwen-code est en **deux segments** — l'`history: HistoryItem[]` stabilisé (`UIStateContext.tsx:45`) et les `pendingHistoryItems` en cours de streaming (`:123`, concaténés avec des id négatifs au rendu, `MainContent.tsx:456-461`). Le freeze de Claude Code ne stocke en réalité que deux nombres `{ messagesLength, streamingToolUsesLength }` et slice au rendu, plutôt qu'un clonage au moment de l'entrée. **qwen-code gèle donc les deux segments sur cette base, mais sous la forme la plus économique** : l'historique stabilisé ne **stocke que la longueur** `historyLength` (au rendu `history.slice(0, historyLength)`, sans cloner tout l'historique), le segment `pendingItems: [...pendingHistoryItems]` en streaming **stocke une copie superficielle** (pending est une zone temporaire, réécrite ou vidée par la suite, il faut une copie pour figer la forme à cet instant). Le transcript rend `history.slice(0, historyLength)` concaténé au snapshot pending **figé au moment de l'entrée**. L'historique / pending ajouté ensuite en arrière-plan **n'entre pas** dans le transcript, garantissant que le gel ne tremble pas.
- **N'affecte pas les données de l'écran principal** : la conversation/streaming en arrière-plan continue (seuls la zone de saisie/spinner ne sont pas rendus). À la sortie, le chemin VP par défaut restaure l'arbre principal dans le même alt-screen de la racine ; le chemin legacy quitte l'alt-screen temporaire puis remonte l'historique actuel via `refreshStatic()`, garantissant ni duplication, ni manque, ni pollution du scrollback.
- **Touches de sortie** : `Esc` / `q` (style less) / `Ctrl+C` pour fermer ; repressez **Ctrl+O** pour aussi basculer la fermeture. Après la sortie, on revient à l'écran principal et on peut voir le contenu streaming ajouté en arrière-plan pendant l'ouverture du transcript.
- La sémantique de l'indication en ligne `(ctrl+o to expand)` est **uniformisée en "pressez Ctrl+O pour entrer dans le transcript et voir le contexte complet", et non "ici c'est tronqué"**. À noter que le résumé des blocs de réflexion porte toujours cette indication (quelle que soit la longueur du texte original), tandis que la sortie des outils ne porte `+N lines` que lorsqu'elle est tronquée par contrainte de hauteur — les deux conditions de déclenchement sont différentes, c'est attendu (voir §7 #7).

> Analyse : claude-code `ink/components/AlternateScreen.tsx`, `termio/dec.ts:16` (`ALT_SCREEN_CLEAR: 1049`), `screens/REPL.tsx:1325/4184/4381` (frozenTranscriptState + slice), `keybindings/defaultBindings.ts:160-169` (`escape/q/ctrl+c → transcript:exit`).

### 3.3 Relation avec Ctrl+S (`SHOW_MORE_LINES` / `constrainHeight`)

- `SHOW_MORE_LINES` (actuel Ctrl+S) reste inchangé : il lève la contrainte de hauteur de **la zone pending actuelle**, c'est un "voir temporairement plus de lignes pendant le streaming", deux choses orthogonales au transcript.
- Ce schéma **ne touche pas à la liaison Ctrl+S**, pour éviter une surface de changement trop grande en une fois. (Alternative : on pourra évaluer plus tard si `SHOW_MORE_LINES` doit aussi être intégré au transcript, mais pas dans cette itération.)

## 4. Conception de l'architecture

### 4.1 Suppression du compactMode global résiduel (suppression nette par-dessus la baseline de partition de #5661)

> **Clarification du périmètre** : #5661 a déjà fait basculer la baseline de rendu des outils vers le modèle de partition par type, **et `compactMode` dans #5661 n'affecte plus le rendu des outils** (`forceExpandAll` ne référence pas `compactMode` ; `compactToggleHasVisualEffect` a été modifié par #5661 pour ne sonder que `gemini_thought`, plus `tool_group`). ### 4.2 Ajout de la machine à états de l'écran Transcript + capacité alt-screen

**La capacité alt-screen a déjà un composant prêt à réutiliser** : qwen-code utilise l'officiel amont **`ink ^7.0.3`** (à noter : **paquet et version majeure différents** de gemini-cli — gemini-cli utilise le fork `npm:@jrichman/ink@6.6.9`(v6) ; il ne faut **plus** les considérer comme la même version). Plus important, **main a déjà en place `packages/cli/src/ui/components/AlternateScreen.tsx` (PR #5627) directement réutilisable**, sans besoin d'en créer un nouveau, de porter un hook, ni d'introduire un fork ink :

- **Réutiliser le composant existant** : `AlternateScreen.tsx` écrit dans `useEffect` `writeRaw(ENTER_ALT_SCREEN + CLEAR + HIDE_CURSOR)`, au démontage/`process.on('exit')` écrit `writeRaw(SHOW_CURSOR + EXIT_ALT_SCREEN)` ; en interne il utilise `useTerminalOutput()`/`useTerminalSize()`. Le transcript n'a qu'à envelopper `TranscriptView` avec `<AlternateScreen>` pour obtenir le cycle de vie complet "entrer dans l'alt-screen à l'entrée, revenir au buffer normal au démontage".
- **Le chemin interactif par défaut utilise déjà `alternateScreen: true` de la racine ink** : au démarrage, `startInteractiveUI.tsx` calcule une fois la décision VP finale via `shouldUseVirtualViewport(setting, screenReader, isInteractiveTerminal())`, utilisée à la fois pour l'`alternateScreen` d'ink et comme valeur initiale gelée transmise à `AppContainer`. Un terminal interactif normal entre par défaut en VP/alt-screen quand le setting n'est pas spécifié ; `ui.useTerminalBuffer: false` explicite, screen-reader, CI, non TTY ou `TERM=dumb` suivent le chemin legacy `<Static>` + scrollback natif.
- ⚠️ **Le mode VP est déjà en alt-screen permanent via la racine ink, il faut utiliser la prop `disabled` pour éviter une double entrée** : quand la décision VP gelée au démarrage est vraie, si le transcript écrivait encore une fois `?1049h`, cela corromprait l'état du buffer. `AlternateScreen.tsx` fournit donc la prop `disabled?: boolean` (son commentaire : "Skip escape writes when the root Ink renderer already owns the alt screen (VP mode)"). Le transcript est toujours enveloppé par **`<AlternateScreen disabled={useVP}>`** :
  - Mode non VP (`useVP=false`) : le composant écrit normalement `ENTER_ALT_SCREEN`/`EXIT_ALT_SCREEN`, entre et sort de l'alt-screen ;
  - Mode VP (`useVP=true`) : on passe `disabled` pour sauter l'écriture des séquences d'échappement, car la racine ink est déjà dans l'alt-screen, le transcript se rend directement dans ce buffer en remplaçant l'arbre de contenu principal.
- **Convergence de la décision de dégradation / disponibilité** : plus besoin de la décision heuristique floue `isAltScreenSupported()`. La décision converge vers deux critères clairs — (1) **être déjà dans l'alt-screen ou non est décidé par `useVP`** (décide s'il faut passer `disabled`) ; (2) **protection non TTY**. ⚠️ **Clarification de l'état actuel (analyse)** : `AlternateScreen.tsx` n'a **actuellement pas** de protection `process.stdout.isTTY` (`writeRaw(ENTER_ALT_SCREEN…)` inconditionnel dans `useEffect`). Mais le TUI lui-même ne rend que si `interactive` est vrai, sans prompt `interactive = process.stdin.isTTY ?? false` (`config.ts:1532`) — **en non TTY, on n'entre par défaut pas du tout dans le rendu interactif**, TranscriptView/AlternateScreen ne sont pas montés ; le seul cas limite est `-i` explicite (force interactive alors que stdout peut être non TTY). **À implémenter** : ajouter à `AlternateScreen` une garde `process.stdout.isTTY` (décider avant d'écrire les séquences d'échappement, en non TTY ne pas prendre en charge tout l'écran, se dégrader en rendu dans le buffer normal), s'aligner sur les conventions existantes du dépôt (`startInteractiveUI.tsx:77/81`, `notificationService.ts:53` etc. décident tous `isTTY` avant d'écrire des séquences d'échappement terminal). Changement minimal, c'est un "filet d'alignement sur la convention", avec le test unitaire correspondant.

État (**source unique de vérité : le `useState` de `AppContainer`, détenu localement, consommé au sommet — pas exposé au large `UIStateContext`**) :

> **Choix de conception (analyse : cohérent avec ThinkingViewer + REPL-local de claude-code + précédent gemini-cli)** : le transcript est un état UI unique "ouvert par la touche globale Ctrl+O, consommé dans le layout au sommet", **sans consommateur profond**. L'overlay similaire le plus récent de ce dépôt, `ThinkingViewer`, place justement l'état canonique dans le `useState` local de `AppContainer` (`thinkingViewerData`), ne transmettant que l'action `open` minimale via le **dédié** `ThinkingViewerContext`, **sans** le fourrer dans le large `UIStateContext` ; l'état de l'écran transcript de claude-code reste aussi local au sommet de `REPL`. Donc le transcript **reste local à `AppContainer`** également, rendu conditionnellement dans le JSX au sommet de `AppContainer` comme `<ThinkingViewer>`, **sans** projection via `UIStateContext`/`UIActionsContext`. (Note : **le code d'implémentation est déjà ainsi** — `transcriptFreeze` est un useState local de `AppContainer`, il n'y a aucun champ transcript dans `UIStateContext` ; le document initial écrivait à tort "exposé à UIStateContext", c'est corrigé ici.)

- **canonique (local)** : `AppContainer` porte via `useState` `transcriptFreeze: { historyLength: number; pendingItems: HistoryItemWithoutId[] } | null` (`HistoryItemWithoutId` est le type des éléments de `pendingHistoryItems`), `isTranscriptOpen = transcriptFreeze != null` en est directement dérivé.
- **action (closure locale)** : `openTranscript()` (prend le snapshot à deux segments : `setTranscriptFreeze({ historyLength: history.length, pendingItems: [...pendingHistoryItems] })`) / `closeTranscript()` (pose null) / `toggleTranscript()` — tous des callbacks locaux de `AppContainer`, appelés directement par la gestion des touches globales (§4.3), sans passer par `UIActionsContext`.
- **Moment et sémantique du snapshot** : chaque `openTranscript()` **reprend** le snapshot actuel ; `closeTranscript()` le vide. C'est-à-dire que le transcript est figé à "cet instant d'ouverture", le refermer puis le rouvrir le rafraîchit au plus récent — pas un gel permanent à la première ouverture. À noter que le snapshot ne **stocke que la longueur pour l'historique stabilisé** (`historyLength`, au rendu `history.slice(0, historyLength)`, aligné sur Claude Code qui stocke `messagesLength` plutôt que de cloner), et **stocke une copie superficielle pour la zone pending en streaming** (`[...pendingHistoryItems]`, car pending est une zone temporaire réécrite/vidée par la suite, il faut une copie pour figer la forme à cet instant). **On ne clone pas tout l'historique**.
- **`isTranscriptOpen` n'est pas intégré à l'agrégat `dialogsVisible`** (voir l'analyse Esc/touches de §4.3 — l'intégration nuirait à des logiques comme "Esc ne peut annuler la requête que si Responding et sans dialog") ; le masquage du composer est naturellement atteint par le transcript qui prend en charge tout l'écran via l'alt-screen, sans dépendre de `dialogsVisible`.

### 4.3 Réécriture de la gestion de la touche Ctrl+O

Dans `AppContainer.handleGlobalKeypress` :

```ts
// 删除：TOGGLE_COMPACT_MODE 分支
// 新增：
} else if (keyMatchers[Command.TOGGLE_TRANSCRIPT](key)) {
  toggleTranscript();           // open <-> close
}
```

- Ajout de `Command.TOGGLE_TRANSCRIPT = 'toggleTranscript'`, liaison par défaut `[{ key: 'o', ctrl: true }]`.

**Attribution des touches (éviter la course à double traitement)** : `KeypressContext` est une **diffusion, sans flag consumed** (`KeypressContext.tsx:655`, tous les abonnés `useKeypress` reçoivent la même touche). Il faut donc un **propriétaire unique**, les règles sont :

- **Ctrl+O n'est traité que par le `handleGlobalKeypress` global** (la sémantique de bascule vaut pour ouvrir/fermer). **Le propre `useKeypress` de TranscriptView ne traite jamais Ctrl+O**, sinon une touche serait répondue à deux endroits → course fermer-puis-rouvrir.
- **Esc / q / Ctrl+C pour fermer le transcript : traité par le `handleGlobalKeypress` global, et doit être la [toute première] branche de `handleGlobalKeypress`** — ⚠️ à noter que la première branche actuelle est justement `Command.QUIT` (Ctrl+C, `AppContainer.tsx:3104`), la seconde est `Command.EXIT` (Ctrl+D, `:3121`), la troisième seulement `ESCAPE` (`:3132`), et en tête de la branche `ESCAPE` il y a encore la garde vim `if (vimEnabled && vimMode==='INSERT') return;`. Donc la branche de fermeture du transcript doit être **avant tout cela** — avant QUIT/Ctrl+C, avant EXIT, avant la branche ESCAPE et sa garde vim INSERT — court-circuit :
  ```ts
  const handleGlobalKeypress = (key) => {
    // 必须是整个 handleGlobalKeypress 的第一个分支：
    // 早于 QUIT(Ctrl+C) / EXIT(Ctrl+D) / ESCAPE 分支（及其 vim INSERT 守卫）
    if (isTranscriptOpenRef.current &&
        (key.name === 'escape' || key.name === 'q' || (key.ctrl && key.name === 'c'))) {
      closeTranscript(); return;
    }
    if (keyMatchers[Command.QUIT](key)) { ... }   // 现有 :3104
    ...
  ```
  Sinon : avec le transcript ouvert, presser Ctrl+C déclencherait d'abord la sortie/`ctrlCPressedOnce` ; presser Esc serait avalé par la garde vim INSERT sans pouvoir fermer le transcript. Comme cette branche est gardée par `isTranscriptOpenRef`, elle n'agit que quand le transcript est ouvert, sans impact sur l'édition vim normale. **Tests** : `Ctrl+C closes transcript and does NOT set quit/ctrlCPressedOnce` ; `Esc closes transcript even when vim INSERT mode is active`.
  - **Pourquoi `q` (touche lettre ordinaire) est sûr** : cette branche est gardée par `isTranscriptOpenRef`, elle ne correspond que quand le transcript est ouvert (où le composer est pris en charge par l'alt-screen, sans focus de saisie de texte) ; quand le transcript est fermé, `q` retombe directement dans le flux de saisie normal, sans impact. Pas besoin de nouvelle liaison `Command`, une correspondance en ligne suffit.
- Comme `isTranscriptOpen` **n'est pas intégré à `dialogsVisible`**, il **ne passe pas** par `useDialogClose` ; l'Esc du transcript est traité indépendamment dans la branche de préfixe globale ci-dessus (`useDialogClose` reste inchangé).
- Pour éviter la clôture périmée, ajout de `isTranscriptOpenRef` (calqué sur le modèle existant `dialogsVisibleRef`, `AppContainer.tsx:2425`).

### 4.4 Composant d'écran Transcript (réutilisation du socle)

Nouveau `components/TranscriptView.tsx`, enveloppé à l'extérieur par **`<AlternateScreen disabled={useVP}>` réutilisé existant** (§4.2 : en mode VP la racine ink occupe déjà l'alt-screen, on passe `disabled` pour sauter l'écriture des séquences d'échappement ; en mode non VP on entre et sort normalement de l'alt-screen ; en non TTY on se dégrade en rendu dans le buffer normal via la garde `process.stdout.isTTY` **à ajouter**, voir §4.2) :

- **Données (snapshot gelé à deux segments)** : `[...history.slice(0, freeze.historyLength), ...freeze.pendingItems]` — préfixe d'historique + copie pending figée au moment de l'entrée (voir §3.2). Les éléments ajoutés ensuite en arrière-plan n'entrent pas, évitant les secousses de défilement.
- **Conteneur de rendu (attention au gating)** : `ScrollableList`/`VirtualizedList` **existent déjà dans main** (composants Ink 7 standard, pas un fork Ink ; `ScrollableList.tsx` a `scrollBy/scrollTo/scrollToEnd/scrollToIndex` et PageUp/Down/Home/End/molette), utilisés par `MainContent` dans le chemin VP/viewport-virtuel par défaut ; seuls l'opt-out explicite, screen-reader, CI, non interactif ou terminal incompatible retombent sur `<Static>` + pending. Le transcript **réutilise inconditionnellement** ces deux composants (découplé du gating de l'écran principal, gérant lui-même son conteneur de défilement). ⚠️ Ces composants sont relativement récents, les performances de défilement sur longues sessions, le défilement clavier, le réagencement au resize doivent être inclus dans les tests (§8), on ne peut pas supposer une "réutilisation à coût nul".
- **`estimatedItemHeight` (estimation de hauteur pour le défilement virtuel, doit être augmentée/adaptative)** : `MainContent` utilise actuellement une constante `estimatedItemHeight=3` pour `VirtualizedList`. Le transcript rend en `fullDetail` (texte complet des réflexions, sortie complète des outils), **chaque élément fait bien plus de 3 lignes**, conserver 3 fausserait la barre de défilement/le positionnement et déréglerait les sauts PageUp/Down. Le transcript doit utiliser un **`estimatedItemHeight` plus grand ou adaptatif** (estimé par type de contenu, ou corrigé par le mécanisme de remplissage de hauteur mesurée de `VirtualizedList`). Cette estimation est incluse dans les tests (§8).
- **Expansion complète (prop `fullDetail`)** : introduire un `fullDetail` explicite dans le chemin de rendu, remplaçant la déduction par `!compactMode`. Quand `fullDetail=true` : blocs de réflexion `expanded={true}` ; la sortie des outils doit **simultanément** satisfaire deux points pour être considérée comme libérée du recadrage de hauteur UI — (a) `availableTerminalHeight={undefined}` (vérifier que `ToolGroupMessage.tsx:357-365` rend ainsi `availableTerminalHeightPerToolMessage` undefined) ; (b) désactiver la contrainte de hauteur de `MaxSizedBox`, `sliceTextForMaxHeight`, le `shellStringCapHeight/shellOutputMaxLines` du shell (`ToolMessage.tsx:67-74,750-756`). ⚠️ **Conserver le budget de réponse du modèle et la compaction du display de l'historique interactif** — ce sont des frontières de corps de requête et de stockage de session, pas du ressort de l'expansion UI du transcript, évitant qu'une seule sortie énorme n'entraîne la requête, le fichier de session ou le défilement virtuel.
- **Frontière de recadrage en trois couches (important, éviter de trop promettre)** : (1) **couche réponse du modèle** : le preview du producteur Shell/MCP et le budget de lot final raccourcissent les `responseParts` envoyés au modèle, le texte complet peut n'être conservé que dans un artefact de sortie temporaire ; le riche `resultDisplay` est indépendant de cela, MCP peut conserver le display transformé complet au niveau du producteur. (2) **couche historique interactif** : avant écriture dans l'historique UI/la session, `compactResultDisplayForInteractiveHistory` / la compaction d'enregistrement recompriment au niveau caractère les display riches trop grands. (3) **couche UI** : `MaxSizedBox`/`sliceTextForMaxHeight` etc. recadrent selon la hauteur du terminal. **Le transcript ne peut lever que la couche 3** ; il ne peut pas restaurer le contenu déjà retiré de la réponse du modèle ou du display de l'historique. Règle : conserver les marqueurs de troncature/compaction existants ; « lire l'artefact de sortie persisté et l'afficher » est listé comme **amélioration optionnelle ultérieure**, pas dans cette itération. Les textes i18n ne doivent pas affirmer « voir la sortie complète des outils », mais « voir le contexte complet (hors parties recadrées par le budget de réponse du modèle ou la frontière de stockage de session) ».
- **Répartition clavier** : le propre `useKeypress` de TranscriptView (`isActive: isTranscriptOpen`) **ne traite que les touches de défilement** (haut/bas/page précédente/page suivante/Home/End). **Les touches de fermeture (Esc/q/Ctrl+C/Ctrl+O) sont toutes traitées par le `handleGlobalKeypress` global** (§4.3), TranscriptView n'y touche pas, éliminant la double réponse à la diffusion.
- **Modèle de rendu (stratégie unique claire, lever l'ambiguïté)** : une seule racine ink ne peut rendre linéairement qu'un seul arbre. Quand le transcript est ouvert, le layout au sommet **remplace l'arbre de contenu principal par `TranscriptView` enveloppé de `<AlternateScreen disabled={useVP}>`** (`MainContent` est démonté du rendu, **plus dessiné**) ; la conversation/streaming en arrière-plan ne met à jour que la **couche données** (`history`/`pendingHistoryItems` continuent de croître), mais **n'est pas dessinée**. À la sortie, le chemin VP par défaut reste dans l'alt-screen déjà occupé par la racine et React restaure l'arbre principal ; le chemin legacy `<Static>` quitte vers le buffer normal via `AlternateScreen`, puis remonte l'historique via `refreshStatic()`, garantissant que l'écran principal n'a ni duplication, ni manque, ni décalage.
- **Supprimer/garder `refreshStatic` pendant l'ouverture du transcript (éviter de polluer le scrollback de l'écran principal)** : des chemins internes comme `useResizeSettleRepaint` (comme le resize) peuvent déclencher `refreshStatic` pendant l'ouverture du transcript — si on laisse faire, il écrirait/réagencerait le contenu principal dans le **scrollback du buffer normal**, alors que l'écran est occupé par l'alt-screen, provoquant un décalage de l'écran principal ou une pollution du scrollback après la sortie. Règle : **garder `refreshStatic` avec `isTranscriptOpenRef`, le sauter toujours pendant l'ouverture du transcript** ; à la sortie du transcript, faire une seule fois `refreshStatic()` pour redessiner l'écran principal (c'est-à-dire le point précédent). Cela clarifie "le scrollback du buffer normal de l'écran principal n'est pas pollué par les écritures pendant l'alt-screen". **Test** : pendant l'ouverture du transcript, un tour d'appel d'outil se termine en arrière-plan / un resize est déclenché, après la sortie ce contenu de tour apparaît exactement une fois sur l'écran principal, le scrollback n'est pas corrompu.
- **En-tête/pied de page** : titre (par ex. `Transcript — ↑↓ scroll · Ctrl+O/Esc/q to close`), `initialScrollIndex` initial défilé vers le bas (aligné sur Claude Code qui ouvre directement au plus récent).

### 4.5 Introduction de la liaison `fullDetail` sur la baseline de #5661 (le chemin transcript pose `forceExpandAll=true`)

La baseline de partition par type de #5661 a déjà établi les deux niveaux de décision "quels outils sont repliés en résumé de partition" (partition `forceExpandAll` + `isCollapsibleTool`) et "replier ou non les résultats terminés" (porte `shouldCollapseResult`). Cette PR **ne réécrit pas ces deux niveaux**, elle ajoute seulement un signal `fullDetail` explicite, permettant au chemin transcript de **lever globalement** le repli de partition + le repli des résultats + la contrainte de hauteur. **Avantage clé** : sous la baseline type-based, le transcript n'a qu'à intégrer `fullDetail` dans `forceExpandAll` (`forceExpandAll = fullDetail || hasConfirmingTool || ...`) — un seul point désactive à la fois la partition (tous les outils vont dans `nonCollapsibleTools` rendus un par un) et active la liaison `forceShowResult` outil par outil pour lever le repli des résultats, **sans besoin de modifier un `showCompact` qui n'existe plus**.

- **Les deux niveaux de décision déjà en place de #5661 (conservés)** :
  - `forceExpandAll` de `ToolGroupMessage` (`fullDetail || hasConfirmingTool || hasSubagentPendingConfirmation || hasErrorTool || isEmbeddedShellFocused || isUserInitiated || hasTerminalSubagent`) vrai → saute la partition par type, tous les outils un par un en `ToolMessage` ; faux → répartition selon `isCollapsibleTool` en collapsible (résumé) / non-collapsible (un par un).
  - La prop `forceShowResult` de `ToolMessage` via `shouldCollapseResult = !forceShowResult && status === Success && isCollapsibleTool(name) && (string|ansi)` décide si les résultats string/ansi des outils collapsible terminés sont repliés. Dans les scénarios force/fullDetail, `ToolGroupMessage` transmet à l'outil `forceShowResult={fullDetail || isUserInitiated || Confirming || Error || pending-agent || sous-agent terminal}`.
  - **Les conditions force ci-dessus reprennent la sémantique de sécurité "erreur/en attente de confirmation/initié par l'utilisateur/shell focalisé/sous-agent doit être entièrement visible"** — cette PR les conserve telles quelles, **n'ajoute pas** `shouldForceFullDetail.ts`, **ne migre** aucune décision.
- **Blocs de réflexion** : `HistoryItemDisplay` fait passer `expanded` des blocs de réflexion d'une dépendance à `compactMode` à `resolvedThoughtExpanded = fullDetail || (thoughtExpanded ?? contextThoughtExpanded)` (§4.7) — chemin transcript fullDetail, ou l'interrupteur par bloc Alt+T de main, l'un des deux vrai suffit à déplier ; en état normal de la vue principale `fullDetail=false`.

**La liaison de `fullDetail` (prend effet simultanément quand le chemin transcript = true)** :

Quand `fullDetail=true` (transcript), il faut simultanément remplir les points suivants pour être vraiment "outil par outil, complet sans troncature" :

1. **Poser `forceExpandAll=true`** (intégrer `fullDetail` dans `forceExpandAll`) — lever la partition par type de #5661, tous les outils vont dans `nonCollapsibleTools` rendus un par un en `ToolMessage` (plutôt que d'agréger la partie collapsible en ligne de résumé de partition) ;
2. **Transmettre `forceShowResult=true` outil par outil** (intégrer `fullDetail` dans `forceShowResult`) — le `!forceShowResult` de `shouldCollapseResult` ne correspond plus, les résultats string/ansi des outils collapsible terminés sont aussi dépliés (les résultats non-collapsible sont de toute façon affichés) ;
3. **Lever la contrainte de hauteur `MaxSizedBox`** — quand fullDetail, `ToolGroupMessage` transmet à chaque `ToolMessage` `availableTerminalHeight={undefined}` ; dans `ToolMessage`, `availableHeight` devient donc undefined, `MaxSizedBox maxHeight` est illimité, le `isCappingShell` du shell (incluant `!forceShowResult`) est levé. ⚠️ **Conserver le budget de réponse du modèle et la limite de caractères du display de l'historique** — distinguer "le recadrage de hauteur de ligne (pour l'UI actuelle, le transcript le lève)" et "la frontière de requête/stockage de session (le transcript ne la lève pas)" ;
4. **`expanded` des blocs de réflexion** — le composant `fullDetail` de `resolvedThoughtExpanded` du chemin transcript est vrai (voir ci-dessus).

**Flux de données de `fullDetail` (qui calcule, qui transmet, valeur par défaut)** :

- `fullDetail` est une prop explicite de `HistoryItemDisplay` / `ToolGroupMessage`, **calculée et transmise par le parent selon le contexte de rendu**, pas lue depuis un context (éviter de recréer un état global implicite).
- **Vue principale** (`MainContent`) : ne transmet pas `fullDetail` (par défaut `false`). "Quels groupes d'outils doivent être entièrement affichés" est entièrement décidé par les conditions `forceExpandAll`/`forceShowResult` déjà en ligne dans `ToolGroupMessage` de #5661 (les entrées comme `embeddedShellFocused`/`activeShellPtyId` sont déjà détenues et transmises par `HistoryItemDisplay`), **pas besoin de calculer un booléen force séparé dans `MainContent`**.
- **transcript** (`TranscriptView`) : transmet toujours `fullDetail={true}` à tous les éléments, déclenchant la liaison ci-dessus.

### 4.6 Interactions en arrière-plan pendant l'ouverture du transcript (dialogues de confirmation / resize)

Le transcript prend en charge tout l'écran via l'alt-screen, mais la conversation en arrière-plan continue — cela implique quelques règles d'interaction à clarifier :

1. **Confirmation bloquante/dialogue (anti-deadlock, doit être traité, couvrir tous les types)** : la confirmation bloquante **n'est pas seulement `WaitingForConfirmation`** — `DialogManager.tsx` rend aussi `shellConfirmationRequest`(ShellConfirmationDialog), `loopDetectionConfirmationRequest`(LoopDetectionConfirmation), `confirmationRequest`(ConsentPrompt), `confirmUpdateExtensionRequests`(ConsentPrompt), `providerUpdateRequest`(ProviderUpdatePrompt) etc. Si l'un d'eux est masqué par l'alt-screen, l'utilisateur ne le voit pas, ne peut pas répondre → **deadlock**. Règle : **quand une confirmation bloquante/un dialogue quelconque nécessite une entrée utilisateur, `closeTranscript()` automatiquement** (ajouter dans `AppContainer` un `useEffect` surveillant l'union de ces états de requête + `streamingState===WaitingForConfirmation`, l'un vrai quitte l'alt-screen), laissant l'utilisateur voir et répondre. C'est plus simple et sans ambiguïté que "rendre à nouveau les divers cadres de confirmation dans l'alt-screen". **Les tests doivent couvrir un par un chaque type de confirmation bloquante déclenchant la fermeture automatique** (§8).
2. **Resize de fenêtre** : redimensionner le terminal pendant l'ouverture du transcript, `VirtualizedList` doit se réagencer à la nouvelle largeur, recalculer les hauteurs de ligne. Réutiliser sa réponse au resize existante suffit ; à la sortie du transcript, le `refreshStatic()` de §4.4 réagence aussi l'écran principal. Les tests doivent couvrir "après un resize dans le transcript, la position de défilement ne s'effondre pas".
3. **Soumission automatique de la file de messages (garde, éviter l'envoi silencieux)** : la logique de vidange (drain) de la file de messages de `AppContainer.tsx` a une garde `if (dialogsVisible) return;`, évitant de soumettre silencieusement automatiquement les messages en file quand un dialogue est ouvert. Comme `isTranscriptOpen` **n'est pas intégré à `dialogsVisible`** (§4.2/§4.3), cette garde ne couvre pas l'état d'ouverture du transcript. Règle : **ajouter à cette logique de drain `|| isTranscriptOpenRef.current` (ou condition équivalente)**, garantissant que pendant l'ouverture du transcript les messages en file ne sont **pas envoyés automatiquement**, et qu'à la sortie du transcript la vidange reprend normalement. **Test** : pendant l'ouverture du transcript, les messages en file ne sont pas soumis automatiquement, après la sortie la vidange reprend.

### 4.7 Relation avec le mécanisme par bloc de réflexion existant de main (coexistence complémentaire, pas de conflit)

Après la fusion de l'amont main, le dépôt a déjà un **mécanisme d'expansion de réflexion par bloc**, qui **coexiste de façon complémentaire** avec le transcript de session entière de ce schéma, chacun répondant à des besoins différents :

- **Capacités par bloc déjà fournies par main** :
  - `ThoughtExpandedContext` — `Alt+T` (`Command.TOGGLE_THINKING_EXPANDED`) bascule en place l'expansion/repli d'**un seul bloc de réflexion** ;
  - `ThinkingViewer` / `ThinkingViewerContext` — voir le **texte complet** d'un seul bloc de réflexion ;
  - Flux de données associés : props `thoughtExpanded` / `thinkingFullText` des blocs de réflexion, `buildThinkingFullTextMap`, `ClickableThinkMessage`.
- **Décision de l'expanded des blocs de réflexion après fusion** : au rendu, `expanded = isPending || fullDetail || resolvedThoughtExpanded` pour les blocs de réflexion — l'une des trois sources vraie suffit à déplier :
  - `isPending` : texte complet en temps réel pendant le streaming (§4.5) ;
  - `fullDetail` : toujours vrai pour le chemin transcript (§4.5) ;
  - `resolvedThoughtExpanded` : l'interrupteur par bloc Alt+T de main.
    La transformation `fullDetail` de ce schéma **ne reprend que les deux premières**, sans toucher à `resolvedThoughtExpanded` — le mécanisme par bloc est conservé tel quel.
- **Pourquoi pas de conflit (réponse directe à la préoccupation du reviewer "le besoin initial de l'utilisateur est par bloc")** : le besoin "déplier en place un seul bloc de réflexion" qui préoccupe le reviewer est **déjà satisfait par Alt+T / ThinkingViewer de main** ; le transcript de ce schéma résout une **autre dimension** — "une revue complète de toute la session" (snapshot gelé en alt-screen, tous les blocs rendus en fullDetail, défilable). Les deux ont des objectifs différents, des canaux d'entrée différents (Alt+T vs Ctrl+O), des portées différentes (un bloc vs session entière), **orthogonaux et complémentaires**, pas d'alternative exclusive.

### 4.9 Complétion de la couche de données du détail complet du transcript (éliminer l'état intermédiaire de "repli de second niveau")

**Contexte** : cette PR définit Ctrl+O comme "l'écran transcript à détail complet" (§3.2) — la vue principale conserve le résumé de partition concis de #5661, Ctrl+O fait apparaître à tout moment "l'enregistrement complet", tous les éléments rendus en `fullDetail`. La conception **promet** que la sortie des outils dans le transcript est **entièrement déployée, pas repliée, pas tronquée par hauteur** ; en implémentation, cela est atteint par un seul signal `fullDetail` intégré dans `forceExpandAll` + `forceShowResult` outil par outil + `availableTerminalHeight=undefined` (§4.5).

**Problème (mesuré lors de l'acceptation, §3.4)** : le modèle de "repli en trois couches" de l'utilisateur est bloqué à la deuxième couche — la première couche (vue principale) `✔ read 1 file, listed 1 dir` le résumé de partition doit être conservé ; la deuxième couche (Ctrl+O actuellement) une ligne par outil + **résumé court** (`列出文件 Listed 3 items` / `Grep Found 4 matches` / `读取文件 README.md`) ; alors que **la couche la plus détaillée manque** (entrées de répertoire réelles, lignes de correspondance grep, texte complet du fichier). Les **outils en lecture seule collapsible** comme `read_file` / `ls` / `grep` / `glob` n'atteignent que le niveau résumé sous le transcript, violant la sémantique "détail complet".

**Cause racine (couche de données, pas interrupteur de repli)** : après analyse, la chaîne `fullDetail → forceExpandAll / forceShowResult / availableTerminalHeight=undefined` de §4.5 **prend effet entièrement et correctement** ; le problème est que le frontend ne peut tout simplement pas obtenir le détail complet :

- `ToolResult` a deux voies de contenu (`packages/core/src/tools/tools.ts:443+`) : `llmContent` ("factual outcome", complet) et `returnDisplay` (le commentaire précise "user-friendly **summary**").
- Le `returnDisplay` de `ls` / `grep` / `ripGrep` / `read_file` ne contient que le résumé (`Listed N` / `Found N` / `''`), le contenu complet ne va que dans `llmContent` (analyse : les retours de `ls.ts` / `grep.ts` / `ripGrep.ts` / `read-file.ts`).
- La structure d'affichage des outils du frontend `IndividualToolCallDisplay` (`packages/cli/src/ui/types.ts:65`) **n'a que `resultDisplay`**, pas de champ de contenu complet ; le point de conversion `useReactToolScheduler.ts:330` ne prend que `response.resultDisplay` (le résumé).
- Le contenu complet arrive bien au frontend via `ToolCallResponseInfo.responseParts` (`turn.ts:116`), mais c'est un enveloppement `functionResponse`, `partToString` / `getResponseTextFromParts` ne prennent que `part.text`, **sans lire `functionResponse.response.output`** (`partUtils.ts:61-69`, `generateContentResponseUtilities.ts:14`) — les parts reçues par le frontend contiennent le contenu complet, mais **il n'existe pas de helper prêt à l'en extraire**.

**Découverte clé : le détail complet est en réalité déjà naturellement persisté (détermine la direction du schéma)**

- `convertToFunctionResponse(...)` (`coreToolScheduler.ts:679-714`) écrit le **`llmContent` complet** dans `functionResponse.response.output` (string directement ; array extrait **tout** le `text` et le concatène, les médias vont dans `parts`) — c'est-à-dire que les parts du résultat d'outil **contiennent déjà le détail complet**.
- Le `ChatRecord.message` persisté stocke justement `response.responseParts` (analyse : les points d'appel `recordToolResult(...)` `coreToolScheduler.ts:4009`, `Session.ts:3334/4404` etc. transmettent tous `responseParts`), c'est le **functionResponse complet**, pas le résumé.
- Donc le détail complet est en place sur les trois chemins, de même source : **live** (`trackedCall.response.responseParts`) / **resume** (`record.message.parts`, cas tool_result de `resumeHistoryUtils`) / **relecture ACP** (`HistoryReplayer.replayToolResult` transmet déjà `message: record.message.parts` à `emitResult`). La "persistance" est **naturellement satisfaite** au niveau des données, sans besoin de nouveau champ de persistance (cette hypothèse est gardée par le test "protection de l'hypothèse du schéma Y" de §8 — affirmer que le `output` complet de `message.parts` n'est ni perdu ni détourné vers l'API `compressedHistory` à travers les quatre étapes recording / loadSession / resume / relecture ; **en cas d'échec on retombe sur le schéma X**).

**Schéma Y (source de données complète unique + extraction au niveau affichage, aligné sur claude code)**

Le mécanisme de claude code est "**conserver le complet au niveau stockage, tronquer selon `verbose` au niveau affichage**", sans scinder `llmContent`/`returnDisplay`, le transcript reste à détail complet après resume (analyse : `claude-code/src/screens/REPL.tsx:4185-4194,4381-4382,4402` frozen transcript = snapshot des messages en mémoire + `verbose=true` ; `src/utils/toolResultStorage.ts`, `sessionStorage.ts` persistent le contenu complet/références de fichiers). Le contenu complet de qwen étant déjà persisté dans les parts, on adopte la même approche — **pas de nouveau champ de persistance, extraire le texte complet pour l'affichage depuis le functionResponse déjà existant**.

- **Pas X (nouveau champ `contentForDisplay` traversant core→sérialisation→relecture→frontend, 8 points)** : **redondance de contenu** avec les `responseParts` déjà persistés (le même contenu complet stocké en deux exemplaires), élargit le schéma de persistance et la surface de migration.
- **Pas B (modifier `returnDisplay` outil par outil pour porter le complet)** : viole la sémantique `returnDisplay`="summary", modifie plusieurs outils.
- **Pas "éparpiller le protocole dans le frontend"** : fragile comme le dit la cause racine — mais le schéma Y extrait via **un seul helper core centralisé**, pas éparpillé en plusieurs endroits.

**Points de changement (schéma Y)** :

1. **Nouveau helper d'extraction dans le core** `getToolResponseDisplayText(parts: Part[]): string | undefined` (aux côtés de `getResponseTextFromParts`). **Règle de priorité implémentable** — les médias sont accrochés aux **`functionResponse.parts` imbriqués** (pas au sommet, analyse : `coreToolScheduler.ts:661-744`, `postCompactAttachments.ts:149-161`, `compactionInputSlimming.ts:205-213`) : parcourir les parts du sommet → pour chaque `functionResponse` lire et concaténer le texte non vide de `response.output` ; puis parcourir ses **`functionResponse.parts` imbriqués**, pour `inlineData`/`fileData` produire un placeholder (par ex. `<image: mimeType>`), conserver aussi le placeholder pour les `{text}` imbriqués (le slimmer de compaction produit cette forme) ; **s'il n'y a pas d'output mais des médias imbriqués → retourner le placeholder** ; **ni output ni médias → retourner `undefined` pour laisser l'UI se dégrader en résumé** (éviter qu'un `read_file` média-only affiche du vide ou utilise à tort "Tool execution succeeded"). **Point d'extraction unique, partagé par live/resume/relecture**.
2. **Ajout à `IndividualToolCallDisplay` du cli (`types.ts:65`)** de `detailedDisplay?: string` — **valeur dérivée, non persistée** (extraite à chaque fois des parts déjà persistées).
3. **Extraction live** : branche succès de `useReactToolScheduler` : `detailedDisplay = getToolResponseDisplayText(trackedCall.response.responseParts)` (**pas de seconde troncature**, voir ci-dessous "mémoire et limites").
4. **Extraction resume** : le cas `tool_result` de `resumeHistoryUtils` (:411-431, détient déjà `record.message.parts`) extrait avec le même helper.
5. **Extraction relecture ACP** : `HistoryReplayer.replayToolResult` (:259) transmet déjà `message: record.message.parts` à `emitResult` ; au point de mappage ACP→display (`resumeHistoryUtils` / `ToolCallEmitter`) dériver avec le même helper. **Pas besoin de nouveau champ de protocole ACP**.
6. **Scission de rendu (corriger la fuite de `forceShowResult`)** : transmettre à `ToolMessage` **explicitement `fullDetail`** (transmis par `ToolGroupMessage`). Seulement quand **`fullDetail && isCollapsibleTool(name) && detailedDisplay`**, remplacer le résumé `resultDisplay` par `detailedDisplay`.
   - **Clé** : séparer "lever le repli/la hauteur" (`forceShowResult`/`forceExpandAll`, pouvant être déclenché par `isUserInitiated` / `Confirming` / `Error` / pending-agent / terminal-subagent, voir `ToolGroupMessage.tsx:469-475`) et "basculer vers la source de données complète" (**uniquement** `fullDetail`). Sinon les scénarios force user-initiated/error etc. de la vue principale afficheraient à tort le détail complet, violant "la vue principale ne change pas".

**Mémoire et limites (pas de seconde troncature, conforme à la sémantique "détail complet")** : `detailedDisplay` **ne passe pas** par la troncature 32k de `compactStringForHistory` — cela ferait de Ctrl+O un "preview borné à 32k" plutôt qu'un "détail complet", en conflit avec les promesses de §3.2/§3.4 (surtout `read_file` : `maxOutputChars=Infinity`, pagination autogérée, exempté de la troncature de caractères du scheduler, voir `read-file.ts:385-390`, une grande lecture légitime dépassera 32k ; à ce moment-là `functionResponse.response.output` contient toujours un contenu complet >32k, qui ne doit pas être recadré à nouveau par l'UI). `detailedDisplay` est directement = le texte complet de `getToolResponseDisplayText(parts)`, sa frontière est celle **déjà imposée par le core** `truncateToolOutput`/la pagination propre de l'outil (l'UI ne peut pas récupérer le contenu déjà écarté par le core, §4.5) — **la couche UI n'ajoute plus de limite de caractères**. `detailedDisplay` est une valeur dérivée, non stockée ; le contenu existe déjà dans `responseParts`, seulement une référence de chaîne de plus. ## 6. Migration et compatibilité

- **settings.ui.compactMode / compactInline** : peuvent déjà exister dans la configuration de l'utilisateur. Stratégie : **retirer du schéma** du CLI (`settingsSchema.ts`), mais **conserver `ui.compactMode` dans `WEB_SHELL_SETTINGS` (`workspace-settings.ts:36)`** — le web-shell a un `CompactModeContext` indépendant (`packages/web-shell/client/App.tsx` lit `'ui.compactMode'`), la couche serve doit continuer à transmettre, sinon casser le web-shell (voir #12 / §7 #5). Vérifié que le système de settings est **tolérant** aux clés inconnues — `getSettingsFileKeyWarnings` (`settings.ts:250-309`, traitement des clés inconnues à `:290-306`, `debugLogger.warn` à `:303-305`) ne fait que journaliser en `debug`, sans erreur ni blocage. Donc l'ancienne configuration CLI de l'utilisateur peut être lue en toute sécurité (ignorée par le CLI), la nouvelle UI/API de settings du CLI ne liste plus cet élément. **Pas de conservation de sémantique rétrocompatible côté CLI** — le concept de mode est entièrement supprimé, le conserver n'aurait aucun effet ; le maintien ou non du compact côté web-shell est **évalué séparément**.
- **Personnalisation des raccourcis (indication de migration)** : la base de code actuelle n'a **pas** de mécanisme de substitution de keybinding configurable par l'utilisateur — `keyMatchers` (`keyMatchers.ts`) est toujours construit depuis les `defaultKeyBindings` codées en dur, et le `settingsSchema` n'a pas d'élément keybinding (seulement `vimMode`). Donc il n'existe **pas** de liaison `toggleCompactMode` persistée par l'utilisateur qui serait silencieusement perdue, la détection de migration au démarrage n'a **aucun objet à scanner, actuellement non applicable**. Une fois qu'un keybinding configurable par l'utilisateur sera introduit à l'avenir, ajouter "détecter les liaisons `toggleCompactMode` résiduelles et indiquer une fois de re-lier `toggleTranscript`". **Cette PR n'a besoin que** d'une note de release indiquant que la sémantique de Ctrl+O a changé vers transcript (`docs/users/reference/keyboard-shortcuts.md` déjà mis à jour).
- **Télémétrie** : on peut aligner sur Claude Code en ajoutant un événement `toggle_transcript` (optionnel).

## 7. Frontières, risques et points ouverts

1. **Performance sur grand historique** : le transcript rend tout l'historique. Le défilement virtuel (`VirtualizedList`) est borné par viewport ; distinguer deux types de limites — **ne lever que le tronçonnage de "hauteur de ligne"** (pour l'affichage, le transcript le lève), mais **conserver la limite de "nombre de caractères"** (pour la performance, toujours conservée). À noter que qwen-code n'a **pas** `SlicingMaxSizedBox` (c'est celui de gemini-cli) ; la protection au niveau caractère côté qwen est le seuil de troncature de sortie d'outil `DEFAULT_TRUNCATE_TOOL_OUTPUT_THRESHOLD` (~25000). À l'implémentation, vérifier la fluidité du défilement sur un historique de dizaines de milliers de lignes.
2. **Coordination alt-screen (réutiliser le composant existant a déjà fortement réduit le risque)** : ce schéma **réutilise `AlternateScreen.tsx` déjà en place dans main (PR #5627)** pour entrer/sortir de l'alt-screen, plutôt que d'écrire à la main le timing `?1049h/l`, le risque est nettement plus faible que la conception initiale. Deux points restant à traiter : (a) **double entrée en mode VP** — quand `useTerminalBuffer` est actif, la racine ink occupe déjà l'alt-screen, il faut passer `disabled={useVP}` pour sauter les séquences d'échappement (§4.2) ; (b) **redessin de finalisation à la sortie** — à la sortie, l'écran principal est nettoyé et redessiné une fois via `refreshStatic()` (§4.4), et pendant le transcript `refreshStatic` est sauté gardé par `isTranscriptOpenRef`, évitant de polluer le scrollback du buffer normal. À noter que l'ancien compact faisait un refreshStatic **à chaque bascule**, ce schéma ne le fait qu'une fois **à la fermeture du transcript**, une fréquence bien plus faible. Il faut encore vérifier sous tmux / iTerm2 / VSCode / Apple Terminal.
3. **Sémantique de sécurité force (conserver les conditions en ligne de #5661, ne pas supprimer par erreur)** : quand cette PR ajoute le préfixe `fullDetail || isToolExpanded(id) ||` devant `forceExpandAll`, il faut absolument **conserver** le reste `hasConfirmingTool || hasSubagentPendingConfirmation || hasErrorTool || isEmbeddedShellFocused || isUserInitiated || hasTerminalSubagent`, ainsi que la porte `shouldCollapseResult` (incluant la garde `isCollapsibleTool`) de `ToolMessage` — c'est la sémantique de sécurité "erreur/en attente de confirmation/initié par l'utilisateur/shell focalisé/sous-agent doit être affiché en entier" déjà en place de #5661 (§4.5), les supprimer par erreur provoquerait la régression "un outil en erreur est replié et pas entièrement visible". **Pas besoin** de migrer vers un nouveau fichier.
4. **Coordination souris / SGR** : attention à la superposition potentielle avec le problème "le suivi souris SGR casse la sélection de texte native" noté dans [[project_vp_text_selection]] — activer ou non la molette souris dans le transcript doit être pesé (activer la molette vs conserver la sélection native du terminal). La gestion de l'entrée/sortie de la souris suit les mécanismes existants de `AlternateScreen` et de la racine VP, sans écriture manuelle supplémentaire.
5. **web-shell (surface indépendante, pas dans le périmètre de suppression de cette PR)** : le web-shell a un `CompactModeContext` **indépendant** (`packages/web-shell/client/App.tsx` lit `'ui.compactMode'`), deux implémentations distinctes du compact du CLI. Pour ne pas le casser, cette PR **conserve `ui.compactMode` dans `WEB_SHELL_SETTINGS`** (même si le schéma CLI ne définit plus cette clé, la couche serve la transmet toujours, voir #12 / §6). Cette itération du CLI ne fait que nettoyer ses propres textes et éléments de settings ; **le maintien ou non du compact propre au web-shell est évalué séparément**, pas dans le périmètre d'implémentation de cette conception.
6. **Intégrer ou non Ctrl+S/`SHOW_MORE_LINES`** : conservé indépendant dans cette itération, pour éviter que la surface de changement ne devienne incontrôlable ; listé comme optimisation optionnelle ultérieure.
7. **Sémantique de l'indication `(ctrl+o to expand)` (fixée)** : le résumé des blocs de réflexion porte **toujours** cette indication (guide "entrer dans le transcript pour voir le contexte complet", pas "ici c'est tronqué") ; la sortie des outils ne porte `+N lines` que lorsqu'elle est tronquée par contrainte de hauteur. Les deux conditions de déclenchement différentes sont un **comportement attendu**, les textes i18n doivent refléter "voir le contexte complet" plutôt que "déplier le contenu tronqué", pour éviter de tromper.

## 10. Inspiration mutuelle avec le document de conception existant #3100

Le travail préalable [PR #3100](https://github.com/QwenLM/qwen-code/pull/3100) a produit `docs/design/compact-mode/compact-mode-design.md` (284 lignes d'analyse concurrentielle). La relation de ce schéma avec lui :

1. **Nous adoptons le chemin qu'il avait analysé, mais pas suivi à l'époque**. #3100 §4.4 comparait déjà "screen-level transcript (Claude Code)" vs "component-level toggle (le choix de qwen à l'époque)", et notait que le premier est "plus simple, cohérence garantie". Ce schéma se tourne justement vers le screen-level transcript.
2. **Corriger une erreur factuelle** : le tableau de #3100 affirmait que Claude Code "Frozen snapshot: None (no concept)". Après analyse du dernier source de claude-code, **il y a bien un snapshot gelé** (`frozenTranscriptState` + `messages.slice(0, len)`). Ce schéma adopte le snapshot gelé selon l'implémentation réelle, et en note la source au §3.2.
3. **Réutiliser directement ses conclusions** : #3100 §4.3/§5.4 défendait "les dialogues de confirmation utilisent une couche d'overlay indépendante, garantie structurelle qu'ils ne sont jamais masqués". Le transcript étant un écran distinct, les confirmations/erreurs de l'écran principal n'en sont de toute façon pas affectées, satisfaisant naturellement ce besoin. Et "erreur/en attente de confirmation/shell focalisé doit être visible" est garanti côté vue principale par les conditions `forceExpandAll` de #5661 + `forceShowResult` (cette PR les conserve intactes, §4.5), sans besoin d'un mécanisme séparé.
4. **Résoudre le débat sur la persistance** : #3100 §4.2/§5.3 pesait répétitivement si le compact devait être persisté (settings vs scopé session). Ce schéma **supprime le mode lui-même**, il n'y a plus d'état à persister, ce débat disparaît automatiquement ; pas besoin non plus de la complexité "session override" de §5.3.
5. **Traitement des documents** : dans la PR d'implémentation, marquer `docs/design/compact-mode/` comme "remplacé par ctrl-o-detail-expand" (conserver l'historique, ajouter une ligne d'orientation), éviter que deux conceptions contradictoires coexistent.

> En une phrase : #3100 est la conception de "comment bien faire le mode compact" ; ce schéma est la conception de "pourquoi ne pas vouloir de mode compact, et utiliser le transcript à la place", les deux sont des décisions itératives sur le même problème.
