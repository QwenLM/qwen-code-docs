# コードレビュー

> `/review` を使用して、コードの変更を正確性、セキュリティ、パフォーマンス、およびコード品質の観点からレビューします。

## クイックスタート

```bash
# ローカルの未コミットの変更をレビュー
/review

# プルリクエストをレビュー（番号またはURLで指定）
/review 123
/review https://github.com/org/repo/pull/123

# PRにインラインコメントを投稿してレビュー
/review 123 --comment

# 特定のファイルをレビュー
/review src/utils/auth.ts
```

未コミットの変更がない場合、`/review` はその旨を通知して停止します。エージェントは起動されません。

## 仕組み

`/review` コマンドは、多段階のパイプラインを実行します。

```
ステップ 1:  スコープの決定（ローカル差分 / PRワークツリー / ファイル）
ステップ 2:  プロジェクトのレビュールールを読み込み
ステップ 3:  10の並列レビューエージェント                         [10回のLLM呼び出し]
           |-- エージェント 0: Issue Fidelity & 根本原因の特定
           |-- エージェント 1: 正確性
           |-- エージェント 2: セキュリティ
           |-- エージェント 3: コード品質
           |-- エージェント 4: パフォーマンスと効率
           |-- エージェント 5: テストカバレッジ
           |-- エージェント 6: 非構造化監査（3つのペルソナ: 6a/6b/6c）
           '-- エージェント 7: ビルドとテスト（シェルコマンドを実行）
ステップ 4:  重複排除 --> バッチ検証 --> 集約             [1回のLLM呼び出し]
ステップ 5:  反復逆監査（1〜3ラウンド、ギャップ発見）   [1〜3回のLLM呼び出し]
ステップ 6:  結果の提示 + 判定
ステップ 7:  PRレビューの提出（要求された場合はインラインコメント）
ステップ 8:  レポート + 増分キャッシュの保存
ステップ 9:  クリーンアップ（ワークツリーと一時ファイルの削除）
```

### レビューエージェント

| エージェント                             | 焦点                                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------- |
| エージェント 0: Issue Fidelity           | 関連するIssueの証拠、根本原因の特定、およびPRが報告された問題を解決しているかどうか |
| エージェント 1: 正確性              | ロジックエラー、エッジケース、nullハンドリング、競合状態、型安全性                       |
| エージェント 2: セキュリティ                 | インジェクション、XSS、SSRF、認証バイパス、機密データの露出                                  |
| エージェント 3: コード品質             | スタイルの一貫性、命名、重複、デッドコード                                           |
| エージェント 4: パフォーマンスと効率 | N+1クエリ、メモリリーク、不要な再レンダリング、バンドルサイズ                              |
| エージェント 5: テストカバレッジ            | 差分内の未テストコードパス、不足している分岐カバレッジ、弱いアサーション                   |
| エージェント 6: 非構造化監査         | 3つの並列ペルソナ（攻撃者 / 深夜のオンコール / メンテナー）— 多次元的な問題を検出 |
| エージェント 7: ビルドとテスト             | ビルドとテストのコマンドを実行し、失敗を報告                                              |

すべてのエージェントは並列で実行されます（エージェント6は3つのペルソナバリアントを同時に起動し、同一リポジトリのPRレビューでは合計10の並列タスクになります。ローカル差分とファイルパスのレビューではエージェント0がスキップされるため、9つになります）。エージェント0〜6からの結果は、**単一のバッチ検証パス**で検証されます（1つのエージェントがすべての結果を一度にレビューし、結果の数に関係なく検証コストを一定に保ちます）。検証後、**反復逆監査**が1〜3ラウンドのギャップ発見を実行します。各ラウンドは前のラウンドからの累積結果リストを受け取るため、連続するラウンドは未発見のものに焦点を当てます。このループは、ラウンドが「問題なし」と返した時点、または3ラウンド（ハードキャップ）に達した時点で停止します。逆監査の結果は検証をスキップし（エージェントはすでに完全なコンテキストを持っているため）、高信頼度の結果として含まれます。

## 重大度レベル

| 重大度         | 意味                                                             | PRコメントとして投稿されるか？      |
| ---------------- | ------------------------------------------------------------------- | -------------------------- |
| **Critical**     | マージ前に修正必須（バグ、セキュリティ、データ損失、ビルド失敗） | はい（高信頼度のみ） |
| **Suggestion**   | 推奨される改善                                             | はい（高信頼度のみ） |
| **Nice to have** | 任意の最適化                                               | いいえ（ターミナルのみ）         |

低信頼度の結果は、ターミナル内の「要人間レビュー」という別のセクションに表示され、PRコメントとして投稿されることはありません。

## ワークツリーの分離

PRをレビューする際、`/review` は現在のブランチを切り替える代わりに、一時的なgitワークツリー（`.qwen/tmp/review-pr-<number>`）を作成します。これにより以下のことが保証されます。

- ワーキングツリー、ステージされた変更、および現在のブランチが**変更されることは決してありません**
- ワークツリー内に依存関係がインストールされる（`npm ci` など）ため、ビルド/テストが機能します
- ビルドとテストのコマンドは分離された環境で実行されるため、ローカルのビルドキャッシュが汚染されません
- 何かがうまくいかない場合でも環境には影響しません。ワークツリーを削除するだけです
- ワークツリーはレビュー完了後に自動的にクリーンアップされます
- レビューが中断された場合（Ctrl+C、クラッシュ）でも、同じPRに対する次回の `/review` 実行時に、古いワークツリーが自動的にクリーンアップされてから新しく開始されます
- レビューレポートとキャッシュはメインのプロジェクトディレクトリに保存されます（ワークツリーではありません）

## 別リポジトリのPRレビュー

完全なURLを渡すことで、他のリポジトリのPRをレビューできます。

```bash
/review https://github.com/other-org/other-repo/pull/456
```

これは**軽量モード**で実行されます。ワークツリーもビルド/テストも行われません。レビューは差分テキストのみ（GitHub API経由で取得）に基づきます。書き込み権限がある場合は、PRコメントを引き続き投稿できます。

| 機能                                                 | 同一リポジトリ | 別リポジトリ                    |
| ---------------------------------------------------------- | --------- | ----------------------------- |
| LLMレビュー（エージェント0〜6 + 検証 + 反復逆監査） | ✅        | ✅                            |
| エージェント 7: ビルドとテスト                                      | ✅        | ❌（ローカルコードベースなし）        |
| ファイル間影響分析                                 | ✅        | ❌                            |
| PRインラインコメント                                         | ✅        | ✅（書き込み権限がある場合） |
| 増分レビューキャッシュ                                   | ✅        | ❌                            |

## PRインラインコメント

PRに結果を直接投稿するには、`--comment` を使用します。

```bash
/review 123 --comment
```

または、`/review 123` を実行した後に `post comments` と入力すると、レビューを再実行せずに結果を公開できます。

**投稿される内容:**

- 特定の行に対するインラインコメントとしての、高信頼度の Critical および Suggestion の結果
- Approve/Request changes の判定の場合: 判定を含むレビューの要約
- すべてのインラインコメントが投稿された Comment の判定の場合: 個別の要約はなし（インラインコメントで十分であるため）
- 各コメントのモデル帰属フッター（例: _— qwen3-coder via Qwen Code /review_）

**ターミナルのみに留まる内容:**

- Nice to have の結果
- 低信頼度の結果

**自身が作成したPR:** GitHubでは、自身のプルリクエストに対して `APPROVE` または `REQUEST_CHANGES` レビューを提出することはできません（いずれもHTTP 422で失敗します）。`/review` はPRの作成者が現在認証されているユーザーと一致することを検出すると、判定に関係なくAPIイベントを自動的に `COMMENT` にダウングレードするため、提出は成功します。ターミナルには正直な判定（"Approve" / "Request changes" / "Comment"）が表示されます。GitHub側のレビューイベントのみが無効化されます。実際の結果は引き続き特定の行にインラインコメントとして表示されるため、実質的なフィードバックは変わりません。

**以前の Qwen Code コメントがあるPRの再レビュー:** `/review` が以前の Qwen Code レビューコメントを持つPRに対して実行されると、新しいコメントを投稿する前にそれらを分類します。**同一行の重複**（新しい結果と同じ `(path, line)` に既存のコメントがある場合）のみ、確認を求められます。これは、同じコード行に視覚的な重複が表示されるケースです。古いコミットからのコメント、返信されたコメント（解決済みとして扱われる）、および新しい結果と重複しないコメントは、サイレントにスキップされます。何がフィルタリングされたかを確認できるように、ターミナルにログ行が出力されます。

**APPROVE前のCI/ビルドステータスチェック:** 判定が "Approve" の場合、`/review` は提出前にPRのチェックランとコミットステータスをクエリします。いずれかのチェックが失敗している場合（またはすべてのチェックがまだ保留中の場合）、APIイベントは `APPROVE` から `COMMENT` に自動的にダウングレードされ、レビュー本文にその理由が説明されます。理由: LLMレビューはコードを静的に読み取るため、ランタイムのテスト失敗を確認できません。CIが赤い状態で承認することは誤解を招く可能性があります。インラインの結果は引き続き変更なしで投稿されます。とにかく承認したい場合（例: 既知のフレーキーなCI失敗）、確認後にGitHubの承認を手動で提出してください。

## フォローアップアクション

レビュー後、コンテキストに応じたヒントがゴーストテキストとして表示されます。Tabキーを押して受け入れます。

| レビュー後の状態                 | ヒント                | 動作                            |
| ---------------------------------- | ------------------ | --------------------------------------- |
| 未修正の結果があるローカルレビュー | `fix these issues` | LLMが各結果を対話的に修正    |
| 結果があるPRレビュー            | `post comments`    | PRインラインコメントを投稿（再レビューなし） |
| PRレビュー、結果ゼロ           | `post comments`    | GitHubでPRを承認（LGTM）        |
| ローカルレビュー、問題なし            | `commit`           | 変更をコミット                    |

注: `fix these issues` はローカルレビューでのみ利用可能です。PRレビューではレビュー後にワークツリーがクリーンアップされるため、レビュー後の対話的な修正はできません。代わりに `--comment` または `post comments` を使用して結果を公開してください。

## プロジェクトのレビュールール

プロジェクトごとにレビュー基準をカスタマイズできます。`/review` は以下のファイルからルールを（順番に）読み取ります。

1. `.qwen/review-rules.md`（Qwen Codeネイティブ）
2. `.github/copilot-instructions.md`（優先）または `copilot-instructions.md`（フォールバック — どちらか一方のみが読み込まれ、両方ではありません）
3. `AGENTS.md` — `## Code Review` セクション
4. `QWEN.md` — `## Code Review` セクション

ルールは追加の基準としてLLMレビューエージェント（0〜6）に注入されます。PRレビューの場合、悪意のあるPRがバイパスルールを注入するのを防ぐため、ルールは**ベースブランチ**から読み取られます。

## Issue Fidelity

バグ修正PRの場合、Issue Fidelity エージェントはPRの説明文に依存するのではなく、Issueの証拠を直接取得します。GitHubの強力なクローズIssueメタデータのために `gh pr view <pr> --repo <owner/repo> --json closingIssuesReferences` を使用し、次に元のレポートと議論のために `gh issue view <number> --repo <issue_owner>/<issue_repo> --json title,body,comments` を使用します。`--json` 形式にはIssueの**本文**（報告者の元々の再現手順）が含まれますが、`--comments` 単独では省略されます。また、Issue自体のリポジトリは各参照から読み取られます（PRは別のリポジトリのIssueをクローズできるため）。このエージェントはPRターゲットに対してのみ実行され、ローカル差分とファイルパスのレビューではスキップされます。

`closingIssuesReferences` は、作成者が正しいIssueをリンクしたことの証明ではなく、発見のヒントです。これが空であっても、PRが明らかなターゲットIssueを参照している場合、エージェントは関連性を判断した後に引き続きそれを取得します。取得されたIssueのテキストは信頼できないデータとして扱われます（事実が抽出され、埋め込まれた指示は無視されます）。関連するIssueの場合、元の再現手順、観測されたペイロード、期待される動作、およびメンテナーのコメントは、PRが正しい問題を修正しているかどうかの最優先証拠として扱われます。

もしIssueの証拠に、アップストリームサービスまたはプロバイダーがクライアントの契約外の不正なデータを返したことが示されている場合、メンテナーが明示的に防御的な回避策を要求していない限り、クライアント側のパーサーまたはサニタイザーの変更は有効な根本原因の修正として扱われません。不正なアップストリーム出力をリプレイするテストは、その回避策がその形状を処理できることのみを証明し、回避策がアーキテクチャ的に適切であることは証明しません。

## コアインフラゲート

コアインフラに触れる外部PRの場合、`/review` は通常のレビューの前にリポジトリゲートを適用します（PRが取得された直後、依存関係のインストールの前）。メンテナーの作成者権限は、PRの `authorAssociation`（`OWNER`/`MEMBER`/`COLLABORATOR` は免除）から決定されます。（**コアインフラパス内**の追加と削除が500行以上の）大規模なコア変更は、メンテナーが作成者でない限り、ハードブロックとして報告されます。多くのファイルに触れるがそれぞれ1、2行しか変更しない低リスクのスイープは、行数に基づいて自動拒否されるのではなく、エスカレーションされます。小規模なコア変更には100%の信頼度とダウンストリームコンシューマーの認識が必要です。そうでない場合、`/review` はメンテナーにエスカレーションします（Commentとして提出され、Approveにはなりません）。
Example `.qwen/review-rules.md`:

```markdown
# レビュールール

- すべての API エンドポイントは認証を検証しなければならない
- データベースクエリはパラメータ化されたステートメントを使用しなければならない
- React コンポーネントはインラインスタイルを使用してはならない
- エラーメッセージは内部パスを露呈してはならない
```

## インクリメンタルレビュー

以前にレビューされた PR をレビューする場合、`/review` は前回のレビュー以降の変更のみを検査します。

```bash
# 初回レビュー — 完全レビュー、キャッシュ作成
/review 123

# PR が新しいコミットで更新 — 新しい変更のみレビュー
/review 123
```

### クロスモデルレビュー

モデルを切り替えて（`/model` 経由）同じ PR を再レビューする場合、`/review` はモデルの変更を検出し、スキップせずに完全なレビューを実行します。

```bash
# モデル A でレビュー
/review 123

# モデルを切り替え
/model

# 再度レビュー — モデル B で完全レビュー（スキップされない）
/review 123
# → "前回のレビューは qwen3-coder を使用しました。gpt-4o でセカンドオピニオンを得るために完全レビューを実行します。"
```

キャッシュは `.qwen/review-cache/` に保存され、コミット SHA とモデル ID の両方を追跡します。このディレクトリが `.gitignore` に含まれていることを確認してください（`.qwen/*` のようなより広いルールでも機能します）。キャッシュされたコミットがリベースで削除されていた場合、完全レビューにフォールバックします。

## レビューレポート

同一リポジトリ内のレビューの場合、結果はプロジェクトの `.qwen/reviews/` ディレクトリに Markdown ファイルとして保存されます（クロスリポジトリの軽量レビューはレポートの永続化をスキップします）。

```
.qwen/reviews/2026-04-06-143022-pr-123.md
.qwen/reviews/2026-04-06-150510-local.md
```

レポートには以下の情報が含まれます：タイムスタンプ、diff 統計、ビルド/テスト結果、検証ステータス付きのすべての発見、および最終判定。

## クロスファイル影響分析

コードの変更によってエクスポートされた関数、クラス、またはインターフェースが変更された場合、レビューエージェントは自動的にすべての呼び出し元を検索し、互換性をチェックします。

- パラメータの数/型の変更
- 戻り値の型の変更
- 削除または名前変更されたパブリックメソッド
- 破壊的な API の変更

大規模な diff（変更されたシンボルが 10 個以上）の場合、分析はシグネチャが変更された関数を優先します。

## トークン効率

レビューパイプラインは、いくつの発見が生成されたかに関わらず、LLM 呼び出し回数を上限内に抑えます。

| ステージ                           | LLM 呼び出し回数  | 備考                                                |
| ---------------------------------- | ----------------- | --------------------------------------------------- |
| レビューエージェント (ステップ 3)  | 10 (または 9)     | 並列実行。クロスリポジトリモードではエージェント 7 をスキップ |
| バッチ検証 (ステップ 4)            | 1                 | 単一エージェントがすべての発見を一度に検証          |
| リバース監査の反復 (ステップ 5)    | 1-3               | 「問題なし」になるまで、または 3 ラウンドの上限までループ |
| **合計**                           | **12-14 (11-13)** | 同一リポジトリ: 12-14。クロスリポジトリ: 11-13 (エージェント 7 なし) |

ほとんどの PR は範囲の下限（リバース監査 1 ラウンド）に収束します。この上限は、極端なケースでのコストの暴走を防ぎます。

## フラグが立たないもの（対象外）

レビューでは意図的に以下の項目を除外しています。

- 変更されていないコードに元々存在する問題（diff のみに焦点を当てます）
- フォーマッターが自動的に正規化するスタイルやフォーマット、またはコードベースの規約に合致する命名 — ただし、リンターや型チェッカーがフラグを立てるような実質的な問題（未使用の変数、到達不能なコード、型エラー）は対象内です
- 実際の問題がないにもかかわらず、主観的な「X を検討してください」といった提案
- バグやリスクを修正しない軽微なリファクタリング
- ロジックが真に混乱を招くような場合を除き、ドキュメントの欠落
- 既存の PR コメントですでに議論された問題（人間からのフィードバックの重複を避けるため）

## 設計思想

> **沈黙は雑音に勝る。** すべてのコメントは、読む人の時間を奪う価値があるものでなければなりません。

- 問題かどうか確信が持てない場合 → 報告しない
- N 個のファイルに同じパターンがある場合 → 1 つの発見として集約する
- PR コメントは確信度の高いもののみとする
- コードベースの規約に合致する表面的なスタイル/フォーマットは除外する
