# WeCom Webhook 送信

内部 WeCom グループのメッセージプッシュ webhook（旧称グループロボット）を使用して、通知やタスク結果を送信します。これにはグループの webhook URL だけで十分であり、Bot ID/Secret、アプリケーション認証情報、長距離接続、パブリックインバウンドサーバーは不要です。エージェントとの会話には [WeCom インテリジェントロボット](./wecom) を、自作アプリケーションには [WeCom コールバック](./wecom-callback) を参照してください。

## グループ配信先の作成

1. 内部 WeCom グループの設定を開き、メッセージプッシュを見つけます。
2. カスタムメッセージプッシュを作成し、`https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=` で始まる webhook URL をコピーします。
3. エントリが利用できない場合は、組織の作成権限を確認してください。管理者はメッセージプッシュを作成できるメンバーを制限でき、オーナー管理グループではエントリをグループオーナーのみに制限できます。

外部グループはこの設定ではサポートされていません。公式の作成条件は内部グループと管理者権限について説明しており、普遍的な企業認証要件または免除を確立するものではありません。

URL には送信認証情報が含まれています。Channel 設定または環境変数に保持し、タスクプロンプトや配信ターゲットには絶対に入れないでください。URL は WeCom から発行されたまま使用してください。ローカル検証では、文字・数字・`-`・`.`・`_`・`~` を含む `key` パラメータを 1 つだけ受け付けます。パーセントエンコーディング、フラグメント、追加パラメータは受け付けられません。署名用の secret は別途存在しません。

## Channel の設定

この統合は、[Web Shell](#use-web-shell) または `settings.json` で以下のように設定します。

ワークスペースの Channel 設定に名前付きインスタンスを追加します。

```json
{
  "channels": {
    "team-notices": {
      "type": "wecom-webhook",
      "webhookUrl": "$WECOM_WEBHOOK_URL"
    }
  }
}
```

Qwen Code の起動に使用される環境で `WECOM_WEBHOOK_URL` を設定し、そのワークスペースでデーモンを実行します。

```bash
qwen serve --channel team-notices
```

1 つの名前付きインスタンスは 1 つのグループを表します。他のグループには追加のインスタンスを作成してください。インスタンスの URL を変更すると、それを通じた将来の配信が変更されます。

開始すると、Channel はローカルで送信準備完了になります。テストメッセージの送信やリモート認証情報の検証は行いません。停止すると送信中の処理がキャンセルされます。再起動またはリロードすると、保存された設定変更が適用されます。

## Web Shell の使用

ビルドにバックエンドサポートが含まれているが Web 統合より前の場合、Channels にはこのメソッドや既存の `wecom-webhook` インスタンスが表示されません。Web 統合を含むビルドにアップグレードするまで、上記の `settings.json` と `qwen serve --channel` の手順を使用してください。

Channels で WeCom を選択し、次に Webhook（送信のみ）を選択します。ワークスペースを選択し、webhook URL を保存して Channel を開始します。署名用 secret は不要です。受信、ペアリング、エージェントセッション設定はこのメソッドには適用されません。インテリジェントボットメソッドは引き続き WeCom の下にあり、WeCom コールバックは別のエントリを保持します。

Scheduled Tasks で、永続タスクセッションを選択し、この Channel を配信先として選択します。Web Shell は設定されたグループを自動的に入力するため、観測されたコンタクトや手動で入力したチャット ID は不要です。既存の実行ごとおよび手動トリガーの配信制限は引き続き有効です。

同じコントロールは、ホストが Channels と Scheduled Tasks を有効にし、デーモンワークスペースを提供する場合、`WebShellWithProviders` を通じて利用できます。

## 明示的な API 配信

Notify と明示的なプロンプト・スケジュール配信は、既存の Channel ターゲットを使用します。このアダプターは 1 つの論理配信先 `chat/default` を所有します。

```json
{
  "text": "# Daily report\n\nThe checks passed.",
  "delivery": {
    "kind": "channel",
    "target": {
      "channelName": "team-notices",
      "type": "chat",
      "id": "default"
    }
  }
}
```

これはワークスペースの Notify リクエストボディです。`default` は設定されたグループを参照する名前であり、WeCom チャット ID ではありません。他の ID、ユーザーターゲット、スレッドは拒否されます。タスクは論理配信先を保存し、認証情報は Channel 設定に保持されます。

永続スケジュールタスクも同じ配信先を使用します。配信は、現在の実行ごとおよび手動トリガーの制限を含め、既存のベストエフォート型成功最終結果動作を保持します。

## メッセージフォーマットと制限

- `markdown_v2` を元のテキストで送信します。サポートされるサブセットには、見出し、リスト、リンク、フェンスコード、テーブルが含まれ、通常テキスト、中国語、絵文字は有効な入力です。完全な GitHub 風 Markdown 互換性は保証されません。
- この形式はメンションやフォントカラーマークアップをサポートしません。アダプターはメンション配列を送信せず、タスクテキストをメンションに変換しません。`< @all>` などのメンション風の文字列はボディに残ります。
- 4.1.36 より前のクライアント（Android は 4.1.38 より前）はメッセージをプレーンテキストとして表示します。Markdown レンダリングには現在のクライアントを使用してください。
- 最終的な **content** は、JSON エスケープ前に **4096 UTF-8 バイト**に制限されています。中国語と絵文字は ASCII よりも多くのバイトを消費します。これは 4096 文字制限ではなく、完全な JSON リクエストの制限でもありません。
- 大きすぎるコンテンツは、送信前に明示的に失敗します。サイレントなアダプターによる切り捨て、自動分割、再試行はありません。プラットフォーム固有のチェック前に、共有配信バインドが引き続き適用されます。
- WeCom は **webhook あたり 1 分間に 20 メッセージ**を許可しています。スケジュールされたレポートは簡潔に保ち、バーストを避けてください。スロットリングされた配信は、キューイングせずに失敗を報告します。

## 失敗とトランスポート

HTTP ステータスと WeCom の数値 `errcode` の両方がチェックされます。無効または無効化された認証情報、拒否されたグループ配信先、レート制限は観測可能な失敗を引き起こします。診断では URL、キー、メッセージ内容、生のプロバイダーエラーテキストは省略されます。

各試行は 15 秒のタイムアウトで最大 1 つのリクエストを行います。API の受け入れは受信確認ではありません。タイムアウトやキャンセルにより、リモートの受け入れが不明になる可能性があります。トランスポートは解決されたワークスペースプロキシと既存の `NO_PROXY` 動作を尊重します。

このモードはメッセージを受信せず、インバウンド webhook タスクを実行せず、Channel ループを開始しません。添付ファイル、インタラクティブカード、自動失敗・キャンセルアラート、永続的な再試行、汎用 webhook プロトコルは追加されません。

現在のプラットフォーム要件については、公式の [メッセージプッシュプロトコル](https://developer.work.weixin.qq.com/document/path/91770) および [セットアップガイド](https://open.work.weixin.qq.com/help2/pc/14931) を参照してください。
