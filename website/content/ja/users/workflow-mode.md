# セッション Workflow モード


Workflow モードは、現在のセッションで通常の新しい送信に対して Workflow ツールを検討するという設定を保存します。デフォルトはオフです。モデルは引き続き workflow が有用かどうかを判断し、すべての権限、信頼、予算、およびツールの制限は引き続き適用されます。モードを有効にしても、実行が開始されたり、推論の effort が変更されたり、デフォルト設定が変更されたりすることはありません。

Workflow ツールはオプトインです。モードをオンにする前に、設定で `tools.workflowsEnabled` を有効にするか、`QWEN_CODE_ENABLE_WORKFLOWS=1` を設定してください:

```sh
QWEN_CODE_ENABLE_WORKFLOWS=1 qwen --workflow-mode on
qwen --resume <session-id> --workflow-mode off
```

ツールが利用できない状態で `--workflow-mode on` を指定して起動すると、初期化に失敗します。`QWEN_CODE_DISABLE_WORKFLOWS=1` は有効化よりも優先されます。

どちらのターミナルレンダラーでも、`/workflows mode` または `/workflows mode status` で状態を確認し、`/workflows mode on` または `/workflows mode off` で変更できます。これらのモード制御はレスポンスのストリーミング中に実行でき、その後の対象となる送信に適用されます。フッターには `Workflow mode: on` が表示されます。保存された設定が現在適用できない場合は `Workflow mode: on (unavailable)` と表示されます。既存の `/workflows` の実行リストと一時停止制御は元の動作を維持します。

状態は `requested`（保存された設定）、`available`（必要なツールが現在利用可能）、`effective`（両方が true）に分離されます。オンにするには Workflow ツールが利用可能である必要があります。オフにすることは、ツールが利用できない場合でも可能です。ツールを失っても保存されたオンの設定は消去されません。ツールが復元されると、その設定が再び有効になります。

このモードは、通常のローカルセッションと、セカンダリワークスペースオーナーを含む通常のデーモンセッションでサポートされています。マネージドセッション、SSH セッション、派生/サブエージェントセッション、セッションエージェントセッション、およびチャット記録が無効になっているセッションでは、モードの変更はサポートされていません。サポートされていないプロトコルのセッションは、この機能やオプションを通知しません。書き込みに失敗しても、公開されたモードは変更されません。

## リマインダーと入力の動作

最初の対象となる送信には、モデルのみのリマインダーが送信されます。他の変更がない場合、まばらなリマインダーは 11 番目と 21 番目の送信に続き、その後は 10 回の対象となる送信ごとに送信されます。オフにするか機能を失うと、次の対象となる送信で 1 回の終了通知が送信されます。実際のモデルのディスパッチのみがリマインダーを消費するかカウントを進めます。ディスパッチ前のキャンセルや拒否はカウントしません。リトライとフォールバックの試行は同じ配信トークンを共有します。キャンセルによってディスパッチされたモードリマインダーがモデル履歴から削除された場合、次の対象となる送信で現在の状態が再び通知されます。

通常の CLI、SDK、および ACP の送信は、human-origin 宣言なしでこの明示的なモードを使用できます。ツールの継続、リトライ、フック、スラッシュコマンドで生成されたプロンプト、シェルモード、サイドクエリ、自動 Goal/Cron/通知/チャネルターン、およびサブエージェントは、新しいモードリマインダーを追加したりカウントを進めたりしません。モードまたは未配信のトランジションにコンテキストが必要な間、プロンプトの speculation は一時停止されます。

[ワンターンのキーワードヒント](./workflow-intent.md)は別個のままです。その human provenance 要件とオプトアウト設定は変更されません。有効なキーワードとモードリマインダーは 1 つのエンベロープを共有します。永続モードをオフにしても、有効なワンターンのキーワードは無効になりません。モードのみのリマインダーは、一時的なキーワードインジケーターやキーワードテレメトリをアクティブにしません。

## セッションライフサイクル

再開は、選択されたトランスクリプトブランチの最後の有効なブール値レコードを復元し、保存されたオンまたはオフの状態を 1 回通知します。明示的な CLI または SDK の初期値は、セッションの準備ができた後に、その復元された値を 1 回オーバーライドします。競合する初期値、または Workflow ツールが利用できない状態での初期オン値は、初期化に失敗します。新規またはクリアされたセッションはオフから開始されます。フォークは選択されたチェックポイントを独立して継承します。rewind は現在の設定を保持し、復元されたブランチにアンカーします。正常なコンパクションは、次の対象となる新しい送信で状態を再通知します。失敗した再開またはブランチ切り替え後の前のセッションの履歴の再構築後、次の対象となる送信で保存された状態が再通知されます。保存された設定がないセッションは何も通知しません。

## TypeScript SDK と ACP

```ts
const session = query({
  prompt: messages(),
  options: { workflowMode: true },
});
const state = await session.getWorkflowMode();
await session.setWorkflowMode(false);
```

`workflowMode` はオプションです。省略すると再開された値が保持され、`false` は明示的にオフを保存します。初期化は初期値をネゴシエーションしてステージングします。`Query.initialized` は制御のハンドシェイクです。get/set 操作はセッションの準備が完了するまで待機します。セッションの初期化が進行中の間、繰り返しの初期化リクエストは拒否されます。古い CLI は、最初のプロンプトの前に明示的なモードリクエストを暗黙に無視する代わりに拒否します。カスタムトランスポートも同じ制御プロトコルを使用します。

ACP は、値 `on` と `off` を持つ標準の `workflow_mode` 設定オプションを通知します。`currentValue` はリクエストされた状態を反映し、`_meta['qwen.workflowMode']` には `available`、`effective`、およびオプションの `reason` が含まれます。コミットされた変更と機能のリフレッシュは、`config_option_update` を通じて完全なオプションを公開します。

デーモンクライアントは既存のセッション設定オプションエンドポイントまたは `setSessionConfigOption(sessionId, 'workflow_mode', 'on', clientId)` を使用します。このオプションは `persist` オーバーライドを受け付けません。常にセッション永続的です。コンテキストの読み取りと更新は、リースと世代チェックを含め、そのセッションの現在のオーナーに属します。Web/IDE 固有の制御はこの実装に含まれません。
