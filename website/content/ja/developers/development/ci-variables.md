# CIとリリースの変数

CIおよびリリースパイプラインのいくつかの設定は、GitHub Actionsのリポジトリ変数（`vars.*`コンテキスト）として公開されているため、オペレーターはプルリクエストを開かずにそれらを再調整できます。このページでは、`.github/workflows/ci.yml`と`.github/workflows/release.yml`でのテスト実行に影響する変数とそのデフォルト値、および各変数が適用される場所を一覧にまとめています。

## 変数の設定

リポジトリのメンテナーは、**Settings → Secrets and variables → Actions → Variables** でこれらを設定します。未設定（または空）の変数は、ワークフロー式のフォールバックを使用します。ワーカーキャップは、変数が設定されている場合でも、予約済みランナー上でのみ適用されます。

ワークフローファイルがこれらの設定の唯一の信頼できる情報源であり、テストスイートはワークフロー式をバイト単位で正確に固定しています。`scripts/tests/package-scripts.test.js`は`release.yml`の共有ワーカーキャップ式（`ecs-qwen-`ガード付きの`QWEN_CI_VITEST_MAX_WORKERS`）を固定し、`scripts/tests/no-ak-integration-ci.test.js`は`ci.yml`のワーカーキャップ式を固定し、`scripts/tests/release-workflow.test.js`は`release.yml`のリトライおよびワークスペーステストのタイムアウト式を固定しています。`scripts/tests/package-scripts.test.js`は、ドキュメント化されたデフォルト値とワークフローの場所を両方のワークフローに対してチェックします。このガードはドキュメントのみのチェックではなくフルプロファイルCIレーン（`test:scripts`）で実行されるため、このページのみに限定された編集は、プルリクエストを開く前に`npm run test:scripts`（または`npx vitest run --config ./scripts/tests/vitest.config.ts scripts/tests/package-scripts.test.js`）でローカルに検証してください。ドキュメントとワークフローに矛盾がある場合は、ワークフローを信頼し、同じ変更でこのページを更新してください。

## 変数

| 変数                                       | デフォルト | 使用場所                | 制御内容                                                                                          |
| ------------------------------------------ | ---------- | ----------------------- | ------------------------------------------------------------------------------------------------- |
| `QWEN_CI_VITEST_RETRY`                   | `2`     | `ci.yml`                | メインCIワークスペースおよびスクリプトテストステップのリトライ回数                                        |
| `QWEN_CI_HOST_LOAD_MAX_RATIO`            | `2.0`   | `ci.yml`                | 単体スイート前にセルフホストのLinuxホストが拒否される、CPUあたりの負荷の上限                        |
| `QWEN_CI_RPC_RETRY`                      | `1`     | `ci.yml`                | VitestのワーカーRPCタイムアウトのみで失敗した全グリーンワークスペーススイートの再実行                |
| `QWEN_RELEASE_VITEST_RETRY`              | `2`     | `release.yml`           | リリースワークスペーステストシャードのリトライ回数                                                  |
| `QWEN_RELEASE_WORKSPACE_TIMEOUT_MINUTES`   | `45`       | `release.yml`           | 各リリースワークスペーステストシャードのジョブタイムアウト                                        |
| `QWEN_CI_VITEST_MAX_WORKERS`               | `4`        | `ci.yml`、`release.yml` | 予約済みランナー上でのメインCI単体テストおよびリリースワークスペース/品質テストのワーカーキャップ |

### リトライ回数

`QWEN_CI_VITEST_RETRY`および`QWEN_RELEASE_VITEST_RETRY`は、メインCIテストステップ（各ワークスペースの`test:ci`。このステップは2つの同時レーンで実行され、`npm run test:scripts:unit`も含む）とリリースレーン（`npm run test:release:workspaces`）で、それぞれ`--retry=<n>`としてVitestに渡されます。2つのレーンは独立して調整できるように、別々の変数を持っています。

Vitestは失敗したテストを同じ実行内で再実行します。これは断続的な競合に役立つことがありますが、リトライバジェット内で回復した失敗はチェックをグリーンにし、フレーキー再実行トラッカーには失敗として記録されません。フレーキーなスイートをリトライで覆い隠すのではなく、バジェットを控えめに保ってください。どちらの変数もリテラル値`off`を受け付けます。この場合、`--retry=0`を渡すのではなく`--retry`フラグ自体が省略されます（コマンドラインの`--retry=0`はワークスペース独自のVitest設定よりも優先され、意図的なリトライポリシーを無効にしてしまうためです）。

### 競合ホストでのワーカーRPCタイムアウト

`QWEN_CI_RPC_RETRY`は`--retry`とは異なる設定です。ワークスペーススイート全体を再実行し、かつそのスイート自身のレポートに失敗したテストがなく、VitestのワーカーからメインへのRPCバジェット（`Timeout calling "onTaskUpdate"`）が唯一の未処理エラーである場合にのみ実行されます。このプールでは、このパターンは退行ではなくホストの競合です — メインの実行43018456551と43016357976は、`packages/channels/github`で902テスト中902がパスしたにもかかわらずレッドになりました。最初の実行はnpm独自のバッチ呼び出しを保持します。npmが失敗として名前を付けたワークスペースのみがそれぞれ単独で再実行されます。

リリースレーンはすでに自身のシャードで同じパスを許可しています（`.github/scripts/run-release-workspace-tests.sh`）。証拠ルールは`scripts/tests/release-workflow.test.js`がそこに固定しているものです。実行はパスのカウントに到達していること、シグナルでkillされていないこと、Vitest独自の未処理エラーのカウントがレポートに含まれるトランスポートタイムアウトの数と一致していることが必要です。クラッシュヘッダーではなくカウントです。ヘッダーはプロデューサーが選択するため、ヘッダーのパターンだけでは不完全です。`Errors`の値はレポート全体の合計ですが、トランスポートの値はVitestの`Unhandled Errors`セクション内でのみカウントされます。テストのコンソール出力もカラム0にechoされるため、表示されたコピーがそれを移動させてはなりません。そしてそれらのセクション内では、エラー自身のヘッダー行（カラム0の`Error: [vitest-worker]: Timeout calling`）にマッチし、プレフィックスを引用する単なるメッセージ、スタック、コードフレームにはマッチしません。したがって、ある実行のグリーンのカウントが後の実行のクラッシュを覆うことはできません。

Linuxレーンは意図的に未処理エラーを致命的に保ち（`scripts/tests/unit-vitest-configs.test.ts`、#10438）、これらは無視されません。失敗したテスト、2つ目の未処理エラー、またはレポート前にプロセスが終了した場合はリトライが拒否されます。両方の試行を超えてストールした場合は引き続き失敗します。`0`に設定すると、最初の失敗がそのままになります。

**カウントが唯一の制限です。**再実行に時間条件はありません。このレーンの初期リビジョンでは、テストステップのバジェットの半分未満が残っている場合に再実行をスキップしていましたが、そのガードは修復ではなく削除されました。バジェットの74%で再実行を拒否しました。バッチの経過時間を2回加算していたためです。そして正しいバージョンはレーンスクリプト内部からは利用できません。ステップはスクリプトより前に開始されます（`chown -R`、`mktemp`、ディスクサンプラー）。そのためスクリプト独自の`SECONDS`はステップのクロックではなく、ステップの開始をワークフローから渡すことは、回避できる1つの切り捨てよりも多くの新しいサーフェスになります。受け入れられたコストは、遅く発行された再実行がステップの`timeout-minutes: 45`でkillされる可能性があることです。その場合ジョブは失敗し、最初の実行のログはまだ残っています。最初の実行はファイルにteeされているためです。これは証拠を保持する切り捨てであり、バジェットの4分の1が未使用の間にリトライを捨てる拒否ではありません。

### ホスト負荷の受け入れ

`QWEN_CI_HOST_LOAD_MAX_RATIO`は、単体テストシャードの`Host load gate (self-hosted)`ステップのCPUあたり負荷の上限です。このゲートは5分間の負荷平均を`/proc/loadavg`から`nproc`に対してサンプリングし、10秒間隔で最大6つのサンプルを待ち、1つのサンプルが上限をクリアした時点でジョブを受け入れます。まだ上限以上にあるホストは、スイート開始前にステップを失敗させます。

ゲートはジョブを移動できません。GitHubがすでに配置しており、再実行のみが別のホストに配置します。変更されるのはジョブが失敗するタイミングです。隣接するディスクフロアゲートは空きバイトとinodeで受け入れますが、これらはCPU競合については何も語りません。2026-11-11に、hk1プールは64 CPUホストで負荷53-98、28-140の同時Vitestプロセスで実行されており、この占有度が60秒のテストバジェット、VitestのワーカーからメインへのRPCバジェット、およびテストステップの45分バジェット全体を期限切れにします。拒否することはすでに費やされたインストールコストを返し、そのバジェットを返します。ブランチが作成したわけではないテスト失敗ではなく、再実行を促すメッセージと共に。

**ゲートはバックストップであり、予測子ではありません。**デフォルトの`2.0`は、2026-11-11に失敗したシャードと同じ時間に同じプールでパスした4つのシャードのCPUあたり5分間負荷に対してキャリブレーションされています。

| シャード | ホスト   | エントリー時 | 中央値 | ピーク | 結果                   |
| -------- | -------- | ------------ | ------ | ------ | ---------------------- |
| 2/2      | hk1-4    | 1.34         | 1.43   | 1.54   | ワーカーRPCタイムアウト |
| 2/2      | hk1-30   | 1.45         | 1.42   | 1.54   | ワーカーRPCタイムアウト |
| 2/2      | hk1-29   | 0.85         | 1.42   | 1.54   | 45分ステップタイムアウト |
| 1/2      | hk1-7    | 0.94         | 1.40   | 1.49   | パス                   |
| 2/2      | hk5-27   | 1.03         | 1.03   | 1.19   | パス                   |
| 1/2      | hk2-32   | 0.75         | 0.97   | 1.18   | パス                   |
| 1/2      | hk3-28   | 0.48         | 0.67   | 0.87   | パス                   |

バンドは重複します。パスしたホストは1.49に達し、失敗したホストは0.85で開始しました。実行中に占有度が成長し、失敗した3つのホストのうち2つのみがスイート開始時にすでに競合していました。それらを分離するエントリー時のしきい値はありません。そのため、競合している2つを捕捉するのに十分に厳しい上限は、明らかにパスするホストも拒否します。`2.0`はスイートを完了したホストで測定されたすべての読み取り値の上に位置します。これらのサンプルのいずれも生き残れなかったホストを拒否し、表のいかなるインシデントでも発生しなかったでしょう。これを厳しくすると誤った拒否が発生すると予想されます。さらに上げるとゲートが機能しなくなります。

その表のRPCフレークは異なる問題であり、このゲートは修正ではありません。それを判断するにはスイート自身のレポートが必要ですが、それはスイート実行前には存在しません。#16945は、全グリーンレポートで唯一の未処理エラーがワーカーRPCタイムアウトであった正確にその形状に対してレーンレベルの再実行を追加します。2つは独立しており、個別に調整または無効にできます。

上限は絶対負荷ではなく比率です。プールはホストサイズを混合しているためです。フリートがリサイズされている間は、`off`を設定してすべてのホストを受け入れます。ゲートはセルフホストのLinux上でのみ実行されます。GitHubホストとmacOSレーンは影響を受けません。読み取れないCPUカウントまたは負荷平均、または`awk`がない場合は、レーンをブロックするのではなく警告付きでジョブを受け入れます。不正なしきい値はゲートをサイレントに無効化するのではなく、設定エラーとして失敗します。

### ワークスペーステストのタイムアウト

`QWEN_RELEASE_WORKSPACE_TIMEOUT_MINUTES`は、リリースパイプラインの3つの`workspace_tests`シャードそれぞれのジョブレベルの`timeout-minutes`を設定します。タイムアウトはスイート自体ではなく予約済みホストの混雑度によってサイズが決められるため、テストの退行を想定するのではなく、ホストが競合している場合はこれを上げてください。

### セルフホストランナーでのVitestワーカーキャップ

`QWEN_CI_VITEST_MAX_WORKERS`は、以下にリストされたステップ（`VITEST_MAX_THREADS` / `VITEST_MAX_FORKS`、対応する最小値は`1`に強制）におけるVitestプロセスを、名前が`ecs-qwen-`で始まる予約済みセルフホストランナー上でキャップします。この変数はメインCIワークスペーステストステップとリリースの`workspace_tests`および`quality_scripts`ステップでのみエクスポートされます。CIおよびリリースワークフローで同じ予約済みプールに到達するVitestを実行する他の統合テストはこれを消費せず、独自のVitest制限を使用します。WebシェルE2EスモークはARM64プールで独自の2つのPlaywrightワーカーで実行されるため、このキャップは適用されません。GitHubホストランナーではこの変数は無視され、Vitestは独自のデフォルトを使用します。

各Vitest実行はキャップを個別に適用します。メインCIワークスペーステストステップは2つのレーンを同時に実行します（`.github/scripts/ci/run-unit-test-lanes.sh`）。メインレーンはCLIとコアのスイートをキャップで実行し、サイドレーンは他のワークスペースのスイートと`npm run test:scripts:unit`をキャップの半分（最低1）で実行するため、ピーク時にはキャップとその半分を合わせた数になります。GitHubホストランナーでは、サイドレーンのVitest実行は2ワーカーを使用します。

このステップは2つのシャード（`Linux unit tests (shard N/2)`）で実行され、それぞれのVitest実行に`--shard=N/2`を渡します。シャードもそれぞれキャップを適用するため、プールでは最大2つのこのようなステップが同時に実行されます。これらは`prepare`ビルドなしでインストールし、`test_build`が一度にビルドしたツリーを展開します。`Test (ubuntu-latest, Node 22.x)`はビルドとすべてのシャードがパスしたときにのみパスします。

`test_build`が唯一ビルドを行うジョブです。これは`scripts/ci-build-cache.mjs`を通じてビルドします。プルリクエストはベースコミットの`main`プッシュが保存したビルドを復元し（`key --at <base>`）、最新のキャッシュされたビルドにフォールバックし、入力が変更されたワークスペースのみを再ビルドします。ワークスペースの追跡ファイル（テストを除く）、ルートファイル、`scripts/tests/`以外の`patches/`と`scripts/`、および依存するワークスペースです。`main`へのプッシュは常にゼロからビルドし、そのビルドを保存します。キャッシュキーにはCPUアーキテクチャが含まれません。x64ラベルのプールにはARM64ホストが含まれており、アーキテクチャ固有の唯一の出力であるバンドルのopentuiネイティブライブラリは、復元と展開のたびにホスト用に再コピーされます（`ci-build-cache.mjs host-assets`）。

ユニットテストシャード、2つの`Integration Tests (no-AK, shard N/2)`シャード、および2つのWebシェルスモークシャードはすべてその1つのツリーを展開します。`test_build`はそれを読み取るチェック（サーブのファストパスバンドルクロージャー、コアのサブパスエクスポート、および設定スキーマの鮮度チェック。これらは`Lint & Static`が以前ビルドしていたもの）も実行します。`Integration Tests (no-AK, No Sandbox)`はビルドとすべての統合シャードがパスしたときにのみパスします。ドラフトプルリクエストは統合シャードとブラウザスモークをスキップし、レビュー準備完了にマークするとそれらを含む実行が開始されます。`packages/managed-agent-server/`または`packages/sdk-java/`（TypeScriptスイートが読み取るファイルを除く）に限定された変更は`java_only`として分類されます。`Lint & Static`はペイロードとそれらのツリーを名前付けする`scripts/tests`スイートを実行し、TypeScriptビルドとテストレーンはスキップされます。

### テスト実行以外の関連変数

`release.yml`は`QWEN_RELEASE_STATIC_TIMEOUT_MINUTES`（デフォルト`60`、`quality_static` lintレーンを制御）と`QWEN_RELEASE_BUILD_TIMEOUT_MINUTES`（デフォルト`45`、`quality_build`パッケージングレーンを制御）も公開しています。これらはテスト実行ではなく静的リンティングとアーティファクトビルドを制御するため、このページのテスト実行スコープの外にあります。
