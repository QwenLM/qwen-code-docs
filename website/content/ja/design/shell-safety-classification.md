# シェル安全性の分類

## コンテキストとスコープ

Issue [#6949](https://github.com/QwenLM/qwen-code/issues/6949) では、プランモードが、読み取り専用であることが証明されたコマンドと、静的に振る舞いを確定できないコマンドを区別する必要がある。ブール値ではその区別を保持できないため、この変更は `shellAstParser.ts` に 3 状態のファクトレイヤーを導入するが、パーミッションのルーティングは変更しない。

この変更は、Shell、Monitor、PermissionManager、speculation、メモリースコープのエージェント、ACP、プランモードのプロンプト、プラン終了の動作におけるルーティングや呼び出し元のロジックを変更しない。既存のブール値のコンシューマーは、クラシファイアが強化された箇所でより保守的になり得る。フォローアップの変更では、このクラシファイアを変更せずに、新しいファクトを使って `unknown` コマンドをワンタイム承認へルーティングできる。

## 契約

`classifyShellCommandSafety(command)` は、次の結果を持つ内部モジュール API である:

| 結果        | 意味                                                                                                                          |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `read-only` | すべての実行可能パスが、現在のルールによって永続的または外部の状態を変更しないことが証明されている。                                 |
| `write`     | 構文に、ファイル、Git、プロセス、またはその他の状態のミューテーションの肯定的な証拠が含まれている。コマンドが最終的に成功する必要はない。 |
| `unknown`   | サポートされている静的ルールでは、コマンドが安全であることもミューテーションを行うことも証明できない。                                                     |

有効な AST に対しては、結果は `write > unknown > read-only` の順序で結合される。`ERROR` を含むツリーは、部分的な構文を評価する前に `unknown` として分類される。コマンド置換とプロセス置換は、その実行可能な内容がスキャンされている間 `unknown` の下限を課すため、ネストされた既知のライターが結果を `write` に引き上げる。リダイレクト解析はリダイレクトノード内部の置換を所有し、コマンドおよびステートメントの評価器はそれらのノードを置換スキャンから除外することで、ネストされた置換の重複トラバースを防ぐ。制御フローは同じ unknown の下限を使用し、取り得るブランチをスキャンする。関数定義は実行ではないため、その本体を実行された書き込みとして分類することなく `unknown` のままである。

単独の純粋な代入と `cd` は、既存の互換動作を維持する。コマンドに前置される代入や、別のステートメントと同じ複合シーケンスを共有する代入は、`LD_PRELOAD`、`PATH`、`PAGER`、ツール固有の設定などの変数が振る舞いを変え得るため、`unknown` の下限を課す。明示的な書き込みの証拠が依然として優先される。サブシェルとコマンドグループは、実行された内容を統合する。この API は与えられたソース文字列のみを解析し、`sudo` やインタープリターの展開、PATH やエイリアスの解決、シェル設定の読み込みは行わない。

## パーサー失敗と互換 API

非公開のクラシファイアは、tree-sitter の読み込み中や実行中にスローし得る。公開されている 3 状態の API は、それらの失敗を `unknown` にマップし、決して正規表現による確信に置き換えない。パース中にスローしたパーサーは破棄され、既に読み込まれている Bash 言語から再構築される。失敗したインスタンスは汚染されたままである可能性があるためである。これによりランタイムや言語の再読み込みは行われない。既存の `isShellCommandReadOnlyAST()` 互換 API は `read-only` の場合のみ `true` を返すが、tree-sitter が読み込めない場合や実行時にスローする場合の既存の正規表現フォールバックは維持する。構文的に無効なツリーは通常の `unknown` 結果であり、パーサー失敗ではないため、そのフォールバックに入ることは決してない。正常に返されたツリーはすべて、`finally` ブロック内で一度だけ解放される。

この非対称性は意図的である: 新しいコンシューマーには正直な不確実性のファクトが必要であり、既存のブール値のコンシューマーは、明示的に移行するまでパーサーの可用性に基づく動作を維持する。

## サポートされる証拠

クラシファイアは、直接的なファイルシステムライター、プロセスへのシグナル送信コマンド、出力リダイレクト、Git のミューテーションファミリー、および `find`、`sed`、`awk`、`sort`、`tree`、`uniq`、`tee`、`dd` の明示的な書き込みモードについて、限定的で大文字小文字を区別するセットを認識する。Sed と AWK は、インラインプログラムをオプション値やファイル引数と区別する共有の線形スキャナーを使用するため、エスケープされた入力、不正な形式の入力、反復の多い入力によって正規表現のバックトラッキングがトリガーされたり、ファイル名から書き込みの証拠が捏造されたりすることはない。`diff`、`log`、`show` の Git 出力ファイルは書き込みである。ステートフルな `printf -v` の形式は unknown である。明示的な Git ヘルパーと署名検証（pager/config の環境変数オプション、diff/テキスト変換ヘルパー、grep の外部 pager、署名プレースホルダーを含む）は unknown である。サポートされていない Git のグローバルオプションとサブコマンドのヘルプパスも fail closed（失敗時は拒否）となる。ヘルプが外部ビューアーを起動し得るためである。動的実行、外部スクリプト、曖昧な出力ターゲット、インタープリターとラッパー、`sort --compress-program`、ripgrep のプリプロセッサー、ホスト名ヘルパー、アーカイブ検索（`--pre`、`--hostname-bin`、`--search-zip`、`-z`）、および通常の pager コマンドは `unknown` のままである。オプションターミネーターとサポートされているオプションの値の項数は解釈されるため、文字通り `--help` という名前のファイル名やメッセージがヘルプの呼び出しと誤認されることはない。大文字小文字の異なるコマンド名、リストにないパッケージマネージャー、サービス、カスタム実行ファイルも `unknown` のままである。クラシファイアはサンドボックスではない。

非推奨の同期チェッカーは、同期スケジューリングに必要な、新たに拒否されたすべてのパターンをミラーリングする。パラメーター展開は `shell-quote` に消去させる代わりにセンチネルで保持し、不正な形式の末尾パイプラインや代入を持つ複合コマンドを拒否し、ラッパーは元のコマンドから評価する。これは意図的にブール値のままであり、AST クラシファイアよりも保守的である: `printf`、オプションの多い `sort`、`tree`、`uniq`、`rg`、`ripgrep` コマンド、および最も単純なリスト表示モードを超えた Git のブランチ形式は、逐次実行として扱われる。

## コンシューマーと移行の境界

現在のブール値のコンシューマーは、Shell、Monitor、PermissionManager、speculation ゲート、メモリースコープのエージェント設定である。それらの呼び出し元はこのリファクタリングでは変更されない。同期チェッカーは、コアのツールスケジューラーとレガシーのシェルパーミッションユーティリティでも使用されている。スケジューラーは、ラッパーが展開されて一見読み取り専用のコマンドになる代わりに unknown のままであるよう、元のコマンドをチェッカーに渡すようになった。`extractCommandRules()` は安全性の分類とは独立したままである。

フォローアップの `fix(core): Route unknown Plan shell commands to one-off approval` は、プランのパーミッション境界でのみ `classifyShellCommandSafety()` を利用すべきである。承認の provenance、有効期間、ACP の動作、プラン終了との相互作用は別途定義する必要があり、それらのポリシーはファクトレイヤーに属さない。

## Claude Code の参照

Claude Code の Bash 解析は、2 つの設計原則の証拠として有用である: パースの不確実性は明示的に表現しなければならず、パースが利用できない場合や複雑すぎる場合、パーミッションの決定は fail closed（失敗時は拒否）でなければならない。Qwen Code は現在の境界で小さなクラシファイアを必要とするだけであるため、そのより大きな Bash パーサーやポリシーエンジンは模倣しない。

## 検証

ユニットカバレッジは、3 つの状態すべて、複合コマンドの優先順位、置換、構文エラー、パーサーの初期化および実行時の失敗、敵対的なネスト入力やエスケープ入力に対する制限された動作、互換の単調性について、テーブル駆動のマトリクスを使用する。同期チェッカーとスケジューラーのテストは、新たに unsafe と判明したコマンドが並行 Shell バッチに入ることを防ぐ。
