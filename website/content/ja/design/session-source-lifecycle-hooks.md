# ライフサイクルフックにおけるセッション source

## コンテキスト

デーモンのセッション作成は、すでに任意の `sourceType` と `sourceId` の値を `_meta['qwen.session.source']` として ACP に転送しています。ACP ランタイムは現在、チャネルセッションのネイティブ cron を無効化するために source type を使用していますが、ライフサイクルフックのペイロードはどちらの値も観測できません。そのため、ブリッジが source を永続化する前に `SessionStart` が発火した場合、受信側は新しいセッションの帰属を特定できません。

## 設計

ACP セッションの境界で既存の source メタデータを一度だけパースします。2 つの任意の文字列を、セッション ID やその他のセッションスコープの状態と並べてセッションの `Config` に保存し、読み取り専用のゲッターを公開します。

フックのイベントハンドラーは、存在する source の値を共通入力に追加します:

- `sourceType` は `source_type` になる。
- `sourceId` は `source_id` になる。

条件付きのオブジェクトスプレッドにより、欠落している値はシリアライズされず、空や undefined のフィールドも出力されません。すべてのライフサイクルイベントが共通入力ビルダーを使用するため、`SessionStart`、`UserPromptSubmit`、`Stop`、`SessionEnd` は、イベント固有の配線なしで同じ帰属情報を受け取ります。

## 境界

これは既存の作成メタデータの読み取りであり、REST の作成リクエスト、ACP ブリッジのメタデータキー、ネゴシエーション、セッションの永続化、再開の動作は変更しません。source メタデータなしで作成されたセッションは、以前のフックペイロード形状を維持します。

## 検証

- フックハンドラーのテストは、`SessionStart` ペイロードにおいて source フィールドが存在する場合と欠落している場合をカバーする。
- ACP セッションのテストは、チャネルの source メタデータがセッションの `Config` に伝播することをカバーする。
- 既存のチャネルワーカーのテストは、チャネルインスタンス名を `sourceId` とすることを含め、引き続き作成メタデータをカバーする。
