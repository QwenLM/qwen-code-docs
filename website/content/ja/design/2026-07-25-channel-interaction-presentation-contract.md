# チャネルインタラクションプレゼンテーション契約

## ステータス

PR #6930 に向けてチャネル中立な契約を実装済み。DingTalk 固有の投影と運用の詳細は
引き続き `2026-07-15-dingtalk-interactive-cards.md` に記載する。

## 問題

以前の実装では、run レベルの `started` イベントで DingTalk のステータスカードを作成していた。
その後モデルが `ask_user_question` を呼び出すと、アダプターは 2 枚目のフォームカードを作成し、
1 枚目のカードを `Waiting for input` に変更していた。モデルが目に見える回答を生成していない
場合でも、ユーザーには 2 枚のアクティブなカードが見えていた。

これは DingTalk のレンダリング競合ではない。所有権の誤りである:

- run レベルのイベントが可視出力イベントとして扱われている;
- 出力と入力のプレゼンテーションが独立したアダプターのステートマシンになっている;
- 可視出力セグメントの共有された定義がない;
- 入力リクエストがアクティブな出力プレゼンテーションを終了させない。

DingTalk のカード削除や recall のみを修正しても所有権の誤りは残り、Feishu や将来の IM
アダプターに安定したインタラクション契約を与えることにならない。

## ゴール

- ユーザー可視の出力がある場合にのみ出力プレゼンテーションを作成する。
- モデルが可視出力を生成する前に入力を求めた場合、ネイティブの入力カードを唯一のアクティブな
  プレゼンテーションにする。
- 入力カードはそのターミナル状態までインプレースで更新する; 通常のライフサイクル中は削除しない。
- 合成のユーザーメッセージを注入せずに、元のパミッションとモデルのコンテキストを再開する。
- すべての出力セグメントと入力リクエストに、正確な run、セッション、ターゲット、オーナーの
  相関を持たせる。
- DingTalk、Feishu、および将来の IM アダプターが、プラットフォームのカード API やテンプレート
  スキーマを共有せずに同じセマンティクスをオプトインできるようにする。
- オプトインしないアダプターの既存の挙動を維持する。

## 非ゴール

- 汎用のクロスプラットフォーム `createCard`、`updateCard`、`deleteCard` API。
- ネイティブの構造化入力の代替としてのフリーフォームテキストの解析。
- すべての IM にストリーミング出力、フォーム、ボタンのサポートを要求すること。
- DingTalk や Feishu のプラットフォームハンドルを `ChannelBase` に移すこと。
- ライブコールバックをプロセス再起動をまたいで永続化すること。
- Core、ACP、または `ask_user_question` の応答契約を変更すること。
- DingTalk の修正の中で既存の Feishu カード実装をリファクタリングすること。

## 設計原則

### 共有セマンティクス、ローカルな投影

`ChannelBase` はコンテキスト、順序付け、settlement のセマンティクスを所有する。IM アダプターは
ネイティブレンダリング、コールバックトランスポート、プラットフォームハンドル、スロットリング、
投影の失敗を所有する。

共有レイヤーはカードを一切参照しない。参照するのは:

- プロンプト run;
- 可視出力セグメント;
- 構造化入力リクエスト;
- それらのオブジェクトのターミナルな結果。

### コンテキストはキャプチャされ、再発見されない

権威ある相関チェーンは:

```text
SessionTarget(chatId/threadId) -> sessionId -> runId -> segmentId/requestId
```

アダプターはネイティブプレゼンテーションを作成するときにこのチェーンをキャプチャする。
コールバックはキャプチャされたレコードを解決する。チャット内の最新のカード、最新の run、
最新のセッションを検索してはならない。

`SessionTarget.threadId` は、プラットフォームがスレッドを公開している場合、引き続きスレッドの
パーティションである。スレッドセマンティクスのないプラットフォームは `chatId` を使用する。
プラットフォームのコールバックは独立して新しいターゲットを導出しない。

### トランザクションと投影は別物

パミッションレスポンスがトランザクションである。カードの更新は UI の投影である。
成功したパミッションレスポンスは、後続のネイティブカード更新が失敗したことを理由に
ロールバックされない。

## 共有セマンティックモデル

### プロンプト run

`runId` は Channel が所有する 1 回のプロンプト実行を識別する。既存の正確な run 単位の
キャンセルとオーナーのルールを保持する。

`started` ライフサイクルイベントは run が受け入れられたことを意味する。出力プレゼンテーションは
開始しない。

### 出力セグメント

出力セグメントは、run 内の 1 つの連続したユーザー可視のアシスタントテキストの並びである。
`ChannelBase` は、そのセグメントの最初の可視テキストが到着したときにのみ不透明な `segmentId`
を割り当てる。

セグメントは以下のいずれか最初に発生した時点で終了する:

- レスポンスの境界;
- 構造化入力リクエストのプレゼンテーション;
- 最終レスポンスの配信成功;
- run の失敗;
- run のキャンセル。

構造化入力リクエストの settlement 後、同じ run 内の後続のテキストは新しい `segmentId` を持つ
新しいセグメントを開始する。質問前のセグメントを再開したり上書きしたりすることは決してない。

### 入力リクエスト

`requestId` は 1 つの元の pending の `ask_user_question` パミッションリクエストを識別する。
1 つのリクエストはそのツール呼び出しからの正規化されたすべての質問を含みうる。
プレゼンテーションの所有権は `sessionId + owner.id` でスコープされる。異なるユーザーや
セッションは同時にライブの入力プレゼンテーションを持ちうる。1 つの run 内で同じスコープの
2 番目のリクエストは `unsupported` を返し、最初のネイティブプレゼンテーションを回答可能な
まま保ち、既存のテキストパーミッションフォールバックを使用する。

アダプター内部の入力ステートマシンは:

```text
reserved -> pending -> claimed -> terminal
```

これはコールバックの調停であり、プラットフォームのカード状態ではない。DingTalk が公開する
のは `pending`、`submitted`、`cancelled`、`expired` のみ: 受け入れられた送信は `submitted`
に、受け入れられたユーザーキャンセルは `cancelled` に、タイムアウト、外部での解決、または
応答不能な responder は `expired` に対応する。すべてのターミナル遷移は既存のネイティブ入力
プレゼンテーションをインプレースで更新し、決して削除しない。

共有の settlement ラベルは `resolved_outside_presenter`。この契約はネイティブフォームや
その他のインタラクションサーフェスで共有されるため、プラットフォーム固有の名詞がパブリック
API になることはない。

## 共有契約

既存のフックが引き続き拡張サーフェスである。プラットフォーム操作ではなく、より強い
セマンティックコンテキストを受け取る。

```ts
interface ChannelOutputSegmentContext {
  channelName: string;
  sessionId: string;
  runId: string;
  segmentId: string;
  owner: ChannelPromptOwner;
  target: SessionTarget;
  messageId?: string;
}

type ChannelOutputSegmentEndReason =
  | 'response_boundary'
  | 'input_requested'
  | 'completed'
  | 'failed'
  | 'cancelled';
```

chunk と完了のフックは、ソース互換性のため任意の末尾コンテキスト引数を追加する。
セグメントの終了は専用フックを使用し、アダプターがレスポンス境界と入力リクエストおよび
ターミナルな原因を区別できるようにする:

```ts
protected onResponseChunk(
  chatId: string,
  chunk: string,
  sessionId: string,
  segment?: ChannelOutputSegmentContext,
): void;

protected onOutputSegmentEnd(
  chatId: string,
  sessionId: string,
  segment: ChannelOutputSegmentContext,
  reason: ChannelOutputSegmentEndReason,
): void | Promise<void>;

protected onResponseBoundary(
  chatId: string,
  sessionId: string,
): void | Promise<void>;

protected onResponseComplete(
  chatId: string,
  text: string,
  sessionId: string,
  segment?: ChannelOutputSegmentContext,
): Promise<void>;
```

より少ない引数を受け取る既存のオーバーライドは引き続き有効であり、変更されない。
`ChannelBase` は、監視されている Channel 所有の run についてレスポンスフックに常にセグメント
コンテキストを供給し、そのセグメントが閉じるたびに `onOutputSegmentEnd` を呼び出す。
そのデフォルト実装は `response_boundary` のみをレガシーの `onResponseBoundary` フックに
委譲する。loop、webhook、およびレガシーの合成パスは引き続きネイティブインタラクション
プレゼンテーションの対象外である。

`ChannelUserInputRequestContext` は既存のリクエスト responder と settlement サブスクリプション
を保持する。さらにキャプチャされたインタラクションスコープを追加で運ぶ:

```ts
interface ChannelUserInputRequestContext {
  requestId: string;
  sessionId: string;
  runId: string;
  owner: ChannelPromptOwner;
  target: SessionTarget;
  precedingSegmentId?: string;
  // 既存の正規化された質問、送信オプション、onSettled、respond
}
```

その settlement reason の union は `resolved_outside_presenter`、`cancelled`、`run_cancelled`
を使用する。

`presentUserInputRequest` を呼び出す前に、`ChannelBase` は共有セグメント identity を閉じて
その ID を `precedingSegmentId` として渡すが、プラットフォームのレスポンス境界は投影しない。
対応するアダプターは、ネイティブ入力を提示する前に自身のプレゼンテーションを
`input_requested` で閉じる。これにより非対応アダプターが既存のストリーミング状態をクリア
したり変更したりすることがなくなる。クローズはべき等なので、先にまたは後から到着した
プラットフォームのレスポンス境界イベントが 2 つの異なるセグメントを閉じることはできない。

共有の capability フラグは不要。capability は挙動で表現される:

- 出力フックは任意であり、デフォルトは既存の配信;
- ネイティブの構造化入力が利用できない場合、`presentUserInputRequest` は `unsupported` を
  返す;
- プラットフォーム固有の設定はアダプター内に残る。

これによりグローバルなブール値の無効な組み合わせを回避し、アダプターがフォームなしで
ストリーミング出力を、またはストリーミング出力なしでフォームをサポートできるようになる。

## 各アダプター内のプレゼンター契約

アダプターは、メインのアダプタークラスにプラットフォーム状態を追加するのではなく、
内部プレゼンターを構成してもよい。そのプレゼンターが所有するのは:

- `segmentId -> ネイティブ出力ハンドル`;
- `requestId/outTrackId/messageId -> ネイティブ入力ハンドル`;
- `runId` ごとの 1 つのシリアライズされた投影キュー;
- 上限付きの出力スナップショットと更新の合体;
- コールバックのオーナー検証とワンショットのクレーム;
- ネイティブ API のタイムアウトとエラーログ;
- コンパクトなターミナルのトゥームストーン。

run ごとの投影キューはこの順序を保証する:

```text
古い出力セグメントの終了
  -> 入力プレゼンテーションの作成
  -> 入力のターミナル状態の更新
  -> 次の出力セグメントを最初の可視テキストで作成
```

中間出力の追加は置き換え可能なフルスナップショットをキューに入れ、モデルの生成をブロック
しない。境界、入力プレゼンテーション、最終配信は同じキューに入るため、先行する書き込みを
追い越すことはできない。

## 必須のインタラクションシーケンス

### 通常の回答

```text
run started
  -> ネイティブ出力なし
最初の可視テキスト
  -> segment-1 を割り当て
  -> ネイティブ出力プレゼンテーションを遅延作成
後続のチャンク
  -> segment-1 を更新
run completed
  -> segment-1 をインプレースで completed に更新
```

プロバイダーがチャンクを発行せずに最終レスポンスを返す場合、最終配信がセグメントを
割り当て、completed な出力プレゼンテーションを 1 つ作成する。

### 直接の質問

```text
run started
  -> ネイティブ出力なし
ask_user_question リクエスト
  -> request-1 の入力プレゼンテーションを作成
```

出力セグメントは存在しないため、ユーザーに見えるのは入力プレゼンテーションのみ。
pending の間、別の run ステータスプレゼンテーションは存在しない。入力プレゼンテーションの
pending 状態こそが、run がユーザーを待っているという可視の表示である。

### テキストの後の質問

```text
最初の可視テキスト
  -> segment-1 の出力プレゼンテーションを作成
ask_user_question リクエスト
  -> segment-1 をインプレースで完了
  -> request-1 の入力プレゼンテーションを作成
```

完了した出力は会話履歴として残るが、アクティブなのは入力プレゼンテーションのみ。

### 質問の送信と継続

```text
有効なコールバック
  -> request-1 を相関付けオーナーを検証
  -> request-1 をアトミックにクレーム
  -> コールバックを ACK
  -> 元のパミッションに応答
  -> request-1 をインプレースで submitted に更新
同じ run 内の次の可視モデルテキスト
  -> segment-2 を割り当て
  -> 新しい出力プレゼンテーションを作成
```

回答は元のモデルコンテキストを再開する。アダプターは合成のインバウンドメッセージを注入しない。

### 同時の質問

同じ `sessionId + owner.id + runId` に対してアクティブなネイティブ入力プレゼンテーションは
最大 1 つ。そのスコープでの 2 番目のリクエストは `unsupported` を返し、`ChannelBase` は
最初のネイティブプレゼンテーションが有効なままセマンティックなテキストフォールバックを
送信する。これにより、キャンセルやインバウンドメッセージを合成せずに、到達不能な pending
リクエストを回避する。異なるユーザーとセッションは引き続き独立しており、run の終了は
その run が所有するすべてのプレゼンテーションを閉じる。

## DingTalk の投影

DingTalk のプレゼンターは次のように対応付ける:

- 出力セグメントを 1 つのステータスカードテンプレートインスタンスに;
- 入力リクエストを 1 つの質問カードテンプレートインスタンスに。

現在の実装からの変更点:

- `started` ではステータスカードを作成しない;
- セグメントの最初のチャンクまたは最終レスポンスで作成する;
- ステータスレコードは `segmentId` をキーとし、Stop 用には `runId` を保持;
- 質問カードの作成前にアクティブなセグメントを閉じる;
- 同じ run が別の質問を要求した場合、最初の質問カードをアクティブに保ち、新しいリクエストには
  テキストフォールバックを使用させる;
- 古いステータスカードを `Waiting for input` に変更しない;
- 質問カードは submitted、cancelled、expired、または外部での解決にインプレースで更新する;
- 新しいステータスカードは送信後のテキストが始まったときのみ作成する。

通常パスではどちらのカードも recall も削除もしない。部分的に失敗したネイティブ配信が、
更新不能な使用不能な孤立カードを残した場合、プラットフォームのクリーンアップが最終手段の
エラーパスとして削除または recall してもよい; これはビジネス状態の遷移ではない。

Stop アクションは引き続き、セグメントがキャプチャした正確な `runId` とオーナーにバインド
される。ライブの出力セグメントからの Stop はその run のみをキャンセルする。
ターミナルな履歴セグメントは後続の run を停止できない。

質問カードの Cancel アクションは元の入力リクエストを cancelled として解決する。
既存の `ask_user_question` キャンセルセマンティクスが run を終了させるかを判断する;
アダプターは 2 回目のセッション全体キャンセルを発行しない。

最初のメタデータ投影は、意図的に設定されたモデルと経過実時間に限定される。DingTalk は
任意のモデルを既存の Channel 設定から読み取り、`Running · qwen3.7-max · 12s` のような
実行中の行をレンダリングする。既存の合体されたモデルテキストストリームがフラッシュされ、
表示される秒が変わったときに経過値を更新するため、ステータスは独立したタイマーなしで
1 秒あたり最大 1 回の更新しか追加しない。したがって、サイレントな思考やツール実行では、
次のテキストフラッシュまで可視カウンターは進まない。ターミナルの更新は常に正確な経過値を
書き込む（例: `Stopped · qwen3.7-max · 18s`）。Channel 設定がモデルを選択していない場合、
その行はモデルを推測せず省略する。

この増分はトークン使用量を公開しない。正確なターンごとのトークン数は現在の Channel ブリッジ
やライフサイクル契約には存在せず、可視テキストからの推定は誤解を招く。後続の変更で
トークンメタデータを追加するのは、共有ランタイムが権威あるターンごとのスナップショットを
提供する後に限る。メタデータの欠落はセグメント状態を遅延させたり変更したりしない。

## Feishu への拡張

既存の Feishu 実装はすでにレスポンスチャンクでストリーミングカードを遅延作成しており、
インタラクティブメッセージの更新や削除も可能。DingTalk の修正に合わせて変更する必要はない。

後続の Feishu インタラクション変更は同じコンテキストを採用できる:

- `segmentId` が出力カードの暗黙の `inboundMsgId` 所有権を置き換える;
- `runId` は引き続き、Stop が新しい run をキャンセルしないよう保護する;
- ネイティブのインタラクティブフォームまたはボタンが `presentUserInputRequest` を実装する;
- コールバックはキャプチャされた `requestId` を解決し、チャット内の最新のカードではない;
- 同じ入力メッセージがターミナル状態にパッチされる;
- サポートされないフィールド型は、任意のテキストを解析するのではなく `unsupported` を返すか、
  読みやすいプラットフォームローカルな失敗でキャンセルする。

Telegram、WeCom、Weixin、QQ、およびプラグインアダプターは、出力コンテキスト、入力
コンテキスト、両方、またはどちらも独立して消費できる。デフォルトフックは現在の挙動を保持する。

## 失敗と degradation のルール

| 失敗                                                  | 必須の挙動                                                                                                                               |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 出力プレゼンテーションの作成失敗                       | 上限付きテキストを保持し、既存の待機テキスト配信パスを使用する。                                                                            |
| 中間出力の更新失敗                         | そのセグメントのネイティブストリーミングを停止; フォールバック用に最終テキストを保持する。                                                               |
| 出力のターミナル更新失敗                             | 既存のフォールバックで最終テキストを送信し、ネイティブ投影を利用不可とマークする。                                                       |
| 入力プレゼンテーションが `unsupported` を返す                 | 既存のセマンティックパーミッションメッセージを使用; 後続のフリーフォーム返信を解析しない。                                                             |
| オプトイン後のネイティブ入力作成失敗                 | ネイティブの質問が失敗したことをユーザーに伝え、元のリクエストをキャンセルし、明示的なリトライを許可する。                                             |
| パミッションレスポンスは成功したが入力カードの更新が失敗 | パミッションを解決済みのまま保ち、ターミナルのトゥームストーンを保持し、投影の失敗をログに記録する。                                                      |
| コールバックが重複、陳腐化、外部、または不正形式      | 同期検証後に ACK し、状態変更は行わない。                                                                              |
| pending の入力を残して run が終了                             | それらの入力プレゼンテーションをインプレースで cancelled に更新する。                                                                                         |
| ライブカードを残してプロセスが再起動                         | コールバックを pending でなくなったと扱い、プラットフォームの相関が許す場合に expired/unavailable に更新する。永続的な復旧は別作業。 |

## 状態とリソースの上限

- 出力内容はセグメントごとに可視 20,000 文字の上限を維持。
- 各セグメントは 1 つのネイティブ書き込みを in-flight に、1 つの置き換え可能な pending
  スナップショットを許可。
- ネイティブ API 呼び出しは明示的なタイムアウトを保持。
- ライブの run、セグメント、リクエスト、コールバックのマップは挿入順で上限付きを維持。
- ターミナルのトゥームストーンは相関とターミナル状態のみを含み、responder、質問、回答、
  タイマー、内容は保持しない。
- すべてのクリーンアップは正確なオブジェクト同一性をチェックし、遅延した非同期完了が
  同じセッションの新しいレコードを変更できないようにする。

## マイグレーション計画

修正は小さく順序立てたままにする:

1. 出力セグメントコンテキストとべき等なセグメント境界を `ChannelBase` に追加し、
   任意の末尾パラメータにより既存のフックシグネチャを保持する。
2. 遅延セグメント割り当て、境界の順序付け、直接の質問、継続セグメント、同時の質問、
   コンテキスト分離の共有テストを追加する。
3. DingTalk の run スコープのステータスコントローラーを、セグメントスコープの出力レコードと
   リクエストスコープの入力レコードを所有する run プレゼンターに置き換える。
4. 即時のステータスカード作成と `Waiting for input` 投影を削除する。
5. 既存の最終コンテンツ V2 フィールドと構造化質問の settlement ロジックを保持する。
6. 実機で DingTalk の直接質問、テキスト後の質問、送信後の継続、Stop、タイムアウト、
   失敗シナリオを検証する。
7. Feishu のプロダクションコードは変更しない; 共有シグネチャ変更が必要とする場合のみ
   互換性の証拠を追加する。

ローカルの修正は、実機の受け入れが上記のシーケンスと一致した後にのみコミットできる。
明示的な承認があるまで push しない。

## 受け入れ基準

### 共有 Channel

- `started` は出力セグメントを割り当てない。
- 最初の可視テキストが正確に 1 つのセグメント ID を割り当てる。
- レスポンス境界または入力リクエストがそのセグメントを正確に 1 回閉じる。
- 質問の settlement 後のテキストは、同じ run とセッション内で異なるセグメント ID を受け取る。
- `chatId/threadId`、セッション、run、リクエスト、セグメント、オーナーの相関は
  並行コンテキスト間で交差できない。
- インタラクションサポートのない既存アダプターは挙動を維持する。

### DingTalk

- 直接の `ask_user_question` は 1 つの質問カードを表示し、ステータスカードは表示しない。
- 質問カードは送信、キャンセル、期限切れ、外部での解決でインプレースで更新される。
- 同じ run 内の 2 番目の質問は、最初のネイティブカードが回答可能なままテキスト
  フォールバックを使用する。
- 異なるユーザーとセッションは独立したライブ質問カードを維持する。
- 質問前のテキストは完了した履歴ステータスカードに残る。
- 送信後のテキストは新しいステータスカードに現れる。
- `Waiting for input` を表示するステータスカードはない。
- Stop はキャプチャされた正確な run のみをキャンセルする。
- 最終完了コンテンツは V2 の `blockList`、`content`、`copy_content` フィールドを通じて
  可視のまま。

### IM 間の互換性

- Feishu はビルドでき、既存のストリーミングカードと Stop のテストは、新しいプレゼンターを
  採用せずにグリーンを維持する。
- アダプターはストリーミング出力なしでネイティブ入力を実装できる。
- アダプターはネイティブ入力なしでストリーミング出力を実装できる。
- どちらもサポートしないアダプターは既存のテキスト挙動を継承する。

## 決定の要約

共有の抽象化はインタラクションプレゼンテーション契約であり、カードフレームワークではない。
`ChannelBase` はコンテキストとセグメント/リクエストのセマンティクスを所有する。各 IM は
自身のネイティブプレゼンターを所有する。出力カードは遅延かつセグメントスコープ; 入力カードは
リクエストスコープでインプレース更新。これにより DingTalk の二重アクティブカードの挙動を
除去しつつ、Feishu と将来のアダプターに安定したプラットフォーム中立の拡張パスを与える。
