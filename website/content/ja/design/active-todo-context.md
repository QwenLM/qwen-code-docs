# アクティブな Todo コンテキスト

## 問題

`todo_write` は、現在のリストをリマインダーとして自身のツール結果にのみ提示する。ツール呼び出しが続くと、そのリマインダーの顕著性は失われ、モデルは未完了の項目を残したままターンを終了してしまう可能性がある。永続化された todo ファイルは、それを作成したワークチェーンよりも長く存続しうるため、ライブな制御状態としては不適切である。

## 設計

`todo_write` が成功した後、未完了の項目のみを含むリマインダーを、安定したワークチェーンのオーナー配下に保持する。リトライや関連する自動ターンで使用されるプロンプト ID はそのオーナーに解決されるため、並行する通知ブランチがフォアグラウンドのリマインダーを移動・上書きすることはない。バックグラウンドタスクとループウェイクアップは、作成時にオーナーをキャプチャし、自身の自動ターンと共にそれを持ち帰る。無関係な cron や通知のターンは、ターン終了時に削除される独立したオーナーを使用する。リトライまたは関連する自動ターンの最初のリクエスト時と、後続のツールターンでは function レスポンスの後にリマインダーを注入する。すべての todo が完了したとき、新しい通常のワークチェーンが開始したとき、またはセッションが変更されたときにクリアする。

注入されたすべてのコピーはチャット履歴に永続的に記録されるため、ターンごとの注入はツールターン数に応じてライブコンテキストを線形に増大させる。そのため、ツールターンの注入は、状態が最後に提示されて以降、3 ツールターンごとにのみリマインダーを再発行する（`todo_write` の結果自体もカウントに含む）。ターン開始時の注入は常に発火し、その間隔をリセットする。ペイロードは、800 文字を上限としたコンパクトな `- [status] content` 行のリストである。履歴は引き続き追記専用であるため、プロバイダーのプレフィックスキャッシングには影響しない。

これは stop のセマンティクスを変更するものでも、`todoStopGuard` を有効にするものでもない。このガードは引き続き、モデルがすでに停止を試みた後のオプションの有界リカバリーであり、本変更は代わりに、その決定の前にタスクのコンテキストを保持する。

## 検証

- 未完了の項目がある書き込みの成功は、セッションのリマインダーを更新する。
- 完了したリストはそれをクリアする。
- Core と ACP のツール結果メッセージは、function 結果の後にリマインダーを追加する。
- ACP のターン途中のユーザー入力は引き続き最後尾に置かれ、したがって優先度が保たれる。
- 通常の新しいプロンプトは古い状態をクリアし、リトライ／続行はそれを保持する。
- 独立した自動ターンは隔離され、関連する自動ターンは継承する。
- 終端の自動ターンは、その一時的な所有状態を解放する。
