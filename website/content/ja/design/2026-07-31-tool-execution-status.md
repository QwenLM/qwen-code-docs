# ツール実行ステータス

## 動機

ターミナルのツール呼び出しステータスは、呼び出し全体が成功、失敗、キャンセルされたかを
記述する。ディスパッチャーが実際に `invocation.execute()` に入ったかは語らない。
したがって、検証失敗、パミッション拒否、実行失敗、実行後の失敗を正確に計測するには、
独立した実行結果が必要になる。

## 契約

`ToolCallResponseInfo` は、ソースと記録の互換性のために任意の `executionStatus` を運ぶ:

```ts
type ToolExecutionStatus = 'not_started' | 'success' | 'error' | 'cancelled';
```

Core スケジューラー（`CoreToolScheduler`）と ACP の `Session.runTool` は常にこの
フィールドを設定する。古い記録、サードパーティのプロデューサー、サブエージェント結果の
プロジェクション（別のエージェントが報告した結果をリプレイする非インタラクティブな
`buildResponse` パス）からの欠落値は、テレメトリー境界でのみ `unknown` になり、
ターミナルの呼び出しステータスから推論されることは決してない。

ターミナルと実行の軸は意図的に独立:

| ターミナルのステータス | 実行ステータス | 例                                                                              |
| --------------- | ---------------- | ------------------------------------------------------------------------------------ |
| `success`       | `success`        | 通常のツール完了                                                               |
| `success`       | `not_started`    | プロトコルレベルの合成 sibling レスポンス                                            |
| `error`         | 任意の値        | 実行前の拒否、実行エラー、後処理エラー、またはバッチフックによる上書き |
| `cancelled`     | 任意の値        | 実行前、実行中、実行後のキャンセル                                      |

各行を（ターミナル、実行）のペアとして読むと、無効な組み合わせは `success/error` と
`success/cancelled` のみ: `success` でターミナルする呼び出しは、実行ステータスが
`success` または `not_started` のみを運べる。
実行ステータスは `invocation.execute()` が確定した時点で凍結される; フック、結果の
ブリッジング、永続化、バッチ処理はそれを上書きできない。PostToolBatch の適用可否と
その親ツールのスパンは、スケジューラーのバッチ開始時にスナップショットされるため、
ランタイムのフック再設定は in-flight のバッチの完了挙動を変えるのではなく、次のバッチに
影響する。

## テレメトリー

正規化された `tool_call` イベントに `call_id` と `execution_status` が追加される。
正規化はすべての sink の前に 1 回行われる:

- 空のツール名は `unknown_tool` に;
- `success` はターミナルの `status` から再計算;
- エラータイプのないターミナルエラーは `unknown` を使用;
- 成功とキャンセルは呼び出しレベルのエラーフィールドを省略;
- 実行ステータスの欠落は `unknown` に。

ターミナルのテレメトリー契約により確立された `qwen-code.tool.call.count` のターミナル
`status` ディメンションは、本設計で不変。新しい `qwen-code.tool.execution.count`
カウンターは `execution_status` と `tool_type` のイベント固有ディメンションのみを使用。
グローバルに設定された共通メトリクス属性（オプトインの `session.id` など）も存在しうる。
実行の失敗率は:

```text
execution_status = error
────────────────────────────────────────
execution_status in {success, error}
```

キャンセル、`not_started`、`unknown` は除外される。エラータイプ、関数名、呼び出し ID、
メッセージ、MCP サーバー名はメトリクスラベルではなくログまたはスパンに残る。
カウンターは意図的に `function_name` を省略するため、実行失敗率からはメトリクス単独で
特定のツールに帰因できない; `call_id` と `function_name` の両方を運ぶ `tool_call` の
ログでドリルダウンする。

実行スパンは、ディスパッチャーが `execute()` を試みた後にのみ存在する。
ツールの identity、凍結された実行ステータス、実行のエラータイプを記録する。親ツールの
スパンは引き続きターミナルの呼び出しステータスを表現し、キャンセルされたスパンは error
ではなく未設定のまま。Core はツールの解決と呼び出し検証の後に親スパンを開く;
それ以前のターミナルパスは正規化イベントと実行カウンターがカバーし、未解決の
リクエスト名からスパンを合成しない。

QwenLogger は正規化されたターミナルのステータス、実行ステータス、呼び出し ID、
ツールタイプを受け取るが、MCP サーバー名や関数の引数は受け取らない。MCP サーバー名は
QwenLogger の外にとどまり、設定されたテレメトリーのログ/スパンエクスポーターが
利用できる。

## 互換性とスコープ

パブリックなレスポンスとイベントのフィールドは任意のまま。組み込みプロデューサーは
内部で必須の形状を使用し、古い JSONL 記録は移行もバックフィルもしない。新しい JSONL
記録は記録されたツール結果に `executionStatus` を含む; このフィールドは加法的なので、
未知フィールドを無視するリプレイリーダーは影響を受けない。Core、ACP、TUI、
非インタラクティブモードの手動記録プロジェクションは、ユーザー向け JSON 出力に
公開せずに新しいスカラーをコピーする。ツールの解決前にキャンセルされた呼び出しは、
パブリックな `CancelledToolCall` バリアントから `tool` と `invocation` を省略しうる
ため、そのバリアントのコンシューマーは使用前にそれらのフィールドをガードしなければ
ならない。
そのような解決前のキャンセルがテレメトリーを通じて発行される場合、ツールの identity が
まだ解決されていないため `tool_type` のデフォルトは `"native"` になる; これは検証前の
キャンセルにおける `tool_type` ディメンションの既知の歪みである。

呼び出しごとの実行エラーは `CoreToolScheduler.schedule()` を拒否しなくなった;
結果は既存の更新・完了コールバックを通じてターミナルの `error` 呼び出しとして配信され、
1 つのツールの失敗がその sibling を中断しない。このメソッドは引き続き `Promise<void>` を
返し、スケジューラーレベルのセットアップやキューの失敗では拒否しうる。
`handleConfirmationResponse()` は確認フローのエラーを再スロー前にターミナル化し、
呼び出しを `awaiting_approval` に残さずに既存の失敗シグナルを保持する。埋め込み側は
コールバックで配信された呼び出しからターミナルの `status` と `executionStatus` を
読むべきで、どちらのパブリックエントリポイントも完了した呼び出しを返すと期待すべき
ではない。

最初のリリースは `CoreToolScheduler` と ACP の `Session.runTool` をカバーする。
speculation、直接の `/fork` 実行、MCP 内部のリトライ、暫定的なサブエージェント結果の
reconciliation、シェルの終了メタデータ、リトライ可能性、所有権、汎用の失敗フェーズは
引き続きスコープ外。

Core と ACP は同時に出荷しなければならない。ダッシュボードはデプロイ時刻または
`service.version` で切り分け、`unknown` は別途監視し、レガシーの `success` メトリクスを
実行失敗の SLI として決して使わないこと。

## 既知のメンテナンス上の危険

実行前キャンセルの不変条件（「実行前パスのすべての `await` の後に abort チェックが
続く」）は、構造的な機構ではなく、`CoreToolScheduler` と `Session.runTool` の各
呼び出し箇所に手作業で配置されたチェックで強制されている。どちらかのパスに後続の
チェックなしで新しい `await` を追加すると、本設計が修正する stale 実行のバグが
サイレントに再導入される。将来のリファクタリングでは await をガード付きヘルパーで
ラップすべき; それまで、これらのパスのレビュアーは不変条件を手動で検証すべきである。
