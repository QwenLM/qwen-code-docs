# ツール呼び出し準備中イベント

## コンテキスト

Qwen Code は現在、プロバイダーが引数のストリーミングを完了した後にのみツール呼び出しを発行します。入力が大きい、または複雑なツールでは、それらの引数の生成にツール自体の実行よりもはるかに時間がかかることがあります。そのため ACP クライアントは、コストの高い段階でアクティビティを一切表示できず、ユーザーはそのターンがストールしたリクエストだと誤解する可能性があります。

プロバイダーのストリームは、引数が完了する前でも安定したツール identity をすでに公開しています:

- Anthropic は `tool_use` ブロックの `content_block_start` で `id` と `name` を送信し、その後、引数の断片を `input_json_delta` として送信します。
- OpenAI 互換プロバイダーは通常、最初の `choice.delta.tool_calls` アイテムで `id` と `function.name` を送信し、その後、引数の断片を追加します。

Qwen Code は意図的に、Gemini 互換の `functionCall` を構築する前に `content_block_stop` または `finish_reason` を待ちます。この実行の安全性の特性は変更せずに維持する必要があります。

## ゴール

モデルがまだツールの引数を準備している間に ACP クライアントがツールカードをレンダリングできるようにし、以下のライフサイクルを持たせます:

```text
preparing -> in_progress -> completed | failed
```

初期のイベントには、安定したツール呼び出し ID とツール名のみが含まれます。部分的な引数は決して含まず、ツールの実行を開始することもありません。

## スコープ

本変更は、統合先のクライアントが使用する 2 つのプロバイダーパスをサポートします:

- Anthropic および Anthropic 互換のストリーミングレスポンス。
- OpenAI および OpenAI 互換のストリーミングレスポンス。

その他のプロバイダーは現在の動作を維持します。準備の metadata はオプションであるため、それらは自然に既存の `in_progress -> completed | failed` ライフサイクルに後退します。

本変更は以下を変更しません:

- ツールのパーミッションチェック;
- フックの順序;
- ツールのスケジューリングまたは実行;
- モデルの会話履歴;
- `functionCall` または `functionResponse` の構築;
- ACP 以外の出力形式。

## 設計

### 1. 内部レスポンス metadata

モジュールローカルな `WeakMap` を介して、一時的なツール準備の metadata を各 `GenerateContentResponse` に関連付けます:

```ts
interface ToolCallPreparation {
  callId: string;
  toolName: string;
}
```

プロバイダーアダプターはこの metadata をトップレベルのレスポンスチャンクに対して保存します。これは列挙可能なレスポンスプロパティでも Gemini の `Part` でもないため、シリアライズされず、Gemini の履歴組み立ては引き続きテキスト、思考、完全な `functionCall` の part のみを参照します。共用ヘルパーが型付きの保存・読み取り操作を提供し、ACP 側でのプロバイダー固有のキャストを回避します。

### 2. Anthropic プロデューサー

`AnthropicContentGenerator.processStream()` で、`content_block_start(tool_use)` が非空の `id` と `name` を含む場合、1 つの準備エントリを持つ、それ以外は空の Gemini レスポンスチャンクを yield します。

`input_json_delta` の蓄積は変更せず継続します。`content_block_stop` で、パースされた引数を持つ既存の完全な `functionCall` を発行します。それ以前の時点で引数データが公開されることはありません。

### 3. OpenAI 互換プロデューサー

`convertOpenAIChunkToGemini()` で、既存のストリームローカルなツール呼び出し parser に渡した後に各 `choice.delta.tool_calls` アイテムを観察します。安定した非空の ID と名前が初めて利用可能になった時点で、現在のレスポンスチャンクに 1 つの準備エントリを付加します。

リクエストコンテキスト内でツール呼び出し ID による重複排除を行います。完全な `functionCall` の発行は引き続き `finish_reason` が存在する場合のみとします。両方の identity フィールドを早期に公開しないプロバイダーは、単に既存の動作を維持します。

### 4. ACP コンシューマーと状態遷移

ACP の `Session` は、完全な `functionCalls` を収集する前に準備の metadata を読み取ります。新しい準備ごとに、標準の ACP `tool_call` フレームを以下で発行します:

```ts
{
  status: 'pending',
  rawInput: {},
  _meta: {
    phase: 'preparing',
    toolName,
    // 既存の出所 metadata は引き続き存在する
  },
}
```

既存の実行パスは、その後同じ `toolCallId` を `status: 'in_progress'` と完全な引数で発行します。既存の結果発行が、カードを `completed` または `failed` として完了させます。

`TodoWrite` は現在のコの特別な処理を維持し、ツールカードを発行しません。準備の発行は同じフィルタリングルールを使用するため、実行パスが意図的に抑制しているカードを作成することはできません。

### 5. リトライ、フォールバック、キャンセル、ストリーム失敗

アクティブな各 ACP モデルストリームは、ストリームが完了してパースされた呼び出しをツール実行に引き渡すまで、準備を追跡します。試行がリトライ、モデルフォールバック、ユーザーのキャンセル、またはストリームエラーによって放棄された場合、ACP は残っている各エントリに対してターミナルの `tool_call_update` を発行します:

```ts
{
  status: 'failed',
  content: [],
  _meta: {
    phase: 'preparing',
    preparationDiscarded: true,
    toolName,
  },
}
```

`preparationDiscarded` は、パースされたツールリクエストが実行に到達する前にモデルの試行が放棄されたことを意味します。ツールの実行失敗ではありません。統合先のクライアントは、この一時的なカードを失敗したツールとしてレンダリングするのではなく削除すべきです。プロトコル上有効なターミナルステータスを使用することで、古いクライアントが無期限に pending のままのカードを保持しないことを保証します。

`RETRY` は、放棄された試行から収集された完全な `functionCalls` をクリアするようになり、4 つのすべての ACP ストリームパスで既存の `MODEL_FALLBACK` の動作と一致します。これにより、失敗した試行でパースされた呼び出しが、代替試行の呼び出しと一緒に実行されることがなくなります。

同じ ID を持つ完全な `functionCall` が到着し、ストリームが正常に終了した場合、ACP は discarded 更新なしで既存の実行パスに引き渡します。呼び出しのパース後、実行前にストリームが失敗した場合、準備は引き続き discarded となります。したがって、通常のツールエラーは既存の結果パスを通じて継続し、discarded としてマークされることはありません。

## 下流への影響

- `GeminiChat` と履歴ビルダーはオプションのトップレベル metadata を無視し、引き続き候補のコンテンツのみを永続化します。
- 準備の metadata のみを含むレスポンスは、ユーザーに見える出力としてカウントされないため、トランスポートのリトライとモデルフォールバックは既存の出力前の動作を維持します。
- 準備の ID は、完全な `functionCall` の ID と同じターン間正規化を使用し、プロバイダーが履歴の ID を再利用する場合でも ACP の更新の対応付けを維持します。
- 新しい Gemini の `Part` やサーバーイベントは導入されないため、core の `Turn`、TUI、非インタラクティブな JSON コンシューマーは現在の動作を維持します。
- ACP は、この metadata をオプトインして初期の UI 状態を発行する唯一のコンシューマーです。
- Anthropic と OpenAI 互換アダプターは同じ metadata 契約を共有するため、ACP にプロバイダー固有の分岐はありません。

## テスト計画

### Core のプロバイダーテスト

- Anthropic: `content_block_start(tool_use)` は、任意の `input_json_delta` より前、かつ最終的な `functionCall` より前に準備の metadata を yield する。
- Anthropic: ID または名前が欠落している場合、準備の metadata は発行しない。
- OpenAI 互換: 安定した ID と名前を持つ最初の delta が 1 つの準備エントリを発行し、後続の引数 delta はそれを重複させない。
- OpenAI 互換: 完全な呼び出しは引き続き `finish_reason` でのみ出現し、パースされた引数は不変である。
- OpenAI 互換: 早期の identity フィールドが欠落している場合、無効な準備イベントなしで現在の動作にフォールバックする。
- GeminiChat: 準備のみのチャンクは、トランスポートのリトライ、プライマリモデルのフォールバック、またはマルチモデルのフォールバックチェーンを通じた継続を抑制しない。
- GeminiChat: ターン間に重複するプロバイダー ID は、準備の metadata と完全な呼び出しで一貫して正規化される。

### ACP テスト

- 準備の metadata は、部分的な入力なしで、`_meta.phase = 'preparing'` を持つ `pending` を発行する。
- 完全な呼び出しは同じ ID を再利用し、完全な引数とともに `in_progress` に遷移する。
- リトライ、フォールバック、キャンセル、ストリームエラーは、ツール実行に到達していない準備を `_meta.preparationDiscarded = true` で破棄する。
- リトライとモデルフォールバックは、代替チャンクを受け入れる前に、放棄された試行から収集された完全な呼び出しをクリアする。
- 完全な呼び出しになった準備は、正常に完了したストリームの後では破棄されないが、そのストリームが実行前に失敗した場合は破棄される。
- `TodoWrite` は引き続き抑制される。

## 受け入れ基準

1. Anthropic と OpenAI 互換の ACP ターンは、安定したツール identity が利用可能になり次第、pending のツールカードを発行する。
2. 完全な引数と既存のパーミッションおよび実行パスの前にツールが開始されることはない。
3. 完全な呼び出しと結果は、現在の ID、引数、順序、履歴表現を維持する。
4. 放棄された試行は、無期限に pending の準備カードを残さない。
5. 準備の metadata を持たないプロバイダーは、従来とまったく同じ動作をする。
