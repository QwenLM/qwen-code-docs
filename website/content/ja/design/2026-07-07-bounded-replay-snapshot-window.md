# Bounded Replay Snapshot Window

## 問題

現在のライブデーモンセッションは、リプレイ履歴をメモリに保持しています。これは、セッションがすでに存在する状態でアタッチしてきたクライアントに対して、`POST /session/:id/load` がリプレイを注入できるようにするためです。このリプレイ保持は、SSE リングとは独立に上限を設ける必要があります。レスポンスモードのリストアでは大量の履歴更新を一括でシードすることがあり、完了したライブターンは長時間稼働するセッション内で無制限に蓄積し得るためです。

ディスク上のセッション履歴が、完全なトランスクリプトの権威あるソースのままです。PR-1 ではデーモンのライブなインメモリリプレイウィンドウに上限を設けるのみで、完全なトランスクリプトのエンドポイントは追加しません。

## ゴール

- ライブセッションごとに、シリアライズ後のバイト数で保持するリプレイイベントに上限を設ける。デフォルトは 4 MiB で、無効な設定は起動時に拒否する。
- 上限は、完了したライブターンのリプレイセグメントと、レスポンスモードまたはストリームモードでリストアされた履歴リプレイの両方に適用する。
- 既存のスナップショットのワイヤ形式（`compactedReplay`、`liveJournal`、`lastEventId`）を維持する。
- 単一のユニットが上限を超えた場合でも、少なくとも 1 つの実リプレイイベント、または 1 つの完了したライブターンセグメントを保持する。
- 切り詰めは、`compactedReplay` の先頭に ID なしの `history_truncated` マーカーを配置して通知する。
- `history_truncated` はステータスとしてのみ扱う。これが `state_resync_required`、リロードループ、またはリプレイウィンドウへの永続化の再書き込みを引き起こしてはならない。

## ノンゴール

- ~~PR-1 では進行中の単一ライブターンへの上限は設けない。`liveJournal` は境界までアクティブなターンを保持し続ける。~~ DAEMON-009（PR #7622）により追加済み: `liveJournal` は `maxJournalEvents`（デフォルト 10 000）と `maxJournalBytes`（デフォルト 8 MiB）で上限が設けられるようになり、`--max-journal-events` / `--max-journal-bytes` で設定可能。
- ターン数の上限は設けない。ターン数は、エンジンがドロップされた完了ターンセグメントを正確にカウントできる場合の診断情報としてのみ使用する。
- この追加イベント用の `/capabilities` フィーチャータグは設けない。解決された上限値はデーモンのステータスで公開する。
- 完全なトランスクリプトのエンドポイントは設けない。PR-2 ではページングまたはストリーミングによるトランスクリプト読み取りを設計する必要があり、配列全体を一度に返すレスポンスを公開してはならない。

## 設計

`TurnBoundaryCompactionEngine` は、保持するリプレイを無制限のフラット配列ではなく、順序付きセグメントとして保存します。完了したライブターン 1 つが 1 セグメントです。リストア／一括シードのリプレイはイベントレベルのセグメントとして保存されるため、バイト上限を超えた際に最も古いリストアイベントを独立して破棄できます。

サイジングは EventBus の安全な JSON サイジングのセマンティクスを再利用します。サイジングの失敗は診断ログを記録し、そのイベントを 0 バイトとしてカウントすることで、publish および seed パスの never-throws 契約を維持します。

`replayBytes > maxReplayBytes` の場合、エンジンはセグメントが 2 以上残っている間、最も古いセグメントから破棄します。`truncatedEvents` をインクリメントし、破棄されたのがライブターンセグメントの場合のみ `truncatedTurns` をインクリメントします。`snapshot()` は保持されているセグメントをフラット化し、先頭に以下を付加します:

```json
{
  "type": "history_truncated",
  "data": {
    "reason": "replay_window_exceeded",
    "truncatedEvents": 12,
    "retainedEvents": 8,
    "maxBytes": 4194304,
    "truncatedTurns": 3,
    "fullTranscriptAvailable": true
  }
}
```

このマーカーは合成的で ID を持ちません。バイト計算と一時的なリプレイ保持の対象から除外されます。`ingest()`、`seed(snapshot)`、`seedReplayEvents()` はいずれもこれをフィルタリングするため、bounded スナップショットの読み込みによってマーカーが累積することはありません。

`EventBus.seedReplayEvents()` は、リストアされたリプレイイベントに ID とタイムスタンプを割り当て、コンパクションエンジン専用の seed メソッドを呼び出し、従来どおり SSE リングをクリアします。これにより、一括リストアのリプレイが `liveJournal` に追記されることを防ぎます。

CLI の配線は、yargs、fast-path パーサー、`ServeOptions`、サーバー配線、`BridgeOptions`、ブリッジステータス、デーモンのステータス表示を通じて、1 つの解決済み上限値を渡します。無効な値（`0`、負数、非整数、`NaN`、`Infinity`、または 256 MiB を超える値）は fail closed（失敗時は拒否）となります。

SDK と WebUI は `history_truncated` を認識してそのペイロードを検証し、view-state のカウンターとトランスクリプトのステータスに投影して、ターミナルのステータス行としてレンダリングします。このイベントは unknown/debug イベントではなく、resync ゲーティングの一部でもありません。

## 監査メモ

ラウンド 1: 完了したライブターンのみに上限を設けるだけでは不十分です。レスポンスモードのリストアは、ライブの境界なしに大量の履歴リプレイをシードできるためです。そこで本設計では `seedReplayEvents()` とイベントレベルの履歴セグメントを追加します。

ラウンド 2: 切り詰めに `state_resync_required` を再利用すると、`/load` が同じ bounded ウィンドウを返し続けるため、リロードループが発生します。本設計では、`awaitingResync` を一切セットしない独立したステータスマーカーを使用します。

ラウンド 3: 1 つのターンに大きなツール出力が含まれる場合、ターン数の上限ではメモリを制限できません。PR-1 ではバイトのみによる強制を採用し、アクティブなターンの上限設定は対象外とします。

ラウンド 4: 完全なトランスクリプトを配列として返すと、リクエスト時に同じピークメモリ問題が再現してしまいます。PR-2 は明示的にページングまたはストリーミングに制約されます。

ラウンド 5: 切り詰め後にリプレイが空になると、クライアントは目に見えるステータスをすべて失います。エンジンは、サイズ超過した場合でも最新のセグメントを保持します。

## 検証計画

- ライブターンのトリミング、リストアシードのトリミング、マーカーの配置、一時的なマーカーのフィルタリング、サイズ超過時の最新セグメント保持、安全なサイジングの失敗、EventBus の never-throws 動作をユニットテストする。
- bounded ウィンドウを用いたブリッジのレスポンスモードリストアとライブセッションの load 動作をユニットテストする。
- CLI パース、fast-path パース、runQwenServe のバリデーション、サーバーブリッジの配線、デーモンのステータス上限をユニットテストする。
- SDK の既知イベント検証、reducer の状態、UI ノーマライザー、トランスクリプトのステータス、ターミナルレンダリング、WebUI のリプレイ注入をユニットテストする。
- 最終検証は `npm run build`、`npm run typecheck`、`npm run lint` で行う。
