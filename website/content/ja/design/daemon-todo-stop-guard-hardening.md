# Daemon Todo Stop Guard の強化

## Context

デーモンの Todo Stop Guard は、モデルターンが信頼された Todo 項目を未完了のまま
残した場合に、上限付きの自動コンティニュエーションを追加できる。現在のターンが
drain されている間に、ブリッジが別のユーザープロンプトを受け入れる可能性があり、
バックグラウンドエージェント、モニター、通知、cron ジョブが同時に完了する可能性
もある。Guard は、受け入れられたユーザー作業を追い越したり、別のワークスペースや
プロンプトの作業を復活させたり、自動送信の失敗時にユーザーおよびツールのコン
テンツを失ったりしてはならない。

## Continuation ownership

`craft/claimTodoStopGuardContinuation` は、ブリッジのプロンプトキューと Guard の
コンティニュエーションの間の順序付け境界である。リクエストにはセッション ID と、
ブリッジ所有のプロンプトの場合はブリッジによって注入された信頼された
`InvocationContextV1.promptId` が含まれる。セッションローカルのプロバイダー
プロンプト ID はオーナーではない。

ブリッジ所有のプロンプトについて、デーモンはそのプロンプトが引き続きアクティブ
で中断されていない実行中エントリである間のみクレームする。キューにあるライブの
プロンプトは `{ claimed: false, hasQueuedPrompt: true }` を生成し、待機を現在の
オーナープロンプト ID にバインドする。欠落、置換、または競合するオーナーは、
別のオーナーの状態を変更することなく fail closed（失敗時は拒否）となる。オーナー
のない自動ターンは、ライブのブリッジプロンプトが存在しない場合のみクレーム
できる。

チャネルとデスクトップ共有エージェントにはデーモンの FIFO がない。これらは現在
のセッションを検証し、それに対する成功のクレームを返す。不明なセッションと
オーナーのないフォールバックハンドラーは fail closed（失敗時は拒否）となる。
このメソッドを実装していないクライアント、不正なレスポンス、および 2 秒の
クレーム期限は、いずれもコンティニュエーションの Guard 部分のみを無効化する。
独立してブロックしている外部の Stop フックは引き続き継続する場合がある。確定
したライブ FIFO プロンプトは、代わりに古いターンを即座に終了させ、古くなった
フックレスポンスを表示もカウントもしない。

`craft/todoStopGuardQueueReleased` は Guard のオーナープロンプト ID を運ぶ。
遅延した解放は、一致する待機のみをクリアできる。FIFO の昇格も、キューに入れ
られたユーザープロンプトが所有権を引き継ぐため、オーナースコープの待機をクリア
する。Session は進行中のクレームも追跡する。一致する解放がクレームレスポンスの
コンティニュエーションより前に処理された場合、短命なトゥームストーンを記録し、
ターミナルの解放状態を適用し、古いレスポンスからの待機のインストールを拒否
する。トゥームストーンは、そのオーナーに対する最後の進行中クレームが確定した
ときに削除される。

## Send ordering and preservation

drain 結果の `hasQueuedPrompt` フィールドはヒントである。肯定のヒントはクレーム
によって確定される。まだライブのキューはターンを譲渡し、消えたキューは Stop
処理の継続を許可する。同じ drain がターン中のユーザーコンテンツも削除していた
場合、譲渡しはそのコンテンツをキューのプロンプトが実行される前にチャット履歴に
保存するため、順序付け境界がデータ損失の境界になることはない。失敗または不正な
drain は、そのようなコンテンツが存在する場合は回復されたユーザーコンテンツを
優先し、存在しない場合は独立した外部の Stop フックを抑制することなく Guard を
ハードサスペンドする。

Guard によるモデルストリームの前に、Session は入力を drain し、画像パーツを
構築し、フルターンのビジョンモデルを選択し、プランモードとバックグラウンドの
状態をリフレッシュし、Guard の決定をリフレッシュし、コンティニュエーションを
クレームする。コンパクション、トークン制限のチェック、プロバイダーへの送信は、
そのクレームの後にのみ行われる。追加の各 Guard ストリームは個別にクレームする。
クレームの前に受け入れられたプロンプトが優先し、クレームの後に受け入れられた
プロンプトは、すでにコミットされたコンティニュエーションの後に順序付けされる。

準備、コンパクション、クレーム、トークン制限の検証、ストリームの作成、または
プロバイダー送信が失敗した場合、未送信の Guard 指示は履歴の保存前に削除される。
drain されたユーザーパーツ、成功した関数レスポンス、およびその他の独立した
Stop コンテンツは残る。Session は履歴を追加する前にユーザーコンテンツのプッシュ
カウンターを比較するため、すでにコンテンツを永続化している下位レイヤーが重複を
引き起こすことはない。

## Hard suspension

ハードサスペンションは、Guard の使い切り、明示的なセッションの破棄、作業
ディレクトリの移動の開始、ターミナルなキュープロンプトの解放、回復された
ユーザー入力がない信頼できない drain、およびチェーンを安全に継続できない制御
されたキャンセルまたは失敗パスの後に入る。これは既存のキューの所有権をクリア
し、遅延した Todo の書き込みが古いチェーンを再アームすることをブロックする。
サスペンションと競合する完全な FIFO の観測は、そのオーナーにプロンプト順序の
優先権を確立する場合があるが、その優先権は Guard の信頼を回復せず、Guard の
送信も許可しない。

新しい通常のプロンプトのみが新しいチェーンを開始する。信頼されたリトライは
リトライで一時停止されたチェーンを再開する場合があるが、バックグラウンドの結果、
cron ターン、通知ターン、設定のリフレッシュ、遅延したツールの完了はハード
サスペンションをクリアできない。プランモードに入ると Guard の信頼がクリア
され、自動コンティニュエーションが防止される。

## Background lineage

Session は各作業チェーンの開始時にバックグラウンドのベースラインをキャプチャ
し、ベースラインと明示的な関連エージェントの集合を一緒にリセットする。

- 新しく作成されたトップレベルエージェントは関連がある。
- 新しい子は親から再帰的に継承する。欠落した親とサイクルは fail closed（失敗時
  は拒否）となる。
- ベースラインのエージェントは、チェーンが `send_message(task_id)` でそれを正常
  に継続しない限り関連がない。
- `send_message(task_id)` は、権限と `PreToolUse` チェックの後、実行の前に
  ターゲットを一時的にマークするため、高速な完了通知が正しく分類される。成功は
  `PostToolUse` の前にコミットし、エラー、キャンセル、またはスローはその呼び
  出しによって導入されたマークのみをロールバックする。
- チーム宛ての `send_message(to)` はタスクの系譜を変更しない。
- オーナーを持つモニターは、モニター自身のベースラインの所属に関係なく、
  オーナーの関係性を継承する。オーナーのないモニターは自身のモニター ID を
  使用する。

通知の関係性はエンキュー時に保存されるため、後からのレジストリ削除やステータス
変更が、すでに配信された結果を再分類することはない。ライブスキャン、優先度選択、
オーバーフロー保護は同じ系譜ルールを使用する。新しい通常のプロンプトの開始時に、
キュー内のすべての通知を意図的に無関連へリセットする。それらの結果は新しい作業
チェーンの境界より前にエンキューされており、以前のチェーンの分類を継承できない
ためである。

## Session lifecycle and bounded queues

`/cd` は、既存のセッションクローズゲートを獲得する前に、ターゲットを検証して
正規化する。見かけ上の no-op もゲートを獲得して現在のディレクトリを再チェック
するため、並行する移動と競合することはない。実際に移動が発生しない限り、Guard
をハードサスペンドしない。移動がゲートされると、Guard をハードサスペンドし、
フォアグラウンド、cron、通知のターンが確定するのを待ち、移動し、モデルコン
テキストをリフレッシュし、`finally` でゲートを解放する。プロンプトの受け入れは、
ライターの受け入れの前と後の両方でゲートをチェックする。確定ループは完了ごとに
所有権を再チェックするため、先行を待っている間にゲートの前に受け入れられた
プロンプトも含まれる。移動の失敗は古い Guard をサスペンドされたままにする。

`dispose()` は同期的なままだが、フォアグラウンドのコントローラーを専用の制御
されたキャンセル理由で中断し、Guard をハードサスペンドし、遅延したツール結果
による復活を防ぐ。本番のクローズパスは、ターンが確定するまで待機する責任を
引き続き負う。

永続化セッションのロードまたは再開時に、履歴のリプレイ、ワークツリーの復元、
一時停止エージェントの復元、goal の復元は、すべてリライターと永続 cron
スケジューラーの開始前に完了する。これにより、期限がすぐに来る cron の発火が
復元と競合し、以前から存在する一時停止エージェントを再開されたチェーンの新しい
作業として分類することが防止される。

遅延 cron のオーバーフローは重複排除の後に計算される。関連のある受信項目は、
20 個の無関連項目を保持する場合がある。無関連の受信項目は、まず 19 個に削減
されてから 20 個目になる。関連エントリは決して追い出されず、複数エントリの
削減は 1 つの診断を出力する。

上限付きエントリがすべて関連している通知キューのケースは、引き続き先送り
される。ある一意な関連結果を別のものと置き換えることは、依然としてサイレントな
データ損失となる。フォローアップの設計では、省略されたすべての関連結果に対し、
回復可能な結果、または永続的でモデルとユーザーの両方から見えるギャップ通知を
提供しなければならない。その作業は
[#7805](https://github.com/QwenLM/qwen-code/issues/7805) で追跡する。
