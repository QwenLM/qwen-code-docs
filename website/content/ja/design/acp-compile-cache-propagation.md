# ACP コンパイルキャッシュの伝播

## 背景

本番環境の `cli-entry.js` ラッパーは、すでにインプロセスの `serve` ファストパス用に Node のモジュールコンパイルキャッシュを有効にしている。デーモンはその後 `createSpawnChannelFactory()` を通じて ACP 子プロセスを spawn するが、`module.enableCompileCache()` は現在のプロセスにのみ影響し、`NODE_COMPILE_CACHE` を設定しない。そのため、オペレーターが Qwen Code の起動前にその環境変数を設定していない限り、ACP 子プロセスはキャッシュなしで起動する。

これは #7264 に記録された直交的なコンパイルキャッシュの候補である。eager モジュールグラフを縮小するものではなく、遅延読み込みの作業後に残るグラフに対して V8 コードキャッシュを再利用する。

## ゴール

- 本番環境の ACP 子孫プロセスが、デーモンのエントリラッパーによってすでに有効化されたコンパイルキャッシュディレクトリを再利用できるようにする。
- オペレーターが指定した `NODE_COMPILE_CACHE` を保持する。
- `NODE_DISABLE_COMPILE_CACHE=1` を保持する。
- キャッシュの失敗は、アプリケーションの失敗ではなく静かな最適化の失敗にとどめる。
- ACP ブリッジ、設定、セッションライフサイクルの変更を避ける。

## 非ゴール

- Qwen 固有のキャッシュ場所、エビクションポリシー、クリーンアップコマンドを導入しない。
- JavaScript API が利用できない Node バージョンにコンパイルキャッシュのサポートを強制しない。
- デーモンや ACP のライフサイクルからキャッシュをフラッシュしない。
- テスト環境やカバレッジ環境をグローバルに変更しない。

## 起動トポロジー

本番環境のデーモンパスは次のとおり:

1. `cli-entry.js serve`
2. デーモンプロセスでの `module.enableCompileCache()`
3. バンドルされた CLI のインプロセスインポート
4. `createSpawnChannelFactory()` が `process.env` をコピー
5. 新しい Node プロセスが起動時に `NODE_COMPILE_CACHE` を読み取る
6. 子プロセスが選択された CLI エントリを `--acp` 付きで実行（デフォルトは `cli.js`、明示的に設定されている場合は `QWEN_CLI_ENTRY`）

現在、ステップ 2 の恩恵を受けるのはデーモンだけである。ステップ 4 でコピーされる環境にはコンパイルキャッシュディレクトリがないため、ステップ 5 と 6 の子プロセスはオプトインしない。

## 提案する変更

既存の `module.enableCompileCache()` 呼び出しの結果をキャプチャする。キャッシュが新しく有効化されたことが報告され、ディレクトリが公開され、オペレーターが `NODE_COMPILE_CACHE` を指定していない場合、そのディレクトリを `process.env` に公開する。既存の子プロセス構築がすでに環境をコピーしているため、ACP レイヤーの変更は不要である。

既存の環境変数の値を上書きしない。Node が既存の環境変数からキャッシュを有効化した場合、すでに有効化された状態を報告し、元のベースディレクトリはそのまま保持されなければならない。これを `getCompileCacheDir()` や already-enabled の結果で置き換えると、子孫プロセスにネストされたバージョンディレクトリが作成される可能性がある。

有効化が失敗した場合、無効化されている場合、API が利用できない場合は、ディレクトリを合成しない。これらのケースは現在の挙動を維持する。

## 検討した代替案

### `spawnChannel` で環境変数を設定する

却下。コンパイルキャッシュの所有はプロセスグローバルなエントリの挙動であり、`spawnChannel` は組み込みホストが使用する共有の ACP インフラストラクチャである。そこにポリシーを移すとアーキテクチャの表面が広がり、Node のブートストラップ挙動が重複する。

### `QWEN_HOME` 配下に Qwen バージョン付きのキャッシュを設定する

却下。Node はすでに互換性のない Node バージョンを分離し、モジュールの内容をキーにしてエントリを管理している。Node は、古いキャッシュの蓄積を避けるため、一時ディレクトリをデフォルトにすることを推奨している。永続的な Qwen 固有のキャッシュには、測定されたパスの改善を示す証拠がないにもかかわらず、新しいクリーンアップ、権限、ライフサイクルのポリシーが必要になる。

### `getCompileCacheDir()` を無条件にエクスポートする

却下。キャッシュが既存の環境変数から有効化された場合、報告されるディレクトリはすでに Node バージョン固有である。それを次のプロセスのベースとして再利用すると、別のネストされたバージョンディレクトリが作成され、意図した共有が妨げられる。

## 失敗と互換性の挙動

- `enableCompileCache()` がない Node: 環境の変更なし、挙動の変更なし。
- `NODE_DISABLE_COMPILE_CACHE=1`: Node は無効化を報告し、ディレクトリは伝播されない。
- オペレーターが指定した `NODE_COMPILE_CACHE`: そのまま保持され、通常どおり継承される。
- 書き込み不可または無効なキャッシュディレクトリ: Node は例外を投げずに失敗を報告し、Qwen Code はキャッシュなしで続行する。
- Node または Qwen のアップグレード: Node は互換性のないランタイムバージョンを分離し、ソース内容の変更は異なるキャッシュエントリを生成する。
- カバレッジ: 唯一の変更点は本番環境のファストパスである。ユニットテストランナーはコンパイルキャッシュにグローバルにオプトインされない。
- シャットダウン: Node は通常のプロセス終了時に蓄積されたコードキャッシュを書き出す。強制終了で新しく生成されたエントリが失われる可能性はあるが、正確性に影響することはない。

## 検証

実現可能性は、両方のバリアントに同一のリリースバンドルを 1 つ使用して、実装前にゲートされる。両方のデーモンバリアントは同じウォームな親プロセスキャッシュを受け取る。コントロールはバンドルのインポート前にキャッシュ環境を削除するため、ACP の子孫はキャッシュなしのままとなる。候補はインポート前に同じベースディレクトリを公開するため、ACP の子孫はそれを継承する。

2 vCPU リファレンスホストのゲートは以下をカバーする:

- 交互に実行する 30 ペアのコールドデーモン起動
- 交互に実行する 30 ペアのプリヒート済み起動
- `channel.initialize`、プロセスから最初のセッションまでの時間、リスナーの準備完了、ピーク RSS
- ウォームな 2 回目のセッション
- 並行する最初のセッション
- テレメトリー有効時と無効時
- レガシーなシングルセッションの挙動
- 空キャッシュでの初回使用、ウォームキャッシュの再利用、キャッシュのフットプリント、残留プロセス

実装は、子プロセス固有のウォームキャッシュ比較で、機能リグレッションなく、初期化またはプロセスからセッションまでの時間に再現可能な改善が示された場合のみ続行する。

## 検証結果

ゲートは、Node.js 22.23.1 を搭載した 2 vCPU、4 GB の Linux x64 ホストで実行された。コントロールと候補は `77af061e` の同じバンドルを使用し、ACP 子プロセスが親のコンパイルキャッシュディレクトリを継承するか否かのみが異なっていた。

30 回のウォームキャッシュペア実行全体で、候補はすべての `channel.initialize` 比較で勝った。ペア中央値の改善は 176.6 ms で、ブートストラップによる 95% 信頼区間は 167.7〜186.2 ms だった。プロセスから最初のセッションまでのペア中央値の改善は 199.0 ms で、95% 信頼区間は 177.6〜226.5 ms だった。候補のプロセスツリーのピーク RSS の中央値は 8.6 MB 高かった。

追加の 10 ペアによる確認では、`origin/main` の未変更の本番エントリをコントロールとして、パッチを適用した本番エントリを候補として使用した。`channel.initialize` の中央値で 181.6 ms、プロセスから最初のセッションまでの中央値で 189.4 ms の改善が再現された。

20 の独立した空キャッシュペア全体で、最初のプロセスからセッションまでの実行は中央値で 117.2 ms 遅く、95% 信頼区間は 69.3〜130.9 ms だった。したがって、測定されたワークロードでは、2 回目の ACP 起動が一度きりの生成コストを回収する。安定したキャッシュには 362 個のファイルが含まれ、9.4 MB を使用した。

すべての測定実行は残留プロセスなしで正常に完了した。候補は、並行する最初のセッションの作成、テレメトリー無効での起動、レガシーなシングルセッションの挙動にも合格した。
