# プランモードのシェルルーティングと厳密なワンタイム承認

## 問題

プランモードは歴史的に、確認の形式をツールが読み取り専用かどうかの代理指標として扱ってきました。これは `run_shell_command` と `monitor` には不十分です: どちらのツールも、読み取り専用、状態変更、またはパーサーが未知のシェルプログラムを表現でき、さらにパーミッションルール、フック、ACP ホスト、stream-json、TUI、teammate、バックグラウンドブリッジのすべてが、異なるパスを通じて同じ承認を解決できるためです。

セキュリティ境界は、`unknown` をプランモード回避の手段に変えることなく、既知の書き込みと未知のコマンドを区別しなければなりません。また、承認は、プロンプトを生成した正確なモデルリクエストに結びついたままでなければなりません。後続のモード変更、パーミッションポリシー変更、ホストによる書き換え、エディターでの変更、競合するレスポンスは、それを再利用できてはなりません。

この設計は、#7053 でマージされた三状態シェルクラシファイアに依存します。

## ゴール

- Core と ACP の両方で、モデル起点の Shell と Monitor の呼び出しに 1 つのルーティングポリシーを適用する。
- `read-only` に分類されたコマンドのみを、新しいプラン固有のプロンプトなしで実行する。
- `write` に分類されたコマンドを、確認フックやホストが承認する前にブロックする。
- `unknown` は、プランモードをアクティブに保ちながら、厳密なワンタイム確認を通じてのみ許可する。
- すべてのプラン固有部分に対して、明示的な PermissionManager の拒否を優先する。
- TUI、ACP、stream-json、デュアル出力、teammate、サブエージェント、バックグラウンドブリッジ全体で、警告と実際に許可された選択肢を伝達する。
- シェル以外のプラン動作と明示的なプラン終了のセマンティクスを変更しない。

## ノンゴール

- プランゲートのライフサイクルの変更や、すでに実行中の ACP ターンへの新しいリマインダーの注入。
- ユーザー入力の `!command` シェル入力への適用。
- 確認タイプ、設定、キャッシュ、フィーチャーフラグ、永続的なワンタイムケーパビリティの追加。
- DataWorks 固有のクエリツールの変更。
- speculation にインタラクティブな承認サーフェスを提供すること。

## 脅威モデル

保護対象は、プランモードがアクティブな間の、ユーザーのファイルシステム、プロセス、ネットワークから見える状態、リポジトリ状態、承認モード境界です。信頼できない入力には、モデルのツール引数、パーサーが安全と証明できないシェル構文、フックが返す `updatedInput`、ACP の選択肢 ID、stream-json ホストによる書き換え、IDE の編集コールバック、teammate/バックグラウンドのレスポンス、並行してアタッチされたホストからの重複レスポンスが含まれます。

関連する攻撃は以下のとおりです:

- 許可ルールや YOLO 系のブリッジを使ってプランモードを回避する;
- 既知の書き込みをラッパーで偽装し、より弱いパスに到達させる;
- あるコマンドを承認しながら、変更されたリクエストや検証済みの呼び出しを実行する;
- 古いプロンプトが表示されたまま、プランモードを終了して再突入する;
- プロンプト表示後、承認消費前に拒否ルールを追加する;
- 提示されていない永続オプションや変更オプションを偽造する;
- TUI、リモート入力、IDE、バックグラウンドブリッジを通じて 2 回承認する;
- 兄弟呼び出しの永続承認を使って、プランのシェル呼び出しを自動承認する。

## ルーティングポリシー

PermissionManager の L3/L4 評価は、ハードな拒否に対して権威を持ち続けます。その決定と、プランが必要な teammate ゲートの後、プランのシェルルーティングは検証されたコマンドを分類します。

| 分類          | PM 拒否 | PM 許可              | PM 確認/デフォルト       | 承認ホストなし                                 |
| -------------- | ------- | -------------------- | -------------------- | ------------------------------------------------ |
| `read-only`    | 拒否    | 実行                 | 厳密なワンタイムプロンプト | 通常の PM プロンプトを表示できない場合は拒否 |
| `write`        | 拒否    | プランブロック           | プランブロック           | プランブロック                                       |
| `unknown`      | 拒否    | 厳密なワンタイムプロンプト | 厳密なワンタイムプロンプト | プランセーフな拒否                                |

Monitor の分類は `normalizeMonitorCommand(command).safetyCommand` を使用し、Shell の分類は検証された呼び出しの元のコマンド文字列を使用します。speculation は、三状態の結果が正確に `read-only` の場合のみ実行されます。`write`、`unknown`、パーサーの失敗、空の入力は speculation 境界で停止します。

## 厳密な呼び出しケーパビリティ

分類は、以下を含む不変のスナップショットを作成します:

- 元のツールリクエスト引数;
- 検証された呼び出しパラメータ;
- 現在の承認モードのリビジョン;
- 実効の Shell/Monitor 作業ディレクトリを含む PermissionManager のチェックコンテキスト;
- 表示に使用される生の Shell または Monitor コマンド。

Core と ACP は、分類の前にプランの Shell/Monitor 呼び出しをクローンするため、ホストから見える生の入力は、実行可能なパラメータへのエイリアスを保持できません。モデルが `directory` を省略した場合、そのクローンは現在のセッションの作業ディレクトリにもバインドされます。元のリクエストは変更されないまま、承認が消費された後の実行は、以降のデーモン/ACP のディレクトリ再配置やリクエストオブジェクトの変更に従わなくなります。

スケジューラーは、分類の後、確認の表示の前、そして確認の消費の前に、このスナップショットを検証します。検証の要件:

- ライブで、中止されていないリクエスト;
- 同じリビジョンのプランモード。これにより、プラン → 他のモード → プラン の遷移がプロンプトを無効化する;
- リクエスト引数と検証された呼び出しパラメータのディープな等価性;
- 呼び出しがセッションのアンビエントディレクトリに依存する場合の、同じ実効作業ディレクトリ;
- `deny` を返さない、現在の PermissionManager 評価の成功。

後続の `allow`、`ask`、`default` の変更は、すでに選択されたプロンプトを再ルーティングしません。PermissionManager の例外は fail closed（失敗時は拒否）となります。最終検証が成功すると、ケーパビリティは消費されます。以降のモードやルールの変更は、すでに消費された呼び出しを取り消しません。

`ProceedOnce` と `Cancel` のみが受け入れられます。`updatedInput` は、スナップショットされたリクエストとディープに等しい場合のみ受け入れられます。`newContent` は決して受け入れられません。承認の成功はツールに空のペイロードを渡すため、応答、パーミッションルール、ホスト専用のメタデータが永続的な許可になることはありません。無効な結果は、stale な承認のメッセージ付きで `Cancel` になります。

Core の確認クロージャは、最初の `await` の前に同期的にレスポンスを確保します。したがって、競合する TUI、リモート入力、teammate、IDE、バックグラウンドのレスポンスは、ケーパビリティを 2 回消費できません。プランのシェル編集確認は IDE の自動 diff パスに入ることがなく、兄弟の永続承認は `hideAlwaysAllow` がマークされた確認をスキップします。

## 確認の提示

すべてのプランシェルプロンプトは、永続的な承認を非表示にします。unknown の確認には以下が追加されます:

> プランモードは、このシェルコマンドが読み取り専用かどうかを判定できませんでした。承認は、この厳密な呼び出しに対して一度だけ適用されます。システム状態を変更する可能性があり、プランモードはアクティブなままです。

unknown の編集確認は、変更アクションも非表示にし、diff を保持したまま、生のコマンドを 2 番目の警告として追加します。TUI は diff の上に編集警告を描画し、その折り返された高さを確保することで、小さなターミナルでも選択肢が見えるままになります。ACP は diff やプランコンテンツの前に警告を送信します。Stream-json とデュアル出力は、既存の `permission_suggestions` フィールドに警告を含めます。

ACP とネストされたサブエージェントのブリッジは、返された選択肢 ID をホストに送信した正確な選択肢と照合して検証します。プラン終了は、それらの選択肢が実際に送信されたものであるため、既存の 4 つの特別な選択肢を保持します。欠落、偽造、非表示、または不正な形式の選択肢は fail closed となります。

Teammate イベントは、オプションのコールバックなし確認詳細を運びます。Stream-json は警告にそれらを使用しますが、teammate の Core スケジューラーが最終的な厳密呼び出しのバリデーターであり続けます。ヘッドレス YOLO は、インタラクティブな警告サーフェスが存在しないため、`hideAlwaysAllow` がマークされたプラン以外の確認をキャンセルします。バックグラウンド承認は、提示されていない永続結果を `ProceedOnce` に変換しません。プラン以外の永続結果はキャンセルされ、プランの確認は実際に存在する `ProceedAlways` の選択肢のみを保持します。

## 失敗メッセージ

既知の書き込み、利用できない unknown の承認サーフェス、stale な承認は、実装計画の固定メッセージを使用します。これらのメッセージは、プランモードがアクティブなままであることを意図的に明示し、ラッパーや難読化を通じた既知の書き込みのリトライを禁止します。

## 却下された代替案

- **unknown を write として扱う。** よりシンプルだが、パーサーがそれ以外は正当なコマンドをモデル化できない場合に、必要な調査をブロックしてしまう。
- **PM 許可の後に unknown を read-only として扱う。** 許可ルールは読み取り専用動作の証明ではなく、プラン境界を消してしまう。
- **unknown の承認後に許可ルールを永続化する。** クラシファイアの結果と厳密なリクエストは一時的であり、永続化は将来のより広いコマンドを認可してしまう。
- **IDE の diff 承認を再利用する。** IDE コールバックはコンテンツを変更し、警告サーフェスと競合する可能性があるため、厳密なシェルケーパビリティを安全に消費できない。
- **生リクエスト引数のみを検証する。** ツールビルダーは入力を正規化・検証する。生と実行可能の両方の形式がバインドされたままでなければならない。
- **プロンプト作成時のみ検証する。** プロンプトが表示されている間に、モードとパーミッション状態は変化しうる。
- **専用の確認タイプやフィーチャーフラグを追加する。** 既存の確認形式と警告フィールドで十分であり、変更を小さく保てる。

## 検証

ユニットカバレッジは、ポリシー分類、スナップショット、中止、リビジョンと引数の変更、PermissionManager の拒否/エラー、警告の装飾、ペイロードのサニタイズ、Core ルーティング、重複レスポンスの所有、兄弟の自動承認、折り返された sed 編集の動作、Monitor の等価性、speculation、ACP の選択肢と警告、SubagentTracker、teammate の stream-json、バックグラウンドの正規化、デュアル出力、TUI レイアウト、プロンプトの文言を検証します。

手動検証は、サンプルファイルを含む使い捨ての Git ワークスペースを使用し、以下のケースをカバーします:

1. プランモードで、`git status` が実行されること、`touch changed.txt` がブロックされること、`python -c 'print(1)'` のような unknown コマンドがワンタイム承認とキャンセルのみを提示し、次の呼び出しで再度プロンプトを表示することを確認する。
2. 狭いコンパクト確認でラップされた編集を実行し、生のコマンド、警告、diff コンテキスト、質問、利用可能な選択肢が見えるままで、変更と永続承認が利用不能であることを確認する。
3. 承認が保留中にプランモードのリビジョンまたは作業ディレクトリを変更し、変更されたまたは提示されていない承認ペイロードを返し、重複または遅延したレスポンスを送信する。各パスが実行なしにキャンセルされることを確認する。
4. 読み取り専用、書き込み、unknown のケースを Monitor、ACP、stream-json、ネストされた teammate、バックグラウンド実行で繰り返す。すべてのサーフェスが同じ分類と fail-closed 動作を使用することを確認する。
