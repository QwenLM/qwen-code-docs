# MCP 接続喪失後の安全なリプレイ

## Problem

MCP ツールは、レスポンス接続が失敗する前に副作用を完了し得る。そのため、再接続して同じ `tools/call` を再度送信すると、ユーザーには 2 回目の結果しか見えないまま書き込みが繰り返される可能性がある。MCP ツールのアノテーションは任意であり、デフォルトは非冪等の挙動であるため、アノテーションの欠落は自動リプレイを正当化できない。

## Replay policy

Qwen Code は、以下がすべて真の場合のみ、失敗した呼び出しを自動的にリプレイする:

- 失敗が既存の MCP 接続チェックにより接続喪失として分類される。
- MCP サーバーが `trust: true` である。
- 現在のワークスペースがワークスペース信頼ゲートを通過する。
- ツールが `idempotentHint: true` を宣言している。または `destructiveHint: true` や `idempotentHint: false` なしで `readOnlyHint: true` を宣言している。

矛盾するアノテーションは安全と扱われない。特に、読み取り専用を宣言しつつ破壊的または非冪等の挙動も宣言しているツールはリプレイされない。明示的な冪等宣言は変更操作をカバーできるが、矛盾する読み取り専用アノテーションを上書きはしない。

同じ決定が両方の実行パスに適用される: 進捗対応呼び出しに使用される直接 MCP クライアントと、callable フォールバックである。中断エラー、接続以外のエラー、MCP `isError: true` のプロトコル結果は既存の挙動を維持する。

再接続後、Qwen Code はリプレイを送信する前に、新しく検出されたツールに対して同じ信頼とアノテーションのチェックを適用する。以前のサーバープロセスの信頼やアノテーションを新しい呼び出しへ持ち込まない。

## Failure behavior

接続失敗がリプレイして安全でない場合、現在の呼び出しは再接続も 2 回目の呼び出し構築も行わない。操作が完了した可能性があり、自動的に再試行してはならないことを説明する安定したエラーを返す。このエラーにはツール引数やアップストリームのトランスポートエラーを含めない。

後続の独立した呼び出しの接続復旧は、引き続き既存のヘルスモニター、明示的な再接続、または通常の検出ライフサイクルの責務である。安全な呼び出しは既存の上限付き再接続挙動を維持する。

## Compatibility

これは意図的な保守的変更である。アノテーションのないツールは、古い Qwen Code リリースがそれらをリトライしていた場合でも、透過的な接続喪失リプレイを受け取らなくなる。リプレイを望むサーバーは正確なアノテーションを提供しなければならず、管理者は信頼されたワークスペースでサーバーの信頼をオプトインしなければならない。

MCP のアノテーションはサーバーが提供する挙動のヒントであり、認可の境界ではない。Qwen Code は、サーバーとワークスペースの両方の信頼ゲートを通過した後でのみ、これらをリプレイに使用する。

## Verification

テストは、直接クライアントと callable フォールバック、安全な冪等および読み取り専用の宣言、アノテーションの欠落と矛盾、両方の信頼ゲート、信頼やアノテーションを失った再検出ツール、接続エラー分類、中断、プロトコルエラー、再接続失敗、リトライ上限をカバーする。別途ローカルの E2E レコードで、レスポンス接続を切断する前に副作用をコミットするサーバーを実施し、安全でない呼び出しがサーバーに 1 回しか到達しないことを検証する。
