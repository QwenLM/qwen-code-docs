# 明示的なモニターキャンセルの通知

## Problem

`task_stop` は、モニターがキャンセルされたことを確認する同期のツール結果をすでに返している。モニターレジストリは終端の `cancelled` 通知も発行し、クライアントはそれを通知のユーザーメッセージとして記録し、新しいモデルターンとして送信する。キャンセルの直前にキューに入った `running` イベントは、終端通知を抑制しても同じ余分なターンを引き起こし得る。

## Design

- キャンセルが `task_stop` から来た場合、モニターをサイレントにキャンセルする。ツール結果がユーザーとモデルに見える確認のままとなる。
- その他の呼び出し元に対するレジストリのデフォルトキャンセル挙動は変更しない。
- drain 時に、レジストリエントリが明示的に `cancelled` となったキュー済みの `running` モニター通知を破棄する。このチェックはインタラクティブキュー、永続 stream-json キュー、ワンショットのヘッドレスキューに適用される。
- 自然な `completed` と `failed` の通知、および `task_stop` 以外のキャンセルパスが発行する終端通知は引き続き配送する。

ACP は `running` モニター通知をすでに拒否するため、サイレントな明示的キャンセルでそのクライアントには十分である。

所有者ルーティングされたモニター通知は、ユーザーの会話ではなくエージェントの入力キュー内に留まる。これらはこのセッション通知修正の対象外である。通常のツール呼び出しパスでは、キュー済みのイベントは、セッションターンを作る代わりに、すでに必須の `task_stop` ツール結果と一緒に配送される。

## Verification

- `task_stop` は、通知コールバックを呼び出さずにモニターをキャンセルして中断する。
- 各クライアントは、モニターが明示的にキャンセルされた後、キュー済みの `running` イベントを破棄する。
- 既存の終端通知テストは、自然な完了と失敗が配送されることを引き続き実証する。
- 実際のモデル駆動で `monitor` の後に `task_stop` を実行しても、フォローアップの通知ターンは発生しない。
