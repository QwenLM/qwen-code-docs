# デーモン全体の deep ヘルス

## Problem

`GET /health?deep=1` は、デーモンが 1 つのワークスペースランタイムを所有していた
当時に導入された。マルチワークスペース対応が投入された後も、このルートは
プライマリーブブリッジに接続されたままであったため、そのカウンターは、
セカンダリワークスペースにセッション、プロンプト、保留中のパーミッションが
あるにもかかわらず、デーモンをアイドルと報告する可能性があった。

shallow エンドポイントは意図的に異なる：`GET /health` は
リスナーが応答できることのみを証明する。低コストであり続けなければならず、
ランタイム状態にアクセスしてはならない。

## Decision

deep ヘルスはデーモン全体の情報提供用スナップショットである。
`WorkspaceRegistry.listManaged()` が返すすべてのランタイムを集約する。
これには、drain 中だがブリッジのクリーンアップが完了していない
ワークスペースも含まれる。

| フィールド           | 集約方法                                                 |
| -------------------- | -------------------------------------------------------- |
| `workspaceCount`     | スナップショット内の管理対象ランタイムの数               |
| `sessions`           | 合計                                                     |
| `pendingPermissions` | 合計                                                     |
| `activePrompts`      | 合計                                                     |
| `connectedClients`   | 既存のデーモン全体の REST SSE 数                         |
| `channelAlive`       | いずれかの管理対象ランタイムのチャネルがライブの場合 true |
| `lastActivityAt`     | null でない最新のブリッジアクティビティ時刻              |
| `idleSinceMs`        | 1 つの `Date.now()` スナップショットから最新のアクティビティ時刻を引いた値 |
| `rateLimitHits`      | 既存の任意のデーモン全体のレート制限カウント             |

このルートは、値を結合する前に各ランタイムの必須ゲッターを読み取る。
チャネルの読み取りをショートカットしない。レジストリやいずれかのゲッターが
スローした場合、deep プローブ全体が部分的なスナップショットを返すのではなく、
`503 {"status":"degraded","reason":"aggregation_failed"}` で失敗する。
ゲッターの失敗は、その識別子を HTTP レスポンスに公開することなく、
デーモンの stderr ログ内でワークスペースランタイムを識別する。

ブートストラップのリスナーは起動しているがランタイムレジストリが
準備できていない間、deep リクエストは `reason: "bootstrap"` と
`Retry-After: 1` を伴う degraded ボディを返す。ヘルス優先の起動モードでは、
そのレスポンスを完了してもランタイムの起動がトリガーされる。
shallow のブートストラップレスポンスは引き続き
`200 {"status":"ok"}` である。

## Compatibility and boundaries

- `deep=1`、`deep=true`、および bare の `deep` がスナップショットを有効にする。
  その他のすべての値は shallow ヘルスを使用する。
- シングルワークスペースの deep レスポンスは既存の値を維持し、
  `workspaceCount: 1` を追加する。
- 認証、Host 許可リスト、CORS、レート制限の挙動は変更されない。
- レスポンスはワークスペース ID、パス、信頼状態、ワークスペースごとの
  詳細を公開しない。
- ケイパビリティや SDK の変更は不要である。`workspaceCount` により、
  コンシューマはデーモン全体の契約を識別できる。

deep ヘルスは全ワークスペースの準備完了チェックではなく、
アトミックな reclaimed リースでもない。カウンターのアクセサーは
子プロセスに ping せず、`connectedClients` は REST SSE のみを表す。
reclaimer は反復したアイドルサンプルとグレースフルシャットダウンを
要求すべきである。トランスポートやワークスペースごとの診断が必要な
オペレーターは、認証済みの `/daemon/status` エンドポイントを
使用すべきである。

## Alternatives rejected

- `WorkspaceRegistry.list()` のみを集約すると、ブリッジのクリーンアップが
  完了する前に drain 中のランタイムが隠され、アイドルを早すぎる時点で
  報告する可能性がある。
- `/daemon/status` を再利用すると、ヘルスが、アクティブなワークスペースの
  スコープと失敗時の契約が異なる、より重いスナップショットに依存するように
  なってしまう。
- ワークスペースセレクターを追加しても、呼び出し側のファンアウト問題は
  残ったままであり、デーモンレベルのアイドル検出を満たさない。
- `channelAlive` を「すべてのチャネルがライブ」と定義すると、既存の
  デーモンステータス互換の意味が暗黙的に変わってしまう。
  ワークスペースごとの失敗は `/daemon/status` に属する。
