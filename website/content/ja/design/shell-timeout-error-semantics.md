# シェルタイムアウトのエラーセマンティクス

## 問題

フォアグラウンドの Shell コマンドは、現在タイムアウトをテキストで説明しつつ、成功した `ToolResult` を返す。そのため下流のコードはその呼び出しを成功として記録し、`output` フィールド付きの function response を送信し、コマンドが完了していないにもかかわらず成功インジケーターを表示し得る。タイムアウトの後に到着したキャンセルが、元の原因を上書きすることもある。PTY の検出中は、実行サービスが起動後までシグナルを観測しないため、すでに中断された呼び出しでもプロセスを spawn できてしまう。

## 結果の契約

Shell が所有するフォアグラウンドのタイムアウトは `ToolErrorType.EXECUTION_TIMEOUT` を返す。結果は、意図的に分離された 3 つのチャネルを使用する:

| チャネル       | 受け手                                | タイムアウト時の内容                                                                                |
| --------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `error.message` | フック、テレメトリー、span、ログ、アラート | 短いタイムアウト概要のみ                                                                     |
| `llmContent`    | モデルへの function response                 | タイムアウト概要、部分出力または明示的な出力なしの記述、切り詰めポインターがあればその位置 |
| `returnDisplay` | インタラクティブ履歴と ACP クライアント     | タイムアウト概要、部分出力または出力なしの記述、切り詰めポインターがあればその位置             |

スケジューラーは、タイムアウトの `llmContent` を、`response` に `error` フィールドを持ち `output` フィールドを持たない function response に変換する。失敗フックの追加コンテキストは、そのモデル向けのエラーに 1 回だけ追加される。トップレベルの `ToolCallResponseInfo.error` は短い運用上の概要のままとなるため、コマンド出力がテレメトリーやフックのエラー引数にコピーされることはない。

その他のソフトなツールエラーは、既存の Core スケジューラーの動作を維持する。ACP と投機的実行は、それらのパスがツールを直接呼び出し、そうでなければスケジューラーの分類ステップを持たないため、すべてのソフトエラーを一貫してエラーエンベロープでエンコードする。

## 最初の原因のルール

`AbortSignal.any()` は、最初に中断したシグナルの reason を保持する。Shell の分類は、実行後に結合されたシグナルの reason のみを読み取る:

- 中断された実行と組み合わさった `TimeoutError` はタイムアウトである。
- background-promote の reason と、中断された promote されていない実行の組み合わせは、既存の promote 拒否の競合である。
- その他の中断された実行はキャンセルである。
- 最初に発生したタイムアウトは、その後のユーザーキャンセルや promote リクエストによって変わらない。
- 最初に発生したキャンセルや promote リクエストは、その後のタイムアウトによって変わらない。

Core スケジューラーには、2 つ目の任意のグローバル実行タイマーがある。ツールが返した構造化タイムアウトは、スケジューラーが結果を消費する前に親シグナルが中断されても、タイムアウトのままである。スケジューラー自身のタイマーがタイムアウト結果を提供する場合、タイマー発火時点で親シグナルがまだ中断されていなければ、それが優先される。親のキャンセルに続き、非協調的なツールに対してタイマーが発火した場合は、キャンセルのままとなる。

ACP は構造化ツールタイムアウトに同じルールを適用する: 親シグナルがその後中断されたと観測されても、タイムアウトは中断（interrupt）ではなくエラーである。スローされた例外は、引き続きライブの中断状態を使用する。

## 起動時の動作

`ShellExecutionService.execute()` は、シグナルがすでに中断されている場合、中断済みでプロセスなしのハンドルを即座に返す。PTY の検出は `getPty()` とシグナルを競わせ、競合後に一時的なリスナーを削除する。中断が勝った場合、その後の PTY の解決や拒否は、PTY を spawn したり `child_process` にフォールバックしたりすることなく消費される。返される結果は `executionMethod: 'none'` を使用し、pid を持たない。

この動作は、リポジトリ内のこのサービスのすべてのコンシューマーに影響する: フォアグラウンドおよびバックグラウンドの Shell 配管、ユーザーの `!` Shell、プロンプトコマンドインジェクション、ACP ブリッジのシェル処理、git 帰属プローブ。動作上の変更点は、すでに中断されたリクエストがプロセスを開始しなくなることのみである。

## コンシューマーの動作

| コンシューマー                            | タイムアウト時の動作                                                                                                   |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Core スケジューラー                      | `status: error`、短いトップレベルエラー、詳細な `response.error`、タイムアウトの失敗種別                            |
| ACP セッション                         | 失敗したツールアップデート、モデル履歴と記録内の詳細なエラーエンベロープ、短い運用メタデータ             |
| 投機的実行               | 詳細なエラーエンベロープ。受け入れられた speculation の履歴は Error を表示する                                                |
| Anthropic アダプター                   | `tool_result.is_error: true`                                                                                       |
| OpenAI 互換アダプター          | 明示的な詳細エラーテキスト。プロトコルレベルのエラービットは存在しない                                                   |
| JSON と stream-json                | `is_error: true` で、短い概要よりも詳細なネストされたエラー内容が優先される                               |
| コンテキスト推定とバッチ予算 | `response.output` と `response.error` の両方のテキストがカウントされる。大きすぎるエラーはオフロード時も error キーを保持する |

マイクロコンパクションは、引き続き失敗したツール結果を変更しないままにする。完全なチャット圧縮は詳細なエラーサイズを認識するようになり、正しい予算でトリガーできる。

## Claude Code との比較

Claude Code は、コマンドのタイムアウトを失敗したツール結果として扱い、終了前に生成された出力をモデルとユーザーのために保持し、Anthropic プロトコルにおいてツール結果をエラーとしてマークする。本設計は、qwen-code の既存の `ToolResult` の形状とテレメトリーの慣習を維持しつつ、それらの観測可能な性質を採用する。コマンド出力を短い運用上のエラーチャネルにはコピーしない。

## 互換性と観測可能性

これは意図的なワイヤーレベルの修正である。ACP と speculation のソフト失敗は `{ output }` から `{ error }` に変わり、Core は `EXECUTION_TIMEOUT` の場合のみその形状を変える。タイムアウトのカウントは成功メトリクスからエラー/タイムアウトメトリクスに移り、成功フックの代わりに失敗フックが呼ばれる。スキーマ、エラー列挙型、タイムアウトのデフォルト、マイグレーション、ロールアウトフラグの変更はない。

部分的なコマンド出力には機微なデータが含まれ得る。分類の修正前と同様に、モデル、インタラクティブな結果、チャット記録、明示的な JSON 出力からは引き続き利用可能である。フックのエラー引数、トップレベルエラー、span の結果属性、運用ログの概要には追加されない。既存の切り詰めとディスクへのあふれ出しの制限は、詳細なモデルチャネルに適用される。

## スコープ外

- heartbeat または定期的な進捗報告
- Todo の停止ガードやプロンプトの変更
- 非ゼロ終了コードのセマンティクス
- 外部シグナルによる終了のセマンティクス
- バックグラウンド Shell のタイムアウト
- グローバルスケジューラータイマーが勝った後の部分出力の待ち
- 新しいタイムアウト設定やプロトコルフィールド

## 検証

ユニットカバレッジは、事前中断および PTY 検出の競合、Shell のタイムアウト/キャンセル/promote の順序付け、sed シミュレーション、スケジューラーの短いチャネルと詳細チャネル、Core のグローバルタイムアウトの順序付け、ACP と speculation の直接呼び出し、Anthropic 変換、JSON の内容選択、エラーサイズ推定、バッチオフロードをテストする。E2E 計画は `.qwen/e2e-tests/shell-timeout-semantics.md` に記録されている。
