# 適応的なターンごとのツール呼び出し上限

日付: 2026-07-17
ステータス: 実装済み
領域: `packages/core` のループ検出

## 問題

常にオンのターンごとのツール呼び出し上限（`model.maxToolCallsPerTurn`、デフォルト 100）は、粗雑なサーキットブレーカーです: モデルが実際にスタックしているか、生産的な作業をしているかに関係なく、101 回目のツール呼び出しでターンを停止します。大規模なマルチパッケージの実装ターンは正当に 100 を超えるツール呼び出しを行うため、この上限は生産的な作業を殺してしまいます — 偽陽性です。

具体的なケース: セッション `80db472f-…`（qwen-code-x1、「Web Shell git status/diff chip」）。`继续Phase 2` のターンはちょうど 100 回のツール呼び出しを行い、`npm run build` の途中で完了サマリーなしに強制停止されました。そのターンと隣接ターンの分析:

| ターン | ツール呼び出し | 個別の (tool,args) キー | 1 キーの最大繰り返し | 同名の最大連続 |
| ---- | ---------- | ------------------------- | --------------------- | -------------------- |
| 7    | 96         | 96                        | 1                     | 7                    |
| 8    | 100        | 99                        | 2                     | 3                    |
| 9    | 95         | 95                        | 1                     | 7                    |

生産的なターンは多様性が高い: 単一の `(tool, args)` 呼び出しが 2 回を超えて繰り返されることはありません。本当にスタックしたターンは、同じ呼び出しを何度も繰り返します。

## 設計

動作は、`maxToolCallsPerTurn` が**明示的に設定された**かどうかに依存します（`Config.isMaxToolCallsPerTurnExplicit()` で追跡）:

- **明示的な値 `N`** → **ハードキャップ**（リリースされた契約）: ターンは `N` を超える呼び出しで停止し、適応的な延長は行われない。これにより後方互換性が保持される — 無人コストを制限するために値を設定したユーザーは、引き続きまさにその制限を得る。（v0.19.10 はこの上限をハードキャップとして出荷。本 PR の以前の反復は明示的な値を 3 倍にしたが、これは破壊的変更であり — 取り消された。）
- **デフォルト（未設定、`S = 100`）** → **適応的**: 繰り返しシグナルを用いて生産的な長いターンとスタックしたターンを区別し、後者のみ（絶対的なバックストップに加えて）を強制停止する。最新のモデルはタスクごとに正当に数百回の呼び出しを行うため、デフォルトは生産的な長いターンを強制停止してはならない。

適応的な（デフォルトの）上限には 2 つのしきい値があります:

- **ソフトキャップ `S`**（100）: ターンが `S` 回のツール呼び出しを超えた場合、スタックの繰り返しシグナルが存在する場合にのみ停止する。それ以外はターンを生産的とみなし、継続させる。
- **ハードキャップ `S * ADAPTIVE_CAP_HARD_MULTIPLIER`**（乗数 10 → 1000）: 絶対的なバックストップ。超えたら繰り返しに関係なく停止するため、呼び出しごとに引数を変化させる暴走（繰り返しシグナルでは捕まらない）も引き続き制限される。乗数は十分に高く、数百回呼び出しの生産的なターンが偽陽性にならない。

スタックの繰り返しシグナル: ターン内で単一の `(tool, args)` キーが出現した最大回数が `GLOBAL_DUPLICATE_THRESHOLD`（6）に達すること。これは既存の global-duplicate のセマンティクスを再利用し、広い安全マージンを持つ（観測された生産的なターンは ≤ 2）。

同名の連続は意図的にゲートシグナルとして使用されません: 並列のツールバッチ（例: 1 つのアシスタントメッセージ内で異なるファイルの `read_file` を複数回）は、行動停滞のしきい値 8 に近すぎる、6〜7 の同名連続を正当に生むためです。

### 常にオンの追跡

上限は常にオン（`skipLoopDetection` ではゲートされない）ですが、既存の `globalToolCallCounts` マップはゲートされたヒューリスティックパスの内部でのみ維持されています。常にオンの上限をゲートされたパスから独立させるため、上限は独自の小さな常にオントラッカーを維持します:

- `capKeyCounts: Map<string, number>` — このターンの `(tool,args)` ごとのカウント。
- `capMaxKeyRepeat: number>` — 単一キーのカウントの走行最大値。

すべての `ToolCallRequest` について `checkAlwaysOnSafeties` で維持され、`reset()` と `Retry` 時にクリアされます（ヒューリスティックパスがリトライ時に `globalToolCallCounts` をクリアする方法と一致）。

## 動作マトリクス

明示的な値 `N`（ハードキャップ）:

| 総呼び出し | 結果      |
| ----------- | ----------- |
| `≤ N`       | 許可       |
| `> N`       | 停止（ハード） |

デフォルト（未設定）、ソフトキャップ `S = 100`、ハードキャップ `H = 1000`:

| 総呼び出し     | 繰り返しシグナル    | 結果             |
| --------------- | -------------------- | ------------------ |
| `≤ S`           | 任意                  | 許可              |
| `S < total ≤ H` | 最大キー繰り返し `< 6` | 許可（生産的） |
| `S < total ≤ H` | 最大キー繰り返し `≥ 6` | 停止（スタック）       |
| `> H`           | 任意                  | 停止（バックストップ）    |

`S ≤ 0` の場合、上限は無効（`getMaxToolCallsPerTurn()` は `Infinity` を返す）。動作は不変（決して発火しない）。

## ノンゴール / フォローアップ

- 停止したターンのその場での再開（アーキテクチャ上不可能: ダイアログが表示される時点でターンはすでに返されている）。
- ループ検出ダイアログ UI の変更（別の改善）。
- ハードキャップ用の独立した設定ノブ（ソフトキャップから導出。`maxToolCallsPerTurn` を上げると両方がスケールする）。
- 直近ウィンドウ化または結果を認識するスタックシグナル。現在のシグナルはターンごとの単調な最大値: 同じ `(tool, args)` がターン内のどこかで 6 回繰り返されると、たとえその繰り返しが正当でも（例: 連続する修正後に同じビルド/テストを再実行する）スタックとマークされる。これは決してリグレッションではない — このシグナルが作用するのはソフトキャップを超えた場合のみで、そこは古い上限が常に停止していた場所 — が、その生産的なクラスは恩恵を受けない。「生産的なターンは ≤ 2 回しか繰り返さない」というエビデンスは 1 つのセッションの 3 ターンに由来する。テレメトリがこの偽スタックパターンを示す場合は、ウィンドウ化シグナルで再検討する。
- 2 つの停止理由のテレメトリでの区別。ソフトキャップのスタックとハードバックストップはどちらも `TURN_TOOL_CALL_CAP` を発行する。`LoopDetectedEvent` の boolean/属性があれば、本番でどちらが発火したかがわかる（10 倍の乗数の検証に有用）。ヘッドレスのメッセージはすでに両方をカバーする表現になっている。
- ACP/デーモンパス（`packages/cli/src/acp-integration/session/Session.ts` の `recordDaemonToolCalls`）は、`LoopDetectionService` を使用しない独自の粗雑なターンごとの上限を持つ。繰り返しに関係なく常に値をハードキャップとして扱う。適応的なデフォルトとの整合は別のフォローアップ（バッチ単位でツール呼び出しを追跡しており、独自の `(tool,args)` ごとの繰り返し追跡が必要になる）。報告された偽陽性を生んだインタラクティブな TUI パスは、ここで修正される。
