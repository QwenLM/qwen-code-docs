# セッションライターリース P0a

## Problem

永続化されたセッションは、元のプロセスがまだターンを生成・記録している間に、2 つ目の Qwen プロセスによって読み込まれ得る。両方のレコーダーは同じ親 UUID をキャッシュする。それらが独立に追記すると、JSONL トランスクリプトにはその親から派生したマークのない 2 つの子が生じる。再開は物理的な末尾に従うため、最初のプロセスの完全な回答が隠されてしまう可能性がある。

本番のインシデントはまさにこの順序だった: 元のプロセスがツール結果を記録し、デーモンがそのセッションを新規に読み込み、元のプロセスが残りのツール作業と最終回答を記録し、その後デーモンが、先のツール結果を親として使ってユーザーメッセージを記録した。

## Scope

P0a は、各 ACP/デーモンの `(runtime base, session ID)` に対して 1 つのクロスプロセスライターを確立し、このインシデントに関係した通常の線形追記パスを保護する。含まれるもの:

- 死プロセスリカバリー付きのアトミックなオーナートークンリース
- リース取得後の権威あるトランスクリプトの再読み込み
- すべての JSONL 追記におけるオーナー、ファイル識別情報、バイト長のフェンシング
- ユーザー、cron、通知、チームメイトの作業開始前のターン受け入れ
- 1 つのデーモン内での、すでにライブなセッションの再利用
- ライブトランスクリプトのリプレイとデスクトップ履歴リフレッシュのためのオーナーバリア読み取り
- 決定論的な ACP/HTTP の競合エラー
- セッションクローズ時および初期化失敗時のリースの drain と解放

P0a は、セッション切り替え、rewind、ブランチ/フォーク、作業ディレクトリの移行、アーカイブ/削除/リネームのメンテナンス、トランスクリプト修復をトランザクショナルにはしない。また、同じデーモンからのすべての load/resume をクローズに対して直列化する初期化中のレジストリエントリも導入しない。繰り返しの load は、そのオーナーが登録された後にオーナーを再利用し、一方でクロスプロセスのリースは初期化中も 2 つ目のライターを拒否し続ける。load/close の結果の完全な統合は P0b に属する。セッション切り替えと persistence root の移行は、ACP の Config がリースを所有している間、fail closed（失敗時は拒否）となる。ACP の論理的な作業ディレクトリ変更は、レコーダーと SessionService を元の persistence root に結びつけたままにするため、引き続きサポートされる。同じオーナーによる rewind は、レコーダーの書き込みバリアの下で、その Config に固定された SessionService 経由で読み込まれる。リネームとブランチは、既存のレコーダーまたはコピー前フラッシュのパスを維持する。デーモンのアーカイブ/削除と非ライブセッションのメンテナンスは、既存のセマンティクスを維持する。ライブオーナーの外部からの並行メンテナンスは引き続きサポートされず、P0b の境界の一部である。インタラクティブおよびヘッドレスの CLI レコーダーは、`/clear`、`/resume`、`/branch`、`/cd` がリグレッションしないよう、既存のリースなしの動作を維持する。P0b がプロトコルを拡張するまで、ACP オーナーと同時に同じセッションへ書き込んではならない。

このプロトコルは `experimental.sessionWriterLease` でゲートされ、デフォルトでは無効である。実効値は ACP 子プロセスの起動時にブートストラップの Config からスナップショットされ、そのプロセスがサービスするすべてのセッションに対して固定される。セッションごとの設定リロードでは変更できない。有効化にはプロセスの再起動が必要である。この設定は ACP/デーモンのレコーダーにのみ影響する。インタラクティブおよびヘッドレスのレコーダーは、設定が有効な場合でも引き続きレガシーパスを使用する。

## Invariants

1. ある runtime base の下で、協調する ACP プロセスは最大 1 つだけがセッションのライターリースを所有する。
2. リース付きの ACP レコーダーは、リースを所有し、かつそれを保持した状態でトランスクリプトを再読み込みするまで非アクティブである。
3. リース前に読み込まれたプレビューデータは、決してレコーダーの権威ある末尾にならない。
4. すべてのリース付き ACP 追記は、オーナートークン、トランスクリプトのハード状態、バイト長を検証する。タイムスタンプのみのドリフトは、安定した内容検証の後でのみ受け入れられる。
5. 所有権またはトランスクリプト整合性の失敗は、そのリース付き ACP Config における後続のトップレベルターンを永続的に拒否する。
6. デーモンは、そのデーモン内で既にライブなセッションに対して、2 つ目の書き込み可能な Config を構築しない。
7. ライブエントリは、そのレコーダーが drain を完了しリースを解放した後にのみ削除される。
8. ランタイム出力ルートは Config ごとに固定され、ロックとトランスクリプトが異なる非同期のワークスペースコンテキストを通じて解決されないようにする。

## Lease protocol

ロックは次の場所に保存される:

```text
<runtime base>/tmp/session-writer-locks/<encoded session id>.lock
```

その不変レコードには、ランダムなオーナートークン、PID、ホスト、プロセス種別、取得時刻、Qwen のバージョン、（利用可能な場合は）安定した OS のプロセス開始識別情報が含まれる。Linux ではカーネルのブート ID とプロセス開始の tick を使用するため、実時間時計の補正によってライブなオーナーが古くなったように見えることはない。Darwin ではプロセス開始のプローブを C ロケールと UTC に正規化し、異なる環境の 2 つのプロセスが同じ識別情報を比較できるようにする。この識別情報は、プラットフォームが信頼して公開している場合、PID の再利用を区別する。他ホストのオーナーと、安全性を証明できないあらゆる状態は fail closed（失敗時は拒否）となる。

取得時は、完全に書き込まれた一時レコードを作成し、それをロック名へアトミックにリンクする。有効なライブオーナーは `session_writer_conflict` を返す。有効な死んでいるローカルオーナーは、リネーム、再チェック、再取得（reclaim）が可能である。reclaim ガードは有限のオーナー世代を形成し、reclaim する側自体がクラッシュした場合に別のプロセスがリカバリーできるようにする。不正な形式、シンボリックリンク、または非regularファイルのロックは、古いと推測されるのではなく `session_writer_unavailable` を返す。

リースは、トランスクリプトが存在するかどうか、そのファイル識別情報、セキュリティメタデータ、バイト長、およびインメモリのインクリメンタル SHA-256 状態をスナップショットする。存在、長さ、デバイス/inode、モード、オーナー/グループ、リンク数の変更は fail closed（失敗時は拒否）となる。作成、変更、修正のタイムスタンプは参考情報である: タイムスタンプのみのドリフトは、1 つのファイルハンドルを通じた安定した全内容チェックをトリガーし、ダイジェストが変わらない場合のみ受け入れられる。モードを変更しない拡張属性や ACL エントリは個別にはフィンガープリントされない。そのような操作がタイムスタンプのドリフトとして表面化した場合は、すべてのハード状態が変わっていなければ同じ内容チェックの後に受け入れられる。ファイルシステムが観測可能なタイムスタンプの差分を公開しない場合、その操作は検出されない。`appendJsonLine` は追記ハンドルをオープンした後に同じチェックを適用し、既知のバイトで候補ダイジェストを進め、永続的な追記の成功、書き込み後のパス検証、最終的なオーナーチェックの後でのみダイジェストと期待状態をコミットする。新規トランスクリプトの作成は排他的作成を使用する。

既存トランスクリプトの取得は、ダイジェストのベースラインを確立するために 1 回の O(n) ストリーミング読み取りを行い、バッファーは 1 MiB に制限される。通常の追記はインクリメンタルのままである。reconciliation スキャンは、読み取り前の状態から読み取り後の状態までタイムスタンプが安定していることを要求し、タイムスタンプのみの不安定性は最大 3 回までリトライする。読み取りカーソルの後ろで非協調的なライターが既に読み取ったオフセットを変更しても、逐次ダイジェストは期待される内容と一致し得るため、この安定区間が必要である。タイムスタンプが変化し続ける場合、リースは引き裂かれた可能性があるスナップショットを受け入れる代わりに `session_writer_unavailable` を返す。

インクリメンタルダイジェストは、ライブプロセスの互換性チェックであり、認定されたハンドオフのための永続化された証明ではない。非協調的なライターは、このプロセスの状態観測のいずれかにタイムスタンプの差分を残すことなく、追記中に同じ長さのプレフィックスを上書きできる。その既存の境界を閉じるには、無条件の O(n) 書き込み後スキャンが必要になり、繰り返しの追記が二次計算量になるため、P0a の範囲外である。

## Activation and close

機能ゲートが有効な場合、ACP の `Config.initialize()` は、拡張、フック、ツール、モデル、スケジューラの初期化の前にリースを取得する。リースを保持している間に、アクティブ/アーカイブ状態を解決し、存在する場合はアクティブなトランスクリプトを再読み込みし、再読み込み中にトランスクリプトが変化していないことを検証し、ロック前のプレビューがあれば置き換え、レコーダーをアクティブ化する。オプトインのない ACP Config と、すべての非 ACP Config は、この P0a リースを取得せず、引き続きレガシーのレコーダーパスを通る。

その後の初期化の失敗は、レコーダーをクローズしリースを解放する。通常のシャットダウンと ACP セッションのクローズは、保留中のメタデータを確定し、レコーダーキューを drain し、オーナートークンを解放し、その後でのみライブセッションエントリを削除する。クリーンアップは識別情報がチェックされるため、失敗した古い初期化が新しい同じ ID のエントリをクローズすることはできない。取得時のクリーンアップは、リースのシングルフライトな正確なレコードの解放を使用する。終端の失敗はプライマリロックを保持し続け、後続の解放呼び出しは 2 度目のリネームを試みる代わりに同じ失敗を観測し、別のライターはプロセス終了時のリカバリーまでフェンスされたままとなる。決定的な子プロセスの拒否はセッションをライブのままにし、クローズをリトライできるようにする。クローズの drain には上限がある。タイムアウトやトランスポートの失敗は結果が不明であるため、ブリッジは共有の ACP チャネルを終了し、そのプロセス所有のリースは古いものとしてリカバリー可能になる。そのチャネル上の他のセッションも、そのリカバリーアクションによって回収される。

## Error contract

| 種別                          | JSON-RPC | HTTP | 意味                                                     |
| ---------------------------- | -------: | ---: | ------------------------------------------------------- |
| `session_writer_conflict`    | `-32020` |  409 | 別のライブプロセスがセッションを所有している。                  |
| `session_writer_lost`        | `-32021` |  409 | この Config はもはやロックを所有していない。                    |
| `session_transcript_changed` | `-32022` |  409 | JSONL が期待される追記シーケンスの外側で変更された。             |
| `session_writer_unavailable` | `-32023` |  503 | 所有権を安全に検証できなかった。                              |

外部レスポンスは固定のメッセージと `errorKind` を使用する。PID、ホスト、オーナートークン、ロックパス、トランスクリプトパスは公開しない。

先行する regularファイルのベースラインがないシンボリックリンクまたは非regularファイルのトランスクリプトパスは `session_writer_unavailable` である。リースが regularファイルのベースラインを確立した後で、そのパスをシンボリックリンクや別の非regularファイルに置き換えることは、外部によるトランスクリプトの置き換えであり、`session_transcript_changed` に分類される。

## Compatibility and rollout

このプロトコルは、機能が有効化された ACP ライターのみを調整する。デプロイとロールバックは、設定を有効または無効にする前に、古い ACP/デーモンのライタープロセスを drain しなければならない。レガシーのライターはロックを無視するため、バージョン混在または設定混在の ACP 運用は安全ではない。同じ永続化セッションへの並行するインタラクティブまたはヘッドレスアクセスは、引き続き P0a の範囲外であり、P0b までサポートされない。

ランタイムのファイルシステムは、アトミックな no-replace 動作を持つ同一ディレクトリ内のハードリンクをサポートしなければならない。この前提条件が利用できない場合、取得は `session_writer_unavailable` で fail closed（失敗時は拒否）となる。

既存のブランチされたトランスクリプトは自動的には修復されない。P0a はロールアウト後の新規の stale-load ブランチを防ぐ。修復と明示的なブランチのセマンティクスは、引き続き別の作業である。

## Verification

ユニットカバレッジは、デフォルト無効および明示的なオプトインのゲート、ロックの競合、死んだオーナーおよびクラッシュした reclaimer のリカバリー、不正な形式および非regularファイルのロック、オーナートークンの並行解放、制限付きの解放プリチェック、終端のクリーンアップ失敗、切り詰めおよび外部で変更されたトランスクリプト、タイムスタンプのみの reconciliation、同長のインプレースおよびアトミック置き換え、セキュリティメタデータの変更、UTF-8 のバイト計算、レコーダーのアクティブ化/フェンシング/クローズ、権威ある再読み込み、初期化クリーンアップ、ランタイムルートの固定、ターン受け入れ、同一デーモンのリプレイ再利用、記録無効時の互換性、レガシーのインタラクティブレコーダーの動作、エラーのサニタイズをテストする。Darwin のカバレッジは、異なるタイムゾーンのプロセスが同じオーナー識別情報を導出することも検証する。PID の再利用処理は実装されているが、プロセス開始のプローブはプラットフォームに依存するため、テストのエビデンスとしては主張しない。

機能ゲートを有効にした状態で、実際の 2 プロセスのリグレッションがインシデントのタイミングを再現する: プロセス A はツール結果の末尾の後にライターを保持し、プロセス B はライターとして読み込まれる前に拒否され、A は最終回答を追記してクローズし、その後 B は取得し、その最終回答を再読み込みし、最終回答を親として次のユーザーレコードを追記する。

デスクトップのカバレッジは、ライター競合がユーザーに表示され、リクエストされた永続化セッションが新しいセッションで暗黙に置き換えられないことを検証する。ライブ履歴リフレッシュは、論理的な `/cd` の後も含め、オーナーの書き込みバリアと Config に固定された SessionService を通じてサービスされる。
