# バックグラウンド npm 更新

## Problem

公開された CLI は、コンテンツハッシュ付きの JavaScript チャンクにコード分割されている。アクティブなセッションから `npm install -g` を実行すると、それらのチャンクがその場で置き換えられるため、古いプロセスの後続の動的 import が `ERR_MODULE_NOT_FOUND` で失敗し得る。インストールをセッション終了まで延期すれば破損は回避できるが、バックグラウンド更新が終了時の遅延に変わり、ユーザーはセッションを離れるまで恩恵を受けられない。

## Design

書き込み可能なグローバル npm インストールに対し、描画後の更新チェックが、グローバルランチャーから導出されたディレクトリ配下に解決された正確なバージョンをインストールする:

```text
~/.qwen/updates/npm/<launcher-id>/versions/<version>/
```

バージョンチェックは npm をそのグローバルコンテキストで実行し、ステージングインストールは分離された prefix を使用する。ステージングコマンドは元のグローバル npm 設定を明示的に保持するため、prefix を変更しても検出とインストールの間でレジストリや認証設定が切り替わることはない。

ランチャーは、バージョンを選択する前に同じホームスコープの `.env` ファイルから `QWEN_HOME` を解決する。完全な環境変数ローダーは後で実行されるが、これによりブートストラップパスは CLI のストレージと整合したままになる。

インストールとアクティベーションは切り離されたワーカーで実行されるため、TUI を終了しても進行中の更新は中断されない。npm が正常に exit した後、ワーカーはパッケージ名、バージョン、バンドル、ランチャーを検証し、そのランチャーのバージョン群の横に `active.json` ポインターをアトミックに書き込む。グローバルの npm パッケージは変更されない。すでに稼働中のプロセスと、それが開始する子コマンドは元のビルドに固定されたままになる。次回の起動時に、安定したランチャーがポインターを読み取り、検証済みのバージョンディレクトリを起動する。

各グローバル npm ランチャーは独自のポインターとバージョンペイロードを持つため、異なる npm や nvm の prefix 配下のインストールが `~/.qwen` を共有しても、互いを上書きしたり依存関係を共有したりすることはない。遅い並行更新が、より新しいアクティブバージョンを置き換えることはできない。

不完全なインストールはアクティブポインターを決して変更しない。アクティベーション前に、ワーカーはインストールされたマニフェストを検証し、ランチャースモークテストを実行する。欠落、不正形式、またはランチャー不一致のポインターは無視され、元の npm パッケージがフォールバックのままとなる。ポインターはベースパッケージとランチャーの識別情報も記録するため、後続の明示的なグローバル npm インストールがマネージドバージョンに優先する。ランチャーはマネージド更新で置き換えられないため、既存の `active.json` フィールドは互換性契約である: 将来の変更でフィールドの追加は可能だが、削除や再解釈はできない。

古いライブセッションがまだそこから読み込む可能性があるため、バージョンディレクトリは保持される。クリーンアップは、ディスク使用量がリースベースのコレクターの必要性を示すまで、意図的に延期される。

## Scope

これは npm インストールの自動更新のみを変更する。その他のパッケージマネージャーやスタンドアローンアーカイブは、同等の不変バージョンインストールレイアウトが整うまで、既存の終了安全な挙動を維持する。
