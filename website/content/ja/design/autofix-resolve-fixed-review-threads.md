# Autofix のレビュースレッド解決の強化

## 問題

Qwen Autofix では、すでにレビュー対応エージェントがコード上で解決されたインラインレビューコメントを特定できる。認証情報を持つホストのワークフローは、それらの REST コメント ID を GitHub のレビュースレッドに対応させ、修正の push 後に `resolveReviewThread` を呼び出す。

現在の順序付けは概ね安全だが、解決対象のライブな PR head が、決定論的検証の対象となったコミットと正確に一致することは証明されていない:

- 拒否された push が、新しく移動したリモート head をマージすることで救済される場合がある。検証がマージより前に行われていたにもかかわらず、マージされたコミットが push される。
- PR の作者が、Autofix の push 後かつ解決ミューテーションの前に再度 push する場合がある。
- 同一実行内のリペアが、拒否された最初の試行から `resolved-comments.txt` や `comment-replies.json` を引き継ぐ場合がある。

これらのギャップにより、現在の PR head が検証済みの修正をまだ含んでいるという証拠がないまま、会話を解決済みとマークしてしまう可能性がある。

## 現状

責務はすでに正しく分離されている:

- `.qwen/skills/autofix/SKILL.md` は、エージェントに所見の分類方法と `resolved-comments.txt` や `comment-replies.json` の書き方を指示する。
- `.github/scripts/run-autofix-review-verification.sh` は、決定論的なビルド、typecheck、lint、影響パッケージのテストを独立して実行する。
- `.github/workflows/qwen-autofix.yml` は GitHub PAT を保持し、ブランチの push、レビュースレッドの取得、ミューテーションの実行を担う。
- `scripts/tests/qwen-autofix-workflow.test.js` は、スタブされた GitHub レスポンスを使ってワークフローのシェルブロックを抽出・実行する。

GitHub のミューテーションは信頼されたワークフロー内にとどまらなければならない。エージェントは GitHub の認証情報を受け取ってはならない。

## 提案する変更

### 検証ゲート

決定論的チェックの前にクリーンな追跡ワークツリーとインデックスを要求し、コミット SHA をキャプチャし、構造チェックの後、およびビルド、typecheck、lint、テストの後に、SHA と追跡状態の両方が変わらないことを要求する。その後、キャプチャした SHA を `verified_head` という名前のステップ出力として記録する。no-op や失敗の結果では出力しない。これにより、永続的な追跡変更や、ブランチが制御するチェックが作成したコミットが拒否される。不変のファイルシステムを保証するものではなく、1 つのコマンド内で一時的に状態を変更して復元するスクリプトを検出するものでもないが、これは既存の CI 信頼モデルの一部として維持される。

### 最終検証の選択

選択された検証 SHA を最終検証ステップへ伝播する:

- リペアが実行されなかった場合は最初の検証 SHA を使用する;
- リペアが実行された場合はリペアの検証 SHA のみを使用する;
- 成功したリペア済みの結果に対して、最初の SHA にフォールバックすることは決してない。

### リペアの隔離

リペアエージェントを呼び出す前に、`resolved-comments.txt` と `comment-replies.json` を、以前の試行の他の成果物とともに削除する。リペアの試行は、最終的な処遇を明示的に再生成しなければならない。ファイルが欠落している場合は fail closed（失敗時は拒否）となる: スレッドの解決も返信も行われない。

### push 後の解決証明

選択されたスレッドを解決する前に、以下のすべてを要求する:

1. `verified_head` が空でない。
2. push 競合の救済によって未検証のマージコミットが作成されていない。
3. push 成功後のローカル `HEAD` が `verified_head` と等しい。
4. ライブな `gh pr view` クエリが成功する。
5. 各ミューテーションの前に、ライブな PR の `headRefOid` が `verified_head` と等しい。
6. 各ミューテーションの直後にも、ライブな PR の `headRefOid` が引き続き `verified_head` と等しい。

各ミューテーションの前に、単一の GraphQL ガードがライブな `headRefOid` と対象スレッドのライブな `isResolved` 状態の両方を読み取る。他のアクターによってすでに解決されているスレッドはスキップされる。ミューテーションの後、同じガードが両方の値を再度検証する。ミューテーションコマンドがエラーを返した場合もこの事後チェックは実行される。レスポンスの喪失は、GitHub がミューテーションを適用しなかったことの証明にはならないためである。

ミューテーション前の条件が不明または偽の場合、またはミューテーション後の条件が曖昧な場合は、それ以上の会話の解決を停止する。事後ガードによって検証済み head が変わっておらずスレッドがオープンなままであることが証明された失敗ミューテーションは、警告して続行しても安全である。ワークフローは `unresolveReviewThread` を呼び出さない: GitHub は compare-and-swap の前提条件やミューテーションの帰属を公開していないため、`resolveReviewThread` のレスポンスが成功しても、事前ガードとミューテーションの間に他のアクターがスレッドを解決しなかったことは証明できない。そのため、自動的に再オープンすると、他のレビュアーの操作を取り消してしまう可能性がある。ミューテーションコマンドが不成功に終わった後、事後ガードで検証済み head と解決状態が確認された場合は、それを Autofix に帰属させることなく、観測された解決済み状態としてカウントする。曖昧な結果は残りのミューテーションをすべて停止する。

検証済みのコード push と通常のラウンドレポートは引き続き成功する。意図的にオープンにされた所見への返信は、スレッドが修正されたと主張しないため、push の成功後に続行できる。

## 設計上の決定

- **解決は fail closed（失敗時は拒否）:** 未解決のスレッドは回復可能だが、誤って解決されたスレッドは実際の欠陥を隠してしまう。
- **競合マージ後の解決をスキップ:** PAT を持つ公開ステップ内で完全な決定論的ゲートを再実行すると、高コストなロジックが重複し、認証情報がスコープ内にある状態でブランチが制御するスクリプトを実行することになる。後のレビューラウンドで安全にスレッドを解決できる。
- **ミューテーションの直前にライブな PR の状態を照会する:** ワークフローの同時実行制御では、コントリビューターによる直接の push は防げない。
- **既存のモデル処遇契約を維持する:** 意味的な判断はエージェントが担い、正確なコミット識別はホストが決定論的に強制する。
- **汎用の CLI／コアのコードは追加しない:** これは Autofix ワークフローのオーケストレーションであり、再利用可能な Qwen Code ランタイム機能ではない。

## 影響を受けるファイル

- `.github/scripts/run-autofix-review-verification.sh`
- `.github/workflows/qwen-autofix.yml`
- `scripts/tests/qwen-autofix-workflow.test.js`
- `.qwen/skills/autofix/SKILL.md`（契約の明確化のため）

## スコープの境界

含まれるもの:

- 検証済み／ライブ head の正確な一致;
- push 競合時の fail-closed 挙動;
- リペア試行の処遇の隔離;
- フォーカスされたワークフロー契約テストと挙動テスト。

含まれないもの:

- 既存の最初の 100 スレッドを超える GraphQL ページネーション;
- Autofix 以外の任意の PR 会話の解決;
- `CHANGES_REQUESTED` レビューの却下;
- モデルへの GitHub 認証情報の直接付与;
- 汎用の `/review` や CLI の挙動の変更。

## 未解決の質問

なし。保守的な挙動はミューテーションの前は決定論的である: 不確実性があれば、それ以上のスレッドの解決は行われない。ミューテーションの後、ワークフローは状態を観測・報告するが、アトミックな所有権の証拠なしに自動的に未解決に戻すことは決してない。
