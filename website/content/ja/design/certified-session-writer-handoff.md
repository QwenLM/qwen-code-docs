# 認定セッション writer のハンドオフ

## 問題

協調的な管理シャットダウンは現在、ACP 子プロセスが終了する前に各セッションの writer ロックを解放している。これにより通常の置き換えパスは修正されるが、記録を意図的に停止した writer と、アクティブなロックを解放せずに消滅した外部ホストの writer を区別することはできない。ホスト名、PID の可視性、ロックの経過時間、トランスクリプトの非アクティブ状態を死亡の証拠として扱えば、2 つのライブな Pod が同じトランスクリプトに追記することを許してしまう。

## スコープ

この変更は、管理対象の ACP writer に、整合性保護されたハンドオフ状態を追加する。受け入れ（admission）を閉じ、受け入れた recorder の作業を耐久性のある形で drain した後、信頼された管理子プロセスは、アクティブなロックを sealed レコードに置き換えることができる。信頼された管理対象の置き換えは、新しい Config が要求する正確なトランスクリプトに対してそのレコードを検証した後でのみ、所有権を引き継げる。

トランスクリプトのパスは、存在しないか、または証明のために開かれた同じ通常ファイルに解決されなければならない。ダングリングシンボリックリンクは、存在しないトランスクリプトとしては扱われない。

このプロトコルは引き続き `experimental.sessionWriterLease` によってゲートされ、デフォルトでは無効で、ACP プロセス起動時にスナップショットされる。スタンドアロン ACP、インタラクティブ、ヘッドレスの recorder は、認定テイクオーバーを得ない。通常のセッションごとのクローズは、sealed レコードを残す代わりに、引き続きそのロックを解放する。

この変更は、SIGKILL、イベントループのストール、未処理のクラッシュ、または sealing 完了前のストレージ障害によって残されたアクティブなロックを回収しない。TTL、heartbeat、ホスト名の窃取、Kubernetes API の参照、オペレーターによる強制奪取エンドポイント、メンテナンスリース、混合バージョンのサポートも追加しない。それらのアクティブロックのケースには、引き続き権威ある外部の writer フェンスと明示的なリカバリーが必要である。

## ロックレコード

新しいオーナーはスキーマ v2 のレコードを書き込む。アクティブなレコードは、既存の不変のオーナー診断情報を保持したまま、次を追加する:

```json
{
  "schema_version": 2,
  "state": "active"
}
```

sealed レコードは、前のオーナーの診断情報を保持したまま、次を追加する:

```json
{
  "schema_version": 2,
  "state": "sealed",
  "sealed_at": "2026-07-28T00:00:00.000Z",
  "transcript": {
    "relative_path": "<runtime-relative transcript key>",
    "exists": true,
    "byte_length": 1234,
    "sha256": "<lowercase hex digest>"
  }
}
```

相対キーは、新しい Config がすでに提供しているトランスクリプトのパスに解決されなければならない。任意のファイルシステムパスを選択するために使われることは決してない。スキーマ v1 のレコードは、ロールバック中の互換性のために引き続き有効なアクティブレコードであるが、sealed として解釈されることは決してない。

## 固定 claim

固定 claim パスは次のとおり:

```text
<primary lock path>.claim
```

これは、プライマリパスを一時的に削除する 2 つの遷移、すなわち active-to-sealed と sealed-to-active をシリアライズする。claim は、既存の write-sync-and-hard-link プリミティブで作成される。曖昧なリンクエラーは、遷移の続行やクリーンアップの前に、正確な claim のバイトと reconciliation（突合）される。claim は PID、ホスト名、経過時間によって回収されることは決してない。既存の claim はすべて `session_writer_unavailable` を返し、手動クリーンアップは権威ある外部の writer フェンスの後でのみ許可される。

通常の取得は、欠落しているプライマリロックをインストールしようとする試みのたびに、その前に claim をチェックする。インストール後にも再度チェックし、並行する遷移が claim を取得した場合は、自身の正確な候補のみを削除する。これにより、現在のアクティブロックのファストパスとローカルな stale オーナーのリカバリーが維持されつつ、両方のパスがハンドオフ遷移を尊重するようになる。古い writer は固定 claim を知らないため、混合バージョンの writer は引き続きサポートされない。

取得者は、遷移が claim を作成する直前に最初の claim チェックを通過し、遷移のプライマリパスのギャップ中にアクティブな候補をインストールする場合がある。遷移は、その同じセッションのスキーマ v2 アクティブレコードを claim 対応の候補として認識し、リタイアした前任者を保持し、候補の必須の 2 回目のチェックがそれを削除してハードリンクをリトライするのを待つ。この待機には上限がある。候補が 2 回目のチェックの前にストールまたは終了した場合、遷移は claim とリタイアした前任者を保持したまま、unavailable として失敗する。不明、不正形式、またはセッション間をまたぐ後継者は、削除も上書きもされることは決してない。

## sealing

管理シャットダウンは、セッションと recorder の受け入れを同期的に停止してから、すべての writer の terminal を並行して開始する。writer の terminal は:

1. カットオフ前に受け入れたすべての recorder 操作を drain する;
2. シンボリックリンクをたどらずに期待されるトランスクリプトを開き、既存のオーナーとトランスクリプトのスナップショットを検証し、保持したままのファイルディスクリプタ経由でバイトをハッシュ化する;
3. オーナーに固有の sealed 候補を書き込んで sync する;
4. 固定 claim を取得し、アクティブなオーナーと、保持したままのトランスクリプトの識別情報およびメタデータを再検証する;
5. 正確なアクティブなプライマリを、オーナー固有のリタイアパスへリネームする;
6. sealed 候補を、欠落したプライマリパスへ、置き換えなしでハードリンクする; そして
7. 自身の正確な retired、candidate、claim レコードのみを削除する。

プライマリパスの遷移は、すべてのインストールが固定 claim を尊重し、最後のハードリンクが他のプロセスによって作成されたロックを上書きできないため、協調する writer 間では論理的にアトミックである。作用後のエラーは、正確なレコードのバイトから突合される。古いオーナーは、不明なプライマリを削除・上書きすることは決してない。

管理フラッシュや証明の失敗は、アクティブなロックを保持する。通常のセッションごとのクローズは、正確なオーナーのクリーンアップを含め、既存の解放の挙動を維持する。通常の解放が管理シャットダウンと競合して先にコミットした場合、プライマリの欠落はすでに安全なハンドオフであり、置き換えは通常の取得を実行する。

失敗時のクリーンアップは、遷移前の正確なプライマリが復元されたことを証明した後でのみ、固定 claim を削除する。ロールバックがそのレコードを復元・検証できない場合、別のプライマリが現れても claim は残る。そのパスは、claim を観測した後に自身を削除する、負けた通常取得の候補である可能性があるためである。ロールバック自体は、固定 claim がまだこの遷移の正確なレコードを含んでいる間のみ試みられる。claim の欠落や置き換えは、現在のプライマリを変更してはならないことを意味する。リカバリーには、他の残留 claim と同様に、権威ある外部の writer フェンスが必要である。

プライマリ遷移の開始前の失敗は異なる: claim を要求する側は、プライマリパスのギャップを作成せず、前任者も移動させていないため、別の認定された争奪者が観測された sealed プライマリをすでに置き換えていたとしても、自身の正確な claim のみを解放する。これにより、遅れて負けた争奪者が、勝者がアクティブになった後に claim を取り残すことを防ぐ。

## 認定テイクオーバー

信頼された管理対象の親のもとで作成された Config のみが、認定テイクオーバーを有効にする。取得が sealed レコードを観測した場合、次を行う:

1. レコードの相対キーが Config の期待するトランスクリプトと一致することを検証する;
2. 固定 claim の外でそのトランスクリプトを開いてハッシュ化し、ファイルディスクリプタとその識別情報を保持する;
3. 固定 claim を取得する;
4. 正確な sealed プライマリを再読み込みし、保持したままのディスクリプタ、パスの識別情報、メタデータ、バイト長、ダイジェストを再検証する;
5. sealed プライマリを、候補固有のリタイアパスへリネームする;
6. claim から sync 済みのアクティブ候補を、プライマリパスへ置き換えなしでハードリンクする; そして
7. 正確な retired レコードと自身の claim のみを削除する。

その後、リースは、recorder の有効化前に、既存の権威あるセッションのリロードとトランスクリプトのフェンスを実行する。同じ sealed レコードを争う 2 つの置き換えは、最大で 1 つのアクティブなオーナーを生成できる。敗者は、勝者のアクティブなプライマリを観測したか、進行中／残留の claim を観測したかに応じて、conflict または unavailable の結果を受け取る。

## 失敗の契約

| 条件                                                                                 | 結果                               |
| ------------------------------------------------------------------------------------ | ---------------------------------- |
| 外部ホストや管理対象の死亡 PID レコードを含む、有効なアクティブオーナー              | `session_writer_conflict` / 409    |
| sealed の証明が期待されるトランスクリプトと一致しない                                | `session_transcript_changed` / 409 |
| 不正形式のレコード、通常ファイルでないパス、残留 claim、または不確実なファイルシステム結果 | `session_writer_unavailable` / 503 |
| 現在の writer が自身の正確なアクティブレコードをもう所有していない                    | `session_writer_lost` / 409        |

公開されるエラーは引き続きサニタイズされる。sealing とテイクオーバーの成功ログには、セッション ID、以前のホスト名／PID、sealing 時刻が含まれるが、オーナートークンやトランスクリプトのパスは決して含まれない。

## 互換性とロールアウト

混合バージョンのロールアウト中は、機能ゲートを無効のままにしなければならない。有効化または無効化には、古い ACP プロセスの drain が必要である。スキーマ v2 のリーダーは引き続きスキーマ v1 のアクティブレコードを受け入れるが、古いリーダーはスキーマ v2 を理解しない。したがってロールバックには、すべての新しい writer を drain し、このプロトコルによるアクティブ、sealed、claim レコードが残っていないことを確認する必要がある。

リースを取得しない writer、例えばスタンドアロン、インタラクティブ、ヘッドレスの recorder はこのプロトコルの外で実行されるため、通常の `qwen --resume` セッションなどがそれに該当するが、管理 writer が sealed したトランスクリプトに追記できる可能性がある。その追記は sealed の証明を無効にするため、同じセッションの後続の認定テイクオーバーは `session_transcript_changed` で fail closed（失敗時は拒否）となり、権威ある外部の writer フェンスが残留レコードをクリアするまで、デーモンはフェンスされたままとなる。したがってロールアウトでは、認定ハンドオフに参加するトランスクリプトから、非リースの writer を遠ざけておく必要がある。

ハッシュ化は、すべての追記にインクリメンタルなダイジェストを追加する代わりに、意図的に sealing とテイクオーバーの時に実行される。これにより最初の実装が小さく保たれ、証明がプロセスメモリに依存しなくなる。非常に大きなトランスクリプトでは、管理 sealing が親の期限を超える可能性がある。その場合はアクティブなロックを保持したまま fail closed（失敗時は拒否）となり、クリーンでないシャットダウンとして観測される。

## 検証

ユニットおよびマルチプロセスのカバレッジは、以下を証明しなければならない:

- スキーマ v1 と v2 のアクティブなロックが、既存のライブ／stale の挙動を維持すること;
- 管理対象の取得が、アクティブな死亡 PID や外部ホストのロックを回収しないこと;
- sealing の成功が、正確な相対キー、存在、バイト長、SHA-256 ダイジェストを記録すること;
- 認定された置き換えが sealed トランスクリプトをリロードし、アクティブになること;
- 1 つの sealed レコードを争う 2 つの置き換えが、正確に 1 つのオーナーを選出すること;
- トランスクリプトの変更、置き換え、切り詰め、証明の破損、不正形式の sealed レコード、残留 claim が fail closed（失敗時は拒否）となること;
- 各プライマリパス遷移の前後の失敗が、不明な後継者を上書き・削除しないこと;
- 管理フラッシュの失敗が、アクティブなプライマリを保持すること;
- 通常の recorder クローズは、sealing ではなく解放を行うこと; そして
- デフォルト無効およびスタンドアロン ACP のパスが変更されないこと。
