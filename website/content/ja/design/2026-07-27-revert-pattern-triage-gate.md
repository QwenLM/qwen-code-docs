# Revert パターン・トリアージゲート

日付: 2026-07-27
ステータス: 提案
領域: CI トリアージ — `.github/workflows/qwen-triage.yml`、`.qwen/skills/triage/`

## 問題

挙動を変えない小さなメンテナンス PR が現在、挙動変更と同じマルチステージのトリアージと
モデルレビューのリソースを消費している。元の提案（PR #7414）はこれらをフィルタリング
しようとしたが、メンテナがライブのバックログを計測したところヒット率は約 2% だった——
この機能はほぼ存在しない問題を対象としていた。

一方、リポジトリには履歴全体で **111 件の revert コミット**（2026 年 7 月だけで 19 件）が
あり、**revert の 61.5% はマージ後 24 時間以内に発生**している——つまり問題は素早く
発見されるが、すでに `main` に載った後である。実際のコストは無害な PR のレビューではなく、
ロールバックが必要な PR をマージしてしまうことである。

本設計は、すでに無害な PR ではなく、実際に revert を引き起こす PR を対象とする、
データに基づくトリアージゲートを提案する。

## データ

### 手法

リポジトリの revert 履歴全体の 3 フェーズ分析:

1. **収集**: `git log --all --grep="^Revert "` で 111 件の revert コミットを発見。
   各 revert の本文から `This reverts commit <hash>` をパースし、元のコミットを
   `gh api` 経由で PR まで遡った。結果: 46 件のユニークな revert 済み PR
   （59 件の revert が PR 番号まで追跡可能; 52 件の revert は PR リンクのない
   元のコミットタイトルのみ）。

2. **エンリッチメント**: 各 revert 済み PR から、トリアージ時点で観測可能なシグナルを
   抽出: 変更範囲（core/auth/providers/tools/services）、diff サイズ、レビュースタ数、
   ボットの Critical 指摘、CHANGES_REQUESTED のサイクル、マージ→revert の時間差、
   自己 revert、E2E 検証の有無。46 件中 31 件の PR を正常にエンリッチ; 15 件は
   削除されておりアクセス不能（HTTP 404）。

3. **コントロールグループ比較**: 最近マージされたが revert されていない 60 件の PR を
   サンプリングし、同じシグナルを抽出。各シグナルの precision（TP / (TP + FP)）と
   recall を計算。

スクリプトと生データ（ローカルの分析成果物、コミットしない）:
`.qwen/scripts/revert-analysis-*.mjs`、`.qwen/scripts/revert-data-*.json`、
`.qwen/scripts/revert-analysis-report-v2.json`。

### シグナルの precision と recall

| シグナル                       | precision | recall | revert 済み (n=31) | コントロール (n=60) |
| ---------------------------- | --------- | ------ | --------------- | -------------- |
| `touches_high_risk`          | **66.7%** | 32.3%  | 10              | 5              |
| `non_maintainer + high_risk` | **58.3%** | 22.6%  | 7               | 5              |
| `core + contested`           | **50.0%** | 19.4%  | 6               | 6              |
| `non_maintainer + core`      | 46.2%     | 38.7%  | 12              | 14             |
| `touches_core`               | 44.7%     | 54.8%  | 17              | 21             |
| `has_contested_pattern`      | 40.9%     | 29.0%  | 9               | 13             |
| `had_changes_requested`      | 40.7%     | 35.5%  | 11              | 16             |
| `non_maintainer`             | 39.6%     | 67.7%  | 21              | 32             |
| `large_diff_gt_200`          | 37.0%     | 54.8%  | 17              | 29             |
| `critical_count > 0`         | 28.6%     | 12.9%  | 4               | 10             |
| `fast_revert_24h`            | 100.0%    | 25.8%  | 8               | 0              |
| `self_reverted`              | 100.0%    | 9.7%   | 3               | 0              |

**サンプリングの注意点:** precision は 1:1.9 のケース・コントロール比（revert 済み 31 対
コントロール 60）で計算されているが、リポジトリの実際のベースレートは約 1.37%
（46/3358）である。precision（PPV）はこのエンリッチメントに最も敏感な指標であり——
リポジトリのベースレートでの真の正値予測率ははるかに低い（例: `touches_high_risk` で
約 5%）。感度（recall）と specificity はサンプリング比に対して不変であり、シグナル比較に
適切な指標である。precision によるシグナルの_ランキング_は依然として有効（固定 n では
尤度比について単調）だが、絶対値をベイズ事後確率としてコントリビューターに引用すべきではない。

`fast_revert_24h` と `self_reverted` は precision 100% だが**マージ後のシグナル**であり——
PR がすでにマージされ revert された後でしか観測できないため、トリアージゲートには使えない。
問題の存在を確認はできるが、防止には役立たない。

`critical_count > 0` は当初強いシグナルと考えられていた（PR #6866 のようなケーススタディで
ボットが正確に根本原因を指摘していた）が、regex を修正して `**[Critical]**` タグのみに
マッチさせ（「no critical blockers」のような本文中の単語 "critical" ではなく）、
precision は 28.6% に低下した。ボットは Critical 指摘を出しすぎる——コントロールグループの
PR の 16.7% にも Critical タグがある。

### 高リスクパスの定義

`touches_high_risk` シグナルは、変更されたファイルが以下のサブシステムパターンに
マッチするかチェックする:

- `openaiContentGenerator` — ストリーミングレスポンスのパース
- `streamingToolCallParser` — ツール呼び出しストリームのパース
- `geminiChat` — Gemini チャットパイプライン
- `acpConnection` — ACP プロセスの spawn
- `shell.ts` / `shellExecutionService` — シェルツール実行
- `mcp-client` / `mcp-pool` — MCP サーバー管理
- `LspServer` — LSP サーバー管理
- `acp-integration` — ACP セッション統合
- `relaunch.ts` — デスクトップアプリの再起動ライフサイクル
- `sandbox.ts` — サンドボックスプロセス管理
- `electron-run-as-node` — Electron の node モードエントリポイント（パスマッチ）

これらは、誤った変更が revert を要する観測可能なリグレッションを最も引き起こしやすいパスである。

### マージ→revert の時間差

有効な（負でない、マージ後の）時間差データを持つ 13 件の PR のうち:

- 中央値: 4 時間
- 24 時間以内: 61.5%
- 72 時間以内: 84.6%
- 最大: 97 時間

これは revert を引き起こす欠陥がマージ後すぐに表面化することを確認するが、
被害はすでに `main` に載っている。

### フリップフロップ PR

8 件の PR が複数回 revert された（revert → 再 revert のサイクル）。未解決の対立を示す:

- PR #6754（3 回の revert）、PR #6751（3 回の revert）、PR #3433（3 回の revert）
- PR #6869（2 回の revert）、PR #5668（2 回の revert）、PR #3567（2 回の revert）、
  PR #3478（2 回の revert）、PR #5060（2 回の revert）

これらのフリップフロップ PR は最もコストの高い結果である——複数回のレビュースタ、
複数回のマージ/revert サイクルを消費し、しばしばパッチリリースが必要になる。

## 設計

### 高リスクパスのエスカレーション

メンテナ以外の PR が高リスクパス（上記定義参照）のいずれかに触れる場合、Stage 1 トリアージは
その PR を通常パスではなく最も深いレビューティアにエスカレートする。これは PR を
ブロックもクローズも**しない**——完全な `/review` パイプラインが最大のエージェント
カバレッジで実行されることを保証する。

これはトリアージ時点で最も強いシグナルである: revert 済み PR 31 件中 10 件（感度 32.3%）が
これらのパスに触れており、コントロール PR 60 件中 5 件（specificity 91.7%;
Fisher p = 0.006）に対して有意。

実装: Stage 1e のスキルテキストが、トリアージモデルに高リスクパスパターンに対して
`gh pr view --json files | grep -E '...'` を実行するよう指示する。workflow の YAML 変更は
不要——検出は独立した workflow ステップではなくスキル内で実行される。

### 本設計がやらないこと

- **PR の自動クローズや自動リジェクトはしない。** ゲートはレビューの深さをエスカレートし
  メンテナの注目を推奨する; マージをブロックしたり PR をクローズしたりすることはない。
- **ボットの Critical 指摘をシグナルとして使わない。** データは precision 28.6% を示す——
  ボットは安全な PR の 16.7% にも Critical を付ける。Critical はゲートにするにはノイズが多い。
- **PR サイズ単独でフィルタリングしない。** `large_diff_gt_200` の precision は 37.0%——
  コンテキストのないサイズは予測力がない。
- **すべての PR に E2E 検証を要求しない。** `no_e2e` は識別力がない——コントロールグループも
  100% が E2E コメントを欠いており、このシグナルは revert されやすい PR と安全な PR を
  区別できない。

## PR #7414 との比較

|                     | PR #7414（挙動不変）         | 本設計（revert パターン）               |
| ------------------- | ----------------------------------- | ------------------------------------------ |
| シグナル              | 「diff が完全に挙動不変」 | 「高リスクパスに触れる」                  |
| revert の recall       | 未計測（比較できる revert がない）  | 32.3% (10/31)                              |
| specificity         | なし                                 | 91.7% (55/60)                              |
| 対象              | 無害な PR（コスト: 低）            | 危険な PR（コスト: 高）                 |
| 偽陽性コスト | 有用な PR のレビューをスキップ         | レビューの深さをエスカレート（追加レビュー時間） |

## 非ゴール / フォローアップ

- **ボットの Critical 改善。** 現在のボットの Critical 検出はノイズが多すぎる
  （precision 28.6%）。ボットが「未解決の Critical」と「解決済みの Critical」を
  区別できれば（指摘スレッドが解決済みとマークされたかチェックする）、このシグナルは
  有用になる可能性がある。これはトリアージゲートの変更ではなく、別のボット改善である。
- **期間を揃えたコントロールグループ。** 現在のコントロールグループは最近マージされた
  200 件の PR からサンプリングされているが、revert 済み PR は 2025〜2026 年にまたがる。
  期間を揃えたコントロールグループなら、より正確な偽陽性率が得られる。
  `gh pr list` API は深いページネーションをサポートしないため、GraphQL の
  カーソルベースフェッチが必要。
- **削除された 15 件の PR の回収。** revert 済み PR 46 件中 15 件は削除されており
  GitHub API からアクセスできない。そのパターンはエンリッチできた 31 件と異なる可能性が
  ある。回収経路は存在しない——GitHub は特定の状態のクローズ済み PR を完全に削除する。
- **フリップフロップ検出のリアルタイムゲート化。** 現在の分析はフリップフロップを
  回顧的に検出する（複数回の revert の後）。リアルタイム版は `main` 上の
  revert→再 revert パターンを監視しメンテナに警告する。これにはトリアージゲートではなく
  別の監視 workflow が必要。
- **高リスクパスリストの拡張。** 現在のリストは revert 済み PR のファイルパスから
  手作業でキュレートされている。コードベースの進化に伴い、新しい高リスクパスが
  現れうる。分析スクリプトの定期的な再実行でリストを最新に保てる。
