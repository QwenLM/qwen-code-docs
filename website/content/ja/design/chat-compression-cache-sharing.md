# チャット圧縮のキャッシュ共有

## 背景

チャット圧縮は現在、専用のシステム指示を持ち、メインセッションのツール宣言を持たないコールドな side query を送信し、会話をメディア削減コピーとして送信している。プロンプトキャッシュのキーがツールとシステム指示から始まるプロバイダーは、メインセッションのキャッシュ済みプレフィックスを再利用できない。

## 設計

以下すべてが真である場合、圧縮はまず特殊化されたシングルターンリクエストを試みる:

- 圧縮モデルが現在のメインモデルである;
- アクティブなプロバイダーが Anthropic または DashScope であり、キャッシュ制御が有効である;
- チャットに、見積もりのアンカーとなるプロバイダー報告のプロンプトトークン数がある;
- 実効プロンプトトークン数と、有界の圧縮出力リザーブの合計が、モデルのコンテキストウィンドウに収まる。

このリクエストは、サブエージェントが使用するリクエストごとのツールオーバーライドを含む、現在のターンの実効生成設定と、メディアを含む完全にキュレートされた履歴を使用する。リクエスト送信時には通常のモデルモダリティフィルタリングが適用されるため、サポートされているメディアは変わらないままであり、サポートされていないメディアは他のモデルリクエストと同じプレースホルダーを使用する。既存の圧縮指示は、最後の user メッセージとして追加される。このリクエストからの function コールを消費・実行するものは何もない。function コールを含むレスポンス、空のレスポンス、不正形式の状態スナップショット、またはリクエストエラーは破棄され、既存のコールドな side query を通じて 1 回だけリトライされる。そのメディア削減入力は、フォールバックが必要になったときにのみ遅延構築される。キャンセルはフォールバックをトリガーしない。

現在の `GeminiChat` を使用することで、リクエストはライブセッションのスコープに保たれる。プロセスグローバルなフォークキャッシュは、短い履歴の末尾しか保持せず、別の並行セッションに属している可能性があるため、意図的に使用しない。

個別のコンパクションモデルを使用するセッションは、そのキャッシュ識別子がメインセッションと異なるため、既存のパスにとどまる。メディアを含む履歴は、変わらないプロバイダー向けプレフィックスがメインセッションのキャッシュを再利用できるように、まず共有パスを使用する。

## 検証

ユニットテストは、正確な system、tools、完全な履歴、末尾の指示の構築、プロバイダー／モデルのゲート、共有パスでのメディア保持、ウィンドウの事前チェック、フォールバック後のメディア削減、ツールコールおよび不正形式レスポンスのフォールバック、キャンセルの挙動を検証する。プロバイダーのテストでは、メインターンと圧縮リクエストについて、シリアライズされたリクエストプレフィックスとキャッシュされたトークンの使用量を比較すべきである。
