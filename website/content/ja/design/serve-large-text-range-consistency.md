# Serve の大容量テキストレージ整合性

## Context

Serve は現在、`MAX_READ_BYTES` より大きいファイルから有限制限のテキストウィンドウをストリーミングする。行のみ、または maxBytes のみのリクエストではこのパスは有効にならない。ワークスペース境界はファイルを一度開き、そのハンドル経由で読み取り、ファイル全体のハッシュなしの部分メタデータを返す。

開いたファイルディスクリプタは inode を固定するが、inode のバイトを凍結するわけではない。Node は同じファイルを並行して変更するファイルシステム操作を同期もしない。そのため、リーダーは `open` 後に書き込まれたバイトを観測し得る。同じ inode とサイズのままでの上書きも含む。

Issue #7946 は、読み取り中に変更または置き換えられたファイルが引き続き拒否されることを要求する。追加許容の読み取りはその契約の一部ではない。

## Decision

大きなストリームウィンドウは、ファイルのオープン時 stat をスナップショットベースラインとして使用する:

1. 最初の `lstat` とオープン時の `fstat` は、同じデバイス、inode、サイズ、変更時刻（modification time）、変更時刻（change time）を持つ同じ通常ファイルを識別しなければならない。
2. ストリーミング後、`fstat` とパス名の `lstat` の両方がその識別情報とバージョンを保持しなければならず、パス名はシンボリックリンクであってはならない。
3. 呼び出し元はすべての読み取りと安定性チェックの後、`finally` でハンドルをクローズする。
4. これらの安定性チェックで検出された不一致は `hash_mismatch` を返す。

コンテンツ検証エラーは、読み取り後のチェックが完了するまでキャプチャされるため、デコードも失敗させる並行ミューテーションは依然として `hash_mismatch` を返す。ミューテーションがなければ、バイナリコンテンツは `binary_file` のまま、大きな非 UTF-8 テキストは変換ヒント付きの `file_too_large` のままである。

これは既存のフルスナップショット安定性ポリシーと一致する。並行する追加は意図的に拒否する: サイズの増大はオープン時のスナップショットが安定でなかったことを証明する一方、inode の識別情報だけでは元のプレフィックスが変更されていないことを証明できないためである。

信頼できる追加許容には、独立したスナップショット機構、または要求された行ウィンドウの位置特定と生成に使用されたすべてのバイトを検証する 2 回目の上限付き読み取りが必要になる。その追加 I/O とプロトコルポリシーはこのバグ修正の範囲外である。

## Range-reader cleanup

呼び出し元所有のファイルハンドルは常にストリーミングパスを選択する。そのため、個別の `forceStreaming` スイッチとハンドルバッファリングのファストパスは削除される。ハンドルのチャンクリーダーは、位置指定読み取りを呼び出し元がキャプチャしたファイルサイズに制限するため、読み取りがオープン時の EOF を超えることはなく、各チャンクはジェネレーターが進む前に同期的にデコードされるため、1 つの 512 KiB バッファを再利用する。

固定のスキャンバイトバジェットはない: 行オフセットにはバイトゼロからのスキャンが必要なため、深いウィンドウは引き続き O(ファイルサイズ) である。有限の行制限と `MAX_READ_BYTES` の上限が返却コンテンツとメモリを制限し、キャンセルは読み取り間でチェックされる。将来のスキャンコストポリシーには、有効な深いオフセットをサイレントに到達不能にするのではなく、カーソルまたはそれに相当する continuation 契約が必要である。

Serve のフルスナップショット読み取りは、デコードされたファイル全体から `lineEnding` を導出する。大容量ファイルのウィンドウパスは引き続き返却ウィンドウから導出するが、バイトカーソルページは返却スライス外のターミネーターもカウントする。それは再開の基準となるものであり、最初の行がバイトバジェットで切られている場合は再スナップショットが歩き越すものである。これにより、行末が均一なファイルにおいて、末尾の未終端ページはその前のページと一致し、バイト切り詰められたページはその後のページと一致する（行末混在ファイルではページ間で変わり得るし、均一ファイルの大容量ファイル行ウィンドウが同じバイトのバイトカーソルページと一致しない場合もある。パスの統合はフォローアップ候補であり、トラッキング issue はまだ存在しない）。Core はその他のコンシューマー向けにファイルレベルのメタデータを報告し続けられる。

すべての大容量ファイルウィンドウは、スキャンがたまたま EOF に到達しても `truncated: true` を保持する。この境界はそのフラグを使用して、ファイル全体ハッシュのないウィンドウを、ファイル全体コンテンツとして扱って安全な完全スナップショットと区別する。デコードされた文字が省略されたことのみを意味するわけではない。

## Consumers

すべての Serve 呼び出し元は、この境界に到達する前に選択されたワークスペースランタイムを通じて解決する:

- `GET /file`
- ACP HTTP `_qwen/file/read`
- 注入された ACP `readTextFile` アダプター

ワークスペースセットアップが使用するウィンドウなしの読み取りは、既存の 256 KiB フルスナップショット拒否を維持する。

## Verification

- 行末混在の大容量ファイル行ウィンドウは、返却スライスに存在する行末スタイルを報告する。バイトカーソルページは、返却スライス外のターミネーターも報告し得る（Decision 参照）。
- 並行する追加、切り詰め、パス名置き換え、シンボリックリンク置き換えは拒否される。同サイズの上書きは、変更が後続のタイムスタンプ量子に着地する場合に常に拒否される: チェックは modification time と change time を比較するため、modification time も復元する上書きは change time の進行によってのみ捕捉され、これはカーネルの粗い時計分解能でのベストエフォートであり絶対的な保証ではないが、それでも以前のサイズ + modification time のフルスナップショット比較よりは厳密に強い。
- ハンドル紐付きレンジ読み取りはフルバッファのファストパスを一切使用せず、ストリーミングバッファを再利用する。
- 10 MiB を超える深いオフセットが有限の行制限で成功する。
- 無制限、行のみ、maxBytes のみのリクエストは引き続き 256 KiB フルスナップショットゲートの背後にある。
- 既存の出力、エンコーディング、バイナリ、ハッシュ、行数の制限は変更されない。
