# ローカル実行と CI 実行で共通の単一 Autofix スキル

## 背景

Qwen Code には、すでに GitHub Actions で使用されているリポジトリ所有の Autofix スキルが存在する。これにはレビューフィードバックのトリアージと検証ルールが含まれ、ワークフロー側がスケジューリング、信頼フィルタリング、認証情報、GitHub への書き込み、ラウンドの予算を所有する。

ローカルの Autofix は、バンドルスキルや 2 つ目のメンテナンスエンジンを追加するのではなく、そのスキルを再利用すべきである。その入力はリモートのプルリクエストではなく、現在のワーキングツリーであり、ステージ済み、未ステージ、未追跡の変更がまとめてレビューされる。

## 設計

既存の `.qwen/skills/autofix/SKILL.md` が唯一の Autofix スキルのままとなる。これには 2 つのエントリーパスがある:

- 直接の `/autofix` 呼び出しは、現在のワーキングツリーを同期的にレビューして修正する。
- 既存の Actions ランナーは、`assess-candidates`、`develop-issue`、`address-review` のいずれかと、信頼されたワークフロー用意済みファイルを提供する。

ローカルパスは、既存の機械可読なレビューコマンドを繰り返し実行する:

```bash
env -u SANDBOX QWEN_SANDBOX=true "${QWEN_CODE_CLI:-qwen}" review run --approval-mode auto --effort high --json --quiet
```

このコマンドは管理されたバックグラウンドシェルとして実行され、より短いフォアグラウンドツールの制限ではなく、自身のタイムアウトが引き続き権威となる。Autofix は引き続き同期的にこれを待機する: インタラクティブ TUI はターミナルタスクの通知から再開し、ACP、stream-json、ヘッドレスセッションは、有界かつ増加する間隔でステータスのサイドカーを検査する。レビューの前後と収束の直前に取得するワーキングツリーのフィンガープリントにより、レビューの副作用や並行編集はすべて可視な `BLOCKED` 結果となる。

ネストしたヘッドレスレビューは、Qwen サンドボックス内で Auto 承認モードを使用する。Autofix は起動前に継承された `SANDBOX` マーカーをクリアし、封じ込めをバイパスできないようにする。承認クラシファイアやサンドボックスが利用できない場合は、不完全なレビューを生成し fail closed（失敗時は拒否）となる。起動前に、Autofix は、レビューがモデルの認証情報とネットワークアクセスを保持するサンドボックス化プロセス内でリポジトリ定義のチェックを実行する可能性があることを説明し、ユーザーがそのリポジトリを信頼することの明示的な確認を要求する。未追跡かつ無視対象外のファイルが存在する場合、Autofix はそれらの内容がレビューモデルのコンテキストに入る前に、それらも一覧表示する。非インタラクティブな実行は、確認が得られない場合に `BLOCKED` で停止する。Windows では、バンドルされたレビューワークフローが POSIX シェル構文を使用するため、ローカルの Autofix は Git Bash/MSYS を必要とし、ネイティブの cmd.exe と PowerShell はレビュー開始前に fail closed（失敗時は拒否）となる。

各完全なレビューの後、Autofix は発行されたレポートを読み取り、すべての所見をコードに対して検証し、最小の一貫した修正バッチを 1 つ適用し、最も狭い関連チェックを実行し、結果のワーキングツリーを再度レビューする。GitHub のポーリングや `/loop` の使用は行わない。

固定のローカルラウンド数はない。プロセスは証拠に基づいて停止する:

- `NO_CHANGES`: レビュー前にワーキングツリーがクリーンだった。
- `CONVERGED`: 上限なしの完全なレビューに実行可能な所見がなく、すべての必須チェックに合格した。
- `BLOCKED`: レビューの証拠が不完全である、必須チェックにスコープ内の安全な修正がない、またはメンテナー／プロダクトの決定が必要である。
- `STALLED`: 同じ実行可能な所見が新しい仮説なしに生き残っている、ワーキングツリーの進捗がない、または変更が発振している。

ローカルの Autofix は、ステージ、コミット、push、履歴の書き換え、インデックスの変更、GitHub への書き込みを一切行わない。ユーザーの既存のステージ状態はそのまま保たれ、修正は検査のためにワーキングツリーの変更として残される。

## ワークフローとの境界

GitHub Actions はすべての決定論的ポリシーを保持する: トリガー、認可、チェックアウト、信頼されたフィードバックの選択、リトライとラウンドの予算、watermark、コミット、push、コメント、最終ゲート。モデルの決定ポリシーのみがスキルに属する。特に、フィードバックを deferred とマークするのはワークフローであり、エージェントがそのセクションをどう扱わなければならないかを決定するのはスキルである。

## 却下された代替案

- バンドルされた Autofix スキルはリポジトリのスキルと競合し、モデルの契約を分裂させる。
- `on`、`off`、`status` は、ローカルの変更を修正するのではなく、リモートのワークフローを制御することになってしまう。
- 新しいウォッチャー、スケジューラー、ランタイムの状態機械は、既存のレビューと Actions のインフラストラクチャを重複させる。
- 固定のローカルラウンド上限は進行中のリペアを停止させてしまう可能性がある。進捗に基づく停止条件は、恣意的な総数を課すことなく、収束しない実行を有界にする。
