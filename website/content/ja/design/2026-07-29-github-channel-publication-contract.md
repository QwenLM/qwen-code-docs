# GitHub チャネルの公開契約

## ゴール

GitHub チャネルの返信を自動で公開しても安全にし、事後に追跡可能にする。チャネルは
アダプターを通じてエージェントの最終レスポンスのみを公開する; 中間の推論、ツール出力、
ストリーミングチャンクが GitHub コメントになることは決してない。

## 契約

- GitHub アダプターはブロックストリーミングを無効化し、受け入れられた各インバウンド
  イベントは最大 1 回の最終レスポンス配信試行のみを生成する。
- 最終配信は、陳腐化しうる共有セッションのターゲットではなく、アクティブなプロンプトの
  Issue/PR スレッドを使用する。
- チャネル指示は、エージェントにコメントやレビューの作成に `gh` や GitHub API を使わない
  よう伝える。公開配信はアダプターが所有する。
- トリムされた内容が `<no-reply/>` センチネルのみの最終レスポンスは意図的に抑制される。
  空白、大文字小文字、`/>` の前のスペース、単一のラッピングコードフェンスは正規化される;
  それ以外のコンテンツは変更されずに公開される。
- 抑制と公開は、`~/.qwen/channels/<workspace-scope>/<channel>-<name-hash>-github-audit.jsonl`
  のローカルな追記専用 JSONL 監査ファイルに記録される。レコードには時刻、チャネル、
  セッション、ソースメッセージ、スレッド、結果、存在する場合は GitHub コメントの
  identity/URL、返信の SHA-256 と文字数が含まれる。返信テキスト、認証情報、GitHub トークン
  は決して含まれない。
- 監査の書き込みはベストエフォート。監査の失敗は公開結果を変更せずにログに記録される。
  曖昧な GitHub API の失敗は配信失敗のままとなり、リトライしない; 明確な書き込みなし
  レスポンスはプライベートの配信 pending ファイルに書き込まれ、次回のチャネル起動時に
  リトライされる。

## フロー

1. GitHub アダプターは受け入れたイベントを `ChannelBase` にディスパッチする。
2. アクティブなプロンプトは、最終配信が完了するまでインバウンドメッセージと Issue/PR
   スレッドを利用可能なまま保持する。
3. エージェントは 1 つの最終レスポンスを返す。
4. アダプターは正確なセンチネルを抑制するか、1 つの Issue コメントを作成する。
5. アダプターは公開監査レコードを追記する。ターミナルのタスクライフサイクルは引き続き
   `ChannelBase` が所有する。
6. 最終配信が明確な書き込みなしレスポンスで失敗した場合、アダプターは最終テキストを
   プライベートなファイルパーミッションで
   `~/.qwen/channels/<workspace-scope>/<channel>-<name-hash>-github-pending-deliveries.json`
   に保存し、再起動後にエージェントを再実行せずにリトライする。

## 非ゴール

- 曖昧な公開失敗のリトライ、ステータスコメントの作成、レスポンスストリーミングの有効化は
  しない。これらは issue #8012 の別部分。
- 直接の `gh`/API 公開に対する指示はエージェントへの運用上の境界であり、サンドボックスの
  強制ではない。ツールレベルの GitHub 書き込み制限の強制はランタイムのパーミッション
  モデルの管轄。
- 配信 pending の保持ポリシー（最大試行回数、最大経過期間、サイズ上限、stale な返信の
  処理、孤立テンポラリファイルのクリーンアップを含む）は #8142 で別途追跡する。

## 検証

フォーカスされた GitHub アダプターテストは、センチネル抑制、通常の最終コメント配信、
返信テキストを含まない監査フィールド、非ブロッキングな監査書き込み失敗をカバーする。
既存のルーティングと配信のテストは変更なし。
