# Ripgrep ランタイム信頼性の実施計画

## 1. 背景と決定

ripgrep が欠落している場合、Qwen Code はすでに主要なフォールバックチェーンを提供している:

```text
内置 ripgrep -> 系统 ripgrep -> GrepTool
                                 -> git grep
                                 -> 系统 grep
                                 -> JavaScript 文件遍历
```

残りの高 ROI な作業は、ランタイム結果の完全性を保証することであり、もう 1 つのバイナリ依存や別の汎用フォールバック層を導入することではない。本計画では、以下の 4 つの関連する改善を、明確な境界を持つ 1 つの変更として実施する:

1. ripgrep がスレッド生成により `EAGAIN` エラーを起こしたことが確認できた場合、シングルスレッドモードで 1 回だけリトライする。
2. stdout と stderr の両方が空である場合にのみ、終了コード 1 を「マッチなし」と解釈する。
3. 検索が完全に実行されなかった場合と通常の出力切り詰めを区別し、不完全な検索を「マッチなし」として決して報告しない。
4. プライバシーに関わらないランタイムリカバリーのテレメトリーを記録し、実際の効果を測定する。

### スコープ外

- `@vscode/ripgrep` は導入しない。Qwen Code はすでにプラットフォームごとのバイナリをパッケージに同梱している。
- 現在の「内置バージョン優先、システムバージョン次点」の選択順序は変更しない。
- ripgrep のスレッド数を恒久的には下げない。
- すべてのランタイム失敗の後に自動的に `GrepTool` へ切り替えることはしない。パーミッション、引数、ファイルシステムのエラーは可視のままにしなければならず、セマンティクスが異なり低速な検索の裏に隠してはならない。
- Node.js の子プロセス起動段階の `EAGAIN` はリトライしない。まだ起動に成功していないプロセスは ripgrep の `--threads 1` 引数の恩恵を受けられない。この種の問題は引き続き明確な `spawn` 失敗として扱うべきである。

## 2. 変更の目的と前後の動作

本変更は検索を「決して失敗しない」ようにするためではなく、Qwen Code が次の 3 つの事実を正確に区別できるようにするためである: 本当にマッチが存在しない、検索が失敗し利用可能な結果がない、検索は失敗したが部分的な結果が得られた。モデルは正しい事実を見て初めて、検索範囲を狭めるか、別のツールに切り替えるか、それとも既存の部分結果を使い続けるかを判断できる。

### 2.1 EAGAIN のシングルスレッドリトライ

**変更の目的:** リソースが制限されたコンテナや CI 環境では、ripgrep プロセスは起動に成功したものの、必要なワーカースレッドを生成できない場合がある。このとき検索ロジックと引数自体には問題がなく、並列度を下げれば通常は検索を完了できる見込みがある。リトライは確認できたスレッド生成失敗のみを対象とし、引数エラー、パーミッションエラー、子プロセス起動失敗を回復可能な問題として誤って扱わないようにする。

**変更前:** `RipGrepTool` は `--threads 4` を固定で渡す。`runRipgrep()` は EAGAIN に遭遇してもリトライしない。そのエラーがまず終了コード 1 の分岐でマッチなしと解釈されず、かつ stdout がない場合、ツールはモデルに明確な grep エラーを返す。すでに stdout が生成されている場合、後続のロジックはそれらの部分結果を使い続ける可能性があるが、今回の検索が EAGAIN により早期終了したことは説明されない。

```text
rg --threads 4
  -> スレッド生成失敗
  -> リトライしない
  -> 終了コード 1: マッチなしとみなされる
  -> その他のエラーで stdout なし: エラーを返す
  -> stdout あり: 完全な結果として使われる可能性がある
```

**変更後:** stderr により ripgrep 内部のスレッド生成 EAGAIN であることが確認でき、かつリクエストがまだキャンセルされていない場合にのみ、現在の呼び出しの `--threads 4` を `--threads 1` に置き換えて 1 回リトライする。リトライが成功すれば完全な結果を返す。リトライも失敗した場合はエラーまたは明確にマークされた部分結果を返す。後続の検索は引き続き 4 スレッドを使用し、一時的な 1 回の障害で恒久的に速度が落ちることはない。

```text
rg --threads 4
  -> スレッド生成 EAGAIN を確認
  -> rg --threads 1、1 回のみリトライ
     -> 成功: 完全な結果を返す
     -> 失敗で stdout なし: 明確なエラーを返す
     -> 失敗だが stdout あり: 明確にマークされた部分結果を返す
```

### 2.2 終了コード 1 のマッチなし判定の厳格化

**変更の目的:** Qwen Code が、エラーメッセージや異常な出力を伴う終了コード 1 を、一律に「リポジトリにその内容は存在しない」と解釈してしまうことを防ぐ。「マッチなし」はモデルの後続の推論に影響する強い結論であり、ripgrep が実際に正常にマッチなしを表明している場合のみ使用できる。

**変更前:** `runRipgrep()` は `error.code === 1` を確認すると即座に空の stdout を返し、今回の呼び出しが保持する stdout と stderr を破棄する。終了コード 1 にエラーメッセージが伴っていても、モデルは最終的に `No matches found` を見ることになる。

```text
終了コード 1 + 空の stdout + 空の stderr -> No matches found
終了コード 1 + 空でない stderr           -> No matches found
終了コード 1 + 空でない stdout           -> stdout は破棄され、No matches found
```

**変更後:** 終了コードが 1 かつ stderr が空の場合のみ、正常なマッチなしの結果を返す。終了コード 1 で stderr が空でない場合は実行失敗として扱う。stdout は判定に関与しない: ripgrep の終了コード 1 はマッチ結果を伴うことがあり得ず、`--json` モードではゼロマッチでも stdout の末尾に summary イベントが出力される。

```text
終了コード 1 + 空の stderr   -> No matches found
終了コード 1 + 空でない stderr -> 明確な実行エラー
```

### 2.3 切り詰め結果と不完全実行結果の区別

**変更の目的:** 「出力長を抑えるために一部のみを表示した」と「基盤の検索が実行しきらなかった」がまったく別のことだとモデルに知らせる。前者は、完全な検索にそれらのマッチが存在することの証拠になり得る。後者は、他のファイルにマッチがないことの証拠には使えない。

**変更前:** `runRipgrep()` は `truncated` を、タイムアウト、最大バッファー超過などの基盤的な終了状況を表すのに使い、`RipGrepTool` はそれを行数・文字数制限と統合して表示する。エラーが発生したがすでに stdout が生成されている場合、ツールは stdout が空の場合のみスローし、空でない stdout は引き続きパースされる。それは通常の結果として現れることもあれば、`(truncated)` として現れることもあり、stdout が空の場合や有効なマッチがパースされなかった場合には 2 つの `No matches found` 分岐に入ることさえある。モデルは検索が本当に完了したかを信頼して判断できない。

**変更後:** 表示側の積極的なトリミングには `truncated` のみを使用する。タイムアウト、最大バッファー超過、その他の実行エラーによる早期終了には `incomplete` を使用する。処理順序は、まず実行の完全性を判定し、その後で有効なマッチの有無を判定する:

| 変更後の実行結果             | モデルが目にする結果                           | モデルが導ける結論                                 |
| ---------------------------- | ---------------------------------------- | -------------------------------------------------- |
| 完全実行でマッチなし         | `No matches found`                       | 今回の検索範囲にマッチはないと判断できる                   |
| 完全実行だが表示内容が上限超過       | 結果 + `(truncated)`                     | 検索は完了しており、すべてのマッチ行を表示していないだけ                   |
| 不完全実行で有効なマッチなし   | 明確な検索未完了エラー                     | リポジトリにマッチがないとは言えず、検索を調整するか他の方法に切り替えるべき |
| 不完全実行だが有効なマッチあり     | 部分結果 + `(incomplete)` と固定の警告     | 返されたマッチは使用できるが、それをもって他の場所を除外できない     |
| 表示のトリミングと実行未完了が同時発生 | `(truncated)` と `(incomplete)` を同時表示 | すべての得られた結果を表示してもおらず、基盤の検索も完了していない       |

### 2.4 ランタイムリカバリーのテレメトリー

**変更の目的:** EAGAIN リトライと結果の完全性保護が、実際の環境でどの程度の頻度で発生し、成功率と失敗タイプがどうであるかを測定し、より複雑なランタイムフォールバック能力への投資を続ける価値があるかをデータで判断できるようにする。同時に、ユーザーの検索内容やリポジトリ情報の収集は避ける。

**変更前:** 既存の `RipgrepFallbackEvent` は、起動時のプローブが失敗し Qwen Code が `RipGrepTool` から `GrepTool` へ切り替わったときにのみ送信される。起動後に発生した EAGAIN、タイムアウト、最大バッファー超過、異常終了、spawn 失敗には専用の構造化指標がないため、「ランタイムリカバリーは本当に役立つのか」に答えられない。

**変更後:** セマンティクス的に独立した `RipgrepRuntimeRecoveryEvent` を新設し、リトライが発生した場合または最終実行が異常だった場合のみ送信する。イベントには内置/システムバイナリの選択、リトライがトリガーされたか、リトライが成功したか、固定の失敗分類を記録するが、検索式、パス、stdout、stderr、ファイル名、生のエラーメッセージは記録しない。正常に成功した検索ではイベントを送信せず、無意味なログ量の増加を避ける。

### 2.5 単一決済の保護

**変更の目的:** 新たに追加するリトライロジックが高々 1 回だけ実行されることを保証する。`execFile` のコールバックと子プロセスの `error` イベントは、同じ 1 回の起動失敗に対して前後して到着し得る。2 つのチャネルがそれぞれリトライを決定すれば、2 つのシングルスレッド検索が起動してしまう可能性がある。

**変更前:** 2 つのチャネルとも同じ Promise の解決を試み得る。Promise は最初の決済のみを受け入れるため、現在はリトライロジックもないので、通常ユーザーに見える重複実行は起きないが、この構造はリカバリー分岐を直接追加するのに適していない。

**変更後:** 単一実行ヘルパーは共有の決済ガードを使用し、1 つの構造化実行結果のみを生成する。外側のロジックはその結果を待ってからリトライするかどうかを決定しなければならず、そのため 1 回の検索につき高々 1 回のリカバリー呼び出ししか起動されない。

### 2.6 全体の動作変化

```text
変更前
rg を実行
  -> code 0: 結果を処理
  -> code 1: 一律にマッチなしとみなす
  -> その他のエラーで stdout なし: エラーを返す
  -> その他のエラーで stdout あり: 完全または切り詰められた結果として処理を続ける可能性がある

変更後
rg を実行
  -> code 0: 完全な結果を処理
  -> code 1 + stdout/stderr とも空: マッチなしを確認
  -> スレッド EAGAIN を確認済み: シングルスレッドで 1 回リトライ
  -> 最終的に失敗で stdout なし: 明確なエラーを返す
  -> 最終的に失敗だが stdout あり: 利用可能なマッチを保持し incomplete とマーク
  -> キャンセル以外の最終異常またはリカバリー: 検索内容を含まない構造化テレメトリーを送信
```

## 3. 満たすべきランタイムセマンティクス

### 3.1 単一実行結果

`packages/core/src/utils/ripgrepUtils.ts` 内の `runRipgrep()` をリファクタリングし、内部の単一実行ヘルパーを抽出する。このヘルパーは、既存の 20 MB バッファー、プラットフォーム依存のタイムアウト、`AbortSignal`、部分 stdout、および不完全である可能性のある最終行の除去などの挙動を保持しなければならない。

このヘルパーは 1 回だけ決済されることを保証しなければならない。`execFile` はコールバックと子プロセスの `error` イベントの両方を通じて起動失敗を報告し得るため、コールバックとイベント処理は同じ決済ガードを共用しなければならない。最初のヘルパー呼び出しが返った後でのみリトライするかどうかを決定できる。いずれの完了チャネルも直接リトライを開始してはならない。

固定され、機微な情報を含まない値で失敗を分類する:

```typescript
type RipgrepFailureKind =
  | 'eagain'
  | 'timeout'
  | 'max_buffer'
  | 'exit'
  | 'spawn';
```

キャンセル操作はランタイム失敗のテレメトリーには属さず、リトライをトリガーしてもならない。

### 3.2 マッチなしの判定

以下の 2 つの条件が同時に成立する場合のみ、その呼び出しを「成功裏に完了したがマッチなし」と解釈する:

```text
終了コード === 1
stderr.trim() === ''
```

ripgrep の終了コードの約束: 0 = マッチあり、1 = マッチなしでエラーなし、2 = エラー発生。終了コード 1 はマッチ結果を伴うことがあり得ないため、stdout をチェックする必要はない。`--json` モードでは、ripgrep はゼロマッチでも stdout の末尾に `summary` イベントを出力するため、stdout が空かどうかは判定基準にできない。

終了コードが 1 で stderr が空でない場合は、実行失敗に属する。

### 3.3 EAGAIN リカバリー

以下のすべての条件が同時に成立する場合のみ、1 回リトライする:

- 現在が最初の実行であり、リトライではない。
- リクエストはまだキャンセルされていない。
- stderr により ripgrep 内部のスレッド生成失敗であることが確認できる: 短いマーカー `os error 11` にマッチするか、またはスレッド生成のコンテキストと完全なリソース不可のエラーメッセージが同時に存在することを要求する。汎用的なリソース不可の文言のみのマッチであってはならない。
- 既存の引数リストが現在の `--threads 4` 引数ペアを含んでいる。

リトライ時にはスレッド数の値を `1` に置き換える。遅延を追加せず、実際の必要のない他の引数の書き方はサポートせず、後続の検索のためにシングルスレッドモードを永続化もしない。リトライ成功後は完全な成功結果を返し、最初の試行が発生させたエラーや不完全な状態は保持しない。

### 3.4 完全、切り詰め、不完全実行

以下の 3 つの状態を明確に区別する:

- **完全（Complete）:** ripgrep が正常に実行を完了した。
- **切り詰め（Truncated）:** Qwen Code が表示のために、元々完全だった出力を行数または文字数で積極的に制限した。
- **不完全実行（Incomplete）:** ripgrep が stdout を生成した後に実行エラーで終了した。タイムアウトや最大バッファー超過による終了を含む。既存のマッチはリポジトリ検索結果の一部に過ぎない。

`RipgrepRunResult` を拡張し、生の stderr やエラーテキストではなく構造化メタデータを使用する:

```typescript
interface RipgrepRecoveryMetadata {
  selectionMode: 'builtin' | 'system';
  retryTriggered: boolean;
  retrySucceeded?: boolean;
  failureKind?: RipgrepFailureKind;
}

interface RipgrepRunResult {
  stdout: string;
  incomplete: boolean;
  error?: Error;
  recovery: RipgrepRecoveryMetadata;
}
```

実装時には具体的な構造をさらに簡略化してもよいが、utility の結果は引き続き現在の `truncated` フィールドでタイムアウトや最大バッファー超過の失敗を表さなければならない。表示側の切り詰めは `RipGrepTool` が計算する。utility は実行未完了の状態とリトライ結果の報告を担当する。リカバリーのメタデータには、検索式、検索パス、stdout、stderr、生のエラーメッセージを含めてはならない。

`packages/core/src/tools/ripGrep.ts` では、まず実行が完全かを判定してからでなければ、既存の 2 つの `No matches found` 分岐に入ってはならない:

| 実行結果                                  | ツールの動作                                         |
| ----------------------------------------- | ------------------------------------------------ |
| エラーが発生し stdout なし                     | 明確な grep 実行エラーを返す                         |
| エラーが発生し stdout あり、ただし有効なマッチがパースされなかった | 明確な検索不完全実行エラーを返す。決してマッチなしは返さない |
| エラーが発生し少なくとも 1 つの有効なマッチをパースできた        | 部分マッチを返し、固定の案内で検索が未完了であることを説明する     |
| 完全に実行されたが有効なマッチなし                  | 既存のマッチなし結果を返す                           |

部分結果は `returnDisplay` で `(incomplete)` を使用し、LLM に固定の案内を出力する。例: `検索未完整执行：以上结果可能未包含所有匹配项。` 通常の結果数の制限は引き続き `(truncated)` を使用する。これら 2 つのラベルは同時に存在し得るが、互いに置き換えることはできない。実行失敗時には、現在のような誤解を招きやすい `[0 lines truncated]` という案内を生成し続けてはならない。

## 4. ランタイムテレメトリー

独立した `RipgrepRuntimeRecoveryEvent` を新設する。`RipgrepFallbackEvent` は再利用しない。後者は起動段階に登録されたツールが `RipGrepTool` から `GrepTool` へ切り替わったことを専ら表す。

リトライが発生した場合または最終実行が異常だった場合のみ新しいイベントを送信する。必須フィールドは以下の通り:

```typescript
selection_mode: 'builtin' | 'system';
retry_triggered: boolean;
retry_succeeded?: boolean;
failure_kind: 'eagain' | 'timeout' | 'max_buffer' | 'exit' | 'spawn';
```

検索式、パス、stdout、stderr、生のエラーメッセージ、ファイル名を記録してはならない。リカバリーを行わなかった正常に成功した検索では新しいイベントを送信しない。

`ripgrepUtils.ts` は引き続き `Config` とテレメトリーに依存しない。リカバリーのメタデータを返すのみとする。`Config` を保持する `RipGrepTool.performRipgrepSearch()` が、部分結果を返すか最終エラーをスローする前にイベントを送信する。

既存のテレメトリー層を通じてこのイベントを接続する:

- `packages/core/src/telemetry/types.ts`
- `packages/core/src/telemetry/constants.ts`
- `packages/core/src/telemetry/loggers.ts`
- `packages/core/src/telemetry/qwen-logger/qwen-logger.ts`
- `packages/core/src/telemetry/index.ts` 内のテレメトリー公開エクスポート

既存の Qwen logger と OpenTelemetry のログパスをカバーする。独立した Clearcut 統合を追加で設計する必要はない。

## 5. 実施順序

1. 単一実行ヘルパーを追加し、`execFile` をモックする集中ユニットテストの枠組みを整える。子プロセスの `EventEmitter` と単一決済の挙動を含む。
2. 終了コード 1 の判定を厳格化し、失敗分類を追加する。この時点ではリトライの挙動はまだ変更しない。
3. 確認済みのスレッド EAGAIN に対する 1 回だけのリトライを追加し、`--threads 4` を `--threads 1` に置き換える。
4. 構造化された `incomplete` とリカバリーのメタデータを `runRipgrep()` から `RipGrepTool` へ渡す。
5. 2 つのマッチなし判定箇所を更新し、それぞれ不完全実行と切り詰めの案内を描画する。
6. ツール層に独立したランタイムリカバリーテレメトリーイベントを追加・接続する。
7. 集中検証を実行し、その後リポジトリが要求する build、typecheck、自己レビューのプロセスを実行する。

これらのステップを互いに独立に保つことで、リグレッション問題の迅速な特定に役立ち、テレメトリーの作業がコアの結果セマンティクス変更を覆い隠すことも避けられる。

## 6. テスト計画

### `packages/core/src/utils/ripgrepUtils.test.ts`

Vitest の hoisted mock で `node:child_process` をモックし、以下をカバーする:

- 終了コード 1 で stdout と stderr がともに空の場合、完全なマッチなし結果が得られる。
- 終了コード 1 で stderr が空でない場合、`exit` 失敗が得られる。
- 終了コード 1 で stdout が空でない場合、stdout が保持され不完全実行とマークされる。
- スレッド EAGAIN を確認後 1 回リトライし、`--threads 1` で正常に完了する。
- スレッド EAGAIN を確認後 1 回リトライするが、リトライはなお失敗する。
- リトライは既存のスレッド数のみを置き換え、呼び出し元が渡した引数配列は変更しない。
- `AbortError`/`ABORT_ERR` はリトライをトリガーしない。
- 子プロセス起動段階の `EAGAIN` はリトライをトリガーせず、`spawn` に分類される。
- タイムアウトと最大バッファー超過時、部分出力は不完全である可能性のある最終行を除去する。
- コールバックと子プロセスの `error` イベントが重複決済や 2 回リトライの開始を引き起こさない。

### `packages/core/src/tools/ripGrep.test.ts`

ツールの呼び出し元に向けたセマンティクスをカバーする:

- 完全な実行で空の出力が発生した場合、なお `No matches found` を返す。
- 不完全実行だが有効なマッチを含む場合、それらのマッチと明確な未完了の案内を返す。
- 不完全実行の stdout から有効なマッチが 1 つもパースされなかった場合、`No matches found` ではなく不完全実行エラーを返す。
- エラーが発生し stdout がない場合、なお明確な grep 実行エラーを返す。
- 切り詰めと不完全実行のラベルは独立を保ち、同時に存在し得る。

### テレメトリーテスト

logger と Qwen logger のテストを拡張し、以下を検証する:

- リトライ成功イベントには、選択モード、トリガー状態、成功状態、EAGAIN 分類が含まれる。
- 最終異常結果には固定の失敗分類が含まれる。
- 正常に成功した検索はランタイムリカバリーイベントを生成しない。
- OpenTelemetry のイベント名、body、Qwen logger の属性が正しい。
- イベント内に検索式、パス、stdout、stderr、生のエラーフィールドが存在しない。

## 7. 検証と受け入れ条件

`AGENTS.md` の要求に従い、対応する package またはリポジトリの位置から実行する:

```bash
cd packages/core && npx vitest run src/utils/ripgrepUtils.test.ts
cd packages/core && npx vitest run src/tools/ripGrep.test.ts
cd packages/core && npx vitest run src/telemetry/loggers.test.ts
npm run typecheck
npm run build
```

実装が `loggers.test.ts` 以外の Qwen logger 専用テストを変更した場合、対応する集中テストファイルも実行する必要がある。

以下の条件を満たした場合のみ、変更が完了したとみなせる:

- 1 回確認された ripgrep のスレッド EAGAIN は、高々 1 回のシングルスレッドリトライをトリガーする。
- キャンセル操作と子プロセス起動失敗は決してそのリトライをトリガーしない。
- 終了コード 1 かつ stderr が空の場合のみ、マッチなしを表す（stdout はチェックしない）。
- いかなる不完全実行パスも、2 つの `No matches found` 返却分岐に入ってはならない。
- 部分マッチはモデルにとって依然として有用だが、不完全実行として明確にマークしなければならない。
- テレメトリーはリカバリー状況を測定できると同時に、検索内容やリポジトリ内容を収集しない。
- 集中テスト、typecheck、build がすべてパスする。
- リポジトリの要求に従い完全な diff の自己レビューを行い、最後の修正後に問題なしのチェックを 2 回連続で完了する。

## 8. コスト、効果、ロールバック

実施コストはテストとテレメトリー接続を含め、約 1.5〜3 エンジニア日と見込む。この範囲は、汎用のランタイムフォールバックリファクタリングよりも意図的に小さく抑えてある。

直接的な効果は以下を含む:

- ripgrep が通常の数のワーカースレッドを生成できない場合、リソースが制限された CI やコンテナ環境で検索をリカバリーできる。
- 終了コード 1 にエラーが伴う際の偽陰性を排除する。
- 部分的な検索結果が完全なリポジトリの証拠であるかのように装う問題を排除する。
- 他のリカバリー能力への投資を続ける価値があるかを判断するための本番データが得られる。

ロールバックの範囲は局所的である: バイナリの選択や既存の起動時フォールバックロジックを変更することなく、リトライ分岐とランタイムイベントを削除できる。リトライ自体をロールバックする場合でも、より厳格なマッチなし判定と不完全実行のセマンティクスは保持すべきである。それらによる正しさの保護は、EAGAIN の実際の発生頻度とは無関係だからである。

## 9. 取り込んだレビュー意見

1 名のサブエージェントが、現在のリポジトリソースコードに基づき本計画をレビュー済みである。そのレビューは初期ドラフトに対して以下の実質的な調整を行った:

- 起動時フォールバックのテレメトリーを再利用せず、独立したランタイムイベントに変更
- テレメトリーの送信位置を utility 層から `RipGrepTool` に移動
- 子プロセス起動段階の `EAGAIN` に対する投機的な遅延リトライを削除
- EAGAIN 検出を確認済みのスレッド生成失敗に絞り込み
- 現在発生し得ないスレッド引数の欠落や他の引数の書き方のサポートを削除
- `incomplete` と `truncated` を区別
- 2 つのマッチなし分岐の前に実行の完全性のチェックを要求
- 終了コード 1 のマッチなし判定は stderr が空であることによることを要求（stdout はチェックしない）
- 単一決済と有効マッチゼロのリグレッションテストを追加
- 将来の実施検証に必要なリポジトリの build ステップを復元
