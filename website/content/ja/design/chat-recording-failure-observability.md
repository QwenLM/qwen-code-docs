# チャット記録の失敗の可観測性

## 背景

`ChatRecordingService` は、最初の非同期 JSONL 書き込み失敗の後、書き込みの受け入れを永続的に停止する。トランスクリプトは引き続き有効なプレフィックスであるが、独立したシグナルがなければ、ユーザーやリモートクライアントは、後続のメッセージもまだ記録されていると誤って想定してしまう可能性がある。

## コアライフサイクル

`Config.onChatRecordingFailure()` は、プロセスローカルの購読境界である。`Config` によって作成された各 recorder は、最初の非同期書き込み失敗を、登録されたリスナーのスナップショットへ転送する。イベントは、失敗したレコードのセッション ID と正規化された `Error` を運び、リスナーの失敗は writer の promise から隔離される。購読は recorder の置き換えをまたいで存続し、それぞれの disposer によって独立して削除される。`Config.shutdown()` は、recorder の最終化とフラッシュを通じてリスナーを存続させ、その後クリアする。

同期的な会話ファイル作成の失敗は、recorder が永続的な失敗状態に入っておらず、後続の呼び出しがリトライする可能性があるため、イベントを発行しない。失敗した recorder は 1 回だけ発行する。スキップされた子孫、後続の追記、繰り返しのフラッシュは再発行しない。

## ローカル CLI のサーフェス

TUI とテキスト出力は、ファイルシステムのパス、errno 値、基盤となるエラーを含まない、汎用的で対処可能な警告を描画する。JSON、stream-json、デュアル出力は `system/session_recording_degraded` メッセージを発行し、そのトップレベルとペイロードのセッション ID はどちらも、現在の `Config` セッションではなく、失敗イベントから取得される。

ワンショットの構造化出力は recorder を最終化し、終端結果を発行する前に最大 2 秒間そのフラッシュを待機する。長期間存続する stream-json セッションは 1 回だけ購読し、ターン間に最終化せずにフラッシュし、セッションのシャットダウン時のみ最終化する。タイムアウトは応答性を保つためのものであり、基盤となる書き込みをキャンセルするものではない。

## デーモンプロトコルと耐久性のあるライブ状態

ACP 子プロセスは、プロトコルバージョン 1、影響を受けるセッション ID、`reason: "write_failed"` を含む `qwen/notify/session/recording-degraded` を送信する。ブリッジはペイロードを検証し、`session_recording_degraded` を公開し、ライブセッションエントリを degraded（degradation 状態）としてマークする。エントリの登録前に到着した通知は、既存の有界な早期イベントバッファーを使用する。バッファーの drain は、リプレイリングとエントリ状態の両方を更新する。

`session_snapshot.recordingDegraded` は、ライブイベントがリプレイリングから去った後もその状態を保持する。これはデーモンのメモリ内状態のみである: デーモンの再起動は新しい recorder を作成し、健全な状態で開始する。このイベントは `EVENT_SCHEMA_VERSION = 1` のもとで追加的であり、capability の変更は不要である。

## SDK と WebUI

SDK はライブイベントと任意の snapshot フィールドを検証する。セッションリデューサーは、ライブイベントを再同期に対して安全な sticky な更新として扱う。snapshot フィールドが存在する場合はそれが権威であり、フィールドが存在しない場合は、古いデーモンとの互換性のために状態が保持される。

UI ノーマライザーは、どちらの degraded 表現も同じ回復可能な記録エラーにマップする。WebUI は明示的な通知 ID `daemon.session_recording_degraded:<sessionId>` を使用するため、リプレイされたイベントの後に snapshot が続いても冪等である。通知を閉じると現在のインスタンスが削除される。後続の snapshot により、依然としてアクティブなリスクが再び表示される場合がある。

## クローズ境界

正常なフラッシュを要求する厳格なクローズパスは、フラッシュが失敗した場合でもデーモンエントリを存続させ、イベントを配信可能なままにする。既存のベストエフォートなクローズ順序は変更なし: 遅延した失敗が発見された時点でその EventBus がすでにクローズされている場合、その失敗を保持するのはデバッグログのみである。

## 非ゴール

この設計は、書き込みのリトライ、degradation 状態の recorder の復旧、JSONL の内容や親リンクの変更、fsync の追加、生のファイルシステムエラーの公開、プロセス間での競合する writer の調整を行わない。
