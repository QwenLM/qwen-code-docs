# ライブジャーナル切り詰めからの復旧

## Context

デーモンは、未完了のターンに対して上限付きのインメモリライブジャーナルを保持する。ジャーナルが 10,000 イベントまたは 8 MiB を超えると、最古のリプレイイベントを破棄し、先頭に `history_truncated` マーカーを付加する。永続化されたトランスクリプトとターン境界のコンパクションが引き続き権威であるため、正式な終端イベントの後にはターン全体が再び利用可能になる。

以前、このマーカーには prompt の所有情報がなく、SDK は汎用メッセージを表示し、WebUI はマーカーを履歴ページネーションの背後に隠すか、保持された末尾を恒久的に表示したままにしていた。この設計は、既存のリソース制限とエビクションポリシーを維持しつつ、喪失を正確にし、追加のモデルリクエストなしに見える末尾を修復する。

## Protocol and SDK

`session/load` が返すライブジャーナルマーカーについて、ブリッジはセッションの権威ある `activePromptId` をオプションの `promptId` としてマーカーエンベロープにコピーする。永続化イベントとイベントスキーマバージョンは変更しない。このフィールドを持たない古いデーモンは、保持されたライブイベントに prompt ID がちょうど 1 つ存在する場合のみ修復可能である。

`DaemonHistoryTruncatedData` は既存のオプションフィールド `scope` と `maxEvents` を公開する。検証は不正な形式のオプション値を拒否する。正規化されたステータスデータはデーモンペイロード全体を保持する。テキストはリプレイ履歴の切り詰めとライブターンの切り詰めを区別し、最新のイベントが保持され古いリプレイイベントが破棄されたことを述べ、`fullTranscriptAvailable` が true の場合のみ終端後の復旧を約束する。

## WebUI recovery episode

スナップショットのリプレイ中、修復可能なライブマーカーはマーカーの直前にエピソードチェックポイントを作成する。チェックポイントは不変のトランスクリプトブロックを再利用し、セッション ID、対象の prompt ID、スナップショットイベントの watermark、マーカーブロック ID、決定的なエピソード署名を保持する。マーカーがアクティブな間、古い履歴ページとプロバイダーローカルのステータスブロックはチェックポイントへミラーリングされる。

対応する `turn_complete` または `turn_error` のみが復旧をアームする。キャンセルは、cancelled の停止理由を持つ正式な終端イベントとして表現され、同じパスに従う。バッファされたトランスクリプトイベントはフラッシュされ、復旧の試行前に prompt 状態が確定される。実行中のセッションロード、履歴ページリクエスト、ナビゲーション、ローカル prompt は、次のアイドル時点まで試行を遅延させる。

復旧は、インメモリリプレイで設定された履歴ページサイズなしの、同一セッション `session/load` を 1 回実行する。現在のトランスクリプトは、検証が成功するまでアタッチされ見えるままになる。新しいスナップショットは degradation していてはならず、対象 prompt のユーザー入力と対応する正式な終端の両方を含まなければならない。検証またはリトライ可能なトランスポートの失敗は置き換えを拒否し、以前のセッションハンドルをその SSE カーソルから再開し、トランスクリプトを保持し、修復可能な `daemon.live_journal_repair.failed` 通知を 1 回発行する。認証失敗とセッション欠落もトランスクリプトを保持して通知を発行するが、その SSE ストリームは安全に再開できないため、プロバイダーの既存の切断または再認証状態を維持する。

成功時、WebUI は最初に対応するユーザー入力から新しいスナップショット末尾までを対象のサフィックスとして再構築する。マーカーブロックがまだ保持されている場合はチェックポイントから開始し、それ以外は上限付きのフルスナップショットを再構築する。リプレイされたイベントは `assistant.done` を含めトランスクリプト状態を再構築するが、エピソードの watermark 以下のイベントは、通知、ワークスペースシグナル、保留中 prompt の公開、フォローアップ公開、その他の副作用を繰り返さない。より新しいイベント ID は通常の効果を保持する。

結果の状態は 1 回のストアリセットでコミットされる。完全なサフィックスがチェックポイントの `maxBlocks` に収まる場合、保持された履歴ブロック ID、ページネーションカーソル、読み込み済み深度、容量状態は安定したままである。その制限を超える場合、既存のストアポリシーは、無制限の修復例外を作るのではなく、最も古い読み込み済みブロックをトリムし得る。別の修復可能なライブマーカーで終わる新しいサフィックスは、その prompt 用の別のエピソードを作成する。

## Concurrency and lifecycle

エピソードは自動で最大 1 回試行される。設定されたリロード、セッション切り替え、ページアンマウント、明示的なセッションクリアはそれを中断して削除する。修復リロードは、成功または失敗までそれを保持する。リロードはセッション登録をデタッチせずに古い SSE サブスクリプションを一時停止する。拒否された候補はデタッチされ、以前のハンドルは既存のカーソルから再開する。検証された候補が新しいサブスクリプションの所有者になる。

チェックポイントは現在のトランスクリプトストアの実効 `maxBlocks` を継承し、マーカーでトリムされたフォールバックは設定された `maxBlocks` を使用する。これにより、修復のための新しい例外を作ることなく、既存のサイズ超過初期リプレイ挙動を維持する。ブロックはテキストペイロードをコピーするのではなく共有され、無制限のジャーナルや第 2 のトランスクリプトキャッシュは導入されない。

## Compatibility

- マーカーの `promptId`、`scope`、`maxEvents` フィールドはオプションである。
- 古いクライアントはマーカーエンベロープの拡張を無視する。
- 新しいクライアントは古いペイロードを受け入れ、曖昧な自動修復は安全に辞退する。
- デフォルトの `reloadSession` 挙動は設定されたリプレイのまま。内部の修復パスのみがメモリリプレイを要求する。
- デーモンの永続化、トランスクリプト API、ジャーナル制限、最古優先のエビクションは変更しない。

## Verification

ユニットカバレッジは、マーカーの所有情報、終端後のコンパクション、ペイロード検証、正確なステータステキスト、prompt マッチング、リプレイ検証、アトミックなサフィックス置換、副作用の重複抑制、履歴保持、障害フォールバック、リロード元の伝播を実施する。デーモン統合テストは、決定的なモック ACP エージェントと 3 イベントジャーナルを使用し、2 番目のクライアントからライブマーカーを観測し、終端後にコンパクションされた完全なターンを検証し、実際の WebUI プロバイダーをマウントして、復旧が 1 回のロードを追加しモデルリクエストは行わないことを証明する。
