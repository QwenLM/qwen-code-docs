# コードホスティングのチャネルアダプター — 設計

## 概要

GitHub ポーリングアダプターにより、AI エージェントは notifications API をポーリングして GitHub 上のタスクを監視し、エージェントの応答を issue/PR のコメントとして投稿できる。IM アダプター（リアルタイムの webhook/ロングポーリング）とは異なり、このアダプターは一定間隔でポーリングする。

## アーキテクチャ: ウェイクアップシグナルとしての notification

核心的な洞察: プラットフォームの notification は **スレッドレベル**であり**可変**である——あらゆるアクティビティ（コメント、push、ラベル変更）が `updated_at` を進める。notification は、コメントごとの信頼できるイベントストリームとしては使用できない。

代わりに、notification は**ウェイクアップシグナル**（「このスレッドで何かが起きた」）としてのみ機能する。アダプターはその後、プラットフォームの comments API を通じて実際のコメントを列挙し、スレッドごとの watermark を使用してどのコメントが新しいかを判定する。

## GitHub: カーソルベースのコメントウィンドウ

### notification/コメントのタイムスタンプの分離

重大なタイミングの問題: **notification の `updated_at` とコメントの `updated_at` は分離されている**。

- `notification.updated_at` は_あらゆる_スレッドアクティビティ（コメント、push、ラベル変更）によって進められ、配信遅延の影響を受ける
- `comment.updated_at` は、コメントが実際に作成/編集された時刻を反映する

これらのタイムスタンプに因果関係はない。notification は、それをトリガーしたコメントの 16 秒後に到着する場合があり、無関係なアクティビティによって再度進められる場合もある。したがって、notification のタイムスタンプを使ってコメントの列挙をゲートすると、2 つの失敗モードが生じる:

1. **重複返信** — `PUT /notifications` は非同期（202 Accepted）で、`last_read_at` カットオフを持つ。ボットの返信により、サーバーがマークを処理する前に `updated_at` がカットオフを超えて進むため、notification が既読としてマークされることがない。次のポーリングでそれを再取得し、同じコメントを再処理してしまう。
2. **返信漏れ** — カーソルが `max(notification.updated_at)` に進み、遅れて到着する notification にあるコメントを飛び越えてしまう場合がある。それらの notification が最終的に到着したとき、そのコメントはカーソルウィンドウの下に位置し、暗黙のうちに除外される。

### 設計

正確性は、notification の既読状態ではなく、**カーソルベースのコメントウィンドウ**から得られる:

ポーリングサイクル:

1. `GET /notifications?since={cursor-1s}` — 未読スレッドを発見する
2. `windowSince = cursor.lastProcessedAt` を保存する（今回のポーリングが進める**前**のカーソル）
3. `markNotificationsAsRead(maxUpdatedAt)` — ベストエフォートのグローバルマーク（issue 以外の notification をクリーンアップする）
4. グローバルカーソルを `max(notification.updated_at)` に進める
5. スレッドごと: `listComments(since=windowSince)` — コメントを列挙する
6. 除外: ボット自身のコメント; `created_at > maxUpdatedAt` のコメント（ウィンドウの上）; `created_at <= windowSince` のコメント（ウィンドウの下）
7. 処理: メンション検出 → エンベロープ → `handleInbound`

実効的なコメントウィンドウは `(windowSince, maxUpdatedAt]` である。前のポーリングで処理されたコメントは `created_at <= windowSince`（前のポーリングの `maxUpdatedAt`）であり、除外される。これにより、`PUT /notifications` が成功したかどうかに関係なく、重複が防止される。コメントの編集は再処理をトリガーしない——ウィンドウのメンバーシップには `created_at` のみが使用される。

グローバルマークは引き続き呼び出され（ステップ 3）、issue/PR 以外の notification をクリーンアップして未読リストを減らす。ただし、重複排除にとって不可欠（load-bearing）ではない。

### 既知の制限: notification の配信遅延

カーソルは（スレッドごとではなく）グローバルであるため、コメントの `created_at` より後のポーリングで到着した notification は、そのコメントがカーソルウィンドウによって除外される場合がある。これには、notification の配信がポーリングの境界をまたいで遅延し、かつその間に別のスレッドのコメントがカーソルをそれらを超えて進めていることが必要である。実際にはこのウィンドウは狭い（notification の配信は通常、1 ポーリング間隔以内に完了する）。ユーザーは再メンションすることでリトライできる。

### 既知の制限: PR のレビューコメント

`issues.listComments` は、PR のレビューコメント（diff の行ごとのコメント）ではなく、一般的な会話のコメントのみを返す。PR のレビューコメント内の @メンションは暗黙のうちにドロップされる。代わりに、PR に対する一般的な会話のコメントを使用すること。

### シナリオ別の挙動

| シナリオ                          | 挙動                                                                                                                          |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 新しいスレッド（コメントで @bot） | 表示される（未読）→ カーソル以降を列挙 → 処理                                                                                  |
| 既存スレッド、新しいコメント       | 再表示される（未読）→ カーソル以降を列挙 → 古いコメントは `<= windowSince` で除外 → 新しいもののみ                              |
| コメント以外のアクティビティ（push/ラベル） | 表示される → ウィンドウ内に新しいコメントなし → スキップ                                                              |
| ユーザーが github.com で既読にする | API から消える → 処理されない                                                                                                 |
| markNotificationsAsRead が失敗    | カーソルウィンドウが引き続き重複を防止 → 正確性への影響なし                                                                    |
| markRead 後、完了前にクラッシュ   | カーソルが保存されない → 次回の起動で同じ notification を再取得 → クラッシュしたバッチは再処理され、失われない                  |
| ボットがスレッドに返信            | `updated_at` が進む → notification は未読のままの可能性 → 次のポーリングで取得 → コメントはカーソルウィンドウで除外 → 重複なし |
| 本文に @bot を含む新しい issue    | コメントなし → 本文にメンションあり → 本文をトリガーとして供給（`dispatchedBodies` で重複排除）                                |

## PollingChannelBase

`PollingChannelBase<Cursor>`（`packages/channels/base/` 内）は `ChannelBase` を拡張し、ポーリングループのインフラストラクチャを提供する:

- **ポーリングループ**: `startPollLoop()`/`stopPollLoop()` を通じて開始/停止し、`connect()`/`disconnect()` から呼び出される
- **ポーリング間隔**: チャネル設定の `pollInterval`（ms）から読み取り、正の有限数として検証され、デフォルトは 60000
- **カーソルの永続化**: JSON カーソルは、成功した各 `pollOnce()` の後にアトミックに保存される。構築時に読み込まれる（破損またはパース不能な日付 → `createInitialCursor()` へのフォールバック）
- **カーソルの検証**: `validateCursor()` 仮想フック — base はオブジェクトでないものと配列を拒否する。サブクラスは形状チェックを追加する（例: GitHub は `lastProcessedAt` 日付の欠落/無効を拒否する）
- **バックオフ**: ポーリングエラー時に指数関数的に 2s → 30s、成功時にリセット
- **中断可能なスリープ**: `abortableSleep(ms)` が protected メソッドとして公開される — ポーリング間隔とエラーバックオフは `disconnect()` によって中断可能

サブクラスが実装するのは次のみ:

- `pollOnce()` — 処理を実行し、`this.cursor` を変更する
- `createInitialCursor()` — 初回実行時のデフォルト値

`Cursor` ジェネリックは任意の JSON シリアライズ可能なオブジェクトである。GitHub は `{ lastProcessedAt: string; dispatchedBodies?: string[] }` を使用する（後者は、初回接触の本文重複排除を直近 500 エントリに制限する）。

## メンション検出

本文ベースで、大文字小文字を区別しない正規表現。検出（`testBotMention`）と除去（`stripBotMention`）は別の関数になっている:

- 検出: boolean を返す明示的な正規表現マッチ — 除去前後の比較から推測することは決してない（空白の違いが誤検出を引き起こす）
- 除去: `@bot` のみを削除し、他のすべてのフォーマットを保持する（空白の収縮はしない）

## セッションのスコープ

ポーリングアダプターは `chat_thread` スコープを使用する: ルーティングキー = `channel:chatId:threadId`。これにより、リポジトリ間のセッション衝突（`repo-a/issue:42` と `repo-b/issue:42`）が防止される。

## エラー処理

配信は**ベストエフォート**である。`handleInbound` の失敗時には、ポーリングサイクルごとにスレッドあたり 1 つのエラーコメントが投稿される（その後 `break` でコメントループを抜ける — 同一のエラーコメントが N 件投稿されるのを防ぐ）。ユーザーは再メンションすることでリトライできる。notification ごとの API エラーは `continue` を使用する — 1 件の notification の失敗が残りのバッチをブロックしない。`subject.url` のない notification（Discussion、SecurityAlert タイプ）は暗黙のうちにスキップされる。

処理の途中でプロセスがクラッシュした場合、カーソルは保存されない（`pollOnce()` が完了した後にのみ永続化される）ため、次回の起動で同じ notification を再取得する——ただし、カーソルベースのコメントウィンドウが処理済みのコメントを除外し、重複を防ぐ。

重複防止は `PUT /notifications` の成功に依存**しない**。グローバルマークはベストエフォートのクリーンアップであり、カーソルウィンドウが不可欠な重複排除のメカニズムである。
