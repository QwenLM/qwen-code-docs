# ACP モデルルートの識別

## 問題

Qwen Code は現在、ACP のモデル ID を `modelId(authType)` として公開している。そのため、モデル ID と認証タイプが同じで `baseUrl` の値が異なる 2 つの設定済みモデルは、1 つの ACP セレクターにまとめられてしまう。クライアントはアクティブな行を特定できず、選択を意図したエンドポイントへラウンドトリップさせることもできない。

Core はすでに `(authType, modelId, configured baseUrl)` をレジストリの識別子として扱っている。識別子の喪失は、その識別子が ACP の境界を越えるときにのみ発生する。プロバイダーのデフォルトが登録後に `baseUrl` を補完する場合があるため、設定された値は解決されたエンドポイントとは別に保たれなければならない。

## 設計

既存の設定済みモデルリストから ACP のモデルオプションを構築する:

- 一意である場合は `modelId(authType)` を維持する。これにより、通常のケースでは既存の ID が保持される。
- 複数のオプションがその ID を共有する場合、それぞれを、秘密情報以外のモデルメタデータと公開エンドポイントの識別情報（認証情報、クエリ、フラグメントを除去）から導出された決定論的な `qwen-route:v1:<digest>` セレクターに置き換える。
- サニタイズ後も区別できないルートは拒否する。配列の順序を使用すると、設定の並び替え後に古いセレクターが再マッピングされる可能性があるため、使用しない。
- 表示には引き続き `ModelInfo.name` とプロバイダーのメタデータを使用する。ルート ID は不透明な機械向けセレクターである。

Core は、元の任意のレジストリ `baseUrl` を、解決された表示用エンドポイントと並べて公開する。同じオプションビルダーが、ACP セッションのモデル、設定オプション、ライブのプロバイダーステータス、デーモンのワークスペースプロバイダーステータスを供給することで、すべてのクライアントが同じ ID を参照しつつ、サーバー側は正確なレジストリの判別子を保持する。

`session/set_model` において、Qwen Code は切り替え前に現在の設定済みモデルリストに対してセレクターを解決する。解決された `baseUrl` を Core に渡し、その後、正規の設定値のみを永続化する:

- `model.name`: 実際のモデル ID
- `model.baseUrl`: 設定されたレジストリのエンドポイント、または暗黙のデフォルトを示す空の tombstone
- `security.auth.selectedType`: 実際の認証タイプ

不透明なセレクターが `settings.json` に書き込まれることはない。

## 互換性

- ACP スキーマは変更なし; `modelId` は引き続き文字列である。
- 一意な既存のモデル ID は現在のワイヤー表現を維持する。
- レガシーな `modelId(authType)` リクエストは引き続き受け付けられる。そのような ID が曖昧な場合は、互換性のために既存の first-match の挙動が維持される。新しく通知されるセレクターは完全一致である。
- 不明または古い不透明なセレクターは、リテラルのモデル ID として扱われる代わりに拒否される。
- Zed を含む汎用の ACP クライアントは、不透明なセレクターをそのまま返すだけでよい。
- CLI TUI の設定と選択の挙動は変更なし。

## 検証

- 重複するルートは、URL を漏洩させることなく、個別で安定したセレクターを受け取る。
- セッションのモデル状態と設定オプションは、同じセレクターと正確な現在のルートを公開する。
- 2 番目のルートを選択すると、その `baseUrl` で切り替わり、正規の設定が永続化され、その不透明なセレクターでクライアントに通知される。
- デーモンのプロバイダーステータスは、Web Shell に対して正確な現在のルートを識別する。
- 一意なモデルおよびレガシーなモデルの選択は引き続き動作する。
