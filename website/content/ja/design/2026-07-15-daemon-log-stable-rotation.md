# 安定した上限付きのデーモンログ

- **ステータス:** 実装済み
- **日付:** 2026-07-15
- **スコープ:** `qwen serve` のファイルロギング、ライフサイクルの所有権、アクセスログの受け入れ、デーモンのステータス、TypeScript SDK のステータスミラー

## 決定

各ランタイムのログ名前空間は、1 つの安定したアクティブパスを持ちます:

```text
${runtimeBaseDir}/debug/daemon/daemon.log
```

通常の再起動はそのパスに追記します。固定のポリシーは以下のとおりです:

| 制限                                 |        値 |
| ------------------------------------- | -----------: |
| アクティブファイル                           |       10 MiB |
| ファミリごとのアーカイブ                   |            4 |
| レンダリングされるファイルレコード                  |      256 KiB |
| 受け入れ済みだが未確定のファイルペイロード   |        4 MiB |
| 安定リースの stale/update             |  60 秒 / 10 秒 |
| 安定/メンテナンスの取得バジェット | 1 秒 / 250 ms |
| パブリックな logger のクローズバジェット            |          2 秒 |

これらの値は意図的に、CLI フラグ、環境変数、設定ではありません。健全な安定ファミリは最大で約 50 MiB を占有します。最新の非アクティブなフォールバックファミリを保持すると、収束した名前空間は約 100 MiB になります。ライブ、またはまだ stale になっていないフォールバックの所有者は決して削除されないため、一時的な使用量は生存している可能性のあるデーモンの数に応じて増加し得ます。

起動のたびにランダムな 128 ビットの `runId` が生成されます。すべてのファイルレコードは、不変の `runId` とデーモンの PID コンテキストで始まります。呼び出し元のコンテキストがそれらの値を置き換えることはできません。Stderr は既存のフォーマットとフィールド順を維持します。

## 名前空間と所有権

設定されたログディレクトリが、所有権と保持の名前空間です。ワークスペース、リスナーポート、PID はストレージの identity ではありません: デーモンは複数のワークスペースをホストでき、ポートゼロは動的であり、ポートは競合時に繰り上がることがあり、埋め込みデーモンは PID を共有し得るためです。

安定ファミリは、ライフタイムの `proper-lockfile` リースによって所有されます。それを取得できないコンテンダーは以下に書き込みます:

```text
debug/daemon/runs/run-<32-hex-runId>/daemon.log
```

そのファミリの `.owner.lock` をライフタイムの間保持し、実行中に安定ファミリに昇格することは決してありません。起動バナーと完全なデーモンのステータスが、選択されたパスの権威です。`runs/recent-fallback` は検証済みの検出ヒントにすぎません。

フォールバックの割り当てとクリーンアップは `runs/.maintenance.lock` によってシリアライズされます。クリーンアップは、ビジーなすべての所有者ファミリと、最大 1 つの非アクティブなファミリを保持します。有効なロケーターを優先し、次に最新のアクティブログの mtime、そしてベース名を決定的なタイブレーカーとします。ロック以外のクリーンアップエラーや削除の失敗は割り当てを拒否するため、破損した名前空間は起動のたびに新しいディレクトリを蓄積しません。

フォールバックのクリーンなクローズは、メンテナンスの所有権を取得し、所有者リースを解放し、現在のファミリを保持し、他の非アクティブなファミリを削除し、ロケーターを修復します。メンテナンスの所有権が利用できない場合、クローズは所有者リースのみを解放し、修復は後日の起動に委ねます。

## ファイルシステムレイアウト

```text
debug/daemon/
├── daemon.log
├── latest -> daemon.log
├── .stable-writer.lock/
├── archive/
│   └── daemon-000000000001-20260715T031415926Z-a1b2c3d4.log
└── runs/
    ├── .maintenance.lock/
    ├── recent-fallback
    └── run-6a45c211000000000000000000000000/
        ├── .owner.lock/
        ├── daemon.log
        └── archive/
```

厳密にマッチする通常のアーカイブファイルのみが保持に参加します。レガシーな `serve-<pid>.log` と `serve-<pid>-<workspaceHash>.log` ファイルは移行も削除もされません。

新しいディレクトリはモード `0700` を使用し、新しいアクティブログとロケーターの一時ファイルは `0600` を使用します。既存のオブジェクトのパーミッションは書き換えられません。`latest` は成功した安定所有者のみが更新し、シンボリックリンクが利用できない環境では引き続きベストエフォートです。

## ファイルレコードとキュー

ファイルレコードは有効な UTF-8 の境界で切り詰められます。元のバイト数マーカーと改行を含む最終レコードは、最大 256 KiB です。その stderr コピーは切り詰められません。

1 つの Promise キューがファイル変更の順序を保持します。受け入れ済みだが未確定のレコードバイトは同期的に計上されます。キューを 4 MiB 以上に押し上げるレコードは、ファイルコピーのみを失います。logger は `droppedRecords` と `droppedBytes` をインクリメントし、そのオーバーフローのエピソードについて 1 回だけ警告します。

キャパシティが回復した後、次の呼び出し元のレコードの前に、`daemon file log records dropped` という名前のファイル専用の警告が付きます。これは未報告のレコード数とバイト数の合計を報告し、それらに再帰的に寄与しません。クローズは、キューを drain した後に最終的な試行を 1 回行います。

各キュータスクは自身の失敗をキャッチし、`finally` で pending バイトの計上を解放します。共用の末尾が拒否されたままになることはありません。アクティブな追記が拒否された場合、その結果は不明です: logger は `write_failed` を記録し、その実行のそれ以降のすべてのファイル変更を停止し、失敗したレコードを正確な損失として主張しません。意図的にスキップされた後続のレコードはカウントされます。

リースの侵害も同様に、新しいファイル変更を即座に停止します。すでに開始された単一のファイルシステム操作は完了し得ますが、そのファミリを通じて後続の追記、ローテーション、削除が開始されることはありません。

## ローテーションのトランザクション

レコードによってアクティブファイルが 10 MiB を超える前に、logger は以下を行います:

1. `archive/` がシンボリックリンクでない実際のディレクトリであることを検証する;
2. 最大 3 つ残るまで、最も古い生成済みアーカイブを削除する;
3. 12 桁の世代番号、UTC タイムスタンプ、ランダムサフィックスを含む、存在しない名前を選択する;
4. アクティブパスをそのアーカイブ名にアトミックにリネームする;
5. トリガーとなったレコードを、モード `0600` の新しい `daemon.log` に追記する;
6. インメモリのサイズと世代の状態をコミットする。

したがって、この実装が生成するファミリは、最大で 1 つのアクティブファイルと 4 つのアーカイブを持ちます。新しいアクティブへの追記が失敗した場合、以前のアクティブファイルは最新のアーカイブ内で完全なままです。

アーカイブの検証、プルーニング、命名、リネームの失敗は、アクティブファイルに 10 MiB を超えさせるのではなく、レコードをドロップします。ローテーションは 60 秒あたり最大 1 回リトライされ、その間も収まる小さいレコードは継続できます。特別な ENOSPC/EDQUOT の削除＆リトライプロトコルや、拒否された追記の切り詰めロールバックはありません。どちらもファイルの結果状態を証明できないためです。

初期化はアクティブファイルの実際のサイズを読み取ります。最後のバイトが改行でなく、起動レコードが最初にローテーションしない場合、logger は改行を挿入し、起動レコードに `previousTailIncomplete=true` をマークします。安定起動プローブが安全に書き込めない場合、安定リースを解放し、フォールバックファミリを 1 回試みます。フォールバックプローブの失敗は、stderr 専用の degraded なロギングにつながります。

## Logger の状態とライフサイクル

```ts
type DaemonLogMode = 'stable' | 'fallback' | 'stderr-only';
type DaemonLogHealth = 'ok' | 'degraded';
type DaemonLogIssue =
  | 'init_failed'
  | 'rotation_failed'
  | 'retention_failed'
  | 'queue_overflow'
  | 'write_failed'
  | 'lease_compromised';
```

`getStatus()` は、run identity、モード、ヘルス、順序付きの issues、損失カウンターを返します。`QWEN_DAEMON_LOG_FILE=0|false|off|no` は、ファイルシステムにアクセスせずに健全な stderr 専用の logger を返します: `info`、`warn`、`error` は引き続き stderr に書き込み、`raw` は引き続きファイル専用であるため何もしません。

`close()` はべき等で、拒否しません。ファイルコピーの受け付けを同期的に停止し、構造化 stderr の呼び出しは引き続き利用可能です。バックグラウンドのファイナライザーがキューを drain し、最終的な損失サマリーを試行し、フォールバックのクリーンアップを行い、ライフタイムのリースを解放します。パブリックな Promise は最大 2 秒待ちます。タイムアウトしてもリースを早期に解放せず、ファイナライザーは開始された I/O が収束するまで生存し続けます。`flush()` は無制限のキュースナップショットのセマンティクスを維持します。強制シグナルパスとリトライ可能なリソースクローズの失敗は、250 ms で競合します。

Logger の所有権は以下のように移ります:

```text
startup -> published handle -> terminal close
       \-> startup signal -> terminal close
```

ハンドル公開前の内部クローズは、logger のキューを待たずにデーモンのリソースを drain し、その後 logger を外側の起動エラー所有者に委ねます。その所有者は `daemon startup failed` を記録してクローズします。ターミナルの公開済みまたはシグナル所有のクローズは、アクセスロギングをシールし、`daemon stopped` を記録し、リソースのシャットダウンがリトライ不可のエラーを返す場合でも logger をクローズします。元のリソースエラーが返されるエラーのままです。ターミナルの診断書き込みはベストエフォートであるため、stderr が利用不能でも元の失敗を置き換えたり logger のクリーンアップをスキップしたりしません。リトライ可能なチャネルワーカー/サービスリースの失敗は logger を開いたままにし、上記の上限付き flush を使用し、`daemon stopped` を記録しません。

## アクセスログの受け入れ

各ランタイムの Express アプリは、バースト 60、リフィル 2 レコード/秒の定数空間トークンバケットを所有し、monotonic クロックで計測します。クロックの巻き戻しがリフィルのベースラインを後退させることは決してありません。ヘルス、ハートビート、成功した SSE の除外は不変です。

ルート、セッション ID、最初の raw `x-qwen-client-id` の出現は、UTF-8 の境界でそれぞれ 2 KiB、256 バイト、256 バイトに制限されます。切り詰められた値は元のバイト数のコンテキストフィールドを持ちます。最初の raw ヘッダーを使用することで、マージされた重複ヘッダーが新しいカーディナリティの源になることを防ぎます。

トークンが利用できない場合、5 つの固定カウンターのみが保持されます: 2xx、3xx、4xx、5xx、その他。回復時に WARN の `access logs suppressed` サマリーが、個別レコードの前に次のトークンを消費します。それが唯一のトークンだった場合、現在のリクエストは次のサマリーに加わります。シャットダウンは、通常のリスナーの drain またはセカンダリの締切後にコントローラーをシールし、最終サマリーを発行し、遅延した完了コールバックを無視し、その後 `daemon stopped` を記録します。

レート制限は診断のみに影響し、HTTP の結果を決して変更しません。抑制された個別レコードは stderr にもファイルにも到達せず、サマリーは両方に到達します。

## デーモンのステータスと SDK

各ステータスレスポンスは 1 つの logger スナップショットを取得します。サマリーと完全なレスポンスには以下が含まれ得ます:

- `daemon.runId`
- `daemon.logMode`
- `daemon.logHealth`

完全なレスポンスには、さらに `daemon.logPath`、`daemon.logIssues`、`daemon.logDroppedRecords`、`daemon.logDroppedBytes` が含まれ得ます。degraded なロギングは、既存の rollup に、パスなしのトップレベル `daemon_log_degraded` 警告を追加します。TypeScript SDK はオプションのフィールドと閉じたユニオンをミラーします。ケーパビリティタグやクライアントのアップグレードは不要です。

オプトアウトは `stderr-only/ok` を報告し、通常の安定競合は `fallback/ok` を報告し、ファイルシステムの初期化失敗は `init_failed` を伴う degraded なロギングを報告します。

## 運用と互換性の境界

- 独立した保持や監査の名前空間には、別のランタイムディレクトリを使用してください。
- macOS/Linux では `tail -F daemon.log` を使用します。すべてのプラットフォームで、ビューアーはローテーション後にパス名を再オープンする必要があります。
- `daemon.log` を変更するように外部の logrotate を設定しないでください。コピーや転送は安全です。リネーム、切り詰め、削除はインメモリのサイズモデルを破壊します。
- stale ウィンドウ内の並行デーモンやクラッシュ再起動の嵐の間、有効期限による削除、圧縮、fsync の耐久性、絶対的な上限はありません。
- 同一ユーザーによる改ざん、偽の stale 引き継ぎ、決して戻らないファイルシステム呼び出し、突然の電源喪失、リネームを妨げる Windows のリーダーは、プラットフォーム固有の no-follow、fsync、プロセス受け入れプロトコルではなく、安全な degradation によって処理されます。
- ダウングレードは引き続き可能です。古いバージョンは単に PID 名のファイルの作成を再開します。

## 検証戦略

ユニットカバレッジには、フォーマット、不変のファイルコンテキスト、安定した再利用、UTF-8 の切り詰め、ローテーションの境界、不完全な末尾、キューオーバーフローのサマリー、汚染された追記、アクティブおよび解放後の侵害されたリース、上限付きのクローズとリトライ flush、安定/フォールバックの並行性、フォールバックの保持、クリーンアップの拒否、ライフサイクル診断の失敗、アクセストークンの受け入れ、シャットダウンのシール、ステータスのスナップショット、分離されたテストランタイム名前空間、SDK の型サーフェスが含まれます。

プロセスレベルの検証では、ビルドされたバンドルと分離されたランタイムディレクトリを使用し、再起動時の再利用、実際のしきい値でのローテーション、安定/フォールバックの並行性、シグナルによるリース解放、SIGKILL の stale ウィンドウの動作、アクセスの集約、レガシーファイルの保持、ファイルシステムアクセスなしのオプトアウトを検証します。CI プラットフォームマトリックスは、macOS、Linux、Windows で直接のアクティブパスを実行する必要があります。Windows ではさらに、リーダーがアクティブ/アーカイブのリネームを妨げる場合の安全な degradation を検証します。
