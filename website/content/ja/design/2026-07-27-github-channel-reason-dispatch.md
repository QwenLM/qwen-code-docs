# GitHub 通知 reason のディスパッチ

## ゴール

GitHub チャネルが送信するプロンプトの選択に `notification.reason` を使用する。
ポーリング、カーソル進行、リトライ、エラー報告の挙動は変更しない。

| reason              | 挙動                                                        |
| ------------------- | --------------------------------------------------------------- |
| `mention`           | 実際にボットをメンションしたコンテンツのみを送信する。               |
| `review_requested`  | プルリクエストには、プルリクエストデータ付きのレビュープロンプトを送信する。 |
| `assign`            | Issue データ付きのトリアージプロンプトを送信する。                           |
| `author`、`comment` | ウィンドウ内の新しいコメントを 1 つのフォローアッププロンプトに集約する。  |
| その他               | コメントごとの処理を維持し、通知の reason を識別する。 |

レビューとアサインのイベントは GitHub イベントのアクターを envelope の送信者として使用し、
既存の送信者ポリシーが Issue やプルリクエストの作者ではなく、アクションを開始した人物を
チェックするようにする。集約は許可された送信者のみを含み、最新の 20 コメント、コメント
あたり 400 文字に制限される。ペアリングポリシーはコメントごとのディスパッチを維持し、
各送信者が独立して認可される。

カーソルは最大 500 件のディスパッチ済みコメントおよび直接イベントのノード ID を記憶する。
固定のインストール時刻フロアにより、遅延したレビューおよびアサイン通知がインストール前の
履歴をリプレイせずにイベントを見つけられる。通知 ID は永続化されない。GitHub が同じ
スレッドの後続アクティビティに ID を再利用するためである。

## 検証

フォーカスされたアダプターテストは、各ルート、直接トリガーのメタデータ、メンション除去、
集約の認可、コメントと直接イベントの重複排除をカバーする。
