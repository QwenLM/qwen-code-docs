# ツール結果の vision bridge

## コンテキスト

既存の Vision Bridge はユーザー入力から解決された画像を変換しますが、`read_file` は通常の画像をテキストのみのツール結果から除外したままです。他のツールは画像を `inlineData` として返すことができ、`convertToFunctionResponse` はそれらの画像を `functionResponse.parts` に格納し、リクエストスリマーが後でテキスト専用モデルのためにそれらを MIME プレースホルダーに置き換えます。その結果、モデルによって発見された画像や、組み込み、MCP、拡張機能のツールが返す画像は、vision モデルが設定されていても、テキスト専用のプライマリモデルには理解されません。

## 設計

`read_file` は、アクティブなターゲットモデルがテキスト専用であり、かつ Vision Bridge モデルが利用可能な場合にのみ、通常の画像を保持します。自身で vision モデルを呼び出すことはありません。PDF 固有の文字起こしは変更されません。

共有のコアヘルパーは、正規化されたツールレスポンスの parts がモデル入力になる直前に処理します。アクティブなターゲットモデルが画像を受け入れる場合、または Vision Bridge が利用できない場合、ヘルパーはレスポンスを変更せずに返します。設定された vision モデルがエージェント対応であり、呼び出し元がターンの残りを切り替えられる場合、ヘルパーはインライン画像のサイズをクランプし、ツール画像を保持し、既存の full-turn override を通じてそのモデルを選択します。それ以外の場合、インライン画像を含む各 `functionResponse` について、画像と、ツール名、画像ラベル、既存のテキスト出力を含む有界のフォーカスヒントを添えて、既存の Vision Bridge を呼び出します。

ヘルパーは、信頼できない機械による文字起こしを既存の `response.output` または `response.error` に追加し、関数名、呼び出し ID、その他のレスポンスフィールド、画像以外のメディアを保持し、`functionResponse.parts` からすべての元のインライン画像を削除します。Bridge の失敗とキャンセルは、生の画像データがテキスト専用プロバイダーに到達することを許さず、明示的な利用不能のメモで画像を置き換えます。Bridge のカウントまたはバイト上限を超える画像も削除され、文字起こしブロックによって報告されます。

共有ヘルパーは、コアのツールスケジューラーと ACP の直接ツールエクゼキューターによって使用されます。インタラクティブスケジューラー、非インタラクティブランナー、アクティブな ACP プロンプトは、ツールトリガーの full-turn override を受け入れることができるため、次のモデルリクエストと以降のツール継続はエージェント対応の vision モデルにとどまります。インラインモデル選択をサポートするサーフェスでは、明示的な選択が優先されます。ターンレベルの override チャネルを持たない利用側は、生の画像をテキスト専用モデルに公開するのではなく、文字起こしフォールバックを保持します。投機的なフォローアップ実行は例外です: その出力は破棄される可能性があり、キャッシュのウォームアップにのみ使用されるため、ツール結果の画像を明示的な利用不能のメモで削除し、vision モデルに送信しません。組み込みツール、MCP ツール、拡張機能ツールは、すべてこれらのパスのいずれかを通じて入ります。

すべての実際のツール結果 bridge 試行は、アクティブなサーフェスで開示されます。文字起こしは既存の Vision Bridge フォーマッターを使用して選択された vision モデルとエンドポイントを報告し、full-turn takeover はターンの残りを所有するモデルを報告します。TUI と JSON 出力は、通知と並んでツールの元の表示を保持し、ACP は同じ通知をエージェントメッセージとして発行します。

インライン画像のバイトのみが変換されます。画像の `fileData`、URL、パスのみのテキスト、音声、動画は、それらを解決すると個別のファイルシステム、ネットワーク、認証、モダリティのポリシーが生じるため、この変更の対象外です。

## 互換性と失敗時の動作

パブリックなツールスキーマは変更されません。既存のユーザー入力および PDF の Vision Bridge の動作はそのままです。vision モデルのない設定は、現在のサポートされていない画像または MIME プレースホルダーの動作を保持します。正常なツール呼び出しは、bridge が失敗したという理由だけでツールエラーに変換されません。モデルは元のテキストと、サニタイズされた画像利用不能のメモを受け取ります。プロバイダーのエラー詳細はログに記録されますが、function response に挿入されることはありません。ターンごとの画像バジェットは、ターン内のすべての bridge パスで共有されます: 実行中のカウントはターンのアボートシグナルをキーとするため、ユーザー入力、PDF、ツール結果の bridge は、それぞれが新しい上限を得るのではなく、同じ上限から引き出します。設定されているがエージェント対応ではない vision モデルでは、上限を早期に使い切ったターンは、以降のツール画像をバジェット枯渇として文字起こしします。エージェント対応の takeover は、画像を文字起こしする代わりに生の画像を保持するため、影響を受けません。

## 検証

フォーカスされたテストは、通常の画像読み取り、ネストされたツール画像、テキストと画像が混在する結果、複数の function response、bridge の失敗とキャンセル、マルチモーダルターゲットのパススルー、full-turn takeover の受け入れと拒否、ユーザーに見える開示、投機的な画像除去、function identity と画像以外フィールドの保持をカバーします。統合チェックは、コアスケジューラー、インタラクティブおよび非インタラクティブの override の配管、ACP エクゼキューター、投機的エクゼキューターの呼び出し箇所を実行します。ビルド、型チェック、バンドル、ローカル CLI の検証がこの変更を完成させます。
