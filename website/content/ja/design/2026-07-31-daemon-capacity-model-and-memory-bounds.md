# デーモンのキャパシティモデルとメモリ上限

## コンテキスト

Issue [#8051](https://github.com/QwenLM/qwen-code/issues/8051) は、デーモンが登録
ワークスペースとセッションを個数で制限していること、そして個数の制限はメモリの制限では
ないことを指摘する。[#8091](https://github.com/QwenLM/qwen-code/issues/8091) は修正を
7 つの PR として提供することを提案し、その最初が [#8093](https://github.com/QwenLM/qwen-code/pull/8093)
である: デーモンルートの JavaScript ヒープに対するプロセス全体の `ResourceBudget` で、
15 のバイトカテゴリ、複合アトミックな受け入れ、分割・移転可能なリース、3 つの
`AsyncLocalStorage` スコープの公平スケジューラー、JavaScript の値を 1 文字列コード単位
2 バイト、1 オブジェクトノード 96 バイト、1 プロパティ 16 バイトと価格付けする
ヒーププロキシ課金モデルを備える。

本文書は、同じ問題に対する別の分解を提案する。#8051 の前提と、#8091 の段階的に提供する
という直感には賛同する。どのプロセスがメモリを保持するか、どの機構がそれを制限できるか、
どの変更を最初に着手すべきかについては見解が異なる。

以下の 3 つの所見は、今日のデーモンを読み解いた結果から得られたものである。

### デーモンは 1 つのプロセスではない

`ServeMode` は `http-bridge` である（`packages/cli/src/serve/types.ts:18-35`）: デーモンは
ワークスペースランタイムごとに 1 つの `qwen --acp` 子プロセスをプリヒートし、1 つの
ランタイム内の複数セッションが `connection.newSession()` 経由でその子プロセスに
多重化する。デーモンルートは ACP の NDJSON を HTTP と SSE 上で中継する。
`types.ts:58-68` で `maxSessions` の根拠として記述されている、おおよそ 30〜50 MB の
セッションあたり RSS は、ルートではなく子プロセス内で消費される。

したがってマルチワークスペースの定常メモリがあるのは子プロセス RSS の合計であり、
ルートのヒープに対するバイト予算はそれを観測も制限も拒否もしない。

これは_デーモン全体の境界としての汎用ルートヒープ台帳_への反対論であり、
ルートローカルの保護への反対ではない。ルートは依然として ACP の NDJSON 組み立て、
EventBus のリプレイリング、仮想サブエージェントのスナップショット、設定読み込み、
アクティブセッションのエクスポート、HTTP と WebSocket のキュー、世代スコープの
キャッシュを所有し、それらのそれぞれが子プロセスとは独立にルートを枯渇させうる。
下記の Part 3 がまさにその理由で完全にルート側の作業である。

### キャパシティモデルはホストメモリと分離されている

デーモンが消費しうるメモリ量を決定するノブが 3 つある。それぞれ独立に導出され、
それらを調整するコードはない:

| ノブ                  | 導出                                                  | 場所                                                |
| --------------------- | ----------------------------------------------------------- | ------------------------------------------------------- |
| 登録ワークスペース | 固定定数 `25`                                         | `packages/acp-bridge/src/channel-control-timeouts.ts:7` |
| セッション総数        | `maxSessionsPerWorkspace × workspaceCount`                  | `packages/cli/src/serve/run-qwen-serve.ts:391`          |
| 子プロセスごとの V8 ヒープ     | `max(min(cgroup またはホストメモリの 50%, 16 GB), V8 デフォルト)` | `packages/acp-bridge/src/spawnChannel.ts:18-36`         |

3 つ目が重要である。`getAcpMemoryArgs()` は 1 つの値を計算し、モジュールレベル変数に
キャッシュし、spawn される**すべて**の子プロセスに適用する。これは何かの取り分ではなく、
ホストの割合である。

`max(…, V8 default)` の項はコードからは自明ではなく、二重に問題になる。このフラグは
計算されたターゲットが **spawn するデーモン自身**の `heap_size_limit` を超える場合のみ
発行され（`spawnChannel.ts:27-34`）、ターゲットが小さいホストではフラグが落とされ、
子プロセスはサイレントに V8 のデフォルト——これもホストメモリから導出される——を継承する。
3.4 GB ホストでの計測: ターゲット 1747 MB、デーモン上限 1795 MB、フラグは落ち、
子プロセスの上限 1795 MB。32 GB ホストではデフォルトは約 4 GB、ターゲット 16384 MB、
フラグは発行される。

つまり許容総量は 32 GB ホストで 25 × 16 GB、3.4 GB ホストで 25 × 約 1.8 GB となり——
いずれにせよ約 12 倍のオーバーコミットであり、今日このガードの唯一の効果は上限を
引き上げることであり、引き下げることは決してない。最後に挙げた性質のため、下記の変更は
それを明示的にバイパスしなければならない。

ルートプロセス内のバイト会計をどう変えてもこれらの数値は変わらない。それらを割り当てる
プロセスはルートではないからである。

### デーモンはメモリを計測するが分母がない

`DaemonMetricsRing` はすでに `rssBytes`、`heapUsedBytes`、`cpuPercent`、
`eventLoopLagP99Ms` を 5 秒ごとに 180 バケットのリングにサンプリングして 15 分間の履歴を
持ち、プライマリ ACP 子プロセスの RSS をシングルフライトガードと 30 秒の鮮度クリフ付きで
ポーリングしている（`packages/cli/src/serve/daemon-metrics-ring.ts`、
`run-qwen-serve.ts:4231-4377` で接続）。`GET /daemon/status` はこれらすべてを返す。

デーモンに欠けているのは、割り算する対象となる数値である。cgroup の読み取りも、
`heap_size_limit` も、比率も、プレッシャーレベルも、メモリ由来の issue コードも、
`limits.*` のメモリフィールドも、CLI フラグも、デーモンプロセスのどこにもない。
Core の `MemoryPressureMonitor` はこれらすべてを計算するが、
`computeEffectiveMemoryLimit()` は `Config.initialize()` でのみ構築されるクラスの
プライベートメソッドであり（`packages/core/src/services/memoryPressureMonitor.ts:766`）、
デーモンはそれを決して呼び出さない。セカンダリワークスペースの子プロセスやすべての
チャネルワーカーは RSS をまったく報告しない。

デーモンは何バイト使っているかは言えるが、それが多いかどうかは言えない。

## 問題

正確に述べると: **デーモンのキャパシティモデルはホストのメモリと関係がなく、デーモンは
枯渇にどれだけ近いかを観測できない。** 別途かつ独立に、ルートプロセスの小さな列挙可能な
コンテナ群が真に無制限である——子プロセスが 1 つも関与しなくても、そのいずれか 1 つが
単独でルートを枯渇させうる。両方とも実在する; どちらもすべての割り当ての上に汎用の
会計レイヤーを作る理由にはならない。

## ゴール

- キャパシティノブを 1 つのメモリ数値から導出し、子プロセスのヒープ上限がホストの割合の
  繰り返しではなく何かの取り分になるようにする。
- デーモンに分母を与え、プレッシャーが致命的になる前に観測可能にする。
- 真に無制限のコンテナを、コンテナのところで上限化する。
- 個別に上限化された多くのコンテナの_合計_に上限を設ける。多重性が合計を真のリスクに
  するからである。
- 各変更を独立にレビュー可能かつ独立に有用に保つ——そしてそれぞれがどのパスをカバー
  するかについて正直に保つ。

## 非ゴール

- ルートヒープに対するプロセス全体のバイト台帳なし、ヒーププロキシ課金モデルなし。
  「却下された代替案」参照。
- 観測作業での修復措置なし: 強制 GC なし、LRU エビクションなし、セッションクローズなし、
  プロセス終了なし。
- インタラクティブ CLI や IDE コンパニオンのメモリ挙動の変更なし。
- RSS やプロセスツリーメモリの_保証_なし。Part 1 は ACP 子プロセスの V8 old space に
  上限を設ける; Buffer、ネイティブ割り当て、チャネルワーカー、MCP の子孫はその外。
- 当面の汎用スケジューリングレイヤーなし。spawn 時の受け入れは経路上にある——それは
  強制可能なライブ子プロセス予算が要求するもの——が、Part 2 のデータを待ち、重い I/O と
  プロセスレーンは並行性の増幅の証拠を待つ。「却下された代替案」参照。

## 設計原則

**上限を呼び出し元からの約束ではなく、コンテナの性質にする。**

呼び出し元が宣言する予約は呼び出し元の品質でしかない。#8093 の
`runBufferedProcessOperation(scheduler, budget, cwd, operation, maximumBufferedBytes, task)`
は呼び出し元が主張するバイト数を受け取り、プロセスの実際の出力と調整するものは何もない;
1 MB を宣言して 500 MB を出力する呼び出し元は、ヒープが増大する一方で台帳には健全と
報告させる。このパターンの汎用化は、数百の割り当て箇所すべてが、すべてのパスで推定、
予約、解放を、コンパイラの助けなしに、永久に覚えなければならないことを意味する。
カバレッジは部分的になる。部分カバレッジは無用ではない——どのパスが保護されているかを
status と capability が正確に名指すなら、それは問題なく普通のことである。これは #8093
自身の提供計画がすでに課している規律である。失敗モードは「部分的」より狭い: 不完全な会計の
上にデーモン全体の保証を広告するため、会計されているパスが 503 で作業を拒否し始める一方、
ヒープを枯渇させているのは会計されていないパスという事態になる。

この原則はすでにこの家の流儀であり、本リポジトリの最良の仕事はこれに従う:

- `readTextRangeFromHandle` は 2 つの**必須**バイト予算を取る——読み取りが返す量の
  `maxOutputBytes` と、コストの `maxScanBytes`——「呼び出し元がハンドルに手を伸ばすのは
  まさに読み取りに上限が必要なとき」だからである
  （[`2026-07-29-handle-bound-text-range-reads.md`](./2026-07-29-handle-bound-text-range-reads.md)）。
  チャンクごとにアキュムレーターをチェックする（フレームごとではない）。「改行のない領域は、
  ファイル全体が常駐するまで増加させ続ける」からである
  （`packages/core/src/utils/read-text-range.ts:350-353`）。
- `packages/cli/src/serve/fs/policy.ts:33-62` はソフト切り詰め（`enforceReadSize`）と
  ハード拒否（`enforceWriteSize`、`enforceReadBytesSize`）を分離し、`MAX_WRITE_BYTES` は
  パーサーを生き延びたボディがポリシーゲートを生き延びるよう Express のボディ上限より
  意図的に小さく設定されている。
- 上限付きリプレイウィンドウ（[`2026-07-07-bounded-replay-snapshot-window.md`](./2026-07-07-bounded-replay-snapshot-window.md)）
  は保持するリプレイをシリアライズバイトで上限化し、単一ユニットが上限を超えるときは
  少なくとも 1 ユニットを保持し、喪失をサイレントな切り詰めではなく明示的な
  `history_truncated` マーカーとして表面化する。その Audit Note ラウンド 3 は教訓を
  直接記録している: 「1 ターンが大きなツール出力を含む場合、ターン数の上限はメモリを
  制限しない。」

下記の作業はそれらを汎用化する。隣に 2 つ目のパラダイムを追加しない。

## 設計

### Part 1 — 1 つの予算、1 つの分母、適用前に報告する

デーモンのメモリ数値を 1 回解決して報告する。まだ何も子プロセスのサイジングに消費せず、
この自制は設計であってステージングの都合ではない。

```
availableMemoryMb        = cgroup 上限、なければ os.totalmem()          （ホスト総量でキャップ）
configuredBudgetMb  = --memory-budget-mb ?? floor(availableMemoryMb * 0.5)
effectiveBudgetMb   = min(configuredBudgetMb, availableMemoryMb)
rootReserveMb       = min(clamp(floor(effectiveBudgetMb * 0.1), 256, 1024), effectiveBudgetMb)
childPoolMb         = effectiveBudgetMb - rootReserveMb
legacyChildCeilingMb     = min(floor(availableMemoryMb * 0.5), 16384)     // 今日子プロセスが得る値
insufficientMemory  = effectiveBudgetMb < 1024
```

設定値と実効値が別々なのは、両方向に乖離するからであり、それらを統合すると機械が
裏付けられない分母が生まれる。ホストより大きい明示的予算はキャップダウンされる。
文書化された最小値より小さい導出予算はクランプ**しない**——以前のドラフトはまさにそれを
行い、768 MB のホストが結果として 1024 MB の予算を報告した。これは観測作業が計算しようとする
すべての比率を汚染する。小さすぎるホストは観測（`insufficientMemory`）であり、
キャパシティを捏造する免許ではない。

`recommendedChildShareMb(budget, children)` はエクスポートされ、登録数とライブ子プロセス数の
両方で報告される。決して適用しない。その 2 つの数値の差こそが、それらを報告する要点である。

#### なぜシェアを適用しないのか

プールをワークスペース数で割ることはそれ自身の条件で失敗する。本文書も以前はそれを
提案していた:

- **登録は割り当てではない。** ワークスペースランタイムは子プロセスを遅延 spawn し、
  `channelIdleTimeoutMs` のデフォルトは `0` — 「チャネルを即座に kill する」
  （`packages/acp-bridge/src/bridgeOptions.ts:415-422`）— なので、休止中のセカンダリには
  子プロセスがない。プリヒートされたプライマリが例外。
- **登録数の除数には実コストがあり、得るものはない。** 32 GB ホストで 25 の登録
  ワークスペース、ライブはプリヒートされたプライマリのみの場合、その子プロセスは
  16384 MB の上限から 614 MB に下がる——メモリを保持しない 24 の登録に起因する
  26.7 倍の削減。同時に子プロセスごとの下限のため、分割されたシェアの合計は依然
  プールを超える: 8 GB ホストでは、512 MB 下限の 25 子プロセスは 3687 MB のプールに
  対して 12800 MB を承認する。
- **動的な登録は健全な数を残さない。** 起動時の数は後続のワークスペースを見逃す;
  再計算は実行中の子プロセスの V8 ヒープを縮小できない; 現在の登録数は休止中の
  ワークスペースに不利になる。代わりに_ライブ_子プロセス数で割っても、上限は spawn 順に
  依存するようになり、依然として合計の上限はない。

真の制御は、同時にライブの子プロセス数をキーとした spawn 時の受け入れであり、
次の子プロセスがプールを超える場合に何が起こるかの明示ポリシーを伴う。それには
Part 2 が生成するデータが必要なので、推測ではなく延期する。

#### 子プロセスキャパシティポリシーが来たときに尊重すべきこと

- **`--max-old-space-size` は V8 の old space に上限を設け、RSS ではない。** Buffer、
  外部・ネイティブ割り当て、young 世代、チャネルワーカー、MCP の子孫、その他の子プロセス
  はカバーしない。ここでのポリシーは_子プロセスヒープのポリシー_であり、プロセスツリーの
  メモリ保証では決してなく、ルート確保はそれらのコンシューマーの会計ではなくヘッジである。
- **拒否なしでもシェアの適用は互換性変更である。** 子プロセスの GC と OOM の挙動を
  変えるからである。「レポートのみ」として出荷することはできない。
- **上限を引き上げてはならない。** `legacyChildCeilingMb` へのクランプこそが、このポリシーを
  無条件に適用しても安全にするもの; それがなければ最小予算定数と過大な明示フラグの両方が
  シェアを膨らませる。
- **spawn パスにはトラップがある。** `getAcpMemoryArgs()` は計算されたターゲットが
  _spawn するデーモン自身_の `heap_size_limit` を超える場合のみ `--max-old-space-size` を
  発行する（`spawnChannel.ts:27-34`）。予算由来のシェアは通常それより小さいため、
  素朴な変更はサイレントに落とされオーバーコミットが復活する。リグレッションテストは、
  フラグがテストプロセス自身の上限より小さい値で生き残ることをアサートしなければならない。

### Part 2 — 強制の前に、分母を持って観測する

既存の 5 秒サンプラーに、実効メモリ上限、`v8.getHeapStatistics().heap_size_limit`、
プライマリのみではなく**すべて**のワークスペース子プロセスとチャネルワーカーにまたがる
子プロセス RSS の合計を追加する。ステータスには `runtime.memory { level, ratio, source }` と、
`daemon-status.ts:70-85` のクローズド issue union に 2 つのコードを追加する。

モードフラグは確立された `--mcp-client-budget` / `--mcp-budget-mode` の慣例に従う:
`off | warn | enforce`、予算設定時のデフォルトは `warn`、`enforce` は後の変更がそれを
勝ち取るまで起動時に拒否される。この Part には修復措置はない。

これはバイト上限作業の前に意図的に昇格されている。これは唯一、その価値が設計の残りの
正しさに依存しない部分であり、後で選ぶすべての上限はそのデータに対して較正すべきであり、
推測すべきではない。#8093 の上限テーブルはこの順序付けに対して最初は見えるより弱い論拠
であり、弱い形こそが正直な形である: `prompt: 384 MiB` はまさに `normalAdmissionBytes`
であり冗長だが、256 MiB のカテゴリは死んで_いない_——単一カテゴリが 256 MiB に到達する
ことは、通常使用の合計が 384 MiB の上限に達するはるか前に拘束力を持つ。テーブルの問題は
単に定数が較正されていないことであり、それを修正するのが観測である。

### Part 3 — 実際に無制限のコンテナに上限を設ける

計測されたリスク順に、それぞれ独立に出荷可能。

**NDJSON フレームリーダーにはどんな上限もない。**
`packages/acp-bridge/src/ndJsonStream.ts:35` は `pending: Uint8Array[]` を宣言し、
`:92` で終端されていない末尾バイトを push し、個数もバイト総量も決してチェックしない。
`takeLineBytes`（`:96-111`）は累積総量の 1 つの連続コピーを割り当て、
`TextDecoder.decode` はその約 2 倍の UTF-16 文字列を生成し、`JSON.parse` はさらに
オブジェクトを構築する——上限のないフレームに対して約 5 倍の増幅。これは spawn された
すべての ACP 子プロセスの stdout の読み取り側であり、
`packages/cli/src/serve/large-pipe-frame-observer.ts:10` は 256 KiB を超えるフレームの
ログのみを取る。修正はチャンクごとにチェックされるフレームのバイト上限、デーモン管理
ストリームでの型付き致命エラー、そして `:33` のデコード済みメッセージ `ReadableStream`
でのキューイング戦略であり、それは `desiredSize` を決して参照せず、遅いコンシューマーの
背後にある 2 つ目の無制限バッファである。`createStderrForwarder`
（`spawnChannel.ts:58-72`、`[truncated]` マーカー付き 64 KiB）とチャネルワーカーの
ログバッファ（`channel-worker-supervisor.ts:67-69`）がリポジトリ内の手本。

**EventBus のリプレイリングはフレーム数のみで上限化する。**
`packages/acp-bridge/src/eventBus.ts:473` は `ring.length > ringSize` でエビクトし、
デフォルト 8000 フレーム、セッションごと、100 万まで調整可能。これは目立つ。リングの
周囲はすべてすでにバイト上限付きだからである: サブスクライバーごとのキュー 2 MiB、
リプレイバースト 8 MiB、ジャーナル 8 MiB、コンパクション済みリプレイ 4 MiB。
リングがギャップであり、上記の無制限フレームを 8000 倍する。シリアライズサイズは
`:459` で**すでに計算されスコープ内にあり**、そこでコンパクションエンジンに渡される;
それをリングに適用するのは、実行総計、両方の上限に対するエビクションループ、そして
コンパクションエンジンがすでに実装している少なくとも 1 つ保持の保証である。

**仮想サブエージェントのトランスクリプトは全体を読み込む。**
`packages/cli/src/serve/virtual-subagent-sessions.ts:331,385` は初回読み取り時に
`this.offset === 0` で `Buffer.alloc(size - this.offset)` を呼び出し、`.jsonl`
トランスクリプト全体と、別途 `.stream` サイドカー全体を実体化し、次に
`.toString('utf8')`、次に `.split('\n')`、次に行ごとのパースを行う。
`createSnapshotOnce`（`:593-620`）は 2 番目のターゲットを構築してトランスクリプト全体を
再読み込みし、2〜3 のライブコピーを残す。進行中のページングリーダーとバイトカーソル
パターンが置き換え先である。

**セッションの読み込みとエクスポートは非対称に上限化されている。**
`packages/cli/src/serve/server/session-export.ts:83-108` はアーカイブブランチではバイト上限を
渡すが、アクティブブランチでは `loadSession()` を上限なしで呼ぶ——デーモンの読み込みと
再開が使う同じ上限なしのパス。アーカイブの上限は 256 MB の JSONL で、これは 1〜2 GB の
オブジェクトにパースされるため、どちらのブランチも実際的な上限ではない。
`session-transcript-reader.ts` が正しいモデルであり、すでに存在する。

**ワークスペース提供の設定ファイルはサイズゲートなしで読み込まれる。**
ワークスペースの `.qwen/settings.json`（`packages/cli/src/config/settings.ts:557,733`）、
信頼フォルダー、serve のファストパス（同期的なのでイベントループもブロックする）、
そして発見されたすべての `QWEN.md` への `fs.readFileSync(path, 'utf-8')`、
20 件並行（`packages/core/src/utils/memoryDiscovery.ts:225,245`）。2 GB の
`settings.json` を含むワークスペースの登録は、セッションなし、プロンプトなし、
エージェントなしでデーモンを枯渇させる——このセットの中で最も安い攻撃であり、
ヒープ台帳が気づくものから最も遠い攻撃。

証拠付きで記録し延期: SSE と WebSocket の書き込みチェーンはバックプレッシャーを尊重するが
キューされたバイトに上限なし（`acp-http/sse-stream.ts:110-128`、
`ws-stream.ts:58-82`）; ACP のアタッチ前フレームバッファは EventBus の `maxQueued` は
反映するが `maxQueuedBytes` はしない（`connection-registry.ts:18,30`）; organized の
セッションリストは 50,000 のサマリーを実体化; 複数のワークスペースごとのキャッシュが
ワークスペースより長生きする。

### Part 4 — 多重性が重要な場所での小さな合計クォータ

コンテナに上限を設けることは 1 つのコンテナに上限を設けることである。_N_ 個に上限を
設けることではなく、デーモンの形状は多くの小さな上限付きのものである: ワークスペース
あたり 32 セッション、25 ワークスペース、それぞれ 8 MiB のジャーナルと 4 MiB の
コンパクション済みリプレイ。それらのすべてが文書化された上限内に収まりながら、
合計が数 GB に達しうる。したがって Part 3 だけでは合計の上限は生まれず、そうでないと言え
ば本文書が #8093 に対して批判した誤りを繰り返すことになる。

必要なのは狭いものである: 保持するリング、キュー、キャッシュ、並行する大きな操作に
対するワークスペースごとおよびプロセス全体のカウンターで、実際の挿入・削除ポイントで
更新される。2 つの性質がこれを #8093 の台帳に逆戻りさせない——推定の V8 オブジェクト
コストではなくコンテナが**実際に保持する**バイトを数えること、そして呼び出し元が覚え
なければならない別の予約呼び出しではなく、データ構造がすでに変更されている場所で
維持すること。`EventBus` の既存のサブスクライバーごとの `maxQueuedBytes` がコピーすべき
形; それはすでに正しく、単に集約されていない。

この Part のスコープと定数は Part 2 の後である。その定数がそうであるのと同じ理由で。

### 共有ヘルパー、2 人目のコンシューマーで抽出する

`truncateUtf8` はプライベートなコピーが 2 つ存在する。個数、バイト、TTL で上限化された
コンテナは 1 回は正しく実装され（`session-transcript-reader.ts:148-150`）、他では近似
されている。REST と ACP は 1 つの共有エラークラスセットに対して 2 つの手書きマッピングを
維持し、その中で独自の HTTP ステータスを持つ唯一のメンバーは `FsError`
（`fs/errors.ts:101`）。それぞれは本作業に 2 人目のコンシューマーが現れたときに
統合する価値があり、それ以前ではない。

## 却下された代替案

**ルートヒープに対するプロセス全体のバイト台帳（#8093 の `ResourceBudget`）。**
これはメモリがない場所に予算を付ける; そのヒーププロキシ定数は V8 と安定した関係がない。
V8 は文字列を rope、slice、外部データとして表現し、hidden-class の共有でオブジェクトを
価格付けするため、誤差はどちらの方向にも 2〜5 倍; そしてカテゴリはワークスペースごと
ではなくグローバルであり、#8051 が求めるテナント分離を提供しない。そのデフォルト自体が、
上記で指摘したように、計測なしに数値を選ぶことの難しさを示す。

ブランチを実行して確認した 2 つの実装特性は、後で再導出されないよう記録に値する。
`ResourceBudget.release()` と `ResourceBudgetLease.commitGrow()` はパブリックかつ未検証で、
1 回のはぐれ呼び出しが `usedBytes` を負にし、以降すべての上限がサイレントに拘束力を
失う; そして `grow()` は別の予算に属するリースを受け付け、両方を破損させる。別途、
`capBytes` が与えられると `emergencyPoolBytes` は `0` になる
（`resource-budget.ts:199-201`）ため、シャットダウンと過負荷応答を可能にするために
存在する確保が、まさにオペレーターが予算を設定したときに消える——それが
`--memory-budget-mb` のすることである。

**書かれたままの新しい公平スケジューリングレイヤー（`FairDaemonBulkScheduler` と
その spawn およびプロセスレーン）。** 上記で列挙したホットスポットはすべてサイズの問題;
並行操作を少なく受け入れることで修正されるものは 1 つもない。並行性のプリミティブはすでに
存在し使用中である: FIFO 受け入れ、`AbortSignal` でのキュー除去、早期スロット解放の
`runUntilReleased` を持つ `createFifoTaskQueue(limit)`
（`extension-operation-scheduler.ts:31`）; キー付きロックの `PathMutexRegistry`;
そして冪等な解放と型付きエラーによる個数受け入れの
`createTotalSessionAdmissionController`（`total-session-admission.ts:40-121`）で、
今日ワークスペースごとの隔離を提供している。

提案されたレーンには、基盤として採用することに反対する欠陥もある: `AbortSignal` は
受け取られるがタスクに転送されないため、リクエストのキャンセルはキューにいる間のみ
キュー除去し、実行中の子プロセスはスロットを保持する; ネストおよびレーン間取得は
`AsyncLocalStorage` 経由で継承されるすべての非同期作業に伝播するハードな 503 であり、
バルク操作が正当に spawn を必要とした最初の時点で失敗する; そして spawn とプロセス
レーンはワークスペースごとのアクティブ上限をグローバル上限と等しく設定するため、
1 つのワークスペースがすべてのスロットを占有できる。これはスケジューラーを排除する
のではなく延期して絞り込むべきケースであり、本文書の以前のドラフトはこれを誇張していた。
既存のプリミティブは完全な代替ではない: `createFifoTaskQueue` には待機上限も
タイムアウトもなく、`PathMutexRegistry` は無制限の promise チェーンを蓄積しうる、
`createTotalSessionAdmissionController` はセッション数を制限するが子プロセスの spawn、
ファイルシステムのデコード、外部プロセスは制限しない。より決定的には、**強制可能な
ライブ子プロセス予算には spawn 時の受け入れが必要**——それはまさにスケジューリング
レーンである。つまり spawn の受け入れは経路上にある; 重い I/O とプロセスレーンは
並行性の増幅やワークスペース間の飢餓を示す計測を待つべきであり、ワークスペースごとの
公平性が必要な場合は、既存キュー上のキー付きラウンドロビンがテスト済みプリミティブに
対しておよそ 40 行である。

**デーモンのリクエストパスへの `AsyncLocalStorage`。** 今日
`packages/cli/src/serve` や `packages/acp-bridge` にはない。ワークスペースの帰属はすでに
明示的に `WorkspaceRequestContext.workspaceCwd`
（`workspace-service/types.ts:68-77`）として、ファイルシステム境界を通じて `AuditContext`
として流れている。すでに明示的に運ばれているデータを運ぶために暗黙の伝播を追加するのは、
情報を追加せずに機構を追加することである。

## 互換性

インタラクティブ CLI、IDE コンパニオン、直接埋め込みブリッジのパスは不変: 1 つの
子プロセスを spawn し、ホスト由来の上限を保持する。

Part 1 は子プロセスの spawn 引数を変更しないため、どのホストでも子プロセスのサイジングの
仕方に変更はない。唯一の新しい起動時挙動は範囲外の `--memory-budget-mb` の拒否と、
予算が明示設定されたとき、またはホストが文書化された最小値を下回るときの stderr への
パンくずのみ。

ここに属する互換性の議論は、後に続く子プロセスキャパシティポリシーのものであり、
それとともに延期される。今言えるのは: そのポリシーは上限を引き下げ、決して引き上げない
こと、拒否なしでも互換性変更であること、実行中の子プロセスを縮小できない場合の
受け入れルールが必要なこと。

新しい拒否は導入されない。唯一の新しい起動失敗は、範囲外の `--memory-budget-mb` に対する
既存の検証形状。ワークスペース登録、永続化された復元、`POST /workspaces` は不変。

`maxSessions` と `maxTotalSessions` は現在のデフォルトと導出を保持し、本変更は新しい上限を
与えない。以前のドラフトは `workspaceCount` が予算でキャップされるため `maxTotalSessions`
は推移的に上限化されると主張していた; それは本 PR に対して誤りで、ワークスペースの
キャップは固定の `MAX_REGISTERED_WORKSPACES = 25` のままであり、予算から上限を導出する
ものは何もない。セッションは引き続きワークスペースごとに 1 つの子プロセスに多重化する
ため、セッションごとのメモリは V8 自身の上限以外何も上限を設けない子プロセスヒープの
中にある。`maxSessions` のドキュメントはメモリではなく、公平性とファイル記述子のレバー
として読むべきである。

`GET /daemon/status` の `limits.memory` と `runtime.memory` は SDK ミラーで加法的かつ
任意であり、古いデーモンが新しいクライアントに対してパースできる。

チャネルワーカーはワークスペースごとに `process.execPath` をメモリ引数なしで spawn する
（`channel-worker-supervisor.ts:823`）。それらはデーモンツリーのメモリの実際の
コンシューマーであり、子プロセスごとの上限ではカバーされない; ルート確保が名目上
それらをカバーし、Part 2 がそれらを計測する。

## 検証計画

- ホスト数値を注入し、制約あり/なしのホスト全体で予算計算をユニットテストする。
  子プロセスごとの下限、16 GB の上限、cgroup センチネルのクランプ、子プロセス数に対する
  子プロセスごとのシェアの単調性を含む。
- 予算由来の上限が spawn するデーモン自身のヒープ上限を下回る場合でも発行されることを
  リグレッションテストする。`getAcpMemoryArgs()` は現在、計算されたターゲットが現在の
  上限を超える場合のみ `--max-old-space-size` を発行する; 予算由来の値は通常小さいため、
  素朴な変更はフラグをサイレントに落としオーバーコミットを復活させる。これは最初の変更で
  最も重要な単一のテストである。
- 実効予算が解決されたホストメモリをどちらの方向にも超えないことをアサートする:
  ホストを超える明示的予算はキャップダウンされ、文書化された最小値を下回るホストは
  クランプアップではなく `insufficientMemory` を報告する。アドバイザリシェアが 768 MB
  から 32 GB のホストサイズ全体で `legacyChildCeilingMb` を超えないことをアサートする。
- 子プロセスの spawn 引数が変わらないことをアサートする: 既存の spawn スイートが
  無変更でパスし、この段階で `getAcpMemoryArgs` は未変更。
- エンドツーエンド: いくつかの `--workspace` 値で起動し `GET /daemon/status` を読む;
  `limits.memory` はホストを正直に記述し、ワークスペースがアイドルになると
  `runtime.memory` は `activeAcpChildren` が `registeredWorkspaces` 以下であることを
  示すべき——後のポリシーをライブ子プロセスをキーにする正当化となる観測。
- Part 2 については、cgroup v2、cgroup v1、どちらでもない環境で有限の比率をアサート;
  レベル分類をアサート; 修復パスが存在しないことをアサート; 子プロセス RSS の合計に
  セカンダリワークスペースとチャネルワーカーが含まれることを確認。その後、実際の使用下で
  デーモンを実行して結果を読む——そのデータが Part 3 を較正する。
- Part 3 の各変更について、受け入れテストは実際のサイズ超過入力に対する前後比較である:
  数 GB の単一 NDJSON フレーム、大きなイベントの 8000 フレームリング、2 GB の
  `settings.json`。デーモンは RSS が横ばいのまま型付きエラーで拒否しなければならず、
  今日はプロセスが死ぬまで増大する。その証拠が要点である: 台帳が内部的に整合することを
  示すテストは、メモリに上限があることを示すテストではない。
- すべての変更で `npm run build`、`npm run typecheck`、`npm run lint`、加えて触った
  ファイルの近接スイート。
