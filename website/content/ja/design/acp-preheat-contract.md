# ACP プリヒートの契約と互換性

## 背景

デーモンは `POST /workspace/acp/preheat` と `GET /workspace/acp/status` を公開しているが、リリース済みのクライアントは `/capabilities` 経由でこれらのルートを発見できない。TypeScript SDK もまた、これらがデーモンの REST コントロールプレーンのルートであるにもかかわらず、デフォルトで両方の呼び出しをアクティブな ACP トランスポート経由で送信する。さらに、タイムアウトした HTTP ウェイターは、基盤となるチャネルの初期化が継続しているにもかかわらず、現在、ワークスペースサービスの共有プリヒート promise をクリアしてしまう。

この変更は、既存のプライマリワークスペースのルートを発見可能かつ信頼性の高いものにする。永続的な準備完了状態の導入や、最初の Session バリアの移動は行わない。Session は引き続き権威ある操作である: プリヒートと Session の作成は、ブリッジの共有チャネル初期化を通じて合体（coalesce）し、Session の作成は、任意の時点のステータスまたはプリヒートレスポンスの後にチャネルを再検証する。

## capability とスコープ

デーモンは、常に有効な 2 つの v1 capability タグを通知する:

- `POST /workspace/acp/preheat` に対する `workspace_acp_preheat`
- `GET /workspace/acp/status` に対する `workspace_acp_status`

各タグは、名前の付いたルートの契約が存在することを意味する。どちらのタグも、ACP チャネルが現在ライブであることを示すものではない。ルートは引き続き単一かつプライマリワークスペース専用である。クライアントは、これらをセカンダリワークスペースに使用したり、セカンダリワークスペースからプライマリランタイムへフォールバックしたりしてはならない。

ワークスペース修飾された ACP ウォームアップには、個別の所有権、信頼、drain、リソース制限のセマンティクスが必要であり、この変更の範囲外である。

## レスポンスのセマンティクス

`GET /workspace/acp/status` は時点スナップショットを返す:

```ts
{
  channelLive: boolean;
}
```

`POST /workspace/acp/preheat` は既存のレスポンス形状を維持する:

```ts
interface WorkspaceAcpPreheatResult {
  ready: boolean;
  channelLive: boolean;
  durationMs: number;
  reason?: 'timeout' | 'error';
  error?: string;
}
```

以下の不変条件が適用される:

- `ready` は常に `channelLive` と等しい。
- ライブなスナップショットは、`reason` や `error` なしで `ready: true` を返す。
- ウェイターのタイムアウトは、レスポンス構築時にチャネルがまだライブでない場合にのみ `reason: 'timeout'` を返す。
- 初期化の失敗、またはライブなチャネルを生成しなかった解決済みのプリヒートは、`reason: 'error'` を返す。
- `durationMs` は単調時計で測定された有限の非負整数である。これは現在の HTTP 呼び出しの経過時間であり、呼び出しが参加した可能性がある共有初期化の存続期間ではない。
- クライアントに表示されるエラーテキストは安定し、サニタイズされている。詳細な子プロセスのエラーはデーモンのログに残る。

操作上のタイムアウトと初期化の失敗は、既存のクライアントが結果を検査できるように、引き続き HTTP 200 を使用する。無効な入力、認証、レート制限、deferred runtime の起動失敗は、既存の HTTP エラー契約を維持する。

## 並行性と失敗時の挙動

ワークスペースサービスは、promise が確定するまで 1 つの共有プリヒート promise を保持する。すべてのリクエストが、同じ promise を自身のタイムアウトと競わせる。ウェイターのタイムアウトはそのリクエストのみを終了させ、ブリッジの操作をキャンセルすることも、共有 promise をクリアすることもない。確定処理は、その識別子が現在の共有操作とまだ一致する場合にのみ promise をクリアするため、古い完了が新しい試行を消去することはできない。

共有操作が確定した後、チャネルがライブでない場合は、後続のリクエストがリトライできる。正常なレスポンスの後に終了したチャネルはリースの対象外である: ステータスは新しいスナップショットを報告し、次の Session またはプリヒートが新しいチャネルを開始する。

## クライアント互換性

TypeScript SDK は、設定された ACP トランスポートに関係なく、両方のルートを REST fetch パス経由で送信する。capability を自動的にフェッチすることはなく、呼び出し元がいつプリフライトを行うかを決定する。

Web UI は、これらのルートを deferred のセッションなしブートストラップフローでのみ使用する。`workspace_acp_preheat` を必須とし、オプションのステータス最適化を `workspace_acp_status` でゲートし、実効ワークスペースが `capabilities.workspaceCwd` と完全一致することを要求する。完全一致の比較は、プライマリパスの別表記に対するプリヒートを保守的にスキップすることはあるが、誤ったランタイムをウォームアップすることはない。

古いデーモンが capability を省略する場合、Web UI は ACP のステータスやプリヒートのリクエストを行わず、最初の Session は既存の遅延初期化パスに従う。プリヒートの失敗は引き続きベストエフォートであり、接続や Session の作成を失敗させることはない。

## 非ゴール

- 最初の Session の前にプリヒートを待機すること
- デーモンや Web UI の起動においてプリヒートをより早い段階へ移動すること
- 準備完了のリース、世代、トークン、プロトコルバージョンの引き上げ
- HTTP ウェイターのタイムアウト時に共有チャネル初期化をキャンセルすること
- ワークスペース修飾された ACP のプリヒートやステータスのルート
- この契約のみの変更によるレイテンシ改善を主張すること
