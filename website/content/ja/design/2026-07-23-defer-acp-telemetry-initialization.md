# ACP テレメトリー初期化をプロトコル初期化の後まで遅延する

- **Issue**: #7264 候補 2
- **スコープ**: テレメトリーが有効な ACP 子プロセスの起動
- **Status**: 実装・検証済み

## 問題

ACP 子プロセスは現在、`Config` コンストラクタからテレメトリーを開始します。この呼び出しは fire-and-forget ですが、テレメトリー実装と設定されたエクスポーターチェーンの読み込みと評価は、CLI ブートストラップ、ACP モジュール読み込み、ブートストラップ設定の初期化、プロトコルの `initialize` ハンドラーと同じイベントループと CPU を奪い合います。制約のあるホストでは、候補 1 の計測により、この競合がユーザーに見える初期化ウィンドウに作業を戻してしまうことが示されました。

テレメトリーイベントはすでに初期化済みゲートを使用しています: SDK の起動完了前に発行されたイベントはドロップされます。したがって、開始を遅延させることは、新しいバッファリングや順序付けモデルを導入するのではなく、既存の損失ウィンドウを延ばすだけです。

## 設計

ACP の設定は既存の `deferTelemetryInitialization` オプションを設定します。これは、デフォルト、ヘッドレス、stream-JSON、インタラクティブ TUI、デーモンランタイムのパスを変更せずに、コンストラクタの fire-and-forget 開始を抑制します。

`runAcpAgent` は、その NDJSON トランスポート上の既存のメッセージ観測フックを使用して、着信した `initialize` リクエストの JSON-RPC ID を記憶します。このフックは、parse されたリクエストがキューに入れられた後、その保留中の読み取り継続がそれを処理できる前に実行されます。送信メッセージについては、同じフックが、エンコードされたレスポンスが基盤の stdout ストリームに正常に書き込まれた後にのみ実行されます。記憶された ID を持つ正常なレスポンスが観測されると、子プロセスは既存のシングルフライトファサードを通じてテレメトリーを開始し、その初期化が確定した後にのみイベントループゲージを登録し、記憶された ID をクリアします。メトリクス API は、SDK がグローバルなメータープロバイダーをインストールする前にゲージが登録されると no-op メーターをキャッシュしてしまうため、この順序付けが必要です。

これにより、トランスポートによって定義された境界が生まれます: テレメトリーの読み込みは、初期化レスポンスの書き込みが解決する前に開始できません。これはイベントループのスケジューリングの仮定に依存しません。

## 所有と下流の利用側

ACP 子プロセスは、プロセスグローバルなテレメトリー SDK を 1 つ、ブートストラップ `Config` を 1 つ持ちます。遅延オプションは設定スコープであり、最終的な初期化側はプロセスグローバルでシングルフライトです。セッションごとの設定は、そのプロセスグローバル SDK を共有し続け、独立したテレメトリーランタイムを所有しません。

影響を受ける利用側は以下のとおりです:

- **ACP ブートストラップ子プロセス**: コンストラクタ開始のテレメトリーから、レスポンス書き込み開始のテレメトリーに変更されます。そのイベントループゲージの登録は SDK 初期化の後ろに移動され、早期の登録がすべてのメトリクスを恒久的に無効化できないようにします。
- **ACP セッション作成とプロンプト**: 既存の初期化済みゲートを保持します; SDK の読み込みが完了するまで、非常に早期のイベントがより長くドロップされる可能性があります。
- **通常のインタラクティブ TUI**: `startPostRenderPrefetches` による、最初の描画後の起動を保持します。
- **ヘッドレスおよび stream-JSON CLI**: コンストラクタでの起動を保持します。
- **`qwen serve` の親/デーモンランタイム**: 明示的な遅延コアランタイム初期化とシャットダウンを保持します。
- **プロセス終了時のクリーンアップ**: `Config.shutdown()` を保持します。プロトコル初期化の成功前に切断した子プロセスは、テレメトリーを決して開始しません。切断が開始直後のインポートと競合した場合、初期化側の内部 catch が未処理の reject を防ぎ、ACP の外部パスは引き続きプロセスを終了させます。`shutdownTelemetry()` は実行中の初期化側を await できますが、`Config.shutdown()` は SDK が初期化済みと報告した後にのみそれを呼び出すため、現在、設定のクリーンアップは、まだ実行中の初期化をスキップできます。

## 失敗と互換性の動作

- テレメトリー無効は、レスポンス後もファサードの no-op のままで、重いテレメトリーモジュールを読み込みません。
- 最初の `qwen-code.auth` イベントと 1 つの早期 `qwen-code.config` イベントを含む、レスポンス前に発行されたワンショットのブートストラップイベントは、単に遅延するのではなく、ACP テレメトリーから恒久的に欠落します。これは SDK 初期化をレスポンスの後ろに移動することの受け入れられたコストです; この変更は代替イベントの合成やバッファリングを行いません。
- 不正な形式または拒否された `initialize` リクエストはテレメトリーを開始しません。後続の正当な initialize リクエストは引き続き開始できます。
- stdout の書き込み失敗は送信済みメッセージフックを実行しないため、クライアントが受信しなかったレスポンスに対してテレメトリーが開始されることはありません。
- リクエスト ID と正常なレスポンスの形式の両方が一致する必要があるため、繰り返しまたは無関係な JSON-RPC レスポンスはテレメトリーを開始できません; 記憶された ID は一度だけ消費されます。
- SDK の読み込みは fire-and-forget でベストエフォートのままです。その既存の実装は、インポート、アセンブリ、起動の失敗をキャッチします。
- プロトコルの形式、ケーパビリティ、認証のタイミング、プロバイダー選択、MCP の動作、テレメトリー設定サーフェスに変更はありません。

## 却下された代替案

- **`QwenAgent.initialize()` 内で開始する**: これはハンドラーが返る前、したがって SDK がレスポンスをシリアライズして書き込む前である。
- **ハンドラーが返った後に `queueMicrotask`、`setImmediate`、またはタイマーを使用する**: いずれも SDK の非公開の書き込みキューが完了したことを証明せず、タイマーは恣意的なレイテンシポリシーを追加する。
- **`AgentSideConnection` をラップまたはフォークする**: パッケージローカルの NDJSON ストリームはすでに書き込み後のメッセージ観測を公開しているため、不要。
- **最初のセッションレスポンスまで待つ**: より多くの競合を取り除ける可能性があるが、ドロップされるイベントのウィンドウを候補 2 を超えて広げ、アイドル状態で初期化済みのチャネルではテレメトリーを決して初期化しない。
- **早期のテレメトリーをバッファリングする**: テレメトリーのセマンティクスとメモリの所有を実質的に変更する; 候補 2 は早期イベントのドロップを明示的に受け入れている。

## 検証

ユニットテストは、ACP 設定の遅延と正確なトランスポートの順序付けをカバーします: 受信時、無関係なレスポンス、エラーレスポンス、書き込み失敗時には開始しない; 一致する正常なレスポンスが書き込まれた後に 1 回開始する。既存のトランスポートテストは、送信済みフックが基盤の書き込みの後に実行され、書き込み拒否時にはスキップされることを証明します。

リリースバンドルは、テレメトリー有効/無効の両方で、実際の ACP 親/子パスを通じて実行されます。互換性チェックは、コールドおよびプリヒート済みのチャネル、並行する最初のセッション、レガシー単一セッションモード、早期切断、クリーンアップ、outfile レコードの生成をカバーします。

この変更は、#7264 の 2C4G ゲートを通過した場合のみマージされます: 30 回の交互ペアシリアルコールドスタートにより、`channel.initialize`、子プロセスから initialize レスポンスまで、コールドセッションリクエスト、process から最初のセッションまで、ピーク RSS、プリヒート済みの動作、テレメトリーオン/オフの互換性を報告します。作業が消えるのではなく後へ移動するため、ゲートは初期化と最初のセッションの両方のタイミングを報告しなければなりません; 最初のセッションの前に返済されてしまうだけの改善は、成功した最適化として扱われません。

## 結果

コントロールは `origin/main` の `14f1f2bb365280a6e1d4a45b452f7992f1928187` でした; 候補は同じコミットにこの正確な作業ツリーの変更を加えたものです。両方のリリースバンドルは同じ lockfile からビルドされ、提供された Linux ホスト（2 vCPU、約 3.5 GiB RAM、スワップなし、バンドルされた Node.js 22.23.1）でテストされました。

outfile テレメトリーを有効にして、30 回の交互ペアコールドスタートの結果:

| メトリクス                               | コントロール P50 / P95  | 候補 P50 / P95 | P50 差分    |
| ------------------------------------ | ------------------ | ------------------- | ------------ |
| `channel.initialize`                 | 942.1 / 1245.0 ms  | 898.3 / 1002.4 ms   | **-43.8 ms** |
| 子プロセスから initialize レスポンスまで | 947.0 / 1249.8 ms  | 903.0 / 998.4 ms    | **-43.9 ms** |
| コールド `POST /session`                 | 1235.5 / 1591.7 ms | 1245.1 / 1462.0 ms  | +9.6 ms      |
| Process から最初のセッションまで             | 1833.1 / 2190.6 ms | 1845.5 / 2417.0 ms  | +12.4 ms     |
| ピーク RSS                             | 418.7 / 443.6 MiB  | 406.7 / 438.4 MiB   | -11.9 MiB    |

ペア分布では、`channel.initialize` は 30 ペア中 26 ペアで高速、ペア中央値の差分は -44.2 ms でした。コールドセッションリクエストと process から最初のセッションまでのペア中央値の差分はそれぞれ +15.0 ms と +13.8 ms で、候補の勝利は 13/30 ペアと 11/30 ペアでした。process から最初のセッションまでのペア中央値のブートストラップ 95% 区間は -2.8〜+27.5 ms であり、したがってこの実行ではエンドツーエンドのリグレッションも改善も確立されませんでした。したがって、この変更は ACP 初期化境界の直接の実益のみを主張します。

同じ実行の 30 ペアのプリヒートフェーズでは、`channel.initialize` は P50/P95 が 950.5 / 1323.7 ms から 908.4 / 964.4 ms に改善しました。すでにプリヒート済みのセッションリクエストは 82.1 / 94.8 ms から 83.7 / 131.6 ms に変化し、process からセッションまでは 3683.5 / 4105.0 ms から 3686.1 / 3749.2 ms に変化しました。ペアのセッションと process-to-session の中央値はそれぞれ +1.4 ms と +1.0 ms でした。2 つの孤立した候補のセッション外れ値といくつかのコントロールの初期化外れ値が、ペアになっていない P95 値を広げました; ペア中央値は中立のままでした。プリヒート済みのメモリ変化は主張しません。

候補の機能実行は、並行する最初のセッション、ゼロレコードのテレメトリー無効、レガシー単一セッションモードをパスしました。テレメトリー有効のベンチマーク実行 120 件すべてが、有効なスタートアッププロファイルと空でない outfile を報告し、すべての実行が残存プロセスなしで終了しました。公式 ACP クライアントを通じたリリースバンドルのスモークは、追加でメトリクスエクスポート間隔を超えて待機し、`qwen-code.session.count` と `qwen-code.acp.event_loop.lag` の両方を確認し、キャッシュされた no-op メーターへの登録をガードしました。利用可能な OpenAI 互換エンドポイントに対するテレメトリー有効のライブプロンプトスモーク 2 件は、いずれも完了し、空でないテレメトリー outfile を生成しました。バンドル ACP の直接スモークテストも、早期切断の両方の境界をパスしました: initialize 前の EOF は、テレメトリーを開始せずにクリーンに終了し、正常な initialize レスポンス直後の EOF は、outfile を作成した後クリーンに終了し、どちらの場合も stderr の出力はありませんでした。
