# Channel Delivery V1

## ゴール

スケジュールタスク、デーモンプロンプト、および直接の Notify API が、選択されたワークスペースを所有する Channel Worker を通じて、明示的な IM ターゲットにテキストを送信できるようにする。配信は即時かつベストエフォートである: 永続的な outbox、リプレイ、リトライ、グローバルな最終回答フックは存在しない。

## 公開契約

```ts
interface ChannelDelivery {
  kind: 'channel';
  target: {
    channelName: string;
    type: 'user' | 'chat';
    id: string;
  };
}
```

スケジュールタスクの作成と `POST /session/:id/prompt` は、任意のトップレベル `delivery` を受け付ける。直接通知は次を使用する:

```http
POST /workspace/notify
POST /workspaces/:workspace/notify

{
  "text": "alert text",
  "delivery": {
    "kind": "channel",
    "target": {
      "channelName": "dingtalk",
      "type": "user",
      "id": "platform-user-id"
    }
  }
}
```

デーモンは、公開ターゲットをその信頼境界において、内部の worker リクエスト `{ deliveryId, channelName, target: { type, id }, text }` に正規化する。worker に送信されるテキストは空であってはならず、IPC の前に 100,000 UTF-16 コード単位に制限される。Prompt と scheduled のリバース制御は、配信可能な最終回答のない正常なターンを `skipped` として報告するためだけに、空文字列を運ぶ場合がある。そのパスが worker IPC に到達することは決してない。

## 実行の境界

スケジュールタスクと Prompt は、自身の最終回答のセマンティクスを所有する。Session は、現在の呼び出しが delivery メタデータを運ぶ場合にのみテキストをキャプチャする。各モデル送信は 1 つのレスポンスブロックを所有する: thought 以外のストリームチャンクはそのブロック内で結合され、continuation ではないリトライやモデルフォールバックは置き換えられたチャンクを破棄し、ツールを要求するブロックはすべて中間的なものであり、配信ペイロードになることはない。後続の自動 continuation は、それ以前の終端候補を置き換える。完全なターンが正常な `end_turn` に達した後、Session は、ツールを含まない最後の assistant レスポンスブロックのみを含む、ただ 1 つのリバース制御リクエストを送信する。ツール間のナレーションと、それ以前のすべてのレスポンスブロックは除外される。

正常な `end_turn` は、最終ブロックが空または空白のみの場合を含め、常にリバース制御リクエストを送信する。デーモンはピン留めされた認可を最初に消費し、worker を解決せずに `skipped` を返し、`channel_delivery_result` イベントを発行する。キャンセル、Agent の失敗、トークン上限による終了は何も送信しない。したがって空の出力は、配信の対象となること自体がなかったターンと区別できる。

Prompt の受け入れは引き続き `202`、Agent の完了は引き続き `turn_complete` または `turn_error` である。チャネルの完了は後続の `channel_delivery_result` イベントであり、Agent の成功を `turn_error` に変換することは決してない。

Notify は Session と Agent をバイパスする。1 回の worker 配信試行を待ち、無効な入力は 400 に、利用不可または満杯の worker は 503 に、タイムアウトは 504 に、アダプターの失敗は 502 にマップする。タイムアウトは配信結果が不明であり、リトライされない。

Webhook は、独自のシークレットと `202` の worker 受け入れ契約を持つ、独立した非同期パスのままである。`ChannelBase` の送信プリミティブとエラー分類を再利用する場合があるが、Prompt/Notify の制御フローは再利用しない。バックグラウンドの通知プロンプトは引き続きローカルな Agent の作業であり、自動的に IM へ送信されることはない。

## ワークスペースの所有

デーモンは、各 ACP ブリッジの構築時にワークスペースをバインドする。Prompt の受け入れは、デーモンが発行した delivery ID とピン留めされたターゲットを記録し、scheduled の配信は永続化されたタスクから認可される。子プロセスのコールバックはその認可と一致しなければならず、`workspaceCwd` を選択したり、ターゲットを置き換えたりすることはできない。ホストのコールバックは、`skipped` と worker 配信のどちらにするかを決定する前に認可を消費するため、空の最終回答がイベントを偽装したり、one-shot／単調な認可の状態を変更せずに残したりすることはできない。空でないテキストは、正規のワークスペースの worker グループにのみルーティングされる。欠落、ブートストラップ中、drain 中、停止済み、または削除済みのオーナーは `channel_worker_unavailable` を返し、プライマリランタイムへのフォールバックも、worker の遅延起動もない。

## 信頼性とプライバシー

認可は worker の可用性チェックの前に消費されるため、消費後の一時的な worker の瞬断は、その 1 件の配信を永続的にドロップする。これは、即時、ベストエフォート、リトライなしの契約と整合する。

この V1 には、永続化、起動時のリプレイ、履歴スキャン、リトライ、冪等性の保証はない。delivery を持たない既存のタスクは送信を行わない。既存のスケジューラーの catch-up 挙動は変更なし。通常の実行は、タスクがすでに delivery を含んでいる場合にのみ delivery を運ぶ。合成された過去の missed-one-shot バッチは delivery を明示的にクリアするため、後で Channel を有効にしても古いアラートの集中発生が起きることはない。

V1 は Channel の送信 Promise のみを観測する。拒否はサニタイズされて `channel_delivery_failed` にマップされるが、型付きの永続的な処遇をすでに提供しているアダプターは `channel_delivery_rejected` にマップされる。プロバイダー固有のレスポンス解析と、IM アダプター間での一貫したエラー理由のセマンティクスはフォローアップの作業である。デーモンと worker にプラットフォーム固有のエラー処理は含まれない。

配信結果のイベントとログには、相関識別子、ソース、ステータス、サニタイズされたエラーデータが含まれる。メッセージ本文、ターゲット ID、認証情報、webhook シークレットは決して含まれない。`delivered` はアダプターの送信 Promise が解決したことを意味し、プロバイダーがメッセージを受け入れたことや、ユーザーが受信・閲覧したことを主張するものではない。

## capability

デーモンは、契約とルートをサポートする場合に `channel_delivery` を通知する。これはプロトコルのサポートであり、worker やアダプターのライブな健全性の主張ではない。
