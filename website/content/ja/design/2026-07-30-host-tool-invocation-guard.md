# ホストのツール呼び出しガード

## ステータス

issue [#8102](https://github.com/QwenLM/qwen-code/issues/8102) と PR [#8032](https://github.com/QwenLM/qwen-code/pull/8032) のドラフト設計。

## 問題

インプロセスの埋め込みホストは、既存のパーミッションとフックを通じてモデルが提案した
ツール呼び出しを評価できるが、それらのチェックは Qwen Code が正規のツール名を解決し
最終的な呼び出しパラメータを構築する前に実行されうる。したがって組織ポリシーを強制する
ホストは、`invocation.execute()` に到達したのと同じ呼び出しを評価したことを証明できない。

欠けているプリミティブは、実行されるツール呼び出しに対する最終実行境界の判定である。
製品固有のタスク状態、承認ワークフロー、ポリシーストレージ、監査トランスポートは
Qwen Code に属さない。

## ゴール

- インプロセスホストが `ConfigParameters` を通じて 1 つの許可/拒否関数を
  提供できるようにする。
- 正規のツール名とクローンされた最終呼び出しパラメータを、実行直前に評価する。
- コアスケジューラー、ACP セッションランタイム、投機的実行パスをカバーする。
- 設定されたガードが拒否、スロー、不正形式の判定の返却、またはクローンされた引数を
  受信できない場合、fail closed（失敗時は拒否）とする。
- ガードが未設定の場合、既存の実行パスを保持する。
- ガードの待機前または待機中にキャンセルが発生した場合、実行を防ぐ。

## 非ゴール

- CLI フラグ、設定キー、環境変数、デーモンルート、ネットワーククライアント、
  外部ポリシートランスポートはなし。
- タスク、プラン、grant、ビジネス認可、監査スキーマはなし。
- パミッション、フック、サンドボックス、承認モードのセマンティクスに変更なし。
- モデルのプランニングやツール実装が決定論的になるという主張はなし。
- 結果コールバックやパラレルなツール結果プロトコルはなし。
- Config 所有ランタイムの外側で `ToolInvocation.execute()` や `Tool.buildAndExecute()` を
  手動呼び出しする SDK コンシューマーのインターセプトはなし。

## 契約

ホストは `ConfigParameters` に `ToolInvocationGuard` を提供する。ガードが受け取るのは:

- ランタイムが受け入れたツール呼び出しの相関識別子;
- 正規のツール名;
- 最終呼び出しパラメータの構造化クローン;
- 呼び出しの abort シグナル。

判定は `{ allowed: true }` または `{ allowed: false, reason? }` のいずれか。拒否理由が
欠落または空の場合は安定した汎用メッセージを使用する。例外、不正形式の判定、クローン失敗は
別の安定した失敗メッセージを使用し実行を拒否する。提供された拒否理由はユーザー可視であり、
既存のツール結果やテレメトリーサーフェスに入りうるため、秘密情報や生のプロバイダーエラーを
含んではならない。

クローンされた引数により、ガードが Qwen Code の実行する呼び出しを変更することを防ぐ。
この契約は任意のツール引数を秘密にするものではない; 埋め込みホストはそれらを機密の
アプリケーションデータとして扱わなければならない。

ツール呼び出し識別子はモデルレスポンスに由来しうる。ガードの判定と既存のライフサイクル
イベントの相関に有用だが、認証された主体でも独立した冪等性キーでもない。強い identity が
必要な managed ホストは、ホスト所有のセッションおよびプロンプトの identity に
バインドしなければならない。

## 実行の配置

コアスケジューラーは、ツール構築、パーミッション処理、パス正規化、`PreToolUse` の後、
呼び出しが `executing` に変わる前、かつ `invocation.execute()` の前にガードを評価する。

ACP セッションは、ツール構築、パーミッション処理、`PreToolUse` の後、その直接の
`invocation.execute()` パスの前に同じ契約を評価する。

実験的な speculation エンジンも、コアスケジューラーを使わず呼び出しを直接実行する。
呼び出し構築後に同じガードを評価し、拒否やキャンセルをエグゼキューター呼び出しゼロの
speculation 境界に変換する。将来の managed 外部プロバイダーモードでは、オーバーレイを
実際のファイルシステムにコピーすることは `invocation.execute()` の外にある別の効果境界
であるため、speculation の apply を無効化しなければならない。

3 つのパスすべてがモデル提供のドラフト引数ではなく、構築された呼び出しパラメータを
使用する。コアと ACP のパスでは、拒否はエグゼキューター呼び出しゼロと構造化された
`execution_denied` ツール結果を生成する。

`ToolInvocation` を直接実行する将来の Config 所有ランタイムは、同じガードを評価するか、
すでにガードされたスケジューラーを経由しなければならない。これはコードレビューの不変条件
であり、任意の外部呼び出し元をインターセプトできるという主張ではない。

エージェントディスパッチの 2 つの呼び出し箇所 — `/fork` スラッシュコマンドと ACP の
エージェント fork ハンドラー — は、ガードに相談せずにエージェントのツール呼び出しを
直接構築・実行する。spawn されたサブエージェントは呼び出し元の `Config` を共有するため、
サブエージェント自身が呼びすすべてのツールはガードされる; ガードされないのはディスパッチ
呼び出し自体のみ。将来の変更でガードをこれらの箇所にも拡張しうる。

## デフォルト off の互換性

Qwen Code は CLI やデーモンのブートストラップで `toolInvocationGuard` を設定しない。
このフィールドはインプロセス埋め込み API のみ。

各実行パスは任意のコールバックを読み取り、コールバックが存在する場合のみ非同期の
評価器に入る。不在の場合、Qwen Code はガードの promise 割り当て、引数クローン、
プロバイダー呼び出し、capability 広告、追加の非同期 yield を行わない。したがって既存の
CLI とデーモンのデプロイは以前の実行パスを保持する。

リポジトリ内のプロダクション setter を意図的に不在にしていることは、本変更がマージ前に
パブリックな埋め込みシームについてメンテナの合意を必要とすることを意味する。
将来の外部プロバイダー変更は引き続き別の PR でなければならず、本 PR の承認の一部として
前提にできない。

## キャンセルと失敗のセマンティクス

評価器は、ガード呼び出し前とその promise が確定した後の両方でキャンセルをチェックする。
各実行パスも await 直後かつエグゼキューター呼び出し前にアクティブなシグナルをチェックする。

- 評価前のキャンセル: ガードもエグゼキューターも呼び出さない;
- ガード待機中のキャンセル: キャンセルを記録しエグゼキューターを呼び出さない;
- 明示的な拒否: `execution_denied` を記録しエグゼキューターを呼び出さない;
- ガード例外、不正形式レスポンス、クローン失敗: fail closed でエグゼキューターを
  呼び出さない。

自動リトライはない。ガードコールバックはプロバイダー固有のリトライポリシーを所有するが、
埋め込みホストはこの API 経由で曖昧な副作用をリトライまたは実行してはならない。

## 証拠

ユニットおよび統合テストのカバー範囲:

- 設定された許可および拒否の判定;
- デフォルトの拒否理由;
- ガード例外、不正形式レスポンス、クローン失敗;
- 引数変更の隔離;
- ガード評価前および評価中のキャンセル;
- コアと ACP パスでの最終正規化引数;
- speculation 実行が拒否時に境界で停止すること;
- 拒否およびキャンセル時のエグゼキューター呼び出しゼロ;
- コアと ACP のツール結果レコード間の `execution_denied` 同値性;
- 周囲のスケジューラーおよび ACP スイートを通じた既存の未設定実行。

本 PR は CLI、設定、デーモンルート、その他のユーザーが有効化できる挙動を追加しないため、
E2E プランは不要。マージ前のクロスプラットフォーム CI は引き続き必須。

## フォローアップの境界

将来の外部ポリシープロバイダーは、信頼できるランタイム所有のセッションおよびプロンプトの
identity でコンテキストを拡張し、`qwen serve` から ACP 子プロセスの境界をまたいで
インプロセスコールバックを適応させうる。そのフォローアップはデフォルト off で、
独立してレビューされ、未設定の CLI とデーモンがプロバイダーを初期化せず、
子プロセス環境を変更しないことを証明しなければならない。

結果の観測は、別の issue が具体的な相関ギャップを示さない限り、既存の構造化ツール
ライフサイクルイベントを再利用すべきである。製品固有のオーケストレーションとポリシーは
引き続き Qwen Code の外。
