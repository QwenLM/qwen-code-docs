# ACP チャネル initialize のプロファイリング

## サマリー

デーモンの `channel.initialize` スパンは ACP 子プロセスの spawn 後に開始し、子プロセスが
ACP の initialize レスポンスを返したときに終了する。したがって Node と ESM の起動、
CLI ブートストラップ、ACP モジュール読み込み、ブートストラップの `Config.initialize()`、
トランスポートのセットアップ、initialize ハンドラーを含む。ハンドラー自体は capability を
返すのみで、観測されたレイテンシを説明することは期待されていない。

本設計は、ACP の initialize レスポンスに固定のオプトインの子プロセス起動プロファイルを
追加し、検証された所要時間を既存の親の `channel.initialize` スパンにコピーする。
チャネルの準備完了、初期化の順序付け、失敗処理、セッションの挙動は変更しない。

## プロトコル

ブリッジは initialize リクエストのメタデータを通じてプロファイルのバージョン 1 を要求する:

```json
{
  "_meta": {
    "qwen.daemon.channelStartupProfile": { "v": 1 }
  }
}
```

対応する子プロセスは同じトップレベルレスポンスのメタデータキー配下にプロファイルを返す。
レスポンスは固定の所要時間フィールド、完全性フラグ、レスポンス構築の実時間タイムスタンプ、
子プロセス全体からレスポンスまでの所要時間のみを含む。パス、拡張機能名、設定、
その他のユーザー由来の値は決して含まない。

プロファイルは子プロセスの起動を重複のないトップレベルフェーズに分割する:

- プロセス開始からプロファイラー準備完了まで;
- Gemini モジュールのインポート;
- 引数のパース;
- 設定の読み込み;
- Config の構築;
- 汎用のアプリケーション初期化;
- ACP モジュールのインポート;
- ブートストラップ Config の初期化;
- トランスポートの構築;
- initialize ハンドラーの実行;
- 固定フェーズ間の帰属不能時間。

ブートストラップ Config の初期化は、初期 extension リフレッシュ、フック、スキル、
最終 extension リフレッシュ、階層メモリ、ツールレジストリ、ツールのウォームアップ、
残余時間に分割される。ripgrep の判定はツールレジストリ時間の子として報告され、
残余時間の計算で再度差し引かれることはない。トップレベルの帰属不能時間には、
トランスポートセットアップと initialize リクエストが子プロセスのハンドラーに到達する
までの待機時間も含まれる。

すべての所要時間は `performance.now()` を使用し、小数点 2 桁に丸める。
レスポンス構築のエポックは `performance.timeOrigin` にレスポンスマークを加えたもので、
任意の親側トランスポート推定にのみ使用される。

## 収集のライフサイクル

CLI は、生の引数に `--acp` または `--experimental-acp` が含まれる場合のみ、Gemini
ランタイムのインポート前に ACP プロファイラーを動的に初期化する。プロファイラーは
マーク名の有限 union に対して最初のタイムスタンプを保存する。ファイル I/O、ヒープ
キャプチャ、テレメトリー初期化、動的なイベント保持は行わない。

コアの起動イベント sink は、ACP のブートストラップ Config が初期化中の間のみ、固定の
Config フェーズイベントを ACP プロファイラーに転送する。これにより後続のセッション
ごとの Config 初期化が起動プロファイルを汚染するのを防ぐ。スキップされた Config フェーズ
も隣接する開始・終了マークを発行するため、正常な起動は bare または safe モードでも
完全なプロファイルを生成できる。

initialize ハンドラーは、呼び出し元がプロファイルを交渉したかどうかにかかわらず、
最初のレスポンスの構築後にプロファイラーを凍結する。マークの欠落は `complete: false` を
生成; 収集が initialize レスポンスを遅延させたり失敗させたりすることは決してない。

## 親スパンのエンリッチメント

ブリッジは、アクティブな `channel.initialize` スパンに固定の数値属性を追加する前に
レスポンスのメタデータを検証する。未知のプロファイルバージョンは無視される。未知の
フィールドは無視される。既知の値は有限、非負、かつ 600 秒以下でなければならない。
無効または欠落の既知フィールドは省略され、実効の完全性フラグを false にする。

任意のレスポンストランスポート推定は、親の受信時刻から子プロセスのレスポンス構築
エポックを引いたもの。有限、非負、かつ設定された initialize タイムアウト以下の場合のみ
記録される。

プロファイルのパースとテレメトリーのエンリッチメントは fail-open（失敗時は許可）。
欠落、不正形式、サポート外のプロファイルは、initialize の成功、チャネルの破棄、
合体された呼び出し元の挙動、リトライの挙動を変更してはならない。ACP のメタデータは
拡張可能なので、新しい親は古い子プロセスと互換; 新しい子プロセスはオプトインしない
古い親にはプロファイルを返さない。

## 検証

フォーカスされたテストは、コレクターの有効化と凍結、固定フェーズの計算、ペイロードサイズ、
プロトコル交渉、不正形式のプロファイル、スパンのエンリッチメント、テレメトリー失敗の
隔離、Config イベントの順序付け、serve のファストパスバンドル境界をカバーする。
リリースビルドの候補は、最適化が選択される前に、代表的な 2C4G ホストでペア交互の
コールド実行により正確な #6907 のマージベースラインと比較される。

## P0-B 最適化の決定

2C4G の P0-A プロファイルは、子プロセス起動 P50 の 67.3% を Gemini と ACP の
モジュール読み込みに帰属した。CPU プロファイルは、ソースモジュールのコンパイルが最大の
CPU コストであること、および ACP の静的インポートグラフが、ACP 子プロセスが TUI を
レンダリングしないにもかかわらず Ink、React、React Reconciler、Yoga を読み込んでいた
ことを示した。

任意のエッジは新しい ACP エントリポイントではなく、既存の UI 専用の依存関係だった。
ACP Session は React フックを通じて API エラー分類器をインポート; extension の補完は
レンダリングコンポーネントを通じてそのデータ形状と結果上限をインポート; コマンド
レジストリは、`/init` が確認を求めるとき、承認モードが auto モードに入るとき、
折りたたまれた履歴が展開されるときにのみ必要な UI サポートを静的に読み込んでいた。
最適化は 2 つの純粋なデータヘルパーをレンダリングモジュールの外に出し、React の型
インポートを型のみとし、3 つのインタラクティブアクションの依存関係をそれらの
アクションが実行されるときのみ読み込むようにする。

ACP の initialize レスポンス、起動順序、Config 初期化、コマンドレジストリの内容、
失敗処理、Session の挙動は不変のまま。bundle-metafile チェックは ACP エージェントの
静的出力クロージャに従い、Ink、React、React Reconciler、Yoga の入力を拒否しつつ、
動的インポートの背後では引き続き許可する。

因果比較には同じ main コミット
`af6a9b640c5d9097c5151b8705dd73aee8e180d0` からビルドしたリリース成果物を使用し、
候補にのみ本最適化を適用した。除外したウォームアップの後、2 回の交互コールド実行が
60 ペアを生成; 別途の交互プリヒート実行が 30 ペアを生成した。2 回目のコールド実行は、
1 回目の実行が ACP パスより前に 2 つの候補側の親リスナーストールを露出させた後に
開始した。どちらの実行のサンプルも破棄していない。プールしたコールド P50 の結果:

| メトリクス                    | マッチしたコントロール | P0-B 候補 |             変化 |
| ------------------------- | --------------: | -------------: | -----------------: |
| ACP インポート                |       115.06 ms |       52.00 ms | -63.06 ms (-54.8%) |
| 子プロセスからレスポンスまで |      1102.88 ms |     1041.09 ms |          -61.80 ms |
| `channel.initialize`      |      1098.25 ms |     1035.61 ms |          -62.64 ms |
| Process から最初の Session まで  |      2046.88 ms |     1980.03 ms |          -66.85 ms |
| コールド Session リクエスト      |      1358.95 ms |     1290.23 ms |          -68.72 ms |

各バリアントの 60 のコールドプロファイルすべてと各バリアントの 30 のプリヒート
プロファイルすべてが完全だった。すべての実行がクリーンに終了し、並行する最初の
Session、テレメトリー無効の起動、レガシーデフォルトの `single` の挙動は両方の機能
ラウンドで成功した。プールしたコールドデータでは、ウォーム Session の P95 は
137.53 ms から 104.98 ms に、最初の health の P95 は 962.99 ms から 824.14 ms に、
プロセスツリー RSS の P95 は 442.27 MiB から 435.70 MiB に変化した。プリヒート
データでは、Session の P50 は 73.90 ms から 73.75 ms に、P95 は 88.38 ms から
76.17 ms に変化した。

一時的なホスト全体のストールが両方のバリアントに影響し、保持された。最初の 30 ペアの
実行では、2 つの候補の親リスナーストールが、health リクエスト自体は 6〜11 ms で
変更された ACP パスがまだ開始していなかったにもかかわらず、最初の health の P95 を
803.82 ms から 1175.67 ms に押し上げた。診断のリトライは方向を逆転させ、
コントロール/候補の最初の health の P95 は 1522.44/727.64 ms; 保持した 60 ペアすべてを
プールして上記の値が得られた。正確な P0-A マージもセカンダリの 30 ペアチェックとして
候補と比較され、独立して同じ ACP インポートの削減と P95 リグレッションなしを示した。

したがってモジュール読み込みの候補は P0-B ゲートを通過する: 選択フェーズは 30% かつ
10 ms 以上改善し、`channel.initialize` と process-to-first-Session の P50 の両方が
10 ms 以上改善した。トップレベルの遅延 yargs コマンドビルダーは、選択フェーズの改善が
30% のゲートを通過しなかったため却下された。ツールレジストリとウォームアップは引き続き
別のディスクリプタ分離設計; extension リフレッシュ、階層メモリ、トランスポートは
P0 の挙動変更を正当化するには小さすぎた。
