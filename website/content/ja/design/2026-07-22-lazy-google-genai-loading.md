# `@google/genai` の遅延読み込み

- **Issue**: #7264 候補 3
- **スコープ**: ACP コールドスタートのインポートクロージャ
- **Status**: 実装・検証済み

## 問題

バンドルされた ACP ランタイムは、現在 9 つの eager な実行時インポート箇所を通じて `@google/genai` の Node エントリに到達します。この SDK は、`google-auth-library` や `gaxios` を含む 77 入力の共有 1,196,331 バイトチャンクに 755,788 バイトを寄与しています。ACP のブートストラップは `initialize` に応答する前に完全な CLI エントリをインポートするため、ブートストラップが Gemini クライアントの初期化と MCP ディスカバリを意図的にスキップしていても、このチャンクは parse されて評価されます。

eager インポートを `import()` に変えるだけでは不十分です。ACP のセッション作成は、セッションレスポンスを返す前に `ensureAuthenticated()` と `createContentGenerator()` を呼び出します。したがって、既存のプロバイダーインポートと `LoggingContentGenerator` の構築は `newSession` 中に SDK を読み込み、作業を `channel.initialize` から移動するだけで、process から最初のセッションまでの時間を改善しません。

## 設計

### 軽量な同期互換値

コアのオーケストレーションは、プロバイダー実装の外では SDK の小さな同期サブセットのみを使用します: `FinishReason`、`FunctionCallingConfigMode`、`createUserContent`、`createModelContent`。パッケージローカルの互換モジュールがそれらの値を提供しつつ、SDK の型は型のみのインポートとして保持します。そのコンテンツ変換は SDK の検証と出力形状をミラーリングするため、既存の呼び出し元は SDK を評価せずに同じ動作を保ちます。

プロバイダー実装は引き続き公式の SDK クラスを使用します。特に、この変更は `GenerateContentResponse` のコピーも置き換えも行いません。

### シングルフライトの遅延コンテンツジェネレーター

`createContentGenerator()` は、セッションライフサイクルの現在の実行時点で、引き続き設定の検証、ランタイム fetch 実装の事前読み込み、Qwen OAuth 認証情報の取得を行います。これは非公開の遅延 `ContentGenerator` を返し、そのメモ化されたローダーが、最初の非同期コンテンツジェネレーター操作時に選択されたプロバイダーを構築して `LoggingContentGenerator` でラップします。

4 つの非同期操作すべてが同じローダー promise を共有します:

- `generateContent`
- `generateContentStream`
- `countTokens`
- `embedContent`

したがって、並行する最初の呼び出しはプロバイダーを一度だけインポートして構築します。`useSummarizedThinking()` は同期のままで、選択されたプロバイダーの既知の動作から供給されます: Gemini/Vertex では true、OpenAI、Qwen OAuth、Anthropic では false です。

Qwen OAuth の認証情報取得は `createContentGenerator()` 内で eager のままです。したがって、期限切れまたは欠落したキャッシュ認証情報は、見かけ上は使用可能だが最初のプロンプトでのみ失敗するセッションを生成するのではなく、引き続き ACP のセッション作成を拒否します。

動的インポートの失敗は既存のバックグラウンド更新再起動メッセージを保持しますが、プロバイダーチャンクの失敗は最初のジェネレーター使用時に表面化します。認証のリフレッシュは遅延ジェネレーターを置き換え、それは失敗したローダー後のリトライ境界も提供します。

### MCP の初回使用

`mcpToTool` は `discoverTools()` 内で動的に読み込まれます。これにより SDK のページネーション、重複名の処理、呼び出し可能ツールのフォールバック、MCP 使用ヘッダーの副作用が保持されます。したがって、MCP サーバーが設定された構成では、最初のモデルプロンプトより前にバックグラウンドの MCP ディスカバリ中に `@google/genai` が評価される可能性があります。これは意図的な初回使用の例外です: `mcpToTool` を置き換えると、実験的な SDK の動作を複製し、リグレッションサーフェスを実質的に広げることになります。

保証される境界は、`@google/genai` が ACP ブートストラップの静的クロージャから存在しないことです。設定された MCP サーバーがなければ、セッション作成を通じて読み込まれないままで、最初の `ContentGenerator` 操作時に読み込まれます。

### バンドルガード

serve fast-path の metafile ガードは、ACP の禁止パッケージリストに `@google/genai` を追加します。動的チャンクは引き続き許可されます。これにより、将来の静的な再インポートは、その出力インポートパスとともに CI を失敗させます。

## 下流利用側の監査

3 つの直接の本番作成パスがあります。`Config.refreshAuth()` はメインセッションのジェネレーターを所有します。`BaseLlmClient` はルーティングされたサイドリクエスト用のキャッシュされたモデルごとのジェネレーターを所有します。`createRuntimeContentGeneratorView()` は、インプロセスエージェントバックエンド、サブエージェントマネージャー、フォークされたエージェントが使用する専用ジェネレーターを所有します。各パスは `ContentGenerator` インターフェースのみを保存して消費するため、非公開の遅延ラッパーはその所有とルーティングの境界を保持します。

インターフェースの利用側は、`generateContent`、`generateContentStream`、`countTokens`、`embedContent`、`useSummarizedThinking` のみを呼び出します。メインチャットパス、プロンプトフック、memory/goal/サイドクエリ、vision ルーティング、サブエージェント、セッションのレジュームは、具体的なプロバイダーを調べたり `LoggingContentGenerator` をアンラップしたりしません。リポジトリ全体の検索でも、本番の `instanceof` や `getWrapped()` の呼び出し元は見つかりませんでした。MCP ツールディスカバリはジェネレーターの所有とは分離されており、SDK 提供の `mcpToTool` アダプターを自身の初回使用インポートの後ろに保持します。

## 却下された代替案

- **現在のインポートのみを動的にする**: `channel.initialize` は改善するが、`newSession` 中に同じ SDK を読み込むため、process から最初のセッションまでの時間に対処できない。
- **`GeminiClient.initialize()` 自体を遅延する**: チャットの構築、レジューム、ツール登録、セッションの準備完了、認証エラーのタイミングを変えてしまう。
- **`GenerateContentResponse` をコピーする**: SDK アップグレード間でプロトタイプとゲッターのドリフトのリスクがあり、OpenAI と Anthropic のアダプターが返す実行時オブジェクトを変えてしまう。
- **`mcpToTool` をローカルで置き換える**: 実験的な SDK アダプターを複製し、そのプロセスグローバルな MCP テレメトリ動作を削除するか再現しなければならない。
- **未文書化の SDK 内部をインポートする**: `@google/genai` はこれらのヘルパーとクラスに対して、サポートされた軽量サブパスを公開していない。

## 互換性と失敗パス

- プロバイダーの検証は `createContentGenerator()` に残ります。
- Qwen OAuth の認証情報チェックは ACP セッション登録の前に残ります。
- 最初のローダーは、並行するプロンプトとサイドクエリ全体でシングルフライトです。
- すでに中止された最初のリクエストは、ESM インポートがキャンセル不能であるため、モジュール評価を完了する可能性があります。プロバイダーはその後、元の中止されたシグナルを受け取ります。
- モデル設定は現在と同様に参照でキャプチャされるため、初回使用より前に行われた同じプロバイダーのモデル変更は、プロバイダーのコンストラクタによって観測されます。
- 認証/プロバイダーの変更は、既存の `refreshAuth()` パスを通じて遅延ジェネレーターを再構築します。
- バックグラウンド CLI 更新後の動的チャンクの欠落は、既存の再起動ガイダンスを生成します。

## 検証

ユニットテストは、ヘルパーの等価性、遅延構築、Qwen 認証情報のタイミング、シングルフライトの動作、プロバイダーごとの summarized-thinking の値、遅延モジュールの失敗、MCP ディスカバリの動作をカバーします。バンドルされた metafile は、`@google/genai` が ACP の静的クロージャから存在しないことを示しつつ、動的なプロバイダー/MCP チャンクには保持されていなければなりません。

2C4G の受け入れ実行は #7264 に従います: 30 回のペアシリアルコールドスタート、`channel.initialize` の P50/P95、process から最初のセッションまで、プリヒート済み/ウォームの動作、並行する最初のセッション、テレメトリーオン/オフ、ピーク RSS。この変更は作業を後へ移動するため、追加で即座の最初のプロンプトに対する session-response から最初のトークンまでと、process から最初のトークンまでを記録します。最初のトークンのリグレッションとして完全に返済されてしまうスタートアップの実益は、成功した最適化としてではなく、報告されます。

## 結果

コントロールは当時最新の `origin/main`（`dd2552018a72a2b5795977211f06435711e5f99a`）で、すでに lazy テレメトリー/プロトコルの作業と lazy-undici の変更を含んでいました。候補は正確に最終的な作業ツリーのバンドルでした。両者は同じ lockfile からビルドされ、提供された Alibaba Cloud ホスト（2 vCPU、約 3.5 GiB RAM、スワップなし、バンドルされた Node.js 22.23.1）でテストされました。

ACP の静的クロージャは 14,279,497 バイトから 13,280,177 バイト（999,320 バイト）に減少しました。コントロールのクロージャには `@google/genai` に直接帰属する 755,788 バイトが含まれていました。候補にはゼロしか含まれません。SDK はプロバイダーと MCP の初回使用のために動的チャンクに存在し続けます。

outfile へのテレメトリーを有効にして、30 回の交互ペアコールドスタートの結果:

| メトリクス                   | コントロール P50 / P95  | 候補 P50 / P95 | P50 差分 |
| ------------------------ | ------------------ | ------------------- | --------- |
| `channel.initialize`     | 984.9 / 1010.6 ms  | 954.8 / 972.5 ms    | -30.1 ms  |
| コールド `POST /session`     | 1293.1 / 1316.0 ms | 1252.4 / 1291.3 ms  | -40.7 ms  |
| process から最初のセッションまで | 1924.6 / 1951.1 ms | 1858.7 / 1901.0 ms  | -65.9 ms  |
| `phase.gemini_import`    | 536.3 / 550.2 ms   | 517.2 / 526.5 ms    | -19.1 ms  |
| ピーク RSS                 | 414.6 / 427.1 MiB  | 406.5 / 420.5 MiB   | -8.0 MiB  |

3 秒のプリヒート後も、`channel.initialize` は P50 で 32.7 ms 高速なままで、`POST /session` は 4.8 ms 改善しました。並行する最初のセッション、テレメトリー無効、レガシー単一セッションモードはすべて成功しました。すべてのプロセスタグがクリーンアップされ、テレメトリー無効モードはゼロレコードを出力しました。

追加のテレメトリーオフ実行は、30 回の交互ペアで即座の実際の OpenAI 互換プロンプトを発行しました。60 のプロンプトすべてが完了しました。Process からセッションまでは P50 で 53.4 ms 改善し、候補は 30 ペア中 28 ペアで高速でした。プロンプトから最初のトークンまでは、モデルとネットワークの分散のもとで実質的に中立でした: 候補の P50 は 24.2 ms 高速で、候補は 30 ペア中 16 ペアで高速でした。P95 は、両方のバリアントに無関係な数秒単位のネットワーク外れ値があったため、297.6 ms 遅くなりました。エンドツーエンドの process から最初のトークンまでの P50 は 57.6 ms 改善し、候補は 30 ペア中 19 ペアで高速でした。これにより、実証された中央値のコストシフトは除外されますが、最初のトークンのテールは、モデル呼び出しパフォーマンスの追加の実益を主張できるほど帰因できません。
