# CUA Driver 0.17.0 のアップストリーム同期

## ゴール

ベンダー化された CUA Driver のソースを、Qwen 固有のランタイムと配布の契約を維持したまま、アップストリームの `cua-driver-rs-v0.7.0` からリリース済みの `cua-driver-rs-v0.17.0` タグに移行する。

リリースタグであるコミット `10279552e2bbe479e367a082f78b1b98ee85a697` が唯一の信頼できる情報源である。ローカルの `/Users/mochi/code/cua` チェックアウト、古い設計ノート、生成成果物は、比較のための入力にすぎない。

## スコープ

アップストリームの取り込みは `trycua/cua:libs/cua-driver` に限定され、`packages/cua-driver` にマップされる。アップストリームのモノレポのワークフロー、ルートスクリプト、ドキュメント、無関係なライブラリは自動的に取り込まれない。それらのファイルに対する新しい依存は、パッケージローカルにするか、既存の Qwen Code の機能に明示的にマップするかのいずれかでなければならない。

Qwen が所有するリリースワークフローは引き続き `.github/workflows/cd-cua-driver.yml` である。新しいドライバーのビルドとリリースの契約が必要とする最小限の変更を受け入れる場合があるが、Qwen が所有する成果物の公開を続けなければならない。

## 必須の Qwen 差分

以下のすべてが有効に保たれない限り、同期は不完全である:

1. インストールされた実行可能ファイル、プロセス、アプリバンドル、バンドル識別子、パス、スケジュールされたサービス、ドキュメント、リリースアセットは、現在の Qwen のリリースラインが想定する Qwen 所有の識別情報を使用する。リリース状態のホームは、アップグレードの互換性のために引き続き `~/.cua-driver` とする。隔離されたローカルビルドのホームは引き続き `~/.qwen-cua-driver-local` とする。
2. `CUA_DRIVER_RS_COORDINATE_SPACE=1` は、引き続き、共有の呼び出し境界においてオプトインの 0-1000 座標契約を提供する。これは、座標を持つすべての新しいデスクトップおよびブラウザ隣接のツールをカバーするか、fail closed（失敗時は拒否）でなければならない。
3. `MCP_MODEL_PAYLOAD_FILTER=1` は、引き続き、バイナリメディアを変更することなく、MCP のテキストコンテンツと構造化コンテンツの両方で、モデルに表示されるブランディングをフィルタリングする。
4. trycua/cua#2021 に由来する、まだマージされていない Windows の空/無題トップレベルウィンドウの挙動は引き続き存在し、現在のウィンドウモデルに適応させる。
5. trycua/cua#2036 の EAGAIN ソケット書き込みパッチは、0.17.0 ベースの一部であるため、ローカルのパッチ一覧から退役させる。

## アップストリームの契約変更

取り込みには、SDK が所有するランタイム、Python と TypeScript の UniFFI SDK、型付きブラウザ自動化、ランタイムの権限モード、セッションごとのキャプチャスコープ、スナップショットに紐付いた要素トークン、クローズドな `ActionResult` 契約、`verify_state`、ネイティブメニューの呼び出し、クリップボードツール、ウィンドウのフレーミング、セマンティックなカーソルテーマが含まれる。

これらは独立した末端の機能ではなく、アーキテクチャ上の置き換えである。Qwen の座標変換とペイロード変換は、正規の SDK/ツール境界に再接続しなければならず、CLI、MCP、直接の SDK、プライベートワーカー、デーモンの実行が乖離してはならない。

## 取り込み戦略

1. 現在の `.vendored-from` の ref から `cua-driver-rs-v0.17.0` まで、リポジトリがサポートするアップストリーム差分のスクリプトを実行する。
2. すべての reject、削除、新しく生成されたファイル、ルート相対パス、パッケージの識別情報、リリースバージョン、外部のビルド依存関係を棚卸しする。
3. アップストリーム/ローカルの重複は、アップストリームのアーキテクチャを保持し、各 Qwen の差分をその新しい正規の境界で再表現することで解決する。
4. `.vendored-from`、`.vendored-patches.md`、バージョン参照、Qwen のインストーラー、Qwen のリリースワークフローをまとめて更新する。
5. ソース、テスト、ドキュメント、生成されたバインディング、インストーラー、バンドルのメタデータ、プロセス名、サービス名、リリースアーカイブについて、識別情報の一貫性を監査する。

## 検証

検証は階層化され、狭いユニットテストがグリーンでも、壊れた配布や信頼境界を隠せないようにする:

- Rust のフォーマット、パッケージチェック、core/contract/SDK のユニットテスト、生成された契約の一貫性。
- フォーカスされた座標正規化、ペイロードフィルター、Windows のウィンドウ列挙、インストーラー、バージョンのテスト。
- Python と TypeScript の SDK の生成/パッケージチェック（パッケージローカルのツールチェーンが利用可能な場合）。
- Qwen のリリースワークフローの静的チェック（実行可能ファイル名、アプリバンドルのレイアウト、バンドル識別子、アセット、埋め込みバージョン）。
- 内包するリポジトリに対する `npm run build && npm run typecheck`。
- 完全な diff と未追跡ファイルの監査を、2 回連続でクリーンになるまで繰り返す。

署名/ノータライズされたリリースの作成と、実際の Windows/Linux/macOS での GUI の認定は、ローカル検証の範囲外であり、明示的なリリースゲートのままでなければならない。
