# Daemon Todo Stop Guard

## Problem

デーモンと ACP クライアントは、モデルターンが終了した後もセッションを存続させ
られる。モデルが未完成のトップレベル Todo リストを書いた直後である場合、自然な
モデルの停止により、セッションに継続のための十分な信頼された状態があるにも
かかわらず、デーモンリクエストが未完成のままになる可能性がある。クライアント
には現在、そのケースを通常の完了ターンと区別する、上限付きの組み込み手段がない。

この設計は、オプトインのデーモン専用 stop guard を追加する。TUI、コアの Todo
ツール、汎用エージェントループは意図的に変更しない。

## Configuration and safety boundary

`experimental.todoStopGuard` はデフォルトで `false` で、再起動が必要であり、
TUI の設定ダイアログには表示されない。この guard はセーフモード、bare モード、
承認 `plan` モードでは強制的にオフになる。`disableAllHooks` は組み込み guard を
無効化しない。これは外部フックではないためである。

中断されていない各自動継続ステージは、プライマリモデルのストリームを最大で
2 つまで追加で作成できる。ターン中のユーザーメッセージは、新しいユーザー入力
であるため、新たな 2 回試行ステージを明示的に開始し、リトライ/継続とバック
グラウンドの結果は現在のステージの予算を保持する。既存の権限チェック、キャン
セル、トークン制限、ループ保護、ACP の猶予期間、デーモンのリソース制限は引き
続き権威を持つ。特に、切断されたクライアントが権限の承認を意味することは
決してない。

## Trusted state

CLI の `Session` は、小さなインメモリの `DaemonTodoStopGuard` ステートマシンを
所有する。これは、現在の作業チェーンがアームされているか、最新の未完成項目数、
コミットされたコンティニュエーションの試行回数、サスペンション/キュープロンプ
トの状態、および使い切りがすでに報告されたかを保存する。Session は作業チェーン
の開始時に、バックグラウンドエージェント、シェル、モニター、wakeup の ID を
個別にスナップショットする。その境界ですでにキューに入っているターミナル通知と
wakeup も含まれる。

アームできるのは、構造化された `{ type: 'todo_list', todos: [...] }` エンベロープ
を伴う成功したトップレベルの `TodoWriteTool.execute()` 結果のみである。観測は
ツール実行とステータス計算の後、Session の `PostToolUse` フックの前に行われる。
引数、リプレイされた履歴、ディスクの状態、失敗または重複したツール呼び出し、
サブエージェントの Todo リスト、および `todo_write` のワイヤー名をシャドウする
検出されたツールは信頼されない。最新の成功結果がカウントを置き換え、空または
完全に完了したリストは guard を即座に解除する。解除は別の自然停止の継続を防ぐ
が、コミットされた Guard ストリームによってすでに開かれたツールループを切り詰め
はしない。

新しい通常のユーザープロンプトは、非アームの作業チェーンを開始し、そのバック
グラウンドベースラインをリセットする。メモリに Todo 状態が残っていても、以前の
リクエストからアクティベーションを継承することはできない。信頼されたリトライ/
継続は、信頼された未完成の Guard 状態が存在する間のみ作業チェーンを維持する。
信頼をクリアするライフサイクルイベントの後には、新しいバックグラウンドベース
ラインで開始し、再度アームしなければならない。ターン中のユーザーメッセージは
アクティベーションを維持し、新たな 2 回試行ステージを開始する。つまり、ハード
な上限は新しいユーザー入力なしの連続 2 回の自動ストリームであり、作業チェーン
の全期間を通じた 2 ストリームではない。cron と通知のターンは、成功したトップ
レベルの Todo 書き込みによって自身のチェーンを確立できる。アームされたチェーン
のバックグラウンド結果を処理する場合、そのチェーンの予算を保持する。関連する
バックグラウンドの結果も信頼された継続であり、ハードサスペンションをクリアする
ことなく API/ネットワークのリトライ一時停止をクリアする。

guard は永続化されない。rewind と履歴の復元は、ブランチ/フォーク、成功した
作業ディレクトリの変更、新しい Session、ディスクからの復元、デーモンまたは
エージェントの再起動と同様に信頼をクリアする。同じ Session へのライブの
クライアントのアタッチはインメモリの状態を保持する。モデルの変更や非 Plan の
承認モードへの変更だけでは、新しい作業チェーンは開始されない。ライフサイクル
による無効化はまた、置き換えられたライブターンからの遅延ツール結果による guard
の再アームもブロックする。次の独立したプロンプトまたは自動ターンが新しい境界を
確立する。遅延自動キューは、無効化されたフォアグラウンドのプロンプトが確定
すると解放される。そのプロンプトがエラーパスで終了する場合も含まれる。

## Stop ordering

guard が関与するのは自然なモデルの停止時のみである。アクティブな場合、Session
は次の順序を適用する:

1. ターン中のユーザーメッセージを drain する。存在する場合、Stop フックと
   guard をスキップし、guard の予算をリセットし、現在のループ内でユーザーの
   コンティニュエーションを実行する。
2. デーモンの FIFO に完全で中断されていないプロンプトが含まれている場合、
   現在のリクエストを終了し、古いチェーンをそのプロンプトを待機中とマーク
   する。キャンセルされたキューリクエストは、後からバックグラウンドのアク
   ティビティが古いチェーンを復活させることを許可しない。最後のキュープロンプ
   トが中断された場合、ブリッジはライブの Session に、待機中の guard の終了と
   無関連の自動キューの解放を明示的に指示する。1 回の drain がターン中の
   メッセージとキューの完全なプロンプトの両方を観測した場合、ターン中の
   メッセージが先に実行され、そのコンティニュエーションが Todo リストを完了
   させたり guard をハード停止させたりしても、FIFO の優先権は有効なままである。
3. フォアグラウンドのターンでは、既存の外部 Stop フックを既存の上限とエラーの
   セマンティクスで評価する。
4. guard は、アームされており、サスペンドやキュープロンプトの待機中でなく、
   未完成項目があり、承認 `plan` の外側であり、関連するバックグラウンド入力が
   ない場合にのみ評価する。
5. 外部フックと guard の両方が同じ停止をブロックする場合、それらの理由を 1 つ
   のコンティニュエーションモデル呼び出しに統合する。それらのカウンターは
   独立したままである。

関連するバックグラウンド入力とは、ID が作業チェーンのベースラインに含まれて
いない、まだライブのバックグラウンドエージェント、シェル、モニター、または
`@wakeup` に加え、同じ関係性を持つキュー入りの通知または wakeup である。古い
リクエストから継承されたバックグラウンド作業と通常の cron ジョブは、新しい
リクエストをブロックしない。自動の cron/通知ターンは組み込み guard のみを実行
し、外部の Stop フック呼び出しを導入しない。関連する結果は現在の予算を保持し、
古いタスクの通知や通常の cron ターンは、アクティブなチェーンが再開できなく
なるまで遅延され、その後、独立した非アームのチェーンを開始する。遅延された
無関連の繰り返し cron の発火は、タスクごとに合体され上限が付くため、停止した
バックグラウンド依存がキューを無限に増やすことはない。Guard チェーンがまだ
再開できる間、または完全な FIFO プロンプトが優先権を持つ間、デーモンのフォロー
アップ提案も抑制されるため、未完成の作業が競合する提案モデル呼び出しをトリガー
することはない。

ハードなターミナルパスは現在の作業チェーンをサスペンドする: ユーザーまたは
権限のキャンセル、`PostToolUse.shouldStop`、ループまたは繰り返し呼び出しの保護、
トークン制限、外部 Stop フックの上限。API とネットワークのエラーは、明示的な
信頼されたリトライ/継続のために状態を保持する。

## Continuations and observability

最初の guard コンティニュエーションは次を送信する:

> [Todo Stop Guard] N 個の Todo 項目がまだ pending または in progress です。ただちに現在のタスクの実行を続けてください。継続するかどうかをユーザーに尋ねないでください。進行にユーザー入力が必要な場合は、構造化された質問または権限フローを使用してください。進行が外部の状態に依存する場合は、ブロッカーを明示的に報告してください。

2 回目はさらに次を送信する:

> これは最後の自動継続です。終了する前に、Todo を完了/更新するか、完了した進行状況と正確なブロッカーを報告してください。

カウンターは `responseStream` が正常に返された後にのみコミットされる。その時点
より前のキャンセル、コンパクションの失敗、トークンの拒否は試行を消費しない。
その後のストリーム失敗は消費する。自由形式のブロッカーテキストは解析されない。
コンパクションの失敗はその guard チェーンをサスペンドするため、到達不可能な
リトライの後ろに自動キューをブロックしたままにすることはできない。外部の Stop
フックが合体されていた場合、その理由はそのフックの既存のセマンティクスの下で
継続する場合がある。予算は、先行する guard ストリームのツール結果を送信する
フォローアップを含め、guard に帰属するすべてのプライマリモデルストリームを
カウントする。2 番目のストリームがさらに多くのツール呼び出しを返す場合、
Session はそれらを実行して結果を保存するが、3 つ目の guard に帰属するストリーム
は開かない。最初のストリームがツール呼び出しによってすべての Todo を完了した
場合、残りの試行は、モデルがレスポンスを完了できるように、別の未完成 Todo
プロンプトなしでツール結果を送信する場合がある。ターン中の入力が代わりにその
ツール結果の送信を保証し、残りの Guard 試行を消費せずに優先する。そのストリーム
が外部の Stop フックと合体されていた場合、そのフックの既存のツールループは、
別の Guard プロンプトや Guard 試行なしでそれらの結果を送信できる場合がある。
Guard を有効化しても、外部フックのコンティニュエーションを切り詰めてはならない。

コミットされた各コンティニュエーションは、`_meta.source = 'todo_stop_guard'`
と、試行回数、最大試行回数、未完成数を伴う、リプレイ可能なディスクリートな
`agent_message_chunk` を発行する。使い切りも同様に次を発行する:

> [Todo Stop Guard] 自動継続は 2 回の試行後に停止しました。N 個の Todo 項目が未完成のままです。

guard のテレメトリに Todo のテキストは決して含めない。通常の使用量メタデータは
引き続き追加の呼び出しを集計する。リプレイのコンパクションは、
`qwenDiscreteMessage` と Guard ソースの両方を運ぶ Guard イベントを独立して保持
するため、ライブのイベントリングがロールオーバーした後に、試行をマージしたり
試行ごとのメタデータを破棄したりすることはない。

## Bridge compatibility

`craft/drainMidTurnQueue` に任意の `hasQueuedPrompt` が追加される。ブリッジは、
保留中のプロンプトリストに、状態が `queued` で abort シグナルが中断されていない
完全なエントリが含まれる場合のみ、これを設定する。古いデスクトップ/チャネルの
クライアントはこのフィールドを省略する場合がある。Session は省略を `false`
として扱う。drain がタイムアウトした場合、遅延レスポンスがメッセージ内容を
回復する場合があるが、そのキュープロンプトのスナップショットは、すでに古く
なっている可能性があるため破棄される。

REST/SSE の切断挙動とイベントリングは変更されない。ACP HTTP は既存の 10 秒の
猶予期間とリプレイパスを保持する。猶予の期限切れと明示的なクローズ/キャンセル
は現在の終了挙動を保持する。

## Verification

ユニットテストは、厳密なアクティベーション、ライフサイクルのリセット、サス
ペンション、予算とストリームコミットのセマンティクス、ブリッジのキュー報告、
設定のゲート、Stop フックの合体、ターミナルパスをカバーする。並行性テストは、
プロンプトの FIFO 優先権、遅延 drain の回復、バックグラウンドベースラインの隔離、
自動ターンをカバーする。デーモンの E2E テストは、SSE サブスクライバーなしの
プロンプト受け入れと、上限付き試行の後からのリングのリプレイをカバーする。
既存の ACP トランスポートの回帰テストは、猶予期間内の再接続、猶予の期限切れ、
権限のラウンドトリップをカバーする。手動の E2E 計画では、guard をアームした
状態でもそれらのパスを実施する。設定が無効な場合、既存の Stop フック、cron、
通知、プロンプトの挙動は変更されないままでなければならない。
