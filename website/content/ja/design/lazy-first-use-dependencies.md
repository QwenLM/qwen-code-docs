# エンコーディング、ターミナル、Git 依存関係の初回使用時遅延読み込み

## Context

Issue #7264 は、ほとんどのセッションでは使用されないにもかかわらず、ACP 子プロセスの eager な静的 import クロージャに含まれている依存関係を追跡している。候補 5 は、初回使用の境界が異なる 3 つのパッケージをグループ化する:

| パッケージ               | ベースライン ACP クロージャ | 初回使用                                                          |
| ------------------------ | -------------------: | ----------------------------------------------------------------- |
| `iconv-lite`             |        551,713 bytes | BOM なしの非 UTF-8 テキストの読み書き                    |
| `@xterm/headless`        |        213,071 bytes | PTY パス経由でのシェル起動                             |
| `simple-git`             |        146,526 bytes | ワークツリー、クリーンアップ、GitHub 拡張の Git 操作の実行 |
| **パッケージ直接合計**   |    **911,310 bytes** |                                                                   |

直接合計は約 890 KiB である。ACP の静的クロージャ全体には、これらのパッケージが eager パスから外れた場合に到達不能になるモジュールも含まれるため、実測のバンドルレベル削減はより大きくなり得る。

## Goals

- 3 つのパッケージすべてを ACP 子の静的 import クロージャから削除する。
- 現在の同期的な公開エンコーディングヘルパーを維持する。
- 各パッケージを実際の初回使用時に 1 回だけ読み込み、新しい設定は追加しない。
- シェルフォールバックの挙動、Git の挙動、ファイルエンコーディングメタデータ、BOM 処理、アトミック書き込みを維持する。
- バンドルガードを追加し、将来の import がこれらのパッケージをサイレントに eager クロージャへ戻せないようにする。
- #7264 の他の候補と同じ 2 vCPU・4 GiB の受け入れ規律を使用して変更を検証する。

## Non-goals

- 公開エンコーディング API を同期から非同期へ変更すること。
- `iconv-lite`、`@xterm/headless`、`simple-git` の置き換え。
- PTY 選択、ワークツリーセマンティクス、エンコーディング検出、エラーポリシーの変更。
- これらの依存関係がすでに読み込まれた後に実行されるコードの最適化。

## Import-Closure Findings

`febb43bc9266cc7a3363539df87d90d752ad782c` からビルドしたベースラインバンドルは、144 出力にまたがる 13,405,027 バイトの ACP 静的クロージャを持つ。esbuild metafile のトラバーサルにより、`iconv-lite` に 551,713 バイト、`@xterm/headless` に 213,071 バイト、`simple-git` に 146,526 バイトが帰属する。

最初のパッケージレベルの遅延 import では不十分だった。CLI には Core パッケージルートの本番名前空間の動的 import が含まれていた。esbuild のコード分割ビルドでは、名前空間全体を要求すると、同期のエンコーディング互換 export を含め、すべてのルート export が到達可能なままになる。そのためこの設計では、依存ローカルなローダーと、各遅延パスが消費するシンボルのみを再 export する狭い CLI ランタイムエントリモジュールの両方が必要である。

## Design

### Shared loader properties

各パッケージは、モジュールスコープの promise に支えられたパッケージローカルなローダーを持つ。並行する初回使用者は同じ import を共有し、後続の使用者は解決済みモジュールを再利用する。ローダーは Node と esbuild が出力する CommonJS 相互運用の形状を正規化し、コンシューマーが必要とするランタイムメンバーのみを公開する。

ローダーは `createRequire()` ではなく意図的に `import()` を使用する。本番バンドルはスタンドアローンであり、別途インストールされた `node_modules` ツリーに依存してはならない。動的 import により esbuild は自己完結なチャンクを出力でき、それらのチャンクは ACP 静的クロージャの外に置かれる。

### `@xterm/headless`

`ShellExecutionService.execute()` はすでに非同期である。このサービスはまず PTY 実装を取得し、PTY 実行パスに入る直前に `@xterm/headless` を読み込む。非同期 import の後に中断シグナルを再チェックし、解決された `Terminal` コンストラクタを既存の同期 PTY およびリプレイヘルパーへ渡す。

ターミナルチャンクの読み込みに失敗した場合、エラーは既存の PTY 障害境界内に留まり、実行は `child_process` へフォールバックする。これは現在のフォールバックポリシーと一致する。PTY サポートが利用できない場合や子プロセスパスが選択された場合は、パッケージの読み込みは発生しない。

### `simple-git`

監査対象コンシューマーの実際すべての Git 操作は非同期である。`GitWorktreeService` は構築を副作用なしに保ち、最初の Git メソッドが呼ばれたときのみインスタンスごとの `SimpleGit` promise を解決する。他の Core コンシューマーは同じパッケージローカルなローダーを直接使用する。

起動時クリーンアップは、まず既存の軽量なリポジトリルート探索を使用する。実際のリポジトリが存在し、古いワークツリーの検査が必要な場合のみ `simple-git` を読み込む。import の失敗は、Git 初期化失敗がすでに報告されていたのと同じ非同期境界で操作を reject する。

### `iconv-lite`

このパッケージには主な互換性の制約がある: `decodeBufferWithEncodingInfo()` と `encodeTextFileContent()` は公開の同期 API である。JavaScript の動的 import は非同期であるため、これらの関数を直接遅延化すると API 破壊になる。

同期 API は `iconv-lite` を静的 import する互換モジュールを通じて引き続き利用可能である。バンドルのために副作用なしとマークされるのは Core ルートの再 export 境界のみであり、esbuild は特定のエントリがそれらの export を使用しない場合に互換モジュールを破棄できる。このモジュールの他の import は通常の副作用扱いのままである。

内部の非同期ファイルサービスパスは遅延バリアントを使用する:

- 空、BOM 付き、有効な UTF-8、ASCII、UTF-8 の書き込みは `iconv-lite` を読み込まずに完了する。
- 検出された非 UTF-8 の読み込みは、デコード前にコーデックを読み込む。
- 非 UTF-8 メタデータを保持する書き込みは、エンコード前にコーデックを読み込む。
- 読み込み側の読み込みまたはデコード失敗は、現在の警告と UTF-8 置換フォールバックを保持する。
- 書き込み側の読み込みまたはエンコード失敗は、バイトを破損させる代わりに書き込みを reject する。

CLI の遅延 Core 名前空間 import は、狭いローカルなランタイムエントリモジュールに置き換えられる。これにより同じバンドル Core インスタンスとクラス同一性を保ちながら、すべての Core ルート export の保持を回避する。

## Bundle Guard

ACP ファストパスガードは `iconv-lite`、`@xterm/headless`、`simple-git` を禁止された静的パッケージとして扱う。ACP エントリからの静的パスはチェックを失敗させ、動的のみのパスは許可される。テストは拒否と許可される動的境界の両方をカバーする。

このガードはバンドルテキストではなく metafile の import グラフを評価するため、リネームされたチャンクや minify されたシンボルではバイパスできない。

## Compatibility and Failure Audit

| 領域                            | 維持される挙動                                             | 新しい境界                                                            |
| ------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------- |
| シェル実行                 | PTY 出力処理、リプレイ、中断、子プロセスフォールバック     | ターミナルチャンクは PTY 選択後に読み込まれる                            |
| ワークツリーと GitHub 拡張 | 既存の `simple-git` オプションとエラー伝播            | Git モジュールは最初の非同期 Git 操作時に読み込まれる            |
| テキスト読み込み                      | BOM と UTF-8 ファストパス、エンコーディングメタデータ、フォールバックデコード | コーデックは検出された非 UTF-8 フォールバックの場合のみ読み込まれる                  |
| テキスト書き込み                     | BOM 保持、非 UTF-8 エンコーディング、アトミック書き込み挙動    | コーデックは非 UTF-8 メタデータが必要な場合のみ読み込まれる                |
| 公開 Core API                 | 同期エンコーディングヘルパーのシグネチャと挙動            | 互換 export は使用しないエントリから tree-shake 可能 |

この設計はプロセスグローバルな可変設定を導入しない。ローダーの promise はプロセスローカルでべき等である。reject された import は reject のまま残る。バンドルされたチャンクの欠落や破損は同じプロセス生存期間中に回復できないため、これは適切である。

## Alternatives Considered

### 同期エンコーディング API を promise へ変換

公開の呼び出し元を破壊し、本来内部の起動時最適化を拡大するため却下。

### 初回使用時に `createRequire()` を使用

バンドルされた CLI がランタイムの `node_modules` インストールに依存するようになり、自己完結なリリース成果物が得られないため却下。

### エンコーディングテーブルやターミナル挙動の再実装

既存パッケージの遅延化より大幅にリスクが高いため却下。

### `@xterm/headless` と `simple-git` のみ着手

これはより単純だが、グループ内で最大のパッケージが eager パスに残り、候補 5 を満たさない。互換ファサードと狭いランタイムエントリモジュールにより、公開 API を変えずに `iconv-lite` を削除できる。

## Verification Plan

1. CLI のみの本番成果物をビルドし、esbuild コード分割でバンドルする。
2. ACP エントリの静的 metafile クロージャをトラバースし、3 つのパッケージすべてについて帰属バイトがゼロであることを要求する。
3. エンコーディングの読み書き、シェル実行とフォールバック、Git ワークツリーの挙動、クリーンアップ、GitHub 拡張操作、各ローダー、バンドルガードに絞ったユニットテストを実行する。
4. 影響する CLI テスト、ビルド、完全な typecheck を実行する。
5. 2 vCPU・4 GiB のリファレンスホストで、ペアのスモークテスト 1 回に続き、交互のシリアルコールドペア 30 回とプリヒート済みペア 30 回を実行する。`channel.initialize`、プロセスから最初のセッションまでのレイテンシ、プロセストリーピーク RSS、並行性、telemetry 無効時の挙動、レガシー単一セッション挙動、残留プロセスを報告する。

## Risks and Rollout

主なリスクは、eager import が以前は起動時に露出していた初回使用時のみの障害である。フォーカステストは初回使用パスを実施し、本番バンドルガードは import が動的なままであることを検証する。リモートのスモークと受け入れ実行は実際のバンドル ACP セッションを実施し、残留プロセスを確認する。

#7264 が要求するとおり、この候補は独立した PR のままにすべきであり、リグレッション面とパフォーマンス効果が帰属可能なままになる。2C4G ゲートが再現可能な起動時の利点や意味のある初回使用リグレッションを示さない場合、バンドルサイズ削減のためだけに実装を着手すべきではない。
