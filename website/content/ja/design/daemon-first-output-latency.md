# デーモンの初回出力レイテンシ

- **Tracking**: #7757
- **Immediate-prompt follow-up**: #7982
- **Background**: #7264
- **Scope**: デーモン/ACP のクライアントから観測可能なレイテンシ
- **Status**: 計測と immediate-prompt の要因帰属

## Decision and scope

最初の PR は計測のみである：opt-in のベンチマーク、純粋な分類/統計ヘルパー、
テスト、バージョン管理されたアーティファクト。本番の起動作動は変更しない。

Provider 準備のプロトタイプは、シングルバンドルのベースラインがそのゲートを
通過した場合に限り別途許可される。そのプロトタイプを公開するには、
個別の control バンドルと candidate バンドルが、この文書のすべてのレイテンシ、
リソース、機能、クリーンアップのゲートを通過する必要がある。
有効な否定結果が出れば、その作業は終了する。

ベンチマークは、ローカル準備、Provider リクエスト到着、初回出力、
最初の回答テキスト、終了完了を分離したまま、プロセス起動から
最初のモデル由来出力までを計測する。既存の本番 `ttft_ms` は変更されない：
引き続き Provider ディスパッチから最初に表示されるコンテンツまでを計測し、
遅延読み込みやローカルのプロンプト準備を取り込まない。

スコープ外は、TUI/Web Shell/エディタのレンダリング、プロンプトキャッシュ、
圧縮、モデルの思考/ツール挙動、ネットワーク事前接続、実モデルの
レイテンシ最適化、本番テレメトリの変更、公開ライフサイクル API、
プロトコルフィールド、設定、機能フラグである。

## Repository and runner contract

| パス                                                             | 責任                                                                                                       |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `integration-tests/cli/qwen-daemon-first-output-benchmark.test.ts` | opt-in ランナー、fake Provider、分離されたプロセスライフサイクル、baseline/compare プロトコル、アーティファクト書き込み |
| `integration-tests/cli/_first-output-benchmark.ts`                 | 純粋なイベント追跡、分類、パーセンタイル、対になるブートストラップ、判定入力                    |
| `integration-tests/cli/_first-output-benchmark.test.ts`            | 純粋契約の決定論的テスト                                                                  |
| `integration-tests/fake-openai-server.ts`                          | 既存の fake Provider。バイアスなしのコールド/ウォーム計測のための opt-in 接続クローズ付き                  |

ランナーは `QWEN_FIRST_OUTPUT_BENCHMARK=1` でない限り無効である。
その 2 つの入力モードは相互に排他である：

- **Baseline**: `BENCHMARK_CLI_PATH`。
- **Comparison**: `BENCHMARK_CONTROL_CLI_PATH` と `BENCHMARK_CANDIDATE_CLI_PATH` の両方。

`BENCHMARK_POST_SESSION_DWELL_MS` は比較専用で、正確に `0`、`100`、`500` のみを
受け付け、デフォルトは `0` である。`BENCHMARK_MEASURED_PAIRS` も比較専用で、
正確に `10` または `30` のみを受け付ける。デフォルトは 500 ms 診断では `10`、
それ以外では `30` である。500 ms 実行は 10 ペアを必要とし、
0/100 ms 実行は 30 ペアを必要とするため、診断が判定を左右するものと
誤表示されることはない。正式なフェーズ 2 実行は 3 つの dwell シナリオに
対してランナーを個別に起動する。異なる dwell 値のサンプルは決して
プールされない。モードの欠落や混在、同一の比較バンドル、読み取り不能なパス、
サポート外の dwell やペア数、dwell/サンプル計画の不一致は、サンプリング前に
`invalid_configuration` として失敗する。

dwell はセッション準備完了ではなく SSE 準備完了にアンカーされる。
SSE 接続はその 2 つの間に位置するため、`sessionReady` にアンカーすると、
遅い接続がウィンドウ全体を消費し、100 ms シナリオを、設定された dwell を
報告し続ける immediate-prompt 実行へと暗黙的に縮小してしまう。
`sseReadyToPromptMs` は各サンプルが実際に受け取ったアイドルウィンドウを記録する。

ミリ秒単位の数値は、ホストを奪い合うものが他に何もない場合にのみ意味を持つため、
ランナーは共有の integration 設定から除外され、
`integration-tests/vitest.firstoutput.config.ts` に専用のシリアル設定を持つ
（`fileParallelism: false`、シリアル実行、`retry: 0`）。純粋ヘルパーのテストは
引き続き共有スイートで実行される。ベンチマークの実行方法：

```text
QWEN_FIRST_OUTPUT_BENCHMARK=1 QWEN_SANDBOX=false BENCHMARK_CLI_PATH=... \
  npx vitest run --config integration-tests/vitest.firstoutput.config.ts
```

アーティファクトは `.qwen/investigations/daemon-first-output-benchmark/` 配下に
書き込まれ、integration ハーネスの使い捨て実行ディレクトリの外に置かれる。
これにより、成功、失敗、否定結果の実行すべてが、`KEEP_OUTPUT` を必要とせずに
グローバルティアダウン後も保持される。

## Measurement contract

### 単一のクロック

すべてのレイテンシタイムスタンプは親ハーネス内の `performance.now()` を使用する。
デーモン、ACP 子プロセス、Provider、実時計を組み合わせた duration は存在しない。
デーモンの FIFO キュー待機値は、分離されたプロンプト完了後に読み取られる
既存の独立した duration であり、親のタイムスタンプから決して減算されない。

| タイムスタンプ             | クライアントから観測可能な定義                                                     |
| -------------------------- | ---------------------------------------------------------------------------------- |
| `processSpawnAt`           | デーモンの `spawn` の直前                                                          |
| `sessionReadyAt`           | セッションレスポンスの成功が完全に読み取られ検証済み                               |
| `sseReadyAt`               | 最初の SSE epoch コールバックを観測。dwell のアンカー                              |
| `promptStartedAt`          | ノンブロッキングのプロンプトリクエスト開始の直前                                   |
| `promptAcceptedAt`         | HTTP `202` ボディ検証済み。最上位の `promptId` とリプレイカーソルを含む            |
| `userEchoAt`               | 対応する中継済み `user_message_chunk` を SSE からパース                            |
| `providerRequestArrivalAt` | fake Provider が計測対象リクエストを、固定遅延の前に受理                           |
| `providerReadyAt`          | 固定 50 ms 遅延が経過し、レスポンスストリームが利用可能になる直前                  |
| `firstModelOutputAt`       | 受理された最上位 `promptId` に対する最初の条件を満たす SSE イベントをパース        |
| `firstAnswerTextAt`        | 最初の条件を満たす回答テキストイベントをパース。null 可能                          |
| `terminalAt`               | 対応する `turn_complete` または `turn_error` をパース                              |

生のタイムスタンプから、これらの正確なメトリクスが生成される：

| メトリクス                             | 計算                                                  |
| -------------------------------------- | ----------------------------------------------------- |
| `processToSessionReadyMs`              | `sessionReadyAt - processSpawnAt`                     |
| `sseReadyToPromptMs`                   | `promptStartedAt - sseReadyAt`、診断用                |
| `promptToAcceptanceMs`                 | `promptAcceptedAt - promptStartedAt`                  |
| `acceptanceToProviderRequestArrivalMs` | `providerRequestArrivalAt - promptAcceptedAt`、符号付き |
| `promptToUserEchoMs`                   | `userEchoAt - promptStartedAt`                        |
| `userEchoToProviderRequestArrivalMs`   | `providerRequestArrivalAt - userEchoAt`、符号付き     |
| `daemonPromptQueueWaitMs`              | 既存のデーモン FIFO キュー待機 duration               |
| `promptToProviderRequestArrivalMs`     | `providerRequestArrivalAt - promptStartedAt`          |
| `promptToFirstModelOutputMs`           | `firstModelOutputAt - promptStartedAt`                |
| `promptToFirstAnswerTextMs`            | `firstAnswerTextAt - promptStartedAt`、null 可能      |
| `providerReadyToFirstModelOutputMs`    | `firstModelOutputAt - providerReadyAt`                |
| `promptToTerminalMs`                   | `terminalAt - promptStartedAt`                        |
| `processToFirstModelOutputMs`          | `firstModelOutputAt - processSpawnAt`                 |

`promptAcceptedAt` はレイテンシの起点ではなく診断用である：Provider リクエストや
イベントは HTTP `202` の受信に先行することがある。デーモンは ACP プロンプトを
転送する前に対応するユーザー echo を公開するが、SSE 配信は依然として
Provider リクエスト到着との競争に負ける可能性がある。そのため、
`acceptanceToProviderRequestArrivalMs` と `userEchoToProviderRequestArrivalMs` は
両方とも符号付きオフセットであり、負の値が有効である。それ以外のすべての
duration は非負でなければならない。キュー待機カウンターは分離されたプロンプト
ごとにちょうど 1 回進み、有限の非負 `lastMs` を保持しなければならない。
そうでない場合、その値を安全に相関させられないため、サンプルは無効である。
必須タイムスタンプの欠落や非有限値はサンプルを無効にする。ハーネスが
30 秒の SSE 準備完了期限を所有する。SDK の接続タイムアウトは記録され、
5 秒後に設定されるため、タイマーの順序が `sse_connect_timeout` を
別の失敗コードに変えることはない。

immediate-prompt の要因帰属メトリクスは、意図的に既存の境界で停止する。
これらを組み合わせることで、クライアント/ルートの受理、転送前のユーザー echo の中継、
デーモン FIFO キューイング、残りの ACP 子プロセス/ローカル準備区間を、
プロセス間タイムスタンプ、プロトコルフィールド、本番テレメトリを追加せずに
区別できる。echo の境界は SSE 中継時間を含み、デーモン内部のタイムスタンプではなく
近似である。これらのメトリクスは、残りの区間を ACP トランスポート、プロンプト準備、
Provider ローダー確定、リクエスト構築に分割しない。より深い計測には
個別のエビデンスと設計が必要である。

### プロンプトとイベントの相関

SSE コレクターはプロンプトの前にアクティブになるか、その前のカーソルから
再開し、`202` が受理された最上位 `promptId` を返すまで固定数のイベントを
バッファする。受理エンベロープは空でない `promptId` と非負整数の
`lastEventId` を含まなければならない。レガシーの同期結果は
`stopReason` によってのみ認識され、その他の不正なレスポンスは拒否される。
プロンプト受理タイムアウトは、サンプルティアダウン前に元のリクエストを
中断する。その後コレクターは、バッファおよびライブイベントを元の到着順に
評価し、最上位 ID の完全一致のみを受け入れる。先行イベント、ID 欠落、
無関係なプロンプトイベントは無視される。バッファオーバーフロー時、
トラッカーは失敗をラッチしてバッファリングを停止するため、サンプルは
無効化され、超過イベントは破棄される。

Provider リクエストはデーモンの `promptId` を持たない。そのため、
各分離された fake Provider は、一度に 1 つの期待される計測リクエストのみを
許可し、その一意の固定長プロンプトセンチネルを照合する。そのタイムスタンプは
`202` の前にバッファできる。追加、欠落、早期、並行リクエストは
サンプルを失敗させる。

最初の条件を満たすイベントが `firstOutputAt` を決定する：

| イベント                             | 種別                                     |
| ------------------------------------ | ---------------------------------------- |
| 空でない `agent_message_chunk` テキスト | `answer_text`、かつ最初の回答の境界      |
| 空でない `agent_thought_chunk` テキスト | `thought_text`                           |
| 整形式の最初の `tool_call`           | `tool_call`                              |

空でないとは、デコードされたテキスト長が 0 より大きいことを意味する。
テキストはトリムも書き換えもしない。リプレイ/ステータスフレーム、
ローカルの個別メッセージ（スラッシュコマンドやバックグラウンド通知の出力を含む）、
ユーザー echo、ロールや使用量のみのチャンク、圧縮診断、不正な更新、
`tool_call_update` はカウントされない。`turn_error` は常に失敗する。
条件を満たす出力前の `turn_complete` も失敗する。純粋トラッカーは、
回答メトリクスが null の、思考やツールが先に来る有効なターンを許可する一方、
ライブの fake Provider は既知の回答センチネルを生成しなければならない。

## Fake Provider と分離

ループバック専用の OpenAI 互換 fake Provider は、リクエスト到着を記録し、
リクエスト/モデルを検証し、設定された 50 ms タイマーを待ち、
実際に経過した遅延と `providerReadyAt` を記録し、ストリーミングされた
回答センチネルを 1 つ出力し、正常に完了する。ベンチマークのレスポンスは
明示的に `Connection: close` を使用するため、ウォームターンがコールドターンに
よって開かれた TCP 接続から利益を得ることはできない。ネットワーク事前接続は
計測される最適化の外に残る。遅延はリクエスト前のローカル作業と
レスポンス/イベント伝播を分離する。これは実レイテンシ分布をモデル化する
ものではない。純粋テストは、ライブ実行に非決定論を追加せずに、
思考優先やツール優先のフィクスチャをカバーする。

すべてのベースラインプロセスと比較の各アームは、新しいデーモン/ACP プロセスツリー、
ワークスペース、ホームおよび `QWEN_HOME`、エフェメラルなデーモン/Provider ポート、
イベントコレクター、リクエスト台帳を取得する。サンプルはシリアルに実行される。

Node のコンパイルキャッシュは正式実行開始時に空であり、バンドルとモードで
分離され、除外されたウォームアップのみによって生成され、その後
同じバンドルによってのみ再利用される。アーティファクトは出所証明のため
各キャッシュディレクトリを記録するが、クリーン実行はティアダウン中に
それを削除するため、記録されたパスはその後存在しないと予想される。
control と candidate は決してそれらを共有しない。ウォームアップの観測は
`measured: false` でアーティファクトに残る。

子プロセスは最小限の環境変数許可リストから起動する。固定のロケール/タイムゾーン、
分離された書き込み可能パス、無効化されたテレメトリ/更新チェック、
ダミーの Provider 設定、クリアされた実際の認証情報とプロキシ変数を使用する。
アーティファクトは、意図的に提供された非機密値のみを記録する。

正式な比較は、同じロックファイルから同じアイドル状態の 2 vCPU Linux ホストで
ビルドされたリリースバンドルを使用する。アーティファクトは、解決されたパス、
SHA-256 ハッシュ、可能な場合はソースリビジョン、Node/OS/CPU/メモリ、
負荷メタデータを記録する。ファイルシステムのページキャッシュや
スケジューラーのノイズは確実にフラッシュできないため、AB/BA の順序付けと
順序感受性ゲートは必須である。

## フェーズ 1: シングルバンドルのコールド/ウォームベースライン

除外される 2 つのウォームアッププロセスを実行した後、50 の計測プロセスを
実行する。各計測プロセスは：

1. 新しい `sessionScope: thread` セッションを作成し、1 つの即時固定長プロンプトを送る（`cold`）；
2. 検証された終了を待つ；
3. 最初のセッションを開いたまま、同じ ACP 子プロセス上に別の `sessionScope: thread` セッションを作成する；そして
4. 別のセンチネルで同じ長さのプロンプトを 1 つ送る（`warm`）。

ランナーは両ターンの後に ACP 子プロセスの PID を記録し、変更されていない
1 つの子プロセスだけがそれらにサービスした場合を除きサンプルを無効にする。
2 番目のターンの後でのみ、両方のセッションを閉じる。したがって
2 番目のセッションは、セッションごとの遅延 Provider ラッパーは新規だが、
ACP プロセス全体の ESM/ランタイムキャッシュはウォームである。このペアは、
会話履歴の交絡なしに、プロセスがプロンプトパスを最初に通過する際の
一回限りのローカルコストの上限を示す。Provider の構築はそのコストの
一要素である。最初のプロンプトは、最初のデーモンルートヒット、
最初の ACP IPC ラウンドトリップ、JIT ウォームアップ、無関係な遅延インポートの
コストも支払う。したがってデルタは、Provider のプリロードが回収できる
可能性のあるものの上限であり、Provider 読み込みの推定値ではなく、
ゲート通過は Provider がその特定の割合を占めることを立証しない。
要因帰属はフェーズ 2 のペア比較がテストするものである。両セッションとも
プロンプト時に独自の Provider を構築するため、プロトタイプが dwell の中に
移動させる可能性のある作業は加算されない。ゲートは保守的である。
2 番目のセッションの process-to メトリクスは診断用である。

ベースラインはプロセスごとに正確に 2 つの Provider リクエストを期待する。
50 のコールド/ウォームペアはすべて有効でなければならない。コールドと
ウォームはプロセスを共有するため、そのデルタは独立したサンプルではなく
ペアであり、ゲートは、シード付きブートストラップ 95% 区間を伴う
ペア中央値で判定される：

```text
providerDelta[i] =
  cold promptToProviderRequestArrivalMs[i] -
  warm promptToProviderRequestArrivalMs[i]

providerDeltaCiLow = lower bound of the 95% CI of median(providerDelta)
```

フェーズ 1 は以下のいずれかで通過する：

```text
providerDeltaCiLow >= 25 ms
```

または：

```text
providerDeltaCiLow >= 10% * P50(cold promptToFirstModelOutputMs)
```

点推定値ではなく下限が閾値をクリアしなければならないため、
閾値をわずかに超えただけのデルタが、ノイズの強さでプロトタイプを
承認することはできない。2 つの P50 の差は継続性のために記録されるが、
もはや何も決定しない。コールドは常に最初のセッションであるため、
ペアはフェーズ 2 の比較のように順序バランスを取ることができない。
これは構成体の既知の制約であり、見落としではない。

それ以外の場合、アーティファクトは保持され、本番作業は停止する。

## 比較と統計

各比較 dwell は、除外される 2 つのウォームアップペアに続いて 30 の
計測ペアを使用する。ただし、明示的に診断用である 500 ms シナリオは
10 を使用し、常に結論の出ない最上位結果を報告する。奇数ペアは
control の後 candidate（AB）を実行し、偶数ペアは candidate の後
control（BA）を実行する。各アームは新しい状態を持ち、記録される
すべてのデルタは `candidate - control` であるため、負のレイテンシが
より高速であることを意味する。

失敗したアームは生出力に残り、そのペアを無効にする。置き換えはしない。
サンプリングは、最初の無効なプロセスまたは完了したペアの後に停止する。
外側の Vitest 期限は、最大の正当なサンプル計画とすべての固定
ライフサイクルタイムアウトから、スケジューラーのマージンを加えて
保守的に導出されるため、正当な期限間際のサンプルでさえ
アーティファクト書き込みを横取りできない。緊急ティアダウンには
独自の固定フック期限がある。外れ値の削除、ウィンザライズ、
サブセット選択、Vitest リトライは行わない。無効な一次ペアは
正式実行を無効にする。

各メトリクスについて、各アームの nearest-rank P50/P90/P99 と平均、
ペア中央値デルタ、勝/分、AB/BA サブグループ中央値を報告する。
P90/P99 は 30 ペアでは記述的なものに過ぎない。少なくとも 100 ペアなしに
P95 やテールレイテンシの結論は出さない。

2 つの中央値定義は意図的に共存しており、列を比較する読者は、
偶数個のサンプルではそれらが異なると予想すべきである。アームごとの
`p50` は nearest-rank であるため、常に観測された値である。
ペアの `median delta` と、ブートストラップ内で再サンプリングされる中央値は、
偶数個の場合に中央 2 値を平均する。したがって Markdown の行は、
どちらも間違っていながら、算術的に一致しない `p50` と `median delta` を
表示することがある。

ペア中央値の 95% 信頼区間は、有効なペアデルタの復元抽出による
10,000 回のシード付きブートストラップ再サンプリングを使用する。
シードと反復回数は保存される。その境界は nearest-rank の
2.5 パーセンタイルと 97.5 パーセンタイルである。各メトリクスのシードは
メトリクスリスト内の位置によってオフセットされるため、メトリクスの
挿入や並べ替えは、それ以降のすべてのメトリクスのブートストラップ境界を
シフトさせ、生のサンプルが同一であっても変更の両側のアーティファクトを
比較不能にする。メトリクスごとに保存された `seed` がこれを監査可能に保つ。
`orderSensitive` は、AB と BA の中央値デルタが反対の符号を持ち、
いずれかの絶対中央値が少なくとも 10 ms である場合に true である。
順序感受性は、平均化して消すのではなく、実行を結論なしにする。

ペアアーティファクトの最上位結果は、その 1 つのシナリオにおける
一次メトリクスのみを記述する。シナリオ間、リソース、機能、公開の
ゲートは評価せず、それ自体ではフェーズ 2 のプルリクエストを
承認できない。

## 失敗、アーティファクト、クリーンアップ

分類されたすべてのライフサイクルまたはサンプルの失敗は保持され、
1 つの一次コードを持つ：

| コード                            | トリガー                                                         |
| --------------------------------- | ---------------------------------------------------------------- |
| `invalid_configuration`           | 無効なモード、パス、dwell、環境、バンドル識別                    |
| `daemon_boot_timeout`             | 期限前にリッスンエンドポイントなし                               |
| `daemon_exited_before_listen`     | デーモンが準備完了前に終了                                       |
| `session_create_failed`           | セッションレスポンスのエラーまたは不正形式                       |
| `sse_connect_timeout`             | 期限前に SSE 未確立                                              |
| `sse_stream_ended`                | 対応する終了前に SSE が終了                                      |
| `prompt_accept_timeout`           | プロンプトリクエストが期限前に完了せず                           |
| `prompt_rejected`                 | エラーまたは不正形式の `202` レスポンス                          |
| `legacy_prompt_response`          | エンドポイントが `promptId` を返さず同期完了した                 |
| `event_buffer_overflow`           | 固定の受理前バッファを超過                                       |
| `provider_request_count_mismatch` | 追加、欠落、早期、または並行の fake リクエスト                   |
| `unexpected_output_kind`          | 回答専用のライブベンチマークが最初に別の出力種別を出力           |
| `first_output_timeout`            | 期限前に条件を満たす出力なし                                     |
| `terminal_before_first_output`    | 条件を満たす出力なしのクリーンな終了                             |
| `turn_error`                      | 対応するエラー終了                                               |
| `terminal_timeout`                | 出力後、期限前に終了なし                                         |
| `wrong_final_text`                | 回答がセンチネルと異なる                                         |
| `cleanup_timeout`                 | 所有リソースが期限までに停止せず                                 |
| `residual_process`                | 追跡されたデーモン/ACP の子孫がクリーンアップ後も生存            |
| `harness_error`                   | 未分類のハーネス不変条件または I/O 失敗                          |

最初の原因となったライフサイクル失敗が一次のままとなる。SSE/セッションおよび
プロセスクリーンアップの失敗は別途記録され、それでもペアを無効にする。
非有限のタイミングと、2 つの符号付きオフセット以外の無効な負のタイミングは
ハーネス失敗として保持されるが、集約前に `null` に正規化され、
失敗した実行がパーセンタイルやゲート計算に寄与することは決してない。
固定タイムアウト、リクエスト制限、バッファ容量は直列化される。
診断メッセージと制限付きの stdout/stderr テールは判定に影響しない。

各起動は、スキーマバージョン 2 の `daemon-first-output` JSON と、
その JSON のみから導出された Markdown を書き込む。これには、
実行/プラットフォーム/バンドル識別、サニタイズされた設定、ウォームアップ、
すべての生の相対タイムスタンプとメトリクス、ラッチされた
初回出力/回答/終了のイベント種別と相関カウント、Provider リクエスト数、
無効なサンプルとペア、失敗、クリーンアップ結果、統計/ブートストラップ/
順序サマリー、明示的な判定理由付きのゲート入力が含まれる。
フェーズ 2 のリソース実行は、RSS 計測で検証エビデンスを拡張する。
分類されたサンプル失敗は固定のサンプルスロットに残る。
無効な設定または未分類のハーネス失敗は致命的なアーティファクトを生成する。
アーティファクトは、非機密のベンチマークセンチネルを超えた認証情報、トークン、
プロンプト内容を除外する。

クリーンアップは常に SSE を中断して待ち、ライブセッションを閉じ、
ACP/MCP の子孫 PID を捕捉し、リーダーがまだ生存と分かっている間に
所有プロセスグループに `SIGTERM` を送り、同じリーダーが固定の
猶予期間を生き延びた場合にのみグループをエスカレートする。
捕捉された子孫と列挙完全性ラッチは、緊急クリーンアップを通じて
アクティブリソースに付いたままとなる。リーダーが終了すると、
POSIX がそれを再利用する可能性があるため、クリーンアップはその数値
プロセスグループ ID を再度プローブやシグナルすることは決してない。
保持された子孫セットのみを検証し、子孫が生存していたり列挙が
不完全だったりした場合は安全に失敗する。Provider ソケットは
プロセスティアダウン後のみ閉じられ、一時状態は両方が検証された後のみ
削除される。クリーンアップはプロセス名全体への kill を決して使用しない。
無効なプロセスまたは完了したペアは、失敗を保持しながら直ちに
サンプリングを停止する。所有プロセスやリスナーの停止を検証できない場合、
ランナーは緊急クリーンアップに先送りされた一時ルートを記録し、
無効ペアを保持する必要がある場合は未開始の対応物をマークし、
追跡リソースを暗黙的に破棄するのではなく緊急ティアダウン失敗を可視化する。
緊急ティアダウンは、先送りされた一時ルートやコンパイルキャッシュを
削除する前に、追跡プロセスと Provider をリトライする。

## フェーズ 2: ベストエフォートの Provider 準備

### 挙動と境界

現在の遅延ジェネレーターは、世代、ストリーミング、トークン数、埋め込み全体で
1 つのローダー promise をメモ化する。準備はその同じ promise を早期に
開始してもよい。別のローダー/Provider を追加したり、model/token/embed
リクエストを行ったり、認証情報を更新したり、eager 検証と Qwen OAuth
認証情報のタイミングを変更したりしてはならない。即時プロンプトは
同じ promise に参加しなければならない。

拒否された準備 promise はメモ化されたままとなり、最初のプロンプトが
同じ失敗を観測する。切り離された呼び出し元は、未処理 rejection を
防ぐためだけに拒否オブザーバーを付加してもよい。保存された promise を
クリアや置き換えしてはならない。この機能は Core 内部にとどまり、
公開の `ContentGenerator` 契約を拡張しない。

最も早い許可トリガーは、ACP 子プロセスによる `session/new` 結果の
書き込み成功である：

1. 受信したリクエスト ID を観測する；
2. 同じ ID と `result` を持つ送信済みレスポンスを観測する；
3. `writer.write(frame)` が解決した後にのみ発生する既存の観測に依存する；そして
4. 準備を開始するが await はしない、unref された `setImmediate` を 1 つスケジュールする。

失敗したレスポンス、認証、`session/load`、`session/resume`、その他の RPC は
これをトリガーしない。レスポンス配信を推測するために sleep は使用しない。
ESM インポートはキャンセルできないため、閉じられたセッションが
既に開始されたインポートの完了を許す場合がある。それでも
リクエストを発行せず、外部リソースを保持せず、未処理 rejection を
生成してはならない。

この境界はベストエフォートに過ぎない。デーモンは引き続き、セッションの
所有権/設定/ソースの永続化作業を行い、子プロセス書き込み後に
外側の HTTP レスポンスを直列化する。Provider インポートは 2 vCPU ホストで
競合し、`processToSessionReadyMs` を劣化させる可能性がある。
`setImmediate` はプロセス間の happens-before 関係を作らない。
したがって、セッションの非劣性はブロッキングである。失敗した場合は、
タイマーを調整するのではなく停止する。正確な外側レスポンス完了シグナルは
HTTP トランスポート、デーモンブリッジ、ACP 子プロセスをまたぐため、
計測された値がその複雑さを正当化する場合にのみ個別の設計が必要である。

### 公開ゲート

リファレンスホストで個別のリリースバンドルを使用する：

| シナリオ                     | 必要な結果                                                                                                            |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Fake、0 ms dwell、30 ペア    | `processToSessionReadyMs` と `promptToFirstModelOutputMs` 両方の 95% ペア中央値 CI 上限が `<= +10 ms`                |
| Fake、100 ms dwell、30 ペア  | `processToFirstModelOutputMs` のペア中央値が `<= -10 ms` かつその 95% CI 上限が `< 0`                                 |
| Fake、500 ms dwell、10 ペア  | 診断用の上限のみ。別の失敗したゲートを補償したり、マージを単独で正当化したりはできない                               |

0 ms と 100 ms の fake 実行全体で、60/60 のペアがすべて有効で、
プリロードウィンドウ内の Provider リクエストがゼロ、残留プロセスがゼロ、
順序感受性なしでなければならない。

Provider 準備が確定した後、プロンプト前に、1、4、16 のアイドルセッションで
プロセスタイル全体の RSS を計測する。両方のゲートを通過しなければならない：

- シングルセッションの candidate と control の差分 P50 RSS が `<= +10 MiB`；
- ライブセッション 1 から 16 への candidate と control の差分増分が、追加セッションあたり `<= +0.5 MiB`：

```text
((candidateRss16 - candidateRss1) -
 (controlRss16 - controlRss1)) / 15
```

各アイドルセッションプローブはセッションをシリアルに作成し、
準備の確定を待ち、RSS 計測前にプロンプトを送らない。
Provider リクエストがあれば失敗とする。ペア数と順序は、正式計測前に
フェーズ 2 検証アーティファクトに固定される。

すべての fake/リソースゲートが通過した後でのみ、同じホストで
実 Provider の外的妥当性を実行する：100 ms での 30 AB/BA ペアと
10 ペアの即時スモーク。機能/認証/ストリーミング/回答の失敗はブロックする。
ネットワークの不確実性は報告されるが、fake ローカルの結論を
どちらの方向にも上書きできない。

## 検証と判定

フェーズ 1 の純粋テストは、回答/思考/ツールの分類、ローカル/リプレイ/診断の
除外、正確な相関と `202` 前の相関、バッファオーバーフロー、終了/エラーパス、
null 可能な回答メトリクス、nearest-rank パーセンタイル、決定論的ブートストラップ、
デルタの符号、無効ペアの保持、順序感受性、代表的な致命的アーティファクト、
JSON から Markdown へのレンダリングをカバーする。opt-in のリリースバンドル
スモークは、Provider 配線、ライフサイクル、アーティファクトスキーマ、
クリーンアップを検証する。正式なベンチマークはデフォルトの CI ではない。

フェーズ 2 の candidate は、さらにトリガータイミングと RPC フィルタリング、
即時プロンプトとのシングルフライト、Provider リクエスト/認証情報更新ゼロ、
メモ化された拒否、ノンブロッキングレスポンス書き込み、安全なシャットダウンを
テストする。ビルド、型チェック、影響を受けるユニット/統合テスト、
完全なアーティファクトゲートを通過しなければならない。

```text
50-process cold/warm baseline valid and threshold met?
├─ no  → retain artifact; stop
└─ yes → prototype separately
         └─ fake 0 ms non-inferior?
            ├─ no  → retain artifact; stop
            └─ yes
               └─ fake 100 ms materially faster with CI < 0?
                  ├─ no  → retain artifact; stop
                  └─ yes
                     └─ 60/60 valid + request/cleanup/order/RSS gates pass?
                        ├─ no  → retain artifact; stop
                        └─ yes
                           └─ real-Provider runs functionally pass?
                              ├─ no  → retain artifact; stop
                              └─ yes → optimization PR may be published
```
