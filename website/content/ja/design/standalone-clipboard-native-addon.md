# スタンドアロンのクリップボードネイティブアドオン

## 問題

CLI バンドルは `@teddyzhu/clipboard` を external のままにしており、npm インストール時にプラットフォーム固有のネイティブパッケージを実行時に読み込めるようにしている。スタンドアローンアーカイブもインポートを external のままにしているが、現在は音声キャプチャのネイティブアドオンのみを `lib/node_modules` にコピーしている。そのため、すべてのスタンドアローンアーカイブでクリップボードからの画像貼り付けがサイレントに失敗する。

## 制約

- 各アーカイブには、`@teddyzhu/clipboard` の JavaScript パッケージと、アーカイブのターゲットに一致するネイティブパッケージがちょうど 1 つ含まれていなければならない。
- リリースジョブはすべてのサポート対象ターゲットを 1 台の Ubuntu ランナー上で作成する。通常の `npm ci` はランナー向けのオプションネイティブパッケージしかインストールしないため、パッケージングはクロスターゲットの成果物についてリポジトリの `node_modules` に依存できない。
- クリップボードパッケージのバージョンはロックファイル由来でなければならず、CLI のオプション依存関係と整合したままでなければならない。
- ホスト以外のクリップボード成果物が利用できない場合でもローカルのパッケージングは動作し続けるべきだが、リリースのパッケージングは部分的にしか機能しないアーカイブを公開するのではなく失敗しなければならない。

## 設計

リリースアーカイブをビルドする前に、ロックされたクリップボードのメタパッケージとすべてのサポート対象ターゲットパッケージを一時ステージングディレクトリにインストールする。そのディレクトリをターゲットごとのパッケージングコマンドに明示的に渡す。

スタンドアローンのパッケージャーは、各ターゲットをそのネイティブクリップボードパッケージにマップし、メタパッケージとそのターゲットパッケージのみを `lib/node_modules/@teddyzhu` にコピーする。明示的なステージングディレクトリが指定されない場合、パッケージャーはリポジトリの `node_modules` を使用する。ホスト成果物の欠落は、ローカルビルドでは警告を出力する。明示的なステージングディレクトリでの成果物欠落は致命的である。

それでもランタイムのモジュールを読み込めない場合、入力プロンプトは最初のクリップボード画像貼り付けの試行時に 1 回だけユーザーに見えるエラーを報告する。既存の Linux の `wl-paste` および `xclip` パスは変更されない。

## 検証

- パッケージングのテストは、ターゲットの選択、他のネイティブターゲットの除外、不完全な明示的ステージングでの失敗をカバーする。
- クリップボードと入力プロンプトのテストは、モジュール利用不可時のコールバックと 1 回限りの UI エラーをカバーする。
- 実際の macOS arm64 アーカイブをリポジトリの外で展開し、バンドルされた Node.js ランタイムで読み込み、システムクリップボード内の実際の PNG で動作を確認する。
