# ワークスペーススコープの observed channel コンタクト

## 問題

デーモン管理のチャネルワーカーは、受信メッセージでプラットフォームのユーザー、グループ、トピックの識別子を受け取りますが、これらの識別子は一時적입니다。認証されたワークスペースクライアントには、最近観測された IM コンタクトを一覧表示する読み取り API が必要であり、それによってユーザーは識別子を手動で探したり再入力したりせずに、完全なプラットフォーム配信ターゲットを選択できます。

## スコープ

この変更は、受け入れられた受信メッセージを観測し、デーモンのワークスペースごとに有界の関係グラフを永続化し、DingTalk、Feishu、Telegram、WeCom チャネルの完全なプラットフォーム識別子を返します。

Webhook の設定やプロアクティブ配信の変更、プラットフォームディレクトリへの問い合わせ、完全なグループメンバーシップの返却を主張すること、ボット出力の観測、過去のトラフィックのバックフィルは行いません。スタンドアロンの `qwen channel start` は変更されません。

## 所有と永続化

デーモンのワークスペースランタイムがレジストリを所有します:

```text
$QWEN_HOME/channels/daemon/<workspaceHash>/observed-contacts.json
```

`QWEN_HOME` はプロセスレベルですが、`<workspaceHash>` が正規化されたワークスペースパスごとにデータを分割します。レジストリはワークスペースの checkout には保存されず、1 つのプロセスグローバルなグラフとして共有されることもありません。そのディレクトリはサポートされている環境ではモード `0700` を使用し、アトミックな JSON ファイルはモード `0600` を使用します。

レジストリは、ワークスペース内のすべてのチャネルと会話を合わせて最大 500 件の関係観測を保存します。各観測には `channelName`、ユーザー identity、オプションのグループ identity、オプションのトピック identity、および `lastObservedAt` が含まれます。重複排除キーは `[channelName, user.id, group?.id, topic?.id]` です。したがって、ノイズの多い会話が別の会話の古い観測をエビクトする可能性があります。最大の 365 日の読み取り可能ウィンドウを超えた観測は、次に受け入れられた書き込み時に削除されます。

## 観測境界

記録は、共有の受信プリフライトが実際の IM メッセージを受け入れた後、コマンドや Agent の処理が開始される前に行われます。したがって、ダイレクト/グループポリシー、メンション、送信者許可リスト、ペアリング拒否は、永続化の前に行われます。

同じ `Envelope` オブジェクトは最大 1 回だけ記録されます。後続のメッセージは、一致する関係のタイムスタンプとラベルを更新します。永続化はベストエフォートです: サニタイズされたエラーが識別子なしでログに記録され、受け入れられたメッセージの処理は継続します。

レジストリは、メッセージ本文、メッセージ ID、添付ファイル、ペイロード、認証情報、webhook リクエスト、プロアクティブ送信、ボット出力を保存しません。

## 関係モデル

```ts
interface ObservedChannelContactObservation {
  user: { id: string; label: string };
  group?: { id: string; label: string };
  topic?: { id: string; label: string };
}
```

- ダイレクトメッセージは、完全なプラットフォーム `senderId` からトップレベルのユーザーを記録します。
- グループメッセージは、完全なプラットフォーム `chatId` からグループを記録し、そのグループ内で観測されたユーザーを記録します。
- スレッド化されたグループメッセージは、`threadId` からトピックも記録し、そのトピック内で観測されたユーザーを記録します。
- グループ内でのみ観測されたユーザーは、トップレベルの `users` には表示されません。同じユーザーがダイレクトメッセージも送信した場合、トップレベルと関連するグループの下の両方に表示されます。
- `groups[].users` と `groups[].topics[].users` は、それらの会話内で観測されたユーザーを意味します。権威あるプラットフォームのメンバーシップリストではありません。
- 送信者ラベルはサニタイズされた受信表示名を使用し、完全なユーザー ID にフォールバックします。グループラベルは、受け入れられた受信 envelope が名前を提供する場合にサニタイズされた名前を使用します。DingTalk は `conversationTitle` を、Telegram は `chat.title` をマップします。Feishu と WeCom のグループラベル、およびすべてのトピックラベルは、完全な ID にフォールバックします。

Feishu は `root_id` を `threadId` にマップし、Telegram は `message_thread_id` を `threadId` にマップします。現在の DingTalk と WeCom の envelope は安定したトピック識別子を公開しないため、それらの観測はグループレベルで停止します。

## 鮮度

人、会話、関係は変化します。読み取り API は、レジストリを恒久的な真実として提示するのではなく、観測をフィルタリングします:

- デフォルトの鮮度: 7 日;
- 呼び出し元によるオーバーライド: `freshWithinSeconds`、1 秒から 365 日まで;
- ユーザー、グループ内ユーザー、トピック内ユーザー、グループ、トピックのタイムスタンプは、最近の観測から独立して導出されます;
- 受動的な観測は、新しいメッセージを生成しない離脱、削除、名前の変更を即座に検出できないため、stale な関係は要求されたウィンドウを超えたときにのみ消えます。

## 読み取り API

プライマリワークスペース:

```http
GET /workspace/channel/observed-contacts?freshWithinSeconds=604800
Authorization: Bearer <daemon token>
```

選択された登録済みワークスペース:

```http
GET /workspaces/:workspace/channel/observed-contacts?freshWithinSeconds=604800
Authorization: Bearer <daemon token>
```

例:

```json
{
  "users": [
    {
      "channelName": "feishu-main",
      "label": "Example User",
      "id": "ou_complete_user_id",
      "lastObservedAt": "2026-07-17T08:00:00.000Z"
    }
  ],
  "groups": [
    {
      "channelName": "feishu-main",
      "label": "oc_complete_chat_id",
      "id": "oc_complete_chat_id",
      "lastObservedAt": "2026-07-17T08:05:00.000Z",
      "users": [
        {
          "label": "Example User",
          "id": "ou_complete_user_id",
          "lastObservedAt": "2026-07-17T08:05:00.000Z"
        }
      ],
      "topics": [
        {
          "label": "om_complete_root_id",
          "id": "om_complete_root_id",
          "lastObservedAt": "2026-07-17T08:05:00.000Z",
          "users": [
            {
              "label": "Example User",
              "id": "ou_complete_user_id",
              "lastObservedAt": "2026-07-17T08:05:00.000Z"
            }
          ]
        }
      ]
    }
  ]
}
```

レスポンスは `Cache-Control: no-store` を使用します。プライマルートはプライマリワークスペースのパーティションのみを読み取ります。修飾ルートは、正確に登録済みで信頼されたランタイムを必要とし、不明、非信頼、ブートストラップ中、drain 中、または削除されたワークスペースに対してプライマリにフォールバックすることはありません。

レジストリが存在しない場合は空のグラフを返します。不正な形式のデータは、コード `channel_observed_contacts_unavailable` を持つサニタイズされた `500` を返します。不正な形式またはサポートされていないレジストリをリセットするには、ワークスペースの `observed-contacts.json` ファイルを削除します。受け入れられたトラフィックがそれを再作成します。無効な鮮度は `400 invalid_freshness` を返します。

クライアントは `workspace_channel_observed_contacts` serve ケーパビリティを介してルートを検出します。ルートは読み取り専用であり、デーモンの bearer 認証の後で登録されます。

## 互換性

Webhook の解析、リクエスト、ターゲット解決、配信は `main` と同一です。この API は観測された識別子を公開するだけです。それらをどのように使うかは呼び出し元が決定します。以前の opaque 参照プロトタイプはリリースされなかったため、レジストリはスキーマバージョン 1 から始まります。

## テスト戦略

- base-channel テストは、プリフライト境界、トピック正規化、Envelope の重複排除、非ブロッキングな永続化失敗をカバーします。
- ストアテストは、ダイレクト対グループのセマンティクス、グループ/トピックの関係、鮮度、更新、上限、権限、不正な形式のデータをカバーします。
- ルートテストは、完全な識別子、no-store レスポンス、鮮度検証、正確なワークスペース所有、サニタイズされた失敗をカバーします。
- サーバーテストは、bearer 認証とケーパビリティの通知をカバーします。
- Webhook リグレッションテストは、`main` と異なる動作がないことを検証します。
