# ツール呼び出しの終端テレメトリー契約

## 問題

ツール呼び出しの終端イベントは、Core スケジューラーと ACP の両方によって生成される。それらはすでに `status`、`success`、`error`、`error_type` を公開しているが、これらのフィールドは食い違うこともあれば欠落することもある。特に、ツールはエラータイプなしでソフトエラーを返し得るし、ACP は `ToolCallEvent` を構築せずにテレメトリーロガーを呼び出し得る。

これにより、ログ、使用統計、メトリクス、フック、チャット記録が、同じ終端結果に対して異なるビューを持つことになる。

## PR1 のスコープ

PR1 は、2 つの境界でランタイムの契約を確立する:

1. Core スケジューラーは、完了した呼び出しを構築する前に、未分類の `ToolResult.error` を `ToolErrorType.UNKNOWN` に変換する。
2. `logToolCall` は、任意のテレメトリーコンシューマーに送信する前に、すべてのイベントを正規化する。

終端の契約は次の通りである:

| `status`    | `success` | `error`   | `error_type`                |
| ----------- | --------- | --------- | --------------------------- |
| `success`   | `true`    | なし    | なし                      |
| `error`     | `false`   | 保持される | 明示的な値または `unknown` |
| `cancelled` | `false`   | なし    | なし                      |

`status` が権威である。空白の `function_name` は `unknown_tool` になる。空でないツール名と空でないエラータイプはそのまま保持される。ノーマライザーはコピーを返し、冪等である。

Core の境界は意図的に非公開である。公開ツール実装は引き続き `ToolResult.error.type` を省略し得るし、成功およびキャンセルされた呼び出しにはエラーの分類がないため、`ToolCallResponseInfo.errorType` は任意のままである。

## コンシューマー

正規化されたイベントは、UI テレメトリー、チャットに記録される UI イベント、QwenLogger、OpenTelemetry のログ、ツール呼び出しメトリクスによって使用される。OpenTelemetry の `error.message` と `error.type` のエイリアスは独立に設定される。

ツール呼び出しカウンターは、`success` を保持しつつ、低カーディナリティの `status` 属性を追加する。公開の `recordToolCallMetrics` の入力は、ソース互換性のために任意の status を受け付ける。省略した呼び出し元は、レガシーの success ブール値からマップされる。レイテンシヒストグラムは引き続き `function_name` のみをキーとし、`error_type` はメトリクスに追加されない。

QwenLogger は `status` と `tool_type` を受け取る。この変更の一部として `mcp_server_name`、関数の引数、結果、スタックトレースは受け取らない。

## 互換性とフォローアップ

この変更はログとメトリクスに対しては付加的だが、PostToolBatch と Core のチャット記録において、未分類の Core エラーを欠落値から `unknown` に変更する。過去のクエリは欠落しているエラータイプを `unknown` として統合すべきであり、データのバックフィルは不要である。

以下は PR1 のスコープ外のままである:

- ACP のパーミッションキャンセルおよびその他の生成側終端ステータスのバグの修正
- ACP の分離された生の `tool_result` 記録の正規化
- PostToolUseFailure フック契約への `error_type` の追加
- プライマリのツールスパンへのエラー分類の追加
- 個々のビルトインおよび MCP のエラー箇所の分類
- レガシー UI の `totalFail` セマンティクスの変更

新しい `status` メトリクスは、ACP の終端ステータス修正が反映されるまで、安定性 SLO のソースにしてはならない。

## ロールアウト時の確認

新しいサービスバージョンについて、オペレーターは以下を確認すべきである:

- エラーのツール呼び出しログに空白の `error_type` が決してないこと
- ツール呼び出しログに空白の `function_name` が決してないこと
- success と cancelled のイベントがエラーフィールドを持たないこと
- 明示的に分類されたエラーが以前のタイプを保持すること
- ツール呼び出しカウンターの総数がツール呼び出しログの量と整合したままであること
- `unknown` の増加が以前の欠落バケットに対応していること
