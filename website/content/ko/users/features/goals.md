# Goal

Goal은 Qwen Code가 명시된 조건이 충족될 때까지 턴 간에 작업을 계속 수행하게 합니다. `/goal <objective>`로 설정하면 세션이 자동으로 계속 진행됩니다. 각 턴은 증거로 기록되며, 모델이 목표가 완료되었거나 차단되었음을 제안하면 독립적인 검증자가 해당 증거만을 바탕으로 그 제안을 판정합니다. 세션은 검증자가 수락하거나, Goal이 일시 중지되거나, 해제되거나, 한도로 중지될 때 종료됩니다.

## 명령어

| 명령어                   | 동작                                                           |
| ------------------------ | -------------------------------------------------------------- |
| `/goal`                  | 현재 Goal과 그 상태를 표시합니다.                              |
| `/goal <objective>`      | Goal을 생성하거나 활성 Goal을 교체합니다.                      |
| `/goal set <objective>`  | 위와 동일, 명시적 형식.                                        |
| `/goal edit <objective>` | 처음부터 다시 시작하지 않고 활성 Goal의 문구를 수정합니다.      |
| `/goal pause` / `resume` | Goal을 유지한 채 루프를 중지하거나 계속합니다.                 |
| `/goal clear`            | Goal을 제거합니다.                                             |
| `/goal-draft <intent>`   | 설정 전에 목표를 대신 작성해 줍니다 (아래 참조).               |

Goal을 생성, 수정 또는 재개하려면 신뢰하는 워크스페이스(`/trust`)가 필요합니다. 헤드리스 사용법은 [헤드리스 모드](./headless.md#run-a-persistent-goal)에서 다룹니다.

Goal이 턴을 청구하면, 푸터 필과 모든 상태 카드는 허용된 창(window)에 대해 얼마나 소비했는지를 `1.2k/30.0m` 형태로 표시합니다. 이 수치는 Goal이 자체 턴에서 수행한 모델 호출 횟수를 세며, 서브에이전트와 검증자의 자체 검사는 포함되지 않습니다. 창은 [`model.goalTokenBudget`](../configuration/settings.md)으로 설정되며, 창을 모두 소모한 Goal을 재개하면 이미 소비한 양에 추가로 새 창이 부여되므로 수치는 처음부터 다시 시작하는 대신 `30.0m/60.0m`으로 표시됩니다. 예산이 없는 Goal은 소비한 양만 표시합니다. 아직 턴을 청구하지 않은 Goal은 아무 수치도 표시하지 않습니다.

세션이 자체적으로 수행하는 각 턴은 Goal이 지금까지 소비한 양, 수행된 턴 수, 그리고 Goal이 무제한으로 실행되지 않는 한 허용된 창을 보고합니다. 이러한 각 턴은 최종 종료 인수인계를 제외하고, 이전 턴의 보고를 신뢰하기보다 워크스페이스를 다시 확인하고, 목표가 요구하는 최종 상태를 향해 작업하며, 이전 턴이 아무것도 변경하지 않았을 때 다른 작업을 수행하고(이전 턴이 존재하여 판단할 수 있는 두 번째 턴부터), Goal이 완료되었다고 제안하기 전에 모든 요구 사항을 인용 가능한 증거에 대해 확인하라는 상시 지시를 포함합니다.

긴 Goal은 주기적으로 기록한 증거를 사이드 모델 검사를 통해 체크포인트 주장으로 압축하므로, 이후 턴과 검증자가 여전히 이를 인용할 수 있습니다. 이 검사는 [`model.goalCheckpointTimeoutSeconds`](../configuration/settings.md)에 의해 제한되며, 기본값은 180초입니다. 주장이 집계 바이트 예산을 초과하거나, 주장이 주장당 문자 제한을 초과하면 한 번의 수정 모델 호출을 수행하며 두 호출 모두 해당 상한을 공유합니다. 시간 내에 완료하지 못한 검사는 결론 없이 포기됩니다. 이는 증거 창이 오버플로우된 경우에만 체크포인트 정지 한도에 포함되며, 오버플로우되지 않은 검사는 연속을 유지하고 이후 턴에 재시도합니다. 호출은 스트리밍되므로 요청별 전송 타임아웃은 연결 및 첫 번째 응답에만 적용되며, 상한 자체는 스트림 가드의 15분 수명 한도에서 중지됩니다. 이를 초과하면 설정이 아닌 가드가 검사를 종료합니다. 설정의 15분 한도는 고정되어 있으며, 스트림 가드 자체의 상한을 높여도 이 한도는 올라가지 않습니다.

## Goal 중단

Goal 턴을 취소하면 Goal이 일시 중지됩니다. 모델이 응답 중이거나 도구가 아직 실행 중인 동안 Esc을 누르면 턴이 중지되고 Goal이 `paused`로 이동하며, 카드와 `/goal` 모두 왜 중지되었는지 표시합니다. `/goal resume`을 실행할 때까지 아무것도 계속되지 않습니다.

Goal이 활성 상태인 동안 메시지를 입력해도 일시 중지되지 않습니다. 메시지는 다음 Goal 턴으로 실행되므로 이를 사용하여 작업을 유도하세요. 중지하려면 `/goal pause` 또는 `/goal clear`를 사용하세요.

모든 일시 중지는 그 이유를 명시합니다: 사용자가 중단한 경우, `/goal pause`를 실행한 경우, 세션 토큰 한도가 다음 모델 요청을 차단한 경우, 턴이 실패한 경우, 또는 연속 세 턴이 검증자가 판정할 수 있는 아무것도 기록하지 않고 제안도 하지 않은 경우입니다. Goal 북keeping 판독(`get_goal`, `update_goal`)은 진행으로 간주되지 않습니다. 한도로 중지된 Goal은 해당 한도의 이유를 대신 유지합니다.

## Goal 판정 방식

검증자는 자체적으로 명령어를 실행하거나 파일을 읽지 않습니다. 트랜스크립트에 이미 있는 내용만 증거로 봅니다:

- 보이는 어시스턴트 출력과 도구 결과가 증거로 인정됩니다. 목표 텍스트, 사용자 프롬프트, 모델의 숨겨진 추론은 증거가 되지 않습니다.
- 출력된 텍스트는 텍스트가 출력되었다는 것만 증명합니다. 테스트가 통과했다는 주장, 파일이 변경되었다는 주장, 원격이 업데이트되었다는 주장은 트랜스크립트에 해당 도구 결과가 필요합니다.
- 사용자가 확인, 선택 또는 승인했다는 주장은 사용자의 실제 메시지가 필요합니다. 검증자는 이를 가정하는 제안을 거부합니다.
- 증거가 없으면 판정은 "아직 완료되지 않음"이지 "완료"가 아닙니다. 아무도 증거로 확인할 수 없는 조건은 한도가 멈출 때까지 루프를 계속 실행합니다.

따라서 목표는 에이전트가 증거를 생산하도록 만들어야 합니다: 명시된 검사를 실행하고 결정적인 출력을 보여줘야 합니다.

## 좋은 목표 작성법

목표에 다음을 이 순서로 포함하세요:

| 부분         | 작성 내용                                                                                                                        |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `Outcome:`   | 완료되었을 때 참이 되는 것을 한 문장으로.                                                                                         |
| `Done when:` | 번호가 매겨진 이진 검사. 최소 하나는 명령어와 예상 종료 코드 또는 출력 라인을 명시하고 해당 라인을 붙여넣도록 요청해야 합니다.     |
| `Must not:`  | 건드리지 않을 파일, 약화시키지 않을 테스트나 임계값, 취하지 않을 되돌릴 수 없는 작업(push, delete, publish).                      |
| `Budget:`    | 포기할 시점: "20턴 후 차단으로 중지" 또는 시간 제한.                                                                              |
| `On block:`  | 막혔을 때 보고할 내용과 사람이 내려야 할 결정.                                                                                    |
| `Context:`   | 에이전트가 워크스페이스에서 찾을 수 없는 사실만: 브랜치, 환경, 이전 결정.                                                         |

목표는 하나로 유지하세요. `/goal set`과 `/goal edit`은 임의의 길이를 허용하지만 대략 1,200자 이하로 유지하세요. 목표는 매 Goal 턴마다 재전송됩니다. 모델이 `propose_goal`를 통해 제안하는 목표는 1,500자로 제한됩니다. 두 명령어 모두 개행을 공백으로 변환하므로, 줄바꿈에 의존하지 말고 항목에 번호를 매기세요.

`Budget`은 언제 중지하고 차단점을 보고할지에 대한 모델에 대한 지시입니다. 목표에 턴 수나 시간 제한을 작성하는 것이 런타임 타이머를 구성하거나 Goal의 토큰 예산을 변경하지는 않습니다.

| 약한 목표                  | 실패 이유                                              | 더 나은 목표                                                                                                                                                                                                                                       |
| -------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| make checkout faster       | 임계값도 검사도 없음.                                  | `Outcome: checkout p95 is below 250 ms. Done when: 1) npm run bench:checkout exits 0 and prints p95 < 250 (paste the line); 2) npm test exits 0. Must not: change the benchmark or skip tests. Budget: stop as blocked after 20 turns.`            |
| clean up the auth module   | "clean"은 증거가 없음.                                 | 관찰 가능한 것을 질문하세요: `src/auth`에서 린트 경고 0개, 커버리지 임계값, 파일 수.                                                                                                                                                                |
| ship the release           | 되돌릴 수 없으며 사람 결정이 필요.                      | 검사 가능한 출시 전 상태로 좁히고(태그 존재, `npm run release:dry-run` 종료 0), "do not publish"를 `Must not`에 넣으세요.                                                                                                                           |
| after I confirm the design | 검증자는 일어나지 않은 확인을 볼 수 없음.               | `On block:`으로 옮겨 사람이 내려야 할 결정으로 명시하세요.                                                                                                                                                                                          |

## `/goal-draft`로 작성하기

`/goal-draft <what you want done>`는 위 과정을 대신 수행하는 번들 skill입니다. 워크스페이스를 범위와 실제 검증 명령어를 파악할 수 있을 만큼만 읽으며, 테스트 실행, 빌드, 의존성 설치, 서비스 시작은 하지 않습니다. 필수적인 선택이 불분명할 때 최대 한 번의 질문을 하고, 간결한 목표를 작성하며, 보통 3–5개의 완료 검사를 포함합니다(충분하면 더 적게). 명시적 요구사항은 유지되며, 횟수를 채우기 위해 검사를 추가하지 않습니다.

감사의 경우, 완료는 합의된 시나리오를 다루고 재현 단계를 포함한 증거를 보고하는 것을 의미합니다. 결함을 찾지 못한 것도 유효한 결과입니다. 초안은 시나리오, 증거 파일, 탐색 라운드, 결함의 최소 개수를 임의로 만들지 않습니다.

성공 기준, 명령어, 입력 경로 또는 필수 결정을 확정할 수 없으면, skill은 `<TODO: …>` 항목과 함께 "Needs clarification"로 표시된 초안을 반환합니다. 해당 초안을 승인용으로 제공하거나 실행 가능한 `/goal set` 또는 `/goal edit` 명령어를 출력하지 않습니다. 비필수적 기본값은 `[ASSUMPTION]`으로 표시되며, 누락된 성공 기준을 대신하지 않습니다.

목표가 준비되면 대화형 터미널 세션에서 아래에 설명된 `propose_goal` 승인 대화상자를 표시할 수 있습니다. Web Shell 및 기타 ACP 클라이언트, 헤드리스 실행, 도구가 비활성화된 세션, 활성 Goal이 있는 세션은 대신 수동으로 실행할 명령어를 받습니다. 전달 시 초안이 적용되지 않았음을 알립니다. skill은 자체적으로 작업을 시작하지 않으며, 승인 없이는 아무것도 설정되지 않습니다.

기존 목표를 전달하여 더 엄격하게 만들 수 있습니다: `/goal-draft all tests pass and the lint is clean`. 활성 Goal에 대해 명시적으로 엄격하게 만들도록 요청하면 `/goal edit`가 생성되며, 교체는 `/goal set`을 사용합니다. 의도한 작업이 불분명하면, skill은 단일 질문 라운드에서 해당 선택을 포함합니다.

### 모델이 제안한 Goal 승인

대화형 터미널 세션에서 모델은 `propose_goal` 도구를 사용합니다. `/goal-draft`가 완료되거나 여러 턴에 걸친 결과를 요청하면, 복사할 `/goal set …` 라인을 출력하는 대신 목표를 제안할 수 있습니다. 제안은 전체 목표를 표시하는 승인 대화상자로 나타납니다. 승인하면 현재 턴이 끝나는 순간(`/goal set`과 정확히 동일하게) Goal이 설정됩니다(모델이 확인하고 중지한 후 첫 번째 Goal 턴이 자동으로 시작됨). 거부하면 아무것도 설정되지 않으며, 모델은 도구 호출이 허용되지 않았다는 사실만 확인하고, 이유를 묻거나 같은 목표를 다시 제안하지 않도록 지시됩니다. 승인은 그것을 요청한 턴에 바인딩됩니다: 해당 턴이 취소되거나 어떤 식으로든 종료에 도달하지 못하면, 승인은 이후 메시지나 자동 턴 아래에서 적용되는 대신 폐기됩니다. 어떤 권한 규칙이나 승인 모드(YOLO 포함)도 이 대화상자를 건너뛸 수 없으며, 다른 Goal이 활성 상태인 경우, 계획 모드, 서브에이전트, 신뢰할 수 없는 폴더에서는 도구가 거부됩니다. 헤드리스 실행에서는 사용할 수 없으며, Web Shell이나 기타 ACP 기반 세션에서도 아직 사용할 수 없습니다(승인을 적용하는 턴 경계를 통과하지 않기 때문). 그곳에서는 출력된 `/goal set` 라인이 여전히 전달 수단입니다.

사용자 설정에서 `goals.modelProposed: "disabled"`로 끌 수 있습니다. 이 설정은 모델이 자율 루프를 시작하도록 요청할 수 있는지 결정하므로, 사용자 및 시스템 범위에서만 적용됩니다. 워크스페이스의 `.qwen/settings.json` 값은 경고와 함께 무시됩니다.

이 skill은 읽기 전용으로 지시되며, 비변경 도구만 자동 승인됩니다(`get_goal`, `read_file`, `glob`, `grep_search`). `ask_user_question`는 의도적으로 자동 승인되지 않으므로, 답변 대화상자가 skill이 답변을 기반으로 초안 작성하기 전에 표시됩니다. 다른 번들 skill과 마찬가지로, `goal-draft`라는 이름의 프로젝트 또는 개인 skill이 이를 재정의하며, `skills.disabled`로 끌 수 있습니다. 번들 skill이 발견되는 방식은 [Skills](./skills.md)를 참조하세요.
