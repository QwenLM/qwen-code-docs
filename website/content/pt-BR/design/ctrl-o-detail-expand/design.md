## 1. Contexto e problema

O qwen-code atualmente vincula **Ctrl+O a `TOGGLE_COMPACT_MODE`**: um **toggle binário global** (`compactMode`, persistido em `settings.ui.compactMode`). Quando ativado:

- oculta a saída de resultados de ferramentas concluídas (Success);
- recolhe blocos de pensamento em uma linha única `Thought for …`;
- uma única tecla **re-renderiza retroativamente todo o histórico** (`refreshStatic()` remonta o `<Static>`).

Isso criou uma divisão global de "**modo enxuto vs modo detalhado**": o mesmo trecho de histórico salta integralmente entre duas formas completamente diferentes por causa de um toggle global, com grande carga mental e instabilidade visual óbvia, e diverge da filosofia de design tanto do gemini-cli upstream quanto do Claude Code.

> **Este esquema se sobrepõe à linha de base de partição do [#5661](https://github.com/QwenLM/qwen-code/pull/5661) (já mesclado no main).** O #5661 refatorou a renderização padrão de grupos de ferramentas: expandiu `CompactToolGroupDisplay` em um **renderizador de resumo particionado por categoria** (`ToolCategory` / `TOOL_NAME_TO_CATEGORY` / `CATEGORY_ORDER` / `getToolCategory` / `buildToolSummary`) e mudou a decisão de recolhimento de `ToolGroupMessage` para **partição type-based**: com gate inverso por `forceExpandAll`, divide ferramentas **por tipo** em `collapsibleTools` (read/search/list, via `isCollapsibleTool(name)`) → recolhidas em resumo de partição `CompactToolGroupDisplay`, e `nonCollapsibleTools` (edit/write/command/agent e Canceled) → **sempre individualmente** `ToolMessage`. **Nota: o #5661 não tem relação com `compactMode`** — `compactMode` não afeta mais a renderização de ferramentas; o recolhimento por partição é determinado puramente pelo tipo de ferramenta + `forceExpandAll`. Este PR **não reconstrói a linha de base de renderização de ferramentas** — sobre a linha de base de partição do #5661 + a infraestrutura de mouse do #5751, ele sobrepõe (1) remoção do `compactMode` global residual, (2) tela de transcript full-detail com Ctrl+O, (3) expansão no local de blocos de ferramentas por clique do mouse. Detalhes em §3.1 (linha de base de partição), §4.1 / §5 (lista de remoção), §9 (divisão de commits em pilha).
>
> **Nota de revisão (rebase para o estado mesclado do #5661)**: versões anteriores deste documento foram escritas com base no snapshot state-based inicial do #5661 (`showCompact = (compactMode || allComplete)`, grupo inteiro recolhido quando inteiramente concluído). O #5661 evoluiu durante o review para a **partição type-based** acima e já foi mesclado no main. §3.1 / §4.1 / §4.5 / apêndice foram reescritos conforme a implementação realmente mesclada: os símbolos centrais são `isCollapsibleTool` / `forceExpandAll` (**eles de fato existem**), e o `fullDetail` do transcript define diretamente `forceExpandAll=true` (em vez de alterar um `showCompact` que não existe mais).

### Objetivos

**Eliminar completamente a distinção de modo global "enxuto/detalhado"**, alinhando ao Claude Code:

1. A vista principal de conversa tem **apenas uma renderização padrão estável e mais enxuta**, que não se deforma mais integralmente com um toggle global.
2. **Ctrl+O é responsável apenas por "ver detalhes completos de certos blocos"** — abre uma **tela de rolagem Transcript full-detail independente**; a vista principal permanece sempre limpa.
3. O aviso inline `(ctrl+o to expand)` serve como orientação de "há mais conteúdo aqui, pressione Ctrl+O para ir ao transcript ver o todo".
4. **(follow-up, fora deste PR) Clique do mouse em bloco para expandir detalhes no local**: como MVP VP-only em PR posterior — clicar em uma linha de resumo de partição recolhida expande no local os detalhes do grupo inteiro. **Este PR não entrega** (justificativa no §4.8: sob partição type-based, ferramentas recolhidas já foram agregadas em uma única linha, sem alvo de clique por ferramenta, sendo necessário redefinir a granularidade do clique; risco sobreposto de mouse SGR/seleção nativa; esforço ~250–400 linhas). O clique em bloco de pensamento recolhido para abrir o ThinkingViewer já é fornecido pelo main/#5751, este PR não mexe.

> Instrução explícita do usuário: **alinhar diretamente ao Claude Code**. Este esquema toma como guia "reproduzir fielmente o modelo ctrl+o = toggleTranscript do Claude Code". A expansão por clique do mouse é uma segunda entrada de interação sobreposta a essa base (canal duplo teclado + mouse).

## 2. Comparação de comportamento dos três (conclusão da pesquisa)

| Dimensão        | qwen-code (atual/base #5661)                                 | Claude Code (real)                          | gemini-cli (upstream)                      |
| ----------- | ------------------------------------------------------------ | -------------------------------------------- | --------------------------------------- |
| Vínculo Ctrl+O | `TOGGLE_COMPACT_MODE`                                        | `app:toggleTranscript`                       | `SHOW_MORE_LINES` + `EXPAND_PASTE`      |
| Modelo central    | **binário global enxuto/detalhado** (persistido) + recolhimento automático de partição do #5661 | **tela transcript global** + expansão per-block por bloco | `constrainHeight` global + expansão por ferramenta  |
| Impacto na vista principal  | re-renderização retroativa de todo o histórico com uma tecla                                         | vista principal constante; transcript é tela independente              | alterna restrição de altura, expande o "último turno"            |
| Estado por bloco    | ❌ nenhum                                                        | ✅ `expandedKeys` (por tool_use_id/uuid)     | ✅ `ToolActionsContext.toggleExpansion` |
| Forma de sair    | pressionar Ctrl+O novamente para voltar                                             | pressionar Ctrl+O / Esc novamente para voltar ao prompt                  | pressionar Ctrl+O novamente para recolher                        |

**A "nova base atual" do qwen = o modelo de partição type-based do #5661 (ponto de partida deste esquema, não a linha de base antiga a ser derrubada):** o #5661 evoluiu a renderização padrão de grupos de ferramentas de "exibir tudo/ocultar tudo via `compactMode`" para **recolhimento particionado por tipo de ferramenta** — quando `forceExpandAll` é falso, `collapsibleTools` (read/search/list, via `isCollapsibleTool(name)`, não Canceled) são recolhidas em linhas de resumo de partição `CompactToolGroupDisplay` (agregadas por `CATEGORY_ORDER`: search/read/list/command/edit/write/agent/other, como `Read 3 files, edited 2 files`), `nonCollapsibleTools` (edit/write/command/agent + Canceled) **sempre individualmente** `ToolMessage`; condições force (confirmação/erro/shell em foco/iniciado pelo usuário/subagente terminal) tornam `forceExpandAll=true` → tudo expandido individualmente. **Esse modelo não tem relação com `compactMode`** — no #5661 `compactMode` não afeta mais a renderização de ferramentas (afeta apenas residualmente blocos de pensamento). Este esquema **mantém intacto todo o mecanismo de partição type-based** sobre essa base, apenas remove o toggle global residual `compactMode` e sobrepõe o `fullDetail` do transcript (definindo `forceExpandAll=true`).

**Mecanismo real do Claude Code (forense do código-fonte empacotado do `claude-code`):**

- `defaultBindings.ts`: `'ctrl+o': 'app:toggleTranscript'`.
- `useGlobalKeybindings.tsx`: `setScreen(s => (s === 'transcript' ? 'prompt' : 'transcript'))`, com telemetria `tengu_toggle_transcript`.
- `REPL.tsx`: quando `screen === 'transcript'`, renderiza **todo** o histórico com **rolagem virtual**, e `verbose={true}` (força expansão completa); o modo `prompt` tem limite de linhas exibidas.
- `CtrlOToExpand.tsx`: no final de blocos truncados renderiza `(ctrl+o to expand)`; clicar/pressionar entra no transcript para ver o todo.
- Há também `expandedKeys` independente (por mensagem), mas **a entrada principal de interação é a tela transcript**.

**Modelo per-block do gemini-cli (complemento forense)**: o gemini-cli segue expansão por ferramenta — `expandedTools` / `toggleExpansion` do `ToolActionsContext` mantêm o estado de expansão por ferramenta individual. Isso pertence à **mesma linha de pensamento da expansão de pensamento per-block Alt+T já existente no main do qwen (`ThoughtExpandedContext`)**: ambos resolvem "expandir um único bloco no local". Já o transcript deste esquema resolve **outra dimensão** — "revisão completa da conversa inteira" (snapshot congelado em alt-screen, todos os blocos em fullDetail, rolável); os dois são ortogonais e complementares (detalhes no §4.7).

**Benefício chave**: o qwen-code já possui naturalmente toda a base necessária para implementar a tela transcript (`ScrollableList`/`VirtualizedList` + `AlternateScreen.tsx` já entregue), ver §4.4.

## 3. Definição do comportamento-alvo

### 3.1 Linha de base padrão (vista principal) = modelo de partição do #5661

A vista principal adota uma regra de renderização única e estável para **todos os itens de histórico**, **sem nenhum toggle global para alterná-la**. Essa linha de base **não foi criada por este esquema**; é o **modelo de partição type-based (recolhimento particionado por tipo de ferramenta) já entregue** do [#5661](https://github.com/QwenLM/qwen-code/pull/5661) — este esquema o mantém intacto, apenas removendo o toggle global `compactMode` não relacionado:

| Tipo de bloco                                                          | Renderização da linha de base padrão (modelo de partição type-based do #5661)                                                                                                                                                                 | Visível por completo apenas no transcript         |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| Pensamento (gemini_thought / \_content)                              | resumo de linha única `✻ Thought for 3s (ctrl+o to expand)`; durante o streaming exibe em tempo real, após estabilizar vira resumo                                                                                                                            | sim                               |
| **ferramentas recolhíveis** (read/search/list, não force)              | via `isCollapsibleTool(name)` entram em `collapsibleTools`, **recolhidas** em **linha de resumo de partição** `CompactToolGroupDisplay` (agregadas por `CATEGORY_ORDER`, como `Read 3 files, edited 2 files, ran 1 command`)                         | detalhes por ferramenta visíveis por completo no transcript |
| **ferramentas não recolhíveis** (edit/write/command/agent / Canceled) | entram em `nonCollapsibleTools`, **sempre individualmente** renderização completa `ToolMessage` (sua saída é em si a resposta) — mesmo com o grupo inteiro concluído não são recolhidas em resumo                                                                                             | ——                               |
| grupo misto (coexistência de recolhíveis + não recolhíveis)                    | **coexistência de linha de resumo + por ferramenta**: parte recolhível → uma linha de resumo `CompactToolGroupDisplay`; parte não recolhível → `ToolMessage` individual. **Não é recolhimento do grupo inteiro**                                                                  | parcial                             |
| resultados string/ansi de ferramentas recolhíveis concluídas                      | recolhidos por padrão (`shouldCollapseResult = !forceShowResult && Success && isCollapsibleTool(name) && (string\|ansi)` → área de resultado não renderizada); **resultados não recolhíveis de Shell/Edit etc. sempre exibidos**; diff/plan/todo/task com renderizadores próprios | visível por completo no transcript               |
| erro / aguardando confirmação / iniciado pelo usuário / shell em foco / subagente terminal              | torna `forceExpandAll=true` → grupo todo `ToolMessage` individual; a ferramenta gatilho correspondente recebe `forceShowResult=true` removendo o recolhimento de resultado                                                                                                         | ——                               |
| mensagem de texto comum                                                    | exibição completa                                                                                                                                                                                                        | ——                               |

Pontos principais:

- **O recolhimento por partição é dirigido por `forceExpandAll` + `isCollapsibleTool` do #5661** — em `ToolGroupMessage`, `forceExpandAll = hasConfirmingTool || hasSubagentPendingConfirmation || hasErrorTool || isEmbeddedShellFocused || isUserInitiated || hasTerminalSubagent` (**não contém `compactMode`/`allComplete`**). Quando `forceExpandAll` é falso, divide por `isCollapsibleTool(name)` (read/search/list, não Canceled) em `collapsibleTools` → resumo `CompactToolGroupDisplay`, o restante vai para `nonCollapsibleTools` → `ToolMessage` individual; quando verdadeiro, todas as ferramentas vão para `nonCollapsibleTools`.
- **O recolhimento de resultados concluídos é dirigido pelo gate `shouldCollapseResult` do #5661** — em `ToolMessage`, `shouldCollapseResult = !forceShowResult && status === Success && isCollapsibleTool(name) && (renderer.type === 'string' || 'ansi')`. **Note a guarda adicional `isCollapsibleTool(name)`**: apenas resultados string/ansi de read/search/list são recolhidos; resultados de ferramentas não recolhíveis como Shell/Edit/Agent são **sempre visíveis**. `ToolGroupMessage` em cenários force passa **individualmente** `forceShowResult=true` para as ferramentas gatilho (`isUserInitiated || Confirming || Error || pending-agent || subagente terminal`).
- **Condições force têm a semântica de segurança de "precisa ser visto"** — pilhas de erro, pedidos de confirmação, shell em foco, ferramentas iniciadas pelo usuário não são recolhidas por partição via `forceExpandAll`, e resultados de ferramentas não recolhíveis naturalmente não são recolhidos (mais `forceShowResult` da ferramenta gatilho). **Os símbolos centrais `forceExpandAll` / `isCollapsibleTool` de fato existem** (implementação mesclada do #5661); **não é necessário** um `shouldForceFullDetail.ts` / `COLLAPSIBLE_CATEGORIES` independente — a semântica force está inline em `forceExpandAll`, o gate de recolhimento de resultado está inline em `shouldCollapseResult` (ver §4.5).
- **`fullDetail` deve valer antes dos dois early returns de `ToolGroupMessage` (ponto chave de implementação, não regredir)** — `ToolGroupMessage` tem dois retornos antecipados antes de calcular `forceExpandAll` que contornam a lógica de partição: (1) **grupo de agentes puramente paralelo** → painel denso `InlineParallelAgentsDisplay`; (2) **grupo memory-only concluído** → selo `Recalled/Wrote N memories`. Ambos fariam com que mesmo sob fullDetail do transcript **não fosse exibição completa**. Por isso os dois early returns são guardados por **`!fullDetail`**: quando fullDetail é verdadeiro, eles são pulados, fazendo cada ferramenta/agente cair em `ToolMessage` individual (`forceExpandAll=true` + `forceShowResult=true` + sem truncamento). Já coberto por teste de regressão (grupo memory-only sob fullDetail renderiza individualmente em vez de selo).

### 3.2 Ctrl+O = abrir/fechar tela Transcript full-detail (tela de snapshot congelado independente)

Reproduzindo fielmente o transcript do Claude Code (forense já feito do código-fonte do claude-code):

- pressionar **Ctrl+O** a qualquer momento: alterna para o transcript que assume a tela inteira, renderizando um **snapshot congelado**: congela o histórico do momento da entrada, **remove o truncamento de altura/linhas da camada de UI** (texto completo do pensamento, saída de ferramentas o mais completa possível), suporta rolagem com cima/baixo/PgUp/PgDn/Home/End. O caminho VP padrão reutiliza a alternate screen já ocupada pelo ink root; apenas o caminho legado `<Static>` usa o componente `AlternateScreen` para escrever DEC `1049` (`\x1b[?1049h`) e entrar temporariamente. ⚠️ "Completo" refere-se apenas à camada de UI — **conteúdo já removido por orçamento de resposta do modelo ou compressão de display do histórico não pode ser recuperado do history da UI** (ver §4.4), não é "texto completo" literal.
- **Semântica de snapshot congelado (incluindo pending; armazena comprimentos em vez de clonar history)**: o histórico do qwen-code tem **duas partes** — o `history: HistoryItem[]` já estabilizado (`UIStateContext.tsx:45`) e os `pendingHistoryItems` em streaming (`:123`, concatenados com id negativo na renderização, `MainContent.tsx:456-461`). O freeze do Claude Code na verdade armazena apenas dois números `{ messagesLength, streamingToolUsesLength }` e faz slice na renderização, em vez de clonar na entrada. **O qwen-code segue isso congelando ambas as partes, mas na forma mais econômica**: para o history estabilizado **armazena apenas o comprimento** `historyLength` (na renderização `history.slice(0, historyLength)`, sem clonar o history inteiro), para o `pendingItems: [...pendingHistoryItems]` em streaming **armazena cópia rasa** (pending é área temporária, será reescrito ou limpo posteriormente, é preciso uma cópia para congelar a forma daquele momento). A renderização do transcript concatena `history.slice(0, historyLength)` com o snapshot de pending **congelado no momento da entrada**. History/pending novos adicionados em segundo plano posteriormente **não entram** no transcript, garantindo que o congelamento não oscile.
- **Não afeta os dados da tela principal**: conversa/streaming em segundo plano continuam rodando (apenas não renderiza caixa de entrada/spinner). Ao sair, o caminho VP padrão restaura a árvore principal dentro da mesma root alt-screen; o caminho legado sai da alt-screen temporária e remonta o history atual via `refreshStatic()`, garantindo sem duplicatas, sem faltas e sem poluir o scrollback.
- **Teclas de saída**: `Esc` / `q` (estilo less) / `Ctrl+C` fecham; pressionar **Ctrl+O** novamente também alterna para fechar. Após sair, volta à tela principal, podendo ver o conteúdo em streaming adicionado em segundo plano enquanto o transcript estava aberto.
- A semântica do aviso inline `(ctrl+o to expand)` é **unificada como "pressione Ctrl+O para entrar no transcript e ver o contexto completo", não "aqui está truncado"**. Note que o resumo do bloco de pensamento sempre traz esse aviso (independentemente do comprimento original); a saída de ferramenta traz `+N lines` apenas quando truncada por restrição de altura — as condições de gatilho dos dois avisos são diferentes, o que é esperado (ver §7 #7).

> Forense: `ink/components/AlternateScreen.tsx`, `termio/dec.ts:16` (`ALT_SCREEN_CLEAR: 1049`), `screens/REPL.tsx:1325/4184/4381` (frozenTranscriptState + slice), `keybindings/defaultBindings.ts:160-169` (`escape/q/ctrl+c → transcript:exit`) do claude-code.

### 3.3 Relação com Ctrl+S (`SHOW_MORE_LINES` / `constrainHeight`)

- `SHOW_MORE_LINES` (atual Ctrl+S) permanece inalterado: ele remove a restrição de altura da **área pending atual**, pertencendo a "ver temporariamente mais linhas durante a saída em streaming", e é ortogonal ao transcript.
- Este esquema **não mexe no vínculo Ctrl+S**, evitando uma superfície de mudança muito grande. (Alternativa: no futuro pode-se avaliar incorporar `SHOW_MORE_LINES` ao transcript também, mas não nesta fase.)

## 4. Design de arquitetura

### 4.1 Remover o compactMode global residual (remoção líquida sobre a linha de base de partição do #5661)

> **Esclarecimento de escopo**: o #5661 já mudou a linha de base de renderização de ferramentas para o modelo de partição type-based, **e no #5661 `compactMode` já não afeta a renderização de ferramentas** (`forceExpandAll` não referencia `compactMode`; `compactToggleHasVisualEffect` já foi alterado pelo #5661 para sondar apenas `gemini_thought`, não mais sondando `tool_group`). Portanto o escopo de remoção deste PR é **menor** do que a concepção inicial: apenas remover o **toggle binário global que ainda resta** após o #5661 (context/settings/binding/i18n), **sem tocar** na decisão de partição de `ToolGroupMessage` (não há `showCompact` nem termo `compactMode ||` para remover), e **mantendo `CompactToolGroupDisplay` e todo o mecanismo de partição type-based**.

Remover os seguintes conceitos e todas as suas referências (lista no §5):

- `CompactModeContext` / `CompactModeProvider` / `useCompactMode`

O overlay similar mais recente deste repositório, `ThinkingViewer`, coloca o canônico no `useState` local do `AppContainer` (`thinkingViewerData`), passando apenas a ação mínima `open` pelo **dedicado** `ThinkingViewerContext`, **não** o colocando no amplo `UIStateContext`; o estado da tela transcript do claude-code também fica no topo local do `REPL`. Portanto o transcript também fica **local no `AppContainer`**, renderizando condicionalmente `<TranscriptView>` no JSX de topo do `AppContainer` assim como `<ThinkingViewer>`, **sem** projeção via `UIStateContext`/`UIActionsContext`. (Nota: **o código de implementação já é assim** — `transcriptFreeze` é useState local do `AppContainer`, sem nenhum campo de transcript no `UIStateContext`; a documentação inicial escrevia "expor ao UIStateContext" incorretamente, corrigido aqui.)

- **ações (closures locais)**: `openTranscript()` (tira snapshot das duas partes: `setTranscriptFreeze({ historyLength: history.length, pendingItems: [...pendingHistoryItems] })`) / `closeTranscript()` (define null) / `toggleTranscript()` — todas callbacks locais do `AppContainer`, chamadas diretamente pelo tratamento de tecla global (§4.3), sem necessidade de passar por `UIActionsContext`.

Ou seja, o transcript congela no "momento desta abertura"; fechar e abrir de novo atualiza para o mais recente — não é congelamento permanente na primeira vez. Note que o snapshot para **history estabilizado armazena apenas o comprimento** (`historyLength`, na renderização `history.slice(0, historyLength)`, alinhado ao Claude Code que armazena `messagesLength` em vez de clonar), e para a **área pending em streaming armazena cópia rasa** (`[...pendingHistoryItems]`, pois pending é área temporária que será reescrita/limpa posteriormente, é preciso armazenar cópia para congelar a forma daquele momento). **Não é clonagem do history inteiro**.
- **`isTranscriptOpen` não é incorporado ao agregado `dialogsVisible`** (ver análise de Esc/teclas do §4.3 — incorporar afetaria indevidamente lógicas como "só pode cancelar requisição com Esc quando Responding e sem dialog"); o bloqueio do composer é alcançado naturalmente pelo transcript assumir a tela inteira via alt-screen, sem depender de `dialogsVisible`.

### 4.3 Reescrita do tratamento da tecla Ctrl+O

Em `AppContainer.handleGlobalKeypress`:

```ts

// Adicionar:

}
```

- Adicionar `Command.TOGGLE_TRANSCRIPT = 'toggleTranscript'`, vínculo padrão `[{ key: 'o', ctrl: true }]`.

**Atribuição de teclas (evitar corrida de tratamento duplo)**: `KeypressContext` é **broadcast, sem flag consumed** (`KeypressContext.tsx:655`, todos os assinantes de `useKeypress` recebem a mesma tecla). Portanto é preciso **owner único**, com as seguintes regras:

- **Ctrl+O é tratado apenas pelo `handleGlobalKeypress` global** (a semântica de toggle vale tanto para abrir quanto fechar). **O próprio `useKeypress` do TranscriptView nunca trata Ctrl+O**, senão uma tecla seria respondida em dois lugares → corrida de fechar-e-abrir.
- **Esc / q / Ctrl+C fecham o transcript: tratados pelo `handleGlobalKeypress` global, e devem ser o [primeiro, absoluto primeiro] branch de `handleGlobalKeypress`** — ⚠️ note que o primeiro branch atual é `Command.QUIT` (Ctrl+C, `AppContainer.tsx:3104`), o segundo é `Command.EXIT` (Ctrl+D, `:3121`), só o terceiro é `ESCAPE` (`:3132`), e no topo do branch `ESCAPE` ainda há a guarda vim `if (vimEnabled && vimMode==='INSERT') return;`. Portanto o branch de fechamento do transcript deve ser **anterior a todos esses** — anterior ao QUIT/Ctrl+C, anterior ao EXIT, anterior ao branch ESCAPE e sua guarda vim INSERT — curto-circuito:
  ```ts
  const handleGlobalKeypress = (key) => {
    // Deve ser o primeiro branch de todo o handleGlobalKeypress:
    // anterior a QUIT(Ctrl+C) / EXIT(Ctrl+D) / branch ESCAPE (e sua guarda vim INSERT)
    if (isTranscriptOpenRef.current &&
        (key.name === 'escape' || key.name === 'q' || (key.ctrl && key.name === 'c'))) {
      closeTranscript(); return;
    }
    if (keyMatchers[Command.QUIT](key)) { ... }   // existente :3104
    ...
  ```
  Caso contrário: com o transcript aberto, pressionar Ctrl+C acionaria primeiro o quit/`ctrlCPressedOnce`; pressionar Esc seria engolido pela guarda vim INSERT sem conseguir fechar o transcript. Como este branch é guardado por `isTranscriptOpenRef`, só vale com o transcript aberto, sem impacto na edição vim normal. **Testes**: `Ctrl+C closes transcript and does NOT set quit/ctrlCPressedOnce`; `Esc closes transcript even when vim INSERT mode is active`.
  - **Por que `q` (letra comum) é seguro**: esse branch é guardado por `isTranscriptOpenRef`, só casa com o transcript aberto (quando o composer foi assumido pela alt-screen, sem foco de entrada de texto); com o transcript fechado, `q` cai diretamente no fluxo de entrada normal, sem impacto. Não é necessário novo vínculo `Command`, basta matching inline.
- Como `isTranscriptOpen` **não é incorporado a `dialogsVisible`**, **não passa** por `useDialogClose`; o Esc do transcript é tratado independentemente no branch global prévio acima (`useDialogClose` permanece intacto).
- Para evitar closure obsoleta, adicionar `isTranscriptOpenRef` (imitando o padrão existente `dialogsVisibleRef`, `AppContainer.tsx:2425`).

### 4.6 Interações em segundo plano enquanto o transcript está aberto (diálogos de confirmação / resize)

O transcript assume a tela inteira via alt-screen, mas a conversa em segundo plano continua rodando — isso traz algumas regras de interação que devem ser explicitadas:

1. **Confirmações/diálogos bloqueantes (anti-deadlock, deve tratar, cobrindo todos os tipos)**: confirmações bloqueantes **não são apenas `WaitingForConfirmation`** — `DialogManager.tsx` também renderiza `shellConfirmationRequest` (ShellConfirmationDialog), `loopDetectionConfirmationRequest` (LoopDetectionConfirmation), `confirmationRequest` (ConsentPrompt), `confirmUpdateExtensionRequests` (ConsentPrompt), `providerUpdateRequest` (ProviderUpdatePrompt) etc. Qualquer um coberto pela alt-screen ficaria invisível e sem resposta para o usuário → **deadlock**. Regra: **quando qualquer confirmação/diálogo bloqueante precisar de entrada do usuário, automaticamente `closeTranscript()`** (adicionar `useEffect` em `AppContainer` observando a união desses estados de requisição + `streamingState===WaitingForConfirmation`; qualquer um verdadeiro sai da alt-screen), permitindo que o usuário veja e responda. Isso é mais simples e sem ambiguidade do que "re-renderizar várias caixas de confirmação dentro da alt-screen". **Os testes devem cobrir individualmente cada confirmação bloqueante acima acionando o fechamento automático** (§8).
2. **Resize de janela**: com o transcript aberto, mudar o tamanho do terminal faz o `VirtualizedList` precisar re-layoutar pela nova largura e recalcular alturas de linha. Basta reutilizar sua resposta a resize existente; ao sair do transcript, o `refreshStatic()` do §4.4 também re-layouta a tela principal. Os testes devem cobrir "posição de rolagem não colapsa após resize dentro do transcript".

Após mesclar o upstream main, o repositório já tem um **mecanismo de expansão de pensamento em nível de bloco (per-block)**, que **coexiste de forma complementar** com o transcript de conversa completa deste esquema, cada um resolvendo demandas diferentes:

- **Decisão de expanded do bloco de pensamento após a mesclagem**: o bloco de pensamento em renderização usa `expanded = isPending || fullDetail || resolvedThoughtExpanded` — qualquer uma das três fontes verdadeira expande:

Os dois têm objetivos diferentes, entradas diferentes (Alt+T vs Ctrl+O), escopos diferentes (bloco único vs conversa completa), **ortogonais e complementares**, sem escolha excludente.

### 4.9 Complementação da camada de dados do full-detail do transcript (eliminando o estado intermediário de "recolhimento de segunda camada")

**Contexto**: este PR define Ctrl+O como "tela de transcript full-detail" (§3.2) — a vista principal mantém o resumo de partição enxuto do #5661, Ctrl+O chama a qualquer momento o "registro completo", todos os itens renderizados em `fullDetail`. O design **promete** que a saída de ferramentas dentro do transcript é **completamente expandida, não recolhida, não truncada por altura**; na implementação, alcançado pelo sinal único `fullDetail` incorporado em `forceExpandAll` + `forceShowResult` por ferramenta + `availableTerminalHeight=undefined` (§4.5).

**Problema (medição de aceitação, §3.4)**: o modelo de "três camadas de recolhimento" do usuário trava na segunda camada — a primeira camada (vista principal) `✔ read 1 file, listed 1 dir` resumo de partição deve ser mantido; a segunda camada (Ctrl+O atual) cada ferramenta uma linha + **resumo curto** (`列出文件 Listed 3 items` / `Grep Found 4 matches` / `读取文件 README.md`); e **a camada mais detalhada falta** (entradas de diretório reais, linhas de acerto do grep, texto completo do arquivo). Ferramentas **recolhíveis somente leitura** como `read_file` / `ls` / `grep` / `glob` ficam apenas em nível de resumo no transcript, violando a semântica de "full-detail".

**Causa raiz (camada de dados, não chave de recolhimento)**: por forense, a cadeia `fullDetail → forceExpandAll / forceShowResult / availableTerminalHeight=undefined` do §4.5 **vale corretamente em todos os pontos**; o problema é que o front-end simplesmente não recebe os detalhes completos:

- `ToolResult` tem dois caminhos de conteúdo (`packages/core/src/tools/tools.ts:443+`): `llmContent` ("factual outcome", completo) e `returnDisplay` (comentário explicitamente "user-friendly **summary**").
- O `returnDisplay` de `ls` / `grep` / `ripGrep` / `read_file` carrega apenas resumo (`Listed N` / `Found N` / `''`); o conteúdo completo vai apenas para `llmContent` (forense: retornos de `ls.ts` / `grep.ts` / `ripGrep.ts` / `read-file.ts`).
- A estrutura de exibição de ferramenta do front-end `IndividualToolCallDisplay` (`packages/cli/src/ui/types.ts:65`) **tem apenas `resultDisplay`**, sem campo de conteúdo completo; o ponto de conversão `useReactToolScheduler.ts:330` pega apenas `response.resultDisplay` (resumo).
- O conteúdo completo chega ao front-end como `ToolCallResponseInfo.responseParts` (`turn.ts:116`), mas é embrulho de `functionResponse`; `partToString` / `getResponseTextFromParts` pegam apenas `part.text`, **não conseguem ler `functionResponse.response.output`** (`partUtils.ts:61-69`, `generateContentResponseUtilities.ts:14`) — as parts recebidas pelo front-end têm o conteúdo completo, mas **não há helper pronto para extraí-lo**.

**Descoberta chave: os detalhes completos na verdade já são naturalmente persistidos (decide a direção do esquema)**

- `convertToFunctionResponse(...)` (`coreToolScheduler.ts:679-714`) escreve o **`llmContent` completo** em `functionResponse.response.output` (string colocada diretamente; array extrai **todo** o `text` concatenado, media vai para `parts`) — ou seja, as parts do resultado de ferramenta **já contêm os detalhes completos**.
- O `ChatRecord.message` persistido armazena exatamente `response.responseParts` (forense: pontos de chamada de `recordToolResult(...)` `coreToolScheduler.ts:4009`, `Session.ts:3334/4404` etc., todos passando `responseParts`), é **functionResponse completo**, não resumo.
- Portanto os detalhes completos já estão posicionados e são homólogos nos três caminhos: **live** (`trackedCall.response.responseParts`) / **resume** (`record.message.parts`, case tool_result de `resumeHistoryUtils`) / **replay ACP** (`HistoryReplayer.replayToolResult` já passa `message: record.message.parts` para `emitResult`). A "persistência" é **naturalmente satisfeita** na camada de dados, sem necessidade de novo campo de persistência (essa premissa é guardada pelos testes de "proteção de premissa do Esquema Y" do §8 — afirmando que o `output` completo de `message.parts` não se perde e não envereda erradamente pela `compressedHistory` da API através das quatro etapas recording / loadSession / resume / replay; **se falhar, retroagir ao Esquema X**).

**Esquema Y (fonte única de dados completa + extração na camada de exibição, alinhado ao claude code)**

O mecanismo do claude code é "**manter completo na camada de armazenamento, truncar na camada de exibição por `verbose`**", sem dividir `llmContent`/`returnDisplay`; após resume o transcript continua full-detail (forense: `claude-code/src/screens/REPL.tsx:4185-4194,4381-4382,4402` frozen transcript = snapshot de messages em memória + `verbose=true`; `src/utils/toolResultStorage.ts`, `sessionStorage.ts` persistem conteúdo completo/referências de arquivo). Como o conteúdo completo do qwen já é persistido em parts, adota-se o pensamento isomorfo — **sem novo campo de persistência, extraindo centralizadamente o texto completo do functionResponse já existente para exibir**.

- **Não escolher X (novo campo `contentForDisplay` atravessando core→serialização→replay→front-end, 8 pontos)**: **redundância de conteúdo** com os já persistidos `responseParts` (mesmo conteúdo completo armazenado duas vezes), amplia o schema de persistência e a superfície de migração.
- **Não escolher B (alterar `returnDisplay` por ferramenta para carregar completo)**: viola a semântica `returnDisplay`="summary", altera várias ferramentas.
- **Não escolher "rasgar o protocolo espalhado no front-end"**: frágil conforme a causa raiz — mas o Esquema Y usa **um helper central de core** para extrair, sem rasgar espalhado em vários pontos.

**Pontos de mudança (Esquema Y)**:

1. **Core adiciona helper de extração** `getToolResponseDisplayText(parts: Part[]): string | undefined` (paralelo a `getResponseTextFromParts`). **Regra de prioridade implementável** — media pendurada em **`functionResponse.parts` aninhadas** (não no topo, forense: `coreToolScheduler.ts:661-744`, `postCompactAttachments.ts:149-161`, `compactionInputSlimming.ts:205-213`): percorrer parts do topo → para cada `functionResponse` ler texto `response.output` não vazio e concatenar; depois percorrer suas **`functionResponse.parts` aninhadas**, para `inlineData`/`fileData` emitir placeholder (como `<image: mimeType>`), para `{text}` aninhado manter também placeholder (o slimmer de compactação produz essa forma); **se sem output mas com media aninhada → retornar placeholder**; **sem output nem media → retornar `undefined` para a UI degradar ao resumo** (evitando `read_file` media-only exibir vazio ou usar indevidamente "Tool execution succeeded"). **Entrada única de extração, compartilhada por live/resume/replay**.
2. **CLI `IndividualToolCallDisplay` (`types.ts:65`) adiciona** `detailedDisplay?: string` — **valor derivado, não persistido** (extraído a cada vez das parts já persistidas).
3. **Extração live**: branch success de `useReactToolScheduler`: `detailedDisplay = getToolResponseDisplayText(trackedCall.response.responseParts)` (**sem truncamento secundário**, ver "memória e limites" abaixo).
4. **Extração resume**: case `tool_result` de `resumeHistoryUtils` (:411-431, já possui `record.message.parts`) extrai com o mesmo helper.
5. **Extração replay ACP**: `HistoryReplayer.replayToolResult` (:259) já passa `message: record.message.parts` para `emitResult`; no ponto de mapeamento ACP→display (`resumeHistoryUtils` / `ToolCallEmitter`) deriva com o mesmo helper. **Sem necessidade de novo campo de protocolo ACP**.
6. **Divisão de renderização (corrigindo vazamento de `forceShowResult`)**: passar **explicitamente `fullDetail`** a `ToolMessage` (passado por `ToolGroupMessage`). Apenas quando **`fullDetail && isCollapsibleTool(name) && detailedDisplay`**, usar `detailedDisplay` para substituir o `resultDisplay` de resumo.
   - **Chave**: separar "remover recolhimento/altura" (`forceShowResult`/`forceExpandAll`, pode ser acionado por `isUserInitiated` / `Confirming` / `Error` / pending-agent / terminal-subagent, ver `ToolGroupMessage.tsx:469-475`) de "trocar para fonte de dados completa" (**apenas** `fullDetail`). Caso contrário, cenários force na vista principal como user-initiated/error exibiriam indevidamente detalhes completos, violando "vista principal inalterada".

**Memória e limites (sem truncamento secundário, conforme a semântica de "full-detail")**: `detailedDisplay` **não** passa pelo truncamento de 32k de `compactStringForHistory` — isso tornaria o Ctrl+O um "preview limitado a 32k" em vez de "full-detail", conflitando com a promessa do §3.2/§3.4 (especialmente `read_file`: `maxOutputChars=Infinity`, autopaginado, isento do truncamento de caracteres do scheduler, ver `read-file.ts:385-390`; leituras grandes legítimas ultrapassam 32k; nesse caso `functionResponse.response.output` ainda tem conteúdo completo >32k, não devendo ser cortado novamente pela UI). `detailedDisplay` é diretamente = texto completo de `getToolResponseDisplayText(parts)`, e sua fronteira é o **já aplicado pelo core** `truncateToolOutput`/paginação própria da ferramenta (a UI não recupera conteúdo já descartado pelo core, §4.5) — **a camada de UI não sobrepõe mais limite de caracteres**. `detailedDisplay` é valor derivado, não entra no banco; o conteúdo já existe em `responseParts`, apenas mais uma referência de string. Saídas enormes são renderizadas pela rolagem virtual do `ScrollableList` do transcript por viewport (limitado), isomorfo ao claude code "armazenamento mantém completo, camada de exibição decide por `verbose`".

**Escopo (decidido por categoria, sem lista hardcoded)**:

- Por **`isCollapsibleTool(name)`** — categoria de nível `read/search/list`, **incluindo `glob`/`FindFiles`** (`getToolCategory` classifica GLOB como search, ver `CompactToolGroupDisplay.tsx:74-95`; o `returnDisplay` de `glob.ts:267-280` também é apenas `Found N matching file(s)`). **Não** hardcoded `read_file/ls/grep`.
- Vista principal (não `fullDetail`), `run_shell_command` (`returnDisplay = result.output`, completo) / `edit` / `write` (diff completo) **inalterados**.

**Pontos de teste (incorporados ao §8)**:

- helper do core: extração de `functionResponse.response.output`, placeholder de media, degradação para vazio/ausente;
- **ambos os caminhos live + resume produzem `detailedDisplay`**, especialmente **transcript continua full-detail após resume/replay**; o caminho ACP já traz texto completo via `transformPartsToToolCallContent` (não é transcript TUI, sem necessidade de `detailedDisplay`);
- `ToolMessage`: `fullDetail && collapsible && detailedDisplay` usa completo; **`forceShowResult` mas não fullDetail (vista principal user-initiated/error) ainda usa resumo** (regressão de vista principal inalterada);
- cobrir `glob` (ou displayName legado de search), não apenas read/grep/list;
- saved history antigo: `detailedDisplay` extraído de parts; parts de registros antigos também estão lá → naturalmente full-detail; registros extremamente antigos sem parts degradam para resumo.

## 6. Migração e compatibilidade

- **settings.ui.compactMode / compactInline**: pode já existir na configuração do usuário. Estratégia: **remover do schema** do CLI (`settingsSchema.ts`), mas **manter `ui.compactMode` em `WEB_SHELL_SETTINGS` (`workspace-settings.ts:36`)** — o web-shell tem `CompactModeContext` independente (`packages/web-shell/client/App.tsx` lê `'ui.compactMode'`), a camada serve deve continuar repassando, senão quebra o web-shell (ver #12 / §7 #5). Verificado que o sistema de configurações é **tolerante** a chaves desconhecidas — `getSettingsFileKeyWarnings` (`settings.ts:250-309`, tratamento de chaves desconhecidas em `:290-306`, `debugLogger.warn` em `:303-305`) apenas registra em `debug`, sem erro nem bloqueio. Portanto a configuração CLI antiga do usuário pode ser lida com segurança (ignorada pelo CLI); a nova UI/API de configurações do CLI não lista mais esse item. **O lado CLI não mantém semântica retroativa** — o conceito de modo é removido por inteiro, manter também não teria efeito; a permanência do compact do lado web-shell é **avaliada em caso separado**.
- **Personalização de atalhos (aviso de migração)**: o código atual **não tem** mecanismo de override de keybinding configurável pelo usuário — `keyMatchers` (`keyMatchers.ts`) é sempre construído do hardcoded `defaultKeyBindings`, e `settingsSchema` não tem item de keybinding (apenas `vimMode`). Portanto **não existe** vínculo `toggleCompactMode` persistido pelo usuário que seria silenciosamente descartado; a detecção de migração na inicialização **não tem objeto para escanear, atualmente não aplicável**. Quando keybinding configurável pelo usuário for introduzido no futuro, complementar "detectar vínculo `toggleCompactMode` residual e avisar uma vez para revincular a `toggleTranscript`". **O PR atual apenas precisa** de release note avisando que a semântica de Ctrl+O mudou para transcript (`docs/users/reference/keyboard-shortcuts.md` já atualizado).
- **Telemetria**: pode-se alinhar ao Claude Code adicionando o evento `toggle_transcript` (opcional).

## 7. Fronteiras, riscos e itens em aberto

1. **Desempenho com histórico grande**: o transcript renderiza todo o histórico. A rolagem virtual (`VirtualizedList`) é limitada por viewport; distinguir dois tipos de limite — **remover apenas o truncamento de "altura de linha"** (para exibição, transcript remove), mas **manter o limite de "número de caracteres"** (para desempenho, sempre mantido). Note que o qwen-code **não tem** `SlicingMaxSizedBox` (isso é do gemini-cli); a proteção em nível de caracteres do lado qwen é o limiar de truncamento de saída de ferramenta `DEFAULT_TRUNCATE_TOOL_OUTPUT_THRESHOLD` (~25000). Na implementação, verificar fluidez de rolagem de histórico de dezenas de milhares de linhas.
2. **Coordenação de alt-screen (reutilizar componente existente já reduziu muito o risco)**: este esquema **reutiliza o `AlternateScreen.tsx` já entregue no main (PR #5627)** para entrar e sair da alt-screen, em vez de escrever manualmente o timing de `?1049h/l`, com risco significativamente menor que o design inicial. Dois pontos restantes a tratar: (a) **double-enter em modo VP** — com `useTerminalBuffer` ativo, o ink root já ocupa a alt-screen, é preciso passar `disabled={useVP}` para pular escapes (§4.2); (b) **redesenho de finalização ao sair** — ao sair, a tela principal passa por `refreshStatic()` uma vez para limpar e redesenhar (§4.4), e durante o transcript `refreshStatic` é pulado pela guarda `isTranscriptOpenRef`, evitando poluir o scrollback do normal-buffer. Note que o compact antigo fazia refreshStatic **a cada toggle**; este esquema faz apenas **uma vez ao fechar** o transcript, frequência muito menor. Ainda é preciso verificar em tmux / iTerm2 / VSCode / Apple Terminal.
3. **Semântica de segurança force (manter condições inline do #5661, não remover indevidamente)**: quando este PR adiciona o prefixo `fullDetail || isToolExpanded(id) ||` antes de `forceExpandAll`, é preciso **manter** os demais `hasConfirmingTool || hasSubagentPendingConfirmation || hasErrorTool || isEmbeddedShellFocused || isUserInitiated || hasTerminalSubagent`, assim como o gate `shouldCollapseResult` (incluindo guarda `isCollapsibleTool`) de `ToolMessage` — essas são as semânticas de segurança já posicionadas pelo #5661 de "erro/aguardando confirmação/iniciado pelo usuário/shell em foco/subagente deve ser exibido completamente" (§4.5); remoção indevida causaria regressão de "ferramenta com erro recolhida e não visível por completo". **Sem necessidade** de migrar para nenhum arquivo novo.
4. **Coordenação mouse / SGR**: atenção à potencial sobreposição com o problema registrado em [[project_vp_text_selection]] de "rastreamento de mouse SGR quebra seleção de texto nativa" — se habilitar a roda do mouse dentro do transcript precisa ser ponderado (habilitar roda vs manter seleção nativa do terminal). O tratamento de entrada/saída do mouse segue os mecanismos existentes do `AlternateScreen` e do root VP, sem necessidade de escrita manual adicional.
5. **web-shell (surface independente, fora do escopo de remoção deste PR)**: o web-shell tem `CompactModeContext` **independente** (`packages/web-shell/client/App.tsx` lê `'ui.compactMode'`), são duas implementações distintas do compact do CLI. Para não quebrá-lo, este PR **mantém `ui.compactMode` em `WEB_SHELL_SETTINGS`** (mesmo que o schema do CLI não defina mais essa chave, a camada serve ainda repassa, ver #12 / §6). Nesta fase o CLI faz apenas a limpeza de seus próprios textos e itens de configuração; **a permanência do compact do próprio web-shell é avaliada em caso separado**, fora do escopo de implementação deste design.
6. **Se incorporar Ctrl+S/`SHOW_MORE_LINES`**: nesta fase manter independente, evitando superfície de mudança descontrolada; listado como otimização opcional posterior.
7. **Semântica do aviso `(ctrl+o to expand)` (definida)**: o resumo do bloco de pensamento **sempre traz** esse aviso (orientando "entrar no transcript para ver o contexto completo", não "aqui está truncado"); a saída de ferramenta traz `+N lines` apenas quando truncada por restrição de altura. As condições de gatilho diferentes dos dois são **comportamento esperado**; os textos i18n devem refletir "ver contexto completo" em vez de "expandir conteúdo truncado", evitando induzir ao erro.

## 10. Intercâmbio com o documento de design existente #3100

O trabalho anterior [PR #3100](https://github.com/QwenLM/qwen-code/pull/3100) já produziu `docs/design/compact-mode/compact-mode-design.md` (284 linhas de análise competitiva). A relação deste esquema com ele:

1. **Adotamos o caminho que ele analisou, mas na época não seguiu**. O §4.4 do #3100 já comparava "screen-level transcript (Claude Code)" vs "component-level toggle (escolha do qwen na época)", apontando que o primeiro é "mais simples, consistência garantida". Este esquema é justamente a virada para screen-level transcript.
2. **Correção de um erro factual**: a tabela do #3100 afirmava que o Claude Code tem "Frozen snapshot: None (no concept)". Por forense do código-fonte mais recente do claude-code, **há de fato snapshot congelado** (`frozenTranscriptState` + `messages.slice(0, len)`). Este esquema adota o snapshot congelado conforme a implementação real, com fonte anotada no §3.2.
3. **Reutilização direta de suas conclusões**: o §4.3/§5.4 do #3100 defende "diálogos de confirmação usam camada de overlay independente, garantia estrutural de nunca serem ocultados". Com o transcript sendo tela independente, confirmações/erros da tela principal naturalmente não são afetados por ele, satisfazendo naturalmente essa demanda. E "erro/aguardando confirmação/shell em foco deve ser visível" é garantido no lado da vista principal pelas condições `forceExpandAll` do #5661 + `forceShowResult` (mantidos intactos por este PR, §4.5), sem necessidade de outro mecanismo.
4. **Dissolução da disputa de persistência**: o §4.2/§5.3 do #3100 ponderava repetidamente se o compact deveria ser persistido (settings vs escopo de sessão). Este esquema **remove o próprio modo**, não havendo mais estado a persistir; a disputa desaparece automaticamente; também sem necessidade da complexidade de "session override" do §5.3.
5. **Tratamento da documentação**: no PR de implementação, marcar `docs/design/compact-mode/` como "superseded by ctrl-o-detail-expand" (mantendo o histórico, adicionando uma linha de orientação), evitando dois designs mutuamente contraditórios coexistindo.

> Em uma frase: o #3100 é o design de "como fazer bem o modo compact"; este esquema é o design de "por que não ter modo compact e usar transcript em vez disso"; os dois são decisões iterativas sobre o mesmo problema.
